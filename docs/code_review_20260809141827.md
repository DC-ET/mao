## 二、新问题 / 遗留问题

### N-1【中】markAsRead 对「边路任务」发布目标错误，父任务 treeUnread 无法刷新（修复 #8 引入）

**位置**
- `SessionController.markAsRead`：`backend/src/main/java/cn/etarch/mao/session/controller/SessionController.java` 第 294~296 行

```java
sessionService.markAsRead(id);
treeSignalPublisher.publish(id);   // id 可能是边路任务
```

**问题**
前端确实会以**边路任务 id** 调用本端点：`stores/session.ts` 第 756 行 `markSideTaskRead(sideSessionId)` → `PUT /sessions/{sideSessionId}/read`。此时 `publish(id)` 会把该边路任务当作「父会话」聚合（其下无子边路），并以 `sideSessionId` 作为事件 sessionId 推送 `session_tree_status`。而前端 `updateSessionTreeSignals`（stores/session.ts L437）只在 `sessionEntities`（主会话实体表）中查找，边路任务不在其中 → **事件被静默丢弃**。

结果：用户读取（打开）边路任务后，该边路任务的 unread 已在 DB 清零，但**父会话的 `treeUnread` 保持 true**——聚焦模式「未读」档（priority 3）与左侧圆点残留，直到下次列表拉取或其他 tree 事件才纠正。

**修复建议**
按会话类型分流发布目标：

```java
Session s = sessionService.getSession(id);
if ("SIDE_TASK".equals(s.getSessionType()) && s.getParentSessionId() != null) {
    treeSignalPublisher.publish(s.getParentSessionId());
} else {
    treeSignalPublisher.publish(id);
}
```

### N-2【低-中】L-4 只修了边路任务「首条消息」路径，后续运行仍不发布 treeRunning

**位置**
- `StreamingWsHandler.handleSendMessage`（L539 附近 `updatePhase(sessionId,"RUNNING")` 处）
- `StreamingWsHandler` edit_and_resend（L832 附近）
- `CrashRecoveryRunner.recoverSession`（仅发 `session_status`，无 tree 发布）

**问题**
`handleCreateSideSession` 已补发（覆盖首条消息），但边路任务**后续消息**复用 `handleSendMessage` 置 RUNNING 时未调用 `treeSignalPublisher.publishIfSideTask(sessionId)`。且本轮前端 `focusSort.ts` 已开始消费 `treeRunning`/`treeFailed`（priority 1/2 判定），因此该缺口产生实际影响：边路任务「完成后再次运行」时，父任务 `treeRunning` 不会重新置 true → 父任务聚焦档位停留在自身 phase 档（如 IDLE=4），不升到「运行中」档（2）。

**修复建议**
在 `handleSendMessage`（及 edit_and_resend）对 `sessionType=SIDE_TASK` 的 RUNNING 更新点统一补 `treeSignalPublisher.publishIfSideTask(sessionId)`（与 create 路径一致）。

### N-3【低】stale sweep 纳入 WAITING_APPROVAL：默认配置安全，但存在边界误杀与慢自愈

**位置**
- `SessionService.findStaleRunningSessions`（L1224-1237）；`touchLastActivity`（L1211-1223）；`enterWaitingApproval`（L610-624）

**对用户问题的核实结论**
- `updatePhase` 每次相位变更都会 `setLastActivityAt(now)`（已核实）；`enterWaitingApproval` 也在登记时刷新 `last_activity_at`。
- 审批等待期间，心跳 `touchLastActivity` **只刷新 RUNNING/RESUMING，不刷新 WAITING_APPROVAL**；但等待时长受 `LocalToolExecutor` 工具超时约束（默认 900s=15min），远小于 `STALE_MINUTES=60`，**默认配置下不会误杀正常审批中的会话**（审批超时后 finally unregister → 相位离开 WAITING_APPROVAL）。
- 边界风险：若 `app.harness.local-tool-timeout-seconds` 配置 ≥ 3600s，正常等待审批的会话会在 60 分钟无活动后被 sweep 终止为 FAILED（误杀）。建议在文档/配置注释中明确该上限，或对 WAITING_APPROVAL 采用与 RUNNING 不同的处理。
- 慢自愈：服务重启后残留的 WAITING_APPROVAL 需等到 `last_activity_at` 超过 60min 才被清理，期间前端持续显示「待审批」（最长近 1 小时）。若希望更快恢复，可考虑在 `CrashRecoveryRunner` 中一并处理（重启时直接按 RUNNING 恢复或 FAILED 收尾），而非仅依赖时间阈值 sweep。

### N-4【低】L-3 瞬态竞态仍在：restore/enter 均在临界区外执行

**位置**
- `ApprovalRegistry.register` / `unregister`：`backend/src/main/java/cn/etarch/mao/harness/approval/ApprovalRegistry.java` L52-102

**问题**
计数增减在 `synchronized(ids)` 内，但 `enterWaitingApproval` / `restoreRunningAfterApproval` 在锁外执行。极端交错（如 r2 先 register 计数=1，随后 r1 的 unregister 归零触发 restore）时，restore 可能把 r2 刚置的 `WAITING_APPROVAL` 打回 `RUNNING`，出现「计数>0 但 phase=RUNNING」的瞬态；反之亦可能。最终随最后一个请求 unregister 自愈，但期间聚焦列表状态标签短暂失准（显示「运行中」而非「待审批」）。修复 M-3 时未同时处理该点。

**修复建议**
将 `enterWaitingApproval` / `restoreRunningAfterApproval` 的调用也纳入同一 `synchronized(ids)` 临界区（或 register 置 WAITING_APPROVAL 后重查计数确认），保证「计数非零 ⇒ phase=WAITING_APPROVAL」不变量在临界区内成立。

### N-5【低】M-4 待回答侧仍未修复：主会话 ask_user_questions 时聚焦档位不达 0

**位置**
- 后端：`ToolDispatcher` 的 ask_user_questions 路径（register 后仅对边路任务发布 tree 信号）；`ApprovalRegistry.publishPhase` 的 `session_status` payload 不带 `pendingQuestionCount`
- 前端：`stores/session.ts` `appendAskQuestion`/`clearAskQuestions` 只维护独立 map `sessionPendingQuestions`，不更新实体 `pendingQuestionCount`；`focusSort.ts` 未并入该 map

**问题**
主会话发起 ask_user_questions 时 phase 保持 RUNNING（无相位事件），服务端也没有实时计数事件 → 聚焦排序按 phase 得档位 2（运行中）而非 0（待回答），状态标签显示「运行中」而非「待回答」。列表刷新后（`applySessionListSignals` 填充 `pendingQuestionCount`）才恢复正确。审批侧已通过 phase=WAITING_APPROVAL 事件解决，待回答侧仍依赖刷新。

**修复建议（任选）**
1. 后端在 ask_user_questions 的 register 路径对主会话也发布 `session_tree_status`（或把 `publishIfSideTask` 推广为「边路→父 / 主会话→自身」双发布）；
2. 前端在 `appendAskQuestion`/`clearAskQuestions` 时同步写回实体 `pendingQuestionCount`。

### N-6【提示】register 在 enterWaitingApproval 失败时仍保留 requestId（自愈，影响极小）

**位置**
- `ApprovalRegistry.register`：先 `ids.add(requestId)`，后 `enterWaitingApproval` 可能返回 false（会话已终态）

**问题**
终态会话的待审批计数短暂 +1，列表 VO 的 `pendingApprovalCount` 对 FAILED/CANCELLED 会话显示 1；工具结束（取消路径 failAllForSession 已保证 future 完成）后 unregister 自愈。纯展示层抖动，可接受；如要消除可在 `entered=false` 时回滚 `ids.remove(requestId)`。
