## 发现问题

### [P2] LOCAL async 在桌面端未连接时仍返回「已提交」——`backend-ts/src/harness/tool/tool-dispatcher.ts:109-123`

同步 LOCAL 工具调用会先经 `LocalToolExecutor.execute()` 检查 `isConnected`，未连接时**立即**返回：

```json
{"error":"Local client is not connected. Please ensure the desktop app is running and connected."}
```

但 async 分支在提交后台任务后直接返回成功：

```109:123:backend-ts/src/harness/tool/tool-dispatcher.ts
      if (toolName === 'shell' && this.backgroundTaskManager) {
        const forwarded = prepareLocalShellAsync(argumentsJson, sessionId);
        if (forwarded) {
          const taskId = this.backgroundTaskManager.submit(sessionId, () =>
            this.localToolExecutor.execute(
              sessionId, toolName, forwarded.argumentsJson, workspace, decision.needApproval, decision.dangerReason,
            ),
          );
          return JSON.stringify({
            async: true,
            task_id: taskId,
            session_id: forwarded.sessionId,
            output_file: forwarded.outputFile,
            message: '命令已提交到后台执行。',
          });
        }
      }
```

**影响场景**：用户关闭 Electron、断线或 LOCAL 客户端未就绪时，Agent 当轮收到 `async:true` 与 `task_id`，误以为命令已下发；实际要到下一轮消费后台结果才能看到连接失败。与同步路径的错误反馈不一致，可能导致 Agent 基于错误前提继续编排（例如假定输出文件已生成）。

**建议**：在 `submit` 之前调用 `localToolSessionRegistry.isConnected(sessionId)`（或等价检查），未连接时直接返回与同步路径一致的错误 JSON，不要返回 `async:true`。

### [P2] LOCAL async 在 shell 会话建立前就返回 `session_id`，与云端语义不一致——`backend-ts/src/harness/tool/tool-dispatcher.ts` / `backend-ts/src/harness/tool/impl/shell-session-tool.ts`

云端 `ShellSessionTool` 在返回 async 响应**之前**已完成：`getOrCreate` → 注入 token →（必要时）`cd` → **`writeStdin(command)`**，后台任务只负责 `readUntilMarker`：

```127:143:backend-ts/src/harness/tool/impl/shell-session-tool.ts
    const marker = this.newMarker();
    session.writeStdin(command + '\necho ' + marker + ' $?\n');
    session.incrementCommandCount();
    session.touch();
    if (isAsync) {
      const taskId = this.backgroundTaskManager.submit(conversationId, async () => {
        const r = await this.outputManager.readUntilMarker(session, marker, yieldTimeMs);
        if (!keepSession) this.sessionManager.close(session.sessionId);
        return r.output;
      });
      return toJson({
        async: true,
        task_id: taskId,
        session_id: session.sessionId,
        ...
      });
    }
```

LOCAL async 则在 `ToolDispatcher` 层立即返回，真正的 `getOrCreate` / 写命令发生在后台任务经 WebSocket 到达 Electron 之后，存在整段 WS 往返的窗口期。

**影响场景**：

1. **session 竞态**：Agent 拿到 `session_id` 后立刻发起第二条 shell（同步 `exec` 或 `write_stdin`），可能与尚未开始或正在执行的第一条命令并发写入同一 bash stdin，造成命令交错。
2. **`write_stdin` 失败**：在后台任务创建会话之前对返回的 `session_id` 调用 `write_stdin`，会得到「会话不存在或已关闭」（`localShell.cjs:401-402`），而云端此时会话已存在。

**建议**：对齐云端——在 `submit` 之前先经 `localToolExecutor` 完成会话创建与命令下发（或拆出「prepare」RPC），后台任务仅等待输出；至少在文档/工具描述中明确「async 返回的 `session_id` 在 LOCAL 模式下不可立即复用」，并在实现上避免在 prepare 完成前暴露可复用 `session_id`。

### [P3] 旧版 `timeout`（秒）参数不再生效——`desktop/electron/localShell.cjs:373`

旧 `main.cjs` 对无 `session_id` 的一次性 `exec` 支持 `timeout`（默认 60 秒），通过 `child_process.exec` 的 `timeout` 选项强制结束进程。

新实现统一走持久 bash + marker，只识别 `yield_time_ms`（默认 300000 ms），未处理 `args.timeout`：

```373:373:desktop/electron/localShell.cjs
    const yieldTimeMs = args.yield_time_ms != null ? asInt(args.yield_time_ms, DEFAULT_EXEC_YIELD_MS) : DEFAULT_EXEC_YIELD_MS
```

**影响场景**：若 Agent 或旧调用方仍传 `{ "command": "...", "timeout": 60 }`（设计文档 `docs/shell-session-design.md` 中仍有 `timeout` 字段描述），实际等待上限变为 5 分钟而非 60 秒，长耗时命令占用资源更久。云端正式 schema 以 `yield_time_ms` 为准，影响面有限。

**建议**：在 `handleExec` 中兼容 `timeout`（秒）→ 映射为 `yield_time_ms`，或至少在参数校验时给出明确错误提示。

## 未列为缺陷的变更（供参考）

| 项 | 说明 |
|----|------|
| `session_id` 需配合 `keep_session:true` 才能跨命令复用 | 与云端 `ShellSessionTool` 一致，属有意对齐；旧 LOCAL「仅凭 `session_id` 持久化」行为会改变，但符合工具 schema |
| `list` 响应去掉 `count` / `command_count` | 与云端 `handleList` 返回结构一致 |
| LOCAL async 需审批时 Agent 主循环不阻塞 | 命令仍须在 Electron `ensureShellApproval` 通过后才执行，安全门未绕过；属 async 语义与同步的差异 |
| 后台任务结果格式 | LOCAL 注入完整 JSON 字符串，云端注入纯 output 文本；LOCAL 同步路径本就是 JSON，可接受 |

## 总体评价

`localShell.cjs` 重构质量较好：stderr 合并、真实 `exit_code`、`keep_session`、进程组回收、token 刷新、输出落盘等核心行为有单测支撑，与云端设计方向一致。

主要风险集中在 **后端 LOCAL async 路由层**：与同步路径相比缺少连接检查，且 async 响应时机早于 shell 实际就绪，可能在断线或快速连续调用场景下产生错误反馈或会话竞态。建议优先修复 P2 两项后再合入。
