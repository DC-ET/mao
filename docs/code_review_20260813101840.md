## 中等严重程度

### 1. 压缩已经持久化后发生统计或锚点异常，首轮会回退到压缩前的旧请求

**代码位置**

- `backend/src/main/java/cn/etarch/mao/harness/core/SessionCompactionOrchestrator.java:65-108`
- `backend/src/main/java/cn/etarch/mao/harness/core/HarnessService.java:407-418`

**问题说明**

`SessionCompactionOrchestrator.compact()` 在 CAS 持久化成功后，会先重载并应用最新摘要，然后继续执行 token 估算、清理/更新上下文锚点以及写入 `session_compaction_event`。这些后置步骤中的任意一个抛出运行时异常，都会继续向调用方抛出异常。

请求开始路径的 `HarnessService` 捕获该异常后，无条件执行：

```java
context.setPreparedRequest(normalRequest);
```

这里的 `normalRequest` 是压缩前构建的旧请求。此时压缩摘要可能已经成功持久化并应用到 `context`，但首轮实际仍会发送旧的完整历史；数据库中的压缩边界也已经前移。结果是：

- 本轮没有使用刚刚生效的交接摘要；
- 可能再次发送接近窗口上限的完整历史并触发模型上下文超限；
- 内存上下文、持久化压缩边界与实际发送请求在该轮不一致。

可触发此路径的异常包括但不限于：

- `activeContextCalculator.estimateRequestTokens()` 或 `promptEngine.buildRequest()` 异常；
- `clearContextAnchor()` / `updateContextTokens()` 数据库异常；
- `sessionCompactionEventService.record()` 写入统计事件异常。

**修复建议**

不要把 orchestrator 的所有异常都等价视为“压缩未生效”。建议让 orchestrator 返回结构化状态，至少区分：

1. 压缩尚未持久化，可安全复用旧请求；
2. 压缩已经持久化或已重载其他并发结果，必须基于当前 `context` 重建请求；
3. 确定性超窗或取消，需要终止执行。

在请求开始路径中，只要 durable boundary 已经变化或 `applyHistory` 已执行，就应在异常降级时调用 `buildNormalRequest(context)`，不能回退到旧 `normalRequest`。统计事件和 context token 更新也宜作为可降级的后置操作，避免其失败改变已成功压缩后的模型请求语义。
