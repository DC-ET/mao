## 问题列表

### [低] 1. requireFileOwner 的 403 分支无路由层测试覆盖

- 位置：`backend-ts/src/file/file.routes.spec.ts`（`listsWorkspaceAndGitJsonEndpoints`）
- 问题：本轮在 download/preview/delete 三个端点新增属主校验，但路由层测试只覆盖了「文件不存在 → 404」（`GET /v1/files/99/download`）与上传流程，**未覆盖「他人文件 → 403 拒绝」的用例**；`requireFileOwner` 的逻辑仅靠人工核查。第 3 轮报告的覆盖缺口（[低]6）在 service 层已补齐，routes 层仍空。
- 修复建议：在 `file.routes.spec.ts` 中 mock `fileService.getFile` 返回 `uploaderId: 8`（与 hook 注入的 `req.userId = 7` 不同），断言 download / preview / DELETE 三个端点返回 403；再补一条 `uploaderId === 7` 时正常放行的正向用例。

### [低] 2. 上传完成但输入区 disabled 时，已上传文件成为不可清理的 runtime 孤儿（[低]3 修复后的残余闭环缺口）

- 位置：`desktop/src/components/chat/ChatInput.vue`（`uploadFileToRuntime` 中 `props.disabled || !editor.value` 分支，约 926-931 行）
- 问题：该分支现在会移除条目并提示「已上传，但输入框不可用，未添加到消息中」——静默丢失已解决。但文件已写入 runtime incoming，且被 `listFiles` 过滤、不出现在任何界面列表中，用户**没有途径撤销/删除该文件**，只能等会话删除时级联清理。反复「Agent 运行中上传」会累积磁盘占用（与第 3 轮 [低]8 在途上传同类，只是不再静默）。
- 修复建议：`uploadChatFile` 返回的 `UploadedChatFile` 含 `id`，该分支可调用 `DELETE /v1/files/:id` 清理刚上传的文件再提示；或在输入区恢复可用时补插引用（与第 3 轮 [低]3 建议一致）。

### [信息] 2. 「保留 %2e 字面量」措辞与实际行为（%2e → . 解码）需确认意图

- 位置：`backend-ts/src/file/file.service.ts`（`sanitizeBaseName`，约 267-277 行）
- 说明：需求描述为「保留 %2e 字面量」，但实现为 `.replace(/%2e/gi, '.')`（解码为点号），`100%2e5.xlsx` 实际得到 `100.5.xlsx`；新增测试 `sanitizeHandlesUrlEncodedTraversalAndKeepsNormalNames` 也断言 `normal.originalName === '100.5.xlsx'`。三者（需求示例 `100%2e5.xlsx → 100.5.xlsx`、实现、测试）一致，仅「保留字面量」的措辞有歧义。若意图确为「%2e 单字面量按点号解码、仅阻断 %2e%2e 穿越组合」，则当前实现正确；若意图是保持 `100%2e5.xlsx` 原样，则实现与测试需同步修改。安全上两种选择均无风险（storedName 只取 uuid+白名单扩展名，originalName 仅用于展示/Content-Disposition 且已有 fallback 清洗）。
- 建议：确认产品意图；如为解码，建议把注释/需求措辞改为「%2e 按点号解码（不构成穿越），%2e%2e 穿越序列归一为 .. 后由 safeExtension 白名单兜底」。
