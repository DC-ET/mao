## 二、本轮新发现问题

### 1. [中] `ask_user_questions_cancelled` → `resolveAsk(...,'fail')` 副作用：正常完成的回合被覆盖为 CANCELLED 并返回 EXIT.QUESTION

- 位置：`src/tui/ink-renderer.ts` `onEvent('ask_user_questions_cancelled')`；`src/session/session-runner.ts` `handleQuestions` fail 分支
- 触发条件：服务端主动取消问答（agent 自行结束回合、问答超时或被替换）时，`resolveAsk(evt.requestId, 'fail')` 使挂起的 askHandler promise 以 `'fail'` 兑现 → `handleQuestions` 走 fail 分支：`questionFailedFlag = true` + **额外发送一次 `cancel`** + `waitCancelThenSettle`。
- 影响：① `buildResult()` 中 `if (this.questionFailedFlag) status = 'CANCELLED'` 会把本可能 `COMPLETED` 的回合强制改成 `CANCELLED`，`exitCodeFor` 返回 `EXIT.QUESTION` —— 服务端取消问答 ≠ 用户取消，退出码语义错误；② 服务端已取消问答后仍补发 cancel，若此时 agent 仍在执行（仅取消了问答环节）会误中止整个执行。
- 第二轮报告已预告「需在 handleQuestions 侧对 cancelled 后的 result 发送做防护」，当前实现未覆盖。
- 建议：cancelled 场景以不触发 fail 分支的方式收尾 —— 例如 `resolveAsk` 传独立值（如 `'cancelled'`），`handleQuestions` 对 cancelled 的 requestId 静默返回（不置 questionFailedFlag、不发 cancel）；或在 resolve 前将 requestId 登记为「已取消」，handleQuestions 检查后跳过。

### 2. [中] `/clear` 不清 `liveAnnounce`；且 Ink `<Static>` 下旧回合无法真正清屏（第二轮 issue 8 遗留）

- 位置：`src/tui/ink-renderer.ts` `mount()` 的 `clearAll` 实现
- 问题：`clearAll()` 重置 staticRounds/historyLines/liveToolCalls/liveError/liveWarnings/segmentRaw/announceBuffer，**遗漏 `liveAnnounce`** —— `/clear` 后输入区上方仍残留「已排队（第 N 条）」「再次 Ctrl+C 退出」等 announce；且 liveAnnounce 只在 `finish()` 清空，若清屏后不再发消息，残留会一直显示到退出。
- 另外：Ink `<Static>` 已写入终端 scrollback 的旧回合无法通过清空数组清除，`/clear` 行为与 `/help` 文案「清屏」不符（第二轮 issue 8 未修）。
- 建议：`clearAll()` 补 `this.liveAnnounce = []`；如需真实清屏，可输出 `\x1b[2J\x1b[H` 后重新 flush，或明确降级语义并同步更新 `/help` 文案。

### 3. [低] modal 单槽设计：ask modal 打开时 `requestApproval` 直接覆盖，ask resolver 挂起泄漏

- 位置：`src/tui/ink-renderer.ts` `requestApproval()`（直接 `this.modal = {type:'approval',...}` 覆盖）
- 触发条件：LOCAL 模式下，ask modal 等待用户回答期间又有 `tool_execute` 需要审批（ask 事件与 tool 审批可并发到达），approval modal 覆盖 ask modal；被覆盖的 ask requestId 的 resolver 永不 resolve，`handleQuestions` promise 挂起，直到服务端 `ask_user_questions_cancelled` 才回收（且按问题 1 的路径产生错误退出码副作用）。
- 建议：`requestApproval` 前若 `this.modal?.type === 'ask'`，先 `resolveAsk(当前 requestId, 'fail')` 关闭旧问答再覆盖；反之 `ask_user_questions` 到来时若 approval modal 打开，同样先 `resolveApproval` 或排队。

### 4. [低] `firstPrompt` 以 `\` 结尾时，repl 层 buffer 续行内容在输入区不可见（双轨 buffer 未完全统一）

- 位置：`src/repl/repl.ts` `handleSubmit` 续行分支（`setContinuation(true)`）；`src/tui/ink-input.tsx` 仅展示自身 `bufferRef`
- 用户手动输入的多行续行走 InkInput 内部 buffer，可见可编辑（修复 7 ✓）；但 `cfg.prompt`（`firstPrompt`）以 `\` 结尾时触发的是 repl 层 `buffer`，InkInput 对此一无所知 —— 提示符虽切换为「… 」，但已缓冲的首行内容无任何展示，用户看不到、也无法编辑/丢弃。
- 建议：统一为单轨 buffer（InkInput 与 repl 共享），或在 repl 层续行时经 `tuiHandle` 将缓冲内容回显到输入区。

### 5. [低] `handleSubmit`/`handleSlash` 无 try/catch：`/model` 网络异常 → unhandledRejection 进程崩溃

- 位置：`src/repl/repl.ts` `handleSubmit`（`onSubmit: (text) => { void handleSubmit(text); }`）
- `resolveModel` 内 `rest.listActiveModels()` 等网络调用可能抛错 → `handleSlash` 抛出 → `handleSubmit` reject → `void` 无人捕获 → Node ≥15 默认 unhandledRejection 终止进程（无友好错误提示；终端由 Ink signal-exit 钩子恢复，但 CLI 直接退出，队列/会话清理被跳过）。
- 该缺陷旧实现同样存在（`onLine → handleSubmit`），非本轮新引入，但迁移后仍在，建议顺手修复：`handleSubmit` 外层 try/catch 或 `handleSlash` 内兜底。

### 6. [低] 死代码未删净（第二轮 issue 9 仅删文件级死代码）

- `src/tui/types.ts`：`InkTuiHandle.setDraft/pushStaticRound/pushHistoryLine` 无任何调用方；`TuiAppProps.draft`/`onDraftChange`/`onSlashClear` 无消费方（app.tsx 未传 `onDraftChange`、`draft` 未传给 InkInput，InkInput 自管 draft）；`InkRendererLike` 接口整体无使用方。
- `src/repl/repl.ts`：`ReplOptions.welcomeLines/historyLines/modelNames/asciiOnly/onInputReady` 传入后均未消费（InkTuiRenderer 构造时已接收 welcomeLines、`setHistoryLines` 单独设置）。
- `src/render/repl-renderer.ts` + `src/ui/composer.ts`：生产路径已不再引用（仅测试文件引用），属遗留死代码。
- 建议：后续清理，避免维护误解。
