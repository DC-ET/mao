## 结论总览

核心链路实现质量良好：消息合并规则（连续 tool 合并 / tool+user 合并 / 连续 assistant 合并 / system 拆分）符合 Anthropic 严格交替与 tool_result 置前约束；SSE 事件映射、usage 与 stop_reason 归一、重试/取消/超时/空响应语义与 OpenAI 适配器一致；AgentLoop 的 toolCalls 按 index/id 聚合与 `input_json_delta` 分片下发方式兼容（多工具并行调用亦正确）；Facade 路由与 create-app 组装正确；无输入消息被协议转换污染的问题（图片 URL→base64 的原地回写系复制自 OpenAI 适配器的存量行为，见信息项 I-1）。

发现 1 个中危功能遗漏、3 个低危边界/一致性问题，列表如下。

## 中危

### M-1 飞书群聊溢出摘要（GroupContextSummarizer）未接入协议路由，默认/会话模型为 anthropic 时摘要静默失效

- 位置：`backend-ts/src/create-app.ts:849`（`new GroupContextSummarizer(modelChatClient, ...)`）、`backend-ts/src/feishu/group-context-summarizer.ts:13-33`
- 现象：本次改造让 `ModelService` 按 provider 路由 `LlmChatClient`，但既有消费方 `GroupContextSummarizer` 仍直接持有硬编码 OpenAI 协议的 `modelChatClient`（POST `{baseUrl}/chat/completions`）。当系统默认模型或会话绑定模型为 provider=anthropic 时（这正是本次需求的主场景），摘要请求会打到 Anthropic 渠道的 `/chat/completions`（404），`summarize` 捕获后返回 null——摘要功能静默失效，无任何错误暴露，用户侧表现为"接了 Anthropic 模型后群聊溢出摘要永远不生成"。
- 附带问题：`create-app.ts:854-858` 的 `resolveModelConfig` 返回的 config 未携带 `provider` 字段，即使后续想复用 `chatClientFor` 式路由也无法命中。
- 修复建议：为该处组装提供按 provider 路由的 client（与 `ModelService.chatClientFor` 同策略），并在 `resolveModelConfig` 返回值中补上 `provider: model.provider ?? undefined`。设计文档 §4.5 接线点清单遗漏了此消费方，建议同步补充。

## 低危

### L-1 AnthropicChatClient 重复实现消息转换，且已与主 Adapter 行为分叉

- 位置：`backend-ts/src/model/anthropic-chat.client.ts:22-45`（消息转换）、`:89-101`（stop_reason 映射）
- 现象：system 拆分/降级逻辑独立实现了一份，与 `convertMessages` 已存在行为差异：非首条 system 在主 Adapter 中会 `pushBlocks('user', ...)` 并入相邻 user 消息（保证严格交替），在 Client 中无条件独立 push 一条 user 消息——若输入为 `[user, system, ...]` 或连续 system，会产出连续 user 消息，Anthropic 将返回 400。当前调用链不可达（连通性测试固定发送单条 `user:'Hi'`，mid-system 探测已对 anthropic 跳过），故未构成线上 bug，但两份实现会随演进继续分叉。另：`max_tokens: 1024` 与主 Adapter 的 16384 常量不一致（连通性测试场景可接受，建议注释说明）。
- 修复建议：复用 `anthropic-llm-adapter.ts` 已导出的纯函数 `convertMessages` 与 `mapStopReason`（Client 可从 harness/llm 引入），删除本地重复实现。

### L-2 assistant.toolCalls 中 name 为空的项被跳过，可能产生悬空 tool_result

- 位置：`backend-ts/src/harness/llm/anthropic-llm-adapter.ts:757-771`（`if (!tc.function?.name) continue;`）
- 现象：若历史消息中某 toolCall 缺失 function.name，该 tool_use block 被静默丢弃，但与之配对的 `role:'tool'` 消息仍会转成 `tool_result`，引用不存在的 tool_use_id → Anthropic 400（"unexpected_tool_use_id"类错误），随后整轮流重试直至耗尽。改为丢弃整条 assistant 消息同样会破坏配对；更稳妥的兜底是保留 `input:{}` 的占位 tool_use。
- 当前可达性：正常流式聚合与持久化恢复的 toolCalls 均含 name，触发概率低，属健壮性问题。

### L-3 blockTypes Map 只写不读（死代码）

- 位置：`backend-ts/src/harness/llm/anthropic-llm-adapter.ts:257`（声明）、`:279`（set）、`:332`（delete）
- 现象：`blockTypes` 记录每个 content block 的类型但从未读取；若本意是在 `input_json_delta` 时校验 index 对应块类型，则校验缺失；若无需校验则应删除。不影响功能，建议清理以免误导后续维护者以为存在块类型校验。

## 信息项（非本次引入或经核实不构成 bug，供参考）

- I-1 图片预处理对调用方消息的原地改写：`buildRequestBody` 仅浅拷贝消息数组，`convertImageUrlsToBase64` 通过 `setImageUrl` 将 image part 的 URL 原地改写为 base64 data URI（与 `openai-llm-adapter.ts` 行为一致），意味着 AgentLoop `context.messages` 中的历史消息会被改写（图片 URL → base64 大字符串），随消息持久化路径进入 DB。系复制存量行为，不构成本次回归；骨架复制的现状放大了此类模式，建议后续抽取共享骨架时统一收敛（设计文档 §八.4 已有规划）。
- I-2 tool 消息 content 含图片 part 的转换产物：tool 分支生成 `[tool_result, image, ...]`（`anthropic-llm-adapter.ts:766-774`）。经查证 Anthropic 官方约束为"user 消息必须以匹配数量的 tool_result 开头"（错误消息 "Did not find N tool_result block(s) at the beginning of this message"），tool_result 之后的 image/text block 是允许的，故该产物合法、不构成 bug。但该路径当前实际不可达（主链路工具结果图片走 attachment + toolMediaInjector 注入 user 消息），如后续放宽 tool 消息图片来源，建议补一条请求体级单测固化行为。
- I-3 `max_tokens: 16384` 常量对输出上限较小（4096）的模型会直接 400，文档 §七 已声明该取舍；真实渠道联调时请优先覆盖小模型。
- I-4 `isRetryableStatus` 包含 404（模型名/路径错误将重试 10 次才报错）：与 OpenAI 适配器一致的存量语义，非本次引入。
- I-5 前端下拉 `clearable` 清空后 `form.provider` 为 `''`，`Facade.pick`/`chatClientFor` 均将空串回落 OpenAI 兼容实现，行为正确；`openai-responses` 选项虽 disabled，但 `allow-create` 下手动输入同值仍可创建并保存，路由会安全回落（无实现），与设计一致。
