## 二、本轮发现的新问题

### N-1（低危）占位 tool_use 的 `name: ''` 可能被 Anthropic 拒绝（400 invalid_request_error）

- 位置：`backend-ts/src/harness/llm/anthropic-llm-adapter.ts` `convertMessages` assistant 分支（`name: tc.function?.name ?? ''`）
- 现象：L-2 的修复消除了「悬空 tool_result」这一必然 400 的失败模式，但兜底产物是 `tool_use` block 的 `name` 为空字符串。Anthropic Messages API 对 `tool_use.name` 要求为非空的有效工具名（需与 `tools` 列表匹配），空字符串 `name` 大概率仍触发 400（`tools.N.name: String should have at least 1 character` 类校验），只是从「配对断裂」变成「name 非法」。相比上一版是净改善（配对语义保留、错误信息更明确），但该兜底在真实 anthropic 渠道上可能仍未通过校验。
- 触发条件：历史消息中 toolCall 缺失 function.name（正常流式聚合/持久化恢复不会出现，仍属防御路径）。
- 建议：占位 tool_use 的 name 无法保证合法时，可考虑（a）用同消息其他 toolCall 的真实名字兜底，或（b）整体丢弃该 assistant 消息及其后所有配对 tool 消息（保持序列一致性），并补一条 convertMessages 单测固化 `name` 缺失行为。若产品决定接受 400（概率极低的防御路径），现状亦可，建议在注释中说明该取舍。

### N-2（低危）`routeChatClient` 三处路由逻辑重复，且 anthropic 协议 code 散落多处

- 位置：`create-app.ts:383-387`（`routeChatClient`）、`model/model.service.ts:51-55`（`chatClientFor`）、`harness/llm/llm-adapter-facade.ts:17-20`（`pick`）
- 现象：provider 路由的「trim + lowercase + 未命中回落」策略现在有三个手写副本。本次修复正确保持了一致，但后续新增协议（如 `openai-responses` 落地）时需同步改 3 处 Map 注入 + 3 处路由函数，漏改任意一处即产生协议路由不一致（例如摘要路由到了错误客户端）。属于可维护性隐患而非当前功能 bug。
- 建议：后续可将「provider → client/adapter」的路由收敛为一个共享工厂（如 `createProviderRouter(map, fallback)` 返回统一路由函数），三处共用；与本需求无冲突，建议随下一迭代处理。
