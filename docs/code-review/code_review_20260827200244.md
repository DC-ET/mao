## 重点关注项核对

### 1. `isBusyOrRecovering` 是否会误判终态 / 首次消息拒之门外
**结论：否。**

- 会话创建默认 `phase: 'IDLE'`（`session.service.ts:103`），首次消息 `isBusyOrRecovering` 返回 `false`，走直接执行路径，**不会**入队。不存在「首次消息永远入队」。
- 每条执行路径进入 `runExecution` 前都先 `updatePhase('RUNNING')`，执行收尾经 `taskTerminal.finishExecution` 把 phase 置为终态（COMPLETED/FAILED/CANCELLED），随后 `busy.delete`。因此「忙判定」在正常完成后为 `false`，**不会**把终态会话误判为忙。
- `runExecution` 内 `updatePhase(RUNNING)` 在三处收尾（正常 / cancel / catch）都由 `onExecutionFinished` 触发 `finishExecution` 转入终态，不存在 phase 永久停留 `RUNNING` 的路径。

### 2. 加锁前 `isBusyOrRecovering` 的竞态窗口
**结论：覆盖到位。**

- `onMessage` 空闲路径：`withLock` 内**先** `busy.add(sessionId)` **再** `executeDirect`（后者才 `updatePhase(RUNNING)`）。`busy.add` 早于 `updatePhase(RUNNING)`，所以在「phase 尚未置 RUNNING」的窗口内，内存 `busy` 已生效。
- 并发第二/第三条 `onMessage`：外层预检可能通过（空闲），但进入 `withLock` 后内层 `isBusyOrRecovering` 看到 `busy` 已置位，转去入队。两段检查（预检 + 锁内双检 + `busy` 集合）足以杜绝同会话并发直接执行。
- `drainNext` 同样在锁内 `busy.add` 后才 `executeQueued`，时序一致。

### 3. queueId 交叉核对与 string value 解析
**结论：正确。** 见 H1/L1 验证。

### 4. hydrate 等 `crash.run()` 完成后消费
**结论：部分兜住，但存在「恢复消费的是同一条被复位消息」的边界隐患（见 M2）。**
`drainNext` 的 `isBusyOrRecovering` 能兜住 crash recovery 进行期（phase=RUNNING/RESUMING）的抢跑；但**恢复收尾钩子** `onExecutionFinished` 里再次调用 `drainNextIfPending` 时 phase 已转终态，会消费同一条被 `hydrate` 复位到 QUEUED 的、且已被 crash recovery 重放的队列行。

### 5. type-safety 闭合
**结论：正确。**
`FeishuTaskQueuePort`（enqueue/setCardMessageId/claimNext/complete/hasPending）与 `FeishuCardActionPort`（findByCardMessageId/jumpToFront/cancel）定义齐全；`FeishuCardActionService` 与 `AgentFeishuInboundHandler` 的消费面与这两个端口一一对应；`FeishuTaskQueueService` 同时实现两端口；`create-app.ts` 的 `queueService`、`interrupt`、`patchCard` 接线正确。`npm run build` 通过。

### 6. 重复消费 / 漏消费 / 死循环 / 队列卡死
- 死循环：`drainNext` 仅在 `claimed===true` 时递归，队列空时 `claimNext` 返回 `null` → 停止，无无限递归。fire-and-forget promise 链，无栈溢出。
- 漏消费：直接路径 `executeDirect` 结束后 `onMessage` 必然触发一次 `drainNext`；入队路径由请求方返回后由当前执行方接力，链路闭环。
- 队列卡死：`executeQueued` 的 `finally` 无条件 `complete(row.id)`，`complete` 失败仅告警（清理失败时行可能残留，但 `resetRunningToQueued` 兜底复位）。L2 已修复。
- **一个新增边界**：见下方 M2。

## 本轮发现的问题

### 中（M）

#### M2. 崩溃发生在「消费队列消息执行中」时，该消息可能被重复执行（崩溃恢复重放 + 队列再消费）

**位置**
- `create-app.ts:1434-1443`：`crash.run().then(... hydrate())` 与 `CrashRecoveryRunner.onExecutionFinished` 钩子（`create-app.ts:1427-1430`）均在消费队列。
- `inbound-queue.service.ts:82-87`：`hydrate()` 无条件把 `status='RUNNING'` 的队列行复位为 `QUEUED`。
- `crash-recovery-runner.ts:recoverSession`：崩溃续跑会把该会话的完整竞态（含最后一条用户消息）重放一次。

**问题场景**
1. 会话正通过队列执行消息 B：`drainNext` → `claimNext` 把 B 置为 `RUNNING`，`executeQueued(B)` → `saveUserMessage(B)` → `prepareMessage(B)` → `execute(B)`（此刻崩溃）。
2. 重启：`hydrate()` 把 B（`RUNNING`）复位为 `QUEUED`。`CrashRecoveryRunner` 收集到该会话 `phase='RUNNING'`，续跑重放「B 的处理」（`recoverSession` 不清空 B 这条用户消息，`agentLoop.execute` 会对从 B 起的未完成轮次重新生成回复）。
3. `recoverSession` 收尾 `finishExecution` 置 phase 为终态，随后触发 `onExecutionFinished` 钩子 → `drainNextIfPending(sessionId)`。此刻 `isBusyOrRecovering` 为 `true`→ 已转终态 → `false`，于是 `claimNext` 认领到复位后的 B（`QUEUED`），`executeQueued(B)` 再次 `saveUserMessage(B)` 并 `execute(B)`。

结果：B 的用户消息被写入两次、Agent 对其生成两次回复（一次来自崩溃续跑，一次来自队列再消费）。

**影响**
崩溃恢复场景下的重复响应 / 重复上下文写入。飞书侧会有重复回答，且会话上下文被污染。

**触发概率 / 边界说明**
仅当「崩溃恰好发生在某条**队列消息**正在执行、且其用户消息已落库」时触发。若崩溃发生在直接路径或队列为空时无此问题。由于 `saveUserMessage` 在 `execute` 之前、且崩溃恢复会从该用户消息重放，该组合在并发执行队列消息时确实存在。

**建议（供参考，勿直接改）**
- 方案 A：`hydrate()` 复位 `RUNNING → QUEUED` 时，对「会被 CrashRecovery 重放的会话」不要复位其当前执行行 —— 但队列表无法直接得知崩溃恢复是否覆盖该行。
- 方案 B：让崩溃恢复的 `recoverSession` 在执行前把该会话的 `RUNNING` 队列行**删除**（该消息本就由恢复重放），随后它在 `onExecutionFinished` 时只消费真正的后续 `QUEUED` 行，从而避免再消费同一条。
- 方案 C：`drainNextIfPending` 消费前增加「跳过本条消息 id 已被 session_messages 落库」的幂等判断（需要跨表核对，成本较高）。
- 至少建议明确：崩溃恢复重放的回合**是否包含**该队列行对应的用户消息。若包含，则应删除该行而非复位；若不包含，则需在消费前确认用户消息未重复。

## 低（L）

### L5. `runExecution` 的 cancel 分支把 phase 置为 `FAILED` 而非 `CANCELLED`
`agent-inbound-handler.ts:302` `await this.options.onExecutionFinished?.(sessionId, context, executionId, false)` → `create-app.ts` 的 `onExecutionFinished` 用 `success ? 'COMPLETED' : 'FAILED'` 调用 `taskTerminal.finishExecution`。因此「立即发送」打断旧任务时，会话 phase 实际进入 `FAILED`，与进度卡展示的 `CANCELLED`（`cardListener.cancel`）不一致。这是既有行为（第一轮已存在），非本轮引入，但建议在取消语义上统一，避免会话列表里被中断任务显示为「失败」。

### L6. 崩溃恢复 `crash.run()` 与 `hydrate()` 的时序依赖注释与实现不完全一致
`create-app.ts:1435-1436` 注释称「这里只消费终态会话遗留的排队行」，但实际 `hydrate()` 会把 `RUNNING` 行复位后一并交由 `drainNextIfPending` 消费；`crash.run()` 的 `.then` 仅代表初始扫描提交完成（`agentExecutor.submit` 为 fire-and-forget，见 `agent-executor.ts:38-48`），并不代表恢复执行已结束。即「等崩溃恢复初始扫描结束后再触发」成立，但注释中「终态会话」表述与 `hydrate` 复位 `RUNNING` 的行为存在措辞偏差，易误导后续维护。

### L7. queue 消费与 phase 置位的原子性依赖「先 busy.add 后 updatePhase」的实现细节
正确性依赖 `runExecution` 内部 `updatePhase(RUNNING)` 严格晚于调用方 `busy.add`。当前二者位于不同方法（`onMessage`/`drainNext` 先 `busy.add`，`runExecution` 内 `updatePhase`），属于跨方法的隐式时序契约。若后续有人调整 `runExecution` 的第一步（如提前到 `createProgressCard` 之前调用 `updatePhase`），会重新引入「phase 已 RUNNING 但 busy 未置位」的窗口。建议在 `withLock` 临界区内、`busy.add` 与 `updatePhase` 之间加注释，或将 `updatePhase(RUNNING)` 上移至调用方紧邻 `busy.add` 处。
