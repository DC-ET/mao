## 总体结论

**核心链路无实质性 bug**，事件链路完整、重试时机正确、WS payload 与过滤一致、无线程安全问题。存在 2 个低严重度问题与 1 个覆盖范围说明（见下）。

## 链路与时序核对（均正确）

1. **事件链路完整**：`OpenAiLlmAdapter.stream()` → `callback.onRetry()` → `AgentLoop` 匿名 StreamCallback → `listener.onLlmRetry()` → `CompositeAgentEventListener.onLlmRetry()`（forEach 扇出）→ `WsStreamingEventListener.onLlmRetry()` → `send("llm_retry", payload)`。
   - 全工程 `AgentEventListener` 实现类仅 3 个：`WsStreamingEventListener`（已实现）、`CompositeAgentEventListener`（已实现）、`SubAgentResultCollector`（默认空实现，仅收集结果，无需处理）。无遗漏。
   - `llmAdapter.stream()` 唯一生产调用方是 `AgentLoop`，且已覆写 `onRetry`；测试代码 `CapturingCallback` 不受影响（default 方法）。
2. **重试时机正确**：
   - `onRetry` 在 `attempt > maxRetries` 判定**之后**调用（重试次数耗尽时直接 `onError`，不会误发重试事件）；
   - `onRetry` 在 `sleepSecondsRespectingCancel` 睡眠等待**之前**调用（客户端立即收到提示，随后进入等待）；
   - 重试仅发生在 HTTP 响应码阶段（`isRetryableStatus` = 429 或 500~599，覆盖 502/503/524），流式内容开始后不重试，不会出现"已输出内容又重试"的乱序。
3. **attempt/maxRetries 语义**：attempt 从 1 起计，maxRetries 为最大重试次数。共发 `maxRetries` 次 `llm_retry` 事件（1/max … max/max），随后第 maxRetries+1 次请求要么成功要么 `onError`，与前端"正在重试 n/max"展示完全对应，无 off-by-one。
4. **WS payload 与过滤**：payload 字段 `statusCode/attempt/maxRetries/delaySeconds` 与前端 `useStreamWS.ts` 解析一致；`executionId` 由 `WsStreamingEventListener.send()` 统一附加，前端 `STREAM_EVENT_TYPES` 已加入 `llm_retry` 并走统一的 `isStaleExecution` 过滤，无旁路。
5. **并发/线程安全**：`onRetry` 在 AgentLoop 执行线程（agentExecutor 线程）上运行，与 `onChunk` 同线程；`registry.send` 走 `BlockingQueue` 异步投递（非阻塞、线程安全）；`CompositeAgentEventListener.forEach` 已用 try-catch 隔离单个 listener 异常；`WsStreamingEventListener.send()` 内部 `activityHeartbeat.touch()`（内部吞异常）与 `registry.send()`（offer 不抛异常）均无异常外溢风险。

## 发现的问题

### [低] 1. 非流式 `chat()` 路径（含 Agent 循环中途压缩）无重试可见性事件
- **位置**：`OpenAiLlmAdapter.java` 的 `chat()` 方法（约 60-75 行）
- **说明**：`chat()` 与 `stream()` 拥有相同的重试逻辑（`attempt > maxRetries` 判定、`resolveRetryDelaySeconds`、`sleepSeconds`），但因其没有 StreamCallback 而完全无法发出重试事件。其中 **`CompactionService.java:639`（Agent 循环中途压缩）在 `AgentLoop` 主循环内同步执行**，压缩摘要调用 LLM 遇到 429/5xx 时仍静默重试（默认 10 次 × 5s = 最长约 50s），期间客户端只看到 `compaction_start/end`，仍存在"界面无响应"的体验空白，与本需求目标（避免重试期间界面无响应）部分冲突。其余调用方（`DangerAssessor`、`ModelService`、`WeixinVoiceSynthesisService`）为工具/后台路径，影响较小。
- **建议**：若需完整覆盖，可为 `chat()` 增加可选的重试回调参数（或复用 `StreamCallback`），由 `AgentLoop` 在压缩阶段透传；至少可考虑为 `CompactionService` 的调用增加同样的 `onLlmRetry` 上报。

### [低] 2. 取消竞态下可能先推 `llm_retry` 再推取消错误
- **位置**：`OpenAiLlmAdapter.java` stream() 约 112-127 行
- **说明**：`awaitResponse` 返回 response 后、进入 `sleepSecondsRespectingCancel` 之前，若用户刚好发起取消，代码仍会先执行 `callback.onRetry(...)` 再在睡眠中检测到取消并 `onError(Cancelled)`。表现为客户端短暂闪现"正在重试"条后被取消清除。功能无害，属竞态瑕疵。
- **建议**：在 `callback.onRetry(...)` 之前补一次 `isCancelled(cancelFlag)` 检查（与循环顶部一致），命中则直接 `onError(Cancelled)` 返回。

### [信息] 3. 子智能体（DelegateTool）的重试事件只进子会话流
- **位置**：`SubAgentVisibilityService.executeVisible()`（约 100-115 行）——非本次改动文件
- **说明**：子代理执行走 `new CompositeAgentEventListener(wsListener, resultCollector)`，`onLlmRetry` 只推到**子会话**的 `WsStreamingEventListener`（childSessionId + child executionId）。若前端未打开 Side Task 标签页，父会话用户看不到子代理重试提示。这与现有子会话流事件路由设计一致（content_delta 等同样只走子会话流），故不算 bug，仅作覆盖范围说明。

## 审查结论

- 核心需求（流式 LLM 调用重试 → WS `llm_retry` 事件 → 前端提示）实现正确，**无阻断性/功能性 bug**。
- 建议择机处理问题 1、2（均为低严重度，不影响本次功能上线）。
