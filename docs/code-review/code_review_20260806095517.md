## 本轮发现的问题

### 1. 原生异步发送失败仍被上层当作成功

- 优先级：高
- 位置：`desktop/src/capacitor/wsBridge.ts:235-255`、`desktop/src/composables/useStreamWS.ts:338-376`
- 触发场景：JS 检查桥为 OPEN 后，原生 WebSocket 恰好断开；随后 Capacitor `plugin.send()` Promise 被 reject。
- 问题：`NativeWsBridge.send()` 在 Promise 完成前直接返回 true，reject 分支只打印 warning。`useStreamWS.send()` 不检查返回值，`sendReliable()` 的 `trySend()` 调用后也固定返回 true。
- 影响：`send_message`、`edit_and_resend`、`create_side_session`、cancel 及队列操作可能没有到达后端，但 UI 仍按发送成功继续等待；对应会话还可能停留在 STARTING tracked 状态，直至超时查询。
- 建议方向：原生桥应提供可 await 的发送接口并向上抛出插件 reject；业务启动类请求应在原生确认发送成功后才进入等待状态，失败时回滚 STARTING track。

### 2. 原生桥处于 CONNECTING 时，`connect()` 会直接返回成功

- 优先级：高
- 位置：`desktop/src/composables/useStreamWS.ts:167-194`、`desktop/src/composables/useStreamWS.ts:351-376`
- 触发场景：原生连接断开并发送 `reconnecting`，桥的 readyState 被设为 CONNECTING；此时 recovery 或 `sendReliable()` 调用 `connect()`。
- 问题：原生分支只要发现已有桥且 `readyState !== WS_CLOSED`，就直接 `Promise.resolve()`，包括 CONNECTING 状态。它没有等待下一次 `open`。
- 影响：
  - `sendReliable()` 先发现非 OPEN，随后 `await connect()` 立即成功，再次检查仍非 OPEN并丢弃请求；
  - `useAppResumeSync.runRecovery()` 会误以为连接已就绪，随后调用原生 recovery。恢复流程可能在 WS 尚未重连时完成，期间服务端的新事件无法及时补齐；
  - 调用方无法区分“正在重连”和“已可发送”。
- 建议方向：复用 CONNECTING 桥时应返回一个等待 `onopen`/`onclose`/超时的 Promise，而不是立即 resolve；同时避免覆盖桥上已有的事件处理回调。
