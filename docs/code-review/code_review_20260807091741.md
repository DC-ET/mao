## 【中】窗口函数每会话仅取第一条命中消息，「首条假命中」导致真实命中会话被误剔除（上轮修复引入的回归）

**位置**：
- `backend/src/main/java/cn/etarch/mao/session/mapper/MessageMapper.java` 第 73-80 行（`ROW_NUMBER() OVER (PARTITION BY m.session_id ORDER BY m.id ASC)` + `WHERE t.rn = 1`）
- 配合 `backend/src/main/java/cn/etarch/mao/session/service/SessionService.java` 第 453-469 行二次校验循环

**问题描述**：
上轮将「全局 LIMIT 200」改为「每会话窗口函数取一条」后，每个候选会话**只剩第一条（id 最小的）命中消息**。若该会话的**最早命中消息恰好是假命中**（关键词命中在多模态消息的图片 URL / JSON 字段名，而 text 部分不含关键词），则 `extractVisibleText` 提取出的文本不含关键词 → `snippet = null` → 第 469 行 `continue` 把整个会话剔除，**即使该会话后续存在真实命中的文本消息**。

具体场景：用户先发带图消息（图片 URL 含搜索词，如上传文件名为「登录页截图.png」的图片，URL 为 `https://oss/.../登录页截图.png`），`extractVisibleText` 只保留 text part（如「帮我看看」），不含「登录」；之后该会话又发了一条文本消息「登录问题已修复」——窗口函数只取第一条（假命中），会话被剔除，搜索「登录」看不到该会话。

对比修复前：`LIMIT 200` 会取回该会话**全部**命中消息，Service 逐条检查时第二条真实命中可正常生成 snippet，不会误剔。

**影响**：
真实包含关键词的会话从搜索结果中消失（假阴性），是上轮修复引入的行为回归。触发条件：会话内「较早的命中消息为多模态假命中」+「较晚存在真实文本命中」，在带图会话中并不罕见（图片文件名、`type`/`text`/`image_url` 等 JSON 键名均可成为假命中关键词）。

**建议修复方向**：
- 方案 A（推荐）：窗口函数改为每会话取前 N 条命中消息（如 `WHERE t.rn <= 5`），Service 循环已有 `break` 逻辑，遍历到首个真实命中即停，不影响 snippet 与排序，且候选最多 20 会话、最多取 100 条消息，量级可控；
- 方案 B：对「候选存在但 snippet 为 null」的会话在 Service 侧发起补偿查询（取该会话全部命中消息再校验），复杂度较高；
- 方案 C：为 `rejectsMultimodalFalseHit` 类测试补充「首条假命中 + 次条真命中」的回归用例，先固化行为再改。

## 【中】防抖窗口期（300ms）内按 Enter 仍会跳转上一次的旧结果（上轮修复不完整）

**位置**：
- `desktop/src/components/search/SessionSearchPopover.vue` 第 121-131 行（`onKeywordInput`：设置防抖定时器时**未清空** `results`/`status`）
- 第 166-172 行（`onPanelKeydown` 的 `Enter` 分支：仅 `if (item)` 守卫，无 `status` 判定）

**问题描述**：
上一轮修复在 `runSearch` 中清空 `results` 与 `activeIndex`，只覆盖了「请求已发出、在途期间」的窗口；但**防抖 300ms 窗口期**（`onKeywordInput` 设置 `setTimeout` 后、`runSearch` 尚未执行）内，`status` 仍为 `'results'`、`results` 仍是**上一次关键词**的数据、列表仍显示旧结果。此时用户按 Enter，`results.value[activeIndex.value]` 命中旧数据 → `handleJump` 跳到与当前输入无关的旧会话。

这正是上一轮报告明确要求修复的「输入新词后立即回车跳旧结果」场景，仅缩小了窗口期，未彻底修复。

**影响**：
「改词后 300ms 内回车」会跳转到错误会话，属功能正确性问题（窗口较上轮收窄，但仍存在）。

**建议修复方向**：
- `onKeywordInput` 设置防抖时同步置 `status = 'loading'`、清空 `results`/`activeIndex`（与 `runSearch` 开头一致）；
- 或按上一轮建议 B：`Enter` 分支增加 `if (status.value !== 'results') return;` 守卫（并在 loading 时回车触发立即搜索跳过防抖，可选）。

## 【低】`extractVisibleText` 对「混合类型 JSON 数组」的文本消息仍假阴性（上轮修复残留边界）

**位置**：
- `backend/src/main/java/cn/etarch/mao/session/service/SessionService.java` 第 517-541 行（`extractVisibleText`）

**问题描述**：
上轮修复通过 `multimodal` 标志区分「多模态 ContentPart 数组」与「普通 JSON 数组」，但判定条件是**数组中出现任一** `type=text` / `type=image_url` 元素即视为多模态。若纯文本 user 消息恰好是**混合数组**（如 `[1, {"type":"text","text":"abc"}]`、`[{"name":"a"},{"type":"text","text":"abc"}]`），解析后 `multimodal=true`，只拼接 text 部分返回 `"abc"`，原文中非 text 元素里的关键词（如 `1`、`name`）全部丢失 → 搜索该词时会话被剔除（假阴性）。

**影响**：
边缘场景（用户消息恰好是含 ContentPart 结构的混合 JSON 数组）下的搜索假阴性，用户无感知；与上轮已修复的 `[1,2,3]`、`["登录","500"]` 属同类残留边界。

**建议修复方向**：
仅当**数组所有元素**均为 ContentPart 结构（每个 Map 元素都含 `type` 且 `type ∈ {text, image_url}`）时才按多模态提取 text；否则回退返回原文，交由 `buildSnippet` 二次校验。
