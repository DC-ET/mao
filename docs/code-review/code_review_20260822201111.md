## 一、严重问题

### BUG-1 AgentLoop 空响应重试：`emptyResponseCount` 从不复位，且重试成功后该轮不落库

- **位置**：
  - `backend-ts/src/harness/core/agent-loop.ts:133`（`let emptyResponseCount = 0;` 仅在 execute 入口初始化一次）
  - `backend-ts/src/harness/core/agent-loop.ts:262-279`（onComplete 空响应分支：计数、达到 3 抛错、注入系统提示、置 `emptyResponseEncountered`）
  - `backend-ts/src/harness/core/agent-loop.ts:313-318`（`emptyResponseEncountered` 分支仅 `clearPendingToolCalls()` 后 continue）
- **描述**：两个独立缺陷叠加：
  1. **计数泄漏**：`emptyResponseCount` 在整个 while 循环外声明，一旦某次空响应发生，即使下一轮模型已正常输出内容，计数也不清零。长会话中只要历史上零散出现过 2 次"无 content 且无 tool_calls 但有 thinking"的响应（部分推理模型在思考耗尽后偶发此类空轮），第 3 次出现时直接抛出 `'LLM 连续返回空响应'` 使整个任务失败——而日志文案宣称的"连续"语义并未实现。正确做法是在收到有效输出（content 或 toolCalls 非空）时将计数归零。
  2. **重试轮不落库**：空响应轮既无 content 也无 toolCalls，走不到任何 `pendingSave`/`onSaveAssistantMessage` 分支；随后 continue 直接进入下一轮构建请求。注入的 `<系统提示>` 通过 `context.addSystemMessage` 只存在于内存 context.messages 中，若中途触发 mid-loop 压缩或进程重启恢复，DB 中没有任何痕迹，历史重建后该提示消失属可接受行为；但更关键的是**空响应前的 usage 已通过 `context.addUsage(usage)` 计入统计**，而消息本身永不持久化，token 统计与消息流水从此不对齐。
- **影响**：长任务被误判失败中断；用量统计漂移。
- **修复方向**：在 onComplete 有效输出分支重置 `emptyResponseCount = 0`；空响应分支同时考虑记录一条占位 ASSISTANT 消息或在 usage 上打标。

### BUG-2 ShellSessionManager 自动生成的会话 ID 用毫秒时间戳，同毫秒并发必撞

- **位置**：`backend-ts/src/harness/shell/shell-session-manager.ts:259`
  ```ts
  shellSessionId = `sh-${conversationId}-${Date.now()}`;
  ```
- **描述**：AgentLoop 对多个 pendingToolCalls 是并行执行的（`agent-loop.ts` 的 `executeToolCalls` 多工具分支用 `Promise.all`）。LLM 单轮流式响应里完全可能同时下发两个 `shell` 工具调用（例如并行跑两个测试）。两个并行 dispatch 各自省略 `session_id` 时都会走到自动生成路径，`Date.now()` 精度为毫秒，Node 单线程事件循环内两次同步取值几乎必然相同；第二个 `this.sessions.set(shellSessionId, session)` 覆盖第一个条目，且 `conversationSessions` 集合去重后 size 少计。
- **影响**：并行的两条 shell 命令共享同一个 Session 对象引用互相覆盖（其一变成孤儿进程无法 close），或 marker 读取串台——A 命令的 `readUntilMarker` 把 B 命令的输出消费掉，返回错误的 exit_code/output。这正是"多工具并行调用"这一官方推荐用法下的高概率翻车点。
- **修复方向**：ID 生成加入随机段（如复用 `randomUUID()` 片段，参考 `ShellSessionTool.newMarker()` 的做法）；或 getOrCreate 内对自动命名加 per-conversation 原子计数器。

### BUG-3 JWT 无 token 类型区分：access token 可直接作为 refresh token 使用

- **位置**：
  - `backend-ts/src/crypto/jwt.service.ts:12-21`（`generateToken` / `generateRefreshToken` / `generateShellToken` 全部调用同一个 `buildToken(userId, username, expMs)`，payload 完全同构，只有 `exp` 时长不同）
  - `backend-ts/src/auth/auth.service.ts:42-56`（`refreshToken()` 只校验签名有效即签发全新 access+refresh 对）
- **描述**：refresh token 与 access token 的唯一区别是过期时长（refresh 更长）。因此一个尚未过期的 access token 本身就是合法的 refresh token：拿着它调 `/auth/refresh` 可以无限续签新的令牌对。这使 access token 的短有效期形同虚设——token 一旦泄露（前端 localStorage/URL query 均有暴露面，如 WS 连接 `?token=`），攻击者可在 refresh 有效期窗口内永久保持登录，服务端无任何吊销手段（`logout()` 注释明确是无状态丢弃）。
- **影响**：凭据泄露后的攻击窗口从 access 过期时间（86400s 内）扩大到整个 refresh 有效期，且可持续滚动续期。
- **修复方向**：`buildToken` 增加 `type` claim（`access`/`refresh`/`shell`），`refreshToken()` 校验 `type === 'refresh'`；各校验入口同样断言类型。

### BUG-4 PromptEngine 快速命令标记替换只替换第一处

- **位置**：`backend-ts/src/harness/core/prompt-engine.ts:94-102`
  ```ts
  const commandMatches = [...replaced.matchAll(COMMAND_PATTERN)];
  for (const m of commandMatches) {
    ...
    replaced = replaced.replace(m[0], command.content);   // ← 无 g 标志，只换第一个
  }
  ```
- **描述**：`COMMAND_PATTERN` 是不带 `g` 的 `/#\{([^}]+)\}#/`（prompt-engine.ts:34 附近定义处 `const COMMAND_PATTERN = /#\{([^}]+)\}#/g;` —— 注意 matchAll 要求 g 标志所以收集阶段没问题，但 `String.prototype.replace(string, ...)` 传字符串永远只替换**第一次出现**）。当用户消息中出现两个相同名字的命令标记（例如模板里引用两次 `#{deploy}#`）时：matchAll 收集到 2 个匹配对象，但两次循环里的 `m[0]` 相同，每次都替换当前字符串中的第一个匹配位——第二次替换的是已经被上一次替换过的产物内部恰好再次出现的文本，或者干脆找不到（替换内容里包含 `#{...}#` 字样时会递归污染），第二个原始标记则原样保留发送给 LLM。
- **影响**：同名命令第二次出现不展开，模型看到裸的 `#{xxx}#` 标记；若命令内容本身含 `#{name}#` 形态文本会被二次展开造成注入式错乱。
- **修复方向**：一次性收集所有匹配后从后向前切片拼接，或按每个匹配的唯一区间做单遍替换（类似 SKILL_PATTERN 用 replace 回调的方式即可天然全局替换）。

## 二、中等问题

### BUG-5 autoConsumeQueue "仍占用"分支把队头塞回队尾，破坏 FIFO 且可能反复搬运

- **位置**：`backend-ts/src/session/ws/streaming-ws-handler.ts:843-861`
  ```ts
  const head = await this.deps.messageQueueService.dequeue(sessionId);   // 先出队（置 DELETED）
  ...
  if (this.executionClaims.has(sessionId) || this.runningTasks.has(sessionId)) {
    await this.deps.messageQueueService.enqueue(sessionId, head.userId!, head.content ?? '', head.images ?? null);
    // enqueue 以 findLastPending().sortOrder + 1 计算 → 排到了队列尾部
  ```

- **描述**：`autoConsumeQueue` 在 finally 中被调用时理论上任务已释放，但存在并发窗口（如 side-task 与主会话共用队列、insert_message 流程、500ms 延迟重发的 handleSendMessage 还持有 claim）。此时代码先 `dequeue` 把队头删了，发现仍在运行，再把这条消息 `enqueue` 回去——但 `MessageQueueService.enqueue`（message-queue.service.ts:10-24）用"最后一条 PENDING 的 sortOrder+1"，于是**队头消息被搬到队尾**。若队列有 A、B 两条且连续两次落入该分支，顺序彻底反转。更糟的场景：如果 claim 由一个很快结束又立刻开始的循环持有，消息会在"出队→入队"间来回搬运，每次搬运都向客户端广播两遍 `queue_updated`，产生抖动。
- **影响**：排队消息顺序错乱（用户排队的指令以错误顺序被执行）；事件风暴。
- **修复方向**：先检查占用再 dequeue；或 dequeue 失败分支改为原位保留（不做任何写操作），仅当下次真正空闲时再消费。

### BUG-6 edit_and_resend 依赖 created_at 找"最后一条用户消息"，排序不稳定时可截断错误消息

- **位置**：`backend-ts/src/session/ws/streaming-ws-handler.ts:428-433` + `backend-ts/src/session/session.repository.ts:listBySession`
  ```sql
  SELECT * FROM message WHERE session_id = ? AND deleted=0 ORDER BY created_at ASC, id ASC
  ```
- **描述**：消息列表排序键是 `(created_at, id)`。同一秒内写入的多条消息（批量保存工具消息、定时任务补投、时钟回拨的服务器实例）created_at 相同，此时顺序由 id 决定尚可；但**跨节点部署或时钟偏移**下，晚插入的消息可能携带更早的 created_at，`[...messages].reverse().find(m => m.role === 'USER')` 找到的就不再是真正的最后一条用户消息。随后 `editMessageAndTruncate`（session.service.ts:838 起）会对该 messageId 执行 `logicalDeleteAfter(sessionId, messageId)`——把 id 更大的所有消息逻辑删除。选错目标意味着**误删大量无辜消息**。
- **影响**：低概率但破坏性极大（不可逆逻辑删除整段对话）。
- **修复方向**："最后一条用户消息"直接用 `SELECT ... WHERE role='USER' ORDER BY id DESC LIMIT 1`（id 单调递增不受时钟影响）；`editMessageAndTruncate` 前再校验一次目标确为最后一条。

### BUG-7 GrepSearchTool rg 输出解析对含冒号路径与上下文分隔行处理错误

- **位置**：`backend-ts/src/harness/tool/impl/grep-search-tool.ts:112-131`（`parseRgLine`）、`:82`（`--context`）
- **描述**：
  1. `parseRgLine` 用第一个冒号切文件名。rg 的输出格式是 `path:line:content`，当 path 本身含冒号（Windows 盘符 `C:\...`、或文件名带冒号）时 `firstColon` 落在盘符处，`Number('C')` 得 NaN 后虽然回退到 `-` 分隔符分支，但普通匹配行没有 `-` 分隔，最终返回 null 丢弃该行——匹配结果静默缺失。（当前云端为 Linux 影响有限，但 LOCAL 模式的 Windows 桌面端走的是另一条本地执行链，此处主要影响 CLOUD 下用户上传的含冒号文件名场景，以及未来复用。）
  2. 开启 `--context N` 后，rg 会在组之间输出 `--` 分隔行，并对上下文行使用 `path-line-content` 格式。解析器把上下文行也当普通匹配行收进 `matches` 并计入 `total_matches`，但不带任何"这是上下文"的标记——调用方（Agent）无法区分真实命中与上下文行，统计数虚高。
- **修复方向**：调用 rg 时追加 `--json` 或至少 `--no-context-separator`，并以行首 `lineNum-` vs `lineNum:` 区分上下文行单独标注。

### BUG-8 useChat 文件引用路径改写发生在乐观 UI 插入之后，气泡与实际发送内容不一致

- **位置**：`desktop/src/composables/useChat.ts`（sendMessage 与 sendMessageAndWaitForSave 两处相同模式）
  - 先 `sessionStore.addUserMessage(sid, { content: resolvedText, ... })`（约 :357/:520 附近）
  - 之后才执行 `resolvedText = resolvedText.replace(FILE_REF_PATTERN, ...)` 把相对路径改写成绝对路径（约 :380/:545 附近）
- **描述**：用户输入 `请分析 @{docs/plan.md}@ 这个文件`，聊天气泡里显示的是相对路径版本；而 WS 发给服务端并被持久化的是改写后的绝对路径版本。刷新页面拉取 REST 历史后，气泡内容变成绝对路径——同一条消息前后展示不一致。另外该正则替换在 `sendMessageAndWaitForSave` 中同样存在一份拷贝，两处逻辑必须人工保持同步，已经具备漂移条件（本报告审查期间两份代码目前一致，属隐患而非现行差异）。
- **修复方向**：把改写逻辑提前到 `addUserMessage` 之前，对同一份 `resolvedText` 做"先改写、后展示、后发送"；或抽成单一函数消除双份拷贝。

### BUG-9 ScheduledTaskService.executeTask 先更新 nextFireTime 再异步加锁执行，扫描周期内可重复触发

- **位置**：`backend-ts/src/schedule/scheduled-task.service.ts:196-200` 及 `ScheduledTaskScheduler.scanAndExecute`
  ```ts
  async executeTask(task: ScheduledTask): Promise<void> {
    task.nextFireTime = this.calculateNextFireTime(task.cronExpression!);
    await this.store.updateById(task);        // ← 立即推进 nextFireTime
    this.agentExecutor(() => withSessionLock(...));  // ← 真正执行是异步派发
  ```
- **描述**：`scanAndExecute` 用 `await this.service.executeTask(task)` 串行处理到期任务，`updateById` 完成后本轮扫描不会再选中它——单实例下看似安全。但 `listDue` 的 SQL 条件是 `next_fire_time <= now`，而 `executeTask` 里计算下一次触发用的是 `new Cron(...).nextRun()`（从**当前时刻**起算）。若任务因 GC/停机等原因延迟触发（比如每分钟任务停机 10 分钟后恢复），nextRun 正常推进没问题；问题在于 `withSessionLock` 排队期间（前一次执行未结束）新触发的 fire 会进入锁队列堆积，`fireCount` 与 `lastExecutionStatus` 由多个闭包竞争最后一个写入，QUEUED/COMPLETED 状态可能互相覆盖；且这些排队的执行共用同一个 `task` 对象引用（scanAndExecute 循环变量），`task.lastFireTime/fireCount` 的读写全部竞态。
- **影响**：执行历史统计失真；极端情况下同一 prompt 在会话解锁后被连环补发多次（每次锁等待结束都 saveMessage USER prompt 并执行一轮）。
- **修复方向**：锁等待分支应在拿到锁后**重新检查**会话 phase 与上次执行时间，跳过过期的补发；task 状态更新改为按 id 从 DB 重读后再写。

## 三、附录：设计性弱点（不计入 BUG）

### A-1 read_file 使用 resolveLenient，绝对路径可读任意服务器文件
`backend-ts/src/harness/safety/path-sandbox.ts:47-58` 的 `resolveLenient` 不做 allowedRoot 校验，`read_file` 传入 `/etc/passwd` 等绝对路径可直接读出。这是产品文档明示的能力（工具描述写着"绝对路径可读取工作区外文件"），属有意设计；但配合 CLOUD 多租户形态，建议至少拒绝读取其他用户的 runtime/home 目录之外的高敏感路径，或对该能力增加审计埋点。

### A-2 BackgroundTaskManager.consumeCompletedResults 的 sessionId 过滤在删除之后判断
`backend-ts/src/harness/core/background-task-manager.ts:47-49`：`if (entry.done) { if (sessionId !== entry.sessionId) continue; ... }`——不同会话的任务不会被误消费（continue 在 delete 之前），逻辑正确；但当查询会话为 null 时（`sessionId=null`）会消费掉所有 `entry.sessionId===null` 的任务，多个匿名会话（sessionId 为 null 的场景目前不存在于生产路径）之间会串结果。当前调用方恒有 sessionId，仅作记录。

## 四、核查方法说明

以上每条均经过以下验证步骤，排除"看起来像 BUG 但实际有兜底"的误报：

1. **BUG-1**：通读 agent-loop.ts 全部 570 行，确认 `emptyResponseCount` 无任何复位语句；`grep -n emptyResponseCount` 仅 4 处（声明/自增/日志/阈值判断）。
2. **BUG-2**：对照 `executeToolCalls` 多工具 `Promise.all` 并行分支与 `getOrCreate` 无锁 Map 操作，确认同 conversationId 并发创建路径真实存在。
3. **BUG-3**：比对 jwt.service.ts 三个生成方法的 payload 构造（完全一致）与 auth.service.ts refreshToken 的校验内容（仅验签）。
4. **BUG-4**：核对 `String.prototype.replace` 字符串参数语义（ECMA-262：仅替换首个匹配）。
5. **BUG-5/6/9**：沿 streaming-ws-handler / scheduled-task 的调用时序逐分支推演并发窗口。
6. **BUG-7**：核对 rg 默认输出格式（`--no-heading --line-number` 下 `path:line:content`）与 `--context` 行为。
7. **BUG-8**：比对 useChat 中 addUserMessage 与 FILE_REF_PATTERN 替换语句的前后顺序。
