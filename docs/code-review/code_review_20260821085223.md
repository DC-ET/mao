## 二、本轮新发现问题

### 1. [中] `ask_user_questions_cancelled` 无条件 `this.modal = null`：误关 approval/其他 ask modal，泄漏 resolver 致回合卡死

- 位置：`src/tui/ink-renderer.ts` `onEvent` 的 `ask_user_questions_cancelled` 分支
- 问题：该分支无条件执行 `this.modal = null`。但已核对后端语义，`ask_user_questions_cancelled` 并非只在「真正取消」时发送：
  - **每次问答被应答后，服务端都会回发 cancelled 作为应答确认**（`streaming-ws-handler.ts` `handleAskUserQuestionsResult`：`registry.complete(...)` 成功后立即 `send(wsEvent('ask_user_questions_cancelled', ...))`）；
  - 问答超时（默认 **15 分钟**，`ask-user-questions-registry.ts` `DEFAULT_TIMEOUT_MILLIS = 900_000`）后 `tool-dispatcher.ts` 也会回发 cancelled；
  - 断线重连/快照重放时旧 cancelled 可能重放（客户端 `asked` 集合只对 `ask_user_questions` 去重，cancelled 不去重）。
- 影响链：用户刚应答完 ask R1（modal 已关，result 已发），服务端回发 cancelled(R1) 作为确认；若此刻（WS 往返窗口内）`tool_execute` 已触发 approval modal，cancelled(R1) 到达后 `this.modal = null` 直接关闭 approval modal 且**未 resolve approvalResolver** → `LocalExecutor.onToolExecute` 中 `await this.opts.askApproval(...)` 永久挂起（executor.ts 无超时兜底）→ 工具永不执行、`tool_result` 不发、回合卡死，只能 `/cancel` 或 Ctrl+C 强制退出。同理，另一 ask modal（R2）打开时收到 cancelled(R1) 也会误关 R2 并泄漏 R2 resolver。
- 修复建议：cancelled 分支只关闭「属于该 requestId 的 ask modal」：
  ```ts
  case 'ask_user_questions_cancelled':
    if (this.modal?.type === 'ask' && this.modal.requestId === evt.requestId) {
      this.modal = null;
    }
    this.resolveAsk(evt.requestId, 'cancelled');
    this.flush();
    break;
  ```

### 2. [中] `requestApproval` 以 'cancelled' 收尾 ask 后服务端无人应答：回合最长停滞 15 分钟

- 位置：`src/tui/ink-renderer.ts` `requestApproval()`；`src/session/session-runner.ts` `handleQuestions` 'cancelled' 分支
- 问题：LOCAL 模式下 ask modal 打开时 `requestApproval` 覆盖，`resolveAsk(requestId, 'cancelled')` → `handleQuestions` 静默返回，**不向服务端发 result 也不发 cancel**。但此时服务端 `waitForAnswer(sessionId, requestId)` 仍在等待该问答的答案（超时 15 分钟），agent loop 阻塞在 ask 工具上。用户批准工具后 `tool_result` 虽已回传，loop 仍卡在问答处，直到 15 分钟超时服务端回发 cancelled 才继续——表现为「spinner 一直转、回合假死 15 分钟」。
- 语义辨析：'cancelled' 静默收尾对「服务端主动取消」是合理的（服务端自己知道取消了）；但本场景的 cancelled 是**客户端单方面丢弃**，服务端不知情。两种来源被同一个 sentinel 混为一谈。
- 修复建议（二选一）：
  - `requestApproval` 覆盖 ask 时，由客户端补发 `ask_user_questions_result`（空 answers）让服务端立即解除阻塞（`handleAskUserQuestionsResult` 会 complete 并回发 cancelled，与问题 1 的修复配合后无副作用）；
  - 或区分两种来源：服务端 cancelled → 静默；本地覆盖 → 发空 result。可给 resolver 传独立 sentinel（如 `{ cancelled: 'local' }`）或单独记录「已被本地覆盖的 requestId」清单，`handleQuestions` 对清单内 requestId 发空 result。

### 3. [低] ask→ask 直接覆盖未防护，且 AskModal 实例状态跨请求保留

- 位置：`src/tui/ink-renderer.ts` `onEvent` 的 `ask_user_questions` 分支（仅处理 approval 覆盖）；`src/tui/modals.tsx` AskModal
- 问题：① `ask_user_questions` 到达时若当前 modal 是 ask（R1）而未决，新 ask R2（不同 requestId 可穿过 SessionRunner `asked` 去重）直接覆盖 → R1 resolver 泄漏（依赖服务端后续 cancelled 才回收，回收路径又受问题 1 影响）；② app.tsx 中 AskModal 无 key，R1→R2 覆盖时 React 复用组件实例，`qIndex`/`answersRef`/`selected`/`customMode` 全部保留 → R2 从错误题目开始，`answersRef` 混入 R1 的答案（多选题会发错答案），R2 题数更少时 `q` 直接 undefined 触发 `onResolve('fail')`。
- 修复建议：`ask_user_questions` 分支补 ask→ask 防护（先 `resolveAsk(this.modal.requestId, 'cancelled')`）；AskModal 渲染处加 `key={modal.requestId}` 强制重置状态。

### 4. [低] `repl.ts` `onAskResponse` 无条件 `setModal(null)`（与问题 1 同根）

- 位置：`src/repl/repl.ts` `onAskResponse`
- 问题：`onAskResponse` 先 `opts.tuiHandle.setModal(null)` 再 `resolveAsk`。若 ask modal 已被 `requestApproval` 替换为 approval（极端时序下用户按键在卸载前派发），`setModal(null)` 会误关 approval modal。当前 AskModal 卸载后按键不再派发、实际触发概率低，但建议与问题 1 一并加固：仅在 renderer 侧 modal 仍为对应 ask 时关闭（或由 renderer 的 resolveAsk 统一负责 modal 归属清理）。

### 5. [低] 第三轮遗留问题复核确认（不在本轮修复清单内，不阻塞合入）

- round-3 issue 4：`firstPrompt` 以 `\` 结尾时 repl 层 `buffer` 续行内容在输入区不可见（`handleSubmit` 续行分支只 `setContinuation(true)`，InkInput 只展示自身 bufferRef）——仍在；
- round-3 issue 6：死代码（`InkTuiHandle.setDraft/pushStaticRound/pushHistoryLine`、`onSlashClear`、`InkRendererLike`、`ReplOptions` 未消费字段、`repl-renderer.ts`/`composer.ts` 生产路径遗留）——仍在。
