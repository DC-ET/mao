# Code Review：feature/embed-sdk（commit f6e151a9）

- 审查对象：`.worktree/embed-sdk` HEAD `f6e151a9`「feat(embed): 新增 Web Embed SDK」
- 审查日期：2026-09-04
- 审查范围：sdk/embed/src、shared/contracts/src/ws.ts、backend-ts normalizeClient、desktop prebuild/CI（按用户要求不含样式与文档）
- 结论：**发现 3 个高严重度、3 个中严重度、4 个低严重度问题**。整体链路（auth 首帧、心跳、重连退避、executionId 门禁骨架）与 desktop 既有实现对齐，但存在会导致 SDK 主流程不可用/状态错乱的功能缺陷。

---

## 高（High）

### H1. SDK IIFE 产物在浏览器直接崩溃：打包进 `process.env.NODE_ENV`

- 位置：`desktop/public/embed/mao-chat.js`（提交的构建产物，全文含 222 处 `process.env.NODE_ENV`，均为 Vue 内部的开发/生产分支判断）；根因在 `sdk/embed/vite.config.ts`
- 现象：vite lib/IIFE 构建中 esbuild 未定义 `process.env.NODE_ENV`，Vue 源码里的裸引用被原样保留。产物被任意网页以 `<script src="https://mao.etarch.cn/embed/mao-chat.js">` 加载后，**模块顶层立即执行 `process.env.NODE_ENV!==...`，浏览器无 `process` 对象 → ReferenceError，SDK 完全不可用**。注意这不是"仅影响开发警告"：`Object.freeze({})` 分支、effect 校验等都在模块顶层/首帧执行路径上。
- 建议修复：`vite.config.ts` 增加
  ```ts
  define: { 'process.env.NODE_ENV': JSON.stringify('production') }
  ```
  （或在 esbuild 选项加 `define`），重新构建并把产物提交进 `desktop/public/embed/`。当前提交的产物是坏的，必须随修复重新生成。
- 附带证据：产物第一行 `var ce=process.en...`，`grep -c 'process.env.NODE_ENV'` = 222。

### H2. 流式增量永不渲染：`ui.messages` 与 `ChatStore.messages` 是两个不同数组

- 位置：`sdk/embed/src/controller.ts:44`（`createUiState` 初始化 `messages: []`）；`controller.ts:280`（RootApp 挂载传 `ui`）；`sdk/embed/src/ui/RootApp.vue:44`（`ChatPanel :messages="ui.messages"`）；而所有事件写入的是 `EmbedController.store = new ChatStore()` 的 `store.messages`（`core/store.ts:29`）
- 现象：controller 中没有任何一行把 `store.messages` 同步到 `ui.messages`（grep 全包仅 spec 文件引用 store.messages）。事件处理只调 `store.handleEvent(msg)` 与直接写 `ui.pendingQuestion/sessionError/llmRetryText…`，消息数组始终为空。**用户发送后只看到自己的气泡（appendLocalUserMessage 写的是 store.messages，同样不会出现在 UI）、收不到任何助手回复**；后续 store 内的 `ensureHistory` 拉取的历史同样进不了 UI。
- 建议：让 `ChatPanel` 直接消费 `controller.store` 的响应式 refs（把 store 传进组件），或在 controller 用 `watchEffect`/同步点把 `store.messages/phase/sessionError/llmRetryText` 投影到 `ui`。当前设计里 `ui.messages` 字段属于死代码。

### H3. 历史消息接口响应结构用错：`GET /sessions/:id/messages` 返回 `{messages:[...]}` 而非数组

- 位置：`sdk/embed/src/controller.ts` `boot()` 内 `ensureHistory` 回调：
  ```ts
  const list = await this.rest.request<...>('GET', `/sessions/${sid}/messages`);
  return list.filter(...)  // list 实为包装对象
  ```
- 对照后端：`backend-ts/src/session/session.routes.ts:356-375` 返回 `{ messages: toMessageVOList(...), hasMore, nextBeforeMessageId, compactionEvents? }`（`sendOk` 再包一层 `{code,data}` 由 rest-client 解出 data）。
- 现象：`list.filter` 不是函数 → boot 抛错 → `sessionError='list.filter is not a function'`，浮窗初始化失败，无历史、无会话（boot 失败后 sessionId 已绑定但历史没加载）。另外 VO 字段名是 `thinkingContent` 而非 `thinking`（`session-vo.ts:269`），映射 `m.thinking ?? ''` 也拿不到值。
- 建议修复：改为 `const page = await rest.request<{messages: EmbedMessageVO[]}>('GET', ...)` 后取 `page.messages`，并把字段映射改为 `thinkingContent`。另注意该接口默认只返回最近 5 轮（`roundLimit ?? 5`），SDK 未处理 `hasMore`，长会话历史会被静默截断（可作为低优先项一并处理）。

## 中（Medium）

### M1. REST 401 重取 token 后 TokenProvider 缓存不失效，可能死循环出 AuthError

- 位置：`sdk/embed/src/core/rest-client.ts:41-45`（401 → `retry=true` 再发一次）；`sdk/embed/src/core/token-provider.ts:12-19`（`get()` 缓存 Promise，仅 supplier 失败才置 null）
- 现象：第一次请求用缓存 token A → 401 → 重试时 `this.getToken()` 仍返回**同一个缓存的 A**（401 不调用 `invalidate()`）→ 必然再次 401 → 抛 AuthError。承诺的"401 时回调宿主 getToken() 重取"实际不会发生（仅 WS 1003 路径有 `onAuthFailed → invalidate`，REST 路径缺失）。TokenProvider 注释与 controller 的 AuthError 分支都表明设计意图是重取。
- 建议修复：`request()` 捕获 401 时先 `this.getTokenProvider.invalidate()`（或在 RestClient 构造里注入 invalidate 回调）再重试。

### M2. 审批卡片永远不会出现：没有任何代码为 `pendingApproval` 赋值，且 embed 无法收到审批请求

- 位置：`sdk/embed/src/controller.ts`（grep 全包，`pendingApproval` 只在 `setPendingApproval`/清空处出现，无赋值调用）；`core/store.ts:204`；UI 侧 `ui/ChatPanel.vue:84`、`ui/ApprovalCard.vue`
- 协议事实（backend-ts）：工具审批仅存在于 LOCAL 执行链路——`harness/local/local-tool-executor.ts:31-36` 里 `needApproval` 时 `approvalRegistry.register()`，实际批准操作由 Electron 主进程弹窗处理（desktop `useChat.ts:22-91` 走 `electronAPI.onToolApprovalRequest/respondToolApproval`），后端 **没有 `approval_required` 之类的服务端→embed 事件**；`tool_execute` 帧也只发给 LOCAL_CAPABLE_CLIENTS（electron/cli），embed 不在其列。而 `POST /sessions` 不传 executionMode 时默认 `CLOUD`（session.service.ts:96），CLOUD 会话根本没有审批环节。
- 现象：提交信息宣称"审批"能力，但当前实现里审批卡片是死代码；即使未来接上，`decide()` 直接发 `tool_approval` 帧后后端仅 unregister（视为已处置），不会给 LOCAL 工具回传结果，语义也对不上。
- 建议：要么在文档/README 明确 embed 不支持审批并把 ApprovalCard 移除，要么按设计补齐服务端事件（范围超出本次需求则先移除 UI 与提交说明中的"审批"承诺）。

### M3. 多 tab 协调的 inquire 永远拿不到回复：BroadcastChannel `session-inquiry` 无人应答

- 位置：`sdk/embed/src/core/tabs.ts`：`ensureChannel()` 的 onmessage 只处理 `session-reply`；`inquire()` 发出 `session-inquiry` 后等 `session-reply`。
- 现象：**没有任何代码监听 `session-inquiry` 并回复 `session-reply`**（claim() 只是单向 postMessage）。因此 `inquire()` 100% 超时返回 null——300ms 纯等待，功能形同虚设；注释里"避免两个 tab 同时读到空记录各自新建"的竞态保护并不存在。两 tab 并发首次初始化仍会各建一个会话（后写的 localStorage 覆盖先写的，先建的会话成为孤儿）。
- 建议修复：在 onmessage 中处理 `session-inquiry`：若 `msg.agentId` 与本 tab 相同且本地已有 sessionId，则回 `session-reply{nonce, sessionId}`。若近期不打算实现，建议删掉 inquire 调用以免每次 open() 固定多等 300ms（体验劣化）。

## 低（Low）

### L1. `sessionError` 只在 `session_already_running` 事件时更新 UI，而 store 的 error 路径不同步

- 位置：`controller.ts` `onWsEvent` `case 'error'` 会写 `this.ui.sessionError`，但 store.handleEvent 也处理 error（`store.ts:189` executionError 写 `store.sessionError`）——双写无冲突；但 `session_already_running` 只进 store（store.ts:196），`ui.sessionError` 不更新，且 ChatPanel 的"重试"按钮 onClick 调的是 `controller.retry()`（boot 重试）而非重发消息，用户点了也无法消除"该任务仍在运行"的提示（phase 是 RUNNING 时按钮本应隐藏，但 `session_already_running` 不改 phase，按钮仍在）。
- 建议：`session_already_running` 也投影到 ui.sessionError；`retry()` 对"任务运行中"场景应只清错误而不是 boot。

### L2. `boot()` 失败重试窗口：`ws.connect()` 失败时 session 已绑定，历史未加载

- 位置：`controller.ts boot()`：`bindSession` → `ws.connect()` → `ensureHistory` 串行。若 connect 抛错（首连 15s 超时/getToken 失败），`booted` 复位、报错，但下次 `retry()` 重新 boot 时 `historyLoaded` 仍为 false，行为尚可；真正的问题是 **connect 失败后 WsClient 的 `scheduleReconnect` 已在后台自动重连**，而 `retry()`/`open()` 又会再触发一次 `boot()` → `connect()`，`connectPromise` 残留已 reject 的旧 Promise 时序上可能错过新 socket 的 auth（ws-client.ts `connect()` 中 `connectPromise` 在 auth 帧发出后才置 null，而 onclose 时已置 null 并 reject——两条路径都可能与新 connect 竞争）。desktop 端有 pendingSettle 归属校验，embed 版裁掉了该保护，存在重复 auth 或 Promise 永不 settle 的小概率窗口。
- 建议：给 ws-client 补上"settle 归属 socket 校验"或简化为 connect() 内不再复用旧 connectPromise（一旦 onclose 即丢弃）。

### L3. 历史加载阈值：`ensureHistory` 仅在 `messages.length === 0` 时写入，流式中打开浮窗会永久缺失历史

- 位置：`core/store.ts:47-56`。若任务在流式执行中用户首次打开浮窗：`appendLocalUserMessage` 只在 send 时调用，但 content_delta 可能先于 ensureHistory 到达（connect → subscribe → snapshot/content 流先回），messages 非空 → 历史分支被跳过 → 上下文不完整且 `historyLoaded=true` 不再补。虽然 snapshot 会恢复 phase，但历史 USER/ASSISTANT 轮次不会显示。
- 建议：按"消息数量 vs 服务端历史数量"合并而非二选一，或 ensureHistory 在 subscribe 之前执行（调整 boot 内顺序）。

### L4. `ContextCollector.truncateByBytes` 的初始下限用 `maxCharBytes` 推导可能溢出限长循环语义（次要）

- 位置：`context/collector.ts:31-41`。`Math.floor(limit / maxCharBytes)` 从小往大逐字符补足虽正确，但 `maxCharBytes` 取 4 时初始下限过小，8KB 上下文最坏要循环数千次且每次重新 `encode(s.slice(...))`，复杂度 O(n²)（n=8192 时约 2 万次 encode 调用，单次发送前阻塞主线程数十毫秒级）。功能正确但实现低效，建议改为"先二分/或按码点累积字节数"。
- 严重度低（性能/交互卡顿），不影响正确性。

## 其他核对过、无问题的点（记录以免重复怀疑）

- auth 首帧顺序（connect → auth → 业务帧）、心跳/静默判定（30s）、指数退避（1s→30s cap）与 desktop useStreamWS 一致。
- `normalizeClient` 增加 `embed` 与 registry 的 clientType 记录行为一致；LOCAL_CAPABLE_CLIENTS 不含 embed 是正确取舍（embed 会话默认 CLOUD）。
- executionId 去重（STREAM_EVENT_TYPES 门禁 + active/cancelled/suppress 三态）语义与 desktop `isStaleExecution` 对齐，单测覆盖合理（session_status/session_snapshot 不进门禁与 desktop 一致）。
- `cancel` 抑制：markCancelled → suppress → 新 RUNNING 带 executionId 解除，测试覆盖；后端 `handleCancel` 的 pendingCancels 窗口语义客户端无需感知。
- `tool_call_result` 字段名（`tool_call_id`、`result`、`status`）——注意 SDK store 里读的是 `data.toolCallId`/`data.error`/`data.result`，而后端实际发的是 snake_case `tool_call_id` 且**没有 `error` 字段**（error 用 `status: 'error'` 表达）！
  - **补充（审查复核时发现，建议按 H2 同级对待）**：`core/store.ts:96-103` `findToolCall` 用 `data.toolCallId` 查卡片将永远 miss（后端发 `tool_call_id`），`tool_call_args_delta` 的 `data.delta` 也不存在（后端发 `arguments`），`tool_call_result` 的 `data.error` 不存在。后果：所有工具卡片停留在 running 状态、args/result 不更新（tool_call_start 恰好能创建卡片因为 genId 兜底）。严格说这是"协议字段名不一致"类问题，本报告为避免序号调整将其并入【H2/H3 同级的协议失配】——建议单列 High 级别问题"工具卡片事件字段名与后端不一致"。
- `session-manager` 的 404 → 新建语义、503 上抛语义正确（对齐后端 FORBIDDEN=403/SESSION_NOT_FOUND=200 的错误码映射：rest-client 以 `code!=0` 判定失败，与后端 `handleError` 的 200+code 行为兼容）。
- prebuild 脚本：存在性判断、fail-fast 策略合理；唯一问题是它依赖的 sdk/embed 构建本身有 H1 的 define 缺陷，且 `desktop/public/embed/*.js` 两个 83 行的占位产物是坏产物（见 H1）。
- CI job（node20、npm ci、build/test/size-limit）配置本身可跑；size-limit 200KB 阈值合理，但注意当前坏产物（含未替换 NODE_ENV）恰好能通过 size 检查，说明 size 门禁挡不住 H1 类问题。

## 修复优先级建议

1. **立即**：H1（define NODE_ENV + 重新出产物）、H2（ui.messages 接线）、H3（messages 响应结构 + thinkingContent）——三者任一存在，SDK 首屏即不可用。
2. **随修复一并**：工具卡片字段名失配（tool_call_id/arguments/status）、M1（token invalidate）、M3（inquire 应答或移除）。
3. **可延后**：M2（审批能力取舍）、L1-L4。
