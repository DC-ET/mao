# 第 8 轮代码审查报告

- 审查范围：当前 Git 工作区未提交代码
- 重点：待绑定消息失败重试、用户消息丢失、重复执行、处理中卡片复用/错位
- 结论：发现重大功能 bug，上一轮问题仍未解决，且正常 OAuth 回调路径实际上不会触发待绑定消息恢复。

## 严重程度：高

### 1. 待绑定消息恢复仍没有可达的重试入口，且正常 GET 回调未传递 state

- **位置**：`backend-ts/src/auth/feishu-auth.service.ts:145-163`、`backend-ts/src/create-app.ts:310-324`
- **问题**：`renderCallbackPage(state, code)` 调用 `completeStateWithCode()` 后，执行回调时仅调用 `onUserAuthenticated(user, oauthState.userId)`，没有把当前 `state` 作为第三个参数传入；而 `create-app.ts` 只有在第三个参数 `state` 非空时才会 `claim()` 并执行待绑定原始消息。因此用户从飞书 OAuth 重定向进入 GET callback 的正常绑定流程，待绑定消息永远不会被恢复执行。
- **同时存在的失败重试问题**：即使其他路径传入了 state，失败时 `release()` 只把 `CLAIMED` 改回 `SENT`，OAuth state 已在此前变为 `SUCCESS`；再次打开同一回调会在 `completeStateWithCode()` 因状态不是 `PENDING` 而被拒绝，仍没有任何定时任务、恢复接口或 SUCCESS 分支重试 `SENT` 消息。
- **影响**：用户完成绑定后，原始群消息可能永久停留在 `SENT`，模型/数据库/飞书 API 的暂时性失败会造成消息丢失；在正常 GET 回调下则是稳定复现的“绑定成功但原消息不执行”。这直接违反本次需求的待绑定消息恢复目标。
- **修复建议**：确保 GET callback 将 `state` 传给绑定完成回调，并将待绑定消息恢复设计为独立、可达且幂等的流程：OAuth state 成功只负责完成绑定；之后由明确的恢复任务或内部服务按 `SENT` 领取执行，并对 `CLAIMED` 增加 lease/超时恢复。重试不得重新兑换授权码、发放登录凭据或重复绑定；应以 pending message 记录状态和原始 message_id 作为执行幂等边界。

## 其他重点核验

- **重复执行**：入站处理器正常路径仍通过 message service claim；恢复路径使用 `skipClaim=true`，且 pending 记录先 `CLAIMED`，可避免被普通飞书事件重复 claim。但 `CLAIMED` 无 lease/启动恢复机制，进程在执行中崩溃会永久卡住，仍应一并修复。
- **卡片错位**：成功发送绑定卡片后保存 `card_message_id`，恢复时传入 `progressCardMessageId` 并 patch 原卡片；该复用方向正确。但由于上述恢复入口不可达，成功绑定后的卡片通常不会进入处理中状态。若 patch 在恢复过程中失败，当前只回退 `SENT`，随后同样无法自动重试。
- **消息丢失**：未发现本轮新增的普通入站 claim/complete 逻辑会无条件吞掉已处理消息；但待绑定消息问题仍足以构成重大消息丢失风险。
