## 结论

不建议将当前变更视为已可用的页面 Agent 功能合入。主要阻塞是页面工具收发尚未闭环、请求协议与实际帧不一致，以及页面授权和执行生命周期不完整。当前 LOCAL 出站路由没有直接回归，但新增结果处理复用了 LOCAL 请求池，仍存在协议串线问题。

## 高严重度（P1）

### 1. 页面工具没有接入 Agent → SDK → pending result 的完整执行链

**位置**：`backend-ts/src/session/ws/streaming-ws-registry.ts:258-259`；`sdk/embed/src/core/ws-client.ts:373-375`；`sdk/embed/src/index.ts:63-75`；`backend-ts/src/session/ws/streaming-ws-handler.ts:611-617`。

- 全树 TS 搜索 `sendPageToolRequest`、`sendPageToolResult` 仅命中方法定义；`page_tool_request` 仅命中类型定义及 registry 发包方法。
- SDK 的 WS 事件入口 `controller.ts:482-550` 没有页面工具分支。index 仅向宿主暴露手动调用 API，没有把 page manager 接入 controller。
- 后端没有页面工具请求的 pending 注册。现有 `LocalToolSessionRegistry.sendToolRequest` 只在有 electron/cli 时创建 pending，且发送 `tool_execute`，不是 `page_tool_request`。新增 handler 调用 complete 无法完成一个未登记的页面请求。

**影响**：普通 `MaoChat.init()` 后 Agent 无法调用新能力；即便单独调用 registry 发包，SDK 也不执行、不回包。仅添加两个 send 方法并不能形成可工作的工具调用。

**建议**：增加页面工具注册及专用执行请求管理器；明确超时、取消、断线和结果完成机制；在 controller 接入页面请求分派，调用 manager/authorization/screenshot 并可靠回包。增加从工具调用到返回结果的集成测试，而非只测试扫描器。

### 2. EMBED_ONLY 是用户级广播，不是当前页面执行端路由

**位置**：`backend-ts/src/session/ws/streaming-ws-registry.ts:254-259,315-327`。

`sendPageToolRequest` 只携带 userId；deliver 取该用户所有连接并仅按 clientType=embed 过滤，没有会话所属连接、标签页或页面实例约束。信封里的 sessionId 不参与服务端目标筛选，订阅也不是连接级筛选条件。

**复现场景**：同一个用户在两个业务页面或标签页初始化 SDK，向页面 A 发页面请求时，两个 embed socket 都收到同一 requestId。接入执行器后会出现错误页面执行、重复点击，或者错误页面的失败先完成请求。即使客户端按 sessionId 过滤，共享/恢复同一 session 的多个标签页仍然无法隔离。

**建议**：任务绑定唯一的 embed connection/pageInstanceId；定向发送并校验结果来源；页面离线时明确失败，不向同用户其他页面广播接管。补双标签页、同 session 多连接、重连后旧连接回包测试。

### 3. task 授权没有任务边界，跨会话和身份继续有效

**位置**：`sdk/embed/src/index.ts:64-75`；`sdk/embed/src/authorization.ts:5-13`。

授权对象以固定 `anonymous` 创建；`task` 和 `full` 在执行入口都直接放行。newSession 只调用 controller，不 revoke；对象未订阅任务终态、stop、断线或身份切换事件，也没有 task/session/identity 标识。

**复现场景**：`setPageAuthorization('task')` 后切换新会话，再 inspect 并 execute，操作仍被允许；SSO 切换账号也不会撤销原用户的内存授权。当前“本次任务授权”实际上是实例生命周期授权。

**建议**：将授权绑定真实 identity、sessionId 和任务执行 ID，并在终态、停止、切换会话/身份、断线时撤销 task 授权；控制器向授权模块提供生命周期事件。不要仅靠宿主自行调用 revoke。

### 4. SPA 导航和页面语义变化不会使旧快照失效

**位置**：`sdk/embed/src/page.ts:85-96`。

execute 仅检查 snapshotId 等于最近一次 inspect 的 ID、元素仍在 document 且可见。pageVersion 没有在执行前比较；没有 URL/路由变化、属性变化或超时失效处理。DOM 被复用时，旧引用仍可执行。

**复现场景**：扫描“订单 A”页面，SPA 切换到订单 B 并复用同一个删除按钮，再用旧 snapshotId/elementId click；校验全部通过，却操作订单 B。`history.pushState` 后保留 DOM 即可触发相同问题。

**建议**：记录并验证页面/路由 generation，对导航和关键语义变化失效快照；动作前比较引用语义和页面版本，过期返回明确错误并要求重新 inspect。统一 pageVersion 的生成与比较规则。

## 中严重度（P2）

### 5. 新请求合同将字段放顶层，实际 WS 发包却放 data

**位置**：`shared/contracts/src/ws.ts:89-95`；`backend-ts/src/session/ws/streaming-ws-registry.ts:258-259`。

合同是 `{type,sessionId,requestId,tool,arguments}`；实际调用 `wsEvent` 发送 `{type,sessionId,data:{requestId,tool,arguments}}`。合同还要求 sessionId 为 number，发包方法却接受 null。

**影响**：按新增共享类型编写的接收器读取 requestId/tool 得到 undefined，无法分派或正确关联回包。当前宽类型 WsServerEvent/服务端 WsEvent 没有强制检查，因此类型检查不一定报错。

**建议**：统一为明确的请求信封与 payload 类型，禁止无会话页面请求；让发包和消费共同使用该类型，并增加序列化后 JSON 形状的契约测试。

### 6. page_tool_result 可以错误完成 LOCAL 请求，且丢失结构化结果字段

**位置**：`backend-ts/src/session/ws/streaming-ws-handler.ts:611-617`；关联 `backend-ts/src/harness/local/local-tool-session-registry.ts:110-127`。

handler 仅校验 session 归属，没有校验 request 的工具类别或执行端。它直接完成 LOCAL pending 池中相同 sessionId/requestId 的条目。成功仅保留 result，丢弃 snapshotId/pageVersion；失败仅保留 message，丢弃 error.code。

**复现场景**：已有一个 LOCAL pending 请求，拥有该会话的连接提交相同 ID 的 page_tool_result，该 LOCAL future 会被当作页面结果完成，真正的 electron/cli 回包随后被忽略。反过来，独立发送的页面请求因根本没有 pending 会静默丢弃（见问题 1）。结果只把版本放在合同规定的顶层字段时，后续处理也拿不到版本。

**建议**：使用独立页面 pending 池或给 pending 增加工具类别与目标连接元数据，拒绝类别/连接不符的回包；完整保留 success/result/error.code/snapshotId/pageVersion。补错误协议不能完成 LOCAL pending 的回归测试。

### 7. 默认 per_action 只有永久拒绝，没有单次批准路径；full 不会持久化

**位置**：`sdk/embed/src/index.ts:64,72-74`；`sdk/embed/src/authorization.ts:7-12`。

默认 per_action 时，execute 始终立即返回 authorization_required，没有确认 UI、pending action 或批准一次的方法。要执行只能切为 task/full，无法实现“每次确认”。此外 index 明确传入 persistFull=false，使 full 从不读取/保存，刷新后必然回到 per_action，与已确认方案的完全授权持久化行为不符。

**建议**：实现真实的单次确认及一次性授权凭据，而不是要求用户升级授权；在接通身份隔离后按方案持久化 full，并处理撤销。补默认确认后仅执行一次及 full 刷新恢复测试。

### 8. screenshot 绕过授权模块，默认也可获得未遮罩原图

**位置**：`sdk/embed/src/index.ts:75`；`sdk/embed/src/screenshot.ts:10-13`。

截图入口直接调用 render，既不检查授权，也不展示确认或遮罩。返回值始终 masked=false。因此 per_action 下虽然页面动作被拒绝，但 screenshot 仍直接产出原图；已确认方案要求该级别原图发送前确认。

**建议**：将截图纳入页面请求授权策略；低授权使用遮罩或显式确认，拒绝时不要调用 renderer。SDK 应内置默认 DOM renderer，不能把必须由业务传 renderer 当作只需 init 的完整集成。当前没有上传闭环，因此这里确认的是截图 API 授权缺失，不声称已经发生自动上传。

### 9. keyboard/不匹配的动作会返回成功但未完成操作

**位置**：`sdk/embed/src/page.ts:99-112`。

keyboard 只派发合成 keydown/keyup，这不会触发浏览器的可信默认输入行为（例如文本输入、Tab 焦点跳转、Enter 原生提交）。fill/select/check 也没有校验元素类型或验证写入结果：对普通 button 执行 fill 时无 value setter，但仍派发事件并成功；radio 的 uncheck 通过 click 无法取消已选状态，仍返回成功。动作后只等一帧就无条件 success=true。

**影响**：Agent 被告知操作完成，实际输入或选择没有变化，后续任务会基于错误状态继续。

**建议**：按元素能力限定可执行动作，验证写入后的值/checked/选项；对可实现的按键明确模拟语义，对浏览器禁止的默认行为返回不支持，不伪报成功。补原生控件、受控表单、radio uncheck 和非法 action/element 组合测试。

## Electron / CLI LOCAL 专项结论

- 最终复核的 `LOCAL_CAPABLE_CLIENTS` 仍只有 electron/cli，LOCAL_ONLY 的筛选保持原有语义；EMBED_ONLY 不会把页面请求发送给 electron/cli。
- 原有 `tool_result` / `tool_error` 分支未改；技能同步和 LOCAL 连通性判断没有因最终路由代码直接改变。
- 不能据此宣称完全无回归：问题 6 的跨协议 pending 完成仍需修复；当前已有测试没有覆盖这一情况。
