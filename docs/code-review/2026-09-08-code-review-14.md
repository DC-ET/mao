## P2

### P2-1. 确认卡片弹出时点「改为每次确认」：卡片消失但确认 Promise 不 settle，动作挂满 120s

**位置**
- `sdk/embed/src/page/authorization.ts:145-152`（`setLevel` 对降级不做任何 settle）
- `sdk/embed/src/controller.ts:294-297`（`onAuthorizationChange` 在 `level !== 'task'` 时清 `ui.pageConfirm`）
- `sdk/embed/src/ui/PageActionPanel.vue:38-40`（`level !== 'per_action'` 即显示「改为每次确认」，与确认卡片同屏）

**问题**

第 6 轮修复让升级方向以 `true` 结束挂起确认；但降级到 `per_action` 的方向被设计为「保留正在等待的确认卡片（它本身就是一次 per-action 确认）」（`authorization.ts:147-148`），而 `setLevel('per_action')` 结尾的 `emitState()` 会触发 controller 的 `onAuthorizationChange('per_action')`，后者无条件 `this.ui.pageConfirm = null`。结果是：**卡片被清掉，但 `PageAuthorization` 里的 `activeConfirm` 未 settle**，其 120s 定时器继续跑。

可复现场景（`task` 级别下唯一会弹卡片的路径是 `page_screenshot {maskSensitive:false}`，或宿主 `capturePageScreenshot({maskSensitive:false})`）：

1. 授权级别为「本次任务授权」，模型调用 `page_screenshot` 且 `maskSensitive:false` → `engine.screenshot` 调 `requestConfirmation`（`engine.ts:150-159`）弹出卡片；
2. 用户不想放开遮罩，点顶部「改为每次确认」→ `setLevel('per_action')`；
3. 卡片立即消失、无任何反馈；挂起的确认只能等 120s 定时器以 `false` 结束（`authorization.ts:238`），该 `page_screenshot` 工具要 120s 后才回包（后端超时 180s，尚不至于超时），期间整轮任务停滞。

与升级方向不同，这里既没有 `onConfirmRequest(null)` 也没有 `resolve`，属「UI 已消失但状态仍挂起」的不一致。第 6 轮报告给的建议正是「仅降级（→per_action）…以 `false` 结束」，本次实现选择了「保留卡片」却漏了同步修正 controller 的清理逻辑。

**修复建议（二选一，需保持一致）**
- 方案 A（贴合第 6 轮建议）：`setLevel` 在 `level === 'per_action'` 时改为 `this.cancelPendingConfirmations()`（以 `false` 结束），与 controller 清卡片一致；
- 方案 B（保留卡片）：去掉 `controller.ts:296` 对 `per_action` 的清空（仅在 `full` 或显式 `onConfirmRequest(null)` 时清），让卡片继续显示、用户仍可点「允许本次/拒绝」。
- 补用例：`requestConfirmation` 挂起 → `setLevel('per_action')` → 断言 Promise 立即 settle（A）或 `onConfirmRequest` 未被以 `null` 回调（B）。

**次要同类点（同一根因，一并处理）**：`setLevel('task', null)`（`authorization.ts:151-157`）会先 `approvePendingConfirmations()` 放行动作，再退回 `per_action`。当 `store.sessionId()` 为 null（身份切换窗口/旧连接残留帧）而确认卡片已弹出时，用户点「本次任务授权」会「动作被放行、级别却显示每次确认」。建议把 `approvePendingConfirmations()` 移到 `sessionId` 校验通过之后。

## P3 / 备注（不阻塞）

### P3-1. 断线/换绑以 `embed_client_not_connected` 结束在途请求，但 SDK 不会中止本地在途动作，模型重试可能造成重复副作用

**位置**
- `backend-ts/src/harness/embed-page-tool-registry.ts:108-124`（`failSession`）
- `backend-ts/src/session/ws/streaming-ws-handler.ts:143-148`（断线）、`:233-241`（换绑）
- `sdk/embed/src/controller.ts:273-278`（`onDisconnected` 只清 LLM 重试与落库计时，不 `pageEngine.cancel()`）
- `sdk/embed/src/ui/PageActionPanel.vue:51-53`（确认卡片按钮不随连接态禁用）

**问题**

断线时后端立即把在途页面工具以「可重试」语义（`embed_client_not_connected`）结束，但同一个浏览器标签页里的 `PageEngine` 仍在执行：`handlePageToolRequest` 已进入 `handleRequest`、正在 `await requestConfirmation`。此时确认卡片仍在界面上且可点击，用户点「允许本次」→ 本地动作照常执行（例如点击「提交」）→ 回包因后端 entry 已被 `failSession` 删除而被 `complete()` 丢弃。模型收到「连接不可用」后大概率重试（新 `requestId`）→ 用户再确认一次 → **同一动作执行两遍**。第 6 轮把 `task_cancelled` 改为可重试码时，未同时给 SDK 补「断线即中止本地在途动作」的对策。

**修复建议**
- `onDisconnected` 中调用 `pageEngine.cancel()`（或在重连对账时取消），使在途确认/动作以 `task_cancelled` 收敛，本地不再产生副作用；
- 或让后端在 `failSession` 的 payload 里带 `retryable:false` + 文案「该操作可能已在页面执行，请先用 page_inspect 确认状态」，避免模型直接重放点击类动作。

### P3-2. 宿主 `setPageAuthorization('task')` 会顺带放行用户正在等待的确认卡片

**位置**
- `sdk/embed/src/page/engine.ts:129-133`（`setHostLevel` 非 full 时直接走 `authorization.setLevel`）
- `sdk/embed/src/page/authorization.ts:149`（`setLevel('task')` → `approvePendingConfirmations()`）

**问题**

宿主调用 `setPageAuthorization('task')` 会触发 `approvePendingConfirmations()`，把用户当前正在逐次确认的动作直接放行。虽然宿主本就允许授予 `task` 级授权、且对页面有完全控制权，不构成实质提权，但注释与类型文档的口径是「用户刚授予更高权限才放行」（`authorization.ts:147`），宿主调用并非用户操作。若要保持语义严格，建议 `setHostLevel` 走一条不 approve 在途确认的入口（或仅在用户 UI 路径 approve）。

### P3-3（第 6 轮遗留）. 页面工具可见性在任务开始时一次性快照，`subscribe` 落后于 `send_message` 时整轮无页面工具

**位置**
- `backend-ts/src/harness/core/harness-service.ts:326`（`filterPageTools(..., isEmbedSession(sessionId))`，仅在 `loadContext` 求值一次）
- `sdk/embed/src/core/ws-client.ts:318-345, 378-398`（`subscribe` 需等 `connected` 帧才发；`sendReliable` 在 socket OPEN 后即发 `send_message`）
- `backend-ts/src/session/ws/attach-websocket.ts:41`（同连接消息未串行）

**问题**

断线重连后用户立即发送时，客户端发出的顺序是 `auth → send_message → subscribe`（`subscribe` 要等收到 `connected` 才补发），而绑定只在 `handleSubscribe` 中建立。若 `loadContext` 早于订阅处理完成，该轮任务将完全没有页面工具，Agent 只能纯文本作答（下一轮自愈）。第 6 轮已提出但本轮未处理，概率仍低（subscribe 路径明显短于 send 路径），列此备查。建议在 `handleSendMessage` 入口对 embed 连接补一次绑定，或每次 LLM 调用重新评估 `filterPageTools`。
