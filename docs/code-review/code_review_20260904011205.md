## 结论摘要

| 等级 | 数量 | 说明 |
| --- | --- | --- |
| P1 阻塞/影响主流程 | 2 | 首连时序脆弱；切任务不 detach 导致终端永不回收、配额耗尽 |
| P2 功能不完整/健壮性 | 10 | attach 结果不可知、帧丢弃无重试、exitHooked 泄漏、上限 TOCTOU、mkdirSync 无兜底、restore 不重 attach、登录强依赖 /users/me、登出残留 tab、被顶替无恢复入口 |
| P3 低/可维护性 | 13 | 审计截断、PS1 加固、tab 回退索引、冗余逻辑等 |

总体判断：后端引擎（RemoteTerminal / TerminalManager / TerminalWsHandler）实现与设计文档一致，单测覆盖较好（54 例全通过）；主要风险集中在**前端连接生命周期管理**（attach 时序、切任务与重连时的 attach/detach 收敛），其中 P1-2 会在真实使用中较快暴露（终端配额被占满）。

## P1 阻塞级

### P1-1 `auth` 与 `attach` 同 tick 连发，依赖到达顺序，首连/重连可能被 `close(1003)`

- 位置：`desktop/src/composables/useTerminalWS.ts:107-119`（`socket.onopen`）；后端 `backend-ts/src/harness/terminal/terminal-ws-handler.ts:100-121`
- 现象：`onopen` 中先 `socket.send({type:'auth',token})`，随后在同一同步块内 `for (const terminalId of attachedTerminals) socket.send({type:'attach',terminalId})`。后端 `handleTextMessage` 是 `async`，入口先 `this.connections.get(socket.id)`，未认证连接收到非 `auth` 帧即 `socket.close(1003,'Not authenticated')`（第 114 行）；`attach-websocket.ts` 的 `socket.on('message')` 用 `void handleTextMessage(...)` 派发，不做串行化。
- 影响：当前 `handleAuth` 是同步方法（第 146 行），顺序到达时 attach 能取到 conn，所以常态可用；但协议正确性完全依赖「消息按序到达且 auth 处理路径上无 await」这一隐含前提。一旦后续在 auth 前引入任何 await（如查库校验用户状态），或 ws 层出现帧合并/乱序，重连时会直接被服务端 1003 断开，触发「断开→重连→再断开」的重连风暴，终端整体不可用。
- 建议：前端改为收到服务端 `connected` 帧（`useTerminalWS.ts:86`）后再 flush `attachedTerminals` 队列；或后端把未认证连接收到的非 auth 帧改为忽略（可加计数阈值后再断开），不要立即 close。二者任一即可解除顺序依赖，建议都做。

### P1-2 切任务时不 detach 旧任务终端，旧终端被判定为 attached，永不进入 idle 回收

- 位置：`desktop/src/components/terminal/TerminalPanel.vue`（`watch(() => sessionStore.activeSessionId, ...)`）、`desktop/src/composables/useTerminal.ts:110`（`visibleTabs` 仅前端过滤）、`backend-ts/src/harness/terminal/remote-terminal.ts:205-209`（`isIdleTimeout` 首行 `if (this.sink != null) return false;`）
- 现象：切换任务时前端只做 `restoreRemoteTabs` + 重设 `activeTabId`，既不清理 `instances`/`handlers`，也不调用 `terminalWS.detach(id)`。后端 socket 仍持有旧任务终端的 sink，`isAttached()` 恒为 true。
- 影响：用户切走的旧任务终端**永远不满足 idle 超时条件**，只能靠 `maxLifetimeHours`（默认 24h）兜底。配合每任务 5 个 / 全局 50 个上限，正常使用几天内就可能把全局配额占满，表现为新建终端报「服务器终端总数已达上限」，且用户无从得知是哪些终端占用。这是本次改动中最可能被真实触发的功能性问题。
- 建议（择一）：
  1. 前端在任务切换 / 终端 tab 不可见时对不可见的 remote 终端发 `detach`，保留 xterm 实例与 handler，切回时重新 `attach`（后端 attach 支持重放缓冲，语义天然契合）；
  2. 后端 `isIdleTimeout` 改为只看 `lastActiveAt`（无输入输出即 idle），不再把 attach 状态当活跃 —— 但这与设计 3.1.11「attach 中视为活跃，避免 tail -f 被杀」冲突，需权衡；可折中为 attach 状态下用更长的 idle 阈值。
  推荐方案 1，语义最清晰，且顺带修好 P2-4（重连恢复）。

## P2 功能不完整 / 健壮性

### P2-1 `attach()` 只等连接建立，不等 attach 结果，失败静默

- 位置：`desktop/src/composables/useTerminalWS.ts:191-195`（`attach`）、`57-`（`send` 在 `readyState !== OPEN` 时静默返回 false）；调用方 `desktop/src/composables/useTerminal.ts:223`（`adoptRemoteTerminal` 内 `void terminalWS.attach(id).catch(...)`）
- 现象：`attach` 流程为 `attachedTerminals.add(id)` → `await connect()` → `send({type:'attach'})`。若此刻 socket 处于 CONNECTING/CLOSING，`send` 直接丢弃并返回 false，返回的 Promise 仍然 resolve，调用方认为成功。
- 影响：重连窗口内新建或恢复 tab 时，attach 帧丢失，终端表现为「tab 在、无输出、输入无响应」，且无任何错误提示，用户只能关闭重开。
- 建议：`send` 失败时入队，`connected` 帧到达后统一重放（与 P1-1 的 flush 队列合并实现）；`attach` 的 Promise 改为在收到 `attached` 帧或超时后 settle，让调用方可感知失败。

### P2-2 输入 / resize 帧在未 attach 时被丢弃，且会向用户弹出误导性错误

- 位置：`desktop/src/composables/useTerminalWS.ts:202-210`（`sendInput` / `sendResize` 直接 `send`，失败即丢）；后端 `backend-ts/src/harness/terminal/terminal-ws-handler.ts:279-289`（`requireAttached` 未绑定时回 `TERMINAL_FORBIDDEN`「终端未绑定到当前连接」）；前端错误展示在 `useTerminal.ts` 的 `onError` 默认分支 `ElMessage.error(message)`
- 现象：断线重连窗口内用户敲键，帧要么被前端丢弃，要么到达后端后因未 attach 被拒；后者会弹出「终端未绑定到当前连接」的红色 toast。
- 影响：用户看到与真实原因（正在重连）无关的报错，容易误判为权限或数据问题；同时按键丢失无提示。
- 建议：前端在未 `connected` 时对输入做短暂缓冲或在终端内打印「连接中断，正在重连…」提示；对 `TERMINAL_FORBIDDEN` 且处于重连窗口的情况降级为 console 日志，不弹 toast。

### P2-3 主动关闭终端不触发 `onExit`，`exitHooked` 条目永不清理，已 attach 的其它连接也收不到 `exit`

- 位置：`backend-ts/src/harness/terminal/terminal-manager.ts:230-238`（`close()`：先 `forget` 再 `terminal.close()`）；`backend-ts/src/harness/terminal/remote-terminal.ts:215-226`（`close()` 内先 `this.sink = null; this.exitListeners = []` 再 `pty.kill()`）；`backend-ts/src/harness/terminal/terminal-ws-handler.ts:94/229-231/305-306`
- 现象：`RemoteTerminal.close()` 在 kill 之前已清空 `exitListeners`，因此主动关闭路径（REST DELETE、`closeBySession`、idle/lifetime 回收中的 `close`）**不会触发任何 `onExit` 回调**。而 `TerminalWsHandler.exitHooked` 仅在 `handleTerminalExit`（第 306 行）与 `handleReclaimed`（第 315 行）中 delete。
- 影响：
  1. 内存泄漏：经 REST DELETE 关闭的 terminalId 会永久留在 `exitHooked` Set 中，长期运行无界增长（单条仅字符串，量级小但确实不回收）；
  2. 更实际的问题：某终端被 A 端主动关闭时，同一终端上其它 attach 中的连接收不到 `exit` 帧，前端 tab 残留，直到用户重开面板触发 `restoreRemoteTabs` 才提示「终端已被回收」。
- 建议：给 `TerminalManager.close()` 增加关闭通知钩子（复用现有 `notifyReclaimed` 或新增 `onClosed`），由 handler 统一 `exitHooked.delete(id)` 并向所有 attach 中的连接补发 `exit`/`reclaimed` 帧。

### P2-4 `restoreRemoteTabs` 对已有实例的终端不重新 attach

- 位置：`desktop/src/composables/useTerminal.ts:296-322`，其中 `for (const info of list) { if (!instances.has(info.terminalId)) adoptRemoteTerminal(info, sessionId) }`
- 现象：本地已有 xterm 实例的终端，恢复流程什么都不做；而 attach 状态可能因重连（P1-1/P2-1）或断连而失效。
- 影响：切回任务或重开面板后出现「tab 在但无输出、输入无响应」，且恢复逻辑本身无法自愈。
- 建议：对已有实例的终端也执行 `terminalWS.attach(info.terminalId)`。该调用是幂等的 —— `RemoteTerminal.attach`（`remote-terminal.ts:167-171`）对相同 socketId 返回 null，不会误触发顶替。

### P2-5 `create()` 上限检查存在 TOCTOU，并发创建可突破配额

- 位置：`backend-ts/src/harness/terminal/terminal-manager.ts:147-186`
- 现象：顺序为 `pruneDead()` → 检查 `existing.size >= maxSessionsPerTask` / `this.terminals.size >= maxSessionsGlobal` → **`await this.buildEnv(params)`**（内部 `await getTokenMapByUser`、`await userLookup.findById`）→ spawn → `terminals.set` / `existing.add`。检查与注册之间存在 await 间隙。
- 影响：用户快速连点 `+` 或多端并发创建时，可同时通过检查，实际创建数超过每任务 5 / 全局 50 上限，绕过配额保护。
- 建议：检查通过后立即占位（先把 terminalId 放入 `existing` 与一个 pending 计数，失败路径回滚），或在 spawn 完成、注册之前复核一次上限，超限则关闭刚创建的 PTY 并抛 `TerminalLimitError`。

### P2-6 `configureUserHome` 的 `mkdirSync` 未做异常兜底，失败时 500 且不写审计

- 位置：`backend-ts/src/harness/terminal/terminal-manager.ts:372-376`（`mkdirSync(userHome, { recursive: true })` 裸调用，同函数内 `chmodSync` 有 try/catch）
- 现象：`/opt/mao-data/users` 不可写或权限异常时，`create()` 抛出的是原始 fs 错误，而非 `TerminalSpawnError`。`backend-ts/src/session/terminal.routes.ts` 的 catch 只识别 `TerminalLimitError` / `TerminalSpawnError`，其余 `throw e` → `handleError` 返回 500 `INTERNAL_ERROR`。
- 影响：错误处理路径不一致 —— 用户看到无信息量的 500；同时**不会写入 CREATE 失败审计**，运维排查时该次失败在审计日志中完全不可见。
- 建议：把 `mkdirSync` 及后续文件写入统一包进 try/catch 并转换为 `TerminalSpawnError`（携带原因），使其走既有的「友好错误 + 失败审计」路径。

### P2-7 `applyLogin` 强依赖 `/users/me`，弱网时表现为「登录失败但其实已登录」

- 位置：`desktop/src/stores/auth.ts:71-77`（`applyLogin` 内 `await setTokens(...)` 后 `await fetchUserInfo()`，无 try/catch）、`118-121`（`fetchUserInfo` 直接 `api.get('/users/me')`）
- 现象：token 已写入本地存储后，若 `/users/me` 因弱网或 5xx 失败，异常会一路抛到 `login()` 的调用方，登录页展示失败。
- 影响：用户实际已持有有效 token，但被留在登录页；对照 `desktop/src/router/index.ts` 的 beforeEach 对 `fetchUserInfo()` 做了 try/catch 并注明「其它错误不阻断导航，避免弱网被踢出」，本次新引入的 `applyLogin` 路径破坏了既有容错策略。
- 建议：`await fetchUserInfo().catch(() => {})`；权限相关的按钮门禁本就有 router 守卫的补拉兜底，缺失 permissions 时按不可用渲染即可，不必阻断登录。

### P2-8 飞书扫码登录继承 P2-7 风险

- 位置：`desktop/src/stores/auth.ts:97-103`（`pollFeishuLogin` 内 `await applyLogin(data.login)`）
- 现象/影响：同 P2-7。轮询期间一次 `/users/me` 抖动即导致扫码成功却提示登录失败，且轮询状态已消费，用户需重新扫码。
- 建议：随 P2-7 一并修复即可。

### P2-9 登出后终端 tab 与实例残留，重新登录出现「有 tab 无输出」

- 位置：`desktop/src/stores/auth.ts:61-69`（`clearLocalSession` 新增 `useTerminalWS().disconnect()`）；`desktop/src/composables/useTerminalWS.ts:216-224`（`disconnect` 内 `attachedTerminals.clear()` + `handlers.clear()`）；`desktop/src/composables/useTerminal.ts` 模块级 `tabs`/`instances` 无 reset 出口
- 现象：`disconnect()` 清掉了 WS 侧的 handler 注册，但 `useTerminal` 的模块级 `tabs` / `instances` 未清理（其它 store 都有 `reset()`）。
- 影响：在同一页面内登出再登录（未刷新），旧 remote tab 仍在 `tabs` 中且 handler 已失效；若新会话的 sessionId 与旧 tab 匹配，`visibleTabs` 还会把它显示出来，表现为「有 tab 无输出、无法输入」。
- 建议：`useTerminal` 暴露 `reset()`（dispose 所有 xterm 实例、清空 `tabs`/`instances`/`activeTabId`），在 `clearLocalSession` 中与其它 store 的 reset 一起调用。

### P2-10 被顶替（`TERMINAL_TAKEN_OVER`）后无恢复入口

- 位置：`desktop/src/composables/useTerminal.ts:247-`（onError 中 `TERMINAL_TAKEN_OVER` 分支仅写一行提示）；`desktop/src/composables/useTerminalWS.ts:81`（`attachedTerminals.delete(terminalId)`，该处处理正确）
- 现象：终端被另一个标签页接管后，本端 tab 保留但已从 `attachedTerminals` 移除，此后重连也不会再 attach，tab 永久失活；提示文案未告知恢复方式。
- 影响：用户只能关闭 tab 再重开（且需知道「重开不会杀进程」这一语义），交互上像是终端坏了。
- 建议：在终端内提示「已在其它窗口打开，点击此处重新接管」，或提供显式「重新接管」按钮调用 `terminalWS.attach(id)`；这也顺带解决多窗口互相顶替时的可恢复性。

## P3 低 / 可维护性

### P3-1 `exit` / `reclaimed` 通知只覆盖当前 attach 的连接

- 位置：`backend-ts/src/harness/terminal/terminal-ws-handler.ts:305-317`，`handleTerminalExit` 与 `handleReclaimed` 均以 `if (!conn.terminals.delete(terminalId)) continue;` 跳过未绑定连接。
- 影响：未 attach 的 tab 收不到退出事件，需等下次 `restoreRemoteTabs` 才清理，属最终一致，可接受。与 P1-2、P2-3 同源，修复其一即缓解。

### P3-2 DELETE 对「已死但未清理」的终端走幂等分支，跨用户探测返回 code=0

- 位置：`backend-ts/src/session/terminal.routes.ts:84-100`。`terminalManager.get()` 对 `!isAlive()` 会先 `forget` 再返回 null，随后直接 `sendOk(reply, null)`，跳过归属校验。
- 影响：他人 terminalId 若恰好已死，调用方得到成功而非 403，泄露「该 id 曾存在」这一极弱信息。幂等语义本身合理，建议在 `get()` 返回 null 时也校验 sessionId 归属后再返回成功。

### P3-3 `closeBySession` 重复清理

- 位置：`backend-ts/src/harness/terminal/terminal-manager.ts:242-269`。`close()` 内部已 `forget`（会删 `sessionTerminals` 条目），外层再 `delete(sessionId)`；无终端分支也 `delete` 一个不存在的 key。功能正确，仅冗余。

### P3-4 `sessionTerminals.set(sessionId, existing)` 每次创建都重复 set

- 位置：`backend-ts/src/harness/terminal/terminal-manager.ts:186` 附近。同一 Set 引用重复写入 Map，无害，可省。

### P3-5 终端审计的 `errorMessage` 未截断

- 位置：`backend-ts/src/create-app.ts` 的 `terminalAudit`（约 590-606 行）直接构造 `AuditLog` 调 `auditService.record()`，绕过 `recordAudit` 的 1024 字符截断。
- 核实：`audit_log`（V048）中 `method VARCHAR(16)`、`path VARCHAR(512)`、`action VARCHAR(32)`、`object_type VARCHAR(64)` 均 NOT NULL，本次五类事件取值长度与非空都满足，无 DB 约束风险。仅 `errorMessage` 缺截断，PTY 启动失败消息通常很短，风险低。
- 建议：与 `recordAudit` 共用截断工具，避免异常长 message 写库失败。

### P3-6 spawn 失败的 CREATE 审计携带未注册的 terminalId

- 位置：`backend-ts/src/harness/terminal/terminal-manager.ts` create 的 catch 分支。与设计 7.7 一致，仅备注：审计里的 terminalId 在注册表中不存在，查询关联时需注意。

### P3-7 `normalizeTaskName` 未剥离反引号与 `$`，PS1 渲染时理论上可命令替换

- 位置：`backend-ts/src/harness/terminal/terminal-manager.ts:428-`（过滤了单引号与控制字符）+ `DEFAULT_BASHRC` 中 `PS1='...${MAO_TASK_NAME:-task}...'`
- 核实：bashrc 落盘内容确为单引号包裹（赋值时不展开），但 bash 在渲染提示符时默认 `promptvars` 为 on，会对 PS1 做参数展开**与命令替换**。因此任务名含 `$(...)` 或反引号时，理论上会在每次渲染提示符时执行。
- 影响：终端本身即该用户的 root shell（设计 11.1 已明确「terminal:use 等于 root shell」），无提权收益，实际影响为零。
- 建议：作为纵深防御，`normalizeTaskName` 顺手剥离 `` ` `` 与 `$`。

### P3-8 `removeTab` 用全量 tabs 下标去索引 visibleTabs

- 位置：`desktop/src/composables/useTerminal.ts:379-389`。`idx` 来自 `tabs.value.findIndex`，随后用于 `remaining = visibleTabs.value` 的索引。
- 影响：同时存在 local tab 与多任务 remote tab 时序号错位，关闭 tab 后可能激活非预期 tab；因有 `Math.min` 夹取不会越界崩溃。
- 建议：`idx` 改为在 `visibleTabs` 中查找。

### P3-9 `closeTerminal` 未校验 `tab.sessionId` 非空

- 位置：`desktop/src/composables/useTerminal.ts:356-362`，`api.delete(\`/sessions/${tab.sessionId}/terminals/${id}\`)`。类型上 `sessionId: string | null`，为 null 时会请求 `/sessions/null/...`。
- 影响：当前 remote tab 必定带 sessionId（由 `adoptRemoteTerminal(info, sessionId)` 保证），不会触发。建议加一条防御性判空。

### P3-10 面板内 `+` 按钮不做权限预判

- 位置：`desktop/src/components/terminal/TerminalPanel.vue` 的 `handleCreate()` 直接 `createTerminal`；`desktop/src/composables/useTerminal.ts:393-401` 的 `togglePanel` 在无 tab 时也直接创建。
- 影响：入口层（`TopNav.vue` 的 `terminalAvailability` + `toggleTerminal()` 首行 return，含 Ctrl+` 快捷键）已有守卫；面板内 `+` 依赖后端 403 + 拦截器 toast「无权限: terminal:use」，可接受。

### P3-11 切 tab 后旧 search addon 的高亮未清理

- 位置：`desktop/src/components/terminal/TerminalPanel.vue` 的 `subscribeSearchResults` / `closeSearch`（`closeSearch` 依赖 `searchVisible` 早退）。属视觉残留，不影响功能。

### P3-12 `TERMINAL_INT_KEYS` 与 `HARNESS_INT_KEYS` 校验逻辑重复
