# 代码审查报告：飞书入站消息队列（inbound queue）

- 日期：2026-08-27
- 范围：`backend-ts/src/feishu/`（inbound-queue.*、agent-inbound-handler、card-action.service、monitor.service、card-progress-listener、create-app.ts 组装）与 `db/migration/V088__feishu_inbound_queue.sql`
- 结论：整体设计清晰、状态机与 CAS 语义正确、单元测试覆盖到位。以下按严重程度列出需要注意的问题，多数为边界 / 竞态层面，不阻塞业务主流程。

---

## 高

### H1. 卡片按钮 `action.value` 类型不一致，可能导致「立即发送 / 取消本次任务」整体失效

**位置**
- 构建端：`create-app.ts` `buildFeishuQueueCard` → `actionValue = (act) => JSON.stringify({ kind:'feishu_queue', queueId, act })`，即按钮 `value` 是 **JSON 字符串**。
- 消费端：`card-action.service.ts` `parseActionValue`：

```ts
if (value == null || typeof value !== 'object') return null;   // 只接受对象
```

**问题**
卡片在 `create-app.ts` 里以 `JSON.stringify(...)` 写入按钮 `value`；而回调处理器只认 `typeof value === 'object'`，两者不一致。SDK 侧 `@larksuiteoapi/node-sdk` 的 `cardActionId()`（`lib/index.js`）专门用了 `typeof action.value === 'string' ? ... : JSON.stringify(...)` 分支，说明飞书回调里 `action.value` **既可能是对象也可能是字符串**（取决于你定义时传入的类型）。当前实现如果收到字符串，`parseActionValue` 直接返回 `null` → `handle` 返回 `undefined`，按钮点击**静默无效**，卡片的打断/取消/插队全部失效。

**建议**
- 在 `parseActionValue` 中先兼容字符串：`typeof value === 'string'` 时先 `JSON.parse`，解析失败再返回 `null`；对象路径保持不变。
- 或者在构建端直接传对象而非 `JSON.stringify`（与进度卡 value 方式对齐），但建议双向兼容更稳妥。

## 中

### M1. 重启时 `hydrate()` 触发的队列消费与 `CrashRecoveryRunner` 续跑存在同会话并行执行风险

**位置**
- `create-app.ts`：`feishuTaskQueue.hydrate().then(... drainNextIfPending)`（启动即挂载）
- `create-app.ts`：`crash.run()` / `CrashRecoveryRunner.onExecutionFinished` 钩子
- `agent-inbound-handler.ts`：`busy` set 只记录经 `onMessage` / `drainNext` 启动的执行

**问题**
`drainNext` / `drainNextIfPending` 的互斥依赖 `busy` set 与 `withLock`，但 `busy` 只感知「由 handler 启动」的会话执行。`CrashRecoveryRunner.recoverSession` 是**另一条独立路径**，它直接调用 `harness.execute`，不写入 handler 的 `busy`。

在「会话表 phase=RUNNING（崩溃前正在执行任务 A）+ 排队表有 QUEUED 行 B」的场景下重启：
1. `hydrate()` 复位 RUNNING 行并把该 session 列为待消费，随即 `drainNextIfPending` → 因 handler `busy` 为空，直接认领 B 并执行；
2. 同时 `CrashRecoveryRunner` 收集到该会话 phase=RUNNING，开始续跑 A。

两者在同一 `sessionId` 上各自 `harness.execute`，**并发写入同一会话上下文**，且设计文档 §8.5 期望的顺序是「先恢复 A，A 收尾后再消费 B」。当前实现未做该顺序约束（`busy` 不包含被恢复的会话），存在双重执行风险。

**建议**
- 在 `hydrate()` 的启动消费路径与 `CrashRecovery` 的恢复路径之间建立互斥：例如 `onExecutionFinished` 恢复钩子在 CrashRecovery 恢复结束**后**才允许 `drainNextIfPending`；启动 `hydrate` 的 `drainNextIfPending` 对「即将被 CrashRecovery 恢复的会话」延后到恢复完成之后触发，或让恢复路径把 `sessionId` 标记进 handler 的 `busy`。
- 至少保证同一 `sessionId` 的 `hydrate` 消费与 CrashRecovery 续跑不会同时进行（可加会话级启动锁）。

## 低

### L1. `parseActionValue` 校验了 `queueId` 但从未使用，行定位只走 `cardMessageId`

**位置**
`card-action.service.ts` `handle` → `findByCardMessageId(cardMessageId)`；`queueId` 仅 `Number.isFinite` 校验后丢弃。

**影响**
`queueId` 与 `row.id` 未被交叉核对。若同一 `card_message_id` 因异常被复用（`findByCardMessageId` 用 `ORDER BY id DESC LIMIT 1`），可能落到非预期行。功能上因为 `card_message_id` 通常全局唯一、影响很小，但 `queueId` 既然从按钮传入就应作为行定位的一条依据，避免「卡片归属不一致」时误操作。

**建议**
`handleRun` / `handleCancel` 在拿到 `row` 后校验 `row.id === queueId`，不一致则按「消息已失效」处理。

### L2. `executeQueued` 中 `reconstructFromQueue` 在 try/finally 之外抛出会导致队列行永久 RUNNING

**位置**
`agent-inbound-handler.ts` `executeQueued`：

```ts
const { context, message } = reconstructFromQueue(row);   // JSON.parse(payload)，可在此抛错
...
try { ... } finally { ...; await this.queueService.complete(row.id); ... }
```

**影响**
若 `payload` 因数据损坏 `JSON.parse` 失败，`reconstructFromQueue` 在进入 `try` 前抛出，`complete(row.id)` 不会执行，该行保持 `RUNNING` 且不被 `claimNext`（只认 `QUEUED`）拾取，队列在该行卡死，直到重启由 `hydrate` 复位。当前 `drainNext` 的 `busy.delete` 仍会执行（外层的 try/finally），但行状态未清理。

**建议**
把 `reconstructFromQueue` 移入 `try`，或在 `drainNext` 的 finally 里对该行做兜底清理（`complete`），并对 `JSON.parse` 失败记录告警。

### L3. `messageId` 兜底值 `no-id-${Date.now()}` 在 `uk_bot_message` 唯一键下可能冲突

**位置**
`agent-inbound-handler.ts` `enqueueMessage`：`messageId: context.messageId ?? \`no-id-${Date.now()}\``。

**影响**
极短时间窗内两条无 `messageId` 的消息会产生相同 `no-id-...`，触发唯一键冲突后走 `enqueue` 的幂等回退路径，导致第二条被误判为「已入队」而丢弃。飞书消息通常都有 messageId，触发概率极低。

**建议**
使用更稳的唯一兜底（如 `no-id-${Date.now()}-${randomUUID()}`）或直接拒绝无 messageId 的消息入队。

### L4. `findMinRankForUpdate` 为死代码

**位置**
`inbound-queue.repository.ts`：`findMinRankForUpdate` 定义后从无调用方（`jumpToFront` 用的是不带 `FOR UPDATE` 的 `findById` + `queryOne`）。

**影响**
无功能影响，仅冗余。若原意是「插队也要锁最小 rank」，则当前 `jumpToFront` 读取 min 未加锁，双实例并发插队可能出现 rank 相同、序不够精确（但 `id ASC` 兜底排序，仍可消费）。

**建议**
删除未用方法，或让 `jumpToFront` 在事务内用 `FOR UPDATE` 读 min 后再更新 rank，保证插队顺序在并发下严格单调。

## 验证情况（无问题的点）

- **并发/竞态主路径**：`onMessage` 忙时路径不持锁直接入队；空闲路径 `withLock` + 内部 `busy` 双检。两条 onMessage 并发到同一私聊时，内层双检会把后到者转为入队，不会双重直接执行；`drainNext` 与 `onMessage` 通过 `withLock` + `busy` + CAS 认领，避免重复消费。设计是健全的，仅 M1 的「启动恢复 + CrashRecovery」这一条未覆盖。
- **队列状态机**：`QUEUED→RUNNING`（CAS 认领）、`QUEUED→CANCELLED`（CAS 后删行）正确；`jumpToFront` 用 `minRank-1`，BIGINT 下反复减一不会越界，`order by rank_no` 保序。
- **卡片鉴权**：非本人返回 toast、行已 RUNNING 返回「已在执行」、行不存在返回「已失效」，分支正确；卡片 PATCH 失败用 `console.warn` 吞掉不影响主流程（符合「PATCH 失败不进主流程」要求）。
- **消息还原**：queue payload 存 `buildMessage` 产物与上下文子集，`reconstructFromQueue` 还原时 `progressCardMessageId=row.cardMessageId` 使排队卡 → 进度卡的「一卡到底」PATCH 生效；媒体在入队时已下载固化，消费时不重复下载，上下文子集足以喂进度卡与 `sendFeishuText`。
- **变更语义回归**：移除自动打断后，直接路径的 `execute` 仍被 `await`（inbound claim 语义保持）；`executeDirect`/`executeQueued` 内部统一调用 `onReply`，`onMessage` 恒返回 `null`，inbound-processor 不会再走 `sendReply`，**无重复发送**；返回 null（已通过进度卡呈现）时也不再发文本，符合设计。
- **类型与接线**：`FeishuTaskQueuePort` / `FeishuCardActionPort` 满足 handler 与 card-action 调用；`create-app.ts` 组装（queueService、createQueueCard、resolveBotId、interrupt、patchCard）接线正确。
- **测试**：4 个相关 spec 全部通过（37 用例），`tsc --noEmit`（build 配置排除 spec）通过。

> 附注：spec 通过 `npx tsc -p tsconfig.json`（含 spec 的全局配置）时会因 mock 类型推断报错（如 `card-action.service.spec.ts` 的 `cancel` 返回 `Promise<string>` 非字面量），但这是测试 mock 的类型问题，不影响构建，且 `tsconfig.build.json` 排除 spec；非本次功能缺陷，未列入。
