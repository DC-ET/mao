## 二、一般问题

### 【一般】1. 追问 USER 消息落库后可能被 `cleanupIncompleteTail` 误删，追问静默失效

- **位置**：`DelegateFollowupTool.java`（保存追问 USER → `buildSubContext` → `buildContext` → `cleanupIncompleteTailAfterId`）
- **问题**：追问流程是「先落库追问 USER 消息，再加载历史」。若子代理上次执行以异常中断收尾（工具结果缺失），`cleanupIncompleteTail` 会删除 cutIndex 之后全部消息，包括刚落库的追问 USER 消息 → 子代理重复执行首次任务（全量重审），追问静默失效。追问允许对 FAILED 子会话发起，异常中断场景真实存在。
- **修复**：在落库追问 USER 消息**之前**，先以与 `buildContext` 同粒度（`loadValidated` + `boundaryOf`）调用 `cleanupIncompleteTailAfterId`，确保落库消息不会被后续清理误删。

### 【一般】2. 追问被取消时，子会话 `phase` 终态被覆盖（COMPLETED → CANCELLED）

- **位置**：`DelegateFollowupTool.java`（原子抢占置 RUNNING + cancelled 分支 `finishSubagent(CANCELLED)`）
- **问题**：父会话在追问开始前已被取消（skip 路径）时，一个已完成（COMPLETED）的子会话终态会被改写为 CANCELLED，「已完成」历史被抹掉。
- **修复**：skip 且原子抢占前原 phase 为终态时，将 phase 恢复为原终态（经 mapper 直接置回）；`finishSubagent(CANCELLED)` 调用保持，由 `TaskTerminalService` 终态守卫拦截不覆盖 phase，仅本条审计记录标记 CANCELLED。

## 三、轻微问题

### 【轻微】3. 抢占前异常也会向子会话写入「执行失败」ASSISTANT 消息，污染历史

- **位置**：`DelegateFollowupTool.java` catch 块（`failCreatedSubagent` 调用）
- **问题**：若异常发生在原子抢占之前（反查/定义解析失败），仍调用 `failCreatedSubagent` 写入虚假失败消息，污染子代理历史。
- **修复**：仅当 `claimed == true`（已抢占执行权、追问已开始）才走 `failCreatedSubagent` 收尾；抢占前异常直接返回错误。

### 【轻微】4. `totalRounds` 语义不一致（skip 路径为 0，且仅含本次追问轮数）

- **位置**：`DelegateFollowupTool.java`（`markExecutionTerminal(..., subContext.getCurrentRound(), ...)`）
- **处理决定**：**不改**。与 `delegate` 既有行为一致（`total_rounds` 均表示本次执行的轮数），skip 路径为 0 表达「未执行」语义合理。

### 【轻微】5. 摘要不含 `child_session_id`，长上下文 compaction 后主代理可能失去追问能力

- **位置**：`ToolResultSummarizer.java`（`delegate` / `delegate_followup` 摘要）
- **问题**：上下文压缩后 tool 消息被摘要化，摘要不含 `child_session_id`，主代理无法再定位子会话发起追问。
- **修复**：新增 `summarizeDelegate`，摘要保留 `child_session_id`（如「委派子代理 #1035 (成功)」）。

### 【轻微】6. 原子抢占的 `.ne(phase, "RUNNING")` 对 `phase=NULL` 的行无效

- **处理决定**：**不改**。追问场景子会话必有执行记录（`resolveAgentType` 前置校验），phase 不可能是 NULL，不构成实际故障。

### 【轻微】7. `resultText` 透传超长结果给主代理上下文

- **处理决定**：**不改**。与 `delegate` 既有行为一致，非本需求新问题。
