## 低

### 低-1. L1 时间窗以「长按触发时刻」为锚：长按保持超过 ~900ms 后松手，合成 click 穿透直接打开任务

- **位置**：`desktop/src/components/task/SideTaskList.vue`（`onTouchStart` 定时回调设置 `suppressClickUntil = Date.now() + 400`、`onTouchEnd`、`handleClick`）
- **场景**：合成 click 只会在 touchend 之后派发，而窗口是从长按触发（touchstart + 500ms）起算的 400ms（即 touchstart 后 500~900ms 之间过期）。若用户长按保持超过 ~900ms 才松手（浏览长按菜单是常见节奏），click 落在窗口之外：
  - `handleClick` 通过时间检查 → `closeContextMenu()` + `emit('open-side-task')` → **菜单关闭、任务被误打开**，用户的菜单操作（升级/重命名/删除）丢失。
  - `onTouchMove` 中 `suppressClickUntil = 0` 会加剧该问题：长按已触发后再拖动 >10px 松手，同样穿透。
- **对比**：旧一次性标志方案在该场景反而正确（首个 click 无论多晚都被消费），旧方案的问题是 Android Chrome 等不派发合成 click 时标志残留。新方案修好了 A 场景、回归了 B 场景。
- **触发条件**：浏览器在长按松手后仍派发合成 click（iOS Safari 行为符合；Android Chrome 长按后通常不派发 click，不受影响），且长按保持 > 900ms 或触发后拖动。可恢复（再点一次菜单项已不可能——菜单已关，需重新长按），非数据性错误。
- **建议**：把窗口锚点从「长按触发时刻」改到「touchend 时刻」——在 `onTouchEnd` 中检测长按已触发（`longPressTimer === null` 且本 touch 序列打开过菜单，可用标志记录），再设置 `suppressClickUntil = Date.now() + 400`；同时移除 `onTouchMove` 中的 `suppressClickUntil = 0`（改为仅 `clearLongPress()`），因为对未触发的长按窗口本来就是 0，对已触发的清零只会有害。

## 提示（不影响主流程合入）

### 提示-1. WeixinBotView confirm 重试期间，弹窗状态文案误显示「绑定成功！」

- **位置**：`desktop/src/views/settings/WeixinBotView.vue:209`（`scanStatus.value = data.status`）与 `:67`（`v-else-if="scanStatus === 'confirmed'"` → 绑定成功！）
- confirm POST 失败进入重试时，`scanStatus` 已在进入分支**之前**被置为 `'confirmed'`，弹窗显示「绑定成功！」，与前 2 次的「绑定确认失败，正在重试…」toast 自相矛盾；与 213 行注释宣称的「失败时保持轮询与『请确认登录』提示」不符。该赋值语句是 HEAD 既有代码（非本轮引入），但本轮修复注释声称覆盖了该提示而实际未覆盖。
- 核心行为（不弹成功 toast、不关弹窗、持续重试、成功后才收尾）均正确。
- **建议**：`scanStatus = 'confirmed'` 只在 confirm 成功后赋值（第 238 行已有一处，移除 209 行的提前赋值或失败分支回滚为 `'scaned'`），让重试期间显示「已扫码，请确认登录」。

### 提示-2. 发送主链路的 `await connect()` 仍无超时，与 M1 的 15s 体验不一致

- **位置**：`desktop/src/composables/useChat.ts:291（prepareAndSendMessage）/613（restoreSession）/753/766/774/782（队列操作）/884`
- M1 只覆盖了 sendReliable 内部的重连等待；发送主链路（发消息/队列操作/会话恢复）的裸 `await connect()` 在 TCP 黑洞下仍依赖 OS TCP 超时（约 75~130s）才解除，期间 `sending=true` 无反馈。属既有模式（HEAD 相同），本轮未恶化；若追求一致性可在这些调用点复用 `withTimeout(connect(), 15_000)`（restoreSession 处已有 try/catch，改造成本低）。

### 提示-3.（既有）disconnect() 发生在 CONNECTING 期间会使 connectPromise 永久挂起

- **位置**：`desktop/src/composables/useStreamWS.ts`（disconnect 未清理 connectPromise；onclose 守卫 `event.target !== ws` 提前返回，该守卫在 HEAD 已存在）
- 登出若恰逢连接建立中，connectPromise 变为孤儿 promise，之后所有 `connect()` 复用它 → WS 永久失效直至刷新。触发窗口窄（连接建立中的登出）。sendReliable 路径经 M1 已 15s 有界；裸 `await connect()` 路径仍会永久挂起。**非本次修复引入**，建议后续在 `disconnect()` 中显式 `connectPromise = null` 收尾。

### 提示-4. L5 删除失败时出现双重 toast

- `stores/session.ts` 的拦截器已对 API 错误统一 toast，`TaskIndexPanel` 两个调用方又弹「删除失败，请稍后重试」，同一失败用户会看到两条提示。轻微，可不处理；若想去重，调用方 toast 可改为仅在拦截器未提示的场景（如 `skipErrorToast`）弹出。
