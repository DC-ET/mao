## 中严重度

### [中] 进度卡片的 loop round 与工具摘要只会在整个 Agent 执行结束时更新，无法反映多轮循环

**位置**：
- `backend-ts/src/feishu/card-progress-listener.ts:35-39`
- `backend-ts/src/harness/core/agent-loop.ts:426`

`FeishuCardProgressListener` 仅在 `onMessageEnd` 中递增 `round`、排队 RUNNING 更新并清空本轮内容/工具；而 `AgentLoop` 的 `listener.onMessageEnd(context.totalUsage)` 位于循环结束后的统一收尾位置，并不是每个 LLM loop round 的回调。因此一次包含“LLM 输出 → 工具调用 → 下一轮 LLM”的执行过程中，监听器不会在各轮边界更新卡片，最终通常只产生一次 `RUNNING` 更新，且 `round` 仍为 1；卡片中的工具摘要也只能展示最后一次收到的工具事件，之前轮次的摘要不会被展示。

这会使“处理中”卡片无法按 loop round 展示进度，用户在长时间、多工具、多轮任务中看不到中间状态；同时第 N 轮的摘要/轮次信息会被错误地标成第 1 轮。现有 `card-progress-listener.spec.ts` 只手动调用一次 `onMessageEnd`，未覆盖真实 AgentLoop 的多轮调用时序，因此测试无法捕获该问题。

**修复建议**：在 AgentLoop 的真实每轮边界（完成当前流、工具执行并持久化后，进入下一次 LLM 请求前）增加专用于进度的 round-end 事件，或明确调用监听器的 round 更新方法；不要复用只在整个 `run` 收尾触发的 `onMessageEnd` 作为轮次事件。该事件应携带当前轮的文本和按 toolCallId 匹配后的工具摘要，并在监听器完成发送/排队后再清理本轮状态。补充至少两轮、每轮含工具调用的 AgentLoop/handler 集成测试，断言卡片依次收到 round 1、round 2 的 RUNNING 更新以及各自的工具摘要。

## 已核验未发现问题

- **成功/失败文本分支**：终态卡片更新成功时 handler 返回 `null`，避免普通文本重复发送；卡片创建失败或终态 patch 失败时返回纯文本兜底。失败/取消终态 patch 成功时不再额外发送文本。
- **处理中卡片时机**：卡片在 Agent 执行前创建；创建异常被隔离并继续执行 Agent，未见卡片故障阻断主业务。
- **群聊引用与私聊目标**：群聊优先通过入站 `message_id` reply，缺少该 ID 时使用 `chat_id`；私聊使用 sender 的 `open_id`，与普通文本发送分支一致。
- **更新频率与并发**：卡片更新通过 Promise 串行化，并在同一卡片 patch 之间至少等待 250ms；未发现按文本 delta 高频 patch 或同卡片并发 patch。
- **异常处理**：卡片 patch 异常被吞掉并返回失败标记，主 Agent 失败仍会执行失败卡片/文本兜底；构建及重点测试通过。
