## P2：常规功能修复

### R5. 账号切换后 WS 仍使用旧账号的到期时间，新账号续期可能被误判超时并断线

**代码位置**
- `sdk/embed/src/controller.ts:192-194`：setIdentity 返回 changed=true 时跳过 refreshAuth，因此没有传入新账号的 expiresAt。
- `sdk/embed/src/core/ws-client.ts:57,63-65,80-84`：authExpiresAt 保存在实例上，续期发送前用它判定旧连接是否过期。
- `sdk/embed/src/core/ws-client.ts:151-159,279-308`：新连接首帧只更新 authToken；disconnect 清除 authToken，但没有重置/替换 authExpiresAt。

**触发路径**
1. 用户 A 已完成认证，SDK 保存 A 的 WS authExpiresAt。例如 A 的票据在 t=300 秒到期。
2. t=250 秒宿主切换到 B，SDK 换到 B 的票据并销毁 A 的连接、清空旧身份会话。B 的票据有效到 t=550 秒。
3. controller 因 changed=true 跳过 refreshAuth；B 新连接虽已使用 B 的 token 鉴权，但 WsClient.authExpiresAt 仍为 A 的 t=300 秒。
4. t=350 秒对 B 正常续期时，refreshAuth 发现 Date.now() >= 旧的 authExpiresAt，在发送任何 auth_refresh 之前直接拒绝并关闭 B 连接。

**影响**
- 有效的 B 会话被不必要地断开，显示“连接认证更新未确认，请重试”；正常同身份轮换无法保持在线。
- 如果断线后用缓存的 B 新票重连，getToken 没有触发 onUpdate，旧 authExpiresAt 仍未刷新，后续轮换还可能重复断线。
- 这是凭证元数据错误，不是跨账号数据泄露；已有重连机制通常能恢复，因此定为 P2。

**验证**
- 通过 Vite middleware 模式在内存加载真实 EmbedController、TokenProvider、WsClient，使用 happy-dom、合成 fetch 和假 socket 驱动 A→B→B 续期，不修改测试文件。
- 观察结果：B socket 被关闭（readyState=3）；B socket 只发出 auth 和 subscribe，没有 auth_refresh；错误为“连接认证更新未确认，请重试”。
- 另外用真实 WsClient 独立驱动同一时间线也复现，异常为 WebSocket authentication confirmation timeout。

**修复建议**
- 将 token 与 expiresAt 作为同一份连接认证元数据管理，每次首次连接/账号切换后的连接都绑定实际使用的 token 及其有效期。
- 身份切换时不要遗漏新账号的 expiresAt；disconnect 应清除旧连接元数据，但仅重置为 Infinity 不足以提供准确的续期确认截止时间。
- 保留“旧连接到期不能继续发业务帧”的安全边界，不通过放宽过期校验隐藏错误。

**建议测试**
- 真实 controller 测试 A 票据临近到期时切换 B，然后跨过 A.exp、但仍早于 B.exp，主动续期 B；断言发送 auth_refresh、确认后连接不关闭、订阅不重放、业务帧不重复。
- 同时覆盖换票后使用缓存 token 重连，断言下一次 auth_refresh 使用该连接实际 token 的有效期。

### R6. REST 重试的迟到 401 会停止已经成功换新的同账号认证

**代码位置**
- `sdk/embed/src/core/rest-client.ts:66-69`：第二次认证层 401 调用 onUnauthorized(token, true)。
- `sdk/embed/src/controller.ts:214-216`：final=true 时直接 rejectAuthentication，忽略该响应实际使用的 token。
- `sdk/embed/src/core/token-provider.ts:62-65,78-87`：invalidate 有 rejectedToken 版本判断，但 rejectAuthentication 没有；后者清票、停止定时器并发出 login_required。

**触发路径**
1. REST 请求使用 T1，认证层返回 401/code=1001，按设计换到 T2 并重试一次。
2. T2 请求的 401 响应在途中延迟（例如浏览器休眠、代理/网络延迟，或另一个恢复动作并行）。
3. 同账号在此期间已经通过有效 SSO 换到 T3，当前 TokenProvider 和其他请求/WS 已使用新认证。
4. T2 的迟到 401 到达；因为身份 userId 没变，REST 的 identity 检查通过。final 分支不比较 T2 与当前 T3，直接停止整个认证生命周期。

**影响**
- 已经成功恢复的用户被误报为宿主登录失效，当前新票被丢弃、认证连接被暂停，需要再次人工重试。
- 不要求 SSO 返回非法票据：旧请求在过期时被认证层拒绝，其响应晚于其他换票完成即可触发。
- 第一轮 401 已有 token 比较，问题集中在最终 401；不建议为了修复而对写请求增加无界重放。

**验证**
- 真实 TokenProvider + RestClient，采用与 controller 一致的 onUnauthorized 回调；从默认 retry=true 开始，合成第一次 401、第二次延迟 401。
- 第二次请求等待期间主动换到 T3，然后放行 T2 的 401。输出为：新票 t3 已签发；原请求 unauthorized；后续 get 返回“登录凭据已失效”；状态序列为三次 authenticated 后 login_required。
- 真实 controller 内存驱动也确认最终 401 会终止当前新认证。

**修复建议**
- 最终认证失败的副作用也须绑定被拒绝的凭证/认证代次；若响应属于已经被替换的旧 token，只让该请求失败，不清除当前认证、不关闭新 WS。
- 对尚未被替换的最终 401，可保留有界失败处理，但不要把旧响应用作当前宿主 SSO 失效的证明。
- 保持单请求最多一次自动重试，未知网络错误不重放写操作。

**建议测试**
- 两个并行恢复动作：请求 X 的重试 T2 返回延迟 401；另一路已换到 T3，并完成 WS auth_refreshed；放行旧 401 后断言 X 失败、T3 仍有效、无 login_required、WS 不断开、没有第三次业务请求。
- 对比测试：未发生 token 替换时连续认证层 401 仍有界失败，不形成换票或请求风暴。
