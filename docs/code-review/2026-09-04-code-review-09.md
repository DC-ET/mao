## 三、遗留低危问题（不阻塞，建议随下次改动处理）

### F1（低）N3 修复无效：disconnect 打断在途 connect 时 await 仍会悬挂

- 位置：`sdk/embed/src/core/ws-client.ts` `disconnect()` 与 `socket.onclose`
- 推演：disconnect 同步执行 `socket.close()` → `this.socket = null` → `this.connectPromise = null`；随后 onclose 异步派发时 `if (event.target !== this.socket) return`（旧 socket ≠ null）**早退**，无条件 reject 永远执行不到。因此 destroy/重复 init 打断在途 `await connect()` 时，等待方（boot 协程）仍永久悬挂——与修复前行为相同。
- 影响范围小（仅 destroy 场景，协程滞留、无用户可见故障），故维持低危。真正修复需要在 disconnect 中直接持有 settle 句柄（对齐 desktop 的 pendingSettle.reject），而不是依赖 onclose。

### F2（低）N4 与既有清零逻辑冲突：完整回复的未读提醒被 COMPLETED 清零吞掉

- 位置：`sdk/embed/src/controller.ts` —— `case 'message_end'/'user_message_saved'` 累加 `store.unread`，与 `case 'session_status'` 中 `if (phase === 'IDLE' || phase === 'COMPLETED') this.ui.unread = 0` 冲突
- 时序：收起状态下 agent 完成一轮回复 → `message_end`（unread=1）→ 紧随的 `session_status COMPLETED` 直接把 `ui.unread` 清零，launcher 圆点熄灭。典型单轮任务下未读提醒几乎恒不可见；且该清零绕过 store（直接改 ui.unread），造成 store.unread=1 / ui.unread=0 双源不一致，后续累加时计数跳变。
- 建议：COMPLETED 时不清 unread（仅 IDLE/open 清），且清零统一走 `store.markRead()` 保持单源；或收起状态改由 `session_status` 的 `unread` 字段语义驱动（desktop 的做法）。
