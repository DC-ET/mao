## 中严重度

### [中] 最终/失败卡片更新失败时仍不会发送纯文本兜底回复

**位置**：`backend-ts/src/feishu/agent-inbound-handler.ts:103-117`

当前 `FeishuCardProgressListener.safeUpdate()` 会吞掉 `progress.update()` 的异常，因此最终 `complete()`、失败 `fail()` 和取消 `cancel()` 不会再阻断 handler，这一点已修复。但 handler 只要成功创建过卡片，就始终不调用 `onReply`：成功路径在 `await cardListener?.complete(text)` 后直接返回，异常路径在 `await cardListener?.fail(...)` 后返回 `null`。

因此，在初始卡片发送成功、后续 `message.patch` 因权限、卡片过期、网络或飞书限流失败的场景，Agent 可能已经生成了最终答案，但用户既看不到更新后的卡片，也收不到普通文本回复。失败状态更新失败时同理，用户会没有任何错误提示。该问题仍违反“卡片展示失败不应改变原有回复语义”的兜底要求。

**修复建议**：让卡片监听器记录最终状态更新是否成功，或让 `complete/fail/cancel` 返回更新结果；当终态更新失败时，在 handler 中走 `onReply` 文本链路。成功终态更新时可继续避免重复发送文本。失败场景至少应发送统一错误文案；取消场景可按业务决定是否发送取消文本，但不能因卡片更新异常导致异常冒泡或静默丢失。

## 已核验且未发现回归

- **卡片发送失败不再阻断 Agent**：`createProgressCard` 已放在内层 `try/catch` 中，创建失败会记录日志并继续执行；此时 `cardListener` 为 `null`，最终走 `onReply` 纯文本回复。
- **toolCallId 乱序归属已修复**：`FeishuCardProgressListener` 使用 `Map<toolCallId, summary>`，结果通过传入的 ID 精确更新；新增测试覆盖了先返回后发起工具的情况。
- **round 与初始卡片时机**：卡片在执行前创建，初始状态为第 0 轮；`onMessageEnd` 递增 round，并在排队更新时捕获当轮内容和工具摘要后再清空状态，未发现明显串轮问题。
- **并发与代际处理**：会话锁、代际检查和取消 flag 的注册时序能够避免旧消息回复及中间排队消息产生 Agent 执行；卡片更新自身通过 Promise 串行化。
- **频率限制**：patch 更新之间至少间隔 250ms，且更新串行；未发现同一卡片并发 patch。该机制不保证跨卡片/跨实例全局限流，但当前代码未表现为本次需求引入的单请求功能错误。
- **卡片 API 参数**：私聊使用 `receive_id_type=open_id`，群聊非引用发送使用 `chat_id`，群聊触发消息存在时使用 `reply`；patch 使用消息 ID 和卡片 `content`，与当前 SDK 类型及既有文本发送方式一致。
