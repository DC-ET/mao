## 🟠 中等问题

### 1. `useChat.ts` — `retryExecution` 未设置 `sending = true`，导致输入框在重试期间未锁定

**文件**: `desktop/src/composables/useChat.ts`  
**位置**: 新增的 `retryExecution` 函数（约第 645 行）

```typescript
async function retryExecution() {
    const sid = sessionId.value
    if (!sid) return
    sessionStore.clearExecutionError(sid)
    wsRetryExecution(sid)
    sessionStore.ensureStreamingAssistantMessage(sid)
    // ❌ 缺少 sending.value = true
}
```

**问题描述**:  
`ChatPanel.vue` 中的 `ChatInput` 是否禁用取决于 `loading` prop，该 prop 绑定到 `agentRunning` computed，而 `agentRunning` 依赖于 `sending.value`。在 `retryExecution` 中，`sending.value` 未被设为 `true`，导致：

1. 点击"重试"后，聊天输入框仍处于可输入状态，用户可在此期间发送新消息，造成并发执行冲突
2. 重试按钮仍可见（因为 `can-retry="!agentRunning"` 仍为 `true`），用户可多次点击重试

**影响范围**: 主会话面板（`ChatPanel.vue`）  
**触发条件**: 用户点击重试按钮后，在服务端返回 `RUNNING` 状态之前操作输入框或再次点击重试

**修复建议**: 在 `sending` 赋值前增加 `sending.value = true`，与其他发送路径（如 `sendMessage`、`sendMessageAndWaitForSave`、`editAndResend`）保持一致：

```typescript
async function retryExecution() {
    const sid = sessionId.value
    if (!sid) return
    sending.value = true          // ← 添加此行
    sessionStore.clearExecutionError(sid)
    wsRetryExecution(sid)
    sessionStore.ensureStreamingAssistantMessage(sid)
}
```

### 2. `SideChatPanel.vue` — `handleRetryExecution` 未设置 `sending = true`，导致重试期间输入框未锁定

**文件**: `desktop/src/components/chat/SideChatPanel.vue`  
**位置**: 新增的 `handleRetryExecution` 函数（约第 621 行）

```typescript
function handleRetryExecution() {
  const sid = realSessionId.value
  if (sid <= 0) return
  sessionStore.clearExecutionError(String(sid))
  retryExecution(String(sid))
  sessionStore.ensureStreamingAssistantMessage(String(sid))
  // ❌ 缺少 sending.value = true
}
```

**问题描述**:  
与 Bug #1 相同，`SideChatPanel.vue` 的 `sending` 是一个 `ref<boolean>`（由 phase watch 控制），`handleRetryExecution` 中未设置为 `true`。`ChatInput` 的 `loading` prop 绑定到 `sending`，导致重试期间输入框未锁定，`can-retry` 条件 `!sending && hasRealSession` 仍为 `true`，按钮可被重复点击。

**影响范围**: 边路会话面板（`SideChatPanel.vue`）  
**触发条件**: 同 Bug #1

**修复建议**: 在 `clearExecutionError` 之前或之后增加 `sending.value = true`：

```typescript
function handleRetryExecution() {
  const sid = realSessionId.value
  if (sid <= 0) return
  sending.value = true              // ← 添加此行
  sessionStore.clearExecutionError(String(sid))
  retryExecution(String(sid))
  sessionStore.ensureStreamingAssistantMessage(String(sid))
}
```

### 3. `SubagentChatPanel.vue` — 重试后按钮短暂可见，无防重复点击

**文件**: `desktop/src/components/chat/SubagentChatPanel.vue`  
**位置**: 新增的 `handleRetryExecution` 函数（约第 172 行）

```typescript
function handleRetryExecution() {
  sessionStore.clearExecutionError(sid.value)
  retryExecution(sid.value)
  sessionStore.ensureStreamingAssistantMessage(sid.value)
}
```

**问题描述**:  
`SubagentChatPanel.vue` 的 `sending` 是 `computed`（基于 phase），无法直接赋值为 `true`。点击重试后，在服务端返回 `RUNNING` 之前，`sending` 仍为 `false`，重试按钮仍可见，用户可重复点击（虽然消息会被 `send()` 静默丢弃，但服务端可能收到重复的 `retry_execution` 消息）。

**影响范围**: 子代理面板（`SubagentChatPanel.vue`）  
**严重程度**: 较低（面板为只读模式，无输入框，无并发发送风险，仅按钮可重复点击）

**修复建议**: 可考虑增加一个 `retrying` 局部 ref 来控制按钮显示，或结合 `sending` computed 做复合判断：

```typescript
const retrying = ref(false)

function handleRetryExecution() {
  if (retrying.value) return
  retrying.value = true
  sessionStore.clearExecutionError(sid.value)
  retryExecution(sid.value)
  sessionStore.ensureStreamingAssistantMessage(sid.value)
}
```

并在 phase 变为 `RUNNING` 时重置 `retrying`（可通过 watch phase 实现），或修改 `can-retry` 条件为 `!sending && !retrying`。

## 🟡 轻微问题

### 4. `useStreamWS.ts` — `retryExecution` 使用 `send()` 而非 `sendReliable()`，断连时消息静默丢失

**文件**: `desktop/src/composables/useStreamWS.ts`  
**位置**: 新增的 `retryExecution` 函数（约第 388 行）

```typescript
function retryExecution(sessionId: string) {
    send({ type: 'retry_execution', sessionId: Number(sessionId), data: {} })
}
```

**问题描述**:  
`retryExecution` 使用 `send()` 函数，该函数在 WebSocket 未连接时仅输出 `console.warn` 并丢弃消息，不做重连重试。如果用户点击重试时恰好 WS 断开（例如网络闪断），消息将静默丢失，用户无任何反馈。

**影响范围**: 所有使用 `retryExecution` 的组件  
**触发条件**: 点击重试时 WS 连接断开

**修复建议**: 考虑使用 `sendReliable()` 替代 `send()`，以确保在 WS 断开时自动重连并重发。但需注意 `sendReliable()` 是异步的，调用方需适配。如果当前设计上认为 `retry_execution` 与 `cancel` 等操作一样不应阻塞（使用 `send()` 保持一致），可保留现状并添加 toast 提示告知用户操作结果。该问题不影响正常网络下的功能。
