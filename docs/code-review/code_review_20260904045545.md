## P1 阻塞级

### P1-1 登出后再登录，云端终端永久不可用（`disconnect()` 置位的 `intentionalClose` 不会被重置）

- 位置：`desktop/src/composables/useTerminalWS.ts:73-82`（`send`）、`151-161`（`connect`）、`294-296`（`disconnect`）
- 现象：`disconnect()` 把模块级 `intentionalClose = true`；`connect()` 内部虽然会重置该标志，但重置发生在 `connect()` **被调用之后**，而唯一的调用入口 `send()` 有前置守卫：

```ts
// useTerminalWS.ts:73-82
function send(payload: Record<string, unknown>): void {
  if (authenticated && ws?.readyState === WebSocket.OPEN) { ws.send(...); return }
  pendingFrames.push(payload)
  if (pendingFrames.length > MAX_PENDING_FRAMES) pendingFrames.shift()
  if (!intentionalClose) connect().catch(() => {})   // ← 登出后此处永远为 false
}
```

  `attach()` 只调 `send({type:'attach'})`，不直接调 `connect()`。因此登出后（同一页面未刷新）重新登录，所有 attach 帧只进队列，永不建连。
- 实测（只读脚本，模拟 FakeWebSocket 驱动真实 `useTerminalWS` 编译产物）：
  - 首次 attach 正常：`onopen` 只发 `auth`，收到 `connected` 后才发 `attach`，Promise resolve；
  - `disconnect()` 后再 `registerTerminal + attach`：**新建 socket 数 = 0**，attach Promise 永久 pending，15s 后按超时 reject，终端只显示「连接中断，正在重试…」且不会真的重试。
- 影响：登出→登录是常见操作（尤其多账号切换、401 强制下线后重新登录）。命中后终端功能完全失效，用户必须手动刷新整页才恢复，且无任何提示指向真实原因。
- 建议：在 `attach()`（或 `ensureConnected()`）入口显式清除 `intentionalClose`，或让 `send()` 的守卫改为「队列非空且存在期望 attach 的终端就尝试连接」。更稳妥的做法是把 `intentionalClose` 的语义收窄为「本轮 socket 的关闭是主动的」，由 `connect()` 在创建新 socket 前统一复位（当前虽然有 `intentionalClose = false`，但因守卫在外层，等价于死锁）。

### P1-2 切走任务再切回，终端区域空白（xterm `open()` 对已挂载实例是空操作，容器已被 Vue 卸载）

- 位置：`desktop/src/components/terminal/TerminalPanel.vue:92-102`（`setContainerRef` 在 el 为 null 时 `mountedTerminals.delete(id)`）、`105-119`（`watch(activeTabId)` 内 `mountTerminal`）、`desktop/src/composables/useTerminal.ts:388-402`（`mountTerminal` 调 `inst.terminal.open(container)`）
- 现象：终端 DOM 由 `v-for="tab in visibleTabs"` 渲染。切换任务时 `visibleTabs` 变化 → 旧任务的容器 div 被卸载，`setContainerRef(id, null)` 把该 id 从 `mountedTerminals` 移除。切回任务时容器重新创建，`mountTerminal` 再次调用 `terminal.open(newContainer)`。但 xterm 6.0.0 的 `open()` 首行即判断「已有 `this.element` 且 `ownerDocument.defaultView` 存在」就直接 return（仅同步 window 引用），**不会把已存在的 DOM 迁移到新容器**。
- 实测（jsdom + 真实 `@xterm/xterm` 6.0.0）：

```
after open#1 -> div1 children: 1 | t.element present: true
after open#2 -> div2 children: 0 | element still inside div1: true
=> 重新 open 到新容器：未生效（终端显示空白）
appendChild 迁移后 div3 children: 1 => 可恢复
```

- 影响：CLOUD 任务 A 打开终端 → 切到任务 B → 切回 A，终端面板出现空白区域（tab 在、attach 正常、输出写入了不可见的旧 DOM 节点）。这是用户可见的功能失效，且比 P1-1 更容易触发。
- 建议：`mountTerminal` 内先判断 `inst.terminal.element`：已存在则直接 `container.appendChild(inst.terminal.element)` 完成迁移再 `fit()`；仅当 element 不存在时才调 `open()`。实测 appendChild 迁移可恢复渲染。另一种方案是让容器 div 不随 `visibleTabs` 卸载（改用 `v-show` 渲染全部 remote tab 并按 session 过滤显示），但会保留更多 DOM，建议采用前者。

## P2 功能不完整 / 健壮性

### P2-1 attach 在途期间到达的 resize/input 被回 `TERMINAL_FORBIDDEN`，多余错误帧且不可自愈

- 位置：`backend-ts/src/harness/terminal/terminal-ws-handler.ts:100-135`（`handleTextMessage` 不串行化）、`209-211`（`handleAttach` 内 `await permissionService.hasPermission`）、`279-289`（`requireAttached`）；投递侧 `backend-ts/src/session/ws/attach-websocket.ts` 的 `void deps.terminalHandler.handleTextMessage(...)`
- 现象：`handleAttach` 的权限校验是一次真实 DB 往返（`PermissionService.hasPermission` 内 3 次 repo 查询）。`conn.terminals.add(terminalId)` 在该 await **之后**才执行，而消息投递不串行化，因此 attach 之后紧随的帧会先看到「尚未绑定」状态。
- 实测（用编译产物 + `setImmediate` 级权限延迟，模拟一次 I/O 往返）：

```
frames: [connected]
        [error TERMINAL_FORBIDDEN 终端未绑定到当前连接]   ← resize
        [error TERMINAL_FORBIDDEN 终端未绑定到当前连接]   ← input
        [attached t1]
resized: []   written: []
```

- 影响：前端目前对 `TERMINAL_FORBIDDEN` 只 `console.warn`（`useTerminal.ts:263-267`），所以不会弹错误 toast——但代价是：
  1. attach 完成前的首个 resize 丢失。`attachRemote` 成功回调里会补发一次 resize（`useTerminal.ts:281-285`），所以尺寸能自愈；
  2. attach 完成前用户敲的键**静默丢弃**，无补偿；
  3. 真实的权限/归属错误也被降级为 console，用户无感知。
- 建议：`handleAttach` 把 `conn.terminals.add(terminalId)` 提前到权限校验之前（或对同一 socket 的 attach 建立在途标记），attach 失败时再回滚；或在 `requireAttached` 中对「该终端存在且 userId 匹配、但正处于本连接 attach 在途」的情况改为排队/静默丢弃而不回错误帧。

### P2-2 已认证连接重复 `auth` 会回 `connected`，前端据此重放全部 attach，造成重复回放与清屏

- 位置：`backend-ts/src/harness/terminal/terminal-ws-handler.ts:182-186`（`dispatch` 的 `case 'auth'` 幂等回 `connected`）；前端 `desktop/src/composables/useTerminalWS.ts:103-109`（`onAuthenticated` 无条件把 `attachedTerminals` 全量重排进队列并 flush）、`113-118`（`onAttached` → `terminal.reset()` 清屏）
- 现象：前端把 `connected` 帧当作「刚认证完成」的唯一信号。任何再次收到 `connected` 的场景（如后续新增逻辑触发重发 auth、或服务端重复回帧）都会导致对所有终端重新发 attach → 每个终端触发 `attached` → `terminal.reset()` 清屏 + 全量重放缓冲。
- 影响：当前代码路径下前端只在 `onopen` 发一次 auth，因此不会自发触发；属于协议契约脆弱（同一帧承担「认证成功」与「认证状态查询响应」两种语义）。一旦触发，用户会看到终端闪屏并丢失滚动位置。
- 建议：认证成功与幂等应答用不同帧类型（如 `connected` 与 `auth_ok`），或前端用 `authenticated` 标志做幂等保护——已认证状态下收到 `connected` 只 flush 队列，不重排 attach。

### P2-3 DELETE 的跨任务防探测校验依赖 terminalId 字符串前缀，可被构造绕过

- 位置：`backend-ts/src/session/terminal.routes.ts:84-95`

```ts
const terminal = terminalManager.get(terminalId);
if (terminal == null) {
  if (!terminalId.startsWith(`term-${sessionId}-`)) {
    throw new BusinessException(ErrorCode.FORBIDDEN, '无权操作该终端');
  }
  return sendOk(reply, null);   // 幂等
}
```

- 现象：终端不在注册表时（已退出/已回收/从不存在），仅用字符串前缀判断归属。调用方可对自己的 sessionId 拼任意 `term-{自己的sessionId}-...` 得到 code=0；也可通过是否返回 403 判断「某 id 不以 term-{sid}- 开头」这类信息。
- 影响：安全影响很小（只能对自己有权限的 session 拿到幂等成功，无法删除他人终端——真实终端仍走下面的 `sessionId/userId` 双重校验）。主要问题是**幂等语义与归属校验混在一起**，后续若 terminalId 生成规则变更（如去掉 sessionId 前缀），该分支会静默失效。
- 建议：幂等分支不做前缀推断，直接返回成功（归属由 `prepare()` 的 session owner 校验兜住）；或改为持久化最近关闭的 terminalId → sessionId 映射后再判断。

### P2-4 `restoreRemoteTabs` 与 `detachRemoteTerminals` 在切任务时存在竞态，可能立即把刚 attach 的终端解绑

- 位置：`desktop/src/components/terminal/TerminalPanel.vue:135-146`（切任务 watch：先 `detachRemoteTerminals(当前 sessionId)` 再 `await restoreRemoteTabs`）、`desktop/src/composables/useTerminal.ts:334-342`（`restoreRemoteTabs` 的 inflight 去重按 sessionId）
- 现象：`restoreInflight` 以 sessionId 为键去重，但快速连续切任务 A→B→A 时，A 的第一次 restore 可能仍在途（`api.get` 未返回），此时第二次切走 A 触发 `detachRemoteTerminals`，随后 A 的旧 restore 回调继续执行 `attachRemote`，把已解绑的终端又 attach 回来——而当前可见任务已是 B。
- 影响：后端认为 A 的终端仍 attached，`isIdleTimeout` 返回 false（`remote-terminal.ts:205-209`），退化为上一轮 P1-2 的「永不 idle 回收」；同时 B 的输出与 A 的输出混在同一连接上（各自 terminalId 区分，功能不错乱，但配额会被慢慢占满）。
- 建议：`doRestoreRemoteTabs` 增加代际校验（进入时记录 `sessionStore.activeSessionId`，`await` 返回后若已变更则直接 return），与 `TaskView.vue` 里 `loadGeneration` 的既有写法保持一致。

## P3 低 / 可维护性

### P3-1 心跳静默检测读模块级 `ws`，旧 socket 的定时器可能误关新连接

- 位置：`desktop/src/composables/useTerminalWS.ts:169-178`。心跳回调内部用模块级 `ws?.readyState` 与 `ws.close()`，而定时器由每次 `onopen` 创建。虽然 `onopen` 首行有 `if (socket !== ws) return`、且 `stopHeartbeat()` 在新建前调用，实际不会残留双定时器；但回调闭包引用的是可变的模块级 `ws`，语义上「上一代心跳可能关掉下一代连接」。建议闭包内改用局部 `socket` 引用（与 `onopen`/`onmessage` 已有的归属校验一致）。

### P3-2 `pendingFrames` 超限丢最早帧，会优先丢掉 attach 而非按键

- 位置：`desktop/src/composables/useTerminalWS.ts:78-80`。注释写「超出丢最早的（多为输入按键）」，但断线期间队列头部通常是 `attach`（`onAuthenticated` 会把 attach 排到队首，但断线时排入的顺序是先 attach 后 input）。长时间断线 + 用户狂敲键时，attach 可能被挤掉，恢复后变成「只发 input 不发 attach」→ 服务端回 `TERMINAL_FORBIDDEN`。建议丢弃时跳过 `type === 'attach'` 的帧，或对 input 帧单独限长。

### P3-3 `TerminalTabs` 收到的 `visibleTabs` 变化不会重置 Ctrl 粘滞态

- 位置：`desktop/src/components/terminal/TerminalPanel.vue:305-306`（`ctrlSticky`）。切 tab / 切任务时 `ctrlSticky` 保持为 true，用户在新终端敲的第一个字母会意外变成控制字符。仅安卓（`showKeyBar`）生效，影响面小。建议在 `watch(activeTabId)` 内复位。

### P3-4 `normalizeTaskName` 已加固，但同处注释与迁移描述仍按旧语义

- 位置：`backend-ts/src/harness/terminal/terminal-manager.ts:428-434`。已按上轮建议剥离 `'`、反引号、`$`、`\`，正确。注释「去掉控制字符与会被 bash promptvars 展开的字符」表述准确，无需改动；此处仅记录复审结论，避免下轮重复排查。

### P3-5 终端审计仍绕过 `recordAudit` 的其它策略（仅复用了截断）

- 位置：`backend-ts/src/create-app.ts:591-606`。已改为 `truncateAuditError(ctx?.errorMessage)`，DB 长度风险解除；但 `shouldAudit` 白名单、`queryString` 等仍不经过统一入口，且 `status` 恒为 200（失败时 `success=0` 但 status 仍 200）。与设计 7.7 一致，仅作可维护性备注：失败审计的 status 建议置 500 或留空，避免报表按 status 统计时失真。

6. **权限门禁链路**：`/users/me` 返回 `permissions` + `isAdmin`（`user.routes.ts:114-126`），auth store 暴露 `hasPermission`，`TopNav` 的 `terminalAvailability` 覆盖「无任务 / 无 terminal:use / 无 workspace / LOCAL 非 Electron」四种禁用情形，`toggleTerminal` 与 Ctrl+` 共用同一守卫。
7. **WS 通道注册位置正确**：`/ws/terminal` 与 `/ws/stream` 同 scope 且在 `register(websocket)` 之后声明（避免 `FST_ERR_DEC_ALREADY_PRESENT`）；`socket.bufferedAmount` 在 @fastify/websocket 的 `ws` 实例上可用，背压判断有效。
8. **`OutputRingBuffer`**：按字节统计、超限从头丢并置 `truncated`，`read()` 前置截断提示；`close()` 内 `buffer.clear()` 避免残留。
9. **前端 detach 时清理在途帧**：`detach()` 会过滤 `pendingFrames` 中同 terminalId 的帧并 settle 等待者，避免解绑后仍发 input（`useTerminalWS.ts:269-277`）。

## 设计既定、本次不改（非缺陷）

1. `getTerminalConfig()` 仅在 bootstrap 读一次（`create-app.ts:312`），管理后台改配置需重启后端 —— 设计 7.5，admin hint 与迁移注释已说明。
2. `/ws/terminal` 走 `PUBLIC_PREFIXES` 的 `/ws/` 放行（`auth/jwt-hook.ts:4`），鉴权完全依赖首帧 auth；`validateAccessToken` 接受 access 与 shell 类型 token（即 `MAO_TOKEN` 亦可开终端 WS）—— 设计 7.3。
3. 无 Origin 校验、无一次性 ticket —— 设计 3.2.5 明确不做。
4. `nodePtyFactory` 未传 `handleFlowControl` —— 设计 3.2.14 明确不做。
5. 终端等价于该用户的 root shell（设计 11.1、V100 注释已警示），故终端内命令注入不作为安全缺陷计入。

## 修复优先级建议

1. **P1-1**：一行守卫问题，收益最大，建议立即修（`attach()` 或 `ensureConnected()` 内复位 `intentionalClose`）。
2. **P1-2**：`mountTerminal` 增加「element 已存在则 appendChild 迁移」分支，实测可恢复。
3. **P2-1**：`handleAttach` 把 `conn.terminals.add` 提前到权限校验之前并在失败时回滚，可同时消除首个 resize 丢失与按键静默丢弃。
