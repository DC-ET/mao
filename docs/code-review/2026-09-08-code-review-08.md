## P1

### P1-1. `embedPageToolTimeoutSeconds` 被当作毫秒传入，页面工具实际只有 180ms 超时

**位置**
- `backend-ts/src/config/app-config.ts:168-170`：`embedPageToolTimeoutSeconds: 180`（注释明确「需覆盖 per_action 逐次确认窗口（SDK 确认超时 120s）」，即语义为秒）
- `backend-ts/src/create-app.ts:639`：`new EmbedPageToolRegistry(wsRegistry, cfg.app.harness.embedPageToolTimeoutSeconds)`
- `backend-ts/src/harness/embed-page-tool-registry.ts:37-40, 76-83`：构造参数是 `timeoutMs`，直接 `setTimeout(fn, this.timeoutMs)`，错误文案按 `Math.round(timeoutMs/1000)` 换算「秒」

**问题**
配置单位是秒（180），注册表按毫秒使用（180ms）。正常一次 `page_tool_request` 要经过 WS 下发 → 浏览器 DOM 扫描/动作 → `page_tool_result` 回传，端到端远超 180ms，因此 `future` 会先被超时定时器以 `page_tool_timeout` 结束；随后 SDK 的回包到达时 `pending` 里已无该 requestId，`complete()` 返回 false 被丢弃。结果是**所有页面工具在生产上稳定失败**（单测用的是显式 40ms，掩盖了配置单位不一致）。错误文案也会显示「超时（0 秒未返回）」。

**修复建议**
统一单位，二选一：
- `create-app.ts:639` 改为 `cfg.app.harness.embedPageToolTimeoutSeconds * 1000`；或
- 把构造参数/字段改名为 `timeoutSeconds` 并在 `setTimeout` 处 `* 1000`。

同时补一个「配置默认值 → 注册表实际超时」的回归测试，避免再次单位错配。

### P1-2. 截图遮罩沿用上次 inspect 的坐标，滚动/布局变化后敏感字段可能未遮罩外发

**位置**：`sdk/embed/src/page/engine.ts:141-149`

```ts
const snapshot = this.manager.current;
const maskRects = mask
  ? (snapshot
    ? snapshot.elements.filter((el) => el.sensitive).map((el) => el.rect)   // ← 旧快照的视口坐标
    : scanPage({ host: this.hooks.host, includeHidden: true, redactSensitive: false })
      .elements.filter((item) => item.descriptor.sensitive).map((item) => item.descriptor.rect))
  : [];
```

**问题**
`PageSnapshotManager.current` 只在 URL 变化时失效（`snapshot-manager.ts:176-182`），`page_scroll`（`executor.ts` `executeScroll`）不会失效也不会刷新 rect。设计流程本身就包含「inspect → scroll → screenshot」，此时 `snapshot` 仍存在但 `rect` 是滚动前的视口坐标：
- 当前视口里新出现的敏感输入框不会被遮罩；
- 旧坐标处会被涂黑，与真实敏感区域错位。

`per_action` 下遮罩截图是**默认不弹确认**的（`engine.ts:130-139` 仅对 `maskSensitive:false` 才确认），因此用户/Agent 以为「已遮罩」，实际可能把密码、验证码、银行卡等明文截图发给 LLM。

**修复建议**
截图前一律按当前 DOM 现算敏感区域，不依赖旧快照：
- 直接无条件走 `scanPage({ host, includeHidden: true, redactSensitive: false })` 分支（现算成本与已有 fallback 相同）；或
- 保留元素引用并在截图时用 `getBoundingClientRect()` 重新测量，而不是用快照里冻结的 `rect`。

可补测试：inspect 含密码框 → 触发滚动使密码框进入视口 → 截图断言 `masked=true` 且 `fillRect` 覆盖的是新坐标。

## P2

### P2-1. `page_keyboard` 携带 `text` 时可写入 readonly 输入框

**位置**：`sdk/embed/src/page/executor.ts:334-350`（`executeKeyboard`），`sdk/embed/src/page/visibility.ts:57-67`（`isEditable`）

`executeFill` 有 `isReadonly` 拦截（`executor.ts:227`），但 `executeKeyboard` 只检查 `isDisabled` + `isEditable`。而 `isEditable` 对 `readonly` 的 input/textarea 仍返回 true（只按 type 排除）。`setElementValue` 走原生 setter，可绕过 readonly 写入，回读校验也会通过，于是对只读字段报告成功。

**修复建议**：`executeKeyboard` 在插入 `action.text` 前与 `executeFill` 一致地检查 `isReadonly(el)`，返回 `element_readonly`；补 readonly input/textarea 的回归用例。

### P2-2. 同源 iframe 内元素使用 iframe 局部坐标，导致高亮/遮罩错位

**位置**：`sdk/embed/src/page/scanner.ts:184`（递归 `contentDocument`）、`scanner.ts:198,213`（`rectOf` / `isInViewport`）；`sdk/embed/src/page/visibility.ts:22-34`

iframe 内元素的 `getBoundingClientRect()` 返回相对该 iframe 视口的坐标，`isInViewport` 却拿主窗口 `innerWidth/innerHeight` 比较。后果：
- `PageHighlight`（`position: fixed` 于主文档）位置错误；
- 截图遮罩坐标错误 → iframe 内敏感字段可能漏遮罩或涂错位置；
- `inViewport` 判定失真。

**修复建议**：扫描时沿 iframe 链累加各层 iframe 的 `getBoundingClientRect()` 偏移，把 rect 换算到主文档视口坐标；或对 iframe 内元素标记为「不参与高亮/遮罩」并明确返回不可截图遮罩。补同源 iframe 的坐标换算测试。

### P2-3. `page_observe` 在导航后永远报告「无变化、未导航」

**位置**：`sdk/embed/src/page/snapshot-manager.ts:121-156`

```ts
this.onNavigation();                       // 导航时会把 this.record 置空
const previous = previousSnapshotId && this.record?.snapshot.snapshotId === previousSnapshotId ? this.record : null;
...
navigated: previous != null && previous.navVersion !== this.navVersion(),   // previous 恒为 null
```

`onNavigation()` 先执行，导航后 `record=null`，`previous` 只能是 null，于是 `added/removed` 恒为 0、`navigated` 恒为 false。Agent 拿到的是「页面没变」的错误结论（虽然 `url/title` 是新值）。

**修复建议**：在调用 `onNavigation()` 之前先取出旧 record/navVersion，或把快照按 `snapshotId` 缓存（而不是单 record），导航后仍能用旧快照做对比；补「导航后 observe 报告 navigated=true 且 removed/added>0」的测试。

### P2-4. 解绑/替换 embed 绑定时不结束在途页面请求，工具只能等到超时

**位置**：`backend-ts/src/session/ws/streaming-ws-handler.ts:259-266`（`handleUnsubscribe` 只 `unbindEmbedSession`）、`backend-ts/src/session/ws/streaming-ws-registry.ts:269-281`（`bindEmbedSession` 换绑时只从旧连接的集合里删 sessionId）

SDK `newSession()`（`controller.ts:668-691`）会 `unsubscribe(previous)` 并 `subscribe(new)`；`pageEngine.cancel()` 只做本地取消，不会回 `page_tool_result`。于是旧会话在途的 `page_tool_request` 既被解绑（回包会被 `handlePageToolResult` 丢弃），又不会收到取消，只能挂到超时（修好 P1-1 后就是 180s）。多标签页同会话「后订阅者胜」的换绑同理。

**修复建议**：
- `handleUnsubscribe` 对该 embed 连接解绑的每个 sessionId 调 `embedPageToolRegistry.failSession(sessionId, '页面已取消订阅，页面操作已取消')`；
- `bindEmbedSession` 换绑时（或让 registry 暴露回调）对被顶掉的旧连接对应会话 `failSession`。

补「unsubscribe / 换绑后 pendingCount 立即归零、future 以 task_cancelled 结束」的测试。

### P2-5. UI「停止页面任务」只停 SDK 本地，未通知后端，且下一次请求会自动恢复

**位置**：`sdk/embed/src/controller.ts:897-900`

```ts
cancelPageTask(): void {
  this.pageEngine.cancel();
  this.ui.pageConfirm = null;
}
```

对比 `stop()`（`controller.ts:846-863`）会额外 `await this.ws.cancel(sid)`，从而触发后端 `handleCancel` → `failSession`。`cancelPageTask` 不通知后端：
- 后端在途请求不会立即失败（依赖超时，见 P2-4）；
- `PageEngine.cancel()` 只置 `cancelled=true` 并 `endTask()`，`activeSessionId` 归 null，Agent 紧接着的下一次页面工具请求会走 `beginTask()` 把 `cancelled` 重置为 false（`engine.ts:181-188`），于是「停止」只影响当前一步，Agent 会继续操作页面。

**修复建议**：`cancelPageTask()` 与 `stop()` 对齐，至少调用 `ws.cancel(sessionId)`（或新增专用取消帧）；如产品语义是「只停页面动作、不停 Agent」，也应保持一个「本会话已停止页面操作」的标记，直到下一轮用户消息才允许重新 `beginTask`。

### P2-6. 宿主 `page.initialLevel: 'full'` 会在身份就绪后静默写入持久化 full 授权

**位置**：`sdk/embed/src/controller.ts:307`、`sdk/embed/src/page/authorization.ts:52,71-83,87-110`

`EmbedController` 构造时 `identity` 仍为 null（鉴权发生在 `open()`），此时 `setLevel('full', null)` 走 `pendingFull = true` 分支；随后首次 `syncIdentity()` 拿到真实身份时，会直接 `localStorage.setItem(key, 'full')` 并保持 `full`。也就是说业务方只需在 `init` 里写 `page: { initialLevel: 'full' }`，就为最终用户持久授予了「完全授权」，与 `MaoChatPageOptions` 注释「宿主不能借此静默授予高权限」以及方案 3.3 的约定不符。

**修复建议**：`initialLevel` 只允许收紧（`per_action`）或作为会话级/内存级初始值；`full` 必须由用户在浮窗内显式点击并确认后才持久化。可让 init 传入的 `full` 退化为 `task`/`per_action`，或强制弹一次确认。

### P2-7. 复用节点的语义签名相同仍可命中，可能操作到错误业务对象

**位置**：`sdk/embed/src/page/snapshot-manager.ts:96-112`（`resolve`）、`sdk/embed/src/page/scanner.ts:129-136`（`signatureOf`）

`signatureOf` 由 `tagName/role/type/name/id/label/text(前 120 字)` 组成。列表复用同一行 DOM、按钮文案固定（如每行都是「编辑」「删除」）时，节点被换成另一条业务数据后签名完全一致，`isConnected` 与签名校验都通过，旧 `elementId` 会作用到新对象上——正是方案第 6.2 节要避免的「DOM 重建/关键属性变化后旧引用必须拒绝」。

**修复建议**（择一）：
- 为每个被采集元素分配一个 `WeakMap` 身份 token，快照保存 token，`resolve` 时校验 `WeakMap.get(el)` 一致；
- inspect 时挂一个 `MutationObserver`，记录「采集后是否发生过 DOM 变更」，发生过则使该快照失效，强制重新 inspect。

补「同一按钮节点被换行数据后旧 elementId 被拒绝」的用例。
