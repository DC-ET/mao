## 一、本轮重点复核结论

### 1. `getRootNode().activeElement` 是否同时覆盖主文档 / 同源 iframe / 开放 Shadow DOM —— 读取口径正确

- 位置：`framework-events.ts:54`、`executor.ts:262`。
- `getRootNode()` 对三类场景分别返回主 `Document`、iframe 的 `Document`、`ShadowRoot`，三者都有 `activeElement`，读取口径正确。实测：
  - 主文档：`document.activeElement`，与旧实现等价（全套 269 用例通过，无回归）。
  - 同源 iframe：`input.getRootNode() === iframe.contentDocument` 为 true（探针 P4），`fill` 后 `blur` 触发 1 次（新用例）。
  - 开放 Shadow DOM：`getRootNode() === shadowRoot` 且 `shadowRoot.activeElement === input`（探针 P8/P9），`fill` 触发 blur、`focus` 成功（新用例）。
  - 嵌套 Shadow DOM：`fill`/`focus` 均成功、blur 触发 1 次（探针 P30/P31）。
  - slot 透传元素：`getRootNode()` 返回主 `document`，`fill` 触发 blur（探针 P32/P33），未被 Shadow 口径误伤。
- **类型转换安全性**：`getRootNode()` 运行时可能返回 `Document` / `ShadowRoot` / `DocumentFragment` / 元素自身。仅后两者没有 `activeElement`（读到 `undefined`，不抛异常），且 `resolve()` 已用 `isConnected` 拦截非连接元素，`fill`/`focus` 不会走到该分支（探针 P17：游离元素 `getRootNode()` 返回自身、`activeElement === undefined`）。转换在编译期通过 `vue-tsc`，运行时安全。
- **反证（证明新用例有效）**：在 `/tmp` 副本中
  - 把 `dispatchBlur` 回退为 `document.activeElement !== el` → iframe 用例失败（`blur` 0 次）；Shadow DOM 用例的 fill 部分失败（`blur` 0 次）。
  - 仅回退 `executeFocus` 为 `el.ownerDocument.activeElement` → Shadow DOM 用例在 `expect(focus.success).toBe(true)` 处失败（`expected false to be true`）。
  - 说明两个新用例分别真实守住 `dispatchBlur` 与 `executeFocus` 两处修复，非静默通过。

### 2. `stateKeyOf` 对 options 改为 `[value, selected, disabled]` —— 未引入新误报，但新用例无效

- 位置：`snapshot-manager.ts:42`。
- 功能正确：真实「非选中 option 的 value 变化」在旧口径下 `updated=0`，新口径下 `updated=1`（探针 P20：`<select><option value="a" selected>A</option><option value="b">B</option></select>` 改第二个 option 的 value）。非选中 option 的 `disabled` 变化同样由 0 → 1（探针 P14）。未发现新增误报：
  - 动态重建但内容/顺序一致的 option 列表：`updated=0`（P12）。
  - 含重复 value 的 select 未变化：`updated=0`（P13）。
  - 敏感 select 未变化：`updated=0`；仅切换选中项：`updated=1`（P15/P16），既无误报也不丢变化。
- `updated` 与 `added/removed` 的扣除口径自洽：`added/removed` 仅按 `signatureUpdates`（同 token 且签名变化）扣除（`:186-187`），与 HEAD 中用于扣除的 `updated` 逐位等价，纯状态更新不参与扣除，无回归。
- **但新增用例未真正覆盖该修复**（详见 P3-1）。

## 二、P3

### P3-1. 新增用例 `reports updated when a non-selected option value changes` 实际未覆盖非选中项（用例无效）

**位置**：`sdk/embed/src/page/snapshot-manager.spec.ts:111-117`

**问题**
用例 fixture 只有一个 option：`<select><option value="a">A</option></select>`。单个 option 默认即被选中，修改其 `value` 会同时改变 `select.value`，因此**旧口径（只比 `descriptor.value` + `options.selected`）同样会报 `updated=1`**，用例无法区分新旧实现，起不到回归保护作用。

**反证数据（`/tmp` 副本）**

| 场景 | 旧口径 `options.map(o=>o.selected)` | 新口径 `[value,selected,disabled]` |
| --- | --- | --- |
| P21 单 option（默认选中）改 value | `updated=1` | `updated=1`（用例通过） |
| P20 两个 option 中改**非选中**项 value | `updated=0` | `updated=1` |

即：把 `:42` 回退为旧写法，该用例仍然通过；真正需要保护的非选中场景未被断言。

**影响**
P3-2 的修复本身有效，但缺少有效回归用例；同时 `options` 中 `disabled`、顺序两项改动也均无对应用例。

**建议**
fixture 改为两个 option 并只改非选中项，例如：
`<select><option value="a" selected>A</option><option value="b">B</option></select>`，然后 `options[1].value = 'z'`，断言 `updated===1`。可选再补一条「改非选中项 disabled」用例。

### P3-2. 同源 iframe 内元素在真实浏览器仍不可操作（既有跨 realm 盲区，非本次回归；新用例给出假信心）

**位置**：`executor.ts:257`（`if (!(el instanceof HTMLElement) ...`）、`executor.ts:284`（`isEditable` 走 `visibility.ts` 的 `instanceof`）、`scanner.ts:roleOf/kindOf`。

**问题**
`getRootNode().activeElement` 的读取对 iframe 是正确的，但 `executeFocus`/`executeFill` 在其**之前**还依赖 `instanceof HTMLElement / HTMLInputElement / HTMLTextAreaElement`（`isEditable`）。在真实浏览器中，iframe 文档内的元素属于**另一个 realm**，`el instanceof parentRealm.HTMLElement` 恒为 `false`，于是：
- `executeFocus` → `not_focusable`；
- `executeFill` → `element_not_fillable`（根本走不到 blur 派发）；
- 扫描侧 `roleOf/kindOf` 也会退化为 `tagName` / `other`。

因此本轮新增的 iframe 用例（`executor.spec.ts:53`）**只在 happy-dom 下通过**：探针显示 happy-dom 的 iframe 元素 `defaultView !== window`（确为独立 Window，P3），但 `instanceof HTMLElement` 仍为 `true`（P1/P2）——即 happy-dom 跨 Window 共享了构造器，与真实浏览器语义不同，用例无法暴露该问题。

**影响**
属既有缺陷（改动前后一致），本次未使其恶化；但 `framework-events.ts:52`、`executor.ts:260` 的新注释宣称覆盖「同源 iframe」，与实际能力不符，易误导后续读者。

**建议**
若确认 iframe 操作在范围内，将相关 `instanceof` 改为 realm 安全判定（如 `Object.prototype.toString.call(el)` 或按 `el.ownerDocument.defaultView` 上的构造器判断）；若不在范围内，至少在注释与用例名中写明「iframe 仅修复焦点读取口径，元素可操作性未覆盖」，避免假信心。

### P3-3. `stateKeyOf` 按顺序比较 options：选项顺序变化会报 `updated`（口径噪声，非错误）

**位置**：`snapshot-manager.ts:42`

**问题**
`options.map(...)` 生成的是**有序数组**，因此仅重排选项顺序（值集合不变）即会报 `updated`（探针 P11：两 option 互换顺序 → `updated=1`）。

**影响**
多数场景下选项重排确为真实 UI 变化，报告 `updated` 合理；但若某些框架会做无意义的重排（如按不稳定键重排），会给 `page_observe` 引入噪声，agent 可能误判页面已变化。非功能错误，可不改。

**建议**
如担心噪声，可改为对 `[value, selected, disabled]` 做排序后比较（多重集口径）；若认为顺序变化即应上报，保持现状并在注释中说明。
