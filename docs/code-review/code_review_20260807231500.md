## 三、本轮新发现问题

### 【一般】1. 追问执行期间，`agentLoop` 的 cancel flag 以 sessionId 为 key，与同会话新请求存在误删冲突

- **位置**：`DelegateFollowupTool.java`（`registerCancelFlag` / `removeCancelFlag`）；`StreamingWsHandler`（RUNNING 会话收消息会 abort 后重新注册 flag）
- **处理决定**：**不做**。触发前提是用户对 RUNNING 中的子代理会话发新消息；子代理 Tab 为**只读**（无输入区），UI 层不存在该入口，API 直调属越权边界外的误用。该机制为既有通用行为（delegate 同样存在），非本需求引入。

### 【一般】2. 执行中取消（非 skip）路径会把子会话上一轮 COMPLETED 终态改写为 CANCELLED，与 skip 路径不对称

- **处理决定**：**不做**。两者语义本就不同：skip = 追问从未开始 → 恢复原终态准确；执行中取消 = 追问已开始且被中断 → CANCELLED 与主会话取消行为一致、状态准确。非「不对称」，是「不同场景不同语义」。

### 【轻微】3. 前端未适配 `delegate_followup`：追问卡片无专属 label 与「查看子代理过程」入口

- **位置**：`desktop/src/components/chat/ToolCallGroup.vue`、`ToolCallCard.vue`
- **修复**：
  - `ToolCallGroup` 增加 `delegate_followup: { label: '追问子代理', icon: Connection }`
  - `ToolCallCard` 的 `isDelegate` 扩展为包含 `delegate_followup`（「查看子代理过程」按钮对追问生效）

### 【轻微】4. `summarizeDelegate` 将「已取消」摘要为「(错误)」

- **修复**：先检查 `cancelled==true` 输出「(已取消)」，再判断 error/success。

### 【轻微】5. skip 路径下前端对「被取消的追问」零感知（无任何 WS 事件）

- **处理决定**：**不做**。与「前端零改动」决策一致；DB/审计状态正确，重开 Tab 可见追问消息。
