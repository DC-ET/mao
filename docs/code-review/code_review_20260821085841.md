## 一、第四轮修复验证

### 1. [中] `ask_user_questions_cancelled` 无条件 `modal = null` —— ✅ 已修复

`ink-renderer.ts` cancelled 分支现为：
```ts
case 'ask_user_questions_cancelled':
  if (this.modal?.type === 'ask' && this.modal.requestId === evt.requestId) {
    this.modal = null;
    this.resolveAsk(evt.requestId, 'cancelled');
  }
  this.flush();
  break;
```
- 仅关闭「属于该 requestId 的 ask modal」，不再误关 approval / 其他 ask modal。✓
- **resolver 不泄漏推演**：`askResolvers` 中条目在 modal 离开 ask 状态的所有路径上均被删除——用户应答/取消走 `onAskResponse → resolveAsk`；`requestApproval` 覆盖走 `resolveAsk(requestId, [])`；ask→ask 覆盖走 `resolveAsk(旧, [])`；服务端取消走本分支。cancelled 不匹配时不 resolve 不会造成泄漏。✓
- **断线重连重放 cancelled 安全**：重放的旧 cancelled(R1) 到达时，modal 若是新 ask R2 / approval / null，requestId 不匹配，不误关。✓
- 正常应答后服务端回发 cancelled(R1) 作为确认：此时 modal 已被 `onAskResponse` 关闭（null），条件不满足，无害。✓

### 2. [中] `requestApproval` 覆盖 ask 后服务端 `waitForAnswer` 阻塞 —— ✅ 已修复

`requestApproval()` 现为：
```ts
if (this.modal?.type === 'ask') {
  this.resolveAsk(this.modal.requestId, []);
}
```
- 空数组走 `handleQuestions` 的**非 sentinel 分支**（`[] !== 'cancelled' && [] !== 'fail'`）→ `sendReliable({ type: 'ask_user_questions_result', data: { requestId, answers: [] } })` → 服务端 `handleAskUserQuestionsResult` 中 `JSON.stringify([])` → `{"answers": []}` → `complete()` 成功 → `waitForAnswer` 立即返回，回合不再阻塞。✓
- 服务端对空 answers 无校验拒绝，`complete` 正常触发并回发 cancelled 确认（与问题 1 修复配合，该 cancelled 因 modal 已是 approval 而不匹配，无副作用）。✓

### 3. [低] ask→ask 直接覆盖 —— ⚠️ 部分修复（resolver 已防护，AskModal key 未加）

`onEvent` ask 分支已补：
```ts
} else if (this.modal?.type === 'ask' && this.modal.requestId !== evt.requestId) {
  this.resolveAsk(this.modal.requestId, []);
}
```
- resolver 泄漏防护 ✓（旧 ask 以空答案提交，服务端解除阻塞）。
- **但 `app.tsx` 中 `AskModal` 仍无 `key={modal.requestId}`**（第四轮建议项未落地）：ask→ask 直接覆盖时 React 复用 AskModal 组件实例，`qIndex` / `answersRef` / `selected` / `custom` 状态跨请求残留——R2 会从 R1 的题目进度开始、`answersRef` 混入 R1 答案（多选会发错答案）、R2 题数更少时 `q` 为 undefined 触发 `onResolve('fail')`。
- **可达性评估**：服务端 agent loop 串行，R1 未决时阻塞在 ask 工具上，不会发 R2；应答后 modal 已关闭再弹 R2 属全新挂载，无复用。故 ask→ask 直接覆盖在正常业务下不可达，仅防御性缺陷。建议补 `key={modal.requestId}`（一行改动），彻底消除隐患。

### 4. [低] `repl.ts` `onAskResponse` 无条件 `setModal(null)` —— ⚠️ 未修改，但实际不可达

代码仍是：
```ts
onAskResponse: (requestId, answers) => {
  opts.tuiHandle.setModal(null);
  opts.renderer.resolveAsk(requestId, answers);
},
```
- **不可达推演**：`setModal(null)` 误关 approval 的前提是「AskModal 的 onResolve 在 modal 已被替换为 approval 之后仍被触发」。但 Ink reconciler 同步提交：`requestApproval` 覆盖时 `this.modal` 变 approval → `flush()` → React 同步卸载 AskModal 并移除其 `useInput` handler；用户按键事件在后续事件循环才到达，此时 handler 已不存在。JS 单线程下 WS 事件与按键事件也不会在同一同步栈交错。故当前实现不可触发。
- 属防御性加固建议：可改为仅在 renderer 侧 modal 仍为对应 ask 时关闭（由 `resolveAsk` 统一管理 modal 归属清理）。不阻塞合入。

## 二、本轮复核未发现新的功能性 bug

逐项核对（重点关注的 6 点）：

1. **`resolveAsk([])` → handleQuestions 是否发 result**：是。`[]` 不命中 `'cancelled'`/`'fail'` sentinel，走 `sendReliable(ask_user_questions_result)`，服务端 `complete` 正常收尾。✓
2. **cancelled 的 requestId 匹配**：`modal.type === 'ask' && modal.requestId === evt.requestId` 双条件，断线重连重放 cancelled 不会误关新 modal。✓
3. **modal 单槽所有覆盖路径收尾**：ask→approval（`resolveAsk(旧, [])`）✓、approval→ask（`resolveApproval('deny')`）✓、ask→ask（`resolveAsk(旧, [])`）✓、approval 用户选择（y/n/a/Esc/Ctrl+C → `resolveApproval`）✓、ask 用户应答/取消（→ `onAskResponse → resolveAsk`）✓、服务端取消（cancelled 匹配分支）✓。所有 resolver 均无泄漏路径。
4. **正常回答路径**：AskModal `onResolve(answers)` → `onAskResponse` → `setModal(null)` + `resolveAsk(answers)` → handleQuestions 发 result → 服务端 complete → 回 cancelled（modal 已关，不匹配）→ 闭环。✓
5. **主链路**：发送（onSubmit→handleSubmit→runOne→runPrompt）、流式（content_delta/tool_call/thinking）、ask、approval（LocalExecutor `askApproval` → `requestApproval` → `tool_approval`）、退出（Ctrl+C 两次 / Ctrl+D / /exit → `requestExit` → shutdown + unmount）均闭环。**Ink `unmount()` 有 `isUnmounted` 幂等保护**（ink.js 源码确认），Ctrl+D 时 `useApp().exit()` 与 `tuiHandle.unmount()` 双重调用安全。✓
6. **--print 隔离**：`inkRenderer` 创建/挂载/`askHandler`/`askApproval`/SIGINT 注册全部有 `!cfg.print` 守卫；打印模式走 TextRenderer/JsonRenderer + readline 回退，无 Ink 泄漏。✓
7. **空数组与用户未回答的区分**：服务端可区分——空数组 result 使 `complete()` 返回 `{"answers": []}`；用户未回答（超时）是 `{"error": "User did not respond within timeout"}`。客户端覆盖场景发空数组不会与「未回答」混淆。✓

## 三、低优先级建议（不阻塞合入）

### 1. [低] `app.tsx` AskModal 缺 `key={modal.requestId}`
- 位置：`src/tui/app.tsx` 第 ~120 行 `<AskModal ... />`。
- 建议：加 `key={modal.requestId}`，使 ask→ask 覆盖时组件状态强制重置（第四轮问题 3 的完整修复）。

### 2. [低] `repl.ts` `onAskResponse` 的 `setModal(null)` 语义加固（第四轮问题 4）
- 位置：`src/repl/repl.ts` `onAskResponse`。
- 建议：由 renderer 侧按 requestId 归属关闭 modal（或 `resolveAsk` 统一管理），避免 `setModal(null)` 与 modal 实际归属脱节。

### 3. [信息] 空数组答案的 Agent 侧语义
- `requestApproval` / ask→ask 覆盖时服务端 Agent 收到 `{"answers": []}`，可能被解读为「用户跳过问题」而追问（再弹新 ask modal）或误判。相比 15 分钟阻塞是更优权衡，但建议确认 Agent prompt 对空 answers 的行为可接受（如提示「用户未提供答案」而非「用户回答了空内容」）。

### 4. [信息] 测试覆盖缺口
- 本轮修复（cancelled requestId 匹配、覆盖发空数组 result、ask→ask resolver 防护）均无回归测试；`test/repl-renderer.spec.ts` / `test/ui.spec.ts` 仅适配 alt screen 移除断言。建议后续补充 `InkTuiRenderer.onEvent` 的单元测试（可 mock `flush`/`handle` 直接断言 modal 状态与 resolver 收尾）。
