## 中等严重程度

### 1. 压缩持久化成功但最新状态重载失败时，仍会发送压缩前的完整历史

**代码位置**

- `backend/src/main/java/cn/etarch/mao/harness/core/SessionCompactionOrchestrator.java:48-70`
- `backend/src/main/java/cn/etarch/mao/harness/core/HarnessService.java:407-420`

**问题说明**

上一轮报告指出，压缩已持久化后如果后置步骤异常，不能回退到旧的 `normalRequest`。当前修复改为在异常处理里执行 `buildNormalRequest(context)`，这可以覆盖“`applyHistory` 已经成功、后续统计或锚点步骤失败”的情况。

但仍有一个持久化后的异常窗口：

1. `sessionCompactionService.persist(...)` 已成功提交新的摘要和边界；
2. 紧接着的 `loadValidated()` 或 `loadHistoryAfterBoundary()` 因临时数据库异常失败；
3. 此时 `applyHistory()` 尚未执行，`context` 仍是压缩前的完整历史；
4. `HarnessService` 捕获异常后从这个旧 `context` 重建请求，实际仍会向模型发送压缩前的历史。

这会导致本轮实际请求与已经前移的 durable compaction boundary 不一致，并可能因为旧历史仍接近上下文上限而调用失败。下一次请求虽然会从数据库加载新摘要，但当前请求的压缩效果丢失。

**修复建议**

异常降级不能只依据当前内存 `context`，还需要知道 durable boundary 是否已经提交。建议：

- 将“生成压缩结果”“CAS 持久化”“重载应用”拆分为可识别阶段，并返回结构化状态；
- 一旦 `persist()` 成功，重载失败时应重试读取最新压缩记录和边界，不能直接继续旧请求；
- 如果在有限重试后仍无法重载，应终止本轮并返回明确错误，而不是发送与 durable boundary 不一致的旧历史；
- 或把持久化与后续必要状态读取设计为同一可靠事务/返回值，使成功持久化后可直接用已知摘要构建一致的内存上下文。

建议补充测试：模拟 `persist()` 返回 `true` 后第一次 `loadValidated()` 或 `loadHistoryAfterBoundary()` 抛异常，断言不会继续使用压缩前请求。
