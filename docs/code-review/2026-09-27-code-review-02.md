## 本轮新发现

### 1.（阻塞）buildDetailWhere 生成 `f.` 前缀条件，但 countTotal 与 sumByReason 的 SQL 无 `f` 别名 → 管理端带筛选查询直接 SQL 报错

- 文件：`backend-ts/src/feedback/feedback.repository.ts:65、73、108-125`
- 描述：`buildDetailWhere` 生成的条件均带表前缀（`f.reason = ?`、`f.created_at >= ?`、`f.created_at < DATE_ADD(...)`）。`listDetails` 的 FROM 是 `message_feedback f`（有别名）没问题；但：
  - `countTotal`：`SELECT COUNT(*) AS c FROM message_feedback ${where}`（第 65 行）
  - `sumByReason`：`SELECT reason, COUNT(*) AS count FROM message_feedback ${where} GROUP BY reason`（第 73 行，本次修改 sumByReason 复用 buildDetailWhere 后新触发）
  两处表名没有 `f` 别名，条件一旦非空即报 MySQL 1054 `Unknown column 'f.reason' / 'f.created_at' in 'where clause'`。
  注：countTotal 该问题第 1 轮即已存在（当时漏报），本次 sumByReason 改动使影响面扩大到汇总接口。
- 触发路径：管理端点踩反馈页选择「原因」或「日期」后查询——`/feedback/admin/list`（reason/startDate/endDate 任一）与 `/feedback/admin/summary`（startDate/endDate 任一）都会 500（INTERNAL_ERROR）。不带筛选时页面正常，属核心筛选路径必现。
- 修复建议：给 countTotal / sumByReason 的表名补别名 `FROM message_feedback f`（与 listDetails 一致），或让 buildDetailWhere 不带前缀。修复后建议补一条验证含 `f.` 前缀 SQL 拼接的用例。

### 2.（重要）listMessageIdsBySession 仍按 snake_case 读键 → 点踩回显接口返回 NaN，桌面端回显全部失效

- 文件：`backend-ts/src/feedback/feedback.repository.ts:54-60`
- 描述：`SELECT message_id FROM message_feedback` 经 `db.query`（toCamelList）后行键是 `messageId`，但代码读 `(r as Record<string, unknown>).message_id` → `undefined`，再经 `Number(undefined)` 固化为 `NaN`，返回 `[NaN, ...]`（JSON 序列化为 `[null, ...]`）。
  注：第 1 轮该处即写的是 `r.message_id`，当时报告未覆盖到此方法，属遗留遗漏；本次 `Number()` 包装使坏值从 undefined 变为 NaN。
- 影响：`GET /v1/feedback/messages/disliked-ids` 永远返回无效 ID；desktop 端 `loadDislikedIds` 后 `isMessageDisliked` 无法命中任何消息 → 刷新页面/切换会话后「已点踩」状态全部丢失（当次会话内新提交的仍是高亮，因为走本地 Set）。点踩提交与取消本身不受影响。
- 修复建议：读取键改为 `r.messageId`（或直接在 SQL 用 `AS messageId` / 接口层统一 camelCase 泛型），与阻塞 1 的修复方式保持一致。

## 结论

**不可合并（阻塞 1 个 + 重要 1 个）**。第 1 轮 6 个问题均已按说明修复，但复查发现：① `f.` 前缀 SQL 条件与无别名表组合导致管理端筛选全挂（核心路径）；② 回显接口的 `message_id` 键名遗留问题导致刷新后点踩状态全部丢失。两处都建议补真实 SQL 拼接路径的测试覆盖（现有单测全部 mock 了 db 返回值，无法发现此类问题）。
