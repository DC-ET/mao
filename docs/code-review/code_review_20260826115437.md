# 第 6 轮代码审查报告

- 审查范围：当前 Git 工作区未提交代码
- 重点：确认失败/过期收敛、OAuth 与待绑定消息状态一致性、绑定回调单次执行、卡片发送回退、原始消息继续执行及同卡片复用
- 结论：发现重大功能 bug，核心需求仍未全部满足。

## 高严重程度

### 1. OAuth 成功状态仍可能在过期后写入 SUCCESS

- **位置**：`backend-ts/src/auth/feishu-oauth.repository.ts:22-49`、`backend-ts/src/auth/feishu-auth.service.ts:107-125`
- **问题**：`updateByState()` 仅在 `expectedStatus === 'PROCESSING'` 时追加 `expires_at > CURRENT_TIMESTAMP`，表面上阻止了 PROCESSING 过期后的 SUCCESS/FAILED 更新。但 `completeStateWithCode()` 在 `catch` 中先尝试把 PROCESSING 更新为 FAILED；如果处理跨过过期时间，该更新同样被拒绝，随后没有将状态收敛为 EXPIRED。更关键的是，`getLoginStatus()` 对 PROCESSING 过期执行 `updateByState(..., { status: EXPIRED })`，该更新也会被同一 `expires_at > CURRENT_TIMESTAMP` 条件拒绝，因此数据库仍长期停留在 PROCESSING，无法真正收敛。
- **影响**：确认失败/外部认证耗时超过有效期后，状态可能永久保持 PROCESSING；轮询虽然返回 EXPIRED，但数据库状态不一致，后续回调、清理和运维无法可靠判断终态。
- **修复建议**：为 PROCESSING→EXPIRED 提供不带有效期正向条件的原子更新（例如 `WHERE state=? AND status='PROCESSING' AND expires_at <= ?`），并检查 affectedRows；失败路径按当前状态区分 FAILED 与 EXPIRED。补充“claim 后等待过期，再失败/轮询”的集成测试，断言数据库最终状态为 EXPIRED。

## 中严重程度

### 2. 原始消息恢复执行失败时，CLAIMED 状态没有回退，后续无法重试

- **位置**：`backend-ts/src/create-app.ts:310-318`、`backend-ts/src/feishu/pending-binding.repository.ts:36-58`
- **问题**：OAuth 成功回调先将待绑定消息从 SENT 原子领取为 CLAIMED，然后直接调用 `pendingBindingProcessor.process(...)`。如果绑定后的原始消息处理在 `resolveSenderName`、`recordGroupMessage`、Agent 执行或其他步骤抛错，异常会从认证回调冒泡，但待绑定消息没有 `FAILED`/可重试状态，也没有记录恢复失败原因。`claim()` 只查 SENT，因此该消息永久停在 CLAIMED，原始消息不再执行。
- **影响**：违反“原始消息继续执行”；一次暂时性数据库、模型或飞书 API 故障会造成不可恢复丢消息，并使 SENT/CLAIMED 状态与实际执行结果不一致。
- **修复建议**：将恢复执行包在独立 try/catch 中；成功完成后明确标记 DONE/CONSUMED，失败时原子回退为 SENT（或进入带重试/错误信息的 FAILED 状态），并避免让绑定成功本身失败。若要求严格只回调一次，应使用 CLAIMED + lease/重试计数，而不是永久 CLAIMED。
