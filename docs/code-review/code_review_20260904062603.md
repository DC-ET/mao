## P2 功能不完整 / 健壮性

### P2-1 attach 的权限查库期间连接断开：终端 sink 绑到已死连接，既不回收也会顶替重连后的新连接

- 位置：`backend-ts/src/harness/terminal/terminal-ws-handler.ts:235-273`（`handleAttach`：`await permissionService.hasPermission` 之后直接 `terminal.attach(...)` 与 `conn.terminals.add(...)`）、`163-173`（`afterConnectionClosed` 按当时的 `conn.terminals` 快照解绑）
- 现象：串行队列解决了「同连接内帧乱序」，但没有覆盖「处理中连接就关闭」。`processTextMessage` 的 `readyState` 守卫（`terminal-ws-handler.ts:126-127`）只在帧**开始处理前**生效；一旦 attach 已进入权限查库的 `await`，后续 `afterConnectionClosed` 只会遍历当时的 `conn.terminals`（尚未包含该 terminalId），随后迟到的 attach 继续执行，把 `sink` 绑到已经关闭的 socket 上。
- 实测（只读脚本，import `dist/` 的 `TerminalWsHandler` + 假 socket，权限查库改为手动放行以精确落在 await 窗口内）：

```
场景一：attach 在途时连接关闭
  permission pending?        true
  connectionCount            = 0
  attachedSocketId           = sock-A   <= 期望 null
  isIdleTimeout()            = false    <= 永不进入 idle 回收

场景二：断连后客户端重连并重新 attach（刷新页面）
  B 绑定后 attachedSocketId      = sock-B | B frames = ["connected","attached"]
  A 迟到完成后 attachedSocketId  = sock-A
  B 收到的帧 = ["connected","attached","error:TERMINAL_TAKEN_OVER"]
```

- 影响：
  1. **配额泄漏**：`RemoteTerminal.isIdleTimeout` 首行是 `if (this.sink != null) return false`（`remote-terminal.ts:206-209`），sink 挂在死连接上 → 该终端永远不被 idle 回收，只能等 `maxLifetimeHours`（默认 24h）。每任务上限 5 / 全局 50，反复命中会占满配额，用户侧表现为「该任务的终端数量已达上限」。
  2. **重连窗口被误报接管**：若客户端已重连并 attach 成功，旧连接迟到的 attach 会顶替新 sink，前端新窗口收到 `TERMINAL_TAKEN_OVER` → 显示「该终端已在其他窗口接管，此处已停止接收输出」并停止输出，用户必须手动点「重新接管」才恢复（`useTerminal.ts:254-259`）。
  3. 次要：为一次实际失败的 attach 写了 `ATTACH` 审计。
- 触发条件：attach 帧发出后、权限查库（`PermissionService.hasPermission` 内 3 次 repo 查询）返回前连接关闭 —— 约 10ms 级窗口，刷新页面 / 关闭标签 / 弱网抖动时可能命中。频率低，但后果持续时间长。
- 建议：在 `handleAttach` 的 `await` 之后补一次连接有效性复核，失效则直接返回（不 attach、不记审计）：

```ts
if (!(await this.deps.permissionService.hasPermission(...))) { ... }
// await 期间连接可能已关闭：此时不能再把终端绑到该 socket，否则 sink 泄漏
if (this.connections.get(conn.socket.id) !== conn || conn.socket.readyState !== TERMINAL_WS_OPEN) return;
```

  也可在 `afterConnectionClosed` 里对该 socket 追加一次兜底 detach（等待该连接队列排空后再遍历 `conn.terminals`），但前者更直接。建议同时补一条单测：`attach 在权限查库期间断连不会留下 sink`。

## P3 低 / 可维护性

### P3-1 `terminal.reset()` 是同步的、`write()` 是异步入队的：二次 attach 的清屏可能失效，出现重复内容

- 位置：`desktop/src/composables/useTerminal.ts:243-245`（`onAttached: () => terminal.reset()`）
- 现象：xterm 的 `write()` 把数据放进内部 writeBuffer 分块消费，而 `reset()` 立即清当前屏幕缓冲。短时间内两次 attach（重连、切任务快速往返、点「重新接管」）时，第二次的 `reset()` 清的是「上一段回放还没写进来的空缓冲」，随后旧回放继续落屏并与新回放拼接。
- 实测（jsdom + 真实 `@xterm/xterm` 6.0.0，先 write 4000 行回放，紧接 `reset()` + 写入新回放）：

```
total non-empty lines after reset+replay2 = 4001
first 3 = ["R1-line-0","R1-line-1","R1-line-2"]
last 3  = ["R1-line-3998","R1-line-3999","R2-ONLY"]
contains R1 leftovers = true      <= reset() 未能清掉排队中的旧回放
```

- 影响：仅显示层重复（滚动区出现两份历史输出），输入/输出通道正常。默认 `outputBufferBytes = 262144`，回放量足够大时才有明显窗口。
- 建议：把清屏交给 write 队列的顺序，例如 `terminal.write('\x1bc')`（RIS）或 `terminal.reset()` 改为在 `write` 回调里执行（`terminal.write('', () => terminal.reset())`）；也可在收到 `attached` 后先记标记，回放帧到达时用 `write(clearSeq + data)` 一次性下发。

### P3-2 `attachRemote` 成功回调无条件 `clearTakenOver`，与 `onError` 的 `markTakenOver` 存在顺序耦合

- 位置：`desktop/src/composables/useTerminal.ts:278-288`（`attach().then(() => clearTakenOver(id) ...)`）、`useTerminalWS.ts:142-151`（error 帧先 `settleAttach`（resolve）再回调 `handler.onError`）
- 现象：`error` 帧的处理顺序是「先结束 attach 等待（按成功 resolve）→ 再回调 onError」。因此当 `TERMINAL_TAKEN_OVER` 落在 attach 在途窗口内时，`onError` 里刚 `markTakenOver(id)`，紧随的 `.then()` 微任务又 `clearTakenOver(id)` 把标记清掉 → 终端里有黄字提示，但「重新接管」按钮不出现（`activeTakenOver` 为 false）。
- 影响：需要「本窗口正在 attach 且同时被第三方顶替」的时序，实践中罕见；当前主路径（已 attached 后被顶替）没有在途 waiter，不受影响。属代码脆弱性。
- 建议：`.then()` 里只在本次 attach 确实成功（例如 `settleAttach` 区分 resolve 原因，或在 `attached` 帧回调内清标记）时才 `clearTakenOver`。

### P3-3 `doRestoreRemoteTabs` 的代际校验放在清理逻辑之前，被后端回收的 tab 会滞留到下次切回

- 位置：`desktop/src/composables/useTerminal.ts:344-360`
- 现象：新增的代际校验 `if (sessionStore.activeSessionId !== sessionId) return` 位于 `remoteIds` 计算与 `removeTab` 循环之前。请求返回时用户已切走的情况下，既不 attach（正确，避免上轮 P2-4），也不清理已被后端回收的本地 tab。
- 影响：切回该任务时下一次 restore 会补上清理并弹「终端已被回收」，最终一致；期间只是标签栏多一个点开无输出的 tab。可接受。
- 建议：若想更干净，可把清理与 attach 分开——清理不受代际影响，只有 `attachRemote` / `adoptRemoteTerminal` 与 `activeTabId` 赋值需要代际守卫。

### P3-4 attach 在途时复用 waiter 不重发 attach 帧，帧丢失只能等 15s 超时且不自动重试

- 位置：`desktop/src/composables/useTerminalWS.ts:254-258`
- 现象：已有在途 waiter 时直接返回旧 promise，仅在未认证时补一次 `connect()`。若上一次 attach 帧已发出但服务端未回帧（帧丢失、后端处理异常被 `harnessLog` 吞掉），只能等 `ATTACH_TIMEOUT_MS = 15_000` 后 reject。
- 影响：`attachRemote` 的 catch 写入「[终端连接中断，正在重试…]」，但实际不会自动重试——文案与行为不符，用户需切走再切回或点「重新接管」。
- 建议：超时 reject 后自动重试一次（或改文案为「连接超时，请点击重新接管」）。同时可考虑重连成功（`onAuthenticated` 重排 attach）时重置在途 waiter 的超时计时。

## 已核实无问题（本轮复审结论）

1. **串行队列的 Map 回收无泄漏**：队尾用 `if (this.queues.get(socket.id) === current) this.queues.delete(socket.id)` 做身份比对，新帧入队后不会被旧回调误删；`afterConnectionClosed` 也会 `queues.delete`，且已入链的帧被 `readyState` 守卫拦下。
2. **`readyState` 守卫不会吞正常帧**：`TerminalSocket.readyState` 由 `attach-websocket.ts:60` 的 getter 映射为 `socket.OPEN → 1`，正常连接期间恒为 `TERMINAL_WS_OPEN`。
3. **DOM 迁移与 attach 顺序无关**：实测「回放先到、迁移后到」的反序场景，迁移完成后 DOM 仍能显示 detached 期间写入的内容，且后续写入正常渲染（xterm 渲染基于内部缓冲重绘，不依赖写入时 DOM 是否在树上）。
4. **迁移后 `fit()` / `focus()` / 输入通道正常**：`FitAddon.proposeDimensions` 对无尺寸容器直接返回 undefined，`fit()` 空操作不抛错；迁移后 `terminal.input('x')` 仍触发 `onData`（实测）。
5. **`mountTerminal` 的 `mountedTerminals` 标记与容器 ref 生命周期一致**：`setContainerRef(id, null)` 同时清除标记，因此切回时必然重新走 `mountTerminal`，与迁移分支配合正确。
6. **后端 DELETE 归属校验无缺口**：`prepare()` = requireUserId + requirePermission(`terminal:use`) + pathId + requireSessionOwner；活终端再校验 `terminal.sessionId !== sessionId || terminal.userId !== userId`。幂等分支返回成功不泄漏任何他人终端信息。
7. **`closeBySession` / `cleanupExpired` / `notifyClosed` 链路**：`close()` 先取 `toInfo()` 快照 → `forget` → `terminal.close()` → 审计 → `notifyClosed`，handler 的 `handleClosed` 按 reason 分文案统一回 `TERMINAL_RECLAIMED`；单测覆盖 idle 与 lifetime 两条路径。
8. **desktop 单测已纳入 CI**：`.github/workflows/ci.yml` 的 desktop job 跑 `npm run test:unit`（= `vitest run` + electron 的 node --test），新增的 `useTerminalWS.test.ts` 会被 `src/**/*.test.ts` 收进，无需额外接线。本地 `npx vitest run` 全量 7 文件 67 例通过。
9. **迁移与配置项**：`V100__settings_terminal.sql` 无版本号冲突；`getTerminalConfig()` 五项默认值（5/50/120/24/262144）与 admin 面板 min/max/hint 一致，`TERMINAL_INT_KEYS` 已接入正整数校验。

## 修复优先级建议

1. **P2-1**：`handleAttach` 在 `await` 权限校验后补一次「连接仍是同一个且仍 OPEN」的复核，三行代码即可，避免 24h 级配额占用与重连误报接管。
2. P3-1：若在意重连后的重复历史，把 `reset()` 改为随写队列执行（`write('\x1bc')` 或 write 回调）。
3. P3-2 / P3-4 / P3-3 按可维护性节奏处理，其中 P3-4 建议至少把「正在重试…」的文案与实际行为对齐。
