## 总体结论

**未发现必须修复的重大（高严重度）bug，核心业务功能正确。**

关键机制均已验证：
- 头像/邮箱置空通过 `UpdateWrapper.set` 显式写列，`set(column, null)` 在 MP 3.5.6 中会生成 `# {ew.paramNameValuePairs.MPGENVALn}` 占位符并绑定 null 参数，确能落库（非 `updateById` 的 NOT_NULL 忽略行为）；`getSqlSet() != null` 判空逻辑正确。
- 邮箱查重排除自身、格式/长度校验、头像 URL 白名单（http(s)/`/` 开头、无空格、≤512）与 DB 列宽（email VARCHAR(128)、avatar_url VARCHAR(512)、display_name VARCHAR(128)）一致。
- 非 LOCAL 用户仅可改头像、LOCAL 用户可改资料，权限校验前置，前端以 `undefined` 规避非 LOCAL 提交（axios JSON 序列化会剔除 undefined 字段）。
- `authSource` 已在登录/刷新/LDAP/飞书/me 全部 5 处 `UserInfoVO` 构建点贯通。
- 新增接口无 `@RequirePermission`，`PermissionInterceptor` 对无注解处理器放行，任何登录用户可自助修改本人资料（符合设计）。
- `UserService.resolveAuthSource` 改为静态方法被 AuthService/LdapAuthService/FeishuAuthService 调用，无 Spring 循环依赖风险。

以下为中等/低风险问题与改进建议（均不影响主流程正确性，可按优先级择机处理）。

## 中（建议修复）

### M1. 飞书登录仍覆盖用户邮箱，与「资料由用户自助管理」存在语义矛盾（非本次引入，但需求未闭环）

- **位置**：`backend/src/main/java/cn/etarch/mao/auth/service/FeishuAuthService.java` `findOrCreateUser()` 已存在用户分支
- **描述**：本次仅注释了 `user.setAvatarUrl(avatarUrl)`，但 `user.setEmail(email)`（及 `setDisplayName`）仍会覆盖用户数据。对于「先以 LOCAL 注册、后绑定飞书」（`findUserByEmail` 命中）的用户：其 `passwordHash` 非空，`resolveAuthSource` 判定为 `LOCAL`，前端据此允许其修改邮箱/显示名；但每次飞书登录又会将其覆盖回飞书侧的值。用户自助修改后下次登录被静默重置，体验困惑。
- **建议**：与产品确认飞书邮箱/显示名是否也应遵循「不覆盖用户已设值」（与头像一致），或将这类双绑定用户的 `authSource` 判定优先级明确为 FEISHU/LDAP（仅当 passwordHash 为空时才判 LOCAL），使前后端语义一致。

### M2. 邮箱查重无唯一索引兜底（并发 TOCTOU）

- **位置**：`backend/src/main/java/cn/etarch/mao/user/service/UserService.java` `updateOwnProfile()` 邮箱查重段；`db/migration/V001__init_schema.sql` `user.email`
- **描述**：查重（`selectCount`）与写入（`update`）非原子，两个用户并发把邮箱改成同一值可同时通过查重，产生重复邮箱；`email` 列无 UNIQUE 约束。概率低但为数据完整性隐患。
- **建议**：对 `email` 加唯一索引（MySQL 唯一索引允许多个 NULL，兼容「无邮箱」用户）；写入时捕获 `DuplicateKeyException` 转为业务错误，作为查重之外的兜底。

### M3. ProfileView 表单为「快照」初始化，数据未就绪/登录态变化时可能误拦截保存

- **位置**：`desktop/src/views/settings/ProfileView.vue` `form` 初始化（`authStore.user?.displayName ?? ''`）与 `save()` 中 `!form.displayName.trim()` 校验
- **描述**：`form` 在 setup 时一次性从 `authStore.user` 取值。若进入页面时用户数据未就绪（如路由守卫 `fetchUserInfo` 失败被 catch 吞掉、或在页面内才完成登录弹窗），`form.displayName` 为空；此时 LOCAL 用户即使只想改头像，保存也会被前端「显示名称不能为空」拦截。另外 `form` 不随 `authStore.user` 更新（如其他端已改资料，本页仍显示旧值，保存会用旧值覆盖）。
- **建议**：`watch(authStore.user)` 在用户尚未编辑时同步 `form`；保存时以 `form.displayName.trim() || authStore.user?.displayName` 兜底，避免误拦截仅改头像的场景。

### M4. 头像上传失败会阻断资料保存（用户改的名字也一起丢失）

- **位置**：`desktop/src/views/settings/ProfileView.vue` `save()` 中 `if (urls.length === 0) { clearPreview(); ...; return }`
- **描述**：LOCAL 用户同时改了显示名称并选择新头像，若图片上传失败（OSS/本地），直接 return 导致显示名称/邮箱也未提交，用户会以为「名字没保存成功」。`uploadImages` 失败仅在内部 toast，未与资料保存解耦。
- **建议**：上传失败时仍继续提交资料字段（仅跳过头像更新），或失败提示中明确「头像上传失败，资料未保存，请重试」，避免用户困惑。

## 低（可选优化）

### L1. 邮箱校验顺序：格式先于长度

- **位置**：`UserService.updateOwnProfile()` email 分支
- **描述**：`!mail.isEmpty() && !EMAIL_PATTERN.matcher(mail).matches()` 先于 `mail.length() > 128`。超长且格式非法的邮箱会报「邮箱格式不正确」而非「长度不能超过 128 字符」，提示不精确。
- **建议**：先做长度校验再做格式校验。

### L2. 非 LOCAL 用户仅改头像时 `avatarUrl` 无归属校验

- **位置**：`UserService.updateOwnProfile()` avatarUrl 分支
- **描述**：头像地址可为任意 http(s) 或 `/` 开头相对路径，无法确认是否为本系统上传产物（相对路径可指向任意 uploads 下文件）。头像场景多为外链图片，风险可接受，但若需收紧可校验前缀必须为系统上传目录或 OSS bucket。
- **建议**：视产品对头像外链的开放程度决定是否收紧；当前实现符合需求文档（支持 http(s)/相对路径）。

### L3. 头像 URL 若为相对路径，Vite dev 模式下请求 dev server 导致 404

- **位置**：`TopNav.vue` / `ProfileView.vue` 头像 `src` 绑定；`FileController.toVO()` 相对路径返回
- **描述**：本地模式上传返回 `/uploads/xxx` 相对路径时，dev 环境（Vite 5173）会向 dev server 请求而非后端 9080。生产（Nginx 同源 `/uploads/`）与远程加载场景无此问题，且与聊天图片既有行为一致，非本次引入。
- **建议**：如需 dev 环境可用，可在 dev 下对 `/uploads` 配置代理或使用 `UPLOAD_BASE_URL` 绝对地址；不影响本次功能验收。

### L4. `updateOwnProfile` 内两次读取用户（`getUser` + 返回前 `selectById`）

- **位置**：`UserController.updateOwnProfile()` / `UserService.updateOwnProfile()`
- **描述**：事务内先 `getUser` 校验、更新后再 `selectById` 组装响应，多一次查询。可改为 `buildUserInfoVO` 复用内存中最新字段或接受此开销。性能影响可忽略，仅记录。

### L5. 邮箱置空（清空邮箱）时无二次确认

- **位置**：`ProfileView.vue` 邮箱输入框（无 maxlength / 无清空确认）
- **描述**：LOCAL 用户清空邮箱可直接保存（后端置 NULL），属合理功能；但无 `maxlength="128"`，超长输入依赖后端报错提示。可补充前端 maxlength 与邮箱格式即时校验，提升交互。

## 已确认无问题的关键点（供参考）

- `UpdateWrapper.set` 对 null 的处理：MP 3.5.6 `formatParam` 生成 `MPGENVALn` 占位符绑定 null 参数，置空可落库（已由字节码 + 单测 `updateOwnProfileClearsAvatarWithBlankUrlAndKeepsProfileUntouched` 双重确认）。
- 权限拦截：`PUT /v1/users/me/profile` 无 `@RequirePermission`，`PermissionInterceptor` 对无注解方法放行，认证由 Security 过滤器负责。
- 前端契约：`displayName/email` 非 LOCAL 传 `undefined`（JSON 序列化剔除）；`avatarUrl` 传 `''` 表示移除、`null` 表示不修改，与后端语义一致。
- 保存成功后 `fetchUserInfo` 失败不误报（catch 吞掉，顶栏下次刷新同步）——与需求一致。
- `UserServiceTest` 17 个用例全部通过；`vue-tsc --noEmit` 无类型错误。
