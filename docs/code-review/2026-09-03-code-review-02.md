## 中风险（Medium）

### M-1 首次压缩（归档目录为空）时，本次压缩后的交接消息不会注入归档指引

- 位置：
  - `backend-ts/src/harness/core/session-compaction-orchestrator.ts:69`（`applyHistory`，hint 构建点）
    先于 `:85`（`writeArchive`，落盘点）执行；
  - `backend-ts/src/harness/core/session-history-loader.ts:38-40`：hint 构建依赖
    `listArchiveFiles(...).length === 0 → null`（目录非空才注入）。
- 现象：`compact()` 内的执行顺序为 persist → loadValidated → applyHistory（此刻首次压缩的
  `compaction-001.jsonl` 尚未写入，目录为空 → `buildArchiveHint` 返回 null）→ advanced 判定 →
  `writeArchive` 落盘。因此：
  - `request_start` 压缩：本次用户消息的请求中交接消息无归档指引；
  - `mid_loop` 压缩（agent-loop.ts:415）：压缩后 loop 内**后续所有请求**均无指引——长任务场景下
    若本次 loop 跑完且不再触发第二次压缩，Agent 在"最需要回查原始消息"的窗口内始终不知道归档存在，
    可能凭摘要臆造细节。
  - hint 要等到下一次 `buildContext`/第二次压缩时才出现，行为与
    `buildHandoffInstruction` 中"系统会在交接消息后自动附上被压缩原始消息的归档目录说明"
    的承诺在首次压缩后不一致。
- 影响：归档指引功能在首次压缩后的当前执行窗口内失效（下次执行自动恢复）；不丢数据，但削弱
  需求的核心目标（压缩后立即可回查）。
- 修复建议：将 `advanced` 判定提前，`writeArchive` 移到 `applyHistory` 之前（归档落盘后再构建
  交接消息即可命中 hint；`advanced=true` 意味着 CAS 已赢、latest 已加载，两个前置条件在
  `applyHistory` 前均已满足）；或对 `buildArchiveHint` 增加"本次刚落盘"的传参联动。

## 低风险（Low）

### L-1 CAS 赢家在重新 load 前被并发压缩超越时，其归档区间出现永久缺口

- 位置：`backend-ts/src/harness/core/session-compaction-orchestrator.ts:72`（`advanced` 判定）与 `:85`。
- 场景：线程 A `persist` 成功（边界 10→20）后、重新 `loadValidated` 前，线程 C 又完成一次压缩
  （20→30）。A 读到 `latestBoundary=30 ≠ 20` → `advanced=false` → A 跳过 `writeArchive`；
  C 只写自己区间 (20,30]。区间 **(10,20] 永久无归档文件**，但这些消息的 DB 边界已推进，
  此后既不出现在 context 中，也无法从归档找回，且无任何告警。
- 触发条件苛刻（同一 session 并发两个执行流 + persist 与 loadValidated 之间的极小窗口），
  但一旦发生即数据静默缺失。
- 修复建议：归档写入的判据应为"本线程 CAS 获胜"（`persisted === true`）而非
  "本线程仍是最新边界"。`persisted=true` 即代表 (boundary, candidate] 区间归属本线程，
  无论之后是否被超越都应写归档；被超越只应影响 token 重算 / 事件记录等逻辑，不应放弃归档。

## 提示级（Info）

### I-1 `writeArchive` 对空消息数组缺少防御，会写出仅含一个换行的 JSONL

- 位置：`backend-ts/src/harness/core/compaction-archive.service.ts:44`（`messages.map(...).join('\n') + '\n'`）。
- 说明：`messages=[]` 时 `body === '\n'`，产出的文件用逐行 `JSON.parse` 回读会报错。
  当前唯一调用点由 `isCompletePhysicalPrefix` 保证区间非空，故实际不可达；但该方法为公共 API，
  建议加 `if (messages.length === 0) return;` 防御。

### I-2 `compactCount >= 1000` 后文件名字符串排序不再等价于时间序

- 位置：`compaction-archive.service.ts` 的 `String(seq).padStart(3, '0')`；hint 文案声明
  "升序即时间顺序"。
- 说明：`compaction-1000.jsonl` 字符串排序位于 `compaction-999.jsonl` 之前（'1' < '9'）。
  理论场景（单会话 1000 次压缩），可忽略；如需严谨可在排序处按数值比较或改用 4 位以上补零。

### I-3 hint 文案中"原图路径见 metadata 内 attachments 的 path 字段"未说明路径基准

- 位置：`compaction-archive.service.ts` `buildArchiveHint`。
- 说明：附件 `path` 是工具结果记录的相对路径（如 `p.png`），Agent 回读原图需结合会话 runtime
  incoming 目录或工作区自行解析，文案未给出基准目录，可能造成 Agent 按相对路径找不到原图。
  建议文案补充一句路径基准说明（如相对于会话 runtime incoming 目录 / 当前工作区）。

### I-4 `writeArchive` 失败（如 rename 前进程崩溃）会残留 `.tmp` 文件

- 位置：`compaction-archive.service.ts` writeArchive 的 try/catch。
- 说明：`.tmp` 残留不影响 `listArchiveFiles`（只过滤 `.jsonl`），同序号下次写入会覆盖同名 tmp，
  属可接受取舍；仅作记录，无需处理。
