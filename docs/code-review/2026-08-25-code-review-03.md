## Bug 1（中）：前端 `handleDelete` 缺少 try/catch 错误处理

**文件**：`admin/src/views/system-commands/SystemCommandListView.vue`

**问题描述**：`handleDelete` 函数没有 try/catch 包裹，当删除接口调用失败时（网络异常、服务端报错等），Promise rejection 未被处理。尽管 axios 拦截器会弹出错误提示，但函数后续逻辑（`ElMessage.success` 和 `loadData`）不会执行，而 `el-popconfirm` 已经关闭，导致：
- 用户看到错误提示但列表未刷新，残留已失效的脏数据
- 控制台出现 unhandled promise rejection 警告

**问题代码**：

```typescript
// admin/src/views/system-commands/SystemCommandListView.vue — handleDelete
async function handleDelete(row: SystemCommandVO) {
  await api.delete(`/admin/system-commands/${row.id}`)
  ElMessage.success('删除成功')
  await loadData()
}
```

**修复建议**：与其他管理页面保持一致，使用 try/catch 包裹（参考 `AgentListView`、`SkillListView`、`ModelListView`、`scheduled-tasks/index.vue` 等）：

```typescript
async function handleDelete(row: SystemCommandVO) {
  try {
    await api.delete(`/admin/system-commands/${row.id}`)
    ElMessage.success('删除成功')
    await loadData()
  } catch {
    // interceptor handles toast
  }
}
```

## Bug 2（低）：前端 `loadData` 缺少 catch 块

**文件**：`admin/src/views/system-commands/SystemCommandListView.vue`

**问题描述**：`loadData` 函数使用了 `try/finally` 但没有 `catch` 块。当 API 调用失败时，错误会从 `onActivated` 生命周期钩子向上冒泡，产生 unhandled promise rejection。虽然 `finally` 正确地重置了 `loading` 状态，但未被捕获的异常可能导致控制台警告。

对比同项目的 `SystemSettingsView.vue`，其数据加载函数包含完整的 catch 块：

```typescript
// SystemSettingsView.vue — 有 catch 块
async function fetchAgents() {
  try {
    const { data } = await api.get('/agents')
    agents.value = data || []
  } catch {
    agents.value = []
  }
}
```

**问题代码**：

```typescript
// SystemCommandListView.vue — 缺少 catch
async function loadData() {
  loading.value = true
  try {
    const { data } = await api.get('/admin/system-commands')
    commands.value = data || []
  } finally {
    loading.value = false
  }
}
```

**修复建议**：添加 catch 块，保持与其他视图一致的错误处理模式：

```typescript
async function loadData() {
  loading.value = true
  try {
    const { data } = await api.get('/admin/system-commands')
    commands.value = data || []
  } catch {
    // interceptor handles toast
  } finally {
    loading.value = false
  }
}
```

## Bug 3（低）：`SYSTEM_USER_ID` 常量在路由文件中重复定义

**文件**：`backend-ts/src/command/admin-system-command.routes.ts`

**问题描述**：新路由文件第 4 行定义了 `const SYSTEM_USER_ID = 0;`，而 `command.service.ts` 中已导出同名常量 `export const SYSTEM_USER_ID = 0;`。两者独立定义，若未来系统用户 ID 值发生变更，存在遗漏同步的风险。

**问题代码**：

```typescript
// backend-ts/src/command/admin-system-command.routes.ts 第 4 行
const SYSTEM_USER_ID = 0;
```

**修复建议**：复用已导出的常量：

```typescript
import { SYSTEM_USER_ID } from './command.service.js';
```
