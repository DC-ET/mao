## 高严重度

### H1. 移除头像（avatarUrl 置空）不会真正写入数据库 —— 核心功能失效

**涉及文件与位置**：
- `backend/src/main/java/cn/etarch/mao/user/service/UserService.java`：`updateOwnProfile()` 中 `user.setAvatarUrl(url)`（约 148 行，`url` 为空时置 null）与 `user.setEmail(mail.isEmpty() ? null : mail)`（约 171 行）
- 前端链路：`desktop/src/views/settings/ProfileView.vue` `save()` 中「移除头像」分支传 `avatarUrl: ''`

**问题描述**：
前端「移除头像」时提交 `avatarUrl: ''`，后端将其归一化为 `null` 并 `user.setAvatarUrl(null)`，随后 `userMapper.updateById(user)` 执行更新。但本项目 MyBatis-Plus 3.5.6 未配置任何字段策略，默认 `updateStrategy = FieldStrategy.NOT_NULL`（已从 `mybatis-plus-core-3.5.6` 源码 `GlobalConfig.DbConfig` 确认，`application.yml` 亦未覆盖，`User` 实体无 `@TableField(updateStrategy=...)`）。因此 **null 字段不会进入 UPDATE 语句的 SET 子句**，`avatar_url` 列保持旧值。

实际效果：用户点击「移除头像」→ 前端提示「保存成功」→ 刷新后头像依旧显示。同根因：LOCAL 用户清空邮箱（`email: ''` → 置 null）同样不生效，数据库仍保留旧邮箱。

**佐证**：新增单测 `updateOwnProfileClearsAvatarWithBlankUrlAndKeepsProfileUntouched` 只断言了内存对象 `local.getAvatarUrl()` 为 null 及 `updateById` 被调用，因 mock 了 mapper，**无法暴露真实 SQL 层行为**，属于假阳性覆盖。

**建议修复方向**：
- 方案 A（推荐）：对需要置空的字段改用 `LambdaUpdateWrapper` / `UpdateWrapper` 显式 `set(...)` 更新，绕过 NOT_NULL 策略；
- 方案 B：给 `User.avatarUrl`、`User.email` 字段加 `@TableField(updateStrategy = FieldStrategy.IGNORED)`（注意会改变这两个字段所有 updateById 路径的行为，需评估 `FeishuAuthService`、`UserService.updateUser` 等调用方）；
- 补充集成级测试（如 `@SpringBootTest` + H2/真实库）覆盖「移除头像后库内 avatar_url 为空」这一场景。

## 中严重度

### M1. LDAP 用户经飞书登录后被误判为 FEISHU，authSource 语义漂移

**涉及文件与位置**：
- `backend/src/main/java/cn/etarch/mao/user/service/UserService.java`：`resolveAuthSource()`
- `backend/src/main/java/cn/etarch/mao/auth/service/FeishuAuthService.java`：`findOrCreateUser()`（约 288-296 行，`findUserByEmail` 匹配后写 `feishuUserId`）

**问题描述**：
`resolveAuthSource` 判定顺序为：有 `passwordHash` → LOCAL；否则有 `feishuUserId` → FEISHU；再否则 → LDAP。而 `findOrCreateUser` 会先按 `feishu_user_id`、再按 `email` 匹配已有用户：LDAP 用户（`passwordHash` 为空）若邮箱与飞书账号一致，登录时会被写入 `feishuUserId`，此后该用户 `authSource` 由 LDAP 漂移为 FEISHU，前端「登录方式」标签展示从「LDAP 目录账号」变为「飞书」。若用户此后不再用飞书登录，判定结果仍保持 FEISHU。

影响面：展示语义错误；`updateOwnProfile` 的 LOCAL 权限判断（两者均为非 LOCAL）不受影响，功能不致出错，但身份归属信息失真，可能误导后续基于 authSource 的权限/审计逻辑。

**建议修复方向**：
- 优先基于 `auth_type` 列判定（建表语句中存在该列但实体未映射），或调整判定优先级为「LOCAL → LDAP → FEISHU」并在飞书关联时区分「飞书登录创建」与「LDAP 用户关联飞书」两类场景；
- 至少应在技术方案中明确该混合身份场景的预期行为。

### M2. 邮箱唯一性校验存在并发竞态，且无数据库唯一索引兜底

**涉及文件与位置**：
- `backend/src/main/java/cn/etarch/mao/user/service/UserService.java`：`updateOwnProfile()` 中 `selectCount` 校验（约 163-168 行）
- `backend/src/main/resources/db/migration/V001__init_schema.sql`：`email` 列（VARCHAR(128)，无唯一索引）

**问题描述**：
「先 selectCount 查重、再 updateById 写入」非原子操作。两个请求并发提交相同邮箱时，可能同时通过校验并写入重复邮箱，且 `email` 列无唯一索引，数据库层无法兜底，最终产生重复数据。当前单用户场景触发概率低，但属正确性隐患。

**建议修复方向**：
- 为 `user.email` 增加唯一索引（注意 MySQL 唯一索引允许多个 NULL，不影响无邮箱用户）；或
- 将查重与更新放入同一事务并在写入后捕获唯一键冲突异常转译为业务错误；或在应用层加分布式锁/乐观锁。

## 低严重度

### L1. `resolveAuthSource` 为静态方法却通过实例调用

**涉及文件与位置**：`backend/src/main/java/cn/etarch/mao/user/controller/UserController.java`（`buildUserInfoVO` 中 `userService.resolveAuthSource(user)`）及 `AuthService`/`LdapAuthService`/`FeishuAuthService` 中 `UserService.resolveAuthSource(user)` 静态调用（后者为类名调用，无问题）

**问题描述**：`UserController` 通过实例引用调用静态方法，Java 虽允许但易误导阅读者以为依赖实例状态，且与其余调用方（类名调用）风格不一致。纯代码质量，无功能影响。

**建议修复方向**：统一改为 `UserService.resolveAuthSource(user)` 类名调用。

### L2. 头像 URL 校验允许协议相对地址（`//host/path`）

**涉及文件与位置**：`backend/src/main/java/cn/etarch/mao/user/service/UserService.java`：`AVATAR_URL_PATTERN`（`^(?=.{1,512}$)(https?://|/)[^\s]+$`）

**问题描述**：`/` 开头分支同样匹配 `//example.com/x.png` 这类协议相对 URL，用户可提交非本域资源。头像用于 `<img src>` 渲染，无脚本注入风险，但允许外部域名资源（可能带来隐私/追踪问题，且移除校验意图之外的数据进入）。

**建议修复方向**：如需限制，可对 `/` 开头的相对路径限定「不以 `//` 开头」，或在正则中增加排除。

### L3. 开发环境下相对路径头像（`/uploads/...`）无法显示

**涉及文件与位置**：`desktop/src/views/settings/ProfileView.vue`、`desktop/src/components/common/TopNav.vue`（`<el-avatar :src="...">`）；`backend/.../FileController.toVO()`（`baseUrl` 未配置时返回 `/uploads/...`）

**问题描述**：local 存储模式下上传返回 `/uploads/xxx` 相对路径，生产环境由 Nginx 虚拟路径映射可访问，但桌面端 Vite dev（localhost:5173）下 `<img src="/uploads/xxx">` 会 404，头像不可见。属环境配置问题，非逻辑缺陷。

**建议修复方向**：dev 环境配置 `VITE_API_BASE_URL` 对应域名的静态资源代理，或上传返回绝对 URL。

### L4. 空请求体（全部字段为 null）仍触发一次无意义更新

**涉及文件与位置**：`backend/src/main/java/cn/etarch/mao/user/service/UserService.java`：`updateOwnProfile()`

**问题描述**：客户端提交 `{}`（三个字段均 null）时，方法走完所有分支后仍执行 `updateById`，因 `updatedAt` 为 `FieldFill.INSERT_UPDATE` 会被刷新，产生一次无业务意义的写操作。影响极小。

**建议修复方向**：三个入参均为 null 时直接 return（可加 `hasChange` 标记）。

### L5. 前端 form 初始值仅在 setup 时读取一次，与 authStore.user 不实时同步

**涉及文件与位置**：`desktop/src/views/settings/ProfileView.vue`（`form` reactive 初始化）

**问题描述**：`form.displayName/email` 在 setup 时从 `authStore.user` 拷贝一次。路由守卫保证进入页面时 user 已加载，正常路径无问题；但若页面停留期间用户信息被其它入口更新（如顶栏重新登录、多标签场景），表单值不回填。影响面很小。

**建议修复方向**：如需严谨，可 `watch(() => authStore.user, ...)` 在页面可见时同步表单（注意避免覆盖用户正在编辑的内容）。
