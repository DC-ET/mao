## 二、发现的问题

### 【中】1. 冷启动探测误判：首次启动页面未加载完成时可能被误判"无响应"而触发多余 reload

**位置**：`MainActivity.java` — `onStart()` / `scheduleWebViewRecoveryProbe()` / `probeWebViewAlive()`

**问题**：
`onStart()` 不仅在回前台时触发，**冷启动（onCreate → onStart）时同样触发**，此时探测被排定在启动后 2s。而该 App 远程加载的 SPA（Vue + Monaco，资源量大）在弱网下可能尚未完成首次页面提交，低端机上初始 bundle 求值也可能长时间占用渲染主线程。此时：

- `evaluateJavascript("1;")` 在页面未提交前会被 WebView 排队、回调延迟投递；
- 渲染主线程繁忙时回调同样无法在 3s 内投递；

于是 3s 超时误判"无响应" → `webView.reload()` **取消进行中的首次加载并重新开始**，弱网/低端机冷启动会出现一次多余整页刷新，首屏时间可能翻倍，且恰好违背"仅回前台兜底"的设计意图。

**佐证不对称**：JS 侧 `useForegroundRecovery` 专门设计了 `COLD_START_GUARD_MS = 3000` 冷启动防护（注释明确说明避免建连窗口误判），原生侧没有对应防护。

**建议**：
- 探测前确认页面已完成过至少一次加载：监听首次 `onPageFinished`（或 WebViewClient 的 `onPageCommitVisible`）置标志位，未加载完成不探测；或探测时校验 `webView.getProgress() == 100`；
- 或增加冷启动防护：进程启动后的第一次探测跳过/延长等待，与 JS 侧 3s 防护对齐。

---

### 【中低】2. 超时回调与 reload 缺少 Activity 销毁 / WebView 有效性二次校验

**位置**：`MainActivity.java` — `probeWebViewAlive()` 末尾的 `handler.postDelayed(...)` 与 `reloadWebView()`

**问题**：
`probeWebViewAlive()` 入口只校验了 `isFinishing()`，但 3s 后执行的超时 Runnable **没有**再校验 `isFinishing() / isDestroyed() / webView != null`。若用户在探测与超时之间退出（返回键 finish / 系统销毁），超时回调仍会执行 `webView.reload()`：

- 对已销毁的 WebView 调用 `reload()` 在部分版本会抛 `IllegalStateException` 或行为未定义；
- Handler 上排定的延迟任务未在 `onDestroy()` 清理，Runnable 持有 Activity 与 WebView 引用，销毁后回调仍会执行（Activity 短暂泄漏 + 越界操作）。

**建议**：
- 超时 Runnable 内补充 `if (isFinishing() || isDestroyed() || webView == null) return;`，`reloadWebView()` 内同样校验；
- `onDestroy()` 中调用 `handler.removeCallbacksAndMessages(null)`。

---

### 【低】3. 探测不感知前后台状态：后台期间超时也会 reload；多次 onStart 探测存在重叠竞态

**位置**：`MainActivity.java` — `onStart()` / `probeWebViewAlive()`（原 `onStop` 已删除）

**问题**：
- 用户回前台不足 5s（2s 延迟 + 3s 超时）又切回后台时，超时回调仍会在**后台**触发 `webView.reload()`——后台刷新被系统节流，属浪费，且与"回前台才兜底"语义不符；
- 快速前后台切换会在 2s 窗口内叠加多个探测：先排定的探测 A 的超时点与后排定的探测 B 的执行点可能落在同一主线程队列相近位置，若 A 的超时先执行（此时 B 尚未确认响应），会误 reload 一次（受 10s 防抖限制，至多一次，影响有限）。

**建议**：
- 恢复 `onStop()` 记录后台状态（或记录最近一次 `onStart` 时间戳），超时回调内校验"仍处于前台"才 reload；
- 排定新探测前取消尚未执行的旧探测（如记录 Runnable 引用并 `handler.removeCallbacks`）。

## 三、确认无误/可选优化

### 4. reload 后 FORCE_TOP_NAV_JS 重新注入：**必要且正确** ✅
`reload()` 后新页面不再经过 `onCreate` 的 `configureWebView()` 注入，而 FORCE_TOP_NAV_JS 是 DOM 级操作（style 元素插到旧文档），随旧文档一起丢失，重新注入是必须的。时序 `post / 300ms / 1000ms` 覆盖首帧与 Vue mount 之后，与 onCreate 注入模式一致，逻辑正确。首次 `post` 注入时新文档可能未提交，`evaluateJavascript` 会排队或作用于即将被替换的旧文档，均无副作用。

可选优化：与 onCreate 的 4 次注入（多一次 2500ms）保持一致，覆盖极慢网络下更晚的 mount 时序；影响很小，可不改。

### 5. 双端 reload 防抖独立但不冲突（跨层说明）✅
原生侧与 JS 侧（`useForegroundRecovery`）各自有独立的 10s 防抖。原生 reload 仅在 JS 无响应（evaluateJavascript 无回调）时触发，JS reload 仅在 JS 存活时触发，主路径互斥；仅"JS 存活但响应慢（>3s）"的边缘场景可能双触发，可接受，无需处理。

---

## 四、建议优先修复项

1. 【中】冷启动探测误判 → 增加"页面已加载完成"前置条件或冷启动防护（与 JS 侧 3s 防护对齐）；
2. 【中低】超时回调/ reload 增加 `isFinishing() || isDestroyed() || webView == null` 校验，`onDestroy` 清理 Handler 任务；
3. 【低】后台期间不 reload（恢复 onStop 状态感知），排定新探测前取消旧探测。

> 说明：以上均为建议，未修改任何代码。
