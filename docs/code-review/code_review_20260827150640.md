## 二、发现的问题

### P2-1（低危·建议加固）：`feishuSendTargetOf` 对无前缀的历史 p2p 键静默回退为 chat_id 发送

- 位置：`backend-ts/src/feishu/media-sender.ts:17-22`
- 描述：存量数据（本版之前建的私聊行，chat_id 形如 `p2p:on_xxx`）在升级后虽不会再被入站键匹配命中，但仍可通过 `findConversationBySessionId` 触达——例如旧会话继续被桌面端打开使用、且用户在其中触发 `feishu_send_image/send_file` 时，`receive_id` 会拿到整个字符串 `'p2p:on_xxx'` 并以 `receive_id_type='chat_id'` 调飞书接口，必然报错，且错误文案是群聊语气的"chat_id 发送失败"，把"身份格式升级残留"伪装成"发送目标非法"，排查易跑偏。
- 说明：项目政策明确初版不考虑存量兼容，且正常入站路径永远新建带前缀会话并落到新工作区，故不定级为中高；但解析器层面"以 `p2p:` 开头却无类型前缀"属已知不可能出现的合法形态，建议对该情形显式抛出带上下文的错误而非静默落入 chat_id 分支（一两行的加固即可让该场景自证）。

### 提示级观察（不计缺陷）

1. **群成员登记执行频次变化**：`authorizeSender` 现对每条群消息都执行 `INSERT ... ON DUPLICATE KEY UPDATE`（旧代码先 SELECT、命中则跳过写）。功能等价（upsert 幂等），代价是每条群消息一次写放大，量级可忽略。注意一个理论边缘：若某事件缺 `senderId` 而 unionId 命中绑定，NOT NULL 列 `open_id` 将插入 NULL 报错——旧代码仅在首次登记时报错、此后因已登记而跳过，新代码每次都会报错；考虑 `im.message.receive_v1` 实际恒携带 open_id，触发概率≈0，仅记录行为差异。
2. **部署后私聊会话形态切换**：同一飞书用户的首条消息会新建 `p2p:union:*` 映射与新 session（由此获得工作区），旧格式映射/会话成为孤儿（桌面端可能出现重复的历史会话项）。符合"重构不考虑存量兼容"政策，但建议随发布向运维口头知会一次。
3. **CHANGELOG 未同步**：本次属于用户可感知修复（私聊文件可正常接收、富文本/语音等消息不再产生空内容、媒体发送错误码更真实），按仓库规约应在根 `CHANGELOG.md` 顶部补写条目后再打包/发版。
4. （非本次引入，顺带记录）`monitor.service.ts:93-95` 注释仍写着自研长连接 endpoint/退避措辞，与其 SDK 化实现的现状略不符；`FeishuBotHandleFactory` 类型经此重构后已无生产调用方，可在下次清理窗口一并处理。
