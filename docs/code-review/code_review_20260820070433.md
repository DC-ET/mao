## 问题列表

### [中] 1. `/v1/files/:id/download`（及 `/preview`、`DELETE /v1/files/:id`）无属主校验，本轮新增的 incoming 可用下载 URL 使跨用户访问成为现实风险

- 位置：`backend-ts/src/file/file.routes.ts`（`GET /v1/files/:id/download` / `:id/preview` / `DELETE /v1/files/:id`，约 214-240 行）
- 问题：三个端点只调用 `requireUserId`，不校验 `file.uploaderId === userId`（也不校验会话归属）。此前 `toVO().url` 对 incoming 文件指向不存在的 `/uploads/...`，风险不可达；本轮改为 `/v1/files/:id/download` 后，任何登录用户只要枚举/猜到自增 file id，即可下载**其他用户上传的 incoming 文件**（可能是敏感文档），也可逻辑删除他人文件记录并物理删除磁盘文件。预存在问题被新功能放大。
- 修复建议：在 download/preview/delete 三个端点按 `getFile` 结果比对 `file.uploaderId === userId`（或经 sessionId 校验会话属主），不匹配返回 403/404。

### [中] 2. 前端在 LOCAL 模式仍允许选择并上传文件，与后端新增的 LOCAL 拒绝逻辑不匹配

- 位置：后端 `backend-ts/src/file/file.routes.ts`（upload-incoming，约 83-85 行 `executionMode === 'LOCAL'` 拒绝）；前端 `desktop/src/components/chat/ChatInput.vue`（`handleFileSelect`/`handleDropFiles`/paste 均无条件调用 `uploadFileToRuntime`，约 880-895 行、920-940 行）
- 问题：设计文档 N1 明确「不在 LOCAL 模式启用文件上传，LOCAL 维持现状」，后端按此拒绝合理；但前端三个入口**未做执行模式判断**，LOCAL 模式下用户仍能选择文件，随后统一得到误导性的「文件 xxx 上传失败」（`uploadChatFile` 吞掉后端真实错误信息 `本地模式不支持服务端文件上传`）。表现为功能入口可见但必然失败，属前后端契约不一致。
- 修复建议：前端在 `executionMode === 'LOCAL'` 时禁用上传入口（`add-btn` 置灰/隐藏），或在调用前先检查模式并给出明确提示「本地模式不支持文件上传，请直接使用 @ 引用工作区文件」；同时 `uploadChatFile` 可将后端 message 透传，避免吞掉真实原因。

### [低] 3. 上传完成时若输入区处于 disabled，文件引用节点被静默丢弃，发送时非图片文件从消息中消失

- 位置：`desktop/src/components/chat/ChatInput.vue`（`uploadFileToRuntime` 成功分支约 924-929 行、`insertFileReferenceAt` 约 944-955 行、`handleSend` 约 961-970 行）
- 问题：`uploadFileToRuntime` 成功上传后调用 `insertFileReferenceAt`，该函数在 `editor.value` 为空或 `props.disabled` 时直接 return——**不插入节点，也不移除 pending 条目、不提示**。典型场景：Agent 运行中（输入区 disabled）用户上传文件，上传完成后引用节点从未插入，但条目仍留在 pendingFiles 且 `uploadingFiles[pos] = false`；用户随后点发送时 `handleSend` 只取出 `image/` 类型文件，该非图片文件**既不在消息文本中也不随发送携带**，静默丢失，且 runtime 留下孤儿文件（直到会话删除才回收）。`handleSend` 的 `uploadingFiles.some(Boolean)` 只拦截「上传中」，拦不住这个「上传完但插入失败」的窗口。
- 修复建议：插入失败时（disabled/编辑器不可用）将条目标记为失败并提示，或延后到输入区恢复可用时再补插；更稳妥的做法是「引用插入」与「发送」绑定为原子流程，插入失败则不发送并提示。

### [低] 4. sanitizeBaseName 会把合法文件名中的字面量 `%2e` 误替换为 `.`

- 位置：`backend-ts/src/file/file.service.ts`（`sanitizeBaseName`，约 267-277 行）
- 问题：`.replace(/%2e/gi, '.')` 无差别替换。文件名本身含字面量 `%2e` 的场景（如 `100%2e5.xlsx`、`v1%2e0.pdf`）会被改写成 `100.5.xlsx`、`v1.0.pdf`，展示名/下载名与用户原文件名不符。安全上无影响（storedName 只取 uuid+白名单扩展名），属展示名意外改写。中文、emoji 不受影响（仅剥离 `\u0000-\u001f`、`\u007f` 控制字符），本轮核心目标「不误伤中文/emoji」达成。
- 修复建议：仅当 `%2e` 构成穿越序列（如 `%2e%2e`）时才替换，或对非 ASCII 安全字符集外的字符统一替换为 `_`，避免改写合法文件名。

### [低] 5. 图片扩展名补全与内容 mime 不一致（非安全项）

- 位置：`backend-ts/src/file/file.service.ts`（`buildFileEntity`，约 151-160 行）
- 问题：内容检测优先。JPEG 字节但用户命名为 `photo.png`/`photo.jpeg` 时，`mimeType = image/jpeg`，`isImagePath(baseName)` 为 true 故不补全，`safeExtension` 取原扩展名 → storedName 为 `uuid.png`/`uuid.jpeg` 而 mime 是 image/jpeg，下载时按 attachment 提供、Content-Type 用 mimeType，扩展名与内容不一致（部分客户端识别异常）。不影响路径安全。
- 修复建议：可接受（保持用户原名）；如需严格一致，可让 storedName 扩展名跟随 mime 检测结果。

### [低] 6. 单测覆盖缺口：listFiles 的 incoming 过滤与 URL 编码穿越无用例

- 位置：`backend-ts/src/file/file.service.spec.ts`
- 问题：新增测试（`uploadIncomingFileSavesToIncomingDirAndRejectsOversized`、`uploadIncomingFileStripsPathTraversalFromFilename`、`uploadInfersImageMimeAndExtensionFromMagicBytes`）断言正确、与实现一致；但 `listFiles` 过滤 incoming 的逻辑（`filePath.includes('/incoming/')`）没有用例，`..%2F..%2Fevil.txt` / `%2e%2e%2f` 编码穿越变体也未覆盖（实现经核查能正确处理，仅为防回归的覆盖缺口）。
- 修复建议：补充两条用例：`listFiles` 传入含 incoming filePath 的记录断言被过滤；上传 `..%2Fevil.txt` 断言 originalName 不含可拼接路径片段、storedName 仅 uuid+安全扩展名。

### [低] 7. runtimeSessionCleanup 与在跑 Agent/Shell 的竞态残留

- 位置：`backend-ts/src/create-app.ts`（`runtimeSessionCleanup`，约 789-800 行）；`backend-ts/src/session/session.routes.ts`（`DELETE /v1/sessions/:id`，约 234-239 行）
- 问题：本轮改为删除整个 `runtime/{userId}/{sessionId}`（含 `shellOutput`、`skills`、`git-askpass.sh`），方向正确；路径由数值 ID 经 `resolve` 拼接，无穿越；`rmSync` recursive 不跟随 symlink（Node ≥14.14 行为，删的是链接本身），无符号链接逃逸。但删除路由**未先停止该会话的 Agent/Shell**：若删除发生在会话运行中，`rmSync` 会与正在向 `shellOutput` 写 stdout 的 shell 进程竞态（写 ENOENT/半截输出），Agent 循环也可能在目录删除后重建目录导致清理不彻底。
- 修复建议：删除前先调用会话级资源释放（如 `releaseSessionExecutionResources` / `closeByConversation`）停掉 shell 再清理；或至少保证路由层在会话非运行态才允许删除。

### [低] 8. 在途上传不随 clearInput / 组件卸载取消，完成后成为 runtime 孤儿文件

- 位置：`desktop/src/components/chat/ChatInput.vue`（`clearInput` 约 1030-1037 行、`onBeforeUnmount` 约 1040-1046 行）
- 问题：`clearInput` 与 `onBeforeUnmount` 只清空三数组，不中止在途 `uploadChatFile` 请求。请求完成后 `findSelf()` 返回 -1 直接 return——不会崩溃、不会误插节点（行为正确），但文件已上传到 runtime incoming，成为孤儿（不占列表、无引用，直到会话删除才回收）。反复「上传→清空/切换会话」会累积磁盘占用。上一轮[低]6 的同类问题未完全消除。
- 修复建议：组件卸载/清空时对在途请求执行 abort（或记录「已取消」标志，完成后调用删除文件接口清理 runtime 文件）。

## 总结

- 本轮 6 个修复点中，**第 1、2、4、5、6 点修复正确**：try/catch 作用域已收敛、整目录清理无路径/symlink 风险、文件名清洗不误伤中文/emoji 且阻断各类穿越、测试断言与实现一致、前端 indexOf 定位与三数组操作一致。
- 需要优先处理：
  1. **下载/删除端点缺属主校验**（[中]1）——本轮让 incoming 文件获得可用下载 URL，跨用户读取他人上传文件从「不可达」变为「可枚举 id 即达」；
  2. **前端 LOCAL 模式上传入口未禁用**（[中]2）——与后端新增拒绝逻辑及设计文档 N1 不一致，用户必然看到失败提示；
  3. 上传完成时输入区 disabled 导致引用静默丢失（[低]3）、在途上传不取消（[低]8）属同类「上传生命周期与编辑器状态不同步」问题，建议一并处理。
