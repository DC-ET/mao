## 阻塞项

### B1. 服务端把 `approvalRegistry.has` 解构后调用，丢失 `this` → 所有 `tool_approval` 帧抛异常被吞掉，多端审批（以及单机审批）完全失效

**位置**

- 触发点：`backend-ts/src/session/ws/streaming-ws-handler.ts:1174-1179`

  ```ts
  const hasFn = this.deps.approvalRegistry.has;   // 1174：方法被摘出来，this 丢失
  if (hasFn && !hasFn(sessionId, requestId)) {    // 1175：以无接收者方式调用
    this.resendRecentResolution(socket, sessionId, requestId);
    return;
  }
  ```
- 根因：`backend-ts/src/harness/approval/approval-registry.ts:186-189` 的 `has` 是**原型方法**，实现体依赖 `this.pending`：

  ```ts
  has(sessionId, requestId): boolean {
    if (sessionId == null || requestId == null) return false;
    return this.pending.get(sessionId)?.has(requestId) ?? false;   // this === undefined
  }
  ```
- 生产装配确认不是代理/包装：`backend-ts/src/app-ws-handler.ts:101` 直接把 `create-app.ts:715` new 出来的 `ApprovalRegistry` 实例塞进 `deps.approvalRegistry`，没有 bind / 箭头函数包装。

**现象**

任何客户端（桌面 / 手机浏览器 / CLI）发出 `tool_approval` 帧，`handleToolApproval` 在第一行 `hasFn(...)` 就抛
`TypeError: Cannot read properties of undefined (reading 'pending')`。
异常被 `processTextMessage` 的兜底 `try/catch` 吞掉，只打一条日志：

```
WS handler failed for type=tool_approval userId=7 TypeError: Cannot read properties of undefined (reading 'pending')
    at has (.../approval-registry.ts:188:17)
    at StreamingWsHandler.handleToolApproval (.../streaming-ws-handler.ts:1175:19)
```

即：**这一票完全没有被处理**——没有认领（`pending` 不摘除）、没有广播 `tool_approval_resolved`、没有相位恢复、没有 `alwaysAllow` 建规则、没有 `resendRecentResolution` 兜底。

**触发路径（任一条即可复现）**

1. 手机浏览器点「执行 / 拒绝 / 总是允许」→ `tool_approval` → 服务端抛错；
2. 桌面点本机 IPC 卡（新客户端已改成「只投票、等回声」）→ `tool_approval` → 服务端抛错；
3. CLI 模态按键 / readline 应答 → `tool_approval` → 服务端抛错；
4. 任何策略自动放行 / 拒绝发出的「已处理通知」帧（不带 `approved`）→ 同样抛错。

**实际验证（临时用例，已删除）**

`backend-ts/src/session/ws/__review_tmp.spec.ts`：用**真实的** `ApprovalRegistry` + 真实 `StreamingWsHandler`（其余 deps 用最小桩），先 `register(11,'req-real-1',null,ctx)`，再走真实分发：

```ts
await approvalRegistry.register(11, 'req-real-1', null, ctx);
expect(approvalRegistry.has(11, 'req-real-1')).toBe(true);
await handler.handleTextMessage(ws, JSON.stringify({
  type: 'tool_approval', sessionId: 11, requestId: 'req-real-1', approved: true,
}));
const resolved = wsRegistry.send.mock.calls.map(c => c[1]).filter(e => e.type === 'tool_approval_resolved');
expect(resolved).toHaveLength(1);          // ← 实际收到 0，用例失败
expect(approvalRegistry.has(11, 'req-real-1')).toBe(false);
```

运行结果（节选）：

```
stderr | ... > 真实注册表：投票会被认领并广播 tool_approval_resolved
WS handler failed for type=tool_approval userId=7 TypeError: Cannot read properties of undefined (reading 'pending')
 ❯ src/session/ws/__review_tmp.spec.ts (2 tests | 1 failed)
   × 真实注册表：投票会被认领并广播 tool_approval_resolved
     → expected [] to have a length of 1 but got +0
   ✓ 真实注册表在 handler 外直接解构调用 has 会抛错（复现未绑定 this）
```

同一文件里补一条最小复现：`const unbound = approvalRegistry.has; expect(() => unbound(11,'x')).toThrow();` —— 通过。

**为什么现有单测没挡住**：`streaming-ws-handler.spec.ts:80`（与 `:2213`）把 deps 桩成
`has: vi.fn(() => true)`（闭包，不依赖 `this`），所以走「桩」的用例全绿；把 `has` 换成真实实例立刻暴雷。
把 `has` bind 回实例后，我又用同一套真实注册表跑了 5 条链路（认领+`resolved` 广播+相位恢复+抑制升级、旧 CLI 通知帧 → `resolved(null)` 不建规则、拒绝先认领后「总是允许」不建规则且只对发起连接补发回声、总是允许获胜建规则、订阅重放带 `approvalHint`），**全部通过**——说明后端其余逻辑正确，缺陷就集中在这一次未绑定调用上。

**影响（严重）**

- 新功能整体不可用：卡片留在各端、远端决策到不了执行端、「总是允许」规则永远不落库。
- **回归到单机审批**：新客户端已改为「点击只投票，放行只认 `resolved` 回声」（`useChat.ts:86-125`、`executor.ts:275-303`），服务端吞掉投票后执行端拿不到回声——
  - 桌面：主进程 `requestToolApproval` 的 Promise 一直挂着，**本机点了「执行」也不跑**，直到 900s 超时（`LocalToolExecutor` 的 `finally → unregister` 才补发 `resolved(null)`）然后工具失败；
  - CLI：模态停在「已提交，等待服务端确认…」且 `submittedFlag` 忽略后续按键（`modal-controller.ts:245-251`），同样卡到 900s；
  - 会话相位停在 `WAITING_APPROVAL`，`alwaysAllow`/`--approve-rule` 之外的审批全部作废。

**修复建议**

- `handleToolApproval` 里改为带接收者调用，例如
  `if (this.deps.approvalRegistry.has && !this.deps.approvalRegistry.has(sessionId, requestId)) { ... }`，
  或 `const has = this.deps.approvalRegistry.has?.bind(this.deps.approvalRegistry)`；也可把 `ApprovalRegistry.has` 改成箭头函数属性（同时 `takeHint/countForSession` 等也建议一并评估，避免后续再被解构）。
- 补回归测试：`streaming-ws-handler.spec.ts` 里不要只桩 `has: vi.fn()`，至少加一条「真实 `ApprovalRegistry` 实例 + 真实 handler」的用例（建议按仓库既有惯例落成 `*.bugcheck.spec.ts`）。

## 重要项

### B2. CLI 缺「重连后立即补发投票」，回声丢失后审批模态可永久停在「已提交」

**位置**

- `agent-cli/src/local/executor.ts:275-303`（`raceVoteAndEcho`）：投票后只写 `approvalEchoWaiters`，等待没有本地超时；
- `agent-cli/src/local/executor.ts:356-377`（`scheduleApprovalResend`）：5s 一次、最多 2 次，之后不再重发；
- `agent-cli/src/local/executor.ts:107-109`（`setApprovalRelaySupported`）：`connected` 帧只用来存布尔位，**没有借这个时机补发**；
- `agent-cli/src/session/session-runner.ts:361-365`：`connected` 只回调能力位即 `return`。
- 对照实现（桌面端有）：`desktop/src/composables/useStreamWS.ts:412-413` 在 `handleAuthenticated` 里调 `replayApprovalEcho()`（`approvalQueue.ts:182-186`）；CLI 侧 `WsClient` 本身也提供了 `onReconnect`（`agent-cli/src/ws/ws-client.ts:225`），但全仓无一处注册。

需求文档 §4.5-6 明确要求：「投票后 5s 未收到 `resolved` 且连接在线 → 重发一次（最多 2 次，**重连成功后立即补发一次**）」，并把它列为「不把会话拖到 900s 超时」的护栏。CLI 只实现了前一半。

**现象**

CLI 人工审批按键后（`submitApprovalVote` → `raceVoteAndEcho`）：
1. 若投票帧已到服务端、但 `resolved` 回声在连接抖动中丢失；
2. 5s / 10s 两次重发打完后仍然没有回声（重发时若连接已恢复，本可拿到服务端 `recentResolutions` 补发的回声，但两次机会已耗尽）；
3. 之后即使 `connected` 重连成功，也不会补发任何投票 → `approvalEchoWaiters` 永不闭合；
4. 模态因为 `markSubmitted()` 冻结（`modal-controller.ts:245-251`，`handleKey` 首行 `if (this.submittedFlag) return`），用户按键无效，工具不执行也不报错。

只能靠：其它端再投一票、本轮终态 `approval_aborted`、或服务端 900s 超时的 `resolved(null)` 才能解开。

**触发路径**：`mao-agent chat`（LOCAL）→ 触发需审批工具 → 模态打开 → 按 y → 投票上行成功 → 立刻断网几秒又恢复（回声那一帧丢了）→ 重试用尽 → 重连成功 → 模态一直停在「已提交，等待服务端确认…」。

**实际验证（临时用例，已删除）**

`agent-cli/test/__review_reconnect.spec.ts`（fake timers，`isWorkspaceTrusted` 打桩为 true）：

```ts
void exec.submitApprovalVote('req-lost', 'allow');                 // 只投票
await vi.advanceTimersByTimeAsync(10);
expect(sent.filter(m => m.type === 'tool_approval')).toHaveLength(1);
await vi.advanceTimersByTimeAsync(APPROVAL_ECHO_RETRY_MS * 2 + 10); // 5s + 10s 两次重发
expect(sent.filter(m => m.type === 'tool_approval')).toHaveLength(3);
// 模拟重连后的 connected 能力位事件
await exec.handleEvent({ type: 'connected', sessionId: null, data: { userId: 7, approvalRelay: true } });
await vi.advanceTimersByTimeAsync(60_000);
expect(sent.filter(m => m.type === 'tool_approval')).toHaveLength(3);   // ← 没有任何补发
expect(delivered).toEqual([]);                                          // ← 模态/等待都没被解除
expect(sent.filter(m => m.type === 'tool_result' || m.type === 'tool_error')).toHaveLength(0); // ← 工具没跑
```

用例通过（即上述「卡死」状态被复现）；随后手工投一条 `tool_approval_resolved` 才能让 `running` 收敛。

**影响**

CLI 执行端在一次短暂的网络抖动后可能长时间卡在审批模态（最长到 900s 超时），本轮任务不推进；与桌面端行为不一致（桌面端重连即补发、可自愈）。属于设计明确要求、实现遗漏的护栏。

**修复建议**

- 在 `LocalExecutor` 里补一条「重连即补发」：给 `WsClient` 注册 `onReconnect`（`ws-client.ts:110` 的 `setReconnectHandler`），或让 `setApprovalRelaySupported(true)`（即 `connected` 帧到达、能力位为 true 时）对 `approvalEchoWaiters` 内每个 `requestId` 立刻重发一次投票帧——与桌面的 `replayApprovalEcho()` 对齐；
- 补用例：参考本报告上面的复现用例，加一条「connected（approvalRelay=true）后立即补发一次，命中回声即收敛」（建议落成 `*.bugcheck.spec.ts`）。

## 已检查且验证无问题的部分（供复审参考）

为避免遗漏与误报，以下路径我逐个读过并（除标注外）用临时用例实跑过，结论是符合技术方案：

1. **后端**（用真实 `ApprovalRegistry` + 真实 handler，仅把 `has` 手工 bind 以绕开 B1）：认领恰好一次 → `resolved` 广播（含 `{approved:null}` 版式）+ 相位恢复 + 抑制升级；旧 CLI 通知帧不建规则；拒绝先认领后「总是允许」不建规则且只对发起连接补发回声；总是允许获胜帧凭 `claim.hint` 建规则；`handleSubscribe` 重放待审批公告（带 `approvalHint`）；参数按码点安全截断到 ≤8192 字节；`register` 无 `userId` 不广播 / SUBAGENT 回退父会话。
2. **桌面端**（`useChat + useStreamWS + approvalQueue` 真实现 + 假 WebSocket）：支持中继时点击只投票、回声前不调主进程、按回声的 `approved` 解锁（与本地按键相反时以回声为准）；旧后端（`connected` 不带 `approvalRelay`）立即本地放行且迟到回声不再解锁；`clearPendingApprovals` / 会话终态按拒绝释放 `awaitingEcho`；浏览器（无 `electronAPI`）只投票、不碰主进程、不抛错；`connected` 按连接写入能力位、重连补发；截断参数展示前缀+提示。
3. **CLI**：Ink 真实按键路径（`submitApprovalVote` → 等回声 → 执行；回声为拒绝则不执行且不回写文件）；模态未按键时被远端决策解除；`approvalRelay=false` 时按键立即本地放行；`resolved(null)` 无模态时不污染后续提问；本轮终态 `approval_aborted` 关闭全部模态。
4. **全量回归**：`agent-cli` 56 文件 / 630 用例全绿；`desktop` 146 文件 / 1461 用例全绿（31 个 Errors 为已知 undici/forks 环境问题）；`backend-ts` 460 文件中仅 `runtime-agent.spec.ts`（worktree 长路径 socket EADDRINUSE，6 条）与 `terminal-manager.spec.ts`（`MAO_BASE_URL` 环境变量，1 条）失败，均为已知环境限制，与本次改动无关。
5. `desktop`（`vue-tsc -b` + vite build）、`agent-cli`（`tsc --noEmit`）构建/类型检查通过；`backend-ts` 的 `tsc --noEmit` 只有 `src/weixin/*.spec.ts` 的历史类型噪声，与本次改动无关。
