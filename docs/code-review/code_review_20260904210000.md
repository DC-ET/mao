## P1-1 重连后 `reloadHistory` 整体覆盖消息流，擦掉本轮流式内容与重放的工具卡

- 位置：`sdk/embed/src/controller.ts:243`（`onAuthenticated` 内 `void this.store.reloadHistory(this.fetchHistory)`）、`sdk/embed/src/core/store.ts:75-83`（`reloadHistory`）、`sdk/embed/src/controller.ts:211-232`（`fetchHistory`）
- 描述：`reloadHistory` 无条件 `this.messages.value = history` 整体替换消息数组，而 `fetchHistory` 只映射 REST 返回的 `USER/ASSISTANT` 且 `toolCalls: []`。REST 只能拿到**已落库**的消息——本轮 assistant 消息由 `harness-service` 在轮次结束时才落库（`persistFinalAssistant` / `saveMessage`），因此正在进行的这一轮在 REST 里根本不存在。
- 触发场景：会话 RUNNING 期间断线重连。`ws-client.ts:131-139` 收到 `connected` 帧后先同步 `restoreSubscriptions()` 发出 `subscribe`，再回调 `onAuthenticated` 发起 REST。服务端 `streaming-ws-handler.ts:212-238` 立即重放 `session_snapshot` + 全部 active `tool_call_start`，这些帧（WS，走 registry 立即 flush）先于 REST 响应到达并已在 store 里建好流式气泡与工具卡；随后 REST 结果回来把它们整体覆盖。
- 为什么是 bug：
  - 已渲染的本轮回答与「执行中」的工具卡在重连瞬间消失；后续 `content_delta` 经 `ensureStreamingAssistant()` 新建气泡从中途继续拼接，用户看到的是**掐头**的回答。
  - 覆盖后 `findToolCall`（`store.ts:432-438`，严格按 `tool_call_id`）必然失配：`tool_call_args_delta` 被静默丢弃；`tool_call_result` 落到「补一张已完成占位卡」分支（`store.ts:138-158`）并可能再新建一个只含工具卡的空气泡。
  - desktop 的同类对账用 `applyFetchedMessages(sid, messages, { preserveStreamingAssistant: true })`（`desktop/src/stores/session.ts:1077-1105`），显式保留 REST 未覆盖的尾部消息与被 tracked 的流式气泡；embed 这次的实现缺了这层保护。
- 建议修复方向：`reloadHistory` 改为「合并而非替换」——以 REST 结果为前缀，保留本地尾部未落库消息（当前流式 assistant 气泡及其 `toolCalls`、尚未确认落库的乐观 user 气泡）；或把重拉延后到本轮终态（`session_status`/`session_snapshot` 命中 `COMPLETED/FAILED/CANCELLED` 后再拉）。合并方案需统一 id 口径：历史用 `h_${id}`、落库确认用 `s_${messageId}`（`store.ts:325-328`），同一条消息两种前缀会导致去重失效。

## P1-2 落库确认 60s 超时在断线场景误判发送失败，并回滚已落库的用户消息

- 位置：`sdk/embed/src/controller.ts:104`（`SAVE_CONFIRM_TIMEOUT_MS`）、`:478-490`（超时定时器）、`:493-501`（`rollbackSend`）、`sdk/embed/src/core/store.ts:295-311`（`rollbackLocalUserMessage`）
- 描述：`send()` 成功写入 socket 后挂 60s 定时器，超时即调 `rollbackSend`（删除/收口气泡）并弹出「发送超时：服务端未确认收到消息，请重试」。`pendingSaves` 只在 `destroy()`、`newSession()`、`session_already_running` 三处清理，**断线不清、不暂停**（`ws-client.onclose` 只回调 `onDisconnected` → `clearLlmRetry`）。
- 触发场景：发送后立即断线（或该帧在关闭窗口内丢失）。服务端 `streaming-ws-handler.ts:325` 已 `saveMessage` 并发出 `user_message_saved`，但该帧丢失且 `subscribe` 重放不包含它（只重放 `session_snapshot` / `tool_call_start` / `ask_user_questions`），因此重连后永远补不回来，60s 后必然触发超时分支。
- 为什么是 bug：
  - 消息其实已落库并已在执行，提示「服务端未确认收到消息，请重试」是误报；用户照提示重发会造成重复消息或被 `session_already_running` 拒绝。
  - `rollbackLocalUserMessage` 的 `hasRealContent` 只看尾部 assistant 是否已有 `content/thinking/toolCalls`。若此时本轮尚无产出（队列等待、compaction、LLM 首 token 慢，>60s 并不罕见），会**直接删掉用户消息与空 assistant 气泡**；随后 delta 新建气泡，界面变成「没有提问的回答」。
  - 对照 desktop `useChat.ts:473-497 sendMessageAndWaitForSave`：60s 超时只 `return false`（不清输入框、不当作成功），**不删除已上屏消息、不打断流式**。embed 这次把超时升级为「回滚」，超出了 desktop 语义。
- 建议修复方向：断线时挂起该定时器（`onDisconnected` 中暂停/延长），重连后改用 REST 历史对账判断是否已落库；或超时只降级为提示（保留气泡、允许用户自行重发），仅在明确收到服务端拒绝（`session_already_running` / `error`）时才回滚。

## P1-3 发送后把选中文本永久标记为 dismissed，同一段文本无法再次引用

- 位置：`sdk/embed/src/controller.ts:458-464`（`send()` 内 `if (selection) this.selectionTracker?.dismiss(selection)`）、`sdk/embed/src/context/selection.ts:51-56`（`currentSelection`）、`:67-70`（`dismiss`）
- 描述：`dismiss(text)` 把文本写入 `dismissed`，`currentSelection()` 对 `raw === this.dismissed` 一律返回 `null`。该状态只有 `dismiss(其他文本)` 或 `undismiss()` 会改变，没有时效与作用域限制。
- 触发场景：用户选中一段文本发送提问 → 想就**同一段文本**继续追问 → 重新选中同一段文字：引用 chip 不再出现，`send()` 里 `this.ui.quotedSelection ?? peek()` 也拿不到，消息不携带 `[用户选中文本]` 块。只有改选别的文本才恢复。
- 为什么是 bug：`dismiss` 的语义来源是「用户点掉引用 chip 表示不要这段」（`clearSelection()`，`controller.ts:540-542`），这是正确用法；发送成功只需要「本条不重复携带」，复用永久 dismiss 把它扩大成了「这段文本此后永久不可引用」。用户重新选中是明确的再次表达意图，却收不到任何反馈，属静默失效。
- 建议修复方向：区分两种语义——`clearSelection` 保持 dismiss；`send()` 改为「一次性消费」（例如记录已消费文本并在下一次 `selectionchange` 事件到来时清除，或只清 `ui.quotedSelection` 而不写 `dismissed`）。

## P2-4 `rollbackSend` 用 `undismiss(null)` 无条件清空 dismissed，误清用户先前关闭的引用

- 位置：`sdk/embed/src/controller.ts:498-501`、`sdk/embed/src/context/selection.ts:73-75`
- 描述：`undismiss(previous)` 的设计是恢复到调用前的快照，但调用方传的是硬编码 `null`，而不是发送前 `dismissedText()` 的值。
- 触发场景：用户先对文本 A 点掉引用 chip（`dismissed = A`），随后选中文本 B 发送且发送失败 → 回滚执行 `undismiss(null)` → A 的 dismiss 记录被一并清除，再次选中 A 时引用 chip 又冒出来。
- 为什么是 bug：与该方法自身的注释语义（「撤销 dismiss：发送失败回滚时恢复引用」）和参数命名 `previous` 不一致，属实现与契约不符；影响面限于「先关引用、再发送失败」这一组合，故定 P2。
- 建议修复方向：`send()` 里先 `const prevDismissed = this.selectionTracker?.dismissedText() ?? null` 并随 `pendingSaves` 一起保存，回滚时 `undismiss(prevDismissed)`。

## P2-5 Escape 监听挂在 `document` 并 `stopPropagation`，会吞掉宿主页的键盘处理

- 位置：`sdk/embed/src/ui/ChatPanel.vue:73-78`（`onKeydown`）、`:80-81`（`document.addEventListener('keydown', ...)`）
- 描述：SDK 渲染在 Shadow DOM 内，但键盘监听注册在宿主 `document` 上，命中 Escape 时调用 `e.stopPropagation()` 后再关闭浮窗。
- 触发场景：宿主页面在 `window` 上监听 Escape（常见于自研弹窗/抽屉/全屏预览）。浮窗处于展开状态时用户按 Escape，事件冒泡到 `document` 被 SDK 拦下，不再传播到 `window`；宿主的 Escape 逻辑失效，同时浮窗被关闭（可能并非用户意图）。
- 为什么是 bug：嵌入式 SDK 的既定边界是不干扰宿主行为（README/设计文档的接入约定即以「不侵入宿主」为前提）。有 `props.open` 守卫可以避免浮窗关闭时的影响，但展开期间对宿主 `window` 层监听器的截断是实际存在的副作用。
- 建议修复方向：把监听挂到 SDK 自己的 Shadow root / 根容器上（配合面板获得焦点），或保留 `document` 监听但去掉 `stopPropagation`，仅在事件 `composedPath()` 落在 SDK host 内时才消费。

## P2-6 断线时输入框被禁用，与 Composer「发送时将自动重连」的提示自相矛盾

- 位置：`sdk/embed/src/ui/ChatPanel.vue:38`（`inputDisabled = !props.connected || running`）、`sdk/embed/src/ui/Composer.vue:66-67`（`:disabled` + placeholder「连接中…」）、`:75-77`（「连接已断开，发送时将自动重连」）
- 描述：本轮把 `ui.connected` 修为随鉴权态双向同步（正确修复），但 `inputDisabled` 仍包含 `!connected`，于是断线期间输入框、发送按钮全部禁用，而同一屏下方仍显示「连接已断开，发送时将自动重连」。
- 触发场景：任何一次断线/重连窗口（网络抖动、静默 30s 触发主动 close、退避最长 30s）内用户想继续输入。
- 为什么是 bug：`ws-client.ts:305-310 sendReliable` 本就实现了「socket 不在则先 `connect()` 再补发」的能力，UI 层的禁用把这条路径完全屏蔽；提示文案承诺的行为无法发生，且用户在重连窗口内无法输入或排队，属提示与实际行为不一致。
- 建议修复方向：二选一保持一致——要么断线时允许输入并依赖 `sendReliable` 重连补发（去掉 `!connected` 或仅在长时间断连后禁用），要么把文案改为「连接已断开，正在重连…」并去掉「发送时自动重连」的承诺。
