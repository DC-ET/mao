## 中等严重程度

### 1. 压缩发生 CAS 冲突后，首轮仍会发送冲突前的旧请求快照

**代码位置**

- `backend/src/main/java/cn/etarch/mao/harness/core/SessionCompactionOrchestrator.java:57-66`
- `backend/src/main/java/cn/etarch/mao/harness/core/HarnessService.java:405-408`
- `backend/src/main/java/cn/etarch/mao/harness/core/AgentLoop.java:395-397`

**问题说明**

当压缩结果持久化发生 CAS 冲突时，`SessionCompactionOrchestrator` 会重新加载并把并发产生的最新摘要和增量历史应用到 `context`，随后因 `advanced == false` 返回 `false`。但是两个调用方都把 `false` 理解为“上下文未变化”，继续保存并使用压缩前构建的 `normalRequest` / `nextRequest`。

因此，本轮真正发送给 LLM 的仍是旧的完整历史快照，而不是 orchestrator 刚刚应用到 `context` 的并发压缩结果。并发执行同一会话时，这可能导致：

- 已生效的交接摘要在下一次模型调用中没有被使用；
- 重复发送已压缩历史，失去本次压缩的上下文缩减效果；
- 旧请求已经接近窗口上限时，仍可能因上下文过长而调用失败。

**修复建议**

让 orchestrator 明确区分“未触发/失败且上下文未变化”和“CAS 冲突但已重载最新上下文”两种结果。只要 `applyHistory` 应用了与原快照不同的最新边界，调用方就应重新执行 `promptEngine.buildRequest(context)`，不要复用旧请求。可以返回包含 `contextReloaded` / `requestNeedsRebuild` 的结果对象，而不是仅返回布尔值。

### 2. 压缩开始事件在异常或 CAS 冲突路径上没有对应结束事件

**代码位置**

- `backend/src/main/java/cn/etarch/mao/harness/core/CompactionService.java:59-71`
- `backend/src/main/java/cn/etarch/mao/harness/core/SessionCompactionOrchestrator.java:57-66`
- `backend/src/main/java/cn/etarch/mao/harness/core/HarnessService.java:409-415`
- `backend/src/main/java/cn/etarch/mao/harness/core/AgentLoop.java:398-406`

**问题说明**

达到阈值后，代码先发送 `onCompactionStart`。目前只有语义校验失败、物理前缀校验失败和成功持久化路径会发送 `onCompactionEnd`。以下路径均不会发送结束事件：

- 非流式 LLM 调用抛出网络、HTTP 或解析异常；
- 第二次校正请求在调用期间抛出异常；
- 压缩结果持久化发生 CAS 冲突，orchestrator 直接返回 `false`；
- 其他持久化或重载阶段异常被上层捕获并降级继续执行。

客户端收到 `compaction_start` 后会把会话设为压缩中，只有 `compaction_end` 才会清除该状态。请求开始压缩的可恢复异常会被 `HarnessService` 吞掉并继续正常 LLM 调用，因此会话可能在整个后续执行期间一直显示/保持“压缩中”的逻辑状态；CAS 冲突也有相同问题。

**修复建议**

在一次 `onCompactionStart` 发出后，用 `try/finally` 或统一的压缩生命周期封装保证恰好发送一次 `onCompactionEnd`。失败、取消和 CAS 冲突可使用 0 或实际已知的统计值结束；如果协议需要区分结果，建议为结束事件增加状态字段，但不要遗漏结束事件。注意避免与当前成功路径重复发送。
