## 一、问题清单（按严重程度）

### [中] 1. `normalizeToolResult` 遗漏 `exit_code !== 0` 判定，shell 非零退出码不再标记为 error

**位置**：`backend-ts/src/harness/tool/tool-result.ts`（`normalizeToolResult`）

**现象**：
- 旧规则（`backend-ts/src/session/ws/ws-streaming-event-listener.ts` 的 `isErrorResult`，本次未删除、保留为 fallback）为：
  ```ts
  if ('error' in node) return true;
  if ('exit_code' in node && Number(node.exit_code) !== 0) return true;   // ← 旧规则有这一条
  ```
- 新 `normalizeToolResult` 只检查 `'error' in parsed`，**未包含 `exit_code !== 0` 分支**。
- 而 `AgentLoop` 现在**总是**通过 `toolResultMeta(result)` 透传 meta 给 listener，`WsStreamingEventListener` 的新判定为：
  ```ts
  const isError = meta?.status === 'error' || (meta == null && isErrorResult(displayResult));
  ```
  由于主路径 meta 恒非 null，`isErrorResult` fallback 分支**永远不会触发**，`isError` 完全由 `meta.status` 决定。

**影响**（功能逻辑回归）：
- `shell-session-tool.ts` 的 exec/write_stdin 结果恒为 `{ exit_code, output, ... }`（无 `error` 键，见 `shell-session-tool.ts` 145-177 行）；LOCAL 模式桌面端 `await_async` 同样返回 `{ exit_code, completed, output }`（见 `tool-dispatcher.ts` 271 行注释）。当命令以非零码退出时：
  - 旧行为：`tool_call_result` 事件 `status:'error'`、activity 记录 `ERROR`；
  - 新行为：`status:'success'`、activity 记录 `SUCCESS`，`tool_call_result` 状态展示错误。
- `tool-result.spec.ts` 的用例仅覆盖 `{error, exit_code}`（含 error 键），未覆盖**纯 exit_code 非零**场景，故单测未暴露该回归。

**建议**：在 `normalizeToolResult` 中补上与旧规则一致的 `exit_code` 判定：
```ts
if ('exit_code' in parsed && Number((parsed as Record<string, unknown>).exit_code) !== 0) isErr = true;
```
并在 `tool-result.spec.ts` 补充纯 `{"exit_code":1,...}`（无 error 键）用例。若希望彻底统一，可考虑把 `isErrorResult` 从 ws 层删除、收敛到 `normalizeToolResult` 单一实现。

### [中/低] 2. `CompositeAgentEventListener.onToolCallResult` 不透传第三参 meta，与主路径行为不一致

**位置**：`backend-ts/src/harness/core/composite-agent-event-listener.ts`（`onToolCallResult(toolCallId, result)`）

**现象**：
- 主 WS 路径（`streaming-ws-handler.ts` / `agent-inbound-handler.ts`）直接 `new WsStreamingEventListener(...)` 传参，meta 能到达。
- 但经 `CompositeAgentEventListener` 包装的路径（`subagent-visibility-service.ts:194`、`crash-recovery-runner.ts:183`）会丢弃第三参，`WsStreamingEventListener` 收到 `meta == null`，回退 `isErrorResult`。
- 结果：这两条路径与主路径对"错误判定"采用**两套规则**。若按问题 1 修复后，主路径以 `meta` 为准（无 exit_code 判定），subagent/crash-recovery 路径仍用旧启发式（含 exit_code 判定），行为进一步分裂；当前状态下则两条路径对 shell 非零退出码判定相反。

**建议**：`CompositeAgentEventListener.onToolCallResult` 增加第三参并透传：
```ts
onToolCallResult(toolCallId: string, result: string, meta?: ToolCallResultMeta): void {
  this.forEach('onToolCallResult', (l) => l.onToolCallResult(toolCallId, result, meta));
}
```
其余现有 listener（Noop `agent-event-listener.ts:37`、`scheduled-task.service.ts:258`、`card-progress-listener.ts:42`、`subagent-result-collector.ts:36`）均只消费 1-2 个参数，第三参为可选，向后兼容，无需改动。

### [低] 3. `dispatchInvocation` catch 分支对非 Error 异常取 `message` 不稳健

**位置**：`backend-ts/src/harness/tool/tool-dispatcher.ts`（`dispatchInvocation` catch 分支）

**现象**：`'Tool execution failed: ' + (e as Error).message` 假定异常一定是带 `message` 的 Error。若上游 `throw 'string'` 或 `throw null`，会得到 `Tool execution failed: undefined`，甚至 `e.message` 访问抛 TypeError（该 TypeError 发生在 catch 块内，会让 `dispatchInvocation` 意外向外抛，破坏"异常归一不向上抛"的承诺）。

**说明**：旧 `AgentLoop.dispatchTool` 的 catch 有相同写法，非本次引入的新问题；但既然本次将"归一不抛"作为新入口的契约，建议顺手加固：
```ts
const msg = e instanceof Error ? e.message : typeof e === 'string' ? e : 'Unknown error';
```

## 二、重点核查项结论（未发现问题）

## 三、补充观察（非阻塞）

- `dispatchFull` 在 CLOUD 模式也会调用 `resolveDescriptor`，但 descriptor 仅 LOCAL 审批路径消费，CLOUD 路径属冗余计算。影响极小，可视后续优化，无需本轮处理。
- `ToolDescriptor.executor` 字段（server/desktop/mcp-server）目前仅为元数据，未驱动任何行为分支；若后续要用它做 LOCAL 执行判断，需注意与 `executionMode` 的语义边界，避免重复定义。
- 本次 `tool-result.spec.ts` 用例较完整覆盖 error 键规则，但建议补上问题 1 所述的 `exit_code` 用例，以及 dispatchInvocation 的异常归一用例（非 Error 异常）。
