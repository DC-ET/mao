# 代码审查报告：聊天输入区任意文件上传到 runtime 临时目录

- 审查日期：2026-08-20
- 审查范围：本次需求涉及的后端改动（file.service.ts / file.routes.ts / session.service.ts / create-app.ts / runtime-data-resolver.ts / path-sandbox.ts / prompt-engine.ts / 相关测试）+ 前端关联改动（ChatInput.vue / chatFileUpload.ts / SideChatPanel.vue）
- 验证：`backend-ts npm test` 122 个文件 787 个用例全部通过；`npm run build`（tsc --noEmit）错误数与本分支基线一致（172 行，均为存量 spec 类型问题，与本次改动无关）

## 问题列表

### [高] 1. 用户打开任意本地图片即自动触发「上传至 runtime 并插入 @引用」，改变既有图片链路行为并引入路径校验缺口

- 位置：`desktop/src/utils/chatFileUpload.ts`（`uploadChatFile` 未做图片分支）、`desktop/src/components/chat/ChatInput.vue`（`handleFileSelect` / `handleDropFiles` / paste 分支按 `image/*` 区分，但后端 `POST /v1/files/upload-incoming` 与 `POST /v1/files/upload` 均不校验内容类型）
- 问题：
  1. 需求明确「图片仍走 `images` 字段多模态链路，不改为节点形式」（`docs/chat-file-upload-technical-design.md` N6/R7）。但新增的 `upload-incoming` 服务端**未限制图片类型**：任一用户上传的图片文件被 `uploadChatFile` 落盘为 `@{绝对路径}@` node 后进入正文文本，Agent 需要自行 read_file 才能拿到图片信息。同时**旧链路**（文件树选择图片、拖拽图片）全部改走 runtime 上传，导致“图片”这个既有成功链路在本版本被整体替换为「文本引用」形态。业务行为出现整体回归，与 R7「图片上传逻辑保持不动」冲突。
  2. 更实际的极简风险：图片通过 `upload-incoming` 上传后 `storedName` 保留 `.jpg/.png` 后缀，该绝对路径 `@{/runtime/...jpg}@` 在后续消息中会被 `ImageFileSupport.mimeFromPath` 判定为图片路径；同时在 `file` 表留下 `fileSize` 元数据。若模型上下文压缩/历史展示使用该路径，可能触发图片解码路径（`read_file` 图片分支）而拿到非预期结果——虽然不是崩溃，但属于两套图片链路并存造成的语义混乱。
- 修复建议：
  - 前端 `uploadChatFile` 第一个参数增加类型判断：`if (file.type.startsWith('image/'))` 时跳过 runtime 上传，继续走既有图片胶囊/`images` 链路（`addPendingImage` / `normalizeImageForUpload`）。
  - 后端 `POST /v1/files/upload-incoming` 增加图片类型拒绝（`mimetype`/魔数校验），返回明确错误，防止绕过前端直接构造图片请求。同时避免与既有 `uploadImages` 双模式（local/OSS）冲突。

### [高] 2. `deleteSession` 级联清理中，`deleteRuntimeWorkspaceFiles` 不再像旧实现那样删除整个自动工作区目录，「遗留数据」从旧版本的行为差异未被文档/发版说明覆盖

- 位置：`backend-ts/src/session/session.service.ts`（`deleteSession` 新增 `deleteRuntimeWorkspaceFiles` / `resolvedRuntimeDirs` / `rmRecursive`）
- 问题：改动前的 `deleteSession` 是「删除会话 + 删除整个 `workspace` 目录」（`deleteWorkspaceDirectory`，包含自动分配的独立工作区 `workspaceRoot/{userId}/{sessionId}` 下的全部用户项目数据）。改动后对所有 CLOUD 会话（含独立工作区）升级为「只删 `mao-runtime-*` 前缀的临时文件 + 清理 runtime 目录（`skills`/`shellOutput`/`incoming`）」，不会再删 `{userId}/{sessionId}` 下的用户文件。严格来说这是修复了旧实现误删用户数据的问题，**方向是好的**；但：
  - 需求的验收标准 5 是「删除会话后 runtime incoming 被清理」，对「会话工作区是否整目录删除」未明确；
  - 本清理对「git 克隆 / existing 项目等共享工作区」会话不做整目录删除，行为与旧实现不一致；
  - 未在 CHANGELOG 记录该行为变化。
- 修复建议：在 CHANGELOG 「后端」小节记录删除语义变化；确认运营侧没有依赖旧行为（自动独立工作区整目录删除）的清理任务，若有请保留显式删除维护任务；`resolvedRuntimeDirs`/`rmRecursive`（未被使用的死代码，见问题 4）一并删除以降低误解。

### [中] 3. 服务端 `POST /v1/files/upload-incoming` 的会话存在性校验缺注册/本实现处的显式 try/catch，且会话删除立即执行时可能清掉正在上传/引用的文件

- 位置：`backend-ts/src/file/file.routes.ts`（`upload-incoming` 路由）、`backend-ts/src/session/session.service.ts`（`deleteSession`）
- 问题：
  1. 路由内直接调用 `sessionService.getSession(sessionId)`：`getSession` 对不存在会话抛 `SESSION_NOT_FOUND`。对比 ws handler 的 `requireOwnedSession`（try/catch 返回「会话不存在」事件）、对比 `requireOwnedSession` 未用于 upload-incoming；`getSession` 抛出的 `BusinessException` 会进入全局 `handleError`，返回错误码与“无权访问”语义不同，但不影响安全性——**已知会话 ID 时上传会成功**，服务端不校验发起端权限之外的其他约束（文件大小 50MB 兜底保留）。此处不构成越权（会话归属已校验），但异常语义不一致，建议与 `requireOwnedSession` 复用。
  2. 用户先上传文件（选择即上传），随后消息尚未发出即删除会话：删除会立刻清掉 incoming 目录；若编辑器引用仍在，发送时路径已失效。前端已做「上传中不发送」，但没有「删除会话中断上传/发送前二次校验」的防护；服务端不校验引用路径是否存在，Agent 会得到「文件不存在」的工具响应（软件提示文案依赖 LLM 判断）。不为严重。
- 修复建议：路由复用 `requireOwnedSession` 保持异常语义一致；在前端发送前对 `@{绝对路径}@` 引用做存在性 preflight（GET `/v1/files/workspace-read` 或新接口）或至少删除会话时清空对应编辑器的引用节点。

### [中] 4. 新增的 `resolvedRuntimeDirs` / `rmRecursive` 是死代码，且与 `runtimeSessionCleanup` 职责重叠；缩进错位影响可读性

- 位置：`backend-ts/src/session/session.service.ts`（`resolvedRuntimeDirs`、`rmRecursive`、`deleteRuntimeWorkspaceFiles` 内层缩进）
- 问题：`resolvedRuntimeDirs` 与 `rmRecursive` 计算后从未被调用（清理实际由 `create-app.ts` 注入的 `runtimeSessionCleanup` 完成；`deleteRuntimeWorkspaceFiles` 只处理工作区内的 `mao-runtime-*` 前缀）。死代码 + 职责重复（两处清理 runtime 目录），长期维护易误改。另 `deleteRuntimeWorkspaceFiles` 方法体内缩进错位（`private` 后无缩进），非功能性但需要修正。
- 修复建议：删除 `resolvedRuntimeDirs`、`rmRecursive`；将 runtime 目录清理统一收敛到 `runtimeSessionCleanup`（或删掉注入回调、统一在 SessionService 内实现），修正缩进。

### [中] 5. `runtimeSessionCleanup` 的 `rmdirSync(userDir)` 存在 TOCTOU 竞态与误删空目录后残留父目录的边界

- 位置：`backend-ts/src/create-app.ts`（`runtimeSessionCleanup`）
- 问题：
  1. `readdirSync(userDir)` 与 `rmdirSync(userDir)` 之间，其他并发执行（同一用户同时运行别的话）可能向 `userDir` 写入新文件 → `rmdirSync` 抛 ENOTEMPTY → 被 catch 吞掉，无副作用但说明竞态存在；更稳妥的做法是不主动删父目录，交由后续清理。
  2. `rmSync(sessionDir)` 会连带删除该会话目录下的 `skills`（skill 同步副本）与 `shellOutput`——如果某个 shell 会话仍存活（删除会话未先释放 shell），其输出文件被删，可能造成「执行中会话的 shell 输出丢失」；同时清理时未先 `closeByConversation`。
- 修复建议：删除前先经过 `streaming-ws-handler` 的 `releaseSessionExecutionResources`（或至少在 `deleteSession` 中增加 `shellSessionManager.closeByConversation` 的调用时机）；对 `userDir` 的删除可保留但注释竞态，或改为仅在 `readdirSync` 返回空时才 `rmdirSync`（当前已经是 try 全吞，竞态只是「删除失败但被吞」的噪音，问题级别中）。

### [中] 6. 前端 `handleSend` 中 `imageFiles` 的过滤基于 `f.type` 字符串，而「非图片文件」上传成功后仍作为文本引用存在 `@{绝对路径}@` 中；服务端对 `images` 字段的校验仍为 10 张上限

- 位置：`desktop/src/components/chat/ChatInput.vue`（`handleSend` 中 `pendingFiles.value.filter((f) => f.type.startsWith('image/'))`；`addPendingImage` 的 10 张限制）
- 问题：`pendingFiles` 现在同时容纳「图片」与「上传中的文件」。若用户选择 5 张图片 + 8 个文件，`pendingFiles.length < 10` 判定通过但图片已 5 张；文件上传完成后不再占位但图片仍有数；整体不严格但业务上可接受。更重要的是 `handleSend` 中 `if (!text && imageFiles.length === 0) return`——若用户只上传了文件（节点文本空）`text` 非空（含 `@{path}@`），可以发送，行为正确。**唯一问题**：`addPendingImage` 的 10 张限制仅针对图片，文件无数量上限（需求 N5 明确「不设数量上限」），确认无冲突。
- 修复建议：无需修改业务限制；如需更严谨可将图片数量单列 `imageCount` 而非复用 `pendingFiles.length`。

### [低] 7. `buildFileEntity` 中 `extension` 取 `originalName.lastIndexOf('.')` 的整段后缀直接拼接到 UUID（含路径分隔符/空字节等），且不校验原始文件名中的路径穿越字符

- 位置：`backend-ts/src/file/file.service.ts`（`buildFileEntity`）
- 问题：`storedName = randomUUID() + extension`，`extension` 直接来自用户文件名（`originalName.slice(lastIndexOf('.'))`）。风险：
  - 用户文件名形如 `foo/bar`、`..`、`a.b/c`（multipart 允许 filename 包含路径）→ `extension` 含分隔符；`join(incomingDir, storedName)` 会生成**不在 incoming 内的路径**（`uploadIncomingFile` 使用 `join` 而非 resolve 拼接，但 `join` 仍会合并 `../`）。`PathSandbox.resolve` 生效了吗？——`addAllowedRoot(runtimeRoot)` 放行的是整个 runtime 根，本路径仍在 runtime 下，不会被沙箱拦截；但 `file` 表落库的 `filePath` 与返回的 `absolutePath`（`resolve(incomingDir, entity.storedName)`）会指向**意外子目录**，若文件名含 `../` 甚至可能写到同用户其他会话目录。
  - 图片链路（`resolveUploadMime`）对 `imageExt` 后缀有追加逻辑，但对 `originalName` 内嵌 `/`、`\`、`..` 无剥除。
- 修复建议：在 `buildFileEntity` 中对 `extension` 清洗：仅保留最后一段合法字符（`/^[A-Za-z0-9._-]{0,16}$/`），或使用 `basename(originalName)` 后再取扩展名；storedName 统一用固定安全字符集（如 UUID + 白名单后缀），杜绝路径分隔符注入。

### [低] 8. 上传错误码 `5000` 与通用错误码混用，客户端只能靠 message 区分失败原因

- 位置：`backend-ts/src/file/file.service.ts`（`uploadIncomingFile` 抛 `new BusinessException(5000, '文件保存失败')`）
- 问题：与 `uploadFile` 行为一致（原实现即 5000），本次重构未改变；`uploadIncomingFile` 若 `buildFileEntity` 内 `resolveUploadMime`/`ImageFileSupport` 抛异常也被转成 5000，前端 `uploadChatFile` 只拿到 `null` 展示「上传失败」，无法区分过大/空文件/存储写失败。维持现状可，但建议补充错误码细分（4001 已有大小限制，空文件 4000 已有；主要是「存储不可用」可新增 5000 细分）。
- 修复建议：可选。将「落盘/落库失败」与「参数不合法」拆分为不同错误码，前端按错误码提示。

### [低] 9. `prompt-engine` 的 `incomingFileHint` 无条件注入固定目录提示，与「该路径可能不存在」的提示语义矛盾

- 位置：`backend-ts/src/harness/core/prompt-engine.ts`（`incomingFileHint`）
- 问题：提示会注入**每条消息**的系统 prompt（`buildSystemPrompt` 中无条件调用），即使会话没有上传任何文件也会把 `## 用户上传的文件` 段落写进 prompt，每个会话固定增加约 300 token 的上下文开销。同时正确性不受影响（内容为静态说明）。若作者想避免噪音，可检测最近一条 user 消息是否含 `@{...}@` 再注入。
- 修复建议：可选优化。改为在有 `@{绝对路径}@` 引用时才注入该段落，减少无效上下文。

### [低] 10. `resolveIncomingDir` 未按技术方案进行 `mkdir`，由 `uploadIncomingFile` 调用 `mkdirSync(incomingDir)` 后写入；但在 `resolve` 返回前先被 `addAllowedRoot(runtimeRoot)` 登记——目录是否存在不影响沙箱判定

- 位置：`backend-ts/src/harness/runtime/runtime-data-resolver.ts`、`backend-ts/src/create-app.ts`（`addAllowedRoot(runtimeRoot)`）
- 问题：无功能问题——`addAllowedRoot` 登记的是根目录，`isUnderAllowedRoot` 对子路径前缀判定，不要求目录已存在。但注意：`addAllowedRoot(runtimeRoot)` 是**全局放行整个 runtime 根**，即任意 `runtime/{任何userId}/{任何sessionId}/...` 下的文件都能被工具读取（凡位于 runtime 内的路径都通过）。这与技术方案第 8.2 节「只放行 `runtime/{userId}/{sessionId}/incoming/` 会话级子目录，不整体放行 runtime 根」存在差距；在用户 ID 与会话 ID 均为服务端凭据不可直接伪造的前提下不构成越权（upload 路由校验归属），但建议收敛为按会话登记（`shell-session-manager` 已有按会话 `addAllowedRoot(resolveSessionRuntimeDir(uid, conversationId))` 的先例）。
- 修复建议：将 create-app 的全局 root 登记改为在 `upload-incoming` 首次使用该会话时按 `resolveSessionRuntimeDir(userId, sessionId)` 登记（或在 route 首次 upload 时调用 `addAllowedRoot(resolveIncomingDir(...))`）。

## 总结

- 功能主链路（上传 → 落盘 → 落 file 表 → 返回绝对路径 → 文本引用 → 工具读取 → 会话删除清理）正确，`npm test` 全部通过。
- 需要优先处理：
  1. 图片链路被新的「任意文件统一入口」吞并，违反 R7（高）；
  2. 删除语义变化（独立工作区整目录删除被替换为仅清理 `mao-runtime-*`）需要明确对齐预期并记录 CHANGELOG（高）；
  3. 新增死代码 `resolvedRuntimeDirs`/`rmRecursive` 与运行时清理职责重复（中）；
  4. `storedName` 扩展名未清洗、可能产生路径穿越式拼接（低但建议修）。
- 不构成问题：image 上传后 `storedName` 带扩展名触发 `mimeFromPath` 图片路径判定，仍属「图片走文本引用」链路自身语义，与问题 1 一并处理即可。
