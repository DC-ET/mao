# 代码审查报告：飞书卡片进度回复

- 审查范围：当前 Git 工作区未提交代码
- 需求：飞书卡片进度回复：先发处理中卡片、按 loop round/toolcall 更新、完成时更新最终内容
- 结论：发现 3 个功能逻辑问题；未修改业务代码。

## 高严重度

### [高] 处理中卡片发送失败会阻断 Agent 执行，并将正常请求误判为处理失败

**位置**：`backend-ts/src/feishu/agent-inbound-handler.ts:75-82`、`backend-ts/src/create-app.ts:804-816`

`createProgressCard` 位于主执行 `try` 内，卡片发送 API 的异常、鉴权异常、群聊引用回复失败，或返回值中缺少 `message_id` 时，会直接进入统一 `catch`。此时 `harnessService.execute` 尚未调用，Agent 实际不会执行；由于 `cardListener` 仍为 `null`，链路只返回“处理您的消息时出现了错误”的文本。这样卡片能力的短暂故障会阻断现有纯文本链路，违背“卡片是进度展示，不应改变 Agent 执行语义”的预期。

**修复建议**：将卡片创建视为可选的通知能力：发送卡片失败时记录日志并继续执行 Agent，使用纯文本回复兜底；不要把卡片发送异常当作 Agent 执行异常。只有在已成功创建卡片后，才将其纳入后续更新生命周期。

## 中严重度

### [中] toolcall 结果未按 `toolCallId` 归属，多个工具并发/乱序返回时会串写摘要

**位置**：`backend-ts/src/feishu/card-progress-listener.ts:21-31`

`onToolCallResult` 忽略 `toolCallId`，通过 `findIndex((item) => item.startsWith('调用 '))` 选择待完成工具。多个 tool call 同一轮并行执行时，若后发起的工具先返回，其结果会被写到第一个工具；随后第一个工具的结果又会写到另一个工具。卡片中的工具名称与结果因此错配，且原始工具 ID 只在没有待处理工具时才显示。

**修复建议**：维护 `toolCallId -> 工具条目/索引` 映射，在 `onToolCallStart` 建立映射，在 `onToolCallResult(toolCallId, ...)` 精确更新对应条目；工具完成后删除映射。对重复 start、缺失 start 的 result 分别定义明确行为。

### [中] 卡片更新 API 失败可能导致整个请求没有最终回复，且失败处理还会再次抛错

**位置**：`backend-ts/src/create-app.ts:819-826`、`backend-ts/src/feishu/agent-inbound-handler.ts:99-113`

轮次更新在 `FeishuCardProgressListener.queue` 中吞掉了更新异常，但最终 `complete()`/`fail()` 使用 `progress.update` 直接调用。如果最终 patch 失败，`complete()` 抛出后会进入 handler 的 `catch`；随后 `fail()` 再次 patch，同样失败并从 `catch` 逃逸。此时不会执行纯文本 `onReply`，请求可能被入站处理器释放并重试，造成重复执行/重复卡片，或者用户完全收不到完成结果。取消路径也有同样的直接 patch 风险。

**修复建议**：卡片 patch 失败必须与 Agent 执行结果解耦：统一捕获并记录卡片更新错误，保证 `complete/fail/cancel` 不阻断 handler；卡片不可更新时应按原纯文本链路发送最终文本（必要时记录卡片已失效，避免继续 patch）。同时为发送、更新、最终状态分别定义幂等/失败策略。

## 已核验项

- 群聊卡片使用 `message.reply` 引用原消息，私聊使用 `message.create` 并按 `open_id` 投递；成功发送后从响应读取 `data.message_id`，生命周期路径清晰。但上述 API 异常兜底不足。
- `CompositeAgentEventListener` 已接入 `onContentDelta`、`onToolCallStart`、`onToolCallResult`、`onMessageEnd` 和 `onError`，轮次更新按 `onMessageEnd` 排队，并以 Promise 串行化更新。
- 文本累计和最终内容限制为 6000 字符，工具摘要单项限制为 240 字符、工具区域限制为 3000 字符；仍建议结合飞书实际卡片大小限制做接口级测试，避免 Markdown/JSON 总体积超限。
- 未发现本次改动将纯文本成功链路普遍改为不发送：当卡片创建返回 `null` 时仍调用 `onReply`。但卡片发送/更新异常会触发上述回归。
- `backend-ts` TypeScript build 通过；新增卡片监听器测试覆盖了轮次更新、工具摘要和取消串行化，但未覆盖并发 toolcall、卡片发送失败、patch 失败及纯文本兜底。
