## 重要（建议本轮修复）

### P2-1（残留）重放 reclaim 后 60 秒「无心跳窗口」，跨 monitor 轮次可再回收同一行 → 双执行/打断在途

**位置**：
- `backend-ts/src/weixin/inbound-message.repository.ts:49-67`（`reclaimStuck` 的事务内 UPDATE：`SET status = 'CLAIMED'`，**不显式刷新 `updated_at`**；列虽有 `ON UPDATE CURRENT_TIMESTAMP`，但 FAILED→CLAIMED 重放时才刷新，**CLAIMED 超时行回收是「原值重赋值」不触发 ON UPDATE**，`updated_at` 保持 10 分钟前的旧值）
- `backend-ts/src/weixin/inbound-processor.ts:107-119`（`startHeartbeat` 的 `setInterval` **首次触发在 60s 后**，无立即心跳）
- `backend-ts/src/weixin/monitor.service.ts:113-117`（重放 fire-and-forget）× monitor 轮询周期 ~35s（`longPollTimeoutMs=35000`，`app-config.ts:230`）

**触发链**（全部在正常运行条件下可复现）：
1. 消息处理中断（或 FAILED），`reclaimStuck` 回收超时 CLAIMED 行重放，`updated_at` 保持旧值；
2. 重放的 `processReplayedMessage` 启动，`startHeartbeat` 首次心跳要等 60s；monitor 35s 后转入下一轮；
3. 下一轮 `reclaimStuck` 的 `updated_at < NOW() - 10min` 判定用旧值 → **该行再次被回收**，第二次重放启动；
4. 第二次重放的 `handler.onMessage` 走 `AgentWeixinInboundHandler.onMessage`：`nextGeneration(sessionId)` 使第一次重放的 generation 失效 + `abortRunningExecution` **打断刚跑了 35s 的第一次重放**；若第一次重放已完成媒体下载/USER 消息落库（`saveMessage`），其产物再由「世代取代回滚」兜底清理（`rollbackSupersededUserMessage`）；
5. 最差情形下该循环每 ~35s 重复一次（每次 reclaim 不刷新 `updated_at`），直到某次重放撑过 60s 发出首次心跳才稳定。

**预期 vs 实际**：预期一行同一时刻只有一个处理者；实际 reclaim 与首次心跳之间存在至多 60s 的「DB 视角无心跳」窗口，跨 35s 轮询周期必然命中一次。

**影响**：中——被打断的重放浪费一次执行（媒体下载 + Agent token），且用户感知为回复延迟/偶发双倍处理；有 handler 世代机制兜底不会双重回复，但属于不必要的中断循环。

**修复建议**（任一即可，改动极小）：
- `reclaimStuck` 事务内 UPDATE 改为 `SET status = 'CLAIMED', updated_at = CURRENT_TIMESTAMP`（显式刷新，绕开 ON UPDATE 的原值重赋值不触发问题）；或
- `startHeartbeat` 启动时先立即 `void repo.heartbeat(...)` 再进入 `setInterval`。

## 建议（不阻塞合并）

### P3-1 心跳进程与重放回收之间的瞬时窗口（秒级，无实际后果）

`processInboundMessage` 正常路径：enqueue（CLAIMED，`updated_at=now`）→ 后台处理启动、`startHeartbeat` 首次心跳在 60s 后。极端时序下（入队后进程恰好停顿 >10min 且 monitor 下一轮 reclaim 跑在 `processClaimed` 启动前）同一行会被重放路径二次处理。窗口需要「入队与处理启动之间停顿超 10 分钟」，实际只有进程假死场景命中，且 handler 世代机制兜底无双重回复。记录备查，不建议为此加锁。

### P3-2 `DONE` 超窗口重发与「ilink 延迟重投」的语义重叠

`shouldSkipDuplicate` 把「DONE 超 24h」一律判为合法重发。理论上 ilink 服务端也可能在 24h 后重投同一条消息（极端的游标回退），此时会误判为合法重发再处理一次。概率极低且后果仅为多回复一次，可接受；若后续观察到 ilink 存在长延迟重投，可考虑在指纹中并入消息自带时间字段。

## 已核实无问题（记录以免重复排查）

- `heartbeat()` 的 `status='CLAIMED'` 守卫：`markDone` 后迟到的心跳不会把 DONE 刷回 CLAIMED，仅徒劳更新 `updated_at`（影响 DONE 去重窗口起点，正向）。
- `reclaimForResend` 不设状态守卫：仅在 `shouldSkipDuplicate` 判定 DONE 超窗口后调用，窗口内不可能被并发重放（DONE 不在 reclaim 范围），安全。
- `processInboundMessage(knownKey)` 直接调用兜底分支（`inbound-processor.ts:61-71`）：生产仅 monitor 以 knownKey 调用，兜底分支只在未先入队的直接调用（测试/未来调用方）时启用，逻辑与 monitor 两步一致。
- monitor 入队失败的游标语义：`enqueueInboundMessage` 抛错 → 外层 catch → 本轮不推进游标 → ilink 重投 → 下轮 enqueue 幂等跳过已入队部分，无重复处理。
- `monitor.service.spec.ts` 新增 mock 覆盖了 `enqueueInboundMessage` 返回 null（重复跳过）与多消息场景，与实现吻合。
- 心跳 spec 用 fake timers 验证了「处理期有心跳、结束后停止」，覆盖到位。
