## 上一轮修复核对（全部通过）

### M-1 修复核对：writeArchive 时序 ✓

- 位置：`backend-ts/src/harness/core/session-compaction-orchestrator.ts:69-78`，
  位于重载 `loadValidated`（latest）/ `loadHistoryAfterBoundary`（latestHistory）之后、
  `applyHistory` 之前。
- writeArchive 为同步写（writeFileSync + renameSync），返回后 `applyHistory` 内
  `buildArchiveHint → listArchiveFiles` 立即可见新归档文件，首次压缩即可注入 hint，M-1 消除。
- writeArchive 全部副作用都在 try 内（含 resolveDir/mkdirSync），不可能向外抛异常；

  失败仅 warn，不改变后续 advanced 判定 / 事件记录路径。

### L-1 修复核对：persisted 判据 ✓

- 写入判据由 advanced 改为 persisted：CAS 获胜即写归档（无论之后边界是否被他人超越），
  消除并发超越场景下的归档区间缺口；CAS 失败路径（persisted=false）不写归档、不记事件，
  无任何副作用（spec `doesNotWriteArchiveWhenCasPersistFails` 覆盖）。
- **并发可行性推演（为何 CAS 获胜场景下 latest?.compactCount 正确）**：
  CAS 条件为 `last_compacted_msg_id = expectedOldBoundary`（session-compaction.repository.ts:47）。
  他人线程要赢得 20→30 的 CAS，必须先在本线程 persist 之后 loadValidated（看到 boundary=20），
  再经一次数秒级 LLM 压缩后才能 persist——不可能落入本线程 persist→loadValidated 的微秒级窗口；
  与本线程同起点的并发线程 CAS 必败。因此在所有现实交错下，CAS 获胜后重载的 latest 就是
  本线程刚写入的记录（boundary=candidate、compactCount=本线程序号），归档序号正确；
  归档区间 (boundary, candidate] 与 applyHistory 排除的区间（id > latestBoundary = candidate）
  恰好互补、不重不漏。

### I-1 修复核对：空消息防御 ✓

## 新发现问题（均为 Info 级理论竞态，实际几乎不可达，不影响业务功能，记录备查）

### I-1 `latest?.compactCount ?? 1` 回退序号 1，在 loadValidated 返回 null 时会覆盖 compaction-001.jsonl

- 位置：`session-compaction-orchestrator.ts:73`（`latest?.compactCount ?? 1`）；
  `session-compaction.service.ts:20-46`（loadValidated 校验失败会 deleteIfBoundaryMatches
  删除记录并返回 null）。
- 触发链：本线程 persist 成功（persist 内部刚校验过边界消息存在）→ 该边界消息在微秒级窗口内
  被软删（编辑/重新生成/删除消息流）→ 本线程 loadValidated 判定记录 invalid 并自删成功 →
  latest=null → seq 回退为 1。若本次为第 2+ 次压缩，writeArchive 的 renameSync 会无条件覆盖
  已存在的 compaction-001.jsonl，第 1 次压缩的归档丢失。同时 latestBoundary=0 会使
  applyHistory 全量重建上下文（该行为为遗留逻辑，非本次修复引入，本次仅新增了归档覆盖这层后果）。
- 评估：需要消息删除恰好落在 persist 校验与 loadValidated 查询之间，且 DB 状态本身已异常。
- 加固方向（如需）：序号不依赖重载的 latest，改由 persist 返回本次写入行的 compact_count，
  或按 `(record?.compactCount ?? 0) + 1` 计算（CAS 获胜时语义等价）。

### I-2 本线程事件循环停顿 + 并发赢家落入重载前窗口时，归档序号取到他人序号导致同名覆盖

- 位置：同上 `session-compaction-orchestrator.ts:70-78`；`compaction-archive.service.ts:39-41`
  （同名 `.tmp` + `renameSync` 覆盖写）。
- 触发链：本线程 persist 后事件循环停顿数秒，期间并发线程（在本线程 persist 之后才 load 到
  boundary=20）完成 20→30 压缩（compactCount=3）→ 本线程重载 latest 读到他人记录 →
  以 seq=3 写归档，与并发线程的 compaction-003.jsonl 同名互相覆盖，一方区间归档丢失；
  极端交错下两线程共用同名 `.tmp`，先 rename 者把对方内容写到自己的序号名下，后者 rename
  失败（ENOENT，仅 warn）。上一轮 L-1 的"区间缺口"在该路径下转化为"同名覆盖"。
- 评估：要求本线程在两个相邻 await 之间停顿整个 LLM 压缩时长，实际不可达；加固方向同上
  （序号随 persist 返回，不依赖重载）。

### 备注：orchestrator spec 第三用例的 mock 建模偏差（非 bug）

`writesArchiveByPersistedEvenWhenAnotherThreadAdvancedBeyondCandidate` mock 的
"他人推进后的记录"为 `record(30, 2)`（compactCount=2）；现实中他人推进 20→30 会使其
compactCount=3，且该场景本身如 I-2 所述实际不可达。断言 seq=2 与 mock 自洽，仅建模简化，
不需修改。
