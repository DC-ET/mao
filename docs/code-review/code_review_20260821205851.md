## 一、轻微问题

### 1. 删除边路任务 / 晋升后，KeepAlive 缓存实例被淘汰卸载时兜底保存会使已清除的草稿"复活"残留

- **严重程度**：轻微（无用户可见功能影响，属内存 / blob URL 资源残留；违反设计 5.5 清理钩子意图）
- **位置**：
  - `desktop/src/views/task/TaskView.vue:584-591`（handleDeleteSideTask）、`600-608`（handlePromoteSideTask）
  - `desktop/src/components/chat/ChatInput.vue:1187-1196`（onBeforeUnmount 兜底 saveDraft）
  - `desktop/src/components/center/CenterTabContainer.vue:3`（`<KeepAlive :max="20">`）
- **描述**：`closeTab(tab.id)` 仅同步移除 tabs 数组项，SideChatPanel 因处于 KeepAlive 内而被 **deactivate 缓存而非立即卸载**，`draftStore.clearDraft(tab.id)` 随即同步执行并生效。但该缓存实例在之后某次缓存超限（>20）被 prune 真正卸载时，`ChatInput.onBeforeUnmount` 的兜底 `saveDraft(props.draftKey)` 会把编辑器中仍保留的旧草稿**重新写回 store**，导致已删除任务的 `side:{id}` 草稿条目复活。该键对应的任务已删除、tab 不可再打开，条目连同其持有的 `File` 引用与未 revoke 的 blob URL 永久滞留。
- **同类时序窗口**：`session.ts:993-1023` 的 `deleteSession` 中 `clearDraft('s:{id}')` 在 `await api.delete` 之后执行，若等待期间用户切走又切回该会话并再次编辑后切走，兜底保存同样会晚于收口清除（触发窗口极窄，后果相同）。
- **建议修复方向**：删除收口处不要与组件卸载兜底竞争——如将 `clearDraft` 延后到组件卸载之后（`nextTick`/`setTimeout(0)`），或为 draft store 增加"显式删除标记"语义（卸载兜底保存时跳过已被显式删除的键），或在 KeepAlive 场景改用 `onDeactivated` 保存 + 卸载时不重复保存。

### 2. 恢复草稿后组件与 store 共享数组引用，移除待发图片会 revoke 仍被草稿持有的 blob URL

- **严重程度**：轻微（边缘交互下的预览裂图，文件本体仍可正常发送）
- **位置**：`desktop/src/components/chat/ChatInput.vue:747-748`（`pendingFiles.value = d.files`、`filePreviewUrls.value = d.filePreviewUrls` 直接引用 store 内数组）、`964-970`（removePendingFileAt 中 revoke）
- **描述**：`restoreDraft` 将 store 草稿条目内部的 `files` / `filePreviewUrls` 数组引用直接赋给组件状态，此后 `removePendingFileAt` 的 `splice` 与 `URL.revokeObjectURL` 会直接作用于 store 草稿条目。用户恢复草稿后删除一张图片再切走：`saveDraft` 快照的 URL 已被 revoke，切回后该图片预览渲染为裂图（File 对象仍在，发送不受影响）。与本次设计的"URL 所有权随草稿转移，仅在没有草稿条目时 revoke"规则在删除分支上不自洽。
- **建议修复方向**：`restoreDraft` 恢复时对数组做浅拷贝（`[...d.files]` / `[...d.filePreviewUrls]`），使 store 快照与组件工作副本隔离；或 removePendingFileAt 时同步用剩余内容回写草稿。

### 3. 新建任务首发失败（保存未确认）时输入框被清空，草稿藏入 'new' 槽位对用户不可见

- **严重程度**：轻微（低频场景，数据未丢但用户感知"内容丢失"，与现状体验相悖）
- **位置**：
  - `desktop/src/components/chat/ChatPanel.vue:588-593`（`pendingNewTaskNav`：createSession 成功即 `router.replace`）
  - `desktop/src/components/chat/ChatPanel.vue:628-632`（仅 `saved` 时才 `clearDraft('new')` / `clearInput`）
  - `desktop/src/components/chat/ChatInput.vue:758-762`（draftKey watcher 的 `restoreDraft` else 分支强制清空编辑器）
- **描述**：新建任务发送后 createSession 成功即路由跳转，`currentDraftKey` 从 `'new'` 变为 `'s:{newId}'`，watcher 执行 `saveDraft('new')`（草稿入 store）+ `restoreDraft('s:{newId}')`（编辑器被清空）。若随后保存确认**失败**（上传失败 / WS 超时 60s 等），`clearDraft('new')` 与 `clearInput` 均不执行——草稿按设计"失败保留"，但保留在 store 槽位而非输入框 UI 中：用户停留在新会话页面看到空输入框，误以为内容丢失，需自行切回"新建任务"模式才能找回。改动前现状是输入框内容原样保留可立即重试，属于本次改动引入的体验回退。
- **建议修复方向**：发送失败（`saved === false`）且 `draftKeyAtSend === 'new'` 时将草稿回填到输入框（如暴露 `restoreContent` 复用撤回回填能力），或发送期间暂缓 draftKey watcher 的恢复动作（如 waitingForSave 时冻结键切换）。

### 4. 草稿空判定不含 html 字段，空文档 HTML 导致"空壳条目"残留

- **严重程度**：轻微（当前无功能影响，与 store 自身设计意图不符，条目随使用累积）
- **位置**：`desktop/src/stores/draft.ts:15-17`（`isEmptyDraft` 仅判 `text` 与 `files`）；`desktop/src/components/chat/ChatInput.vue:722-729`（buildCurrentDraft 的 `getHTML()`）、`1145-1156`（clearInput 后依赖 setDraft 空判定删条目）
- **描述**：TipTap 空文档的 `getHTML()` 返回 `<p></p>`（非空字符串）。`clearInput` 清空输入后触发键切换 / 卸载兜底 `saveDraft` 时，`isEmptyDraft` 判定为空并删除条目——主路径正确；但存在中间路径（如 1.1 中"复活"写入、或 text 为空但 html 含残留节点结构的情况）会留下 `text` 为空、`html` 非空的条目。恢复此类条目时 `setContent(d.html)` 会写入空段落，视觉为空、行为正常，但条目与设计注释"空内容写入时删除条目，避免空壳堆积"不符。
- **建议修复方向**：`isEmptyDraft` 增加 html 判空（如剥除 `<p></p>`/`<br>` 等空文档结构后为空即视为空），或 `buildCurrentDraft` 在 `text` 为空时直接将 `html` 置空字符串。

### 5. SideChatPanel 队列发送路径未显式清除草稿，与等待保存路径处理方式不一致

- **严重程度**：轻微（当前功能正确——tabId 恒定且 `clearInput` 内部按当前 `props.draftKey` 清除；属与设计 5.4 及同文件另一路径的一致性欠缺）
- **位置**：`desktop/src/components/chat/SideChatPanel.vue:527-532`（队列分支仅 `chatInputRef.value?.clearInput()`）对比 `604`、`613-618`（等待保存路径先 `draftStore.clearDraft(draftKeyAtSend)` 再 `clearInput`）
- **描述**：设计文档 5.4 要求边路发送成功路径"捕获 tabId 并显式 clearDraft（与 clearInput 幂等）"。等待保存路径已按设计实现，但队列路径（`hasRealSession && isSideActive`）遗漏了显式清除，仅依赖 `clearInput` 的内部联动。当前 `draftKey` 恒等于 `props.tabId` 且发送期间不会变化，故功能正确；但若未来 draftKey 语义调整（如占位期键与正式键演变），该路径将漏清。
- **建议修复方向**：与等待保存路径对齐，在队列分支 `clearInput()` 前补一句 `draftStore.clearDraft(props.tabId)`，消除对 clearInput 内部实现隐式依赖。

## 二、已核查无问题的关键点（供回归参考）

1. **键空间隔离**：`s:{sessionId}` / `new` / `side:{tabId}` 三类键无冲突；store 统一 `String(key)` 处理，单测有覆盖。
2. **新建任务发送成功**：`draftKeyAtSend='new'` 被显式清除；发送成功后 `clearInput` 内部清的是新会话键（no-op），最终 `'new'` 槽位正确清空，切回新建任务输入框为空（场景 3 达成）。
3. **发送等待期间切走会话**：`clearDraft(draftKeyAtSend)` 清旧槽位 + `sendGeneration` 拦截 UI 误清 + 切回时 `restoreDraft` else 分支清空编辑器，三者配合正确，场景 4 达成，且不会误清用户切回后重新输入的内容。
4. **队列发送被拦截**（上传期间切走会话触发 `requireCurrentSession` 失败）：返回 false，草稿保留，行为正确。
5. **关闭边路 tab（不删任务）**：KeepAlive deactivate 保留组件状态、不触发误存；缓存被 prune 时兜底保存，重开（重挂载）后 `onMounted restoreDraft` 正确恢复，场景 7 达成。
6. **blob URL 主路径所有权**：卸载时仍有草稿条目则不 revoke，切回预览正常；仅问题 2 所述删除分支存在例外。
7. **登出**：`draftStore.reset()` + TopNav 登出后整页 reload，无跨账号残留（场景 10 达成）。
8. **`onMounted restoreDraft` 时序**：`useEditor` 内部 onMounted 先于组件自身 onMounted 注册（FIFO），恢复时编辑器已就绪。
9. **GIT_SUGGEST_TEXT 自动填充**与草稿恢复无冲突（仅在 `editor.isEmpty` 时填充）。

## 三、总体评价

本次改动整体实现质量良好：键设计清晰、发送/切换/卸载三挂载点覆盖完整、发送目标键捕获与 `sendGeneration` 机制配合正确、单测覆盖了 store 核心语义。上述 5 个轻微问题均不影响主流程业务正确性，建议按优先级处理 **1（资源残留，违反设计清理钩子）** 与 **3（失败场景体验回退）**，其余可随手修复或择机处理。
