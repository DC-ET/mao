三份产物彼此一致，但都**早于**本轮最终源码编辑（engine.ts/controller.ts 的 mtime 为 22:46:10~22:46:14）。对产物做文本检查：

handleRequest(...){ ... this.activeSessionId!=null&&this.cancelled ... this.activeSessionId==null&&this.beginTask(n) ... }

即产物里是「中间版本」：`beginTask` 无 `invalidateSnapshot` 形参、`handleRequest` 不传 `true`、没有 `prepareNewTask`/`isCancelled`。这些文件是被 `git` 跟踪并作为宿主页面加载入口的产物（`desktop/public/embed/*.js`），因此**宿主线上实际运行的是旧逻辑**，与已通过测试的源码不一致，具体差异：

1. 每个新任务首个页面请求不会 `manager.invalidate()`（`engine.ts:95,220` 的修复缺失）→ 上一任务遗留快照仍可被复用；

### P3-1. 重连/重新绑定竞态下，在途页面请求会悬挂到后端超时，并堵住串行队列

**位置**
- `backend-ts/src/session/ws/streaming-ws-handler.ts:233-239`（`handleSubscribe`）
- `backend-ts/src/session/ws/streaming-ws-registry.ts:269-282`（`bindEmbedSession`）、`:290-295`（`getEmbedSessionConnection`）、`:306-316`（`releaseEmbedConnection`）
- `backend-ts/src/session/ws/streaming-ws-handler.ts:145-148`（`afterConnectionClosed`）

**问题**

`handleSubscribe` 只在 `getEmbedSessionConnection(sessionId)`（会校验 `readyState === WS_OPEN` 且已授权）返回一个**不同的**连接时才 `failSession`。若新连接先完成订阅、而旧 socket 的 close 事件后到（旧 socket 此时 `readyState` 已非 OPEN），则：

- `previous` 为 `null` → 不调用 `failSession`；
- `bindEmbedSession` 把该会话从旧连接的 `embedConnectionSessions` 集合中移除（`registry.ts:270-273`）；
- 旧 socket 的 `afterConnectionClosed` 再取 `getEmbedSessionsForConnection(old)` 时已为空 → 也不会 `failSession`。

结果：旧连接上在途的 `PendingEntry`（`connectionId` 指向旧 socket）无人结束，只能等 180s 超时；又因为本会话已改为串行派发，同会话后续页面请求会一起排队，表现为「页面操作长时间无响应」。SDK 侧正常重连是 `onclose`→`socket=null`→延迟 1s 重建（`ws-client.ts:212-227,275-283`），服务端 close 事件通常先到，故该竞态较窄，但真实存在。

**修复建议（任选）**
- `handleSubscribe` 判断改用原始绑定（`embedSessionBindings.get`）而非「已授权连接」，只要绑定的不是当前 socket 就先 `failSession`；
- 或让 `bindEmbedSession` 在替换绑定时主动结束旧连接上的在途请求（把 `EmbedPageToolRegistry` 依赖注入 registry，或在 `releaseEmbedConnection` 里回调）；
- 补一个「旧连接未 OPEN 时新连接 subscribe」的用例，断言旧请求被立即结束。

### P3-2. 升级授权仍会拒绝当前正在等待的确认（第 4 轮 P3-1 遗留，本轮未修）

**位置**
- `sdk/embed/src/page/authorization.ts:136-138`（`setLevel` 首行 `cancelPendingConfirmations()`）
- `sdk/embed/src/page/authorization.ts:75-90`（`cancelPendingConfirmations` 以 `false` 结束）

**问题**

确认卡片弹出时，用户点「完全授权」或「本次任务授权」（`PageActionPanel` → `applyUserPageAuthorization` → `setLevel`），`setLevel` 会先把活动确认以 `false` 结束，当前动作随即以 `authorization_denied` 失败。用户意图是放行，结果却是拒绝；需模型重试一次才成功。功能可自愈，故 P3。

**修复建议**
- 按方向区分：升级（→`task`/`full`）时以 `true` 结束或保留挂起，仅降级/`revoke`/`endTask`/身份切换时以 `false` 结束；
- 同步调整 `authorization.spec.ts` 中依赖当前行为的断言。

### P3-3. 宿主在首个任务前调用 `executePageAction` 会消费 `initialLevel:'task'`，使第一个真实任务被降级为 per_action

**位置**
- `sdk/embed/src/index.ts:67-69`（`executePageAction` 传 `store.sessionId() ?? 0`）
- `sdk/embed/src/page/engine.ts:208-210`（`ensureTask → beginTask(sessionId)`）
- `sdk/embed/src/page/authorization.ts:166-181`（`beginTask` 内 `initialTask` 一次性消费并绑定 `taskSessionId`）

**问题**

宿主按文档在会话建立前独立驱动页面操作（`inspectPage()`→`executePageAction()`，此时 `store.sessionId()` 为 `null`，传入 `0`）会触发 `beginTask(0)`：若宿主 `page.initialLevel:'task'`，则 `initialTask` 被消费、`level='task'`、`taskSessionId=0`。随后真实任务在 session N 开始，`authorization.beginTask(N)` 因 `taskSessionId(0) !== N` 而把 `task` 降级为 `per_action`。实测：

```
AFTER_HOST0      level= task        taskSessionId= 0
AFTER_AGENT_BEGIN level= per_action taskSessionId= 1
```

宿主「本次任务授权」的初始意图被提前消耗。属行为偏差，非阻断（后续动作仍可通过逐次确认完成）。

**修复建议**
- `ensureTask`/`executeAction` 在 `sessionId == null`（无会话）时不要建立任务绑定，或用一个独立的「宿主会话作用域」而不是 `0`；
- 或 `PageAuthorization.beginTask` 忽略 `sessionId <= 0` 的绑定，把 `initialTask` 留给首个真实任务。

### P3-4. 宿主单独驱动页面操作后 `pageTaskActive` 长期为真，面板常显「停止页面任务」

**位置**
- `sdk/embed/src/page/engine.ts:88-96`（`beginTask` 无条件 `onTaskStateChange(true)`）
- `sdk/embed/src/controller.ts:911-916`（`cancelPageTask` → `ws.cancel(sid)`）
- `sdk/embed/src/ui/PageActionPanel.vue`（`v-if="taskActive"` 显示停止按钮）

**问题**

宿主用公开 API 驱动页面操作时，`ensureTask` 会 `beginTask` 并置 `pageTaskActive=true`，但宿主路径不会走到 phase 终态的 `endTask()`（`controller.ts:329`），因此「停止页面任务」按钮会一直显示；点击它会 `ws.cancel(当前会话)`，可能取消一个与本次页面操作无关的正在运行的 Agent 任务。建议宿主路径不置 `taskActive`，或为宿主操作使用独立标志/独立的「停止」语义。
