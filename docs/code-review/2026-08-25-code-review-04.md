# 代码审查报告

- 审查范围：当前 Git 工作区未提交代码
- 审查重点：飞书多机器人隔离、身份绑定、长连接生命周期、私聊/群聊会话复用、@判断、回复发送、数据库字段、前后端接口
- 结论：发现功能性问题，建议修复后再验收。

## 严重问题

### [严重] 飞书会话创建传入非法 cloudProjectKey，私聊和群聊首次对话都会创建失败

- 位置：`backend-ts/src/create-app.ts:664-670`
- 代码：创建会话时传入 `` `feishu:${accountId}` `` 作为 `cloudProjectKey`，同时 `workspaceMode` 传入 `'new'`。
- 问题：`SessionService.initializeCloudWorkspace()` 在 `workspaceMode` 不是 `git`/`existing` 时仍会进入 `cloudProjectKey` 分支，并调用 `CloudWorkspaceResolver.normalizeAndValidate()`。该校验只允许字母、数字、下划线和连字符，`feishu:1` 包含冒号，必然抛出“项目名称非法”。因此不存在既有会话时，私聊和群聊均无法建立首个会话。
- 修复建议：明确使用合法且与业务隔离要求一致的项目 key（例如 `feishu-<botKey>-private-<userId>`，群聊使用合法的 `feishu-chat-...`），或在创建群/私聊专用 workspace 时直接传入已校验的绝对 workspace 路径，并为相同 key 增加并发创建保护。

### [严重] 绑定状态仓储访问了不存在的 `sys_user` 表，绑定接口在运行时会失败

- 位置：`backend-ts/src/feishu/binding.repository.ts:11,17,19`
- 代码：`SELECT ... FROM sys_user`、`UPDATE sys_user ...`。
- 问题：当前迁移和现有用户仓储使用的是 ``user`` 表（例如 `backend-ts/db/migration/V001__init_schema.sql`、`backend-ts/src/user/user.repository.ts`）。本次迁移 `V084` 也没有创建 `sys_user`。因此绑定状态、绑定、解绑接口会直接报表不存在；桌面端无法完成绑定闭环。
- 修复建议：统一使用实际用户表及其字段映射，或新增并完整迁移 `sys_user`（不建议仅在代码中兼容两套表）。同时补充接口集成测试。

### [严重] 飞书入站未做身份绑定和群成员授权，任何收到事件的用户都可以使用 Agent

- 位置：`backend-ts/src/feishu/agent-inbound-handler.ts:21-23`、`backend-ts/src/create-app.ts:663-665`、`backend-ts/src/feishu/inbound-processor.ts:26-40`
- 问题：`authorizeDirectMessage()` 无条件返回 `true`；私聊/群聊创建会话时直接通过 `userRepo.findByFeishuUserId()` 查用户，未查询 `feishu_binding`，也未维护/检查 `feishu_chat_member`。未绑定用户不会收到设计要求的绑定引导，群聊也没有“仅已绑定成员触发”的限制。
- 影响：身份绑定安全边界失效；若用户因 OAuth 登录被自动写入用户表中的 `feishu_user_id`，即可绕过显式绑定使用机器人；群聊未绑定成员可触发 Agent，且可能创建共享群会话。
- 修复建议：入站处理统一通过绑定服务按 `union_id` 查询绑定关系；私聊未绑定时只发送绑定引导；群聊先记录消息，再校验绑定及 `feishu_chat_member`，未授权时不得创建 session/workspace 或执行 Agent，并按触发机器人发送引导/拒绝回复。

## 高严重问题

### [高] 群聊 @判断只判断“存在任意 mention”，会把 @普通成员误认为 @机器人

- 位置：`backend-ts/src/feishu/inbound-processor.ts:48-51`、`backend-ts/src/feishu/event-normalizer.ts:22-24`
- 问题：默认判断为 `event.mentions.length > 0`，但没有保存或比较机器人自身的 `open_id`/mention key；文本正则也会把普通 `@用户` 当成机器人提及。结果是群内 @任意成员都可能触发 Agent。
- 修复建议：事件标准化时保留 mention 的 key/id，按当前机器人 app 的身份精确匹配；无法确认机器人身份时应按未触发处理，而不是放行。

### [高] 同一机器人/用户或机器人/群的首次并发消息可能创建重复会话并破坏映射

- 位置：`backend-ts/src/feishu/message.service.ts:16-28`、`backend-ts/src/feishu/message.repository.ts:38-48`
- 问题：`getOrCreateP2p/getOrCreateGroup` 都是先查询再创建，没有按会话维度加锁或使用原子插入。两条长连接事件并发到达时会各自创建 session，随后 `ON DUPLICATE KEY UPDATE` 将映射覆盖为后创建的 session，前一个 session 成为孤儿，消息/执行可能分叉。
- 修复建议：按 `(bot,user)` / `(bot,chat)` 加进程内锁（单实例约束下）并在数据库层采用唯一键配合“插入后读取”的原子创建策略；创建失败时重新读取已存在映射。

### [高] 配置的回复长度、群上下文窗口未生效

- 位置：`backend-ts/src/create-app.ts:713-731`、`backend-ts/src/feishu/message.service.ts:8`、`backend-ts/src/feishu/inbound-processor.ts:48`
- 问题：发送逻辑硬编码 `2000`，未使用 `cfg.feishu.bot.reply.maxLength`；`FeishuMessageService` 使用默认 `contextWindow=30`，未使用 `groupContext.maxItems` 和 `maxMinutes`，也没有时间窗口过滤。配置修改后实际行为不会改变。
- 修复建议：将配置值注入消息服务和发送器，查询同时按数量和时间条件限制，并对配置做边界校验。

## 中等问题

### [中] 飞书 OAuth 登录和“绑定”数据模型脱节，解绑无法阻止继续使用

- 位置：`backend-ts/src/auth/feishu-auth.service.ts:184-211`、`backend-ts/src/feishu/binding.repository.ts`、`backend-ts/src/feishu/binding.routes.ts:10-19`
- 问题：OAuth 成功后写入的是用户表 `feishu_user_id`，并自动创建/更新用户；`feishu_binding` 表从未写入。解绑接口只清理用户表字段，而入站又没有绑定表校验，导致绑定记录、登录身份和通道授权状态不一致，解绑语义无法可靠成立。
- 修复建议：明确区分“登录身份”和“通道绑定”，OAuth 回调根据授权 state/当前登录用户写入 `feishu_binding`，并以唯一约束原子校验 union_id 与 user_id；所有入站和解绑后的权限判断只依赖统一绑定服务。

### [中] 长连接启动失败后不会被监控重试

- 位置：`backend-ts/src/feishu/monitor.service.ts:89-96`、`backend-ts/src/feishu/long-connection.ts:25-29`
- 问题：监控把 handle 放入 `active` 后调用 `start()`；SDK `start()` 返回的 Promise 被 `void ...catch` 消化，handle 没有失败/断线状态回调。启动或后续连接永久失败时，reconcile 认为该机器人已 active，不会重新创建或重试。配置中的重连参数也没有被使用。
- 修复建议：把启动/断线/重连状态反馈给 monitor，失败时移除 active 或由 handle 内部实现可观察的重连状态；停用/删除时确保等待关闭完成，避免旧连接继续分发事件。
