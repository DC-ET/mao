## 一、高（High）

### H1. Flyway 迁移版本号冲突：新增 `V081__add_llm_model_client_impersonation.sql` 与已发布的 `V081__drop_agent_tag.sql` 版本号重复

- **位置**
  - 新增：`backend-ts/db/migration/V081__add_llm_model_client_impersonation.sql`（本次需求新增，未跟踪文件）
  - 已存在（已提交且已发版）：`backend-ts/db/migration/V081__drop_agent_tag.sql`
    - 提交记录：`a7e7917 feat(agent): 移除 Agent「标签」功能`，CHANGELOG 0.0.50 中明确记载「删除 `agent_tag` 表（Flyway V081 自动清理）」，即该迁移已在生产库执行并写入 `flyway_schema_history`。
- **问题分析**

  自研 Flyway 执行器 `backend-ts/src/db/flyway.ts` 的 `listMigrations()` 对同版本号文件不做任何去重或报错，仅按版本排序后顺序执行：

  ```ts
  // flyway.ts listMigrations() —— 同版本号会同时保留在列表中
  .sort((a, b) => compareVersions(a.version, b.version));
  ```

  生产环境 `flyway_schema_history` 中已存在 `(version='81', script='V081__drop_agent_tag.sql', success=1)` 记录。部署后执行迁移时：

  ```ts
  for (const migration of migrations) {
    if (appliedVersions.has(migration.version)) {
      continue;   // ← version '81' 已命中，新迁移被无条件跳过！
    }
    ...
  }
  ```

  由于判断依据是 **version 字符串 `'81'`** 而非 script 文件名，新迁移 `V081__add_llm_model_client_impersonation.sql` 会被判定为"已应用"而直接跳过——**`client_impersonation` 列永远不会被创建**。

- **故障表现（连锁后果）**

  随后任何读写该列的 SQL 都将抛出 MySQL `Unknown column 'client_impersonation' in ...` 错误：
  - 管理后台模型列表页加载失败（`SELECT *` 虽不报错，但 insert/update 会失败）：新增/编辑模型接口 500；
  - 所有 LLM 调用出口的模型查询虽不受影响，但只要触发一次模型保存（如后台编辑任意字段），`updateById` 携带 `clientImpersonation` 字段即报错；
  - 更严重的是：仓库中两个 V081 文件的执行顺序取决于 `readdirSync()` 目录序，在**全新环境**（空库）上，若先执行 `add_llm_model...` 再执行 `drop_agent_tag`，两条都能成功；但若目录序相反也无影响——真正的破坏发生在存量生产库（跳过）。此外 `validateOnMigrate=false` 掩盖了校验告警，无 checksum 冲突拦截。
  
  > 补充验证：本机 `fs.readdirSync` 实测返回顺序为 `V081__add_...` 在前、`V081__drop_agent_tag` 在后，说明全新环境两条均会执行成功；**风险集中在已升级到 ≥0.0.50 的存量数据库**，即当前生产环境 `/opt/mao/backend-ts/.env` 已开启 `FLYWAY_ENABLED=true`。

- **修复建议**

  将新迁移重命名为下一个未占用版本号（如 `V083__add_llm_model_client_impersonation.sql`，注意 `V082__weixin_session_peer.sql` 已占用 82），SQL 内容不变。同时在 `listMigrations()` 增加同版本号重复检测（fail-fast）以防再次发生。

## 二、低（Low）

### L1. `openai-llm-adapter.ts` 残留未使用的 `randomUUID` 导入

- **位置**：`backend-ts/src/harness/llm/openai-llm-adapter.ts:3`

  ```ts
  import { randomUUID } from 'node:crypto';  // 硬编码删除后已无引用
  ```

- **影响**：伪装头逻辑迁出后遗留的死代码。因 tsconfig 未开启 `noUnusedLocals`，tsc 不报错，不影响运行时行为，仅损害可维护性。
- **建议**：删除该导入行。

### L2. `domain/types.ts` 的 `LlmModel` 接口缺失 `clientImpersonation` 字段（类型声明滞后于运行时行为）

- **位置**：`backend-ts/src/domain/types.ts:66-78`（`LlmModel` 接口）；消费方 `backend-ts/src/session/session-title.service.ts:166`

- **现象**：`session-title.service` 通过 `modelLookup.selectById()/selectDefault()` 查询模型（实际由 `MysqlLlmModelRepository.findById/findDefault` 提供，返回行经 `toCamelList` 自动映射后**运行时携带 `clientImpersonation` 字段**），再调用 `llmModelToConfig(model)` 注入配置。但该处 `LlmModel` 类型定义（`domain/types.ts`）没有 `clientImpersonation?: string | null` 声明，导致 `llmModelToConfig` 从该类型视角读不到该字段——标题生成链路的伪装头配置实际上依赖"DB 层多返回了字段 + 函数内部宽松访问"这一巧合而非类型保障。本次改动为 `harness/deps.ts` 的 `LlmModel`、`session/types.ts` 的 `LlmModelRef`、`model/types.ts` 的 `LlmModel` 都补了字段，唯独漏掉了 `domain/types.ts` 这一份同名接口。

- **影响**：当前运行时行为碰巧正确（`SELECT *` + camelCase 映射确实带出了值，标题生成能按配置注入伪装头），因此不是功能性 bug；但这是三份重复的 `LlmModel` 类型中唯一未同步的一份，后续任何人以 `domain/types.ts` 的 `LlmModel` 为准重构时，伪装头配置会被静默丢弃。
- **建议**：为 `domain/types.ts` 的 `LlmModel` 接口补充 `clientImpersonation?: string | null;`，与其他两份保持一致。
