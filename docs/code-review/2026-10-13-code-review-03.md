## BUG-1 文件搜索工具的 activity 类型映射用了改名前的死标签（backend-ts，P3）

**位置**
- `backend-ts/src/session/activity/activity-type-mapper.ts:13-14`（`case 'glob': case 'list':` → `'EXPLORE'`）
- 上游写入：`backend-ts/src/session/ws/ws-streaming-event-listener.ts:297`（`const activityType = mapToolToType(toolName)`）
- 下游消费：`backend-ts/src/admin/admin-analytics.service.ts:631-639`（`selectRunTraceToolFailureRates` 对 `session_activity` 按 `type` 分组，喂管理后台「工具失败率」排行）

**关键代码**

```ts
// activity-type-mapper.ts:5-23
switch (toolName.toLowerCase()) {
  ...
  case 'glob':      // ← 注册表里没有叫 glob 的工具
  case 'list':      // ← 注册表里没有叫 list 的工具
    return 'EXPLORE';
  default:
    return 'TOOL';
}
```

**根因**：内置工具的真实名称是 `glob_search` 与 `grep_search`（`harness/tool/impl/glob-search-tool.ts:24`、`grep-search-tool.ts:23` 的 `getName()`），全仓 grep 确认不存在名为 `glob` / `list` 的已注册工具。两个 `case` 标签是工具改名前的残留，`EXPLORE` 分支对真实调用永不可达。同一文件里的 `read_file` / `write_file` / `edit_file` / `shell` / `task_*` 都与现行工具名一致，说明只有搜索类漏改；其他按工具名分发的模块（`session/util/tool-result-summarizer.ts`、`desktop/src/utils/toolDisplay.ts`）用的都是新名字。

**触发场景**：用户让 Agent「找一下所有的测试文件」→ LLM 调 `glob_search` → `session_activity.type` 落 `TOOL` 而非 `EXPLORE`。管理后台「工具失败率」按 `type` 聚合时，所有文件/内容搜索活动被并进 `TOOL` 桶，搜索类的次数与失败率统计被稀释（用户侧无直接可见异常，属统计口径失真）。

**验证用例**（`backend-ts/src/session/activity/zz-logicbug-probe.spec.ts`，纯函数，4 条断言 3 败 1 过）：`glob_search` / `grep_search` / 大小写变体断言归 `EXPLORE` 均失败（实际返回 `TOOL`）；`read_file` / `write_file` / `edit_file` / `shell` / `task_create` / `unknown_tool` / `null` 的回归护栏全过，证明只有搜索类标签过时。

**建议修复**：把 `case 'glob': case 'list':` 改成 `case 'glob_search': case 'grep_search':`（已反向验证，改后 4/4 转绿）。若担心历史 `session_activity` 存量行，可只改映射不改存量——类型仅用于聚合展示，无需数据迁移。

## BUG-2 钉钉同 Client ID 判重只标记失败、不摘旧连接，旧 Stream 永久泄漏（backend-ts，P2）

**位置**
- `backend-ts/src/dingtalk/monitor.service.ts:188-191`（`seenClientIds.has(bot.clientId)` 分支）
- 关联：`MysqlDingtalkBotRepository.list()` 是 `ORDER BY created_at DESC`（`dingtalk/bot.repository.ts:9`），新 bot 永远排在旧 bot 前面，使下述顺序必然成立

**关键代码**

```ts
// monitor.service.ts:181-196
const seenClientIds = new Set<string>();
for (const bot of bots) {
  ...
  if (seenClientIds.has(bot.clientId)) {
    console.warn(`钉钉同一 Client ID 只保留一条 Stream, 跳过 id=${bot.id}, clientId=${bot.clientId}`);
    this.mark(bot.id, { status: 'failed', ... });
    continue;                       // ← 只标记，不停旧连接
  }
  seenClientIds.add(bot.clientId);
  if (this.active.has(bot.id)) continue;
  this.launch(bot);
}
```

**根因**：循环第一段（`:173-180`）只会停掉「被禁用」或「指纹变化」的 entry。旧 bot 仍然 enabled、`clientId:clientSecret:robotCode` 未变，指纹相同，永远进不了停止分支。而判重分支又只 `mark` + `continue`，不调 `entry.handle.stop()`、不 `this.active.delete()`。于是旧 bot 的 `DWClient` socket 与 handle 一直活在 `active` 表里，每一轮 `reconcile` 都原样放过，直到进程重启。代码注释与日志宣称的不变式（「同一 Client ID 只保留一条 Stream」）与实现不符。

**触发场景**：Bot A（clientId=X）已启用并 connected；管理员在后台再建一条 Bot B（clientId 同样填 X）。下一轮 reconcile：B 排在前（`created_at DESC`）先抢到 X 并 launch，A 落到判重分支被标 `failed` 但 socket 不断。此后同一 clientId 上同时有两条长连接在收消息——钉钉侧同一账号的 Stream 会话互踢会导致消息随机分发到其中一条，A 的入站消息可能被丢弃或重复；A 的状态又显示 `failed`，排障时完全看不出来。

**验证用例**（`backend-ts/src/dingtalk/zz-logicbug-probe.spec.ts`，真实 `DingtalkMonitorService` + 假 repository / 假 StreamClient）：先用假时钟让 bot 1 连上并 `ready`，再把 repository 返回值换成 `[新bot2, 旧bot1]` 并推进一个 reconcile 周期。断言 `clients[0].disconnect` 已被调用、`getStatus(1).status === 'failed'`、存活连接数为 1。当前代码下 `expected "spy" to be called at least once` 失败——旧连接从未被断开。

**建议修复**：判重分支在 `continue` 之前，按 `clientId` 从 `this.active` 里找出仍持有该连接的 entry，执行 `clearRetryTimer()` + `handle.stop()` + `this.active.delete(id)`（已反向验证转绿）。

## BUG-3 钉钉重连退避计数被每次 launch 清零，指数退避与两个配置项全是死代码（backend-ts，P2）

**位置**
- `backend-ts/src/dingtalk/monitor.service.ts:207`（`let failureCount = 0;` 在 `launch()` 内）
- `:218-241`（`onFailure` 里计算 `delay` 并只武装一次 `retryTimer`，到点后 `this.active.delete()` + `void this.reconcile()` → 重新走 `launch()`）
- 配置项 `reconnectMaxMs` / `maxConsecutiveFailures`（`DingtalkMonitorConfig`）因此完全失效

**关键代码**

```ts
private launch(bot: DingtalkBot): void {
  try {
    let failureCount = 0;                       // ← 每次 launch 都归零
    ...
    onFailure: (error) => {
      failureCount += 1;                        // 最多到 1
      if (failureCount > this.config.maxConsecutiveFailures) { ... }   // 不可达
      const delay = Math.min(this.config.reconnectMaxMs,
                             this.config.reconnectBaseMs * 2 ** (failureCount - 1));  // 恒为 base
      if (retryTimer == null) {
        retryTimer = setTimeout(() => {
          retryTimer = null;
          this.active.delete(bot.id!);          // ← 丢掉整个 entry（含退避上下文）
          void this.reconcile();                // ← 重新 launch，failureCount 回到 0
        }, delay);
      }
    },
```

**根因**：退避上下文（`failureCount`）的生命周期是「一次 `launch`」，而重连动作的生命周期是「跨多次 `launch`」——`onFailure` 到点后删 entry 并靠 `reconcile()` 重新 `launch()`，新 closure 里 `failureCount` 又是 0。因此 `failureCount` 对任何 handle 都不会超过 1，`2 ** (failureCount - 1)` 恒等于 1，`reconnectMaxMs` 的 `Math.min` 恒不生效，`failureCount > maxConsecutiveFailures` 分支不可达。

**触发场景**：钉钉 Stream 服务端不可用 / clientSecret 配错 / 网络分区。期望按 `reconnectBaseMs → 2× → 4× …` 退避并在 `maxConsecutiveFailures` 后收敛；实际恒定每 `reconnectBaseMs` 重连一次，故障期间对钉钉端点形成固定频率的重连风暴（配 `reconnectBaseMs=1s` 时即每秒一次，直到人工介入）。

**验证用例**（`backend-ts/src/dingtalk/zz-logicbug-probe.spec.ts`，假时钟 + 永远 reject 的 `connect()`，`reconnectBaseMs=1000`、`maxConsecutiveFailures=10` 以单独考察退避曲线）：在 `repository.list` 里打时间戳，推进 20s 虚拟时间后取相邻两次 reconcile 的间隔。当前代码下 `expected 1000 to be greater than 1000` 失败——间隔恒定 1000ms，不递增。

**建议修复**：把 `failureCount` 提升为按 botId 常驻的状态（如 service 上的 `Map<number, number>`），`onReady` 时清零、`onFailure` 时自增并回写，使退避跨 `launch` 保留（已反向验证转绿）。

## BUG-4 文件树「重试」按钮是空操作：拿到的是非目录占位节点，expandDir 首行即 return（desktop，P2）

**位置**
- `desktop/src/components/file-browser/FileTree.vue:722-725`（`handleRetry`）
- `desktop/src/components/file-browser/FileTreeNode.vue:44-46`（错误行与 `$emit('retry', node)`）
- `desktop/src/composables/useFileBrowser.ts:41,46`（`loadChildren` 失败时造占位节点）、`:81`（`expandDir` 首行守卫）

**关键代码**

```ts
// useFileBrowser.ts:40-47（loadChildren 失败分支）
if (result.error) {
  node.children = [{ name: '', path: node.path, isDirectory: false, error: result.error }];
}
// useFileBrowser.ts:80-81（expandDir 首行）
async function expandDir(node: FileNode) {
  if (!provider.value || !node.isDirectory || node.isSymlink) return   // ← 占位节点 isDirectory:false，直接返回
```

```vue
<!-- FileTreeNode.vue:44-46 -->
<div v-if="node.error" class="node-error">
  <span>{{ node.error }}</span>
  <button class="retry-btn" @click.stop="$emit('retry', node)">重试</button>
</div>
```

```ts
// FileTree.vue:722-725（handleRetry）
node.error = undefined
node.children = undefined
expandDir(node)        // ← node 是上面的占位节点，空操作
```

**根因**：`loadChildren` 失败时生成的占位错误节点 `isDirectory: false`、`path` 指向失败的那个目录。`FileTreeNode` 把这个节点原样 emit 给 `handleRetry`，后者清掉 `error`/`children` 后调用 `expandDir(node)`，而 `expandDir` 第一行就因 `!node.isDirectory` 返回。净效果：错误文案被抹掉、留下一行空白节点，**没有任何新的列举请求发出**。同一根因的次生症状：点错误行本身（非按钮）会走 `handleClick` → 非目录 → `emit('open-file', { path: <目录路径> })`，把目录当文件打开成页签。该问题自功能引入（`32cfe145`）起就存在，占位节点的形状一直是 `isDirectory: false`。唯一可用的恢复手段是工具栏的刷新按钮（`refresh()` 走 `loadRoot`，不受该守卫影响）。

**触发场景**：文件树（右侧栏或文件管理页）中某个目录列举失败——CLOUD 模式下 `/files/workspace-directory` 网络抖动或 500，或 LOCAL 模式下目录权限不足。目录下出现一行错误文案和「重试」按钮，用户点「重试」，错误行变成空白行，目录依然列不出来，反复点击无效。

**验证用例**（`desktop/src/components/file-browser/zz-logicbug-probe.test.ts`，真实 `useFileBrowser` + 假 provider；`handleRetry` 是组件内联函数未导出，探针逐行复刻其函数体并注明出处）：
- 根列举失败 → `treeData[0]` 是 `isDirectory:false` 的占位节点；复刻 `handleRetry` 后 `listDirectory` 调用次数不增（`expected 1 to be greater than 1` 失败）
- 子目录 `src` 列举失败 → 占位节点 `path === 'src'` 且 `isDirectory === false`；复刻 `handleRetry` 后 `src` 仍只被请求过 1 次（`expected 1 to be 2` 失败）
- 对照组：同一 provider 走 `refresh()` 能正常重拉（通过），排除 provider 本身坏掉
- 正向对照：用真实 `findNodeByPath` 按 `path` 找回真正的目录节点再 `expandDir`，`src` 被请求 2 次（通过）——证明修复方向成立且只需动 `handleRetry`

**建议修复**：`handleRetry` 里先分辨节点类型——`node.isDirectory` 为假时用 `findNodeByPath(treeData.value, node.path)` 找回真实目录节点（`useFileBrowser` 已导出该函数，补进 `FileTree` 的解构即可），再清 `error`/`children` 并 `expandDir(target)`；找不到时回落到整树 `refresh()`。顺带在 `FileTreeNode` 的错误行点击分支里排除 `emit('open-file')`，避免把目录当文件打开。

## BUG-5 本地 Git 提交失败时具体原因被丢弃，用户只看到笼统的「Git 操作失败」（desktop，P2）

**位置**
- `desktop/src/composables/workspace-git-provider.ts:148`（`if (changes.error) return failedOperation('commit', changes.error)`）
- 同文件 `:82-88`（`failedOperation` 只对 `Error` 实例保留 message）
- 类型来源：`desktop/src/types/electron.d.ts:96`（`GitCommitGenerationInput.error?: string`）
- 生产来源：`desktop/electron/gitOperations.cjs:174-180`（`buildCommitInput` 在 `resolveRepository` 抛错时 `return { error: error.message }`）
- 展示处：`desktop/src/components/task/TaskInspector.vue:537`（`ElMessage.error(result.error || 'Git 操作失败')`）

**关键代码**

```ts
// workspace-git-provider.ts:148
const changes = await window.electronAPI.gitCommitInput(workspace, repoPath)
if (changes.error) return failedOperation('commit', changes.error)   // ← 传的是 string

// workspace-git-provider.ts:82-88
function failedOperation(operation, error: unknown): GitOperationResult {
  return {
    success: false,
    operation,
    error: error instanceof Error ? error.message : 'Git 操作失败',   // ← string 走 else 分支
  };
}
```

**根因**：`gitCommitInput` 的失败契约是「返回对象带 `error?: string`」，而 `failedOperation` 的保留条件是 `error instanceof Error`。字符串不满足该条件，具体原因（「当前工作区不是 Git 仓库」「目录不存在」等）被替换成通用文案。同一函数内其余失败路径都传 `catch (e)` 拿到的 `Error` 实例，因此只有这一处静默丢消息。

**触发场景**：LOCAL 模式、Git 面板，工作区目录被外部删除/移动，或多仓库模式下选中的子仓库被外部删除。点「提交」后只弹「Git 操作失败」，用户无法判断是仓库不存在、目录被删还是别的问题，只能逐个人工排查。附带一处不一致：该早退路径跳过了 `recordLocalActivity`，其他失败路径都会记审计。

**验证用例**（`desktop/src/composables/zz-logicbug-probe.test.ts`，真实 `createLocalGitProvider` + 假 `window.electronAPI`）：mock `gitCommitInput` 分别返回 `{ error: '当前工作区不是 Git 仓库' }` 与 `{ error: '目录不存在' }`（含多仓库 `commit('sub-repo')`），断言 `result.error` 等于原文。当前代码下两条均 `expected 'Git 操作失败' to be '当前工作区不是 Git 仓库'` / `'目录不存在'` 失败。

**建议修复**：`failedOperation('commit', new Error(changes.error))`（已反向验证 2/2 转绿）；或把 `failedOperation` 改成同时接受字符串。建议同时让该早退路径也走一次 `recordLocalActivity`，与其他失败路径对齐。

## BUG-6 定时任务「上次执行」漏了 CANCELLED 汉化，取消过的任务显示「-」（desktop，P3）

**位置**
- `desktop/src/composables/useScheduledTasks.ts:158-166`（`statusLabel` 的 switch 无 `CANCELLED`）
- 同文件 `:131-143`（`runBadge` 有 `case 'CANCELLED': return '取消'`）
- 后端确实会落该状态：`backend-ts/src/schedule/scheduled-task.service.ts:708`（`markTaskResult(task, actualPhase)`，`actualPhase === 'CANCELLED'`）、`:907`（`settleQueuedExecution` 的 `lastExecutionStatus: status`，`status` 含 `'CANCELLED'`）、`:1136`；入口 `backend-ts/src/create-app.ts:1456-1459`（`onScheduledTaskQueueConsumed`）

**关键代码**

```ts
// useScheduledTasks.ts:158-166
function statusLabel(status: string): string {
  switch (status) {
    case 'COMPLETED': return '成功'
    case 'FAILED':    return '失败'
    case 'SKIPPED':   return '跳过'
    case 'QUEUED':    return '排队中'
    default:          return '-'        // ← CANCELLED 落到这里
  }
}
```

**根因**：后端 `lastExecutionStatus` 的取值集合包含 `CANCELLED`（用户取消执行中的会话，或排队执行因会话消失/超时未消费被结算为 CANCELLED），`statusLabel` 的 switch 没有对应分支，落到 `default` 返回 `-`。同文件的 `runBadge`（执行历史行）对同一状态返回「取消」，两个格式化函数口径不一致；`ScheduledTaskPanel.vue` 里也没有 `.exec-cancelled` 样式规则，印证该状态从未被考虑过。

**触发场景**：定时任务的运行被用户取消（在会话里点停止，或排队中的执行被取消）。任务列表中该任务的「上次执行」一列显示 `-`，与「从未执行过」无法区分；而展开执行历史看到的却是「取消」。

**验证用例**（`desktop/src/composables/zz-logicbug-probe.test.ts`，真实 `useScheduledTasks`）：`statusLabel('CANCELLED')` 断言为「取消」失败（实际 `-`）；`statusLabel('CANCELLED') === runBadge({ status: 'CANCELLED' })` 一致性断言失败；`COMPLETED` / `FAILED` / `SKIPPED` / `QUEUED` 回归护栏通过。

**建议修复**：`statusLabel` 补 `case 'CANCELLED': return '取消'`（已反向验证 3/3 转绿）。建议顺手把 `MISSED` / `RUNNING` 也补上，与 `runBadge` 的集合对齐，避免同类遗漏。
