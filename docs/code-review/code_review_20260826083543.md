- 审查范围：当前 Git 工作区未提交代码

- 结论：发现 1 个中等严重度的功能问题。未修改业务代码。

## 中严重度

### [中] 终态卡片更新成功后仍会额外发送一条纯文本回复

**位置**：
- `backend-ts/src/feishu/agent-inbound-handler.ts:111-114`
- `backend-ts/src/feishu/inbound-processor.ts:39-40、72-73`

成功路径在卡片 `complete(text)` 成功后仍返回 `{ text }`。`FeishuInboundProcessor` 收到该返回值后，无条件调用 `sendReply`，因此一次用户请求会先发送处理中卡片，终态 patch 卡片，再发送一条普通文本答案。失败/取消时的返回值也会由 processor 发送文本，这是兜底所需；但成功更新卡片时不应再发送普通文本，否则会造成重复消息，并使“卡片作为回复载体、更新失败才走纯文本兜底”的生命周期失效。

当前生产组装未传入 `onReply`，所以这里的返回值确实会进入 processor 的普通文本发送分支，并非仅测试回调造成的表象。

**修复建议**：为 handler 返回值区分“已通过卡片完成回复”和“需要普通文本发送”的状态，或在成功终态更新后返回 `null`；仅当终态 `complete/fail/cancel` 更新返回 `false` 时返回纯文本兜底内容。若保留 `onReply` 作为发送出口，应同时避免 processor 再次发送，防止双发。

## 已核验未发现问题

- **初始卡片失败不阻断 Agent**：`createProgressCard` 在独立 `try/catch` 内执行，发送失败时继续执行 Agent；监听器为空时最终返回普通文本。
- **终态更新失败可触发兜底**：`FeishuCardProgressListener.safeUpdate` 吞掉 patch 异常并返回 `false`；成功路径、失败路径和取消路径均根据该结果返回文本，processor 随后可发送纯文本。建议补充 handler 层回归测试确认该链路。
- **round/toolcall 更新**：每次 `onMessageEnd` 捕获当前内容和工具摘要后排队更新，再清空本轮状态；工具结果按 `toolCallId` 归属，乱序结果不会串工具。
- **更新频率与并发**：监听器通过 Promise 串行化更新；单卡片 patch 之间至少等待 250ms，未见同卡片并发 patch 或按 delta 高频更新。
- **群聊/私聊参数**：群聊有 `messageId` 时使用 `message.reply`，否则以 `chat_id` 创建；私聊以 `open_id` 创建；与当前入站上下文字段及普通文本发送逻辑一致。
- **卡片大小**：正文截断 6000 字符，工具区域截断 3000 字符，未发现明显的无界增长或因单轮内容导致的超大 payload 问题。
