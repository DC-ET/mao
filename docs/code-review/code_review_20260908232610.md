## P2

### P2-1. 断线只拒绝确认，不中止在途动作/批量；`task`/`full` 下剩余动作继续执行，且重连后的新请求可与旧批次并发

**位置**
- `sdk/embed/src/controller.ts:273-281`（`onDisconnected` 只 `clearLlmRetry` / `pauseSaveTimeouts` / `rejectPendingConfirmations`，不置取消态）
- `sdk/embed/src/page/engine.ts:145-147`、`:199-207`（`executeBatch` 的 `shouldAbort: () => this.cancelled`）
- `sdk/embed/src/page/executor.ts:142-186`（批量循环仅以 `shouldAbort` 判断是否中断；`wait`/`scroll` 不进入确认分支）
- `backend-ts/src/harness/embed-page-tool-registry.ts:108-124`（`failSession` 删除 `pending` 与 `queues`，立即释放该会话的串行队列）
- `sdk/embed/src/controller.ts:930-950`（`pageToolInFlight` 仅按 `requestId` 去重，不同 `requestId` 可并发执行）

**问题**

断线时后端 `afterConnectionClosed → failSession(sessionId, ..., 'embed_client_not_connected')` 已把该会话在途页面工具结束并清空队列；但同一标签页里的 `PageEngine.cancelled` 仍为 `false`。于是：

1. `task`/`full` 授权下（无需确认）已在执行的 `page_actions` 批量，会继续执行剩余动作；含 `wait`/`scroll` 的批量尤其明显（`wait` 最长 10s，期间断线）。
2. 即使 `per_action`，不含确认的动作（`scroll`/`wait`）也会继续。
3. 后端 `failSession` 清空队列后，模型重试会生成新 `requestId`，`dispatch` 立即下发；此时旧批次仍在浏览器里跑，两个 `requestId` 的 `pageToolInFlight` 不冲突 → **旧批次与新请求并发执行 DOM 动作**。

**复现（task/full）**

1. 用户授予「完全授权」；
2. 模型调用 `page_actions`，`actions = [click(提交), wait 3000, click(确认)]`；
3. SDK 执行第一个 `click` 后进入 `wait 3000ms`；
4. 此刻 WS 断线：`onDisconnected → rejectPendingConfirmations()` 无等待确认，属 no-op；后端 `failSession` 结束该请求并清空队列；
5. `executeBatch` 的 `shouldAbort()` 仍返回 `false` → 继续执行 `click(确认)`；
6. 模型收到 `embed_client_not_connected` 后重试同一批动作（新 `requestId`），重连后 SDK 立即执行新请求，与仍在跑的旧批次并发 → 提交/确认类动作可能执行两遍。

**影响**：与设计 4.3「会话断开时停止任务」不符；提交、删除、支付类动作可能重复执行，且旧批次的结果因后端 entry 已删除而被 `complete()` 丢弃，会话记录与页面实际状态不一致。

**建议（二选一，推荐 A）**
- A：给页面请求引入「可中止的在途信号」（如自增 `requestGeneration`），`onDisconnected` 时 `abortInFlight()`（把当前代次标记为已中止，`shouldAbort` 读取该代次；同时 `rejectPendingConfirmations()`）。新一轮请求（`handleRequest` 入口）开始时递增代次并复位，从而**只中止旧批次、不误杀断线后的重试**。注意不能简单地在断线时置 `pageEngine.cancelled = true`：`prepareNewTask()` 只在用户 `send()` 时复位，重连后模型直接重试会被误拒为 `task_cancelled`。
- B：后端在 `failSession` 的 payload 增加 `retryable:false` 与「该操作可能已在页面执行，请先用 `page_inspect` 确认状态」文案，抑制模型直接重放点击类动作；同时 SDK 侧仍需对旧批次做中止（否则并发问题依旧存在）。

## P3 / 备注（不阻塞）

### P3-1. `task` 授权下发送未遮罩截图仍逐次确认，与设计口径不一致（过度收紧）

**位置**：`sdk/embed/src/page/engine.ts:161-170`

`page_screenshot { maskSensitive:false }` 时，只要不是 `full` 就 `requestConfirmation`。而设计 7.1 明确「task：在本次任务授权范围内允许」，6.3 只要求「per_action 下发送原图必须显示确认」。当前在 `task` 下也弹确认卡片，且与 `shouldRedactSensitive`（task 下 `page_inspect` 不脱敏）口径不一致。功能安全但行为偏离设计。

**建议**：`if (this.authorization.current === 'per_action' && options.maskSensitive === false)` 才弹确认；`task`/`full` 直接按 `maskSensitive` 取值。

### P3-2. `executeFill` 的 `blur` 事件几乎不会派发，依赖 blur 提交的表单可能「回读成功但未提交」

**位置**：`sdk/embed/src/page/executor.ts:268-285`、`sdk/embed/src/page/framework-events.ts:51-56`

`executeFill` 不先聚焦元素，而 `dispatchBlur` 有 `if (document.activeElement !== el) return;`。因此单动作 `page_fill` 时元素通常不是 `activeElement`，`blur`/`focusout` 不会派发。设计 6.5 要求 fill「触发 input、change、blur」。对于「失焦才提交/校验」的表单，`el.value` 回读一致会返回 `success:true`，但业务状态未提交。

**建议**：fill 前 `el.focus()` 后再 `dispatchBlur`（或在 fill 分支无条件派发 `blur`/`focusout`），并补一条「无焦点输入框 fill 也派发 blur」的用例。

### P3-3. `page_observe` 的 `changes.updated` 恒为 0

**位置**：`sdk/embed/src/page/snapshot-manager.ts:158-168`

`observe()` 只统计 `added`/`removed`，`updated: 0` 写死。设计 6.6 要求返回「新增/移除/更新的交互元素数量」。Agent 依据该字段判断页面变化时，值变化但元素数量不变的场景会被误判为「无更新」。

**建议**：按 `signature` 对齐前后快照，统计签名相同但 `value/checked/disabled` 等状态不同的元素数（或至少在注释中明确当前不支持 updated）。

### P3-4. `page_select` 仅支持单值，`multiple` select 会被覆盖为单值

**位置**：`sdk/embed/src/page/executor.ts:290-310`

`executeSelect` 用 `HTMLSelectElement.prototype.value` setter 写入单个 `value`，对 `multiple` select 会清掉其它已选项。设计 3.1 第 9 条包含「多选项」。当前工具 schema 也只有单个 `value`，属能力缺口。

**建议**：工具参数改为 `value` 或 `values: string[]`，对 `multiple` select 逐个设置 `option.selected` 并派发 `input/change`，回读校验集合。

### P3-5（第 8 轮 P3-1 遗留，未修）. `setLevel('task', null, true)` 在会话校验前放行等待中的确认

**位置**：`sdk/embed/src/page/authorization.ts:158-164`

`setLevel` 先 `approvePendingConfirmations()`，再判断 `level === 'task' && sessionId == null` 退回 `per_action`。当 `store.sessionId()` 为 null（身份切换窗口/残留帧）而确认卡片已弹出时，用户点「本次任务授权」会出现「动作被放行、级别却显示每次确认」。触发概率低，列此备查。建议把 `approvePendingConfirmations()` 移到 `sessionId` 校验通过之后。
