# 代码审查报告：5 个关键 BUG（2026-08-21）

审查范围：backend-ts 全部核心域（harness 引擎、session、WS、file、skill、mcp、weixin、auth）、desktop（Vue + Electron 主进程/preload）、agent-cli、android 原生插件。以下 5 个 BUG 均经过交叉验证（调用方 + spec + 同类端点对照），非风格问题。

---

## BUG #1：diff 私有字段名不一致 → 文件全文经 WS 泄漏 + 前端实时 diff 失效

**位置**：`backend-ts/src/session/ws/ws-streaming-event-listener.ts:30` vs `backend-ts/src/harness/tool/file-change-diff-util.ts:1`

**成因**：两处各自定义了同名常量但值不同：

- 写入方 `file-change-diff-util.ts:1`：`PRIVATE_DIFF_FIELD = 'file_change_diff'`（write-file-tool.ts:67、edit-file-tool.ts:89 用它把 diff 写进工具结果 JSON）
- 消费方 `ws-streaming-event-listener.ts:30`：`PRIVATE_DIFF_FIELD = '_private_diff'`

后果链（ws-streaming-event-listener.ts:206、221-222）：
1. `resultNode['_private_diff']` 读取永远是 `undefined` → `file_change` WS 事件丢失 `diff_mode/before_content/after_content/patch_content`，前端实时 diff 视图拿不到数据；
2. 本地 `stripPrivateDiff` 删 `'_private_diff'` 删不掉 → `tool_call_result` 事件把完整 `file_change_diff`（SNAPSHOT 模式含**前后全文**，单侧上限 512KB）推给所有订阅该会话的客户端。

**触发路径**：CLOUD 模式任意 write_file/edit_file 调用 → AgentLoop → listener 推流。注意 agent-loop.ts:468 用的是 FileChangeDiffUtil 的正确剥离，所以**持久化到 DB 的消息已剥离，泄漏仅发生在 WS 实时路径**——这正是它难以被功能测试发现的原因。

**佐证**：测试自洽地错——`ws-streaming-event-listener.spec.ts:67` 用 `'_private_diff'` 构造数据（测试绿），而 `file-change-diff-util.spec.ts:38`、`harness-service.spec.ts:305` 用 `'file_change_diff'`。

## BUG #2：删除运行中会话无任何守卫 → 孤儿执行 + 删掉正在使用的文件

**位置**：`backend-ts/src/session/session.routes.ts:236-240`、`backend-ts/src/session/session.service.ts:394-414`、`backend-ts/src/harness/core/agent-loop.ts:102-110`

**成因**：`DELETE /v1/sessions/:id` 只做 `requireSessionOwner` 归属校验，`deleteSession` 直接 `lockActiveSessionById`（只加锁不检查 phase）后级联删除消息、清理 runtime incoming 目录、`rm` 工作区内 `mao-runtime-*` 文件。**对 RUNNING/WAITING_APPROVAL 状态的会话照删不误**。

**后果**：
1. AgentLoop 每轮循环用 `isTerminalPhaseInDb` 检查取消标志，`getSession` 抛 SESSION_NOT_FOUND 后 `agent-loop.ts:107` 的 `catch { return false }` 把"会话已删除"当成"未取消"→ **执行继续跑**；
2. 执行结束 `taskTerminalService.finishExecution` 内 `getSession` 再抛异常 → 用户收到 error 事件，会话状态永久不一致；
3. Agent 正在写入的工作区 runtime 文件被 `deleteRuntimeWorkspaceFiles` 删掉，产生写入竞态。

**对照证据**：同文件 `promoteSideTaskToMainSession` 对 RUNNING/WAITING_APPROVAL/RESUMING/CANCELLING 有完整 phase 拒绝守卫，说明删除缺守卫是疏漏而非设计。

## BUG #3：用户技能删除接口路径穿越 → 任意目录递归删除（服务端 RCE 级破坏）

**位置**：`backend-ts/src/skill/skill.routes.ts:80-84` → `backend-ts/src/skill/user-skill.service.ts:163-176`

**成因**：`DELETE /v1/user-skills/:name` 的 `name` 经 `pathParam`（common/request.ts:15-17，原样透传无任何清洗）进入 `deleteUserSkill`，直接 `join(getUserSkillsDir(userId), name)` 后 `rmSync(skillFolder, { recursive: true, force: true })`。**没有 `..` 检查、没有 resolve 后前缀校验**。

**触发路径**：任意登录用户 `DELETE /api/v1/user-skills/..%2F..%2F..%2Fopt%2Fmao%2Fdata`（Fastify 默认解码 URI 组件）→ `join('/opt/mao/data/skills/<uid>', '../../../opt/mao/data')` → 递归强删服务器任意可写目录。同样问题存在于 `getUserSkill`（user-skill.service.ts:62-64，任意文件读取，需目录下有 SKILL.md 才返回内容）。

**对照证据**（说明这是遗漏而非设计）：
- 同文件 `uploadUserSkill` 对 skillName 有 `startsWith('.')` 检查；
- desktop 主进程 `main.cjs` 的 `resolveLocalSkillFolder` 对同类输入做了完整 `path.resolve` + 前缀校验；
- 后端 `workspace-git.service.ts` 的 `getFileDiff` 甚至显式拒绝路径中的 `..` 段。

## BUG #4：技能同步包接口缺归属校验 → 拉取任意用户私有技能（越权数据泄漏）

**位置**：`backend-ts/src/skill/skill.routes.ts:89-101`

**成因**：`POST /v1/skills/sync-package?sessionId=N` 只调 `requireUserId(request)` 拿到 userId 后**立即丢弃**，随后按 sessionId 查会话、按 `session.userId`（会话属主，不是请求者）收集该用户的全部私有技能打 zip 返回。**没有校验 `session.userId === 请求者`**。

**后果**：任意登录用户枚举 sessionId（自增 ID，从 1 遍历即可），把其他用户上传到 `/opt/mao/data/user-skills/{uid}/` 的全部技能包（SKILL.md 正文 + 附属文件，常含内部流程、密钥说明）下载到本地。zip 由 `writeSyncZip`（skill-sync-service.ts:151-172）以 `session.userId` 的目录为源打包。

**对照证据**：同项目 file.routes.ts 的每个端点都有 `requireOwnedSession`（校验 `session.userId !== userId` 即 403）；session.routes.ts 全部 30+ 端点均有 `requireSessionOwner`。唯独这个端点漏了。

## BUG #5：消息编辑接口 IDOR → 篡改并截断任意用户的会话

**位置**：`backend-ts/src/session/session.routes.ts:380-387` → `backend-ts/src/session/session.service.ts:873-888`

**成因**：`PATCH /v1/sessions/:sessionId/messages/:messageId` 只校验了 `sessionId` 的归属，`messageId` 直接传给 `editMessageAndTruncate`，其内部 `messageRepo.findById(messageId)`（session.repository.ts:233-234）**只按 id 查、不带 sessionId 条件**，之后对 `message.sessionId`（可能是别人的会话）执行：改写消息内容、`logicalDeleteAfter` 截断该会话之后的所有消息。

**触发路径**：用户 A 对自己任意会话调用编辑接口，但 URL 中 sessionId 用自己的、messageId 填用户 B 的消息 id（自增可枚举）→ B 的消息内容被改写、B 会话该消息之后的全部消息被逻辑删除、B 的上下文被污染（下次执行从被篡改的消息重建历史）。

**对照证据**：同文件 `PATCH /v1/sessions/:sessionId/todos/:todoId` 的 repo 调用是 `updateFields(todoId, sessionId, fields)`——**带 sessionId 复合条件**，说明消息编辑漏掉了同样的约束。

## 观察但不定为 BUG

- `crash-recovery-runner.ts` recoverSession 在 `updatePhase(RESUMING)` 后 notifyClient 发的是 `'RUNNING'`，前端状态显示短暂不准。
- `message-queue.service.ts` reorder 两次 `updateById` 非事务，中途失败会留下重复 sortKey（有列表重排兜底）。
- `statistics` getModelStats 存在 N+1 查询，量大时慢但正确。
- `useChat.ts` 错误清理用 `messages.value.pop()` 直接改 computed 内部数组，hack 但当前可用。
- `McpSyncService.nameToId`（mcp-sync-service.ts:16）是全局 Map，同名 MCP server 跨会话会互相覆盖 id；因 LOCAL 上报路径 `serverId ?? 0` 兜底且执行按名字走桌面端，实际影响有限。
- `agent-cli` session-runner.ts `handleAlreadyActive` 非 printMode 分支两个三元表达式结果相同（死代码）。
- `qr-login.service.ts` `qrcodeSessionMap` 无上限无过期，长期运行可缓慢积累（量级小）。
- desktop `main.cjs` skill-sync 直接 `zip.extractAllTo`——adm-zip 0.5.17 已修 zip-slip，且 zip 来源是可信服务端，不构成问题。
- read-file-tool 用宽松 resolve 可读任意绝对路径：与 shell 工具能力对齐的设计一致性选择，不算安全 bug。

## 总结

5 个实锤中 3 个是权限/越权类（#3 路径穿越删目录、#4 越权拉技能包、#5 IDOR 改会话），2 个是状态机/字段一致性类（#1 字段名错位、#2 删除无守卫）。共同模式很清晰：**同类端点都有校验，漏掉的恰恰是后补的端点**——建议按端点清单做一次归属校验全覆盖排查。
