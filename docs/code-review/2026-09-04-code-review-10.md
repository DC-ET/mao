## 低优先级问题（非功能性 bug，建议关注）

### L1. ChatCompletions 与 Responses 对「reasoning 缺 effort」的兜底行为不一致

- 位置：`backend-ts/src/harness/llm/json.ts:86`
- 现状：`if (request.reasoning != null) body.reasoning_effort = request.reasoning.effort;` —— 若上游构造了 `reasoning: {}`（effort 缺失），赋值为 `undefined` 会被 `JSON.stringify` 静默丢弃，导致参数整体不发送；而 Responses 路径（`responses-llm-adapter.ts:826`）有 `?? 'high'` 兜底，两条协议行为不一致。
- 影响评估：当前所有生产代码路径均不会构造空 reasoning——PromptEngine 恒定填非空 effort（空串兜底 'high'），辅助调用固定 `'none'`，压缩 deriveRequest 仅透传。因此实际无影响。
- 建议：与 Responses 侧对齐，改为 `body.reasoning_effort = request.reasoning.effort ?? 'high';`。

### L2. 行为面扩大：所有 openai-compatible 模型默认携带 `reasoning_effort:"high"`（需求规定行为，提示上线风险）

- 位置：`backend-ts/src/harness/core/prompt-engine.ts`（buildRequest 中协议判断）
- 现状：旧逻辑仅 `gpt-*` 前缀模型发送 reasoning；新逻辑下任何 openai-compatible 协议模型（含第三方网关、vLLM/Ollama 等严格实现）都会收到该参数。
- 影响评估：这是需求明确规定的默认行为（留空=协议默认 high），非 bug；但严格按 OpenAI 规格校验参数的上游对非推理模型可能返回 400。
- 建议：发版说明中提示管理员——若某 compatible 模型因不支持 `reasoning_effort` 报错，将其 effort 设为 `none` 即可关闭。

### L3. 未跟踪文件 `shared/contracts/package-lock.json` 疑似误生成

- 位置：`shared/contracts/package-lock.json`（新增未跟踪文件）
- 现状：内容为空依赖的 lockfile；`shared/contracts` 是零依赖纯类型包（根 package.json 无 workspaces，该包也无 dependencies），此 lockfile 无意义。
- 建议：确认后删除或不提交，避免噪音入库。
