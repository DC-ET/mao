# 第 9 轮代码审查报告

- 审查范围：当前 Git 工作区未提交代码（飞书 OAuth 回调与待绑定消息恢复相关变更）
- 重点复核：`state` 回调传递、待绑定消息失败重试、`PROCESSING` 崩溃/过期、成功回调幂等、同消息卡片 patch
- 结论：发现重大功能 bug。`state` 已传至回调、恢复路径会复用原绑定卡片，但失败重试和进程崩溃恢复仍不可达。

## 严重程度：高

### 1. 待绑定消息恢复失败后没有可达的重试入口，成功 OAuth 回调也不是可重入的

- **位置**：`backend-ts/src/create-app.ts:310-324`、`backend-ts/src/feishu/pending-binding.repository.ts:36-58`、`backend-ts/src/auth/feishu-auth.service.ts:97-103, 157-169`
- **问题**：正常回调现已把 `state` 传给 `onUserAuthenticated`，并能将 pending 记录从 `SENT` 领取为 `CLAIMED`。但原消息恢复失败时仅调用 `release()` 将其回退到 `SENT`；OAuth state 此时已是 `SUCCESS`。再次打开相同回调链接会在 `completeStateWithCode()` 的 `oauthState.status !== PENDING` 检查处被拒绝，无法再次执行 `claim()`。代码中也没有扫描 `SENT` 的后台恢复器、显式重试接口或 `SUCCESS` 状态下安全恢复 pending 消息的路径。
- **影响**：Agent、数据库、飞书卡片 patch 等任一短暂故障都会使用户原始群消息永久停在 `SENT`，绑定已经成功但消息永远不执行；同时用户看到授权失败页面，实际 OAuth 绑定却已完成，回调不具备期望的成功后幂等性。
- **修复建议**：将“完成 OAuth/绑定”和“恢复待绑定消息”解耦。绑定成功后由独立、幂等的恢复任务/服务领取 `SENT` 记录，或允许 `SUCCESS` 的 state 仅安全触发 pending 恢复（绝不可再次兑换 code、创建用户或发放登录结果）。恢复失败应记录重试次数、下次重试时间和错误信息，并设置上限/告警。补充覆盖“恢复失败后重新触发，原消息恰好执行一次”的集成测试。

### 2. `CLAIMED` 没有 lease、超时回收或启动恢复；进程崩溃会永久丢失待绑定消息

- **位置**：`backend-ts/src/feishu/pending-binding.repository.ts:36-64`、`backend-ts/db/migration/V085__feishu_pending_binding_message.sql:7-13`、`backend-ts/src/create-app.ts:315-321`
- **问题**：`claim()` 通过 `SENT -> CLAIMED` 领取记录，但记录中没有 lease/领取时间/重试计数，且没有任何按 `updated_at` 回收长时间 `CLAIMED` 记录的调度或应用启动恢复逻辑。应用在 `claim()` 成功后、`process()` 正常返回前崩溃，`catch` 不会执行，记录将永久停留在 `CLAIMED`；后续只查询 `SENT`，因此无法恢复。
- **影响**：部署重启、进程 OOM、节点故障或强制中断会造成已经完成绑定的用户原始消息永久丢失，不能满足 PROCESSING/执行中崩溃后的恢复要求。
- **修复建议**：为 pending 消息实现带租约的领取机制（例如 `claimed_at`/`lease_until`），查询和原子更新只领取 `SENT` 或 lease 已过期的 `CLAIMED`；应用启动及周期任务应回收过期领取。完成后显式进入 `DONE`，失败则按退避策略回到可重试状态。领取 SQL 应在单个条件更新中确认当前状态，避免“先 SELECT 再 UPDATE”造成状态与读取数据不一致。补充崩溃模拟和 lease 到期后的单次恢复测试。

## 已核验

- **state 传递**：`renderCallbackPage()` 已将 `state` 作为第三参数传给 `onUserAuthenticated`；第 8 轮所述正常 GET callback 不传 state 的问题已修复。
- **OAuth PROCESSING 过期**：轮询 `getLoginStatus()` 会将查询到的过期 `PROCESSING` 尝试更新为 `EXPIRED`，且仓储层只对 `PROCESSING -> SUCCESS` 追加未过期限制，方向正确。但没有后台清理/恢复，未再查询状态的崩溃记录仍会滞留，不能替代上述 pending 执行租约。
- **同消息卡片 patch**：pending 记录保存 `card_message_id`，恢复时写入 `progressCardMessageId`；`createFeishuProgressCard()` 对该 ID 执行 `patch`，不会另发一张处理中卡片。该路径实现正确。
- **测试**：已运行 `cd backend-ts && npm test -- --run src/auth/feishu-auth.service.spec.ts src/feishu/agent-inbound-handler.spec.ts && npm run build`，命令成功；现有测试未覆盖上述重试、崩溃回收和成功回调幂等场景。
