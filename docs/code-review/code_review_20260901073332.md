## 一、轻微问题

### 轻微-1：reorder 相邻对反向并发会死锁，失败的一次操作被 WS 层静默吞掉，前端无感知

- 位置：
  - `backend-ts/src/session/message-queue.service.ts:57-77`（`reorder`）
  - 上游：`backend-ts/src/session/ws/streaming-ws-handler.ts:946`（调用点）、`:172-176`（dispatch 的 catch 仅 `console.error`）
- 描述：两个客户端（或同一用户双端）同时对相邻两条消息做相反方向排序时：事务 T1 锁行 A(sort=2) 后去锁 B(sort=1)，事务 T2 锁行 B 后去锁 A → InnoDB 死锁。MySQL 检测后回滚一侧并抛 `ER_LOCK_DEADLOCK`；该异常在 WS dispatch 的 catch 中只打日志，前端收不到 `queue_updated` 推送，表现为"点击无响应"（数据保持一致，用户重试即可恢复）。代码注释已承认该权衡，属已知取舍，但"静默失败 + 前端状态不收敛"值得改善。
- 建议（任选其一即可，均为小改动）：
  1. 统一加锁顺序：事务内先按 `sort_order` 升序一次性 `SELECT ... FOR UPDATE` 锁定两行（如 `WHERE id IN (?, ?) ORDER BY sort_order FOR UPDATE`），再做交换，从机制上消除死锁；
  2. 或在 `reorder` 内对 `ER_LOCK_DEADLOCK` / `ER_LOCK_WAIT_TIMEOUT` 做一次有限重试；
  3. 无论采用哪种，建议失败路径也向前端推送一次 `queue_updated`，使 UI 与库内状态收敛。

### 轻微-2：updateTask 仍整行写回读取时刻的 created_at/updated_at 旧值，与本次新引入的增量 patch 路径语义不一致（既有行为，非本次引入）

- 位置：
  - `backend-ts/src/schedule/scheduled-task.service.ts:179`（`updateById({ ...task, id: task.id! })`，展开含 `createdAt`/`updatedAt`）
  - `backend-ts/src/db/db.ts:31-38`（`updateById` 对对象全部键生成 `SET`）
- 描述：显式赋值会抑制 `updated_at` 的 `ON UPDATE CURRENT_TIMESTAMP`（V061 迁移 ：16），导致 `updateTask` 之后行的 `updated_at` 停留在 SELECT 时刻（与真实修改时刻相差毫秒级，业务影响很小）。而本次修复新增的增量 patch 路径（:214/:306/:342/:450）不写 `updated_at`，由 ON UPDATE 自动刷新、语义更正确——两条路径并存后行为不一致。
- 建议：`updateTask` 改为构造显式字段 patch（`name`/`prompt`/`cronExpression`/`status`/`nextFireTime`/`finished`/`finishedAt`），不回写 `createdAt`/`updatedAt`；顺带消除"把 SELECT 出的全部列盲写回"的隐患，与本次修复的整体方向保持一致。

## 三、六项修复逐项验证结论

### 1. 定时任务增量 patch 写库（scheduled-task.service.ts / scheduled-task.store.ts）— 正确

- 接口签名 `Partial<ScheduledTask> & { id: number }`：全库唯一实现为 `ScheduledTaskDbStore`（store.ts:12-14），spec 中 stub 为对象字面量，全部兼容（build 通过确认）。
- patch 语义核实：`db.updateById` → `toSnakeRow`（`common/case.ts:27-33`）**剔除 `undefined`**，`null` 会显式写入——本次 patch 中出现的 `null`（如 `nextFireTime` 计算失败、`finishedAt`）均为合法业务终态，无误伤。
- 5 个调用点逐一核对（service.ts:179 / :214 / :306 / :342 / :450）：均为有意全量或有意增量；执行收尾（:296-306）重算 nextFireTime 改用重读库的 `latest.cronExpression`，比旧版（T0 快照）更正确。
- 修复有效性：用户在"扫描→执行"窗口内修改 prompt/暂停任务不再被 T0 快照覆盖；暂停（PAUSED）状态在执行中被保留。QUEUED 路径不计 fireCount/lastFireTime 的语义保留（既有用例覆盖通过）。

### 2. updateUser 角色校验前置（user.service.ts:80-84）— 正确

- `assertCanChangeRoles`（`permission/permission.service.ts:132-142`）只读 role/user_role/user 表，与 `user` 行持久化无顺序依赖，前置等价；消除了"断言失败但 displayName/email/status 已落库"的半截修改。同函数内 `assertCanDisableUser` 本就在写入前，两处时序现已一致。

### 3. readFile 文本预览 10MB 上限（workspace-browse.service.ts:19/:233-239）— 正确

- 检查点位于 `readFileSync` 之前，size 取自 `lstatSync`（此前已排除符号链接/非普通文件）；图片路径有独立的 `MAX_IMAGE_BYTES` 检查、PDF 端点仅读 header，互不影响。
- 错误码 `PARAM_INVALID` + "文件过大…请下载后查看"与图片/zip"过大"路径文案一致。stat 与 read 之间文件增长的 TOCTOU 极端边界对 OOM 防护目的无实质影响。

### 4. Webhook 10s 超时 + SENDING 恢复节流（webhook-sender.ts / delivery.scheduler.ts）— 正确

- `AbortSignal.timeout(10s)`：Node 22 原生支持，且内部计时器为 unref'd，不会阻碍事件循环与进程正常退出；现有 `webhook-sender.spec.ts` 使用本地真实 HTTP server 即时响应，10s 不会触发，**未引入测试不稳定**。`FetchLike` 的 `signal` 为可选字段，真实 `fetch` 与测试 stub 均兼容。
- 超时异常（TimeoutError）走既有 catch → `webhookFailure(retryable=true)` → 正常进入重试链路，符合"失败并进入重试"的预期。
- 恢复节流（delivery.scheduler.ts:74/:77/:115-119）：`lastRecoveryAt` 初始为 0，进程首个 tick 必执行恢复（不丢首扫）；置位在 `await` 之前，恢复不会被并发重入；恢复失败后 60s 自动重试（优于旧版"每进程一次、失败即永不"）。
- 5 分钟 cutoff 不误伤在途发送：`task_notification_delivery.updated_at` 带 `ON UPDATE CURRENT_TIMESTAMP`（V054:31），且 10s 超时保证 SENDING 在途时间远小于 cutoff。
- 对现有测试无影响：恢复逻辑现仅在首次 `dispatchDueDeliveries` 时执行（旧版同为一次），`lastRecoveryAt` 节流不改变测试可观察行为。

### 5. withSessionLock Map 清理条件（scheduled-task.service.ts:91-106）— 正确

- 与 `git-write-operation.service.ts:279-290` 的 `withRepoLock` 完全对齐：Map 中存链式 Promise，`finally` 以同一引用比较后删除。并发 A/B 同 session 场景推演：B 覆盖条目后 A 的清理条件为假、B 完成时删除——无泄漏、无误删。
- 附带收益：`chained` 增加 rejection handler 后，`prev` 永不 reject，消除了旧版在先前置 Promise 异常时潜在的 unhandled rejection 及后续调用被误伤的问题。

### 6. reorder 事务 + 行锁（message-queue.repository.ts / message-queue.service.ts:57-77）— 正确（见轻微-1 的死锁提示）

- `MessageQueueRepository.transaction` → `Db.transaction`（db.ts:47-60）：回调抛错即 rollback 并 rethrow，提前 return 则提交空事务——回滚语义正确；tx repo 绑定事务连接，`FOR UPDATE` 读取与 `tx.updateById` 同连接，锁生效。
- `message_queue` 为 InnoDB（V032），`findByIdForUpdate`/`findNeighborUp|DownForUpdate` 与既有 `findLastPendingForUpdate`（enqueue 队尾锁）模式一致；reorder 与 enqueue/enqueueHead 之间为单向等待，不构成锁环。
- spec 的 `transaction: fn(repo)` mock 与真实"传入同接口事务内仓库"语义一致，更新后的用例覆盖了交换与边界（缺失/软删/队端）路径。
