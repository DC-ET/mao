## 严重问题

### [严重] `feishu_binding` 换绑同一用户时会被旧的唯一键记录截获，导致绑定关系不更新

- 位置：`backend-ts/src/feishu/binding.repository.ts:25-35`、`backend-ts/db/migration/V084__feishu_bot_channel.sql:17-20`
- 问题：`unbind`/`bind` 只将用户旧记录标记 `deleted=1`，但表对 `user_id` 和 `union_id` 都是无条件唯一索引。随后 `bind` 使用 `INSERT ... ON DUPLICATE KEY UPDATE user_id = VALUES(user_id), deleted = 0`，当同一用户换绑到新的 `union_id` 时，会因旧的 `uk_user_id` 触发更新旧行，却没有更新 `union_id`；最终旧身份被重新激活，新身份未建立，用户仍无法按新身份使用。该问题直接破坏换绑闭环。
- 修复建议：不要用当前 upsert 处理带软删除的双唯一映射；在事务内先删除/失效旧记录，再对冲突 union_id 做明确的旧用户清理，最后插入新记录。建议采用有效记录的唯一约束设计或物理删除/历史表分离，并补充同一用户换绑、身份被其他用户占用、解绑后重新绑定测试。

### [严重] 群成员白名单仍被首次消息自动授予，未解决前三轮授权边界问题

- 位置：`backend-ts/src/create-app.ts:731-741`
- 问题：已绑定用户首次在群内 @机器人时，如果不在 `feishu_chat_member`，授权回调立即执行 `addGroupMember` 并返回 `true`，随后进入 Agent。这样成员表不是授权门槛，而是首次消息自动放行的记录；与技术方案中“触发者必须在白名单中”及前三轮要求不一致。
- 修复建议：入站仅查询白名单；未命中时发送引导/拒绝执行，不创建会话。若产品确实选择自动入表，应明确将其改为初始化/管理流程并在需求与验收标准中同步，而不是在授权判断中隐式授予。

## 高严重问题

### [高] 生产长连接仍只处理 `start()` Promise 失败，断线/重连耗尽不会回收 active handle

- 位置：`backend-ts/src/feishu/monitor.service.ts:35-44, 101-121`
- 问题：当前仅捕获 `wsClient.start()` 返回 Promise 的启动异常；没有监听 SDK 的 close/error/重连耗尽状态。若 SDK 连接建立后断开，monitor 仍保留 handle，后续 reconcile 因 `active.has(id)` 不会重建。`reconnectBaseMs` 只用于“启动 Promise reject”后的单次 reconcile，`reconnectMaxMs`/`maxConsecutiveFailures` 也未参与状态机；停用时 `close()` 还是同步 fire-and-forget，旧连接的回调没有 generation 校验，可能在停用/重启后继续处理消息。前三轮长连接失败回收问题未解决。
- 修复建议：封装可观察的 running/closed/failed 状态与异步 stop；监听 SDK close/error/重连耗尽，失败时从 active 原子移除并按退避重建；停止和重建增加 generation/token 检查，旧连接事件直接丢弃，并覆盖启动失败、建立后断线、停用后旧事件测试。

### [高] 精确 @ 仍未在生产 wiring 中实现，默认只信任未经校验的 `is_at_me`

- 位置：`backend-ts/src/create-app.ts:729-744`、`backend-ts/src/feishu/inbound-processor.ts:59-62`、`backend-ts/src/feishu/event-normalizer.ts:24-25`
- 问题：生产构造 `FeishuInboundProcessor` 时没有提供 `isBotMentioned`；处理器因此直接采用标准化阶段的 `event.isBotMentioned`。标准化仅将事件中的 `message.is_at_me/event.is_at_me` 转成布尔值，没有拿 mentions 中的 ID 与当前机器人身份（当前 app 的 bot open_id/mention key）比对。普通成员 @、字段缺失/误读、多机器人事件都无法得到可证明的精确匹配。前三轮指出的精确 @问题仍然存在。
- 修复建议：每个 bot 获取并缓存自身 open_id/官方 mention key；以 mentions 中的精确 ID 匹配当前 bot，字段缺失或无法确认时按未 @ 处理；补充普通成员 @、当前 bot @、多 bot、无 mention 字段测试。

## 中等问题

### [中] 独立发送服务仍未按飞书 API 约定传递 `receive_id_type`

- 位置：`backend-ts/src/feishu/send.service.ts:26-30`
- 问题：`receive_id_type` 被放在 JSON body 中，而技术方案及飞书消息接口要求它作为请求 query 参数（`?receive_id_type=open_id|chat_id`）。虽然 `create-app.ts` 的主发送路径使用 SDK 的 query 参数，不能掩盖该独立服务的错误；调用该服务的私聊/群聊发送会被飞书按默认类型解析，可能失败。
- 修复建议：将 `receive_id_type` 放入 endpoint query，并对 open_id、chat_id 两种路径补请求断言测试；统一主路径与该服务，避免两套发送语义漂移。
