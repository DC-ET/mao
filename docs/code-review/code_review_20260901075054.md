## 一、轻微问题（本轮新发现）

### 轻微-1：ER_LOCK_WAIT_TIMEOUT 也纳入重试且重试无退避，极端场景下单次 reorder 请求最长可挂起约 3×innodb_lock_wait_timeout（默认 50s，约 150 秒）

- 位置：
  - `backend-ts/src/session/message-queue.service.ts:57-70`（`reorder` 重试循环，`attempt < 2` 共最多 3 次执行）
  - `backend-ts/src/session/message-queue.service.ts:105-112`（`isLockConflictError` 同时匹配 `ER_LOCK_DEADLOCK` 与 `ER_LOCK_WAIT_TIMEOUT`）
- 描述：两种锁冲突错误的代价差异很大。`ER_LOCK_DEADLOCK` 由 InnoDB **即时检测**并回滚一侧，立即重试成本低、收益高，是本次修复的主要目标场景；而 `ER_LOCK_WAIT_TIMEOUT` 意味着已有事务持锁 `innodb_lock_wait_timeout`（MySQL 默认 **50 秒**）未释放，此时立即重试大概率继续等待同样时长——最坏 3 次共约 150 秒，期间该 WS 消息处理一直挂起（WS 连接不中断，dispatch 兜底，最终要么成功要么抛错后由 finally 推送收敛）。数据正确性不受影响，属响应时长退化风险；实际发生概率低（reorder 事务持锁为毫秒级，需有其它事务持锁 50s+ 才触发）。
- 建议方向（任选其一）：
  1. `isLockConflictError` 仅匹配 `ER_LOCK_DEADLOCK`，`ER_LOCK_WAIT_TIMEOUT` 直接抛错交由 WS finally 推送收敛；
  2. 或保留两类错误但重试前加短暂退避（如 100~200ms），并把重试只应用于死锁、锁等待超时仅重试一次。

## 二、观察项（不要求本次处理）

1. **finally 中推送失败会替换原始异常**：`streaming-ws-handler.ts:946-952` 的 `finally { await this.sendQueueUpdated(...) }`——若 reorder 抛错且 `sendQueueUpdated` 也抛错（如推送时 DB/WS 异常），JS 语义是 finally 中的异常**替换** reorder 的原始异常，dispatch catch 打印的是推送错误，日志归因失真。功能无碍（dispatch catch 兜底，前端下次操作仍收敛）。如在意可改为 `try/catch` 包裹 finally 内的推送。
2. **重试语义为"基于最新状态重放移动"**：死锁侧回滚后重试时，若对端事务已提交交换，本次移动将相对最新排序再动一格（而非相对用户点击时的快照）。这是注释中已声明的语义，不会产生重复 sort_order 或交换丢失，属合理取舍。

## 三、修复复核明细

### 复核 1：reorder 拆分 + 锁冲突有限重试（message-queue.service.ts:57-70、:72-97、:105-112）— 正确

- 重试次数：`for (let attempt = 0; ; attempt++)` + `attempt < 2` → 初始 1 次 + 最多 2 次重试 = 最多 3 次执行，与声明一致；重试耗尽重抛原始错误对象。
- `isLockConflictError` 守卫完备：`typeof e !== 'object' || e == null || !('code' in e)` 先行排除 null/原始类型/普通 Error；mysql2 抛出的 MySQL 错误 `code` 命名正确（`ER_LOCK_DEADLOCK`/errno 1213、`ER_LOCK_WAIT_TIMEOUT`/errno 1205），非锁错误（如连接错误 `ECONNREFUSED`、语法错误）不会被误重试。代价问题见轻微-1。
- 重试路径安全：死锁时 `Db.transaction` 已 rollback 并释放连接，`reorderOnce` 每次全新事务、全新 `FOR UPDATE` 读取，无跨尝试残留状态；不会产生重复 sort_order 或交换丢失。
- 异常链路：重试耗尽 → 重抛 → WS finally 推送 → dispatch catch 日志。与修复 2 组合后，上轮"静默失败"问题已消除。

### 复核 2：handleReorderQueueMessage 改为 try/finally（streaming-ws-handler.ts:946-952）— 正确

- 成功路径：reorder 成功 → finally 推送一次 `queue_updated`（原成功路径的独立推送已移入 finally，无双推）。
- 失败路径：reorder 抛错（含重试耗尽）→ finally 先推送刷新使前端状态收敛，随后原始异常继续向上传播（`finally` 不吞异常）→ dispatch catch 打日志。符合"失败也收敛"的意图。推送自身异常的边界见观察项 1。
