### 低-1 逐场景推演

1. **长按保持任意时长（含 >900ms）后松手**：定时器 500ms 触发置 `longPressTriggered=true` 并开菜单；touchend 时 clearLongPress（no-op）→ 标志为 true → 复位标志并置 `suppressClickUntil = touchend+400`。合成 click（若浏览器派发）落在窗口内被 `handleClick` 首行抑制 → 菜单保留、任务不再误打开。**第二轮低-1 回归已消除**。
2. **正常短点（<500ms）**：touchend 先于定时器触发，clearLongPress 取消定时器，标志为 false → 不设窗口 → click 正常打开任务。无影响。
3. **长按触发后再拖动 >10px 松手**：`onTouchMove` 在 `longPressTriggered` 后直接 return（不再清零窗口）→ touchend 设窗 → click 被抑制。第二轮的加剧场景一并消除。
4. **未触发长按即拖动（滚动）**：clearLongPress 取消定时器、标志保持 false → 不设窗口，行为与 HEAD 一致。
5. **Android Chrome 长按后不派发合成 click**：窗口锚定 touchend，400ms 后自然过期，不会残留吞掉下一次真实点击 —— 原时间窗方案的优点保留。
6. **早退路径兜底**：被抑制的 click 虽在 `handleClick` 提前 return，但事件仍冒泡至 window 级 `closeContextMenu`，菜单不会卡死。`longPressTriggered` 在每次 touchstart 复位、`suppressClickUntil` 随时间过期，两类状态均无残留路径；`onUnmounted` 补了 `clearLongPress()`，无定时器泄漏。

### 提示-1 复核要点

- `if (data.status !== 'confirmed') scanStatus.value = data.status`（210 行）：非 confirmed 状态照常更新；confirm 失败重试期间后续轮询仍返回 confirmed → 不再覆盖 `scanStatus`，弹窗维持「已扫码，请确认登录」。

- 用户中途关弹窗（@closed → resetQrcode → stopStatusPolling → pollingActive=false）：in-flight confirm POST 失败后因 pollingActive=false 不再续订，无僵尸轮询；`confirmFailures` 在 `startStatusPolling`（含「重新获取」）复位。

## 提示级备注（均不阻塞合入，非本轮新引入的功能性 bug）

### 提示-A. 长按特性未处理 touchcancel（自特性引入起即存在）

- **位置**：`desktop/src/components/task/SideTaskList.vue` 模板仅绑定 `@touchstart/@touchmove/@touchend`
- 系统中断触摸（来电、手势接管等）触发 `touchcancel` 时无处理：若定时器尚未触发，500ms 后仍会弹出菜单（手指已不在屏上）；若已触发，`longPressTriggered` 残留至下一次 touchstart 复位（无窗口误设，影响仅限菜单残留，点击任意处可关）。第二轮版本行为相同，非本轮回归。可后续补 `@touchcancel="onTouchEnd"`（或专用清理）顺手解决。

### 提示-B. touchend 锚点的固有权衡：长按释放后 400ms 内对边路条目的真实点击会被吞一次

- 长按保持 >900ms 场景下，第二轮版本窗口已过期（低-1 的表象即此），真实快点可打开任务；第三轮改为 touchend 锚点后，窗口覆盖 [touchend, touchend+400ms]，期间对**任意**边路条目（组件级全局变量）的一次真实点击会被 `handleClick` 首行吞掉。此为第二轮报告建议方案（时间窗锚定 touchend）的固有成本：窗口有界（400ms）、一次点击后自然恢复，且长按刚释放的 0.4s 内用户通常在浏览菜单而非点条目，实际触发概率很低。属可接受权衡，不建议改动。
