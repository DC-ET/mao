# 微信入站文件处理未提交代码审查报告

审查范围：当前 Git 工作区中与 `docs/weixin-inbound-file-handling-technical-design.md` 相关的未提交代码，仅关注功能逻辑。

## 发现的问题

### 1. [高] 文件下载或解密失败时，纯文件消息仍会被静默丢弃

- 位置：`backend/src/main/java/cn/etarch/mao/weixin/service/InboundProcessor.java:65-68`
- 位置：`backend/src/main/java/cn/etarch/mao/weixin/service/InboundProcessor.java:193-216`

`downloadFiles()` 在 CDN 下载、AES 解密或字段解析失败时只记录日志并跳过文件项。若用户发送的是纯文件消息，成功文件列表最终为空，随后命中“无文本无图片无文件”的空消息分支并直接返回，用户收不到任何回复。

这与技术方案要求的“文件接收失败、下载/解密失败时向用户回复明确错误提示”相违背，也意味着本轮要解决的核心问题在异常链路上仍然存在。当前 `InboundProcessorTest.fileDownloadFailure_messageIgnored` 还将该错误行为固化成了测试预期。多文件消息中某个文件失败时，该文件也会被静默遗漏，Agent 会在不知情的情况下仅处理其余文件。

建议保留“消息包含文件项但下载失败”的结果状态，并将失败信息传给 handler 或直接构造错误回复；不能仅以成功下载列表参与空消息判断。

### 2. [中] 同名文件的选名与写入不是原子操作，并发消息可能互相覆盖

- 位置：`backend/src/main/java/cn/etarch/mao/weixin/service/WeixinFileStorageService.java:64-69`
- 位置：`backend/src/main/java/cn/etarch/mao/weixin/service/WeixinFileStorageService.java:130-144`

`uniquePath()` 先通过 `Files.exists()` 选择目标名，返回后再由 `Files.write()` 写入。两个并发入站消息若上传同名文件，可能同时观察到目标不存在并获得同一路径；`Files.write()` 默认会覆盖已有文件，因此后写入的内容会覆盖先写入的内容。

结果是两条用户消息可能都引用同一个路径，较早启动的 Agent 也可能读到后一条消息的文件内容，违反“同名文件不覆盖”的业务要求。建议使用 `CREATE_NEW` 原子创建并在冲突后重新选名，或对选名和写入整体加锁。

### 3. [中] 文件媒体字段解析未实现技术方案要求的回退兼容

- 位置：`backend/src/main/java/cn/etarch/mao/weixin/service/WeixinMediaService.java:128-140`
- 位置：`backend/src/main/java/cn/etarch/mao/weixin/service/WeixinMediaService.java:249-264`

`downloadFile()` 强制要求 `file_item.media.encrypt_query_param`；`resolveAesKey()` 只识别 item 级 `aeskey` 和 media 级 `aes_key`。技术方案明确要求 `encrypt_query_param` 缺失时回退 `file_item` 其他可用字段，并兼容 `aeskey`、`aes_key` 的字段位置差异。

如果真实微信入站结构将 `encrypt_query_param` 放在 `file_item` 级，或将 `aes_key` 放在 `file_item` 级，当前实现会拒绝合法文件；结合问题 1，纯文件消息随后会被静默丢弃。建议按方案建立明确的字段回退顺序，并补充覆盖实际 `downloadFile()` 入口的测试。
