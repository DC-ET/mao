## P2

### P2-1. 「本次任务授权」在任务内未执行任何页面动作时不会失效，泄漏到下一个任务

**位置**
- `sdk/embed/src/page/engine.ts:90-96`（`PageEngine.endTask()` 第一行 `if (this.activeSessionId == null) return;`）
- `sdk/embed/src/page/authorization.ts:168-175`（`endTask()` 才把 `level==='task'` 降回 `per_action`）
- `sdk/embed/src/controller.ts:329`（phase 终态调用 `pageEngine.endTask()`）、`controller.ts:899-901`（浮窗「本次任务授权」→ `setLevel('task')`）

**问题**

`PageEngine.activeSessionId` 只在 `beginTask()` 里被赋值，而 `beginTask()` 只在收到后端 `page_tool_request`（`engine.ts:202`）时调用。浮窗的「本次任务授权」按钮走的是 `applyUserPageAuthorization → pageEngine.setLevel('task', sessionId)`，**不会**设置 `activeSessionId`。于是：

1. 用户在 Agent 尚未发起任何页面动作时点「本次任务授权」→ `authorization.level='task'`、`taskSessionId=S`，`PageEngine.activeSessionId` 仍为 `null`；
2. 该任务结束（COMPLETED/FAILED/CANCELLED）→ `controller.ts:329` 调 `pageEngine.endTask()` → **`activeSessionId == null` 直接 return**，`authorization.endTask()` 没执行，`level` 仍是 `task`、`taskSessionId` 仍是 `S`；
3. 用户在同一会话发起下一个任务 → Agent 第一次调用页面工具 → `beginTask(S)` → `authorization.beginTask(S)` 里 `if (this.taskSessionId === sessionId) return;`（`authorization.ts:153`）直接返回 → `level` 保持 `task`。

结果：下一个任务的所有写操作**不再逐次确认**，而浮窗仍显示「本次任务授权」。用户以为自己只授权了上一个任务，实际是持续授权。`stop()` 路径（`controller.ts:853` → `pageEngine.cancel()` → `authorization.destroy()` + `endTask()`）同理：`cancel()` 只清 pending，不重置 `level`，`endTask()` 又因 `activeSessionId == null` 提前返回。

**修复建议**

- `PageEngine.endTask()` 去掉 `if (this.activeSessionId == null) return;`，改为始终调用 `this.authorization.endTask()`（`activeSessionId`/highlight/taskState 的清理可保留条件判断）；或
- 在 `PageEngine.cancel()` 中额外调用 `this.authorization.endTask()`，并在 `applyUserPageAuthorization('task')` 时同步设置 `activeSessionId`（更贴合「task 绑定到具体任务」的语义）。
- 补回归用例：`engine.setLevel('task', 1)`（不调任何页面工具）→ `engine.endTask()` → 断言 `authorizationLevel === 'per_action'`。

### P2-2. 并发 `page_tool_request` 时确认卡片互相覆盖，先到的动作卡片丢失、120s 后静默拒绝

**位置**
- `backend-ts/src/harness/core/agent-loop.ts:516`（同轮多个 tool call 用 `Promise.all` 并发派发）
- `sdk/embed/src/page/authorization.ts:212-226`（`requestConfirmation` 只 `notify(request)`，不排队）
- `sdk/embed/src/controller.ts:298-300`（`onConfirmRequest: (request) => { this.ui.pageConfirm = request; }`）
- `sdk/embed/src/page/engine.ts:317-339`（每个动作各自 `await requestConfirmation`）

**问题**

模型在同一轮输出多个页面工具调用是常态（例如「把姓名和电话都填上」→ 两个 `page_fill`）。`agent-loop.ts:516` 用 `Promise.all` 并发执行，SDK 侧 `handlePageToolRequest` 也并发执行（`pageToolInFlight` 按 requestId 去重，不会串行化）。`per_action` 下两个动作都会 `requestConfirmation`：

- `notify(req1)` → `ui.pageConfirm = req1`；紧接着 `notify(req2)` → `ui.pageConfirm = req2`，**req1 的卡片被覆盖且无 UI 可点**；
- 用户只能处理 req2，req1 只能等 120s 定时器以 `false` 结束 → 该动作 `authorization_denied`，整轮 `Promise.all` 卡满 120s；
- 两个动作若作用在同一元素/表单上，还可能交错执行（`settle()` 之间互相插入）。

**修复建议**

- 在 SDK 侧对页面工具请求串行化：`PageEngine`/`controller` 维护一个 promise 队列，同一时刻只执行一个 `handleRequest`（`page_inspect` 等只读工具可豁免）；或
- `PageAuthorization.requestConfirmation` 用队列 + 逐张展示（一次只弹一张，处理完再弹下一张）。
- 补用例：连续两次 `requestConfirmation` → 断言 UI 依次收到两条请求且都能 `resolveConfirmation`。

### P2-3. `page_actions` 在 per_action 下不会「遇到确认即停止」，多次确认累计超过后端 180s 超时后动作仍在继续

**位置**
- `backend-ts/src/harness/tool/impl/page-tools.ts:280-285`（`PageActionsTool` 描述承诺「…或需要用户确认时立即停止，返回已执行步骤和中断原因」）
- `sdk/embed/src/page/executor.ts:140-175`（`executeBatch` 每步 `await options.authorize(...)`，确认通过后继续，不中断）
- `sdk/embed/src/page/authorization.ts:217-223`（单次确认超时 120s）
- `backend-ts/src/harness/embed-page-tool-registry.ts:84-92`（后端工具超时默认 180s，见 `DEFAULT_PAGE_TOOL_TIMEOUT_SECONDS`）

**问题**

`page_actions` 里每个 mutating 动作在 `per_action` 下都要用户确认。单次确认超时 120s，而后端整个工具调用只有 180s。只要用户对前两步稍微犹豫（或批量里有 2 个以上写操作），后端 `future` 会先以 `page_tool_timeout` 结束；SDK 这边还在弹确认/执行，最终回包到达时 `complete()` 因 pending 已删除而丢弃（`embed-page-tool-registry.ts`）。

后果：**Agent 收到「页面操作超时」，但页面动作仍在被用户点击确认后真实执行**。Agent 常见反应是重新 inspect 并重试，可能造成重复提交/重复点击等副作用。实现与工具描述（「需要用户确认时立即停止」）也不一致。

**修复建议**

- 与描述对齐：`executeBatch` 在 `authorize` 返回「需要确认」时立即中断并返回 `stoppedAt/reason`（让 Agent 改为逐个调用单动作工具），或
- 若保留「批量内联确认」，需把批量确认的累计时间计入超时：批量开始前用后端可配置的更长时间/取消机制，或在第一步确认通过后把剩余步骤改为自动放行（与 `task` 语义一致）并明确告知模型；
- 至少把 `page_actions` 描述改掉，避免模型对行为有错误预期。

### P2-4. 截图渲染器只补偿 `window` 滚动，页面内滚动容器（`overflow:auto`）仍按未滚动内容渲染，遮罩与图像错位

**位置**
- `sdk/embed/src/page/screenshot.ts:90-118`（`defaultRenderer` 仅用 `window.scrollX/scrollY` 平移克隆体）
- `sdk/embed/src/page/engine.ts:160-163`（遮罩 rect 来自 `rectOf`，是**当前视口**坐标）
- `sdk/embed/src/page/visibility.ts:22-40`（`rectOf` 只沿 iframe 链累加偏移，不含滚动容器）

**问题**

第 2 轮 P2-3 的修复对 `window` 滚动是对的（`left:-scrollX / top:-scrollY`，渲染自然视口后再 `drawImage` 缩放，遮罩按 `scale` 缩放，坐标系一致）。但 `cloneNode` 不会复制任何元素的 `scrollTop/scrollLeft`，而很多业务页面（后台管理、列表页）主内容是在 `overflow:auto` 的容器里滚动的，`window.scrollY` 恒为 0：

- 图像渲染的是容器的**未滚动内容**（容器顶部 400px），而 `maskRects` 是当前视口的坐标 → 遮罩涂在错误位置；
- 视口上方滚出屏幕的敏感字段，其 rect `y` 为负，`maskRects` 里 `Math.max(0, rect.y*scale)` 会被钳到 0，而该字段在克隆图中可能被渲染在容器中部/底部 → **存在敏感值未被遮住就发出的窗口**（与 P2-3 同类风险，只是触发条件是容器内滚动）。

**修复建议**

- 渲染前遍历源文档中 `scrollTop/scrollLeft !== 0` 的可滚动元素，对克隆体中对应节点回写相同的 `scrollTop/scrollLeft`（或对内层容器叠加 `translate(-scrollLeft,-scrollTop)`）；克隆后按 DOM 顺序与源节点一一对应即可定位。
- 附带：`defaultRenderer` 用 `clone.innerHTML` 丢弃了 `body` 自身的样式（`inlineStyles` 的结果没生效），`body` 默认 `margin:8px` 未补偿，遮罩整体偏移约 8px；建议把 body 的 margin/padding 显式补到内层容器或直接渲染 body 克隆本身。
- 补一个「容器内滚动后截图」的用例（注入 renderer 断言传入的 `maskRects` 与期望一致）。

## P3 / 备注（不阻塞）

1. **host `executePageAction` 在 `cancel()`/`newSession()` 之后被永久阻断**：`engine.ts:170-176` 的 `executeAction` 走 `authorizer`，而 `authorizer` 第一行 `if (this.cancelled) return task_cancelled`（`engine.ts:318`）；`cancel()` 置 `cancelled=true` 后只有 `beginTask()` 会复位，`executeAction` 从不调用 `beginTask`。`newSession()`（`controller.ts:682`）会调用 `cancel()`，因此 `chat.newSession(); chat.executePageAction(...)` 会稳定返回 `task_cancelled`，直到某次后端页面工具请求把 `cancelled` 复位。建议 `executeAction` 开始时复位 `cancelled`，或改为不依赖该标志。
2. **遮罩扫描预算**：`engine.ts:161` 用 `scanPage({includeHidden:true, maxElements:2000})`；`includeHidden` 会把 `type=hidden`、`display:none` 等也计入预算，元素很多时排在预算之外的敏感字段不会被遮罩。建议遮罩单独扫描（只收集 `isSensitiveField` 命中的元素，不受 2000 预算限制）。
3. **`page_scroll` 显式 x/y 被浏览器 clamp 时误报失败**：`executor.ts` 的 `expected` 直接用请求值，实际 `scrollTo` 会被钳到最大滚动位置，`verified` 为 false → `scroll_failed`（`to:'bottom'` 已按 `scrollHeight-clientHeight` 修正，但显式坐标没有）。建议「位置不再变化且朝请求方向到达边界」也算成功。
4. **`initialLevel:'task'` 实际对每个任务生效**：`authorization.ts:161` 的 `initialTask` 只在 `setLevel/revoke` 清除，`endTask()` 不清，因此 host 传 `initialLevel:'task'` 等于为每个任务持续开启「免确认」，与 `setInitialLevel` 注释「在首个任务开始时生效」不符（若产品语义就是每任务，请改注释）。
5. **刷新后 UI 授权级别显示滞后**：`createUiState` 用 `options.page?.initialLevel ?? 'per_action'` 初始化，而持久化的 `full` 要等首次 `syncIdentity()`（首次页面工具请求/inspect）才 `loadPersisted` + `emitState`。表现为刷新后浮窗先显示「每次确认」，首次页面操作后才变「完全授权」。建议 controller 拿到身份后主动调一次 `authorization.syncIdentity()`。
6. **截图具体错误码被折叠**：`capturePageScreenshot` 抛出的 `screenshot_too_large` / `screenshot_render_timeout` / `screenshot_timeout` 在 `engine.handleRequest` 的 catch 里统一变成 `internal_error`（`engine.ts:222-224`），`PageToolErrorCode` 里定义的 `screenshot_*` 从未出现在结果中。建议按 message 前缀映射回具体 code。
7. **`page_inspect` 结果体积**：单快照最多 400 个元素，每项含 label(≤500)/text(≤500)/options 全量，多个大 `select` 时 JSON 可能接近 WS `maxPayload`（`attach-websocket.ts:19` = 1MB），帧会被直接断开。建议对 options 数量/总字节设上限并在结果里标注截断。
8. **`types.ts` 被整体压缩**：`sdk/embed/src/types.ts` 本轮把接口/联合类型/注释全部压成单行并删除了原有中文注释（导出的符号未变）。属可维护性回退，建议恢复换行与注释。
9. **`desktop/package.json` 版本手改**：0.0.109 → 0.0.112 直接改文件，而仓库约定用 `./scripts/changelog-extract.sh sync-desktop` 同步。建议按约定流程处理。
