## 1. 拖放读目录期间切 Tab，上传目标会变

**位置**：`admin/src/views/skill/SkillListView.vue` `handleDrop`（约 465–489 行）、`uploadFiles`（约 554–579 行）

拖放先异步遍历目录，遍历结束才调用 `uploadFiles`。目标 Tab 和用户列表是在 `uploadFiles` 里才读取的。遍历过程中没有占用状态，上传区也不转圈，Tab 仍可点。

点选目录是安全的：文件对话框关掉后，`change` 同步进入 `uploadFiles`，`personal` 立刻定下来。拖放不是。目录文件一多（含 `node_modules` 时尤其明显），`readEntries` / `file()` 要几百毫秒到数秒，页面看起来像没接住这次拖放。

**触发**：

- 在「个人 Skills」已选用户，拖入目录，遍历未完成时切到「系统 Skills」。随后请求打到 `POST /skill-docs/upload`，没有「添加到指定用户」确认框，技能进入系统技能库，所有用户可见。
- 反过来：在系统 Tab 拖入目录后切到个人 Tab。若之前选过用户，这次会弹出确认框并写入那些用户；若没选用户，这次系统上传被悄悄丢掉，只提示「请先选择要添加技能的用户」。

**建议**：在 `handleDrop` 一开始记下 `activeTab` 和 `assignUserIds` 的副本，遍历完成后用这份副本调用上传，不要再读当前 Tab。遍历期间把上传区标成忙碌，避免连点第二次拖放。

## 2. 批量覆盖不是一次提交，失败后列表是旧的

**位置**：`backend-ts/src/skill/skill.routes.ts` 约 109–120 行；`backend-ts/src/skill/user-skill.service.ts` 约 164–184 行；`SkillListView.vue` `uploadFiles` 的 `catch`（约 591–592 行）

用户 ID 校验在写盘之前，不存在的用户不会写入任何人。通过校验之后，按用户依次调用 `uploadUserSkill`。某一个用户失败时，接口整体返回业务错误，但前面的用户已经写完。

覆盖实现是先删掉同名目录再写新文件。删除成功、后续 `writeFileSync` 失败（磁盘满、权限、路径过长）时，该用户原来的个人技能已经不在，新目录也不完整。错误文案只说「写入用户 N 失败」，看不出旧技能已被删掉。

管理后台把非 0 的 `code` 当成整次失败，`catch` 里不刷新个人技能表。表格仍显示覆盖前的记录。提示条里虽有「已写入用户 …」，几秒后消失，操作者看到的列表和磁盘不一致。

同一份文件对每个用户的校验结果相同，校验失败会停在第一个用户、不会删旧技能。会伤到数据的是写盘阶段，以及一次上传里包含多个技能时，前面的技能已覆盖、后面的技能写失败。

**建议**：先对文件做一次校验，再对每个用户写入。覆盖时先写到临时目录，成功后再替换原目录。任一用户失败时，响应里的已成功用户要能对上刷新后的列表；前端收到失败也重新拉一次个人技能。

## 3. multipart 中断后仍用已读到的片段继续上传

**位置**：`backend-ts/src/skill/skill.routes.ts` `collectAdminSkillUpload` 约 279–296 行；全局限制 `backend-ts/src/create-app.ts` 约 362 行 `files: 500`；CLI 字段顺序 `skills/mao-cli/lib/http.js` `buildMultipart`（字段在文件之前）；管理后台 `SkillListView.vue` 约 569–576 行（文件在 `userIds` 之前）

解析抛错时函数把已经读到的文件和 `userIds` 原样返回，调用方分不清「用户没填」和「请求被截断」。

```279:296:backend-ts/src/skill/skill.routes.ts

  // ...
  try {
    const parts = request.parts({ preservePath: true });
    for await (const part of parts) { /* 收集 files / userIds */ }
  } catch {
    return { files, userIdValues };
  }
  return { files, userIdValues };

```

服务端单个请求最多 500 个文件。技能目录里带上 `node_modules` 就会超过。桌面端上传会事先排除 `node_modules` 并在超过 500 个文件时直接提示；这次的管理后台上传区没有这层检查。

两种客户端字段顺序不同，结果也不同：

- **管理后台**：先追加全部 `files`，最后才追加 `userIds`。第 501 个文件触发限制时，`userIds` 还没读到。接口返回「请指定至少一个用户」。用户明明选了人，技能也没写上。
- **mao-cli assign**：`buildMultipart` 先写 `userIds` 再写文件。`userIds` 已经在手，前 500 个文件里通常包含 `SKILL.md`。接口按成功返回，用户目录里是一份缺文件的技能。

**建议**：解析失败直接返回 400，不要带着半截文件继续 `uploadUserSkill`。管理后台在组 FormData 之前按桌面端同样的规则排除 `node_modules` / `.git`，并限制文件数和总体积。
