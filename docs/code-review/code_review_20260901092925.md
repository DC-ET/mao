## 总体结论

**未发现会导致业务功能错误的新引入 BUG。** 5 处修复的方向与实现均正确，具体核验如下：

1. **withSessionLock（agent-inbound-handler.ts:287-302）**：Map 中存 `chained = prev.then(() => current, () => current)` 并按同一引用比较删除，与 `schedule/scheduled-task.service.ts:88-106` 的写法一致。核验：`chained` 的 onRejected 返回 `current`，永不 reject，`await prev` 不会抛；`release()` 与引用比较位于同一同步段，无微任务插入窗口，不会误删后到者的锁条目，也不再泄漏。✅
2. **被取代消息回滚**：`savedMessageId` 由 `onMessage` 精确传入（非"删末尾 USER"的模糊定位），回滚发生在 `withSessionLock` 内——被取代的 genN 释放锁之前，genN+1 必然尚未开始执行（新消息的 saveMessage 在 onMessage 同步流中已完成），因此删除不会与后续执行的上下文读取产生竞态；`prepareMessage` 仅生成 UUID 无副作用，跳过执行无需额外清理。`logicalDeleteByIdInSession` 带 `session_id` 限定、参数化查询，重复删除幂等（`deleted = 0` 条件不命中）。✅
3. **handleRetryExecution（streaming-ws-handler.ts:743-790）**：try/catch 覆盖了 claim 添加到 submitExecution 的全程；`submitExecution` 提交被拒时内部已自回滚并发 error 事件，不向外抛，故外层 catch 不会重复清理/重复发事件（与注释声明一致）。claim 添加与 `cancelFlags/runningExecutionIds` 写入、`submitExecution` 调用之间无 await 插入点，catch 中无条件 delete 不会误伤其他执行的状态。✅
4. **WS 晚到竞态抑制（delivery.service/scheduler）**：两级 CAS（WAITING_WS→SUPPRESSED_WS 失败后补 SENDING→SUPPRESSED_WS）+ deliver() 发送前 findById 重查，覆盖了「resolveWebSocket 被 claim 抢先」的窗口。方向正确：`SENDING` 仅由 `claim()` 产生（PENDING/WAITING_WS→SENDING），不会误伤其他终态。✅
5. **grep JS 回退分支**：`globToFileRe` 按 gitignore/rg --glob 语义逐例验证通过（`'**/*.md'` 命中根目录零层文件、`a/**/b/**/c.txt` 中间 `**` 零层匹配 `a/b/c.txt`、`*`/`?` 不跨目录段、末位 `**` 兜底 `.*`；`collectFiles` 的 basename 兜底测试保证无斜杠 glob 任意深度生效）。上下文输出改为独立条目 + `contextual:true`，经逐行推演与 rg 分支的「前上下文→命中→后上下文」顺序及相邻命中去重语义一致（重叠上下文经 `lastPrinted` 只输出一次，`lastPrinted` 按文件重置）。10MB 单文件上限防 OOM，超限跳过。✅

验证：`file-tools.spec.ts` 26 用例、微信 handler/flow + session + ws-handler + notification 共 9 文件 80 用例均通过；工作区全量基线（148 文件 / 1159 用例）由需求方确认通过。

## 发现的问题

### Medium

无。

### Low

#### L-1 deliver() 终态回写无状态 CAS，极端时序下可覆盖 SUPPRESSED_WS

- 位置：`backend-ts/src/notification/task/delivery.scheduler.ts` `deliver()` 尾部（约 158-183 行）与 `delivery.service.ts` `resolveWebSocket()` 的第二次 CAS（约 111-125 行）
- 场景：deliver() 通过 findById 重查（状态仍 SENDING）→ resolveWebSocket 第二次 CAS 成功（SENDING→SUPPRESSED_WS）→ deliver() 继续发送 webhook（用户收到 WS+webhook 重复通知，已知残留）→ 若 webhook 返回可重试失败，`updateById` 无条件写回 `status=PENDING + nextRetryAt`，**把 SUPPRESSED_WS 覆盖为 PENDING**，行复活并在下个 tick 重发 webhook；写 SUCCEEDED 时则覆盖为事实正确的终态。
- 影响：仅发生在 findById 检查与 webhook 发送之间的毫秒级窗口内，且代码已通过 `console.warn` 显式声明 "duplicate notification possible"，属 best-effort 语义的已知残留，非功能错误。
- 建议（后续优化，非本次必改）：deliver() 的终态回写改用条件更新（仅 `status = SENDING` 时生效，如 `updateIfStatus(id, SENDING, ...)`），即可同时消除「覆盖抑制态」与「重复通知后状态漂移」两个尾巴；`resolveWebSocket` 中「行已是 SUPPRESSED_WS 的重复回调」触发的 warn 文案（"WS result arrived after webhook dispatch"）在重复调用场景下略有误导，可顺带区分。

#### L-2 被取代消息回滚后未向 WS 客户端补发删除事件，前端残留幽灵消息；且回滚分支无单测覆盖

- 位置：`backend-ts/src/weixin/agent-inbound-handler.ts` `onMessage`（约 129 行）与 `runAgent` skip 分支（约 146-158 行）
- 场景：`user_message_saved` 事件在消息落库后立即广播给 WS 客户端；当该消息随后被更新消息取代时，服务端回滚了 DB 记录，但未补发任何「消息已删除」类事件。桌面端会话历史中会保留一条 DB 中已不存在的 USER 消息（幽灵消息），刷新会话后才消失。同时，新增加的 skip 分支回滚逻辑没有专门的单测（现有 flow 测试覆盖的是 cancel 路径；skip 路径下 mock 的 sessionService 未实现 `deleteMessageById`，靠可选调用静默跳过而通过）。
- 影响：LLM 上下文污染（本次修复目标）已正确解决；此为前端展示一致性问题 + 测试缺口，不阻塞。
- 建议：回滚成功后向 `registry` 补发一个消息删除事件（若前端已有对应事件类型，如删除/截断类 wsEvent）；为 skip 分支补充一个用例：gen1 在锁等待中被 gen2 取代，断言 `deleteMessageById` 以 (sessionId, gen1 的 messageId) 被调用、gen2 正常执行。

#### L-3 updatePhase(RESUMING) 之后的异常会使会话 phase 停留在 RESUMING

- 位置：`backend-ts/src/session/ws/streaming-ws-handler.ts` `handleRetryExecution`（约 765-775 行）
- 场景：若异常发生在 `updatePhase(sessionId, 'RESUMING')` 成功之后（候选抛点：`registerCancelFlag`/`clearActiveToolCalls`/`failAllForSession`/`registry.send`，实际均几乎不可能抛出），catch 会释放 claim 与 flags，但 phase 停留在 RESUMING。后续重试被 `isTerminalPhase` 拒绝（"任务尚未结束"），CrashRecoveryRunner 仅在进程启动/延迟恢复时扫描，运行期不会自动收敛。
- 影响：概率极低；且相比修复前（claim 永久占用导致会话永久 busy），本次修复已消除了更严重的后果，属改进后的残余边界。
- 建议（可选）：catch 中检测「phase 已被本次置为 RESUMING」时回写 FAILED 或 CANCELLED 终态，保证状态收敛。

### Info（无需处理，仅记录）

1. **回滚失败仅 warn**：`deleteMessageById` 抛异常时跳过回滚并 `console.warn`，行为退化为修复前的孤立 USER（有日志可查），符合可接受的降级预期。注意此路径仅是容错，不应视为功能回退。
2. **grep 10MB 上限与 rg 分支语义差异**：rg 分支 `maxBuffer` 是整个 stdout 的总量上限（超限整体失败），回退分支是单文件跳过，两者对超大文件的表现不同；作为无 rg 环境的防 OOM 手段合理，注释已说明。
3. **`deleteMessageById` 为 SessionService 公共方法**：当前仅被 weixin handler 内部调用（sessionId 源自 `getOrCreateWeixinSession`，非用户直接输入），无越权面；未来若经 REST 暴露，需补充归属校验。
4. **git 注释合规**：`globToFileRe` 上方注释以行注释书写，避免了块注释中 `*/` 提前终止的问题，符合注释中的自我说明。
