## 高（H）

### H-1 useStreamWS：settle 句柄（resolveRef/rejectRef）放在 composable 实例作用域，与模块级 connectPromise 生命周期错位，多实例场景下存在「Promise 永不 settle」的悬挂风险

**位置**：`desktop/src/composables/useStreamWS.ts`
- 151–155 行：`resolveRef` / `rejectRef` 声明在 `useStreamWS()` 函数体内（实例级）
- 195 行：`connectPromise` 为模块级单例
- 253–266 行：onclose 早退分支
- 302–326 行：`disconnect()`

**问题分析**：
`useStreamWS()` 在多个组件/模块中被独立调用（`useChat`、`SideChatPanel`、`SubagentChatPanel`、`useForegroundRecovery`、`stores/auth.ts` 登出），每个调用产生一套独立的 `resolveRef/rejectRef`；而 `connectPromise`、`ws`、`intentionalClose` 是模块级共享。两个层次不对齐，产生两类错位：

1. **disconnect() 无法 settle 未完成的连接 Promise（跨实例幽灵句柄）**。
   `disconnect()` 中 `rejectRef?.(new Error('WebSocket connection cancelled'))` 读的是**调用 disconnect 的那个实例**的句柄。实际调用方 `auth.ts:54` 是 `useStreamWS().disconnect()`——每次登出/401 强制下线都创建**全新实例**，其 `rejectRef` 恒为 null。
   时序：实例 A（如 useChat）`connect()` 进行中（`connectPromise = pA`，句柄在 A）→ 登出触发实例 B 的 `disconnect()`：`connectPromise = null`（模块级，生效），但 `rejectRef` 为 null，**pA 无人 settle**；随后 A 的 socket 因 `ws.close()` 迟到 onclose，走早退分支，此时 `connectPromise` 已为 null → 跳过 settle。**pA 永不 settle**，实例 A 中 `await connect()` 的调用方永久悬挂（useChat 的 `sendMessage`/`editAndResend` 直接 `await connect()`，无超时；仅 `sendReliable` 有 15s withTimeout 兜底）。本次修复想解决的「输入框锁死」问题在该路径下依然存在，只是从「后续 connect 返回死 Promise」变成了「在途 await 悬挂」。

2. **迟到 onclose 会错误地置空/占用不属于它的当前连接 Promise**。
   早退分支 `if (connectPromise && socketRef === socket)`：`socketRef` 就是本闭包创建的 socket，该条件**恒为 true**，等于没有保护。旧 socket 的迟到 onclose 只要发现模块级 `connectPromise` 非空就执行 `connectPromise = null` 并调用**本实例**的句柄。若此时 `connectPromise` 已被其它实例的下一轮 `connect()` 覆盖为 pC，旧连接的关闭事件会把 pC 从模块级「注销」；随后若 pC 的 socket 又被更新的 connect 顶替（`socket !== ws` 早退，不 settle），**pC 永不 settle**，等待它的调用方永久悬挂。

**修复建议**：
把 settle 句柄与 connectPromise 绑定在同一层级——推荐提升到模块级，如 `let pendingSettle: { resolve: () => void; reject: (err: Error) => void } | null`，在每轮 `connect()` 创建 Promise 时写入、settle 处清空；`disconnect()`、onclose（正常与早退分支）都读写同一模块级结构，并可顺带用 `pendingSettle.socket === 本轮socket` 做真正的归属校验（替代恒真的 `socketRef === socket`）。

## 中（M）

### M-1 ChatInput：URL/路径排除正则 `[/.@:\\]` 误伤「名称含点/斜杠/@/冒号的指令」的自动补全

**位置**：`desktop/src/components/chat/ChatInput.vue:883–887`（`detectAutoComplete()` 新增排除）

```ts
if (/^(https?|ftp|file):\/\//i.test(currentWord) || /[/.@:\\]/.test(currentWord)) {
  if (panelVisible.value && autoComplete.value) closePanel()
  return
}
```

**问题分析**：
- 已核实**显式 `/` 触发不受影响**：`onUpdate` 中 `detectSlashTrigger()` 先执行并打开面板（`autoComplete` 为 false），`detectAutoComplete()` 开头的守卫 `if (panelVisible.value && !autoComplete.value) return`（851 行）会先行退出，排除逻辑不会关闭 slash 面板。此链路安全。
- 但**按名称自动补全**（autoComplete 模式）会受影响：匹配逻辑是 `cmd.name.toLowerCase().startsWith(lower)`，指令名本身可含 `.`（如 `git.commit`、`npm.run` 这类用户自定义快捷指令或技能名）。用户输入 `git.` 时，`currentWord` 含 `.` 命中排除集，面板被关闭——**此类指令从此无法通过输入自动补全**，属于本次修复引入的功能回退。
- 另外 `@`、`:` 同理（如 `user@host` 形式的指令名），`/` 对无协议前缀的路径词（`src/index`）也生效——后两类属于可接受的误伤设计，但指令名含 `.` 的场景是真实的常用路径。

**修复建议**：
排除条件对「显式触发符开头」的词放行（`/`、`、` 开头是触发语法本身）：在排除前加 `if (currentWord.startsWith('/') || currentWord.startsWith('、'))` 跳过 URL/路径排除（显式场景本就由 detectSlashTrigger 接管，此处只是防御性放行）；或收窄正则，仅排除协议前缀、形如 `./`、`../`、`~/` 的路径与含 `@` 且形如邮箱/域名的词。

### M-2 useStreamWS：`scheduleReconnect` 丢弃 `connect()` 返回的 rejected Promise，未登录窗口产生 unhandled rejection

**位置**：`desktop/src/composables/useStreamWS.ts:329–338`（`scheduleReconnect()`）、186–188 行（无 token 时 `return Promise.reject(new Error('No token'))`）

**问题分析**：
`reconnectTimer = setTimeout(() => { ...; connect() }, ...)` 未接 `.catch()`。登出/401 下线后（token 已清）若 reconnectTimer 已排队，到期后 `connect()` 返回 rejected promise 且无人捕获 → unhandled rejection（控制台报错，某些全局错误上报/提示组件会误报）。该问题为存量，但本次改动正好触碰 disconnect/reconnect 生命周期，顺手修复成本低。

**修复建议**：`scheduleReconnect` 内改为 `connect().catch(() => {})`。

### M-3 disconnect() 清空 pendingCallbacks，使 useChat 等待执行完成的 Promise 永不 settle

**位置**：`desktop/src/composables/useStreamWS.ts:327–333`（`pendingCallbacks.clear()` 等）；`desktop/src/composables/useChat.ts`（`await new Promise((resolve, reject) => { pendingCallbacks.set(sid, { resolve, reject }) })`）

**问题分析**：
本次在 disconnect 中新增 `pendingCallbacks.clear()`（防换号串用户，方向正确）。但 useChat 发送消息后 `pendingCallbacks.set(sid, ...)` 等待终态事件 resolve；若执行中恰逢登出/401 下线，Map 被清空，该 await 永久悬挂、`sending.value` 停留 true。目前因下线必然跳转登录页、聊天组件卸载，用户可见影响有限（悬挂 promise 仅泄漏），故列中低。更稳妥做法：clear 前对每个 cb 调用 `cb.reject?.(new Error('已登出'))`，语义完整。
