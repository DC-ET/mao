## 一、用户三个核查点的结论

### 1. progress 判据的遗漏场景 —— ⚠️ 存在 1 个低概率遗漏（可接受）

**遗漏场景：progress 卡在 <100 且 WebView 冻结 → 不可恢复**
- 若页面已可交互但某子资源挂起（iframe / 字体 / 慢图片 / 长轮询）导致 progress 停 <100，此时切后台被冻结，回前台探测被 `progress < 100` gate 跳过 → 不 reload → 用户卡死。
- **概率评估**：本 App 远程加载 SPA、无 iframe、Monaco 按需加载，实际触发概率低；且该状态与「弱网加载中」无法区分（这正是 gate 要防的误判），属**刻意取舍**——当前设计宁可漏掉此低概率场景，也要防弱网首屏误 reload。
- **SPA 加载完成但 progress 未到 100 的边界**：Android WebView 的 progress 随主文档+子资源加载推进，history API 客户端路由不改变 progress；"DOM 可交互但 progress<100"只会在上述挂起子资源场景出现，与上同。

### 2. reload 后 progress 重置 —— ✅ 自动避免重载期间连环 reload

- `webView.reload()` 将 progress 重置为 0 再爬升，网络重载阶段 `progress < 100` → 探测跳过 → 不触发二次 reload。✅ **彻底解决了上轮 `everResponded` 不复位导致的弱网连环刷新问题**（比 everResponded 方案更优）。
- 残余窗口（低概率）：网络完成后（progress=100）JS 重新初始化（Vue/Monaco）期间若切后台→回前台且渲染进程忙 >3s，可能误 reload 一次；10s 防抖限频，最多一次，可接受。

### 3. 完整探测逻辑的竞态与主场景 —— ✅ 无竞态、主场景已恢复

**主场景验证（上轮缺口，现已修复）**：
冷启动 → 首屏加载完成（progress=100）→ 正常使用 → 切后台冻结 → 回前台 → 探测放行（progress 保持 100，页面已提交）→ evaluateJavascript 无回调 → 3s 超时 → reload。✅

**竞态全路径复核（均通过）**：
| 场景 | 结果 |
|------|------|
| onStart→onStop→onStart（2s 窗口内） | onStop `removeCallbacksAndMessages` 取消排队任务 → 重新排定全新探测，无双重探测 ✅ |
| 探测进行中（probing=true）切后台再回 | onStop 取消超时任务 + 重置 probing → onStart 重新调度 ✅ |
| 探测进行中 Activity 销毁 | onDestroy 清理 + 回调处 `isFinishing/isDestroyed` 校验 ✅ |
| 探测期间切后台（后台 reload 防护） | onStop 取消超时任务，回调不会在后台执行 ✅ |
| probe 因 progress<100 提前 return | 返回发生在置 probing=true 之前，无残留标志 ✅ |
| 超时与 evaluateJavascript 回调主线程竞争 | 同 Looper 串行；回调晚到仅造成边缘一次 reload（10s 防抖兜底）✅ |

三重防护（onStop 取消任务 + probing 标志 + 主线程串行）自洽，无竞态。
