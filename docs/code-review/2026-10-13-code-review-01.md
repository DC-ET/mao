## BUG-1 点「停止」后终态重拉先于服务端 CANCELLED 帧落地，已流出的部分回复被永久丢弃（desktop，P1）

**位置**
- `desktop/src/composables/useChat.ts:640-670`（`stopExecution`，661 行乐观置 CANCELLED，不打中断标记）
- `desktop/src/composables/useChat.ts:813-835`（phase watcher 终态分支，833 行 `fetchMessages()` 不传 `preserveLiveStream`）
- 下游：`desktop/src/stores/session/messages.ts:188-191`（tail 规则丢弃 tracked 流式气泡）、`:209-216`（删注册）、`:531-534`（`finishInterruptedStreamingMessage` 无 liveId 直接早退）

**关键代码**

```ts
// useChat.ts:661（stopExecution）
sessionStore.updateSessionPhase(sid, 'CANCELLED')   // 只清 sending/streaming 标志，不标记中断气泡
// useChat.ts:833（watcher 终态分支）
fetchMessages()   // 不带 preserveLiveStream → applyFetchedMessages 删气泡 + 删注册
```

**根因**：被中止轮次服务端从不落库流式文本（已复证 `cleanupIncompleteTail`/`markLastMessageFinished` 只补工具结果、只碰已存在的最后一条消息，`session.service.ts:1276-1303,1373-1384`），本地气泡是唯一副本。`stopExecution` 先把 phase 置 CANCELLED 触发 watcher 重拉，而重拉发生在迟到数个 DB 跳数的服务端 CANCELLED 广播之前——气泡被当「REST 覆盖范围的尾部残留」删除、注册被清，随后帧里的 `finishInterruptedStreamingMessage` 空转，内容永久丢失（刷新也回不来）。REST GET 在停止点击后一个 tick 内即发出，服务端广播要多个数据库跳，**REST 响应通常先落地，是常见情形而非罕见竞态**。

与 2026-10-12 round2「BUG-8」的关系：那轮修复（`040bf4ca`）只改了 `stores/session/messages.ts`，让**已被标记中断**的气泡在重拉后保留；但 `stopExecution` 与 error 帧两条路径在重拉前从未打中断标记，气泡还不是「中断气泡」就被 tail 规则删掉。本轮 BUG-1/BUG-2 是同一机制在新路径上的残留，不是重复报告。

**触发场景**：流式输出中点「停止」→ 已流出的半段回复从对话区凭空消失，只剩用户消息。

**验证用例**（`desktop/src/zz-probe-desktop-1.test.ts`，真实 useChat + 真实 session store，mock ws/api）：

```
× 部分流式回复不得因「先重拉、后收 CANCELLED 帧」而丢失
AssertionError: expected [ 'user' ] to deeply equal [ 'user', 'assistant' ]
Tests  1 failed | 2 passed (3)
```

对照组 A（CANCELLED 帧先打中断标记、后重拉）与对照组 B（正常完成按 REST 覆盖、不重复）均通过——证明断言非空转，问题纯在顺序。既有 `session-streaming-bubble.test.ts` 只覆盖了「先标记后重拉」的安全序，未覆盖生产实际顺序。

**修复方向**：watcher 终态分支（或 `stopExecution`）在重拉前先 `finishInterruptedStreamingMessage(sid, '执行已被中止')`；或让终态回传的 `fetchMessages` 传 `preserveLiveStream: true`（REST 本就不会返回该气泡，保留无副作用）。

## BUG-2 WS `error` 帧分支不标记中断气泡，终态重拉同样丢弃部分回复（desktop，P2）

**位置**
- `desktop/src/composables/useStreamWS.ts:1138-1164`（`case 'error'`：1153 行只调 `resetSessionStreamState`，不调 `finishInterruptedStreamingMessage`；与 `session_status` 终态分支 `useStreamWS.ts:701-709` 对 CANCELLED/FAILED 的处理不对称）
- 下游与 BUG-1 同一丢弃链：useChat watcher 终态分支 → `applyFetchedMessages`
- 后端依据 `backend-ts/src/session/ws/streaming-ws-handler.ts:730-733`：`error` 帧必先于 `finishFailedSession` 的终态 `session_status` 帧发出

**关键代码**

```ts
// useStreamWS.ts:1149-1153（error 分支）
sessionStore.setExecutionError(sessionId, message)
sessionStore.updateSessionPhase(sessionId, 'FAILED' as TaskPhase)  // 客户端自己翻终态
resetSessionStreamState(sessionId)   // 不清 running 工具、不标记中断、不保留气泡
```

**根因**：`error` 帧由客户端自己把 phase 置 FAILED，watcher 立即触发不带 `preserveLiveStream` 的重拉，气泡被删、注册被清；迟到的终态 `session_status FAILED` 帧再调 `finishInterruptedStreamingMessage` 已空转。与 BUG-1 不同，这里是**确定性顺序**（不是竞态）：后端先发 `error` 帧再走 `finishFailedSession`，每次执行中失败都丢失已流出的部分回复。

**触发场景**：Agent 执行中后端抛错（LLM 调用失败、LOCAL 技能同步失败等）→ 顶部出现错误横幅，同时已流出的半段回复从对话区消失。

**验证用例**（`desktop/src/zz-probe-desktop-3.test.ts`，真实 useStreamWS + FakeWebSocket + 真实 useChat，按后端真实帧序投递 RUNNING → error → session_status FAILED）：

```
× error 帧置 FAILED 后的终态重拉必须保留部分回复（与 CANCELLED 帧路径对称）
AssertionError: expected [ 'user' ] to deeply equal [ 'user', 'assistant' ]
Tests  1 failed | 1 passed (2)
```

对照组（正常完成：message_end + COMPLETED，REST 含完整回复，不重复不留残）通过。

**修复方向**：`error` 分支补 `sessionStore.finishInterruptedStreamingMessage(sessionId, '执行失败中断')`，与 `session_status` 终态分支对称（顺带能把仍在 running 的工具就地终结）。

## BUG-3 编辑重发的占位气泡未注册进流式表，首包 delta 新建气泡（desktop，P2）

**位置**
- `desktop/src/composables/useChat.ts:762-771`（`editAndResend` 手搓 placeholder 走 `appendMessage`，不写 `streamingAssistantMessageIds`；对比 `prepareAndSendMessage` 的 `useChat.ts:488-489` 用 `ensureStreamingAssistantMessage` 并注册）
- `desktop/src/stores/session/messages.ts:337-353`（`ensureStreamingAssistantMessage` 认不出尾部未注册气泡即新建）

**关键代码**

```ts
// useChat.ts:763-771（editAndResend）
const placeholderMsg: ChatMessage = { id: `msg_${Date.now()}_assistant`, role: 'assistant', content: '', ... }
sessionStore.appendMessage(sid, placeholderMsg)   // 未注册！首个 content_delta 会再建一条
```

**根因**：乐观截断后追加的占位气泡没有登记为「本轮流式气泡」。服务端重新执行、首个 `content_delta` 到达时，`appendDelta → ensureStreamingAssistantMessage` 发现尾部 assistant 的 id 不在注册表里，判定「不是本轮气泡」而追加第二条 assistant。

**触发场景**：编辑最后一条用户消息并重发 → 整个流式期间对话区多出一条空 assistant 气泡，回合头部显示「已执行 1 个步骤」（实际 0 步）；同一轮回复视觉上被劈成「空 + 新起一段」。终态重拉后会自愈，但每次编辑重发必现。

**验证用例**（`desktop/src/zz-probe-desktop-2.test.ts`）：

```
× 编辑重发：首个 content_delta 必须落到重发自带的占位气泡上
AssertionError: expected [ 'user', 'assistant', 'assistant' ] to deeply equal [ 'user', 'assistant' ]
Tests  1 failed | 1 passed (2)
```

对照组（普通发送路径先 `ensureStreamingAssistantMessage` 再 delta，复用同一气泡）通过。

**修复方向**：把 `appendMessage(sid, placeholderMsg)` 换成 `ensureStreamingAssistantMessage(sid)`（或补登注册），与 `prepareAndSendMessage` 保持一致。

## BUG-4 会话分组口径漂移：embed 会话泄漏进同工作区的 CLOUD/LOCAL 分组（backend-ts，P2）

**位置**
- 分组键生成（唯一口径）：`backend-ts/src/session/util/session-group-key.ts:89-107`（`of` / `ofMode`）
- 分组过滤（漂移源头）：同文件 `:171-228`（`applyFilter`），其中 `CLOUD:<ws>` 在 `:221-226`、`LOCAL:<ws>` 在 `:209-214`、`LOCAL:未设置` 在 `:203-208`、`CLOUD:临时工作区` 在 `:215-220`（唯一带了 embed 排除的桶）
- 受影响的两个 API：`backend-ts/src/session/session.service.ts:249-277`（`listSessionGroups`，按 `of()` 分组）与 `:279-312`（`listSessionsByGroup`，按 `applyFilter()` 过滤）
- embed 会话来源：`session.service.ts:337-350`（`markSessionSource`，web → embed 单向惰性迁移，保留原 workspace 与 execution_mode）

**关键代码**

```ts
// session-group-key.ts:91-93（of：source=embed 优先分流，一个会话只产出一个 key）
if (sessionOrMode.source === 'embed') return `${EMBED_PREFIX}${sessionOrMode.agentId ?? 'null'}`;
// session-group-key.ts:221-226（applyFilter 的 CLOUD:<ws> 桶：只按 execution_mode + workspace 精确匹配，无 embed 排除）
if (groupKey.startsWith('CLOUD:')) {
  return { clauses: ['execution_mode = ?', 'workspace = ?'], params: ['CLOUD', groupKey.slice(6)] };
}
```

**根因**：`of()` 的分流优先级是 `source=embed` > 飞书/钉钉 > 模式+工作区，一个会话只产出一个 key。但 `applyFilter()` 只在 `CLOUD:临时工作区` 桶补了 `(source IS NULL OR source != 'embed')`（`:217`），`CLOUD:<ws>`（`:221-226`）、`LOCAL:<ws>`（`:209-214`）、`LOCAL:未设置`（`:203-208`）三个桶全是「模式 + workspace 精确相等」，**没有把 `of()` 已经优先分流走的 embed 会话排除掉**。embed 会话由普通会话惰性标记而来、保留原 workspace，与普通会话同工作区是常见形态，于是展开分组时同一条会话出现在两个分组里。

> **复证校正（2026-10-13）**：round 1 原文另称「飞书/钉钉私聊会话 workspace 仍是普通 `/projects/...` 路径，也会泄漏进 `CLOUD:<ws>`」——与现状不符。飞书/钉钉私聊会话的 workspace 分别是 `{root}/feishu-chat/{账号}/private-{userId}`（`create-app.ts:348-353,1590-1605`）和 `{root}/dingtalk-chat/{botId}/…`（`dingtalk/workspace.ts:5-9`），`of()` 对它们走 `FEISHU_PRIVATE` / `DINGTALK_PRIVATE` 分支；能命中它们的 `CLOUD:<chat 工作区>` 键在生产中不会产生（机器人会话必被 `of()` 分流到 `FEISHU_*`/`DINGTALK_*`，普通会话的 workspace 不会落在渠道目录下），该泄漏路径不可达。探针 1 枚举出的 11 处漂移里，**生产可达的只有 embed 相关各项**；转正回归时应以探针 2 的端到端断言为准，或先剔除探针 1 中的不可达形态。

**触发场景**：用户在项目 X 有普通 CLOUD 会话（workspace `/data/workspace/projects/proj`），又把该项目的一个会话嵌进自家站点（`source='embed'`）。侧边栏预览显示 `proj`（total=1）与 `EMBED:9`（total=1）互不重叠；点 `proj` 的「展开更多」→ `GET /v1/sessions?groupKey=CLOUD:/data/workspace/projects/proj` 返回 **2 条**，同一条嵌入会话在两个分组各出现一次，`total` 由 1 变 2，`hasMore`/分页偏移错乱。

**验证用例**
- 探针 1（过滤器语义层，`src/session/zz-probe-sess-1.spec.ts`）：用内存 SQL 子句求值器对 15 种会话形态 × 全部可达分组键逐一代入 `applyFilter()`，断言「每个会话只属于 `of()` 指出的那一个分组」。失败摘要：`分组口径漂移 11 处`（含不可达形态，见上方校正）。
- 探针 2（端到端 API 层，`src/session/zz-probe-sess-2.spec.ts`）：驱动真实 `SessionService.listSessionGroups` / `listSessionsByGroup`：

```
FAIL ... 嵌入 SDK 会话只出现在 EMBED 分组，不挤进同工作区的 CLOUD 分组
AssertionError: expected 2 to be 1   ← listSessionsByGroup('CLOUD:/data/workspace/projects/proj').total
Tests  1 failed | 1 passed (2)
```

同文件中「`listSessionGroups` 只产出两个键且各 total=1」这条断言**通过**——即预览口径正确、展开口径错误，漂移被精确定位在 `applyFilter()`。同文件「飞书私聊会话只出现在 FEISHU_PRIVATE 分组」（使用真实 `feishu-chat` 工作区）亦通过。对照组：`npx vitest run src/session` → 504 条存量用例全绿，仅 3 条探针失败。

**修复方向**：给 `CLOUD:<ws>`、`LOCAL:<ws>`、`LOCAL:未设置` 三个桶都补上 `(source IS NULL OR source != 'embed')`，与 `CLOUD:临时工作区` 桶（`:217`）对齐。更稳的做法是让两端共用一份「会话 → 分组键」判定（例如 `applyFilter` 内部对每个候选行反算 `of(row)` 并比对），从结构上消除两处漂移。

## BUG-5 agent-cli LOCAL 工具用 `Number(x) || 默认值` 解析数值参数，非法值静默改语义且与云端分叉（agent-cli，P2）

**位置**
- `agent-cli/src/local/tools/files.ts:258`（read_file `limit`）
- `agent-cli/src/local/tools/search.ts:108`（glob `head_limit`）
- `agent-cli/src/local/tools/search.ts:297`（grep `max_output_chars`）

**关键代码**

```ts
// files.ts:258
const limit = args.limit != null ? Math.max(0, Number(args.limit) || 0) : Number.MAX_SAFE_INTEGER;
// search.ts:108
const headLimit = Number(args.head_limit ?? 100) || 100;
// search.ts:297
const maxOutputChars = Number(args.max_output_chars ?? 10000) || 10000;
```

**根因**：`Number(x) || default` 把三种完全不同的情况压成同一个结果——非数字（`NaN`）、合法 `0`、以及「未传」都落回默认值，负数则原样透传。而云端口径（`backend-ts/src/harness/tool/json.ts:24-31` 的 `asInt`：仅对非有限数回落 fallback，`0` 原样保留；`glob-search-tool.ts:57-59` 显式校验 `head_limit` 必须为正整数否则报错）三者是分开的。于是 LOCAL 与 CLOUD 对同一份 LLM 生成的参数给出不同结果。

> **复证补注（2026-10-13）**：agent-cli 的 grep `ignore_case`（`search.ts:294-295`）本就接受 `true / 1 / 'true' / '1'`，不在此 BUG 范围；受影响的确实是上述三处数值参数。

**触发场景与用户可见损害**（模型吐出畸形参数时，本地与云端结论相反）：
- `read_file {limit:"abc"}` 或 `{limit:""}`：云端读全文件，LOCAL 返回**空 content**（`NaN || 0 = 0`）。模型看到空内容会认为文件是空的，进而在 `write_file` 里整体覆写 → **文件内容被清空的数据丢失风险**。
- `glob {head_limit:0}`：云端报错「必须为正整数」，LOCAL 静默按 100 返回**全部文件**（模型要 0 条却拿到全部）。
- `glob {head_limit:-2}`：LOCAL 不报错，负数流入 `globWithRg` 的 `.slice(0, -2)`，变成「**全部结果砍掉末尾 2 条**」且 `truncated:true`——实测 6 个文件返回 4 条的毫无语义子集。
- `grep {max_output_chars:0}`：云端预算为 0、返回 0 条；LOCAL 回落 10000 **全量输出**，把模型的输出预算约束整个作废。

**验证用例**（`agent-cli/test/zz-probe-cli-1.spec.ts`）：`Tests 5 failed (5)`，失败摘要：

```
expected '' to be 'l1\nl2\nl3'                                  ← limit 非法/空串各一条
expected undefined to be truthy ×2                              ← glob 应报错
expected 3 to be +0                                             ← grep 预算 0 应无匹配
```

诊断脚本另确认 `head_limit=-2` 返回 4 条、`head_limit=0` 返回全部 6 条。对照组（`test/args.spec.ts`、`local-files.spec.ts`、`local-search.spec.ts` 等 80 条）全绿——合法数值路径全部正确，探针只隔离出非法值路径。

**修复方向**：三个工具统一改用与云端一致的 `asInt` 语义（非有限数才回落、`0` 原样保留），并给 glob 补 `head_limit` 正整数校验；或直接复用/下沉一份共享的 `asInt` 实现，避免两端再次分叉。

## BUG-8 `withUserLock` 锁表清理条件永假，`userLocks` 按 userId 无界泄漏（backend-ts，P3）

**位置**：`backend-ts/src/weixin/session.service.ts:81-93`

**关键代码**

```ts
this.userLocks.set(userId, prev.then(() => current));   // 存入「链式 promise」
...
release();
if (this.userLocks.get(userId) === current) this.userLocks.delete(userId);  // 与 current 比 → 永假
```

**根因**：Map 里存的是 `prev.then(() => current)`（chained），finally 里却拿 `current` 比较，两者永不为同一对象，`delete` 永不执行。这是典型的「存/比不同引用」错误模式——`weixin/agent-inbound-handler.ts:381-383` 的注释明确把「若与 current 比较，条件永假导致 Map 条目按 sessionId 泄漏」列为反面教材；全仓其它 `withLock` 实现（`feishu/agent-inbound-handler.ts:899-911`、`feishu/inbound-processor.ts:51-62`、`feishu/message.service.ts:338-351`、`dingtalk/agent-inbound-handler.ts:580-605`、`weixin/agent-inbound-handler.ts:378-393`）都是存/比同一个引用。git blame：引入于 `f5b84551`，之后未改。

**触发场景**：进程长跑的微信 Bot 服务，每有一个 userId 调用过一次 `getOrCreateWeixinSession`（即每个微信用户发过消息），`userLocks` 就永久多一个条目。用户量上来后 Map 无界增长。

**验证用例**（`backend-ts/src/weixin/zz-probe-weixin-2.spec.ts`）：

```
× E1 单用户调用返回后，userLocks 不应残留该 userId 条目（expected 1 to be +0）
× E2 连续 20 个不同 userId 调用后，锁表不应随用户数增长（expected 20 to be +0）
Tests  2 failed | 2 passed (4)
```

对照组：E3 同用户并发仍只 `createSession` 1 次（串行化语义未被破坏）；E4 泄漏后同用户再次调用仍返回正确 sessionId（无死锁、无串味）——证明泄漏是唯一后果。

**修复方向**：把存储与比较统一到同一引用（`const chained = prev.then(() => current); this.userLocks.set(userId, chained); ... if (this.userLocks.get(userId) === chained) this.userLocks.delete(userId);`），与其它 withLock 实现对齐。

## 其他观察（未验证，不计入正式结论）

以下推演成立但**无法用失败探针复现**或属设计取舍，仅备查：

1. **异步 exec 不刷新 currentWorkdir**（`harness/tool/impl/shell-session-tool.ts:205` 用 `session.currentWorkdir`，同步路径 `:227` 却调 `resolveCurrentWorkdir`）：异步 `cd sub && pwd` 后该字段保持旧值，`handleList` 也报旧值。当前被 BUG-6 掩盖（字段反正被丢弃）；若按 BUG-6「展开 parsed」方案修复会立刻暴露，两者应一起修。
2. **`normalizeResult` 的 400 字符预留偏紧**（`harness/core/background-task-manager.ts:131`）：最坏情况合计约 9.7-9.8k，距 `MAX_RESULT_LENGTH=10000` 余量很小；若 `wait_for` 200 字符或 message 300 字符上限上调，外层 `text.slice(0, 10000)` 会拦腰切断 JSON。
3. **grep rg 路径 entrySize 双重计费**（`harness/tool/impl/grep-search-tool.ts:126`）：`JSON.stringify(entry).length + path.text.length + content.length`，path/content 已含在 JSON 里；JS 回退路径（`:150`）只算 `JSON.stringify(entry).length`。同预算下 rg 少返回约一半条目。方向保守，但两条路径口径不一致。
4. **`extractActivityTarget` 工具名过期**（`session/ws/ws-streaming-event-listener.ts:368-369`）：switch 的是 `'glob'`/`'list'`，注册名是 `glob_search`/`task_list`，glob 搜索记不到活动目标。
5. **`sendMessage` 完成回调读活跃会话而非本次发送 sid**（`desktop/src/composables/useChat.ts:527-574`）：执行中切走会话会把耗时写到别的会话最后一条回复、并对新会话做一次非 preserve 重拉（可再触发 BUG-1 式丢弃）。该函数当前无生产调用方（仅测试用），用户不可见。
6. **`quick-command-parser.ts:43-53` 嵌套/交叠标记**（如 `${@{a}@}$`）会使 `lastIndex` 回退，产生重复/错位 segment；需病理输入才触发。
7. **`updateTask` 改 cron 同时正等待一次性重试**（`harness/…/scheduled-task.service.ts:426-443`）：换 cron 且仍在等重试时会重算 `nextFireTime` 并清 `finished`，可能与重试入口叠档。代码注释表明是刻意取舍。
8. **`listSessionGroups` 的 `previewLimit` 未设上限**（`session/session.service.ts:250`）：客户端传极大值会把全量会话拉进预览。属客户端可控参数。
9. **`of()` 大小写敏感 vs MySQL 默认排序规则大小写不敏感**：迁移脚本未显式声明 `COLLATE`，表继承库默认 `utf8mb4_0900_ai_ci`，`workspace = ?` / `LIKE` 在 MySQL 侧大小写不敏感而 `ofMode` 用 JS `includes`（大小写敏感）。workspace 为 `/data/FEISHU-CHAT/1/x` 时预览可见、展开消失。触发条件偏窄。
10. **`feishu/doc-reader.ts:36` base 类型链接用 `doc_type:'docx'` 请求 content 接口**：飞书侧对 base token 是否返回可读 markdown 未实测，可能只拿到 API 错误（有二跳错误味道，无本地证据）。
11. **`agent-cli` `--print=false` 反向陷阱**：`print` 是 `kind:'optional'`（值即 prompt），`--print=false "问题"` 得到 `print=true, prompt="false\n<问题>"`——用户想关打印模式反而进了打印模式。因该 flag 的 `=` 值按设计就是 prompt，是否算 bug 取决于产品口径。
12. **`config-store` 跨进程读-改-写竞态**：`saveUserConfig` 无文件锁，两个 mao-agent 进程同时写 `~/.mao/agent-cli/config.json` 可能互相覆盖。属设计限制、复现窗口小。
13. **`sdk/embed/src/ui/historyTime.ts` 的 DST 边界**：`dayDiff` 用 86400000 整除取 floor，夏令时地区「N 天前」可能少算一天；Asia/Shanghai 无 DST，实际用户不可见。
14. **AppUpdatePlugin 空 body 边缘情形**（`android/.../AppUpdatePlugin.java:138`）：HTTP 200 但 body 为空时 `tmp.length() > 0` 不成立，直接返回旧的 `mao-update.apk`（可能是上一次下载的残留），未经验证即拉起安装器。
