# 代码审查报告

## 一般问题

### 1. `subagent_followup` 在任务提交失败时会遗留 RUNNING 子会话，阻塞后续追问

- 位置：`backend-ts/src/harness/delegate/background-subagent-manager.ts:136-140`、`backend-ts/src/harness/delegate/background-subagent-manager.ts:324-347`、`backend-ts/src/harness/delegate/subagent-invocation.service.ts:89`
- 相关代码：
  - `createFollowupWithOptions()` 先在事务内把子会话 `phase` 更新为 `RUNNING`，并创建 `status: 'RUNNING'` 的 FOLLOWUP execution 与用户消息。
  - 之后 `submitExecution()` 可能失败；失败时只把 execution 更新为 `FAILED`，没有恢复/终结 child session 的 phase，也没有通知可见性服务完成。
- 问题说明：
  如果线程池拒绝提交或 `agentExecutor.submit()` 抛错，工具会返回失败，但子会话已被置为 `RUNNING`。后续再次追问时，`createFollowupWithOptions()` 会因为 `child.phase === 'RUNNING'` 返回 null，用户无法继续追问；前端也可能持续显示子代理运行中。

  `spawn_subagent` 首次创建在提交失败时也有类似可见状态不一致风险；但 FOLLOWUP 更容易影响业务，因为它会把一个已有子代理会话卡在 `RUNNING`，阻断该子代理的后续追问/纠偏。
- 修复建议：
  在 `submitExecution()` 的 catch 分支中同步终结子会话状态，例如调用 `visibilityService.finishSubagent(child.id, child.userId, 'FAILED', '')` 或至少 `sessionService.updatePhase(child.id, 'FAILED')`；同时保留 execution 的 `FAILED/SUPPRESSED` 更新。若担心首次 spawn 的子会话也遗留，可统一在提交失败时对传入的 `child` 做可见状态收尾。
