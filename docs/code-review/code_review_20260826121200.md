# 第 10 轮最终代码审查报告

- 审查范围：当前 Git 工作区未提交代码，仅关注本次 OAuth/飞书待绑定消息需求逻辑。
- 结论：发现重大功能 bug，仍需修复；本轮不能通过最终审查。

## 严重程度：高

### 1. 待绑定消息成功执行后没有终态落库，会在后续启动恢复中重复执行

- **位置**：`backend-ts/src/feishu/pending-binding.repository.ts:claim/release/listRecoverable`、`backend-ts/src/create-app.ts:314-324`、`backend-ts/src/create-app.ts:1208-1218`。
- **问题**：恢复或 OAuth 回调路径先将记录从 `SENT` 改为 `CLAIMED`，随后调用 `pendingBindingProcessor.process(..., true)`；但成功返回后没有 `complete`/`DONE` 更新，也没有删除记录。表结构只有 `PENDING/SENT/CLAIMED/FAILED`，因此成功记录永久停留在 `CLAIMED`。超过 10 分钟后，下一次启动的 `listRecoverable()` 会再次列出它，`claim()` 会重新领取并再次执行原始消息。
- **影响**：绑定后的原始消息、Agent 工具调用、数据库写入和外部副作用可能重复发生；这违反“绑定后原始消息自动执行并复用同一卡片”的幂等要求，并且会使每次重启都可能重复处理历史消息。
- **修复建议**：增加明确的 `COMPLETED/DONE` 终态及条件更新方法（例如 `complete(state)`，仅 `CLAIMED` 可转移），在 `process` 成功返回后原子落库；失败保留 `SENT` 以便重试。若要求消息服务幂等，也应同时以原始 `message_id` 建立恢复执行边界，不能用 `skipClaim=true` 绕过唯一的入站幂等记录而不补充 pending 终态。

### 2. 卡片已发送但进程在保存 card_message_id 前崩溃时，记录停留 PENDING 且永不恢复

- **位置**：`backend-ts/src/create-app.ts:1032-1060`、`backend-ts/src/feishu/pending-binding.repository.ts:listRecoverable`、`backend-ts/db/migration/V085__feishu_pending_binding_message.sql:8`。
- **问题**：发送绑定卡片前插入 `PENDING`；飞书发送成功后，只有拿到响应并成功执行 `setCardMessageId()` 才变为 `SENT`。若进程在飞书 API 成功返回后、状态更新前崩溃，数据库仍是 `PENDING`，而 `listRecoverable()` 只恢复 `SENT` 或超时 `CLAIMED`，该原始消息和已展示卡片都会永久失去恢复入口。
- **影响**：用户看到绑定卡片并完成 OAuth 后，原始消息可能无法自动执行；这是可复现的崩溃窗口，属于消息丢失/需求主流程失败。
- **修复建议**：设计发送阶段的可恢复协议：为 `PENDING` 增加 lease/超时恢复并记录发送幂等键，或先生成并持久化稳定的发送幂等标识、调用支持幂等的发送接口，再将结果条件更新为 `SENT`；恢复时必须避免无幂等地重复发卡。至少不能让“API 已成功、DB 尚未更新”的窗口成为永久 PENDING。

## 重点核验结果

- **OAuth state 传递**：本轮 GET callback 已将 `state` 传入 `onUserAuthenticated`，上一轮“正常回调不可达”的问题已修复。
- **并发幂等**：OAuth state 使用 `PENDING -> PROCESSING` 条件更新，授权码兑换和状态提交的并发入口基本具备单领取语义；pending claim 的条件更新方向正确，但必须补齐成功终态。
- **SENT/CLAIMED 与启动恢复**：SENT/超时 CLAIMED 可被启动恢复；但成功后无终态导致重复恢复，PENDING 崩溃窗口无法恢复。
- **过期处理**：OAuth PENDING/PROCESSING 的过期检查已覆盖主要路径；pending 消息本身没有业务过期/清理策略，FAILED/PENDING 记录会长期保留，建议补充清理与状态定义。
- **卡片发送失败文本回退**：发送异常或无 message_id 时会标记 FAILED 并回退文本，逻辑符合要求；但“发送成功后持久化失败”的崩溃窗口仍未覆盖。
- **绑定后自动执行及同卡片复用**：state 已传递，恢复时传入 `progressCardMessageId` 并 patch 原卡片，主路径方向正确；但上述终态和 PENDING 恢复问题使其不能保证一次且最终完成。

## 仍需修复的重大问题

1. 为待绑定消息增加成功终态并在执行成功后条件落库，阻止后续重复执行。
2. 为卡片发送与状态持久化之间的崩溃窗口建立可恢复且具发送幂等性的协议，避免 PENDING 永久丢失。
