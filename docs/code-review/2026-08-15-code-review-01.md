# 子代理崩溃恢复功能代码审查报告

- 审查时间：2026-08-15 14:08:29
- 审查范围：当前 Git 工作区中与“子代理运行期间重启后端后，恢复原 execution 并幂等交付父结果，避免父任务重复委派”相关的 `backend/` 与 `backend-ts/` 未提交代码
- 结论：**存在重大功能 Bug，当前版本不应发布。**

## 严重（阻断发布）

### 1. Java 后端无法编译，恢复功能无法启动

**代码位置**

- `backend/src/main/java/cn/etarch/mao/config/DelegateConfig.java:1`：文件已被清空，不再声明 `cn.etarch.mao.config.DelegateConfig`。
- `backend/src/main/java/cn/etarch/mao/harness/delegate/SubagentExecutionRecoveryService.java:3,42`：仍导入并注入 `DelegateConfig`。
- `backend/src/main/java/cn/etarch/mao/harness/delegate/SubagentExecutionRecoveryService.java:83,116`：调用 `waitForLocal(child.getId(), cancelFlag)`，但现存方法签名为 `waitForLocal(Long childId, long deadline, AtomicBoolean cancelFlag)`。

**影响**

执行 `cd backend && mvn -q -DskipTests compile` 时，编译器首先报告 `DelegateConfig.java` 不包含 `DelegateConfig` 类；即使去掉该依赖，`waitForLocal` 的实参与形参数量也不匹配。Java 后端无法构建，更不可能在重启后执行本次恢复逻辑。

**修复建议**

统一超时策略后一次性清理残留：如果本次设计确实移除了委派超时，应删除 `DelegateConfig` 注入、`startedDeadline` 及 deadline 版 `waitForLocal`，并提供与调用一致的可取消等待实现；如果恢复阶段仍需超时，则恢复 `DelegateConfig` 类并显式计算、传入 deadline。修复后至少执行 Java 编译及恢复相关单测。

### 2. Java 与 TypeScript 的 recovery claim 不具备互斥性，同一 execution 可被多个后端实例同时恢复

**代码位置**

- Java：`backend/src/main/java/cn/etarch/mao/harness/delegate/mapper/SubagentExecutionMapper.java:31-39`
- Java：`backend/src/main/java/cn/etarch/mao/harness/delegate/SubagentExecutionRecoveryService.java:47-49`
- TypeScript：`backend-ts/src/harness/delegate/subagent-execution.mapper.ts:88-96`
- TypeScript：`backend-ts/src/harness/delegate/subagent-execution-recovery.service.ts:40`

**问题说明**

两套 `claimForRecovery` / `claimRecovering` 都执行类似条件：

```sql
UPDATE subagent_execution
SET status = 'RECOVERING'
WHERE id = ? AND status IN ('RUNNING', 'RECOVERING')
```

第一实例把 `RUNNING` 改成 `RECOVERING` 后，第二实例仍能用 `RECOVERING` 命中并得到成功结果，因此该更新不是 CAS 抢占。Java 会依据返回值继续恢复；TypeScript 更进一步完全忽略 `claimRecovering()` 的布尔返回值。滚动发布、双实例部署或旧实例尚未完全退出时，多个实例会并发续跑同一个子代理。

**影响**

同一 execution 会重复调用 LLM 和工具，可能重复执行 shell、写文件或外部 API 等有副作用操作；两次运行还会竞争写入子会话终稿。之后虽有父结果交付锁，也只能避免部分父消息重复，无法撤销重复的子代理执行和工具副作用。这直接违背“恢复原 execution”及幂等要求，并可能导致父会话收到非确定性结果。

**修复建议**

使用真正的所有权/CAS 协议，例如仅允许 `RUNNING -> RECOVERING`，并为 `RECOVERING` 增加带实例 owner、lease/heartbeat 和过期时间的重新认领机制；调用方必须检查 claim 结果，失败立即退出。若系统保证启动时会遗留 `RECOVERING`，应依据 lease 过期而不是无条件认领。建议补充两个恢复协调器并发 claim 同一 execution、仅一个实际进入 `executeVisible` 的集成测试。

## 高（重要功能缺陷）

### 3. TypeScript 恢复执行注册了取消标志，却没有绑定到执行上下文

**代码位置**

- `backend-ts/src/harness/delegate/subagent-execution-recovery.service.ts:50-61`
- 对照正常委派：`backend-ts/src/harness/tool/impl/delegate-tool.ts:114-124`

**问题说明**

恢复代码先执行 `buildSubContext()`，随后调用 `agentLoop.registerCancelFlag(child.id)`，但没有执行 `context.cancelFlag = cancel`，也没有把 cancel flag 传给 `executeVisible`。正常委派路径会把父取消标志写入 `subContext.cancelFlag`。因此恢复阶段注册到 `AgentLoop` map 中的对象只被 LOCAL 等待循环和执行结束后的状态判断读取，实际 LLM/工具循环并不使用它。

**影响**

用户取消父任务或系统尝试取消恢复中的子代理时，正在进行的 LLM/工具调用不会被中断；恢复可能继续产生消息和工具副作用，最后才被标记为 `CANCELLED`。对于 LOCAL 模式，连接完成后同样失去取消传播。这会造成“界面显示已取消但后台仍执行”，也会延迟父会话恢复和结果交付。

**修复建议**

在调用 `executeVisible` 前将同一个注册对象赋给 `context.cancelFlag`，并确认父会话取消会传播到该 child flag；或者修改恢复/可见执行 API，显式接收 cancel flag，避免注册对象与上下文对象脱节。增加测试：恢复已进入 LLM/工具循环后置 cancel，断言循环停止、后续工具不执行且 execution 最终为 `CANCELLED`。
