## P2

### P2-1. 会话被新 tab/新连接接管时只 `failSession`，不通知旧连接；旧 tab 的在途动作/批量仍继续执行 → 重复副作用

**位置**
- `backend-ts/src/session/ws/streaming-ws-handler.ts:233-241`（`handleSubscribe` 换绑：仅 `failSession(...)` 后 `bindEmbedSession`，未向 `previous` 连接发任何帧）
- `sdk/embed/src/controller.ts:273-281`（`onDisconnected` 才 `abortInFlight()`；socket 未关闭时不会触发）
- `sdk/embed/src/page/engine.ts:151-159`、`:207`、`:221`、`:318`（`abortEpoch` / `shouldAbort`）
- `backend-ts/src/session/ws/streaming-ws-registry.ts:326`（`sendPageToolRequest` 只发 `page_tool_request`）
- `sdk/embed/src/controller.ts:924-950`（`handlePageToolRequest` 按 `requestId` 幂等，不同 `requestId` 可并发）

**问题**

第 9 轮修的是“**socket 断开**”路径：客户端 `onclose → onDisconnected → pageEngine.abortInFlight()`，同时服务端 `afterConnectionClosed → failSession`。但“**同一 agent 会话被另一个 embed 连接接管**”（多标签页同会话、或快速重连时新连接先到）走的是另一条分支：`handleSubscribe` 只对后端 future 做 `failSession`，**旧连接依然 OPEN**，因此旧 tab 的 `onDisconnected` 不会触发，`cancelled`/`abortEpoch` 都不变，旧 tab 的 `PageEngine` 会继续执行剩余动作/批量。

由于同一 `sessionId` 现已被绑到新连接，模型重试会立刻被派发到新 tab；旧 tab 与它各自操作自己的 DOM，**同一动作在两处执行**（提交/删除类动作尤其危险）。旧 tab 的结果回包会因 `handlePageToolResult` 的 `getEmbedSessionsForConnection(session).includes(sessionId)` 判定失败而被丢弃，会话记录与页面实际状态不一致。

**复现**
1. 标签页 A 打开浮窗并授予 task/full；模型发起 `page_actions = [click(提交), wait 3000, click(确认)]`，A 执行到 `wait`；
2. 此时用户在标签页 B 打开浮窗（B `boot()` 复用 A 的会话 S，`subscribe(S)`）→ 服务端 `failSession(S, '页面连接已切换')` 并把 S 绑到 B，但 A 的 socket 仍在线；
3. A 的 `executeBatch` 的 `shouldAbort()` 仍为 false → 继续执行 `click(确认)`；
4. 模型收到 `embed_client_not_connected` 后重试（新 `requestId`）→ 派发到 B → B 再执行一遍 → **提交/确认执行两遍**。

**影响**：与设计 4.3“会话断开/切换时停止任务”不符；多标签页场景下会出现重复副作用、错页操作。与第 9 轮已修的断线路径相比，这是同一问题的未闭合分支。

**建议（任选其一，推荐 A）**
- A：换绑时向被顶掉的 `previous` 连接下发一个取消帧（如 `page_tool_cancel { sessionId }`，或复用 `page_tool_result` 语义），SDK 在 `onWsEvent` 中收到后调用 `pageEngine.abortInFlight()`（或针对该 `sessionId` 取消）；这样旧 tab 的 in-flight 批量会立即中止，且不影响旧 tab 的后续新任务。
- B：`handleSubscribe` 换绑时主动 `closeConnection(previous)`，让旧 tab 走既有 `onDisconnected → abortInFlight` 路径（代价：旧 tab 会被断开并触发重连，需确认重连后不会再抢占绑定）。
- 补一条「A 有在途批量 → B subscribe 接管 → A 本地批次中止」的用例。

## P3 / 备注（不阻塞）

### P3-1. 多 tab 共享同一 sessionId 时按“最后订阅者”路由，页面工具可能在另一个标签页执行

**位置**：`backend-ts/src/session/ws/streaming-ws-handler.ts:233-241`、`sdk/embed/src/core/tabs.ts:69-79`、`sdk/embed/src/controller.ts` 的 `boot()`

`TabsCoordinator.inquire()` 会让新 tab 复用旧 tab 的 `sessionId`（localStorage 共享），而页面工具只按 `sessionId → 连接` 绑定。于是两个 tab 都在线时，请求会发往**最后订阅**的那个 tab：用户在 A 输入“点击提交”，点击可能发生在 B 的页面。需求“同用户多 tab 请求必须按 embed 连接隔离”更自然的解读是“路由到发起消息的那个 tab”。历史轮次已把“后订阅者胜”作为既定机制（第 4 轮 P2-4 只要求换绑时结束旧 pending），故仅备注；若采纳，建议在 `handleSendMessage` 时按发起 `session` 重新绑定，而不是在 `handleSubscribe` 时绑定。

### P3-2. `page_observe.changes.updated` 仍不覆盖 value/checked/selected 变化

**位置**：`sdk/embed/src/page/snapshot-manager.ts:145-165`、`sdk/embed/src/page/scanner.ts:139-150`

`updated` 只比较 `signatureOf` 的变化，而 `VOLATILE_ATTRIBUTES` 刻意排除了 `value/checked/selected`（且 `signatureOf` 用的是 `attributeHash` + `textOf`，input 的 `textContent` 为空）。因此最常见的“输入值/勾选状态变了、元素数量与属性没变”场景，`observe()` 仍返回 `added=0/removed=0/updated=0`，与设计 6.6“目标元素值或状态是否变化”不完全一致（`page_inspect` 或动作结果里的 `effect:'state'` 可部分补偿，`page_observe` 工具描述也只写了“增减”，故不升级为 P2）。

**建议**：对 token 相同的元素，除签名外再比较 `descriptor.value/checked/disabled`（可用执行器的 `stateOf` 同口径）计入 `updated`；或至少在类型/工具描述中明确当前 `updated` 仅表示“属性/文本签名变化”。

### P3-3. `dispatchBlur` 用顶层 `document.activeElement`，同源 iframe 内元素 fill 后不会派发 blur/focusout

**位置**：`sdk/embed/src/page/framework-events.ts:51-55`、`sdk/embed/src/page/executor.ts:276-284`

`executeFill` 先 `el.focus()` 再 `dispatchBlur(el)`，但 `dispatchBlur` 判断的是顶层 `document.activeElement !== el`。对同源 iframe 内元素，`el.focus()` 后顶层 `document.activeElement` 是 `<iframe>` 元素而非内部元素（`executeFocus` 用的是 `el.ownerDocument.activeElement`，口径不一致），因此 `blur/focusout` 不会派发，依赖失焦提交/校验的 iframe 表单会出现“回读成功但未提交”。扫描器明确支持同源 iframe（设计 3.1.14）。

**建议**：`dispatchBlur` 改用 `el.ownerDocument.activeElement !== el`（与 `executeFocus` 对齐），并补一条 iframe 内输入框的用例。

### P3-4. `observe` 从 added/removed 统一扣除 `updated` 存在过度扣除的边界

**位置**：`sdk/embed/src/page/snapshot-manager.ts:156-165`

`updated` 是“同 token 且签名变化”的个数，但对每个这样的元素，added/removed 不一定各 +1（其新/旧签名可能已在前后多重集里）。统一 `added -= updated; removed -= updated` 在“被更新元素的新签名恰好等于某个被移除元素的签名”时会少报 removed。例：前 `{X:A, Y:B}` → 后 `{X:B}`：`added=0、removed=1、updated=1` → 结果 `removed=0`，实际 Y 被移除。触发条件较窄，列此备查。

**建议**：改为按 token 精确配对（同一 token 视为“更新”并从签名多重集的增/减中各扣 1 次），或对 `added/removed` 只在“该签名确有新增/消失”时扣减。

### P3-5. `handleSubscribe` 在 `await requireOwnedSession` 之后才绑定，存在“首条消息工具列表漏掉 page_*”的窄竞态

**位置**：`backend-ts/src/session/ws/streaming-ws-handler.ts:229-241`、`backend-ts/src/session/ws/attach-websocket.ts:41`（`void handler.handleTextMessage(...)`，帧处理未串行化）

`bindEmbedSession` 在异步 `requireOwnedSession` 之后执行；若 `subscribe` 与紧随其后的 `send_message` 交错，`HarnessService.filterPageTools(..., isEmbedSession)` 在构建工具列表时可能还没绑定，导致该轮模型看不到任何 `page_*` 工具（用户表现为“页面操作不可用”）。正常交互（打开浮窗后订阅完成再输入）不易触发，列此备查。

**建议**：把绑定改为在 `handleSubscribe` 进入时（`requireOwnedSession` 之前）基于已鉴权连接完成，或在 `getClientType(session)==='embed'` 时于 `handleTextMessage` 入口同步登记绑定意图。
