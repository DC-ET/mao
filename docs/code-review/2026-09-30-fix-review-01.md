## 阻塞（合并前必须修复）

### P1-1 微信重放 10 分钟超时窗口会并发双执行同一用户消息，产生重复回复与垃圾会话历史

**位置**：
- `backend-ts/src/weixin/inbound-message.repository.ts:48-62`（`reclaimStuck`：CLAIMED 超 10 分钟即回收重放）
- `backend-ts/src/weixin/monitor.service.ts:112-117`（重放 fire-and-forget 启动）
- `backend-ts/src/weixin/inbound-processor.ts:70-93`（`reclaimStuckMessages` / `processReplayedMessage`）
- 放大点：`backend-ts/src/weixin/agent-inbound-handler.ts:114`（`onMessage` 内 `nextGeneration` + `abortRunningExecution` 无条件打断本会话在途执行）

**触发链**：
1. 用户发消息 M，enqueue（CLAIMED）后 `processClaimed` 进入 Agent 执行，微信入站执行是长任务（AgentLoop 跑十几分钟很常见）；
2. 第 10 分钟起，`hasInFlight` 判定该行超时（updated_at 停在最开始的 CLAIMED），游标恢复推进，且下一轮 `reclaimStuck` 把 M 回收重新置 CLAIMED；
3. 重放的 `processClaimed` 再次调用 `handler.onMessage`：重新 `saveMessage` 落一条重复的 USER 消息、`nextGeneration` 使原执行的 generation 失效并 `abortRunningExecution` **打断正在为用户干活的原执行**，随后起第二个 Agent 执行；
4. 重放执行完成后 `resolve(reply)` → `sendReply` 发送回复；此后原执行跑到 `processClaimed` 返回，外层 `markDone` 置 DONE；若游标未推进期间 ilink 重投了 M，`enqueue` 撞唯一键跳过（有界）。净效果：**用户收到两份（可能不一致的）回复，会话历史里多出一条被部分回复的孤立 USER 消息，原执行被打断白烧 token**。
5. 且每次重放完成置 DONE 后，若 ilink 因游标未推进重投 M，enqueue 返回 false 跳过、无任何行留在 FAILED/超时 CLAIMED——双执行风险在「原执行跑满 10 分钟且 monitor 至少再转一轮」时必然触发一次。

**预期 vs 实际**：预期「超时 CLAIMED」只重放真正中断（进程崩溃/异常退出）的消息；实际微信通道的「处理中」状态没有任何心跳刷新，长执行会被误判为中断而并发重放。注释「CLAIMED 超过 10 分钟允许重认领，与钉钉/飞书同口径」不成立：钉钉/飞书的认领在**入口回调**内快速完成（秒级返回 ack），10 分钟超时相对处理时长很安全；微信的处理是 Agent 长执行，10 分钟是相对长执行过短的窗口。

**影响**：消息不丢的目标达成，但引入了「正常慢执行 → 打断 + 双执行 + 重复回复 + 历史污染」的新故障模式，属于本次修复引入的回归。

**修复建议**（任选其一）：
- 重放窗口从「固定 10 分钟」改为「对 CLAIMED 行做存活性判断」：重放前检查该消息对应会话是否确有在途执行（如经 `AgentWeixinInboundHandler` 暴露的 generation/cancelFlags，或执行心跳表），仅当无在途执行时才回收；`hasInFlight` 同理按真实在途判断而非 updated_at 超时；或
- 在 `processClaimed` 处理期间定期 `UPDATE weixin_inbound_message SET updated_at = CURRENT_TIMESTAMP` 心跳刷新，把「超时」语义真正对齐为「无心跳即中断」（需要 monitor/handler 层配合，改动较大）；或
- 最低限度：把重认领窗口拉长到远大于最坏执行时长（如 60 分钟），并在重放入口加日志告警便于观测——缓解但非根治。

## 重要（建议本轮修复）

### P2-1 内容指纹幂等键会永久误去重「同一发送者重复发送相同内容」的合法消息

**位置**：`backend-ts/src/weixin/inbound-message.repository.ts:16-25`（`messageKeyOf`：`{from_user_id, item_list, description}` 的 SHA-256）；生效点 `inbound-processor.ts:36-43`（enqueue 撞唯一键即跳过）。

**触发链**：用户向 bot 先后两次发送完全相同的文本（如隔半小时又问「你好」，或常见的「嗯」「好的」复读）。第一条 DONE 后，第二条指纹相同 → `INSERT IGNORE` 返回 affectedRows=0 → 直接跳过，**第二条消息永久无响应**。表无 TTL/清理任务，窗口是永久的；即使加清理，`DONE` 窗口内的相同重发同样被吞。

**预期 vs 实际**：预期幂等键区分「ilink 重投同一消息」与「用户合法重发相同内容」；实际二者不可区分。ilink getupdates 协议确无服务端 message_id（修复说明中的刻意设计可理解），但指纹未纳入任何时间维度，误杀面是真实用户行为而非边缘情况。

**影响**：中——触发条件（逐字重发）日常可见，后果是用户消息静默无回复，且无日志告警（仅 `console.debug`）。

**修复建议**：指纹基础中加入消息自带的时间/序号字段（若 ilink 消息体有 `create_time`/`seq` 等字段，当前仓库未见使用，需确认协议字段）；协议确无可用字段时，至少对 DONE 行加时间窗口去重（如唯一键换成 `(account_id, message_key, date_bucket)` 或 DONE 超过 N 小时允许再次入队），并在 enqueue 跳过处升级日志为 `console.warn` 便于发现误杀。

### P2-2 游标推进依赖 DB 读写的「恰好时序」，无可诉保证

**位置**：`backend-ts/src/weixin/monitor.service.ts:104-125`。

**触发链**：monitorLoop 每轮 fire-and-forget 启动 `processInboundMessage`（其中第一步是 enqueue 落库），随后**不等这批消息入队完成**就执行 `hasInFlight` 判定游标是否推进。两个分支都不安全：
- 若 `hasInFlight` 的 COUNT 查询跑在 enqueue 的 INSERT 提交之前（并发连接，无同步点），查询看不到新行 → 误判「无在途」→ **游标在消息落库前被推进**。后续若进程在 fire-and-forget 完成前崩溃/DB 抖动，该批消息游标已过、表中无记录，回到 BUG-2 原始的丢消息模式（窗口小但真实存在，恰是高负载 DB 延迟时最易发生）。
- 反向亦然：若 INSERT 已提交而处理尚未启动，行是 CLAIMED 未超时 → 游标暂缓一轮，无害但说明该判定本质是竞态。

**预期 vs 实际**：预期「游标严格在新消息全部入队之后推进」（代码注释即此承诺）；实际入队与判定跨并发 Promise 无同步，注释承诺不成立。

**影响**：中低——进程崩溃 + DB 延迟同时命中才丢消息，概率低，但这正是本修复要堵的洞。

**修复建议**：让 monitorLoop 拿到入队完成的确定性信号再判游标：把 `processInboundMessage` 拆成「`enqueue`（可 await）+ `processClaimed`（fire-and-forget）」两步，循环内先 `await repo.enqueue(...)` 全部完成（重复消息跳过不影响），再启动后台处理并做 `hasInFlight` 判定；重放段同理在 reclaimStuck 返回后无需等待 run()，但游标判定应基于「本轮 enqueue 全部完成」这一已知事实。
