**H1 为本次需求的主体功能缺陷**：reasoning 往返四环节中，「响应侧捕获」的流式路径缺失、blob 写入侧完全不存在，导致流式主链路（AgentLoop 唯一 LLM 调用方式）产生的多轮工具调用从第二轮起不回传 reasoning 项。对强制校验的 Responses 网关（即设计文档 §三 列举 400 报错的场景）功能不可用；对弱校验网关表现为思维链上下文跨轮丢失。其余外围改动（注册、白名单、mid-system 跳过、admin 下拉、连通性路由）均正确。

## 二、问题清单

### H1（高）流式链路 reasoning 引用从未捕获，blob 写入侧缺失 → 多轮工具调用第二轮起缺失 reasoning 项回传

**位置与证据链**（四环节逐段核验）：

1. **响应侧捕获（断点所在）**：`responses-llm-adapter.ts` 流式事件处理仅覆盖 `function_call`：
   - `:308` `response.output_item.added` 与 `:333` `response.output_item.done` 分支均只处理 `item.type === 'function_call'`；
   - **reasoning item 的 `id`（rs_*）与 `encrypted_content` 在流式下被整体丢弃**（`response.reasoning_summary_text.delta` :298 只下发人类可读 summary 文本，不带引用）；
   - 对照非流式 `parseResponsesChatResponse`（:917-943）则正确捕获 reasoning item 并挂靠 `toolCalls[0].reasoning`——同一能力流式缺失。
2. **持久化侧（机制在、无值可存）**：`harness-service.ts` `persistAssistant`/`persistToolRound` 用 `JSON.stringify(toolCalls)` 入库，`ToolCall.reasoning` 字段（chat-request.ts:40-51）本可随 JSON 持久化；但流式轮 `toolCalls[0].reasoning` 恒为 undefined，`tool_calls` 列永远不含 reasoning 字段。
3. **blob 写入侧（完全不存在）**：全仓 grep `REASONING_REF_PREFIX` / `encryptedContent`，该前缀**只有读取侧**（responses-llm-adapter.ts:878-890 `extractReasoningRef`）与 spec 造数（responses-llm-adapter.spec.ts:199,212,224），**没有任何代码把 `__mao_responses_reasoning__:{json}` 写入 `thinking_content`**。设计文档 §三 声称「Responses 轮的 thinking_content 存的是前缀引用 blob」，实现中该路径从未发生。
4. **请求回传侧（逻辑正确但上游永不为真）**：`convertMessages` → `extractReasoningRef`（:875-899）按 `toolCalls[0].reasoning` 优先、blob 兜底解析；因上游永不产生引用，历史恢复（session-history-loader.ts:77 还原 reasoningContent）后仍为 null → `include` 恒为 `[]`（:754 `needsReasoningReplay` 恒 false）、请求 input 中无 reasoning 项。

**影响**：
- AgentLoop 唯一 LLM 链路是流式（agent-loop.ts:315 `this.llmAdapter.stream(...)`），因此**同会话第二轮工具调用请求**（内存 `context.messages` 内）即缺失 reasoning 项，无需等到崩溃恢复/compaction；
- 对强制校验网关（设计文档 §三：`function_call was provided without its required reasoning item` 类 400）→ 多轮工具调用从第二轮起必然 400，**功能不可用**；
- 对弱校验网关（含官方 OpenAI）→ 不报错但 stateless 思维链跨轮丢失，推理质量下降、重复思考；
- 恶性循环：`include` 恒为 `[]` → 网关永不下发 `encrypted_content` → 即使补捕获也拿不到密文，需同时修复 include 条件或常驻 include。

**测试缺口佐证**：27 个 spec 用例中 reasoning 相关全部为 convertMessages/parseResponsesChatResponse 的构造输入单测（spec:183-228、325-343），**无任何「流式事件 → 捕获 reasoning 引用」的端到端用例**，四环节的断裂点恰好落在未覆盖区。

**修复方向建议**（供决策，不在本次执行）：
- 流式 `handleEvent` 捕获 reasoning item：在 `output_item.added`/`done` 的 `item.type === 'reasoning'` 分支记录 `{id, encrypted_content}`（done 事件在 include 生效时携带密文；需将 `include` 改为常驻 `['reasoning.encrypted_content']`，成本仅每请求多传密文）；
- 通过既有边界传递引用：方案 A——在**首个 function_call 的 added 事件**时把引用并入 `delta.toolCalls[0].reasoning` 下发（AgentLoop.mergeToolCall 按 id 聚合时保留该字段即可随 toolCalls 持久化，需确认 applyToolCallDelta 不清掉 reasoning）；方案 B——stream 收流结束时把引用序列化为 blob 前缀注入 reasoningContent（AgentLoop 侧配合）；A 更贴合现有「挂靠 toolCalls[0]」设计；
- 补端到端 spec：SSE 序列（reasoning item + function_call）→ 断言聚合出的 toolCalls[0].reasoning 与下一轮请求体中的 reasoning 项。

### M1（中）`response.incomplete` 终态不提取 usage，截断轮 token 统计归零

- **位置**：`responses-llm-adapter.ts:367-375`（incomplete 分支仅设置 `responseIncomplete`/`finishReason`/`done`）对照 `:377-388`（completed 分支提取 `parseResponsesUsage(response.usage)` 并 `usageObjAssign`）。
- **影响**：Responses API 的 `response.incomplete` 事件的 `response.usage` 同样含完整 token 计数，当前被丢弃 → `callback.onComplete(usage)` 上报零值。受害场景：思考截断整轮重试前的失败轮、`content_filter` 等非 max_output_tokens 的 incomplete 轮（该场景正常收流不重试）→ 会话 contextTokens/上下文水位偏低、LLM 用量报表失真。
- **修复建议**：incomplete 分支补一行 usage 提取（与 completed 对称）。spec:539（思考截断重试用例）的 SSE 中 response 无 usage 字段，恰好绕开了此缺陷，建议补断言。

### L1（低）`StreamInterruptedAfterOutputException` 文案/设计文档与实际可重试行为不符（沿袭 anthropic，行为本身合理）

- `:32-38` 异常 message 为 "automatic retry disabled"，`docs/plan/openai-responses-adapter-design.md` §四 亦写「有输出 → 禁止自动重试」；但 `:627` `isRetryableNetworkFailure` 对该异常返回 true → stream() 实际执行 `onStreamReset` + 整轮重试（`:207-230`）。
- 与 `anthropic-llm-adapter.ts:618-620` 完全一致，属复制既有语义：实际行为（reset 清空后重试，用户不看到重复输出）是合理的，spec:505 只在 maxRetries=0 下断言最终文案，默认重试路径未断言。
- **建议**：统一口径——改异常 message 与设计文档为「重试前重置已下发内容」；或若确想禁止重试则从 isRetryableNetworkFailure 移除该分支（需同步 anthropic，影响面大，不推荐本次做）。

### L2（低）回传 `function_call` item 时 `id` 字段携带 call_* 格式值

- `:865-873` `functionCallItem` 输出 `{ id: tc.id, call_id: tc.id, ... }`；而持久化的 `ToolCall.id` 在两种解析路径下均为 **call_id（call_*）**（非流式 `:936` call_id 优先、流式聚合键 syntheticId 亦为 call_id）。Responses API 中 function_call item 的 `id` 本应是响应侧 item id（fc_*），`call_id` 才是工具调用标识。
- 官方 API 中该 `id` 为可选字段，是否严格校验前缀未知；部分网关可能 400。`call_id` 配对 `function_call_output` 不受影响（正确）。
- **建议**：真机验证官方端点；稳妥做法是省略 `id` 字段（仅传 call_id/name/arguments），或流式 added/done 时额外登记并持久化 fc_ item id 供回传。

### L3（低）极端网关下流式聚合键可能错乱（设计已自认可接受降级，仅备案）

- 并行多工具且 added 事件既无 `call_id` 也无 `id`、`output_index` 缺失时，`:310` 兜底键恒为 `__idx_0` → 多工具参数互相拼接；
- 网关不发 `output_item.added` 直接发 `function_call_arguments.delta` 时，delta 以 item_id（fc_*）为键（`:325` resolveCallKey 未命中映射返回原值），done 侧以 call_id 为键 → `keysWithArgsDelta` 判重失效 → 参数重复下发。
- 设计文档 §七 已声明 `__idx_` 兜底属「极罕见可接受降级」，予以备案；正常网关（spec:422 序列）键映射正确。

### L4（低）非流式解析丢弃纯文本轮 reasoningRef（设计声明，无功能影响）

- `:943` `reasoningRef != null && toolCalls.length > 0` 才挂靠：纯文本轮的 reasoning 引用被丢弃且 summary 未转入 `reasoningContent`。非流式链路（连通性测试/摘要/提交信息）均为单轮、不回传历史，无实际影响；设计文档 §七 已声明。备案。

| 方向 | 结论 |

| a) reasoning 往返四环节 | **断裂（→H1）**：环节 3/4（恢复 blob 解析、请求回传）逻辑正确；环节 1 流式捕获缺失、环节 2 无值可存、blob 写入侧不存在。非流式单测全绿掩盖了断裂。 |
| b) function_call/output 顺序 | ✅ 正确。连续 tool 消息缓冲 + 遇非 tool 消息统一冲刷（`:704-716` flushToolBuffer；system/tool/assistant/user 各分支与结尾均正确冲刷）；并行多工具全部 function_call 先于全部 function_call_output（spec:167 验证）；无配对 call_id 降级 user 文本不丢结果（spec:263）。 |

## 四、修复优先级建议

1. **H1**（阻塞级）：强制校验网关下 openai-responses 模型的多轮工具调用不可用——建议在真实网关联调前修复，并补「SSE → toolCalls[0].reasoning → 持久化 → 回传」端到端用例。
2. **M1**：一行级修复（incomplete 分支补 usage 提取）+ 补断言。
3. L1–L4：随下次迭代或真机联调结论处理即可。
