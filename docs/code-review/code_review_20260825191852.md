## 严重问题

### [严重] 群聊 @机器人 永不触发 Agent：`isBotMentioned` 依赖飞书事件中不存在的 `is_at_me` 字段

- 位置：`backend-ts/src/feishu/event-normalizer.ts:24-25`、`backend-ts/src/feishu/inbound-processor.ts:59-62`、`backend-ts/src/create-app.ts:748-750`
- 代码：
  ```ts
  isBotMentioned: isStrictTrue(message.is_at_me ?? event.is_at_me)
    && extractMentions(message.mentions ?? event.mentions).length > 0,
  ```
- 问题：`FeishuInboundProcessor` 生产构造时未传入 `isBotMentioned`，群聊分支实际使用 `event.isBotMentioned`。但飞书 `im.message.receive_v1` 官方事件体中 `message` 对象只含 `message_id / chat_id / chat_type / message_type / content / mentions / create_time`，**没有 `is_at_me` 字段**（已对账飞书开放平台文档）。`isStrictTrue(undefined)` 恒为 `false`，因此所有群消息的 `isBotMentioned` 恒为 `false`。
- 影响：群聊链路整体失效——@机器人的消息只会被写入群日志（`recordGroupMessage` 后直接 return），**永远不会触发 Agent 执行**，与验收标准第 4 条直接冲突。前几轮报告指出的是“@任意用户被误触发”（旧实现 `mentions.length > 0`），当前版本改为依赖 `is_at_me` 后问题**反转**为“永不触发”，属于本轮代码状态下的新问题。
- 修复建议：@判定不应依赖不存在的布尔字段，应以 `mentions` 中携带的机器人身份（mention 的 `key` 为机器人应用 key，如 `cli_xxx`，或 `id.open_id`）与当前机器人比对；无法确认时按未@处理。同时为“@当前机器人 / @普通成员 / 无 mention 字段”补充用例。

### [严重] 设置页绑定链路绑定错用户：回调用目标用户的旧 `feishu_user_id` 执行绑定，而非扫码飞书用户的 union_id

- 位置：`backend-ts/src/auth/feishu-auth.service.ts:151-160`、`backend-ts/src/create-app.ts:266-270`、`backend-ts/src/feishu/binding.repository.ts:31-37`
- 流程（设置页用户 B 发起绑定，扫码授权飞书账号 A）：
  1. `POST /v1/feishu/binding` → `getQrCodeUrl(B.id)`，`state.userId = B.id`；
  2. 回调 `renderCallbackPage` → `completeStateWithCode` 中 `authenticateByCode` 返回**扫码用户 A**（`feishuUserId = A 的 union_id`），随后把 `state.userId` 更新为 `B.id`；
  3. `renderCallbackPage` 用 `state.userId` 查出用户 B，回调 `onUserAuthenticated(B)`；
  4. create-app.ts 的 `onUserAuthenticated` 实现为 `bind(user.id, user.feishuUserId)`，即 **`bind(B.id, B.feishuUserId)`**。
- 问题：`bind` 的 union_id 参数应是扫码用户 A 的 union_id（`authenticateByCode` 的返回值），实际却取了目标用户 B 的 `feishuUserId`：
  - B 从未用飞书登录过（`feishuUserId == null`）→ `onUserAuthenticated` 内层判断直接跳过 → **绑定静默失败**，桌面端显示“授权成功”但 `feishu_binding` 无任何记录，机器人侧仍按未绑定处理；
  - B 曾用其他飞书身份登录过 → 绑定的是 B 的**旧身份**，与本次扫码的 A 无关，绑定关系错误。
- 附带问题：`onUserAuthenticated` 回调签名本有 `targetUserId` 参数，但两处调用（`handleCallback`、`renderCallbackPage`）都只传了 user，未传目标用户，说明绑定“以扫码身份绑定到指定用户”的意图未落地。
- 修复建议：`renderCallbackPage` 绑定场景应将扫码用户 A 与目标用户 B 一并传入回调（如 `onUserAuthenticated(A, B.id)`），由回调执行 `bind(B.id, A.feishuUserId)`；`handleCallback`（登录场景）保持 `bind(A.id, A.feishuUserId)`。补充“目标用户未绑定过飞书”“目标用户已绑定其他身份”“扫码身份已被他人占用”等用例。

## 高严重问题

### [高] 桌面端绑定页未对接绑定接口，绑定无法落到当前登录用户

- 位置：`desktop/src/views/settings/FeishuBotView.vue:73-93`、`backend-ts/src/feishu/binding.routes.ts:8-13`
- 问题：后端已实现 `POST /v1/feishu/binding`（`getQrCodeUrl(userId)`，state 携带当前登录用户 ID）与 `GET /v1/feishu/binding/status`、`DELETE /v1/feishu/binding`，但桌面端 `startAuthorization` 仍调用登录接口 `GET /auth/feishu/qrcode`（state 不含 userId）。结果：
  - `state.userId = null` → 回调走 `renderCallbackPage` 时 `oauthState.userId == null`，绑定回调不触发；
  - 即使触发（登录入口 `handleCallback`），建立的是**扫码飞书账号 A 自身**与 Mao 账号的绑定（`bind(A.id, A.unionId)`），与当前登录用户 B 无关。
- 影响：桌面端“绑定飞书账号”对当前登录用户**完全不生效**（页面文案也自述“绑定状态和解绑接口尚未提供”，与后端实际已提供不符，前后端脱节）。
- 修复建议：前端改为调用 `POST /v1/feishu/binding` 获取绑定授权链接（带当前用户），并展示 `status` / 支持解绑；同时依赖上面“严重问题 2”的后端修复。

### [高] 长连接重连成功后遗留 `retryTimer` 未清除，到点会把已恢复的连接强制重建

- 位置：`backend-ts/src/feishu/monitor.service.ts:101-121`
- 问题：`onFailure` 会安排 `retryTimer`（退避延迟后执行 `active.delete + handle.stop + reconcile`）；`onReady / onReconnected` 只重置 `failureCount`，**没有清空 `retryTimer`**。若 SDK 断线后内部快速自动重连成功（触发 `onReconnected`），此前安排的 `retryTimer` 仍会到期执行，把已恢复的机器人连接 stop 并重建，造成无谓的连接抖动与事件窗口丢失；停用机器人时 `retryTimer` 同样未清理（该场景因 generation 校验影响较小）。
- 修复建议：`onReady / onReconnected / stop` 时清除并置空 `retryTimer`；重建逻辑再增加 generation 校验。

## 中等问题

### [中] 群成员白名单仍被“首次消息自动授予”，未形成授权门槛（前几轮未闭环，简述）

- 位置：`backend-ts/src/create-app.ts:757-759`
- 问题：已绑定成员首次在群内 @机器人 时，`authorizeSender` 发现不在 `feishu_chat_member` 会先 `addGroupMember` 再返回 `true`，成员表被首次消息自动写入而非授权前置校验。与技术方案“触发者必须已在白名单中”不一致；已绑定但未授权成员可直接使用群 Agent。
- 修复建议：入站仅查询白名单，未命中发送引导/拒绝并记录日志，不创建会话；自动入表如需保留应显式声明为产品规则。

### [中] 会话执行只有串行队列，未实现“新消息代际取消当前执行并纠偏”；cancelFlag 只注册未清理

- 位置：`backend-ts/src/feishu/agent-inbound-handler.ts:23-38`
- 问题：`onMessage` 通过 `previous.then(() => current)` 排队，新消息会**等待**前一条 Agent 执行完成后才开始，没有对正在执行的上一代任务调用 `cancelFlag.set(true)` 取消（微信通道为 `abortRunningExecution` 代际取消）。需求明确要求“新消息到达时按代际取消当前执行并纠偏”。此外 `createCancelFlag` 通过 `agentLoop.registerCancelFlag(sessionId)` 注册后，本模块**从未清理**（无 removeCancelFlag 调用），长期运行 Map 会持续增长。
- 修复建议：新消息入队时先取消上一代执行（cancel 当前 flag），并补充取消后的清理；执行结束后移除 cancel flag。

### [中] 触发消息自身被注入群上下文，Agent 看到重复内容

- 位置：`backend-ts/src/feishu/inbound-processor.ts:72-76`、`backend-ts/src/feishu/message.service.ts:76-79`
- 问题：群聊触发链先 `recordGroupMessage`（含本次触发消息）再 `buildGroupContext` 查询最近 30 条/2 小时，刚插入的触发消息必被包含，随后 `AgentFeishuInboundHandler` 又把 `context.text` 与 `groupContext` 拼接，导致触发消息文本在最终 prompt 中出现两次。
- 修复建议：上下文查询排除当前 `messageId`，或在组装时过滤。

### [中] 图片/文件入站处理未实现，群日志类型恒为 text（需求 §2.1.7 / 验收第 7 条未达成）

- 位置：`backend-ts/src/feishu/event-normalizer.ts`（未解析 `message_type`）、`backend-ts/src/feishu/inbound-processor.ts`（无媒体下载）、`backend-ts/src/feishu/message.service.ts:64-67`（`msgType` 恒 'text'）
- 问题：图片消息的 `text` 为空，直接以空文本进入链路（私聊会保存空 USER 消息并执行 Agent；群聊日志 content 为空、`msg_type` 恒 'text'、`file_key` 恒 null），未实现需求要求的图片转 data URI 多模态、文件落工作区、`[图片]`/`[文件:名称]` 标注。文件消息同理。
- 修复建议：按需求实现媒体下载与标准化后再进入链路；至少让群日志正确记录类型与 key，避免空内容污染上下文。

### [中] 未绑定用户引导回复文案对私聊不适用，且不含绑定链接（需求要求“含绑定链接”）

- 位置：`backend-ts/src/feishu/inbound-processor.ts:33-35, 53-56`
- 问题：私聊与群聊未绑定场景共用文案“请先完成飞书账号绑定，并在群内获得使用权限后再试。”——私聊场景出现“群内”字样不合语义；且文案不含任何绑定引导链接，需求 §2.1.3/§2.1.8 要求“回复绑定引导消息（含绑定链接）”。当前未绑定用户从飞书内无法自助完成绑定（桌面端入口又存在上述高严重问题）。
- 修复建议：按场景区分文案，并在回复中拼接可用的绑定引导链接（如 `/v1/feishu/binding` 生成的授权链接）。

### [中] `resolveFeishuUserId` 改为 union_id 优先，存量 `user.feishu_user_id`（旧 user_id）登录识别中断

- 位置：`backend-ts/src/auth/feishu-auth.service.ts:261-263`
- 问题：该改动后 `findByFeishuUserId(union_id)` 无法命中存量用户（旧值存的是飞书 user_id），存量飞书登录用户会被按 email 匹配或重建用户。按“初版不考虑存量兼容”可接受，但建议评估存量数据迁移或在 changelog 明示。
- 修复建议（可选）：迁移脚本将存量 `feishu_user_id` 批量切换为 union_id，或保留双键回退。
