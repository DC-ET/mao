## 高严重程度

### 1. 未授权卡片发送失败仍会中断入站处理，文本回退没有真正生效

- **位置**：`backend-ts/src/create-app.ts:1021-1052`；调用方 `backend-ts/src/feishu/inbound-processor.ts:67-72`
- **问题**：`sendUnauthorizedCard` 在 `reply()` 抛错时虽然调用 `pendingBindingMessages.fail(auth.state)`，但随后重新抛出异常。`FeishuInboundProcessor` 只是直接 `await sendUnauthorizedCard(...)`，没有捕获异常，因此不会继续执行后面的 `if (!sentCard) await this.sendUnauthorized(...)`。同样，插入 pending 记录失败、`setCardMessageId` 失败也会直接抛出并跳过文本回退。只有“响应没有 message_id”这一分支显式返回 `false`，才会触发回退。
- **影响**：飞书卡片 API 瞬时失败、数据库写入失败或卡片 ID 持久化失败时，用户收不到任何绑定引导文本；消息处理最终进入 `finally` 的 release，后续也不会自动补发。卡片已成功发送但 `setCardMessageId` 失败时，还会留下 PENDING 记录，未来无法可靠恢复同一张卡片。
- **修复建议**：将卡片发送增强能力完全封装为失败返回 `false`：捕获插入、发送、响应解析及 `setCardMessageId` 的异常，按需要把 state 标记 FAILED，并保证异常不穿透到 processor；processor 再统一发送文本回退。若卡片已经发送但无法持久化 message_id，应标记为不可恢复状态，并仍发送文本提示，避免留下可重复执行的 PENDING 记录。补充各失败点的测试。

## 中严重程度

### 2. OAuth state 可能在授权请求执行期间过期，却仍被写成 SUCCESS

- **位置**：`backend-ts/src/auth/feishu-auth.service.ts:94-135`；`backend-ts/src/auth/feishu-oauth.repository.ts:22-49`
- **问题**：`completeStateWithCode` 只在调用飞书 API 前检查一次 `expiresAt`。调用 `authenticateByCode` 可能耗时较长；返回后 `updateByState` 的 SQL 仅按 `state AND status = PENDING` 更新，没有再次约束 `expires_at > 当前时间`。因此 state 在外部 API 调用期间过期时，仍会被更新为 SUCCESS，并继续触发 `onUserAuthenticated` 和待绑定消息恢复。
- **影响**：已过期二维码可以完成登录/绑定，违反 state 的有效期；在待绑定消息场景还可能恢复一条本应失效的原始消息。
- **修复建议**：成功落库必须使用数据库时间或同一 `now`，在条件中加入 `expires_at > ?`，并检查 affectedRows 必须为 1；更新失败时重新读取状态并返回“已过期/已被处理”，不要继续认证回调和消息恢复。建议把“消费/成功转换”设计为原子状态迁移，补充外部调用跨过过期时间的测试。

### 3. 重复/并发 OAuth 回调仍会重复执行外部认证及成功后的副作用

- **位置**：`backend-ts/src/auth/feishu-auth.service.ts:94-135, 161-178`
- **问题**：并发请求都可以先读取同一个 PENDING state，然后各自调用 `authenticateByCode`；只有之后的 `updateByState` 带状态条件。代码没有检查该更新的 affectedRows，也没有在成功状态转换前建立 claim/锁。因此第二个请求即使状态转换失败，仍会返回 user；`renderCallbackPage` 随后重新读取 SUCCESS 并继续调用 `onUserAuthenticated`。当前 pending 消息的 `claim` 只能防止消息恢复重复，不能消除重复的飞书 token 交换、用户更新及绑定副作用。
- **影响**：重复回调会产生不必要的外部请求和竞态；在绑定回调中可能重复执行绑定及卡片恢复，失败重试的结果也不明确。
- **修复建议**：在开始外部认证前原子地将 PENDING claim 为 PROCESSING（带 `status` 和有效期条件），只有 claim 成功的请求继续；成功/失败分别转换状态。或者在最终更新后严格检查 affectedRows，失败请求只读取最终状态并返回已处理，绝不继续执行 `onUserAuthenticated`。`renderCallbackPage` 不应通过二次读取 SUCCESS 再无条件触发副作用，应由唯一的成功事务路径触发。

## 已核验

- **Db camelCase 映射：已修复。** `MysqlFeishuPendingBindingRepository.claim()` 当前读取 `row.appId`、`row.messageId`、`row.cardMessageId`、`row.eventJson`，与 `Db.queryOne()` 的 camelCase 返回约定一致；迁移中的 `app_id/message_id/card_message_id/event_json` 字段也与写入映射对应。
- **原始消息恢复与同卡片 patch：主链路已接通。** OAuth 成功回调通过 `claim(state)` 读取保存的事件，并以 `progressCardMessageId` 传入 processor；`createFeishuProgressCard` 对该 ID 使用 `message.patch`，不会重新创建进度卡片。`claim` 的条件更新对并发领取有基本保护。
- **state 基础过期与成功消费：部分正确。** `getLoginStatus` 会识别 PENDING 过期，`consumeSuccess` 有 `consumed_at IS NULL` 和过期条件；但这不能弥补成功转换阶段缺少过期条件及回调副作用竞态。
- **上一轮卡片创建失败问题：已改善。** Agent handler 已捕获进度卡片创建异常并继续执行 Agent；但本轮新增的未授权绑定卡片发送链路仍存在上述回退缺陷。

未修改业务代码；本报告按要求写入当前审查目录。
