## P2-1 断线重连发生在「已落库过工具轮次」的执行中途时，同一段回答会重复上屏（且随每次重连累积）

**文件位置**
- `sdk/embed/src/core/store.ts:50`（`mergeHistory`，其中 `:82` 的 `if (m.streaming)` 分支无条件保留本地流式气泡）
- `sdk/embed/src/core/store.ts:39-41`（`sameMessageText`：`fetched === local || fetched.endsWith(local)`）
- `sdk/embed/src/controller.ts:221-239`（`fetchHistory`：`GET /sessions/:id/messages?roundLimit=20`，`USER/ASSISTANT` 全部映射为 `h_<id>` 气泡，`toolCalls: []`）
- `sdk/embed/src/controller.ts:244-261`（`onAuthenticated` 重连 → `reloadHistory` → `mergeHistory`）
- 后端契约：`backend-ts/src/harness/core/harness-service.ts:182+`（`persistToolRound` 在**每个工具轮次结束时**就插入一条 `ASSISTANT`，content 为该轮文本）；`agent-loop.ts:430`（`onMessageEnd` 整个执行只发一次）

**触发条件**
1. 本轮执行使用了工具，且至少一个工具轮次已结束 → 服务端已落库一条 `ASSISTANT`（content = 该轮文本，如「我先查一下」）。
2. 执行仍在进行（或该轮之后还产出了更多文本）时发生断线重连。
3. 重连鉴权成功 → `reloadHistory` 拉到含该中间 `ASSISTANT` 行的历史 → `mergeHistory`。

**错误行为**
- 客户端一次执行只有一个流式 assistant 气泡（`ensureStreamingAssistant` 在 `message_end` 前复用同一条，而 `message_end` 整个执行只发一次），
  因此本地气泡内累积的是「第 1 轮文本 + 第 2 轮文本 + …」。
- `mergeHistory` 对本地尾部的判定顺序是「`streaming` 无条件保留」优先于文本去重，
  故仍在流式的气泡必然被保留；而 history 侧的中间 `ASSISTANT` 行又被原样拼在前面（`mergeHistory` 从不过滤 history）。
- 结果：已落库轮次的文本在界面上出现两次——一次是历史里的纯文本气泡（`toolCalls: []`，没有工具卡），一次在保留的流式气泡里（带工具卡）。
- 即使执行已结束、气泡已收口，文本去重也命中不了：history 行是**单轮片段**，本地气泡是**全轮拼接**，
  `fetched === local` 与 `fetched.endsWith(local)` 均为 false（片段比拼接短），本地副本继续保留。
- 该状态会累积：下一次重连时本地已多出 `h_<中间轮 id>`，回溯在它处 `break` 之前仍会再次保留同一条本地气泡，
  同时 history 又新增了最终 `ASSISTANT` 行，界面上同一轮回答可叠到三段以上。
- 次生现象：工具轮次若没有前置文本（content 为 null），`fetchHistory` 映射成 `content: ''` 的 assistant 气泡，
  `mergeHistory` 不过滤 history 侧空气泡，消息流中会插入空白 assistant 气泡（本地侧的空气泡有丢弃规则，history 侧没有）。

**期望行为**
重连对账后，一轮回答只呈现一份：要么以 history 为准（则需识别并丢弃本地流式气泡中已落库的片段，或按 executionId/轮次边界拆分本地气泡），
要么以本地流式气泡为准（则 `fetchHistory` 应过滤掉属于「当前仍在执行的 executionId」的中间 `ASSISTANT` 行，
即对齐 desktop `applyFetchedMessages` 的做法——history 与本地在**同一 id 空间**内比对，不靠文本长短判断）。
history 侧 content 为空且无工具卡的 assistant 行同样应丢弃。

**严重程度**：P2（内容重复/空泡，会累积，用户可见；不丢消息、不影响后续发送与工具卡按 id 命中）

**修复方向建议**
- `fetchHistory` 增加过滤：`toolCalls` 非空（工具轮次中间行）或 content 为空的 `ASSISTANT` 行不上屏；
  或在 store 侧记录本轮 `executionId` 起始的服务端 messageId 水位，合并时丢弃水位之后的 history assistant 行。
- 若保留现有「以 history 为准」思路，则本地流式气泡应按轮次切分（每次 `persistToolRound` 对应的 `message_end`/轮次边界收口一个气泡），
  使片段与 history 行一一对应，文本去重才具备可比性。

## P3-2 落库确认超时提示不会被后续成功事件清除，且超时后迟到的 `user_message_saved` 不再补做 id 升级

**文件位置**
- `sdk/embed/src/controller.ts:533-545`（`armSaveTimeout`：超时后 `pendingSaves.delete(eventId)` → `markSendUnconfirmed` → 写 `ui/store.sessionError = '发送未确认：服务端未回执，若长时间无响应请重试'`）
- `sdk/embed/src/core/store.ts:406`（`markSendUnconfirmed`：只收口空流式气泡，不删消息——本身正确）
- `sdk/embed/src/controller.ts:385`（`onUserMessageSaved` 中 `if (!pending) return;`）
- `sdk/embed/src/core/store.ts` 事件路由：无任何分支在收到 `content_delta` / `message_end` / 终态时清除 `sessionError`（仅 `send()`、`retry()`、`reset()`、鉴权恢复会清）

**触发条件**
连接保持存活但 60s 内没收到 `user_message_saved`（服务端落库慢、或该帧单点丢失），随后服务端正常回执并推流。

**错误行为**
1. 超时横幅「发送未确认：服务端未回执，若长时间无响应请重试」在回答正常流式产出、甚至整轮 `COMPLETED` 之后仍挂在面板上，
   与实际状态矛盾，可能诱导用户重复发送（重复发送会被服务端 `session_already_running` 拒绝，进而回滚乐观气泡）。
2. 超时时 `pendingSaves` 条目已被删除，迟到的 `user_message_saved` 在 `:385` 直接 return，
   `confirmLocalUserMessage` 不再执行 → 该本地气泡永久停留在客户端 id（`u_…`），拿不到 `s_<id>`，
   后续 `mergeHistory` 只能依赖文本比对来识别它是否已落库。

**期望行为**
- 收到本轮的 `content_delta` / `message_end` / 终态 `session_status` 后，若当前 `sessionError` 是「发送未确认」这类未决提示，应自动清除。
- 迟到的 `user_message_saved` 即使 `pendingSaves` 已无条目，也应按 `tempEventId`→localId 的对应关系补做一次 id 升级
  （例如保留一份「已超时未确认」的 eventId→localId 映射，仅用于补登记，不再参与计时）。

**严重程度**：P3（提示与实际状态不一致，误导性；不丢消息，用户可点「重试」或继续发送）

## 已复核确认无误（本轮修复的正向验证，不需改动）

- `mergeHistory` 的 `break` 判据（`serverKey ∈ fetchedKeys`）安全：落库是严格时序的，不存在「未落库消息排在已落库消息之前」的本地序列，
  `break` 丢弃的部分必然被 history 完整覆盖。
- 用户气泡的文本后缀判定（`fetched.endsWith(local)`）在 embed 场景成立：服务端存的是 `prefix + '\n\n---\n\n' + content`，
  本地气泡存 `content`，且 `fetchedOnly` 已用 `localKeys` 排除了本地已持有服务端 id 的行，比对面很窄。
- `pauseSaveTimeouts()` / `reconcilePendingSaves()` 的生命周期：`onDisconnected` 清计时并置 null，重连拉历史（成功/失败两路都调）后按
  `hasLocalUserMessage` 销账或重新武装；`clearPendingSaves` / `rollbackAllPendingSaves` / `destroy` / `newSession` 均已兼容 `timer` 可为 null。
- `markSendUnconfirmed` 不删消息、且「已有产出则保持流式」，与 desktop `sendMessageAndWaitForSave` 超时只返回 false 的语义一致。
- `SelectionTracker` 单槽 `blocked` + `blockedStale`：折叠不清引用、`consume` 后同段不重复携带、重新选中同段恢复、`unconsume` 立即恢复，
  `rollbackSend` 中 `unconsume()` + 手工恢复 `ui.quotedSelection` 结果正确。
- `ChatPanel` Escape 去掉 `stopPropagation` 后不再吞宿主逻辑；`inputDisabled` 只由 `running` 驱动，与「发送时将自动重连」文案一致
  （`Composer` 的 `'连接中…'` 分支因此不可达，属死分支，非功能问题）。
- 单测与构建：`sdk/embed` 8 文件 / 96 用例全绿；`npm run build` 通过。
