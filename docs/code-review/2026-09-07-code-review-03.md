## P2

### R7. 面板收起期间同账号自动恢复认证，重新展开后不会恢复 WS

**位置**
- `sdk/embed/src/controller.ts:290-298`：resumeAuthenticatedPanel 在 panelOpen=false 时返回，这是预期的隐藏面板保护。
- `sdk/embed/src/controller.ts:570-576`：open 取票成功后只调用 boot，没有对已 boot 但断开的 WS 执行恢复。
- `sdk/embed/src/controller.ts:414-415`：booted=true 时 boot 直接返回。
- `sdk/embed/src/controller.ts:201-208`：明确认证拒绝 disconnect(true)，但保留 booted 和当前会话；后台 authenticated 清除错误提示。

**实际触发路径**
1. 用户已正常打开面板并完成会话 11 的初始化，booted=true。
2. SSO 明确拒绝一次续期，SDK 按设计暂停 WS，保留会话以供同账号恢复。
3. 宿主恢复登录，用户点击重试；该次换票暂时返回 503（429 也可以形成同类路径），TokenProvider 安排自动重试。
4. 用户等待期间收起面板。自动重试随后成功，同账号身份未变，错误提示清除；resumeAuthenticatedPanel 因面板未打开而不启动 WS，符合隐藏面板保护的意图。
5. 用户在新 token 仍有效且未到 refreshAt 时重新展开。tokens.get() 直接返回缓存 token，不再发出 authenticated 回调；open 调用 boot，但 booted=true 导致立即返回。
6. 因为先前是 intentional disconnect，WS 本身没有自动重连计时器。此时面板已展开但仍离线、没有错误提示，也没有恢复订阅与历史对账。

**影响**
- 有效 SSO 和网络恢复后，用户正常重新展开仍不能立即恢复聊天，需要等待下一次主动换票成功触发恢复，或进行额外操作。
- 默认长 TTL 下等待可能较长。不是永久失去认证，也不是越权，因此定为 P2。
- 不能用“隐藏面板也立即连接”规避：隐藏期间不启动连接是当前明确保护，应补齐重新展开入口。

**验证**
使用 Vite middleware 在内存加载真实 EmbedController、TokenProvider、WsClient，配合 happy-dom、合成 fetch 和异步 close 的假 socket；未写入/修改测试脚本，未请求外部服务。驱动顺序为：

```text
初次成功并连接
→ 续期明确 401
→ 用户 retry 遇到 503
→ close 面板
→ 自动重试成功
→ open 面板
```

观测结果：

```json
{"exchanges":4,"before":1,"after":1,"panel":true,"connected":false,"error":null,"session":11}
```

before/after 是再次展开前后的 socket 实例数。没有创建恢复连接，原会话仍保留，错误却已清空。

**建议修复**
- 让 open 在成功取得有效 token 后走统一、幂等的面板恢复入口：未 boot 则 boot；已 boot 且有当前会话而 WS 未连接则 connect。
- 恢复前后保持 destroyed/panelOpen 检查，不在关闭或销毁后启动连接。
- 复用现有订阅意图和 authenticatedOnce，恢复原会话的订阅/历史，不重建会话或重放 send_message。
- 仅需恢复连接时不要强制 invalidate/resume 换票，避免不必要的 SSO 请求和限流。

**建议测试**
- 真实 controller 完整覆盖上述序列；隐藏期间不创建 socket，随后 open 应用缓存票创建恰好一个 socket，不新增 exchange。
- connected 后原会话 subscribe 恰好一次，补拉历史一次，不创建新 session，不重放业务帧。
- 连续 open、open 后立即 close/destroy，以及与后台 authenticated 回调并发，断言恢复幂等且不会在销毁后建连。
