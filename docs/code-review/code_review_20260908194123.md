## 高严重度（P1）

### 1. embed 被计入 LOCAL 执行端，导致本机在线判断失真及本机工具误投递

**位置**：`backend-ts/src/session/ws/streaming-ws-registry.ts:13,269-273,319-324`；调用链 `backend-ts/src/harness/local/local-tool-session-registry.ts:47-49,78-83,104`。

**问题**：LOCAL_CAPABLE_CLIENTS 新增 embed，但 embed 仅运行浏览器页面能力，不具备 Electron/CLI 的 shell、文件和技能同步执行器。只有 embed 连接时，hasLocalClientConnection 返回 true，LOCAL 会话会越过“本机未连接”检查；sendToLocalClients 也会把 tool_execute 发给 embed。SDK 不处理该事件，后续工具或技能同步只能等待失败/超时。即便另外在线 Electron，原本只应投给本机执行器的消息也会发给 embed。

**验证**：使用实际 StreamingWsRegistry 的内存脚本，仅注册一个 embed socket；输出 `embedOnlyCountsAsLocal: true`，调用 sendToLocalClients 后输出 `localFramesDeliveredToEmbed: 1`。

**修复建议**：LOCAL 集合仅保留真正的本机执行端；页面连接在线判断和投递使用独立能力/连接集合，不通过扩大 LOCAL 集合接入页面工具。增加 embed-only、embed+electron 两种回归测试。

### 2. 旧快照在 SPA 导航或节点复用后仍可操作新业务对象

**位置**：`sdk/embed/src/page.ts:86,91-94,107`。

**问题**：execute 只核对内存 snapshotId，并检查节点存在和可见，没有检查 URL 或目标业务语义变化。inspect A 记录后，SPA 切换到 B 并复用同一删除按钮，旧请求仍命中同一 DOM 节点，可以执行 B 的删除逻辑。pageVersion 在快照中含时间戳，成功结果却不含时间戳，也不能可靠用于状态比对。

**修复建议**：导航和关键目标语义变动时使快照失效；执行前验证页面版本和目标身份，失效后要求重新 inspect。统一快照与结果版本定义，增加路由复用、列表节点复用测试。

**历轮状态**：18:52 报告第 1 项仍存在；snapshotId 判等不能代替页面变化失效。

### 3. task 授权没有任务边界，newSession 后仍持续允许页面写操作

**位置**：`sdk/embed/src/index.ts:64,69,72-74`；`sdk/embed/src/authorization.ts:5-13`。

**问题**：task 只是实例字符串，未绑定任务/会话，没有在结束、停止、身份变化或 newSession 时撤销。设置 task 后，即使创建新会话，executePageAction 仍持续放行。用户只批准本任务却影响后续任务。

**修复建议**：授权绑定任务和会话身份，在生命周期结束及身份切换时撤销，每次执行前检查归属；没有任务上下文时不要接受 task 作为可执行授权。

**历轮状态**：18:52 报告第 2 项仍存在；入口关闭持久化后不再报告刷新恢复授权。

## 中严重度（P2）

### 4. page_tool_result 接入 LOCAL pending 池，不能建立页面请求响应闭环，且可完成错误类别的请求

**位置**：`backend-ts/src/session/ws/streaming-ws-handler.ts:209,611-617`；`backend-ts/src/harness/local/local-tool-session-registry.ts:69-123`。

**问题**：新增 handler 将页面回包直接交给 LocalToolSessionRegistry。该池只通过 sendToolRequest 注册请求，发出的事件是 tool_execute，并没有页面请求注册/派发路径。独立的页面 requestId 因池中不存在而静默丢弃；反之，只要 sessionId/requestId 匹配某个 LOCAL 请求，page_tool_result 就会提前完成并删除该请求，因为池中不记录工具类别或目标连接。这里已经校验会话所有权，不是跨用户会话越权；缺少的是页面/本机请求类别和目标关联。

同时成功分支只转交 data.result，丢弃合约允许放在同级的 snapshotId/pageVersion；失败分支只保留 message，丢弃 error.code。合法的结构化版本或失效错误信息无法完整传给等待方。

**修复建议**：使用页面请求注册器，或为统一 pending 池增加明确的请求类别、目标连接与页面上下文绑定。注册、发送 page_tool_request、匹配回包、超时/断连清理必须成对实现；保留结构化结果和错误。补充未知 ID、跨类别 ID、错误连接及快照元数据的测试。

### 5. 页面请求类型未从 contracts 入口导出，SDK 也没有请求执行与回包调度入口

**位置**：`shared/contracts/src/ws.ts:88-94`；`shared/contracts/src/index.ts:24-56`；`sdk/embed/src/core/ws-client.ts:373-375`；`sdk/embed/src/index.ts:63-75`。接收链：`sdk/embed/src/controller.ts:253,482-545`。

**问题**：WsPageToolRequest 只在 ws.ts 定义，包入口只新增导出 WsPageToolResultFrame，消费者无法按现有 `@mao/contracts` 入口导入请求类型。更重要的是 sendPageToolResult 没有调用方：WS 事件交给 controller 后，page_tool_request 没有处理分支；index 创建的页面管理器和授权管理器也没有接到 controller。收到页面请求不会 inspect/execute，更不会返回授权失败或执行结果。公开本地 API 可调用不等于聊天 Agent 可使用页面工具。

**修复建议**：从共享入口导出请求类型，明确统一的请求信封形状；接通 controller 到页面执行器的受控调度，并将成功、失败、授权拒绝都经 sendPageToolResult 返回。测试实际入站帧到出站帧，不仅测试单独的发送函数。

**范围说明**：这是当前新增协议仍未完成的功能链路，不声称既有聊天功能因此全部失效。与问题 4 分别对应客户端调度和后端等待方，需两侧同时修复。

### 6. keyboard 合法请求必然落入 fill 分支并失败

**位置**：`sdk/embed/src/page.ts:32,101-105`。

**问题**：PageAction 的 keyboard 使用 key，但 execute 没有 keyboard 分支，最终进入 fill 的 else。合法请求 `{type:'keyboard',key:'Enter',elementId,snapshotId}` 没有 value，会返回 element_not_fillable，不产生任何按键事件。公开按键 API 实际不可用。

**修复建议**：增加独立的 keyboard 分支，定义可可靠实现的按键行为；不支持的行为明确报错，不混入 fill。覆盖 Enter/Escape/Tab 并确认不会覆盖已有字段值。

**历轮状态**：18:52 报告第 4 项仍存在。

### 7. 控件动作缺少类型与最终状态验证，仍存在无效操作成功和意外点击

**位置**：`sdk/embed/src/page.ts:94-95,103-107`。

**问题**：显式 disabled/readonly 检查已加入，但动作仍以类型断言代替实际校验，并在未抛异常时统一成功：

- select 不存在的 option value 会清空选择，仍触发 change 并成功；禁用 option 也未拒绝。
- check/uncheck 对普通 button 读取 checked 得到 undefined，随后调用 click，可意外触发提交；对已选 radio 执行 uncheck 又无法取消，却返回成功。
- fill 作用于 button 时可能只跳过不存在的 setter、派发 input/change，随后成功。
- disabled fieldset 中继承禁用的控件没有自身 disabled 属性，仍会越过检查，出现点击无效却成功等情况。

**修复建议**：按动作验证元素类型和支持能力，使用有效禁用状态（含 `:disabled`）；select 写入前检查 option，填写/勾选/选择后校验状态，错误组合在产生任何副作用前拒绝。

**历轮状态**：18:52 第 3 项部分修复。不得继续声称当前完全没有 disabled/readonly 检查；剩余缺陷如上。

### 8. destroy 未覆盖截图与授权入口，旧实例仍可读取页面

**位置**：`sdk/embed/src/index.ts:73-80`；`sdk/embed/src/screenshot.ts:8-13`。

**问题**：destroy 只销毁 controller/page；capturePageScreenshot 仍直接把当前 document.body 交给宿主 renderer。保留旧 instance，在 destroy 或重复 init 后仍能截图当前业务页面；授权修改也仍可调用。新增 API 生命周期不一致。

**修复建议**：实例层统一检查销毁状态，拒绝销毁后的截图和授权修改；对进行中的截图明确取消或丢弃结果。增加重复 init 后旧实例调用测试。

**历轮状态**：18:52 第 5 项仍存在；inspect/execute 的 page manager 销毁保护已存在，不重复报告已修复路径。
