# 代码审查报告：Embed SDK 对话浮窗历史会话列表

- 分支：`feat/embed-sdk-history-session-list`（worktree `.worktrees/embed-history`）
- 审查提交：`44d27b01`（对照 `main`，diff 共 30 个文件）
- 技术方案：`docs/plan/2026-09-11-embed-sdk-history-session-list-technical-design.md`
- 审查日期：2026-09-11
- 范围：仅功能逻辑，不含页面样式与文档变更；只审查不修改代码

## 总体结论

后端部分（V109 迁移、source 列、过滤分页、PUT 单向迁移、GET 新旧分支兼容）实现基本正确；SDK 的正常切换主流程（退订旧 → 校验 → 绑新 → 订阅 → 拉历史）时序合理。主要问题集中在**失败回退与并发/身份切换的边界场景**：回退路径漏退订目标会话、切换流程之间没有互斥、身份切换后历史面板状态残留。

已确认无问题的点：
- `PUT /v1/sessions/:id/source`：`requireSessionOwner` + service 内二次归属校验，权限正确；仅允许 `web→embed` 单向、幂等（已是 embed 直接返回）。
- `GET /v1/sessions` 新旧分支：desktop 只用 `groupKey/keyword/status`（`desktop/src/stores/session.ts` 从不传 `source/agentId`），不传新参数时行为不变；service 层对 offset/limit 做了下限/上限 clamp。
- WS 重连订阅恢复：`WsClient.unsubscribe` 正确从意图集合（`subscribedSessionIds`）删除并补发退订帧；`restoreSubscriptions` 在每次鉴权成功后按意图集合重建，语义正确。
- `store.reloadHistory/ensureHistory` 均有 `activeSessionId !== sid` 丢弃守卫，切换期间旧历史不会写进新会话。
- boot 惰性补标链路（`resolveSession` → `markSourceEmbed` → PUT）失败静默、不阻断聊天，符合设计。

## 高

### H1. selectHistory 失败回退未退订目标会话，泄漏的订阅会在宿主页执行页面动作

- 位置：`sdk/embed/src/controller.ts` — `switchSession()` / `selectHistory()`
- 现象：`switchSession` 中订阅先于历史拉取执行：

  ```ts
  this.ws.subscribe(session.id);          // 目标会话已进入订阅意图集合（连接时立即发帧）
  await this.store.reloadHistory(this.fetchHistory);   // ← 此步失败（网络抖动等）
  ```

  失败后 `selectHistory` 的回退分支只做了 `bindSession(previous)` + `ws.subscribe(previous)`，**没有 `ws.unsubscribe(目标会话)`**。目标会话永久留在 `subscribedSessionIds` 中：
  - 当前连接上双订阅（previous + target）；
  - 断线重连后 `restoreSubscriptions()` 会再次把 target 订阅回来，泄漏跨连接持续存在。
- 放大因素：`onWsEvent` 中 `page_tool_request` 与 `session_already_running` 两个分支都**不校验 `msg.sessionId === store.sessionId()`**：
  - `page_tool_request` → `handlePageToolRequest` 直接在宿主页面执行 DOM 动作并把结果回传给一个用户已切换走的会话；
  - `session_already_running` → `rollbackAllPendingSaves()` 会误回滚**当前会话**的在途乐观气泡。
  单会话模型下原本等价于"只处理活跃会话"，双订阅泄漏后不再成立。
- 修复建议：
  1. 回退分支补 `this.ws.unsubscribe(targetId)`（在 `switchSession` 中已 subscribe 的情况下）；
  2. 顺手给 `page_tool_request` / `session_already_running` 增加与 `message_end` 相同的 `msg.sessionId === this.store.sessionId()` 归属校验，作为兜底。
- 备注：现有测试（`controller.spec.ts` 845-898 行）只覆盖"目标已删除（GET 失败，未切换）"和"切换成功"，未覆盖"reloadHistory 失败"这条回退路径，建议补一个用例。

## 中

### M1. selectHistory / newSession / switchSession 之间无并发互斥，快速连续操作产生双订阅与状态覆盖

- 位置：`sdk/embed/src/controller.ts` — `switchSession()`、`newSession()`、`selectHistory()`
- 现象：三条流程都先 `const previous = this.store.sessionId()`，再 `await`（GET / POST / reloadHistory），await 返回后**不校验 store 当前会话是否仍是 `previous`**，直接 `store.reset()` + 重新绑定 + subscribe。两次快速操作交错时（例如点击历史项 B 后立刻点"新对话"，或快速连点两个历史项）：
  1. 后完成的一方会用过期的 `previous` 执行 `unsubscribe`（对已被对方退订的会话是 no-op），但**不会退订对方刚订阅的会话** → 双订阅泄漏（后果同 H1）；
  2. `store.reset()` 会把对方刚加载完成的历史/流式状态整体抹掉，用户可能看到消息区闪空；
  3. `newSession` 与 `selectHistory` 并发时，新建的会话在服务端已创建、`tabs.claim` 已写入，但随后被 `adoptSession(另一方)` 覆盖，产生一个"孤儿会话"且用户无感知。
- 修复建议：引入切换串行化——例如一个 `switchSeq` 递增序号或 `switching` in-flight 标记：`selectHistory/newSession` 在已有切换在途时直接忽略（或排队）；`switchSession`/`newSession` 在每个 `await` 之后校验序号未变再继续，否则中止并退订自己订阅的会话。

### M2. 身份切换（setIdentity）未清理历史面板状态，跨账号数据残留

- 位置：`sdk/embed/src/controller.ts` — `setIdentity()`
- 现象：`setIdentity` 清理了 messages/pendingQuestion/pageLogs 等几乎所有 UI 状态，但**遗漏了本次新增的 `historyOpen / historyItems / historyHasMore / historyError / activeSessionId`**。SSO 账号切换后：
  - 若历史面板处于展开状态，浮窗直接显示上一个账号的会话列表（标题、时间），直到用户手动收起再展开才会重新拉取；
  - `activeSessionId` 仍指向旧账号会话，新 boot 完成前列表高亮错位。
- 修复建议：在 `setIdentity` 中与 `pageLogs` 等一起清空这五个字段。

### M3. switchSession 失败回退缺身份守卫，会把旧身份的会话重新绑定到新身份下

- 位置：`sdk/embed/src/controller.ts` — `selectHistory()` 回退分支
- 现象：`switchSession` 的 `GET /sessions/:id` 在途期间发生身份切换（`setIdentity` → `store.reset()`）。GET 因 RestClient 的 identity 校验抛 `AuthError` 后，回退条件 `previous != null && this.store.sessionId() !== previous` 成立（null ≠ previous），于是执行 `bindSession(previous) + ws.subscribe(previous)`，把**旧身份**的会话绑定/订阅到新身份下。随后新身份的 boot 会再次覆盖绑定，但旧会话订阅已泄漏（后果同 H1），且中间窗口内 `page_tool_request` 可能命中旧会话。
- 修复建议：`selectHistory` 入口捕获 `identityVersion`（对齐 `boot`/`send` 的 `stale()` 模式），回退分支先校验版本未变；`switchSession` 本身也应加同样的 stale 检查。

## 低

### L1. SessionRepository.insert() 未持久化 source 字段（当前靠 updateById 二次写"侥幸"正确）

- 位置：`backend-ts/src/session/session.repository.ts` — `insert()` vs `updateById()`
- 现象：`createSession` 在内存对象上设置了 `source: 'embed'`，但 `insert()` 的字段清单没有 `source`（新列依赖 DB 默认值 `web`）；而 `updateById()` 本次新增了 `source: session.source ?? 'web'`。当前 SDK 建会话走 CLOUD 默认分支，`initializeCloudWorkspace` 后必然触发一次 `updateById(session)`，source 恰好被补写为 `embed`，所以线上行为碰巧正确。但：
  - 任何 `executionMode != 'CLOUD'`（LOCAL）或未来不走工作区初始化的调用方传 `source:'embed'` 会静默落成 `web`，新建会话随即从历史列表消失，且 SDK 拿到的 VO `source='embed'` 会跳过惰性补标，错误无法自愈；
  - insert/updateById 字段不对称，属明显维护陷阱。
- 修复建议：`insert()` 增加 `source: session.source ?? 'web'`。另建议 `updateById` 对未从 DB 加载的 Session 对象写 `source ?? 'web'` 有把 embed 重置回 web 的风险（当前调用方均来自 DB 读取，暂无实际触发），长期看全量 update 不应携带 source。

### L2. pageSessionsByFilter 直接字符串插值 LIMIT/OFFSET，非整数参数导致 500

- 位置：`backend-ts/src/session/session.repository.ts` `pageSessionsByFilter`；`backend-ts/src/session/session.service.ts` `listSessionsByFilter`
- 现象：`ORDER BY ... LIMIT ${limit} OFFSET ${offset}`。service 只做了 `Math.max/Math.min` 范围钳制，未做整数化；`queryOptInt` 对 `Number.isFinite` 即放行，`?offset=1.5`、`?limit=2.5`、`?offset=1e21` 会生成 `OFFSET 1.5` / `LIMIT 1e+21` 之类的非法 SQL → MySQL 语法错误 → 接口 500（应为 400 或取整）。无注入风险（`Number()` 已保证为数字）。
- 修复建议：`safeOffset/safeLimit` 处 `Math.trunc`，或改用参数占位符（`LIMIT ? OFFSET ?`，与 `selectPage` 一致）。

### L3. 历史分页按 updated_at 排序 + offset 翻页，条目漂移时重复/跳过且无去重

- 位置：`sdk/embed/src/controller.ts` — `loadMoreHistory()` / `loadHistoryPage()`
- 现象：offset 取 `historyItems.length`，但列表按 `updated_at DESC` 排序——当前会话每收到新回复就会上浮到列表顶部，用户触底翻页时后续页会跳过条目或把已上浮的条目再次拉回，`historyItems` 中出现重复 id（渲染 `:key` 重复告警、条目重复展示）。属方案已知限制，但缺兜底。
- 修复建议：至少在拼接时按 id 去重（`offset===0 ? items : [...existing, ...new].filter(去重)`）。

### L4. toggleHistory 重新打开时的首页加载与在途 loadMore 并发，响应乱序会交错列表

- 位置：`sdk/embed/src/controller.ts` — `toggleHistory()` / `loadHistoryPage()`
- 现象：`loadMoreHistory` 有 `historyLoading` 守卫，但 `toggleHistory` 打开时直接 `loadHistoryPage(0)` 不检查守卫。快速"收起→再展开"（或打开瞬间同时触发滚动 loadMore）会出现两个在途请求，若 offset=0 的响应先回、loadMore 后回，最终列表变成 `[...旧列表, ...追加页]`，与首页数据交错重复。
- 修复建议：`loadHistoryPage` 内对 offset=0 也复用同一守卫（在途时忽略新请求），或引入请求序号丢弃过期响应。

### L5. 从历史面板点"新对话"后，面板不收起、列表不刷新

- 位置：`sdk/embed/src/controller.ts` — `newSession()`；`sdk/embed/src/ui/HistoryPanel.vue`
- 现象：HistoryPanel 内的"新对话"入口触发 `newSession`，但 `historyOpen` 不会被置 false，消息区仍被历史面板覆盖；`historyItems/activeSessionId` 也不更新，高亮丢失。顶部工具栏的"新对话"按钮同理（面板开着时）。
- 修复建议：`newSession` 成功后 `this.ui.historyOpen = false`（并可选刷新首页列表）。

### L6. GET /v1/sessions 过滤分支：agentId 非法值被静默忽略，报错文案有歧义

- 位置：`backend-ts/src/session/session.routes.ts`（GET 分支）、`session.service.ts` `listSessionsByFilter`
- 现象：
  - `?source=embed&agentId=abc` → `parseEntityId → null` → agent 过滤被丢弃，返回**所有 agent** 的 embed 会话，与调用方预期（指定 agent）不符，静默扩大数据范围；
  - 只传 `agentId` 不传 `source` 时报 `"source 仅允许 'web' / 'embed'"`，文案未说明"该分支要求同时提供 source"，排查体验差。
- 修复建议：过滤分支内对 `agentId` 做 `Number.isInteger` 校验，非法直接 400；错误文案改为"过滤查询需同时提供 source 与 agentId"之类的明确提示。
