## 本轮发现的问题

### 中（M）

#### M2′. M2 修复引入新回归：崩溃发生在「saveUserMessage 之前」时，该队列消息被永久丢弃（漏消费）

**位置**
- `backend-ts/src/feishu/inbound-queue.service.ts:84`：`hydrate()` 调用 `repo.deleteRunning()`（`DELETE FROM feishu_inbound_queue WHERE status='RUNNING'`，全局删除）。
- `backend-ts/src/feishu/inbound-queue.repository.ts:127-130`：`deleteRunning()`。
- `backend-ts/src/feishu/agent-inbound-handler.ts:228-245`（`runExecution` 的时序）：`createProgressCard` (async，含 Feishu 卡 PATCH 网络调用) → `updatePhase('RUNNING')` → `saveUserMessage` → `prepareMessage` → `execute`。
- `backend-ts/src/harness/core/crash-recovery-runner.ts:145-146`：`recoverSession` 重查 `current.phase` 若仍为 `RUNNING`/`RESUMING` 则从会话历史重放。

**问题场景**
`deleteRunning` 的核心前提是「RUNNING 行对应的消息**已写入会话历史**，会由 CrashRecovery 从历史重放」。但该前提只在 `saveUserMessage` 成功后成立。现有时序为：

1. `drainNext` → `claimNextQueued` 将行置为 `RUNNING`（repo:55-66）→ `busy.add` → `executeQueued` → `runExecution`。
2. `runExecution` 内**先**执行 `createProgressCard`（`agent-inbound-handler.ts:233`，为异步网络调用，且可能耗时较长）**再** `updatePhase('RUNNING')`（238）**才** `saveUserMessage`（239）。
3. 若此刻进程崩溃：行 `status='RUNNING'`，但用户的这条消息**尚未写入 session_messages**。
4. 重启：`hydrate()` 的 `deleteRunning()` 把这条 RUNNING 行直接**删除**。
5. `CrashRecoveryRunner.recoverSession` 因该会话 phase=RUNNING 而续跑，但从会话历史重放时**找不到这条用户消息**（从未落库）。

结果：该条排队消息被**永久丢弃**——既不执行，也不存在于历史，用户不会收到任何处理结果或提示。相比旧方案 `resetRunningToQueued`（把行复位为 QUEUED，漏消费但不会丢），`deleteRunning` 在此窗口是**数据丢失**，属功能性回归。

**触发概率 / 边界说明**
- 仅在「崩溃恰好发生在某条**队列消息**已 claim 为 RUNNING、但尚未完成 `saveUserMessage`」时触发。该窗口包含 `createProgressCard`（网络 PATCH）与 `updatePhase` 两个异步步骤，实际窗口不小。
- 若崩溃发生在 `saveUserMessage` **之后**（M2 主要覆盖场景），删除行 + 崩溃恢复重放是正确的，不会重复。
- 同一问题不存在于「直接执行路径」（executeDirect 也是 runExecution 同一函数，但直接路径无队列行、无 RUNNING 状态残留，不涉及 deleteRunning）。

**建议（供参考，勿直接改）**
- 方案 A（最小改动，推荐）：把 `saveUserMessage` **前移**到 `updatePhase('RUNNING')` 之前（甚至 `createProgressCard` 之前），使「行置 RUNNING」与「消息落库」之间的窗口收窄为仅剩 `createProgressCard`；但 `createProgressCard` 仍是窗口，不彻底。
- 方案 B：`deleteRunning()` 改为「删除 RUNNING 行前，先判断该行对应消息是否已存在于 session_messages」——若不存在则**保留（复位为 QUEUED）**，存在则删除。可行但需跨表核对。
- 方案 C：`hydrate()` 中把 RUNNING 行按消息是否落库做分支：落库 → 删除（交给崩溃恢复重放）；未落库 → 复位为 QUEUED（由队列消费，保证不丢）。这等价于「按需复位」，从根上避免两个方向的错误。
- 至少应明确补一个判定：崩溃恢复重放的回合是否包含该队列行消息。若**不保证**包含（即存在未落库窗口），则不能简单全局删除 RUNNING 行。

## 低（L）

### L8. `hydrate()` 全局 `deleteRunning` 在「崩溃恢复已 submit 但尚未消费完」时执行，边界语义依赖时序

**位置**
- `backend-ts/src/create-app.ts:1434-1438`：`crash.run().then(async () => { ... await feishuTaskQueue.hydrate(); ... })`。
- `crash-runner` 的 `recoverSession` 是 `agentExecutor.submit`（fire-and-forget，`crash-recovery-runner.ts:90`）。

**说明**
`crash.run()` 的 `.then` 仅表示**初始扫描已提交**（`submit` 为 fire-and-forget），并不表示恢复执行已结束。`hydrate()` 的 `deleteRunning` 运行时会与**正在异步续跑**的 `recoverSession` 并行。二者操作不同表（队列表 vs session/消息表），不会同表冲突；且 `deleteRunning` 删 RUNNING 行正是为了去重崩溃恢复正在重放的那批消息，方向正确。此条为**依赖时序的边界提示**，非缺陷：只要确保 `deleteRunning` 不要删到「非崩溃、正常新起点」的会话行即可，而 hydrate 仅在进程启动后执行一次，此刻不会存在正常执行中的会话行。标记为低，供后续维护注意。

### L9. spec mock 基类残留 `resetRunningToQueued`

**位置**
- `backend-ts/src/feishu/inbound-queue.service.spec.ts:20`：`resetRunningToQueued: vi.fn(async () => 0),`。

**说明**
仓库删除了 `resetRunningToQueued` 方法（改为 `deleteRunning`），但 spec 的 `repo()` mock 基类仍保留 `resetRunningToQueued` 键。`vitest run src/feishu` 通过（mock 多出的键不影响运行），但 `npx tsc -p tsconfig.json --noEmit` 报 `error TS2353: Object literal may only specify known properties, and 'resetRunningToQueued' does not exist in type 'Record<keyof FeishuInboundQueueRepository, unknown>'`。属测试 mock 残留，建议删除该行，避免全量 TS 类型检查报告噪音。

## 重点项核对（按用户列出的验证点）

### 1. onExecutionFinished 签名改动后调用点是否全部对齐
**结论：正确。**
- `agent-inbound-handler.ts:254`（CANCELLED）、`:258`（COMPLETED）、`:267`（FAILED）三个分支均传字面量 phase，与签名 `phase:'COMPLETED'|'FAILED'|'CANCELLED'` 一致。
- `create-app.ts:1111-1113` 的 `onExecutionFinished(sessionId,_context,executionId,phase)` 直接把 phase 透传给 `taskTerminal.finishExecution(sessionId, session.userId!, phase, executionId)`，无成功/失败布尔转换，正确。
- 崩溃恢复 `crash-recovery-runner.ts` 的 `onExecutionFinished` 是**独立参数** `(sessionId, userId) => Promise<void>`，签名与 handler 的 phase 版互不影响，未被改动（`git diff` 确认该文件 UNCHANGED），兼容。

### 2. hydrate 删除 RUNNING 行是否导致重放消息消失 / 用户消息重复落库
**结论：部分正确，存在 M2′ 漏消费回归。**
- **重复落库**：已修复。`saveUserMessage` 在 `execute` 之前（`agent-inbound-handler.ts:239`），崩溃恢复会从该用户消息重放；删除 RUNNING 行后，`onExecutionFinished` 钩子的 `drainNextIfPending` 不会再 claim 到这条已被删除的行，因此不会二次 `saveUserMessage` + 二次 `execute`。
- **消息彻底消失**：见 M2′。当崩溃发生在 `saveUserMessage` **之前**，该消息从未落库，删除 RUNNING 行后既不入队也不在历史，被永久丢弃。

### 3. deleteRunning 是否会误删「正常消费但标记 RUNNING」的行
**结论：不会误删（正常路径）。**
- RUNNING 行仅由 `claimNextQueued` 的 CAS 置位，且仅在 `executeQueued` 的 `finally` 通过 `complete(row.id)`（`deleteById`）清除。故一条 RUNNING 行严格对应「正被某个 `drainNext` 执行中」的行。
- `hydrate()` 只在进程启动后执行一次，此刻进程刚重启，不存在「本实例正常执行中」的 RUNNING 行；历史遗留的 RUNNING 行都来自崩溃前的在途执行，删除正确。
- 唯一例外即 M2′：该行代表的消息可能尚未落库。

### 4. 取消分支传 'CANCELLED' 后 finishExecution 是否接受
**结论：正确。**
- `task-terminal.service.ts:12` `TERMINAL = new Set(['COMPLETED','FAILED','CANCELLED'])`，`finishExecution` 校验 `if(!TERMINAL.has(phase)) throw`，`'CANCELLED'` 合法。
- 既有行为：`finishExecution` 在 `phase==='FAILED'` 且 `failureReason` 非空时才写 `executionError`，CANCELLED 不会写错误信息，符合预期。
- 被打断任务的会话 phase 现在正确进入 `CANCELLED`（此前是 `FAILED`），与进度卡 `cardListener.cancel()` 展示的 CANCELLED 一致，会话列表不再误显示「失败」。✅

### 5. 新增重复消费 / 漏消费 / 死循环 / 队列行永久卡死
- **重复消费**：M2 覆盖场景已解决；但引入 M2′ 漏消费（见上）。
- **漏消费**：新增的 M2′ 是漏消费（消息丢失）回归。
- **死循环**：`drainNext` 仅在 `claimed===true` 时递归，`claimNext` 返回 null 即停止；`hydrate` 后对每个 sessionId 只触发一次 `drainNextIfPending`；无新增无限递归。
- **队列行永久卡死**：`deleteRunning` 在启动时清空所有 RUNNING 行，配合 `executeQueued` 的 finally 无条件 `complete(row.id)`，队列卡死风险未新增。
