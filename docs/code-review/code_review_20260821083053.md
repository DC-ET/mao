## 二、本轮新发现问题

### 1. [高] writeErr / announce 消息在 Ink 交互模式下不可见（延迟到下一回合才显示）

- 位置：`src/tui/ink-renderer.ts`（`announce`/`noteUser`/`printHeader` 仅 push 进 `announceBuffer`）、`src/tui/app.tsx`（不渲染 announceBuffer）
- 触发条件：交互模式下任何走 `writeErr` 的路径 —— `/help`、`/session`、`/todo`、`/queue`、`/verbose`、`/copy`、`/cancel` 的确认文案、排队提示「已排队（第 N 条）」、第一次 Ctrl+C 的「再次 Ctrl+C 退出」、runOne 捕获的异常消息等。
- 原因：`announceBuffer` 只在 `finish()` 时被 drain 进下一回合的 static round，`app.tsx` 的 live 区、输入区都没有渲染该缓冲。
- 影响：用户输入 `/help` 看不到任何帮助；`/cancel` 后无确认反馈；排队成功无提示。若无后续回合（如 `/help` 后直接退出），这些输出永久丢失。旧实现 `ReplRenderer.announce` 直接写 stderr 即时可见，本轮迁移是功能回归。
- 建议：将 announceBuffer 作为 live 状态的一部分实时渲染（例如在输入框上方展示最近若干条 announce），或 `announce()` 时同步写 stderr。

### 2. [中] AskModal 中 Ctrl+C 进入自定义输入模式，ApprovalModal 中 Ctrl+C 无响应

- 位置：`src/tui/modals.tsx` AskModal `if (input === 'c' || input === 'C')`、ApprovalModal 按键分支
- 原因：`app.tsx` 以 `exitOnCtrlC: false` 创建 Ink 应用（正确，否则 Ctrl+C 会直接退出），此时 Ink 会把 Ctrl+C 作为 `input='c', key.ctrl=true` 派发给 `useInput`。AskModal 未排除 `key.ctrl`，命中 `input === 'c'` 分支进入自定义模式；ApprovalModal 则无任何分支匹配，按键被吞。
- 影响：与旧实现（`modal-ask.ts`/`modal-approval.ts` 中 `ctrl-c` = fail / deny）行为不一致。用户习惯性按 Ctrl+C 中止时，AskModal 反而切到自定义输入，ApprovalModal 则毫无反应（此时 InkInput 被 `enabled={!modal}` 禁用，Ctrl+C 无处处理）。
- 建议：在两个 modal 的 `useInput` 中显式处理 `key.ctrl && input === 'c'`（AskModal 走 `onResolve('fail')`，ApprovalModal 走 `onResolve('deny')`），并在普通字符分支排除 `key.ctrl`。

### 3. [中] AskModal 自定义模式下 Esc 直接失败整个问答，与提示文案不符

- 位置：`src/tui/modals.tsx` AskModal `if (key.escape) { onResolve('fail'); return; }`（在 customMode 判断之前）
- 影响：自定义输入提示写着「Esc 返回选项 / 取消」，但实际 Esc 直接 `'fail'` 结束全部问题，已输入的自定义内容与之前所有题目的答案一并作废。旧实现（`modal-ask.ts`）在 customMode 且存在选项时第一次 Esc 先返回选项列表，第二次才 fail。
- 建议：customMode 且 `options.length > 0` 时，Esc 先退出 customMode 回选项列表；否则才 `onResolve('fail')`。

### 4. [中] 无 options 的纯文本问题：不自动进入自定义模式，Enter 直接提交空答案

- 位置：`src/tui/modals.tsx` AskModal `const [customMode, setCustomMode] = useState(false)`
- 原因：旧实现 `customMode = options.length === 0`（无选项自动进入自由文本输入）；新实现恒为 `false`。当服务端下发 `options: []` 的开放题时，界面只显示空列表和「↑↓ 选择 Enter 确认」提示，按 Enter 直接提交 `selectedLabels: []` 的空答案，用户不知道需按 `c` 才能输入文本。
- 影响：开放题的答案被静默置空，Agent 基于空答案继续执行。
- 建议：初始化 `customMode` 为 `questions[qIndex].options?.length === 0`，或 Enter 时若 `options.length === 0` 且无自定义输入则先进入 customMode 而非提交空答案。

### 5. [低] attach 期间（setInputHandlers 之前）回答 ask modal，modal 不会关闭

- 位置：`src/tui/ink-renderer.ts` 默认 `inputHandlers.onAskResponse`（仅 `resolveAsk`，未 `setModal(null)`）
- 触发条件：恢复一个正在等待问答的会话，ask modal 在 `runner.attach()` 期间弹出且用户在 `runRepl` 的 `setInputHandlers` 执行前完成回答（loadHistory 毫秒级完成，人类几乎不可能更快，属理论竞态）。
- 影响：答案已提交但 modal 残留，输入区被 `enabled={!modal}` 禁用，界面卡死直到下一个 `ask_user_questions_cancelled`。
- 建议：默认 `onAskResponse` 中同时 `this.modal = null`（与 repl 层 handler 保持一致），成本为零。

### 6. [低] `ask_user_questions_cancelled` 不 resolve 挂起的 askHandler promise

- 位置：`src/tui/ink-renderer.ts` onEvent `'ask_user_questions_cancelled'`（仅 `this.modal = null`）；`src/session/session-runner.ts` `handleQuestions` await `askHandler`
- 影响：服务端取消问答时 modal 关闭，但 `setAskResolver` 注册的 resolver 永不 resolve，`handleQuestions` 挂起（fire-and-forget，不阻塞主流程，属 promise 泄漏）。旧代码同样存在该行为，非本轮新引入，建议顺手修复：cancelled 时按 requestId 找到 resolver 并以 `'fail'` 或空结果 resolve。
- 建议：在 `onEvent('ask_user_questions_cancelled')` 中调用 `resolveAsk(requestId, 'fail')`（注意此时不应再发 `ask_user_questions_result`，需在 handleQuestions 侧对 cancelled 后的 result 发送做防护）。

### 7. [低] InkInput 续行缓冲不可见、不可编辑，continuation 提示不生效（双轨 buffer）

- 位置：`src/tui/ink-input.tsx`（内部 `bufferRef` 管理续行并合并提交）；`src/repl/repl.ts` `handleSubmit` 的 `buffer`/`setContinuation` 逻辑实际成为死代码
- 原因：InkInput 已拦截以 `\` 结尾/未闭合 ``` 的续行并自行累积，`onSubmit` 只会收到合并后的完整多行文本，因此 repl 层 `handleSubmit` 中的续行分支永不触发、`setContinuation(true)` 永不调用，提示符不会切换为「… 」；同时续行内容存在不可见的 `bufferRef` 中，用户无法查看/编辑/丢弃已累积内容（backspace 只能删当前行）。
- 影响：功能上提交内容正确，但多行输入体验回归（旧 InputController 中 draft 可见可编辑）。若用户在续行中途想放弃，只能通过空 Enter 提交已缓冲内容，无法清空。
- 建议：续行内容显示在输入区，或在 InkInput 内同步 continuation 状态并展示已缓冲行；移除 repl 层重复的续行逻辑或让 InkInput 与 repl 共享 buffer。

### 8. [低] `/clear` 无法真正清屏

- 位置：`src/repl/repl.ts` `handleSlash('clear')` → `opts.tuiHandle.clearAll()`；`src/tui/ink-renderer.ts` clearAll 仅重置内部状态
- 原因：Ink `<Static>` 已输出的历史回合写在终端 scrollback 中，清空 `staticRounds` 数组并不会清除终端上已渲染的内容。
- 影响：`/clear` 后旧内容仍留在屏幕上（Ink 应用本身也占用了整屏），与旧实现 `\x1b[2J\x1b[H` 的真实清屏行为不符。
- 建议：Ink 下可通过输出 `\x1b[2J\x1b[H` 序列清屏后重新 flush，或明确接受「只清内部状态」的降级语义并在帮助文案中说明（若属有意为之，仅建议更新 `/help` 文案）。

### 9. [低] AskModal questions 为空数组时任意按键触发整个应用退出

- 位置：`src/tui/modals.tsx` AskModal `useInput` 首行 `if (!q) { onExit(); return; }`，`onExit={() => exit()}`
- 影响：若服务端下发 `questions: []`（异常数据），modal 显示空框，任意按键调用 Ink `exit()` 卸载整个应用，而 repl 的 `closing` 未置位，进程可能卡死在无 UI 状态。
- 建议：`questions.length === 0` 时直接 `onResolve('fail')` 而非 `exit()`。

### 10. [低] 死代码 / 未接线接口（代码质量）

- `session-runner.ts` `submitAskResult` / `submitApprovalResult` 无任何调用方（答案与审批结果实际经 askHandler promise / LocalExecutor 链路提交），建议删除以免后续维护误用；
- `types.ts` `InkTuiHandle.setMeta/setDraft/pushStaticRound` 与 `TuiAppProps.draft`、`onDraftChange` 均无实际消费方（app.tsx 未传 `onDraftChange`，`draft` prop 未传给 InkInput，InkInput 内部自管 draft）；
- `chat.ts` 残留 `askQuestionsWithController` / `askApprovalWithController` / `InputController` 未使用 import。
