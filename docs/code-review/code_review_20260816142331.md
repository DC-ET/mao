## 新发现问题

### N1（中）`preparedRequest` 与后台结果注入的时序冲突，可能导致结果不被模型消费

- 文件：`backend-ts/src/harness/core/agent-loop.ts`
- 相关位置：
  - 循环顶部（约第 155-169 行）：先 `consumeResults` 并 `context.addSystemMessage`，再 `const request = context.preparedRequest ?? buildRequest(context)`
  - 循环底部 mid-loop compaction（约第 350-365 行）：`context.preparedRequest = await this.promptEngine.buildRequest(context)`

问题链路：

1. 某一轮触发 mid-loop compaction（`CompactionConfig.loopMidwayCompact` 默认 `true`），在轮次末尾将新构建的 `preparedRequest` 存入 context；
2. 下一轮循环顶部，`consumeResults` 若拿到后台子代理结果，会以 `<后台子代理结果>` 系统消息写入 `context.messages`；
3. 但随后 `request = context.preparedRequest ?? buildRequest(context)` 命中非空 `preparedRequest`，直接使用「上一轮构建、不含该系统消息」的旧快照，且本轮 `context.preparedRequest = null`；
4. 结果已被 `consumeResults` 从 `resultsByParent` 中删除。若模型本轮恰好输出无工具调用的最终回答，主循环随即 `break`，注入的系统消息再也未被发送给模型——模型实际没有消费到这次后台结果。

影响：在「长任务触发 mid-loop compaction」与「后台子代理结果恰好于下一轮顶部到达」重叠时，模型会漏看一次后台结果。完成通知消息（`persistCompletionNotice` 持久化的 ASSISTANT 卡片消息）不受影响，用户仍可见；结果也未从数据库丢失，只是实时注入失败。

修复建议：在顶部 `consumeResults` 注入系统消息后，将 `context.preparedRequest = null`，强制本轮用新上下文重新构建 request；或把 `preparedRequest` 的消费点移到结果注入之前。同理也适用于上方的 `backgroundTaskManager.consumeCompletedResults`（该路径为既有代码，但同一模式）。

### N2（低）`cancel_subagent` 取消「已终结」子代理时会遗留 cancel flag

- 文件：`backend-ts/src/harness/delegate/background-subagent-manager.ts`
- 相关位置：`cancel()` 第 161-172 行

```ts
const loop = this.deps.agentLoop();
const flag = loop.getCancelFlag(execution.childSessionId) ?? loop.registerCancelFlag(execution.childSessionId);
flag.set(true);
```

当子代理已完成（`runBackground` 的 `finally` 已 `removeCancelFlag`），模型/用户再调用 `cancel_subagent` 时，`getCancelFlag` 返回 `undefined`，这里会重新注册一个 flag 并置 true，但该 flag 之后无人清理，残留在 `AgentLoop.cancelFlags` 中。

影响：仅为小规模内存残留；该残留 flag 会在后续 `delegate_followup` 等路径 `registerCancelFlag` 时被覆盖，基本无功能副作用。

修复建议：取消前先判断 execution 是否已终态（`isTerminal`），终态直接返回，不注册 flag；或注册后统一在 `waitTerminal` 结束处清理该 flag（但要避免误删运行中的子代理 flag，需结合是否由本方法注册来判断）。
