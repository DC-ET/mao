## 结论摘要

本轮三处修复均正确，前两轮的核心问题已解决：

- **边路/子代理重试漏显已修复**：`isAssistantRunning` 按会话读取后，与 `llmRetry`（同样按会话读取）作用域一致。后端时序为 `thinking_start`（LLM 调用前）→ `llm_retry`（HTTP 失败时），故重试期间该会话 `thinking=true` → 最后一条 assistant 消息（`isLast`）满足 `isAssistantRunning` → `llm-retry-bar` 正确渲染。
- **`thinking_start` 补 `clearLlmRetry`**：在正常重试序列中该分支位于 `llm_retry` 之前（后端先发 `thinking_start`），实际作用为防御性清理上一轮残留，无副作用。
- **断线 `onclose` 全量清理**：符合「断线后瞬时状态不可信」的意图；重连后若会话仍在重试，新的 `llm_retry` 事件会重新写入，若重试已结束则不会残留过期提示。
- **主会话无回归**：`ChatPanel` 传入 `sessionId ?? ''`，`useChat.sessionId` 与 `activeSessionId` 在 `restoreSession` 中同步赋值，`isSessionStreaming(sessionId)` 与 `activeStreaming` 等价；新任务模式/无会话时传 `''` 走旧回退分支，行为与改前一致。

## 问题清单

### 【低】取消（stop）路径未清理 `llmRetry`，且取消后终态事件被 stale 拦截导致兜底清理也不执行

- 位置：
  - `desktop/src/composables/useChat.ts:636-665`（`stopExecution`，不在本次 diff 内但为取消路径入口）
  - `desktop/src/composables/useStreamWS.ts` `routeEvent` 的 `session_status` 分支（终态清理逻辑所在）
- 根因：`stopExecution()` 本地只清 `thinking/streaming/compacting/askQuestions`，**未调用 `sessionStore.clearLlmRetry(sid)`**；同时 `stopExecution` 先执行 `clearActiveExecution(sid)` → `suppressedStreamSessions.add(sid)`，导致后端回包的 `session_status CANCELLED` 在 `routeEvent` 中被 `isStaleExecution` 判定为 stale 而 `break`——终态分支内的 `clearLlmRetry(sessionId)`（useStreamWS.ts:683）同样不会执行。两处叠加，取消时 `sessionLlmRetry[sid]` 必定残留。
- 影响：
  - UI 上无残留显示（取消后 `thinking/streaming` 已置 false → `isAssistantRunning=false`，`sending=false` → 两处提示条均不渲染），不会出现「已取消仍显示重试」的可见错误；
  - 残留条目在下次该会话运行时被 `thinking_start` 的 `clearLlmRetry`（本轮修复 2）兜底清除，无跨会话串扰（按 sessionId 隔离）。
- 建议：在 `stopExecution()` 中补充 `sessionStore.clearLlmRetry(sid)`（与 `clearAskQuestions` 并列），使取消路径与 error/终态路径的清理约定一致，避免依赖 thinking_start 兜底。

### 【低】SideChatPanel 占位会话（`session-id=''`）回退主会话 retry/运行状态（前两轮遗留）

- 位置：`desktop/src/components/chat/SideChatPanel.vue:21`（`:session-id="hasRealSession ? String(realSessionId) : ''"`）
- 说明：首次发送边路消息、`side_session_created` 未返回的占位窗口内，`session-id=''` 使 `isAssistantRunning` 与 `llmRetry` 均回退主会话 `active*`。本轮修复后两者作用域已一致（不再像第 2 轮那样错配），行为退化为「占位消息完全跟随主会话状态」。由于占位窗口极短、且占位阶段后端不会向无真实 id 的占位会话推送 `llm_retry`（事件带真实 sid，需 `side_session_created` 先到达），误显概率极低。
- 建议：可维持现状（影响可忽略）；若要彻底隔离，可在 `realSessionId` 就绪后再渲染消息列表。

### 【提示】主会话重试时两处提示同时显示（重复，非功能错误）

- 位置：`MessageBubble.vue:103`（`llm-retry-bar`）与 `ChatPanel.vue:41-44`（`typing-retry`）
- 说明：后端先发 `thinking_start` 再进入重试，因此主会话重试期间 `activeThinking=true` → 最后一条 assistant 消息内的 `llm-retry-bar` 与打字区 `typing-retry` **同时**展示相同文案（第 2 轮报告称「两处互补不重复」的结论基于 thinking_start 晚于重试的时序假设，与实际后端时序不符）。功能上两处信息均正确，仅视觉重复，不影响业务正确性（按需求约定不关注样式，不列为缺陷）。

### 【提示】断线重连后「重试中」提示不恢复

- 位置：`useStreamWS.ts` `ws.onclose`（`clearAllLlmRetry`）
- 说明：断线期间若某会话重试结束，重连后不再有新的 `llm_retry` 事件，提示不会恢复——这是「清掉不可信的过期状态」的设计意图，符合第 2 轮建议；若断线期间重试仍在进行，下一次 `llm_retry` 事件会重新写入并恢复显示。无问题，仅记录。
