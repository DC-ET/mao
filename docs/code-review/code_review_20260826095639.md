# 代码审查报告

- 审查范围：当前 Git 工作区未提交变更
- 需求：飞书消息触发者身份注入 shell 的 `MAO_TOKEN`，同时保持群会话 owner
- 结论：发现 2 个功能逻辑风险

## 高严重程度

### 1. 异步/持久 shell 可能在同一 shell 内发生身份竞争

- **位置**：`backend-ts/src/harness/tool/impl/shell-session-tool.ts:116-153`，尤其是 `handleExec` 的 `injectMaoToken`、`session.writeStdin(command...)` 与异步任务提交之间。
- **问题**：每次执行只是在共享持久 shell 中先写入一次 `export MAO_TOKEN=...`，随后写入命令。异步执行立即返回，真正的输出等待在后台任务中进行；如果同一个持久 shell 在前一个异步命令完成前再次被调用，后一次调用会再次写入新的 `export MAO_TOKEN`。此时前一个命令若尚未读取环境变量，或命令内部启动后续子命令，可能使用后一次触发者的 token，造成 MAO CLI 身份串用。
- **影响**：群聊中不同触发者复用同一持久 shell 时，异步命令不能可靠保证使用发起该命令的触发者身份；属于跨用户身份泄漏/权限执行错误。
- **修复建议**：不要依赖共享 shell 环境变量承载请求级身份。至少应对同一 `ShellSession` 的命令发送和生命周期进行串行化，并保证异步任务完成前不会插入下一次命令；更稳妥的是为每个请求使用隔离进程，或将 token 绑定到命令进程的环境而非持久 shell 全局环境。关闭/重用 shell 时也应明确处理未完成异步命令。

## 中严重程度

### 2. 新增的 `session.executionUserId` 没有作为实际执行身份使用

- **位置**：`backend-ts/src/feishu/agent-inbound-handler.ts:96`。
- **问题**：`FeishuSessionAdapter.getOrCreateSession` 的返回类型新增了 `executionUserId`，但 handler 最终调用 harness 时传入的是 `context.maoUserId ?? null`，完全忽略了已获取的 `session.executionUserId`。当前 `create-app.ts` 中两者通常由同一个解析逻辑得到，因此常规链路不一定暴露；但当 session adapter 做了身份解析、消息上下文未携带 `maoUserId`，或两者解析结果不一致时，shell 会回退到群 owner（`context.userId`），违背“消息触发者身份”要求。
- **影响**：私聊/群聊的替代调用方、异步重放或上下文构造不完整时，shell 可能使用 owner 身份或不注入 token；同时新增返回字段实际成为死字段，无法起到设计上的身份隔离作用。
- **修复建议**：handler 应将 session adapter 返回的 `executionUserId` 作为本次执行身份传给 harness，并将其作为身份来源的单一事实；`context.maoUserId` 仅可作为明确的输入解析结果，不能在已完成会话解析后被无条件优先使用。补充测试：`context.maoUserId` 为空但 `session.executionUserId` 有值，以及两者不同的群聊场景。

## 已核对且未发现回归

- 群会话查找仍按 `accountId + chatId`，未因触发者身份改变 owner；已有群会话不会切换 owner。
- `ToolDispatcher` 的 8/9 参数旧调用形态保留，新增第 10 个总参数仅在完整调用中传递；非 shell 工具仍使用原 `userId`。
- 同步 CLOUD shell、持久 shell 的每次命令注入路径均已连接到 `executionUserId`；`write_stdin` 也会重新注入 token。
- 飞书 processor 在私聊和被 @ 的群聊路径均解析绑定用户，并将解析结果放入上下文。
- `git diff --check` 通过；构建命令 `cd backend-ts && npm run build` 通过。此前按项目脚本直接执行的测试命令包含不受 Vitest 支持的 `--runInBand` 参数，因此该次测试未能启动，不能作为业务测试结论。
