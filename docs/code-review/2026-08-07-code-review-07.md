## 本轮新增改动的核验（通过）

`OpenAiLlmAdapter.stream()` 重试分支（约 121-127 行）现在的顺序为：

```java
if (attempt > llmRetryConfig.getRateLimitMaxRetries()) { onError(重试耗尽); return; }
int delaySeconds = resolveRetryDelaySeconds(response);
log.warn(...);
if (isCancelled(cancelFlag)) {            // ← 本轮新增
    callback.onError(new RuntimeException("Cancelled by user"));
    return;
}
callback.onRetry(response.code(), attempt, maxRetries, delaySeconds);
if (!sleepSecondsRespectingCancel(delaySeconds, cancelFlag)) { onError(Cancelled); return; }
continue;
```

逐项核验：

1. **竞态窗口收敛正确**：用户在「重试判定 ↔ 睡眠等待」之间取消时，现在先走取消分支直接 `onError(Cancelled)`，不再先推 `llm_retry` 再取消（第 1 轮问题 2 已修复）。与循环顶部、睡眠取消的既有取消处理模式完全一致。
2. **无资源泄漏**：该分支位于 `try { ... } finally { response.close(); }` 内。AgentLoop 的 `onError` 会抛 `RuntimeException`，经 finally 关闭 response 后向外传播；即使 `onError` 不抛（测试等其它调用方），`return` 也会触发 finally 关闭。两种情况均无泄漏。
3. **无双重 onError**：`awaitResponse` 返回非 null response 说明其未调用过 onError；本轮分支是取消路径上唯一一次 onError，与循环顶部/睡眠取消互斥。
4. **取消语义与 AgentLoop 衔接正确**：`onError("Cancelled by user")` → AgentLoop.onError 抛 `RuntimeException("LLM call failed: Cancelled by user")` → catch 块 `contains("Cancelled by user")` → break 结束循环，符合既有取消约定。
5. **`cancelFlag == null` 场景兼容**：`isCancelled` 对 null 返回 false，与 `sleepSecondsRespectingCancel` 一致，不影响无取消标志的调用方（测试等）。

## 链路、时序、payload、并发核验（均通过，与第 1 轮结论一致）

1. **事件链路完整**：`StreamCallback.onRetry`（default 空实现）→ AgentLoop 匿名回调 → `listener.onLlmRetry` → `CompositeAgentEventListener.onLlmRetry`（forEach + try-catch 隔离）→ `WsStreamingEventListener.onLlmRetry` → `send("llm_retry", payload)`。全工程仅 3 个 `AgentEventListener` 实现：`WsStreamingEventListener`、`CompositeAgentEventListener`（均已实现）、`SubAgentResultCollector`（default 空实现，仅收集结果，无需处理）。`stream()` 生产调用方仅 AgentLoop 一处；测试用例使用 Mockito stub 不受影响。
2. **重试时序**：`onRetry` 在「重试耗尽判定之后、睡眠等待之前」调用；重试仅发生在 HTTP 状态码阶段（429 / 500-599，覆盖 502/503/524），流内容开始后不重试，无乱序。
3. **attempt/maxRetries 语义**：attempt 从 1 起计，共发 maxRetries 次 `llm_retry`（1/max … max/max），第 maxRetries+1 次要么成功要么 onError，无 off-by-one。
4. **WS payload 与 stale 过滤**：`statusCode/attempt/maxRetries/delaySeconds` 与前端 `useStreamWS.ts` 解析完全一致；`executionId` 由 `WsStreamingEventListener.send()` 统一附加；前端 `STREAM_EVENT_TYPES` 已含 `llm_retry`，走统一 `isStaleExecution` 过滤，无旁路。
5. **并发/线程安全**：`onRetry` 与 `onChunk` 同线程（AgentLoop 执行线程）；`registry.send` → `outboundQueue.offer` 非阻塞、线程安全、不抛异常；`activityHeartbeat.touch` 内部吞异常；`WsEvent.of` / `eventItem` 纯构造不抛异常。主路径 listener 虽为裸 `WsStreamingEventListener`（非 Composite），但其 `send()` 链路无异常外溢风险，与既有所有事件同一模式，未引入新风险类。
6. **前端清除时机**：`content_delta` / `thinking_delta` / `tool_call_start` / `thinking_end` / `message_end` / `error` / 终态 `session_status` 均调用 `clearLlmRetry`，后端事件流提供了完整的「重试结束」信号。

## 遗留问题（第 1 轮已报告，本轮未处理，非本轮引入）

### [低] 1. 非流式 `chat()` 路径（Agent 循环中途压缩）仍无重试可见性事件
- **位置**：`OpenAiLlmAdapter.chat()`（约 60-75 行）；调用方 `CompactionService.java:639`（AgentLoop 中途压缩，同步执行）
- **说明**：`chat()` 与 `stream()` 重试逻辑相同（默认 10 次 × 5s ≈ 最长 50s），但无回调可上报。中途压缩发生在 AgentLoop 主循环内，压缩摘要 LLM 重试期间客户端只见 `compaction_start/end`，仍存在界面无响应空白，与本需求目标部分冲突。`DangerAssessor` 为工具/后台路径，影响较小。
- **建议**：为 `chat()` 增加可选重试回调参数（或复用 `StreamCallback`），由 AgentLoop 在压缩阶段透传。

### [信息] 2. 残余极小竞态：取消发生在 isCancelled 检查与 onRetry 之间
- **位置**：`OpenAiLlmAdapter.java` stream() 约 121-127 行
- **说明**：本轮检查已把竞态窗口从「重试判定到睡眠」收敛为「isCancelled 检查到 onRetry 调用」的微秒级 check-then-act 窗口（本质上不可完全消除）。命中时客户端先收到 `llm_retry` 再收到取消错误，提示条随即被清除，功能无害。

### [信息] 3. 子智能体重试事件只进子会话流
- **位置**：`SubAgentVisibilityService.executeVisible()`（非本次改动文件）
- **说明**：子代理执行走 `CompositeAgentEventListener(wsListener, resultCollector)`，`onLlmRetry` 只推到子会话（childSessionId + child executionId）。父会话用户未打开 Side Task 面板时看不到子代理重试提示，与既有 content_delta 等子会话流事件路由设计一致，非 bug。
