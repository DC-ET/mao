## 总体结论

**有条件可合并（阻塞项 0，重要项 1，建议项 1）。**

本次抽取方向正确，且相比原实现有两点实质改进：

1. 原实现 `ensureCommandContent` 在发请求**之前**就置位 `commandsFetched = true`，并发调用会产生重复请求且失败后永不重试；新实现改为成功后才置位、失败不置位可重试，并用 `fetchInflight` 做在途去重。并发去重逻辑本身无竞态（赋值发生在同步段内，JS 单线程下第二个调用必然看到已赋值的 promise）。
2. `invalidateCommandContent()` 整体替换 `commandContentMap.value`，而 `getCommandContent()` 在 MessageBubble 模板渲染期间读取该 shallowRef，依赖被渲染副作用收集，因此失效能触发已渲染气泡重渲染（原实现从不失效，标签 tooltip 永远停留在旧内容）。

但「失效 → 重渲染 → 拿到新内容」这条链路**断在中间一环**，见问题 1。

## 问题列表

### 重要

#### 1. 缓存失效后，已挂载消息气泡的指令内容无法恢复（tooltip 永久丢失直到偶发重取）

- 位置：`desktop/src/utils/commandContent.ts:34-37`（`invalidateCommandContent`）+ `desktop/src/components/chat/MessageBubble.vue:405`
- 描述：失效链路分三步：① invalidate 清空 map 并置 `commandsFetched = false`；② shallowRef 整体替换触发已渲染气泡重渲染，此时 `getCommandContent` 返回 `undefined`，`QuickCommandTag` 走 `v-if="content"` 的 else 分支，tooltip 消失；③ 需要有人再次调用 `ensureCommandContent()` 才能拉回新数据。但唯一调用点是 MessageBubble 中 `watch(hasCommandSegments, ..., { immediate: true })`——对**已经挂载**的气泡，`hasCommandSegments` 保持 `true` 不变，watch 不会再次触发；聊天面板被 KeepAlive 缓存，切回聊天 Tab 也不重挂载。因此：
  - 用户在设置页编辑/删除指令后回到聊天，已渲染的 `@指令` 标签 tooltip 内容**整体消失**（不是显示新内容，也不是旧内容）；
  - 只有当任意位置**新挂载**一个含 command 段的 MessageBubble（如新消息到达、历史会话重开），其 `immediate` watch 才会触发重取，届时所有气泡才一次性恢复。
- 影响：修复的原始目标「缓存失效后正确刷新」对存量气泡不生效，出现可稳定复现的 tooltip 内容丢失。
- 修复建议（二选一，推荐 a）：
  - a. 在 `invalidateCommandContent()` 中标记失效后主动调度一次后台重取（`commandsFetched = false; void ensureCommandContent()`）。失效总是发生在指令写操作成功之后，此时重取即可拿到最新数据，重取完成后整体替换 shallowRef，所有已跟踪渲染的气泡自动恢复。若同时修复问题 2，可用「代数（generation）计数」一并解决：invalidate 时 `generation++`，`ensureCommandContent` 在 await 前捕获代数，回写前比对，代数变化则丢弃本次结果（避免旧响应回填），invalidate 内调度的新请求自然胜出。
  - b. MessageBubble 改为 watch 一个共享的「缓存版本号」ref（invalidate 时自增），版本变化且本气泡含 command 段时调用 `ensureCommandContent()`。改动面更大，不如 a 集中。

### 建议

#### 2. invalidate 与在途 GET 存在竞态，旧数据可能回填并锁死缓存

- 位置：`desktop/src/utils/commandContent.ts:13-32`（`ensureCommandContent`）与 `:34-37`（`invalidateCommandContent`）
- 描述：时序：某气泡触发 `ensureCommandContent()`，GET `/user-commands` 在途；期间用户完成一次指令写操作（如删除）→ `invalidateCommandContent()` 清空 map、置 `commandsFetched = false`；随后在途 GET 返回，将**旧数据**整体写回 `commandContentMap.value` 并置 `commandsFetched = true`。此后缓存被标记为已取，内容却是过期数据，直到下一次 invalidate 才纠正。真实触发场景举例：用户停留在设置页期间，聊天 Tab 仍被 KeepAlive 保活，WS 推送的新消息气泡挂载并发出 GET，与用户同时进行的删除/编辑操作交错。
- 影响：低概率但后果是缓存锁定为过期内容且不再自愈（不会无限重试，因为 `commandsFetched = true`）。
- 修复建议：与问题 1 的修复方案 a 合并处理——invalidate 递增代数，`ensureCommandContent` 回写前校验代数一致才应用结果并置位 `commandsFetched`。

## 已检查且确认无问题的点

- **`ensureCommandContent` 基础并发安全**：`fetchInflight` 赋值在 IIFE 同步段完成，同 tick 内多次调用能正确共享同一 promise；失败路径 `finally` 清理在途标记、成功路径才置位 `commandsFetched`，无重试风暴风险。
- **模板普通函数调用的响应性**：`getCommandContent` 虽是普通函数，但其在渲染期间读取共享 shallowRef，依赖可被收集，整体替换 `.value` 可触发重渲染；与原实现相比行为一致或更优（原实现无失效路径）。
- **失效调用点覆盖**：创建/更新（`CommandEditDialog.vue:122`）与删除（`CommandManager.vue:116`）均已在成功后调用 invalidate；`CommandManager` 通过 `@saved="fetchCommands"` 刷新列表，与缓存失效互不冲突、不会漏调。
- **与快捷指令面板互不干扰**：ChatInput 的补全面板走独立的 `GET /quick-commands`（`ChatInput.vue:522`，自带 `commandsLoaded` 标志与失败置位逻辑），不读写 `commandContent.ts` 的缓存；`CommandManager` 的 `GET /user-commands`、`GET /user-commands/system` 也只更新组件本地状态。两端数据通路隔离，无交叉污染。
- **入口迁移配套**：ChatPanel / SideChatPanel / SubagentChatPanel 中 `ref` 均已导入，`CommandEditDialog` 已正确注册并暴露 `open/openEdit`，`add-to-command` 的互斥语义（弹窗打开中提示不覆盖）与原抽屉一致。
