### P2-1. 数值/布尔参数在 SDK 侧被静默转成空串：`page_fill` 写空、`page_actions` 写入成功却报失败

**位置**
- `backend-ts/src/harness/tool/impl/page-tools.ts:190-195`（`PageFillTool.requireArgs` 用 `asText` 校验）
- `backend-ts/src/harness/tool/json.ts:16-21`（`asText(123) === '123'`）
- `sdk/embed/src/page/engine.ts:205`：`value: stringArg(args.value) ?? ''`
- `sdk/embed/src/page/executor.ts:254`：`if (actual !== action.value)`

**问题**

后端校验与 SDK 取值对「非字符串」的判定不一致，导致同一个参数出现两种错误行为：

1. 单动作 `page_fill`：模型对数字输入框常会输出 `{"value": 123}`（JSON number）。后端 `requireArgs` 用 `asText(123)` 得到 `'123'`，判定参数存在并放行；SDK `stringArg(123)` 只接受 `typeof === 'string'`，返回 `undefined`，于是被 `?? ''` 兜成**空串**。`setElementValue(el, '')` 把字段清空，回读 `'' === ''`，动作被报告为 **success**。Agent 以为填了 123，实际清空了用户输入。
2. 批量 `page_actions`：`handleBatch` 把原始 JSON 对象直接 `as PageAction[]`（`engine.ts:270-289`），不做归一化。`executeFill` 里 `setElementValue(el, 123)` 会把值写成 `"123"`（原生 setter 会转字符串），但回读 `actual` 是 `"123"`、`action.value` 是 `123`，`"123" !== 123` 成立 → 返回 `value_not_applied`（文案「写入后回读值不一致」）。**副作用已发生，却报告失败**，批量因此中断，Agent 很可能反复重试。

`page_select` 的 `value` 同理（数字会在 SDK 被兜成 `''` → `option_not_found`，属“响亮失败”，影响较小）；`page_keyboard.key` 数字会被兜成空 key。

**修复建议**

- 在 SDK 入口统一归一化：`engine.handleRequest` 的 `page_fill`/`page_select` 用 `typeof v === 'string' ? v : (typeof v === 'number' || typeof v === 'boolean' ? String(v) : undefined)`，而不是 `?? ''`；`page_actions` 在 `handleBatch` 里对每个 action 的 `value`/`key`/`text` 做同样归一化（或直接拒绝非字符串并返回 `invalid_arguments`）。
- 后端 `requireArgs` 与 SDK 口径保持一致：要么都接受可转字符串的标量，要么都只接受字符串。
- 补回归用例：`page_fill`/`page_actions` 传 `value: 123` 时，字段最终值为 `"123"` 且 `success === true`。

### P2-2. 切换授权级别时 pending 确认不 resolve：弹窗消失、动作挂满 120s 后被拒

**位置**
- `sdk/embed/src/controller.ts:294-297`：`onAuthorizationChange` 中 `if (level !== 'task') this.ui.pageConfirm = null;`
- `sdk/embed/src/page/authorization.ts:108-137`（`setLevel` 不处理 `this.pending`）、`:196-209`（`requestConfirmation` 120s 定时器）

**问题**

`per_action` 下 Agent 请求点击等动作时会 `requestConfirmation`，弹窗（`ui.pageConfirm`）显示“拒绝 / 允许本次”。若用户此时点了浮窗里的「完全授权」「本次任务授权」或「改为每次确认」按钮：

- `setLevel` 只改级别并 `emitState`，**不会 resolve 已挂起的 confirmation**；
- `onAuthorizationChange` 因 `level !== 'task'` 把 `ui.pageConfirm` 置 null，弹窗消失，`id` 也随之丢失，用户再也无法点“允许/拒绝”；
- 挂起的 Promise 只能等 120s 定时器触发后以 `false` 结束，`authorize` 返回 `authorization_denied`，该页面工具在**120 秒后**才失败返回。

用户刚授予了更高权限，动作却被静默拒绝并卡 2 分钟，属可复现的功能缺陷。`syncIdentity()`（重登/切身份）走到同一个 `onAuthorizationChange` 分支，同样会触发。

**修复建议**

- `PageAuthorization.setLevel()` / `revoke()` / `syncIdentity()` 在级别或身份变化时，先 `for (entry of this.pending) { clearTimeout(entry.timer); entry.resolve(false) } ; this.pending.clear(); this.options.onConfirmRequest?.(null)`（抽一个 `cancelPendingConfirmations()`），再改级别；
- 或者保留弹窗：`onAuthorizationChange` 不要无条件清 `ui.pageConfirm`，只在 `cancel/destroy/endTask` 时清。
- 补用例：`requestConfirmation` 挂起 → `setLevel('full')` → 断言 Promise 立即 settle 且 `ui.pageConfirm === null`。

### P2-3. 内置截图渲染器不应用滚动偏移，遮罩坐标与图像内容不同坐标系（P1-2 修复的残留）

**位置**
- `sdk/embed/src/page/screenshot.ts:90-116`（`defaultRenderer`：`clone.innerHTML` 放进固定 `width/height` 的 `overflow:hidden` 容器）
- `sdk/embed/src/page/screenshot.ts:164-182`（`capturePageScreenshot` 用视口尺寸、`scale` 缩放遮罩）
- `sdk/embed/src/page/engine.ts:148-149`（遮罩 rect 来自 `rectOf` → `getBoundingClientRect()`，即**视口坐标**）

**问题**

P1-2 已改成“截图前按当前 DOM 现算敏感区域”，方向正确。但内置渲染器把 `document.body` 的 `innerHTML` 塞进一个 `height = 视口高` 的 `overflow:hidden` 容器，**没有任何 `window.scrollY/scrollX` 补偿**，所以图像内容是“文档顶部起算的视口高度”，而 `maskRects` 是“当前视口坐标”：

- 页面已滚动时，二者整体错位 `scrollY`：遮罩涂在错误位置，真正的敏感字段可能未被遮住；
- 更糟的是“滚动后截图”正是方案 4.1 的既定流程（inspect → scroll → screenshot）。若敏感字段（非 `type=password`，如 `name=cvv`/`idcard` 的文本输入）在**当前视口上方**，它会被渲染进图（文档顶部起算），而遮罩 rect 的 `y` 为负被 `Math.max(0, …)` 钳到 0，几乎必然盖不住 → 敏感值可能以明文形式发给 LLM。

`MaoChatPageOptions.screenshotRenderer` 注释也写明内置渲染器是“当前视口”，与其实际行为不符。测试都用注入的 renderer，所以覆盖不到。

**修复建议**

- 在 `defaultRenderer` 里把克隆体按 `-window.scrollX/-window.scrollY` 平移（例如给内层容器加 `transform: translate(-scrollXpx, -scrollYpx)`，或 `position:absolute; left:-scrollX; top:-scrollY`），使输出与当前视口一致；`position: fixed` 元素不要叠加该偏移。
- 或者在 `capturePageScreenshot` 里把 `maskRects` 先减去 `scrollX/scrollY` 再乘 `scale`（与所选渲染器语义保持一致），并在注释里固化“rect 一律视口坐标”的约定。
- 补一个「页面滚动后截图，遮罩 rect 覆盖的是新坐标」的用例（可用注入 renderer 断言传入的 `maskRects` 与期望一致）。

### P2-4. 宿主公开 API `setPageAuthorization('full')` 仍可静默持久化完全授权（P2-6 同类未闭合）

**位置**
- `sdk/embed/src/index.ts:71`：`setPageAuthorization: (level) => controller.setPageAuthorization(level)`
- `sdk/embed/src/controller.ts:893-895` → `pageEngine.setLevel(level, sessionId)` → `authorization.ts:108-137`（`level === 'full'` 时 `localStorage.setItem(key, 'full')`）
- `sdk/embed/src/types.ts:33`（`MaoChatInstance.setPageAuthorization`）

**问题**

P2-6 只把 `page.initialLevel: 'full'` 降级为 `per_action`，但业务方仍可调用 `instance.setPageAuthorization('full')`，一行代码即可为最终用户**持久化**完全授权，且不弹任何确认。方案 3.3 / `MaoChatPageOptions` 注释的约定是“完全授权必须由用户在浮窗内显式授予”。窗口内 UI 的「完全授权」按钮属于用户显式操作，没问题；但这个同名公开 API 绕过了该约束。

**修复建议**

- 公开 API 只允许收紧/会话级：`setPageAuthorization` 对 `'full'` 走与 `setInitialLevel` 相同的降级（或抛错/忽略），或改为 `requestPageAuthorization()` 触发一次浮窗内确认；
- 若确实要给宿主做自定义授权 UI 的能力，需在接口文档里明确“宿主调用即代表已获用户同意”，并至少加一次 SDK 内确认。
- 补用例：`instance.setPageAuthorization('full')` 后 `getPageAuthorization() !== 'full'`（或需要确认）。

## P3 / 备注（不阻塞）

1. **截图结果缓存常驻内存偏大**：`controller.ts:215,916-942` 的 `pageToolResults` 以 requestId 缓存完整结果，含 `dataUri`（上限 600KB PNG → ~800KB base64），最多 51 条 ≈ 40MB 常驻在宿主页面。建议截图类结果只缓存 `requestId` 已处理标记 + 轻量摘要，或对缓存总量按字节设上限。
2. **`page_scroll {to:'bottom'}` 误报失败**：`executor.ts:206-219`，window 场景 `expected.top = document.documentElement.scrollHeight`，而实际最大 `scrollY = scrollHeight - innerHeight`，因此“已经到底 / 页面不可滚动”时 `after.top > before.top` 与 `after.top >= expected.top - 2` 都不成立 → `scroll_failed`。建议用 `scrollingElement.scrollHeight - clientHeight` 作为期望值，或“位置不再变化即视为成功”。
3. **遮罩扫描受 400 元素上限影响**：`engine.ts:148-149` 调 `scanPage` 未传 `maxElements`，`scanner.ts` 默认 400 且 `includeHidden:true` 会把隐藏控件也算进预算；元素很多且敏感字段排在 400 之后时不会被遮罩。建议遮罩扫描单独放大上限或只扫敏感字段。
4. **导航后 `page_observe` 的 `snapshotId` 返回 null**：`snapshot-manager.ts` `observe` 返回 `this.record?.snapshot.snapshotId ?? null`，导航使 `record=null`，Agent 无法用新 snapshotId 继续链式对比（虽已能正确报告 `navigated=true`）。可考虑 observe 时补建一条 record，或在结果里明确提示需重新 inspect。
5. **单动作 `page_wait`/`page_scroll` 未接 `shouldAbort`**：`engine.ts:255` 的 `handleSingle` 只传 `authorize`，而 `execute` 对 `wait` 在授权前就 `return this.executeWait(...)`（`executor.ts:96`），因此用户点停止后单条 `page_wait` 仍会跑满（最长 10s）再回包。后端 `failSession` 已能让 Agent 立刻解阻塞，故仅影响一次多余回包；建议与批量路径一致地传 `shouldAbort`。
6. **非法 `action.type` 会先弹确认**：`executor.ts:96-129` 对未知 type 仍会走 `authorize`（`isMutatingAction('foo')` 为 true），`engine.describeAction` 无 default 返回 `undefined`，确认弹窗内容为空；随后才以 `unsupported_action` 失败。建议在 `execute` 开头先校验 type 白名单。
7. **P2-7 残留**：签名加入属性哈希 + WeakMap token 后，能拦住「节点被替换」和「节点属性变化」；但若列表**原地复用同一 DOM 节点、且该节点自身文本与属性都不变**（业务标识只在兄弟单元格或闭包中），旧 `elementId` 仍会命中新业务对象。如后续有该类场景，可考虑 inspect 时挂 `MutationObserver` 使快照失效。
