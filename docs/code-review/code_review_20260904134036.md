## 二、本轮新发现的问题

### N1（高）`ui.connected` 永远为 false → 输入框与发送按钮永久禁用（第一轮遗漏，本轮确认）

- 位置：`sdk/embed/src/core/ws-client.ts:103-107`（onmessage 拦截 `type === 'connected'`，只调 `onAuthenticated` 后 return，**不转发给 onEvent**）；`sdk/embed/src/controller.ts:209-211`（`case 'connected': this.ui.connected = true` 永不可达）；`sdk/embed/src/ui/ChatPanel.vue:39`（`inputDisabled = !props.connected || running`）
- 现象：全代码库中 `ui.connected = true` 只有这一条不可达路径（grep 证实）。修复 H2 时建立的 6 组 watch 投影恰好漏掉了 connected。后果：**浮窗能打开、历史能看到，但 textarea 与发送按钮永久禁用（placeholder 恒为"连接中…"），用户无法发送任何消息**——SDK 的核心交互仍被阻断。该问题在第一轮即存在（当时被 H2/H3 掩盖），本轮 H2 修复后成为剩余的主要阻断点。
- 建议修复：在 `onAuthenticated` 钩子里同步 `this.ui.connected = true`（重连后自动恢复），或对 `ws.connected` ref 增加 watch 投影；onclose 对应置 false。

### N2（中）`tabs.inquire(this.options.agentId)` 参数错位：agentId 被当作 waitMs，300ms 等待窗口变为 ~1ms

- 位置：`sdk/embed/src/controller.ts:164`（`await this.tabs.inquire(this.options.agentId)`）；`sdk/embed/src/core/tabs.ts:96`（`async inquire(waitMs = 300)`）
- 现象：M3 重构把 agentId 挪进 TabsCoordinator 构造器、`inquire` 签名改为 `(waitMs)`，但 controller 调用点没同步——`agentId`（如 1）被当成 `waitMs=1`。BroadcastChannel 跨 tab 投递是异步任务，1ms 超时窗口内另一 tab 几乎必然来不及应答 → **M3 的应答闭环虽已写对，但被调用点废掉，多 tab 首开竞态保护实际仍不生效**。TS 编译不报错（number→number）。
- 建议修复：调用点改为 `await this.tabs.inquire()`。

### N3（低）disconnect() 打断在途 connect() 时，等待中的 Promise 永不 settle（L2 残留）

- 位置：`sdk/embed/src/core/ws-client.ts` `disconnect()`（只置 `connectPromise = null`，不 settle）+ `onclose`（`intentionalClose` 分支不 reject）
- 现象：若 `destroy()`/`disconnect()` 恰好发生在 `boot()` 的 `await this.ws.connect()` 期间，该 await 永久挂起，boot 的 catch 不执行。因 controller 同时已 destroyed 且引用被释放，实际影响是轻微的悬挂协程/内存滞留，非用户可见故障。desktop 版通过 pendingSettle.reject 处理了此场景，embed 裁剪时丢失。
- 建议：disconnect 时对未 settle 的 connectPromise reject 一次（对齐 desktop）。

### N4（低）`unread` 从未累加、`MaoChatEvent 'unread'` 永不触发（死代码）

- 位置：`sdk/embed/src/core/store.ts`（`unread` 仅 `markRead()` 置 0，无任何累加点）；`controller.ts` watch(store.unread) 投影
- 现象：launcher 的 attention 圆点永远不会因新消息点亮（仅 pendingQuestion 生效）。不影响对话主流程，属未完成的功能点或应移除的死代码。

### N5（低）M2 移除审批后的残留

- 位置：`sdk/embed/src/core/ws-client.ts:9,224-228`（`WsToolApprovalFrame` import 与 `sendToolApproval` 方法已无调用方）；`shared/contracts/src/ws.ts` 保留 `WsToolApprovalFrame`（作为协议类型保留可接受）
- 现象：无行为影响，建议随下次改动清理。

## 三、修复逻辑复核中确认无问题的点

- **H2 watch 投影正确性**：`store.messages` 是 `ref`（数组本身是 reactive proxy），`ui.messages = v` 后同一引用的原地变更（push/字段修改）能穿透 `reactive(ui)` 触发 ChatPanel 更新；`store.reset()` 换新数组也触发投影。newSession → reset → 投影清空链路验证通过。
- **boot 顺序（L3）**：ensureHistory 先于 connect/subscribe，无首开竞态；subscribe 经 `onAuthenticated → resubscribe` 与显式 `subscribe()` 双路径幂等（重复 subscribe 帧服务端无害）。
- **connect 归属校验（L2）**：新连接建立后旧 socket 迟到 onclose 正确早退，不再误清新连接心跳/重复排程重连。
- **M1 链路**：401 → invalidate → 重试取新 token → 仍 401 抛 AuthError → boot 展示"凭据失效"；与 WS 1003 → onAuthFailed 路径一致。
- **M3 闭环（tabs.ts 内部）**：inquiry 应答校验 agentId、nonce 配对、BroadcastChannel 不回环（发者不收）均正确；claim 广播 + 共享 localStorage 的组合对"错开时序的多 tab"已能收敛到同一会话（真正的并发首开仍可能产生一个服务端孤儿会话——设计固有局限，影响小，仅记录）。
- **产物一致性**：提交的两份产物（latest + v0.1.0）md5 相同，且已包含全部源码修复（thinkingContent/tool_call_id/session_already_running 均可在产物中检索到），不存在"源码改了产物没重出"的脱节。
- CI（sdk/embed job）、prebuild 脚本本轮未改动，维持上轮"无问题"结论。
