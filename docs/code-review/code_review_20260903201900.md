# 代码审查报告：Shell 工具「等待语义」变更

- 审查时间：2026-09-03 20:19
- 审查基线：工作区未提交变更（HEAD = `454e6c02`）
- 涉及范围：`backend-ts/src/harness/{shell,tool,core}`、`desktop/electron/localShell.cjs`、`agent-cli/vendor/localShell.cjs`（desktop 与 agent-cli 两份文件当前完全一致）、相关 spec
- 变更主题：Shell 工具新增 `wait_for` 提前放行与 `await_async` 续等、会话常驻缓冲、命令未结束不回收会话、`write_stdin` 直喂运行中命令、后台任务可主动领取
- 验证情况：backend-ts vitest（87 例）、desktop `node --test`（18 例）、agent-cli vitest（474 例）全部通过；本报告所列问题均通过独立复现脚本对真实 bash 子进程实际复现确认

## 总体评价

本轮重构方向正确：常驻读取解决了「提前放行后输出丢失」这一老问题，`pendingMarkerTail` 对 marker 跨 chunk 的处理、`trimBuffer` 落盘裁剪、`awaitResult` 三态化等实现都比较细致，且补了大量针对性测试。发现的问题集中在**并发窗口**（拿锁前的快照过期）与**等待期间的输入归属**上，属于低频但后果较重的功能性缺陷；另有几处低风险语义偏差，一并列出供参考。

## 问题清单

### P1-1 会话被假 `pendingCommand` 永久卡死（CLOUD，backend-ts）

**文件**：`backend-ts/src/harness/tool/impl/shell-session-tool.ts`（`handleWriteStdin`、`handleAwaitAsync`）与 `backend-ts/src/harness/shell/shell-session-manager.ts`（`readUntilMarker` 开头的补登记逻辑）。

**机理**：两个入口都是先取 `session.pendingCommand` 快照、再 `await session.acquireCommand()` 拿锁，拿锁后仍按**拿锁前**的旧快照处理。若在等待锁期间命令被其他持锁者读完（`finishCommand` 置 `pendingCommand = null`），后续 `readUntilMarker` 开头的兜底逻辑：

```ts
// readUntilMarker() 开头
if (session.pendingCommand?.marker !== marker) session.beginCommand(marker, true);
```

会把**已消费过的旧 marker**重新登记为一条新的假 `pendingCommand`。这个 marker 在缓冲区里早已被消费掉、永远不会再次出现，于是：

- 该调用方自己超时返回 `completed:false`；
- 会话从此带上一条永不消失的假 pending，之后所有 `exec` 被永久拒绝（「会话仍有未结束的命令」），`await_async` 也只能反复空等到超时，只能 `close` 整个会话才能解脱。

**触发窗口**：上一条命令在「快照读取」与「拿到锁」之间自然结束（命令刚结束、输出已在缓冲区、锁又被并行调用者持有）。并行工具调用 / 用户快速连续操作时即可触发。

**复现**（真实 bash 子进程，已验证）：

```
[1] exec 提前放行（completed:false）
[2] await_async: completed:true, output:"done\n"        ← 正常消费
[3] write_stdin: completed:false, output:"next-marker\n" ← 旧快照补登记假 marker，等 6s 超时
[4] exec 被永久拒绝：会话仍有未结束的命令
[5] await_async 永远 completed:false
[6] 后续 probe 命令同样被挡，会话只能 close
```

**建议方向**：拿锁后重新校验快照（拿锁后 `session.pendingCommand` 与 T0 快照不一致时直接按新状态走，例如返回「命令已结束，无待读输出」或重新取 pending）；`readUntilMarker` 的补登记只对「从锁内刚写入的 marker」生效，或补登记前校验该 marker 是否真的从未消费过（如保留 `lastConsumedMarker` 记录）。

### P1-2 `write_stdin` 在审批窗口期命中命令结束，输入的响应被张冠李戴（desktop / agent-cli）

**文件**：`desktop/electron/localShell.cjs` 与 `agent-cli/vendor/localShell.cjs` 的 `handleWriteStdin`（两份文件相同）。

**机理**：`pending?.background` 检查发生在 `await ensureApproved(ctx, input)` **之前**，但真正的 `pending` 分支判断发生在审批**之后**。若审批等待期间正在运行的命令恰好结束（marker 行已进入缓冲区），恢复执行后代码仍按「有 pending」分支处理：

```js
if (pending) {
  session.writeStdin(input...)                     // 输入被 bash 当作新命令排队执行
  const answered = await readUntilMarker(session, pending.marker, ...)
  // readUntilMarker 立即在缓冲区里找到旧 marker → 马上返回旧命令的结果
}
```

后果有两层：

1. **响应错配（主要）**：`readUntilMarker` 对旧 marker 立即命中，把**旧命令的输出当作本次输入的响应**返回给模型（`completed:true`、旧 exit_code），模型会以为交互输入已经得到应答；
2. 输入被当作新命令执行，其输出滞留缓冲区，通常会被紧随其后的 `resolveCurrentWorkdir` 的 `pwd` 协议读取静默吞掉（副作用小，但语义已错）。

复现（真实 bash + 模拟 800ms 审批延迟，已验证）：

```
[1] exec "sleep 1.2; echo finished" 提前放行
[2] write_stdin input:"echo my-interactive-input"（审批期间命令结束）
    → 返回 completed:true, output:"finished"   ← 是旧命令的输出，不是输入的响应
[3] 输入本身已被执行，输出被 pwd 探测吞掉
```

**建议方向**：审批通过后、写 stdin 前重新读取 `session.pendingCommand`；`pending?.background` 的拒绝检查也可挪到审批通过后再做一次（避免白弹审批框，属体验问题非功能问题）。

### P2-1 双 `await_async` 并发：一方拿锁读到空段并污染边界（backend-ts）

**文件**：`shell-session-tool.ts` `handleAwaitAsync` / `shell-session-manager.ts` `readUntilMarker`。

**机理**：锁串行化了读取，但**两个调用者在拿锁前都取了同一个旧快照**。时序：A 拿锁→读到 marker→`finishCommand`（缓冲区裁掉前缀、`emittedUpTo=0`、pending 置空）→B 拿锁→按旧 marker 补登记假 pending（同 P1-1）→ 在当前缓冲区（从 0 开始）里找不到 marker→直到超时，把这一整段**新产生的输出原样交付**（`emittedUpTo` 前移到段尾）。实测两类症状：

- 两者拿锁间隔足够近（marker 已在缓冲区）：先到者正常拿到 `done`，后到者拿到**空输出** `completed:false` 并把会话卡死（同 P1-1）；
- 稍晚进入：后到者把该时段新输出整段交付（输出归属错乱），同样留下假 pending 卡死会话。

复现输出：

```
await#1: { completed: true, output: 'done\n' }
await#2: { completed: false, output: '' }
exec after race blocked: 会话仍有未结束的命令（假 pending 残留）
```

**建议方向**：与 P1-1 同根：拿锁后重新校验/刷新快照即可一并解决。

### P2-2 桌面端双 `await_async` 并发可能空交付（desktop / agent-cli，低风险）

**文件**：`localShell.cjs` `handleAwaitAsync`。

桌面版没有命令锁，两个并发 `await_async` 直接同时轮询同一缓冲区。实测绝大多数时序下后到者报「该会话没有未结束的命令」（可接受），但**两者都在 marker 到达前进循环**时，两者都会看到同一个 marker 并各自 `finishCommand`：一方拿到输出，另一方拿到**空输出 + `completed:true`**（伪造的 exit_code=0）。不会卡死会话，但模型可能把空结果误读为「命令成功且无输出」。复现确认后到者拿到 `completed:true, output:''` 的窗口存在（`finishCommand` 前无幂等保护，第二个调用者的 `markerIndex` 同样 ≥0）。

**建议方向**：`readUntilMarker` 拿到 marker 后、`finishCommand` 前校验 `session.pendingCommand.marker === marker`（不匹配视为「已被别人消费」，返回明确错误而非空成功）；或给桌面版补一个与后端等价的轻量命令互斥。

### P2-3 `writeCommand` 后先 `readUntilMarker` 再 `finishCommand`，中间状态下 `exec` 误判「上一条未结束」（backend-ts，自愈型）

**文件**：`shell-session-tool.ts` `handleExec`。

**机理**：异步路径 `writeCommand`（置 pending）→ 后台任务开始 `readUntilMarker`。此后到命令真正结束前，`pendingCommand` 一直非空——这是**设计内**状态（防并发写）。但同步路径里还有一个细窗口：`readUntilMarker` 已在 marker 处 break、`finishCommand` 尚未执行（两者间有 `preview`、`EXIT_STATUS_PATTERN` 等同步代码，不含 await，实际窗口极小），此时并行 `exec` 会被拒。因为窗口内无 await，实测难以触发，列为知悉项即可；真正需要警惕的是它叠加 P1-1 时的修复顺序——修 P1-1 时应保证「拿锁后发现命令已结束」走快速路径而非补登记。

### P3-1 `resolveCurrentWorkdir` 与「输入直喂」组合可能吞输出（desktop / agent-cli，低风险）

**文件**：`localShell.cjs` `resolveCurrentWorkdir`（backend-ts 同名逻辑等价）。

**机理**：`write_stdin` 走 `pending` 分支（输入直喂运行中命令）返回 `completed:false` 时，外层随即调用 `resolveCurrentWorkdir`——但命令仍在运行，pwd 会排在命令之后，其输出被运行中的命令（或后续探测读取）消费，`pwd` 探测 5s 内拿不到 marker，最终 `return session.currentWorkdir` 兜底。功能上无害（workdir 未变时本就正确），但 pwd 行会混入输出文件/缓冲区，等命令结束后作为下一条命令的输出首行出现，可能污染 `current_workdir` 判定（`resolveCurrentWorkdir` 取「最后一个以 `/` 开头的行」，通常仍能纠正）。实测本次未观察到显性错误，列为知悉项。

**建议方向**：`completed:false` 时跳过 `resolveCurrentWorkdir`（backend-ts 的 `resolveCurrentWorkdir` 已在函数开头对 `!result.completed` 短路返回 `session.currentWorkdir`；desktop 版**没有**这个短路，是两份实现的实质差异，建议对齐）。

### P3-2 `flushPersist` 未 `finishCommand` 时可能把 marker 尾部之后的新输出提前落盘（极低风险，知悉项）

**文件**：`shell-session-manager.ts` / `localShell.cjs` 的 `flushPersist`。

**机理**：marker 已完整出现在缓冲区但读取者尚未 `finishCommand` 的间隙里，若后续命令的输出先到达（`onData` → `flushPersist(false)`），`buffer.indexOf(marker)` 命中后 `visibleEnd = idx`，`persistedUpTo` 会推进到 marker 之前——后续写入的正文不受影响；但如果 marker 尾部之后紧跟下一个命令的输出且旧 marker 尚未消费，此时落盘的边界仍是正确的（idx 之前）。此场景经推演无法构造出错误落盘，仅在「marker 后跟退出码回显」时，退出码行会短暂留在缓冲区等待消费，落盘内容不受影响。列为知悉项，无需处理。

## 结论

- **P1-1 / P1-2 建议在合入前修复**：两者都会在真实使用中造成会话不可用或交互应答错配，且修复面小（拿锁后刷新快照 / 审批后重读 pending）。
- P2 三项为并发窗口下的输出归属/空成功问题，影响面较窄，可与 P1 一并处理（P2-1 随 P1-1 自然解决）。
- P3 为低风险语义偏差与知悉项，不阻塞合入。
- 文档/CHANGELOG 与实现一致（`mao-cli` 两处文档同步更新，未发现文档性错误）；desktop 与 agent-cli 两份 `localShell.cjs` 当前逐字节一致，未发现分叉。
