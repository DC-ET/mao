# 第 7 轮代码审查报告

- 审查范围：当前 Git 工作区未提交代码
- 重点：PROCESSING 状态收敛、待绑定消息 CLAIMED 重试、成功回调、卡片复用、文本回退及数据库状态完整性
- 结论：发现重大功能 bug，需求仍未全部满足。

## 高严重程度

### 1. 待绑定消息执行失败后虽然回退为 SENT，但没有可达的重试入口；后续回调会被 SUCCESS 状态拒绝

- **位置**：`backend-ts/src/create-app.ts:310-324`、`backend-ts/src/feishu/pending-binding.repository.ts:36-58`、`backend-ts/src/auth/feishu-auth.service.ts:88-145`
- **问题**：绑定成功回调中，`completeStateWithCode()` 先将 OAuth state 从 `PROCESSING` 更新为 `SUCCESS`，随后 `onUserAuthenticated` 才 claim 待绑定消息并执行原始消息。若该执行在任意步骤失败，代码将待绑定消息从 `CLAIMED` 回退为 `SENT`，但同时把异常继续抛出。之后使用同一个授权回调 URL 重试时，`completeStateWithCode()` 只接受 `PENDING`，会直接因 state 为 `SUCCESS` 返回“二维码状态无效”，因此不会再次进入 `claim()`；轮询也只消费登录成功状态，不会触发待绑定消息恢复。`release()` 的状态回退在数据库层存在，但业务流程没有真正的重试路径。
- **影响**：模型、数据库或飞书 API 的暂时性故障会导致原始群消息永久停留在 `SENT`，用户重新打开同一绑定链接无法恢复执行，违反“CLAIMED 执行失败可重试”，造成消息丢失。
- **修复建议**：为 pending binding 增加明确的恢复入口和幂等语义：例如在绑定成功后先完成/记录绑定，再由独立重试任务或显式的绑定成功处理接口按 `SENT`（或带 lease 的 `CLAIMED`）领取执行；重试必须不重复 OAuth 成功处理，并以待绑定消息状态作为幂等键。若仍允许重复打开回调，则 `SUCCESS` state 应能安全触发 pending message retry，但不能重复发放登录凭据或重复绑定。

## 已核验

- `PROCESSING` 过期轮询会使用 `PROCESSING -> EXPIRED` 的条件更新；失败路径也会尝试将 `PROCESSING -> FAILED`，本轮未再发现上一轮报告中的“过期更新被有效期条件阻止”问题。
- 未授权群消息在卡片发送异常、缺少 `message_id` 或卡片 ID 持久化失败时会进入文本回退；卡片成功发送后会持久化 `card_message_id`，绑定后的原始消息通过 `progressCardMessageId` 复用原卡片。
- 入站处理器在成功完成时标记 inbound message 完成，Agent/前置步骤失败时释放为可再次 claim；待绑定消息本身的 `CLAIMED -> SENT` 回退只覆盖异常场景，但缺少上述可达重试入口。
