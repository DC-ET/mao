# 第 3 轮代码审查

审查范围：当前 git 工作区未提交代码；重点检查未绑定卡片回退、OAuth state 状态机、原事件恢复/卡片复用、迁移及 Db camelCase 映射。

## 重大问题

### [P1] 卡片消息 ID 写入失败会遗留 PENDING，且文本回退不完整

- 位置：`backend-ts/src/create-app.ts:1027-1052`；`backend-ts/src/feishu/pending-binding.repository.ts:18-26`。
- 现象：`sendUnauthorizedCard` 先插入 `PENDING` 记录，再发送卡片，最后调用 `setCardMessageId`。当卡片已成功发送但 `setCardMessageId` 因数据库异常失败时，异常会被 `FeishuInboundProcessor` 捕获并触发文本回退，但 `setCardMessageId` 没有内部兜底将记录改为 `FAILED`，因此该 state 永久保持 `PENDING`。后续 OAuth 回调仍可能 claim 该记录，造成重复处理；同时数据库异常场景也不满足“不会留 PENDING”。
- 修复建议：将 pending 记录的生命周期设计为可回收的原子状态机；`setCardMessageId` 失败时必须尝试把该 state 从 `PENDING` 原子更新为 `FAILED`，并对清理失败记录告警。更稳妥的是先发送卡片、拿到 message_id 后再插入记录，或用明确的 `CREATING/SENT/FAILED` 状态及超时清理，避免任何异常路径留下不可处理的 PENDING。文本回退发送失败也应记录可观测错误，并确保 inbound claim 不再被重试成重复消息。

### [P1] OAuth 回调失败时状态更新异常可使 state 永久停留 PROCESSING

- 位置：`backend-ts/src/auth/feishu-auth.service.ts:107-136`。
- 现象：回调先通过 `claimPending` 将状态从 `PENDING` 改为 `PROCESSING`。之后授权码换 token、查询用户、绑定目标用户或成功状态更新任一环节抛错时，catch 中先执行 `updateByState(... PROCESSING -> FAILED)`，随后又执行 `markStateFailed(... expected PENDING)`。只要第一次状态更新因数据库/连接异常抛错，第二次不会执行，PROCESSING 记录没有过期恢复或失败兜底；`getLoginStatus` 对 PROCESSING 也不会过期处理，轮询可能永久卡住。
- 修复建议：用 `try/finally` 或独立的安全状态收敛函数，保证 PROCESSING 无论失败原因都尝试原子转为 FAILED；增加 PROCESSING 的超时恢复/查询过期策略（带时间条件），并避免以 PENDING 作为第二次更新条件。状态收敛失败应记录 state 和错误，供定时任务补偿。

## 其他确认结果

- 未绑定群消息的正常卡片发送失败路径会调用 `fail` 后再文本回退；但上述 `setCardMessageId` 异常路径存在重大缺口，因此不能确认“所有异常都能文本回退且不会留 PENDING”完全成立。
- `claimPending` 使用 `UPDATE ... WHERE status='PENDING'`，并发重复回调的 claim 本身具备单次抢占效果；SUCCESS 消费也使用 `consumed_at IS NULL` 条件，重复消费受保护。
- 回调成功后通过 `onUserAuthenticated(user, targetUserId, state)` claim 原事件，并将 `progressCardMessageId` 传回处理器，卡片复用链路逻辑存在。
- V085 的 snake_case 字段与 `Db.insert`/`Db.query` 的 camelCase 转换总体匹配（`appId/eventJson/cardMessageId` 对应 `app_id/event_json/card_message_id`）。
