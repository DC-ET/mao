## 一、高严重度

### H1. 【L1 修复未生效】failAllForSession 写入的 `cancelled:true` 标记没有任何代码路径解析，waitForAnswer 成功分支无条件返回 `cancelled:false`

- **位置**：
  - 生产者：`backend-ts/src/harness/tool/ask-user-questions-registry.ts:99`（`failAllForSession` → `resolve(JSON.stringify({ error: 'Session cancelled', cancelled: true }))`）
  - 消费者：同文件 `waitForAnswer()` 第 50 行 —— `return { answered: true, cancelled: false, resultJson };`
- **现象**：`waitForAnswer` 的成功分支拿到 resolve 的字符串后**直接原样返回，没有做任何解析**。`failAllForSession` 精心塞进 JSON 的 `cancelled:true` 只是一段普通文本，躺在 `resultJson` 里传给 LLM，结构化的 `result.cancelled` 永远是 `false`。
- **后果**：dispatcher 中 `if (!result.answered || result.cancelled)`（tool-dispatcher.ts:157）的第二半条件永假，等价于 `if (!result.answered)`。会话停止/中止场景（`releaseSessionExecutionResources` / `abortRunningExecution` / 重试清理均走 `failAllForSession`）依然**不会广播 `ask_user_questions_cancelled`**——第 1 轮 L1 指出的问题原样存在，修复目标未达成。前端 SideChatPanel.vue:653、SubagentChatPanel.vue:183 注释所依赖的「服务端取消确认信号」依旧缺失。
- **测试为何没拦住**：现有单测只 mock 了 registry 返回 `{ answered: false, ... }` 验证 dispatcher 分支（tool-dispatcher.spec.ts），registry 自身无 spec，`failAll → waitForAnswer → cancelled=true` 这条集成链路零覆盖，因此全绿但无效。
- **建议修复方向**：在 `waitForAnswer` 成功分支解析标记，例如：

  ```ts
  const parsed = parseObject(resultJson);
  return { answered: true, cancelled: parsed?.cancelled === true, resultJson };
  ```
  
  并补充一条真实链路的 registry 单测（register → failAllForSession → waitForAnswer 断言 `cancelled === true` 且 `resultJson` 含 error 说明）。

### H2. 新增测试断言写错对象：对已截断文本做 `JSON.parse`

- **位置**：`backend-ts/src/harness/tool/tool-dispatcher.spec.ts:206-209`
- **现象**：LOCAL shell 异步结果断言改为：

  ```ts
  expect(JSON.parse(consumed[result.task_id])).toEqual({
    exit_code: 0, completed: true, output: 'done',
  });
  ```

  但该任务结果是经 `normalizeResult(..., null, 2)` 缩进序列化后的文本，`toEqual` 对对象比较本可容忍键序，然而一旦该用例未来换成超长 output（触发预算内截断重组，仍合法 JSON）或纯文本路径，断言就会因格式差异脆裂。更实质的问题是：**这个 mock 的返回值 `{exit_code:0,output:'done',completed:true}` 本身就是合法 JSON，`JSON.parse` 能过纯属巧合**——它验证不了归一化逻辑真正想保证的「缩进序列化 + 结构字段补全」。对比 token-estimator.spec.ts:222-229 用 `toMatchObject` + 长度上限断言的做法，此处断言强度不足且形式误导。
- **影响**：当前不失败（测试通过），属测试质量问题而非功能 bug，但作为本次修复配套的新增测试，建议同步修正。

## 二、中严重度

### M1. 【L2 修复残留边界】error 字段过长时仍会触发整体二次截断，产出非法 JSON

- **位置**：`backend-ts/src/harness/core/background-task-manager.ts:96-120`
- **现象**：output 截断预算为固定值 `MAX_RESULT_LENGTH - 200 = 9800`。但 payload 还可能包含 `payload.error`（来自 LOCAL await_async 错误负载，如 `'会话不存在或已关闭：sh-xxx'`）。实测模拟：当 `output` 接近 9800 预算且 `error` 字段较长时，重组后总长可达约 9974+，逼近甚至超过 10000 时仍会落入整体截断分支，把 JSON 尾部切掉并追加第二个 `[truncated]`——双重标记 + 非法 JSON 的问题在「长 output + 长 error」组合下复现。
- **影响**：概率低（需要 output 与 error 双双接近上限），且注入给模型阅读时信息量仍足够，不构成主流程功能错误；但与修复说明「消除双重 [truncated] 标记与非法 JSON」的目标不完全一致。
- **建议**：预算计算纳入 error 字段长度，例如 `budget = MAX_RESULT_LENGTH - 200 - (parsed.error ? String(parsed.error).length + 20 : 0)`（下限保护），或将 error 一并纳入限长。
