# 代码审查报告

审查范围：当前 worktree 未提交代码，重点为 `sdk/embed/src/page-scanner.ts`、`sdk/embed/src/page.ts` 及其测试。

## 严重

### [高] 页面动作执行无法使用 `inspectPage` 返回的 elementId

- **位置**：`sdk/embed/src/index.ts:63-64`
- **问题**：`inspectPage` 和 `executePageAction` 每次调用都会 `new PageSnapshotManager(...)`。`PageSnapshotManager` 中的 `refs` 仅保存在实例内，执行动作时新实例的 `refs` 为空，因此任何带 `elementId` 的 `click`、`fill`、`focus`、`check`、`select` 等动作都会返回 `element_not_available`。这使页面扫描与页面操作无法形成闭环。
- **修复建议**：在 `createMaoChat`/实例生命周期内创建并复用同一个 `PageSnapshotManager`，让 `inspect()` 写入的引用可被后续 `execute()` 使用；页面导航或快照失效时重新 inspect，并明确处理旧 elementId。

## 中

### [中] `select` 动作可能报告成功但没有实际选择目标选项

- **位置**：`sdk/embed/src/page.ts:78`（`action.type === 'select'` 分支）
- **问题**：代码直接设置 `select.value` 并派发 `change`，但没有检查目标 value 是否存在。对不存在的 value，浏览器通常会将 value 置为空，代码仍返回 `success: true`，上层会误以为选择成功。
- **修复建议**：执行前检查 `select.options` 中是否存在对应 value，或者设置后校验 `select.value === action.value`；不存在时返回明确错误并避免派发成功语义的事件。

### [中] `fill` 对 contenteditable 元素可能只修改 DOM 文本，未可靠触发宿主框架状态更新

- **位置**：`sdk/embed/src/page.ts:79`（`fill`/`keyboard` 共用分支）
- **问题**：对 contenteditable 元素，代码先尝试调用其 prototype 的 `value` setter（通常不存在），再设置 `textContent`，随后统一派发 `InputEvent`。这不模拟真实编辑行为，React/Vue 等应用可能依赖 `beforeinput`、Selection 或 DOM mutation 细节，导致页面显示已更新但业务状态未更新；同时该分支对非输入元素也会派发不匹配的 input/change 事件。
- **修复建议**：按目标类型分支处理：表单控件使用对应原生 value setter 并派发必要事件；contenteditable 使用可被浏览器/框架识别的编辑流程（或至少校验目标确实可编辑、派发 `beforeinput`/`input`，并明确不承诺完整键盘语义），对不支持的目标返回错误。

## 低

### [低] `page-scanner.ts` 的快照类型与 SDK 当前 Page 类型不一致，且存在两套实现

- **位置**：`sdk/embed/src/page-scanner.ts:1-18`、`sdk/embed/src/page.ts:1-101`
- **问题**：两套 `PageSnapshot`/元素类型字段不同（例如 `page-scanner.ts` 缺少 `viewport`，`kind` 将 link 归为 button，option value 允许 `null`，而 `page.ts` 使用统一的 Page 类型）。当前测试只覆盖未被实际入口使用的 `collectPageSnapshot`，无法验证 SDK 对外暴露的 `inspectPage`/`executePageAction` 行为，容易造成需求实现与实际 SDK 行为偏离。
- **修复建议**：保留单一实现和单一类型来源；将测试直接覆盖 `PageSnapshotManager` 及公开 API，包括快照后动作执行、宿主排除、导航/节点变化、select 无效值和 contenteditable 等边界。
