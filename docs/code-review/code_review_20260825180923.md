# 代码审查报告

- 审查范围：当前 Git 工作区未提交代码（不含页面样式及文档内容）
- 审查重点：上一轮报告问题的修复情况，以及会话、绑定授权、@判断、并发、配置、OAuth、长连接和 SDK 回复发送
- 结论：仍发现功能性问题，建议修复后再验收。

## 严重问题

### [严重] 私聊会话的 workspace key 未包含用户身份，多个用户会共享同一个云工作区

- 位置：`backend-ts/src/create-app.ts:683-686`
- 问题：私聊创建会话时使用 `feishu-${accountId}-private`，该 key 只包含机器人账号，不包含 `senderUnionId`/用户 ID。虽然 `feishu_chat` 的映射按用户保存，但 `SessionService` 的云 workspace 会按该 project key 复用，因此同一个机器人下不同用户的私聊会话可能落到同一 workspace，造成工作目录和文件操作相互可见/互相影响。
- 修复建议：私聊 key 必须包含稳定且经过合法化的用户维度，例如 `feishu-${accountId}-private-${userId}`；同时保留按用户的会话映射，并对 key 长度和字符做统一校验。

### [严重] 群成员授权仍然是“首次收到消息即自动加入”，未实现白名单授权

- 位置：`backend-ts/src/create-app.ts:728-735`
- 问题：群消息通过 `feishu_binding` 查询到用户后，如果 `isGroupMember` 返回 false，代码立即 `addGroupMember`，随后返回 true 放行执行 Agent。这样任意已绑定用户只要在群里发一次消息，就能自动获得该群的成员授权；`feishu_chat_member` 实际没有形成授权门槛，与“群成员授权”要求不符。
- 修复建议：只有明确的管理操作/初始化同步流程才能写入 `feishu_chat_member`；入站消息只查询成员关系，未授权应拒绝执行并发送引导，不应自动插入后放行。

## 高严重问题

### [高] 群聊精确 @机器人仍未修复，默认逻辑会把 @任意用户视为触发

- 位置：`backend-ts/src/feishu/inbound-processor.ts:54-57`、`backend-ts/src/create-app.ts:761`
- 问题：生产创建 `FeishuInboundProcessor` 时没有传入 `isBotMentioned`。默认实现仍使用 `event.mentions.length > 0` 或 `@` 文本正则，无法比较当前 bot 的 open_id。因此 @普通成员也会触发 Agent；同时无 mention 信息但文本中存在普通 @用户名时也可能误触发。
- 修复建议：为每个机器人解析并缓存自身 open_id，在标准化事件中保留 mention 的可比 ID，并且仅当 mention 精确匹配当前机器人时放行；无法确认身份时按未触发处理。

### [高] 同一飞书会话的消息执行没有并发互斥，连续消息会并行写入和执行同一 Agent session

- 位置：`backend-ts/src/feishu/message.service.ts:17-25`、`backend-ts/src/feishu/agent-inbound-handler.ts:19-42`
- 问题：新增的锁只保护 `feishu_chat` 会话首次创建，`onMessage` 在保存用户消息和调用 `harnessService.execute` 时没有按 session 加锁/排队。长连接并发投递两条消息时，两次 Agent 执行会同时读取和写入同一会话上下文，回复查询还可能拿到另一条执行的 assistant 消息，导致消息串线、上下文破坏或回复错配。
- 修复建议：按 `(bot, user)`/`(bot, chat)` 建立持久化或进程内执行队列，确保同一会话串行；跨实例部署时使用数据库 claim/队列实现，并明确失败、超时后的释放策略。

### [高] SDK 长连接启动或断线失败后仍会永久停留在 active，不会按配置恢复

- 位置：`backend-ts/src/feishu/monitor.service.ts:34-47, 89-96`
- 问题：`WSClient.start()` 的失败只被 catch 后打印，handle 已提前放入 `active`；handle 没有失败/断线状态回调，monitor 的 reconcile 会认为该 bot 已运行，不会移除并重建。`reconnectBaseMs`、`reconnectMaxMs`、`maxConsecutiveFailures` 也未参与恢复逻辑。
- 修复建议：监听 SDK 的启动失败、close/error/reconnect 状态，失败时从 active 移除或由 handle 自行执行带退避的重连；停止/配置变更时等待旧连接关闭，并避免旧连接继续处理事件。

## 中等问题

### [中] 回复长度配置仍未生效，实际固定截断为 2000 字符

- 位置：`backend-ts/src/create-app.ts:744`
- 问题：配置已提供 `cfg.feishu.bot.reply.maxLength`，但发送 SDK 逻辑仍硬编码 `2000`。修改配置不会改变实际回复长度，超出配置值时可能发送过长消息，低于配置值时又会被错误截断。
- 修复建议：使用经过边界校验的 `cfg.feishu.bot.reply.maxLength`，并统一所有回复发送路径的截断逻辑。

### [中] 绑定迁移/换绑时可能留下旧用户的 legacy 绑定，导致解绑后的旧用户仍被授权

- 位置：`backend-ts/src/feishu/binding.repository.ts:31-41`
- 问题：`bind` 对 `union_id` 冲突使用 `ON DUPLICATE KEY UPDATE user_id = VALUES(user_id)` 将绑定转给新用户，但没有清理原用户 `user.feishu_user_id`。入站查询 `findUserIdByUnionId` 在绑定表查不到（或已删除）时还会回退查询 `user.feishu_user_id`，因此旧用户仍可能被识别为已绑定；换绑与解绑后的授权状态不一致。
- 修复建议：在同一事务中清理被替换用户的 legacy 字段及旧绑定状态，或彻底移除 legacy 回退并让 `feishu_binding` 成为唯一授权来源；为换绑、解绑后入站增加集成测试。

### [中] 备用 FeishuSendService 未将 receive_id_type 发送给飞书 API

- 位置：`backend-ts/src/feishu/send.service.ts:26-29`
- 问题：`sendText`/`send` 接收了 `receiveIdType`，但请求体只包含 `receive_id`、`msg_type`、`content`，没有将 `receive_id_type` 放入 API 要求的 query 参数。使用该服务发送私聊或群聊消息时，飞书可能无法按指定类型解析接收者，造成发送失败。当前 create-app 使用另一套 SDK 发送逻辑，不能掩盖该新增服务本身的功能缺陷。
- 修复建议：按飞书 API 规范将 `receive_id_type` 放入请求 query（或 SDK 对应参数），并补充 p2p/chat 两种发送断言测试。
