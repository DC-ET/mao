## 一、前两轮问题的修复核查结果

### 修复 1：后台 reload —— ✅ 已真正修复

**位置**：`onStop()`（L93-97）

```java
onStop() { super.onStop(); probing = false; handler.removeCallbacksAndMessages(null); }
```

- `handler` 是专用于探测的私有 Handler（仅 schedule/probe 的 postDelayed 与 onStop/onDestroy 的 remove 引用它，无其他用途），`removeCallbacksAndMessages(null)` 会同时取消**排队中的延迟探测任务（2s）与超时任务（3s）**，无副作用；
- 主线程上 `onStart` 的 postDelayed 与 `onStop` 的 remove 严格串行，无 ABA 竞态；
- **onStart→onStop→onStart 正常往返验证**：onStop 取消残留任务 + 重置 probing → 下次 onStart 重新排定全新探测，任务队列任一时刻最多 1 个，后台期间无任何残留回调可触发 reload。✅
- 上轮指出的「注释与实际不符」也已消除（回调不再依赖 probing 标志作后台防护）。✅

### 修复 2：双重探测竞态 —— ✅ 已修复

**位置**：`probeWebViewAlive()` 入口（L119）`if (probing || ...) return;`

- 结合修复 1，onStop 已取消排队任务，队列中不可能同时存在两个延迟探测；入口 probing 检查是兜底保险，逻辑自洽；
- evaluateJavascript 回调与超时回调均投递到主线程（同一 Looper），无跨线程可见性问题。✅

## 二、新发现的问题

### 【中】1. everResponded 使「冷启动后的首次后台冻结」不可恢复 —— 恰是兜底设计的主场景

**位置**：`probeWebViewAlive()` 回调（L122-124 `everResponded = true`）与超时回调（L128 `if (everResponded && ...)`）

**问题**：
`everResponded` **只在探测成功回调时置 true**，而探测只在 `onStart`（回前台）触发。完整时序：

1. 冷启动 → `onCreate` 置 `firstStartAt` → `onStart` 调度探测 → **被 10s 冷启动防护拦截，首次前台期间从不探测** → `everResponded = false`；
2. 用户正常使用几分钟（期间无任何探测，everResponded 始终 false）；
3. 用户切后台 → 系统冻结 WebView（**这正是本功能要兜底的主场景**）；
4. 回前台 → `onStart` 调度 → +2s 探测 → evaluateJavascript **无回调**（已冻结）→ +3s 超时 → `everResponded=false` → **不 reload** → 用户面对卡死页面，只能手动杀进程重开。

即：**首次后台冻结（最典型场景）完全无法被原生兜底恢复**；只有用户先经历一次「后台→回前台且页面恰好存活」（探测成功 → everResponded=true）之后，后续冻结才能被恢复。而 JS 侧 `useForegroundRecovery` 此时也失效（JS 已死），两层兜底同时失效。

**评估**（回应用户问题「冷启动即卡死导致永远不 reload 是否可接受」）：
- 「冷启动加载中即卡死 → 永远不 reload」这个角落场景本身**可接受**（概率低，加载中与卡死本就难区分，10s 防护已覆盖常见情况）；
- 但「**已加载完成 → 首次后台冻结**」不可恢复**不可接受**——这是该功能设计文档明确的目标场景（「后台冻结 / 渲染进程异常 / 主线程卡死时，由原生兜底恢复」），当前实现恰好在这类场景的第一次发生时失效。

**建议（非侵入式替代方案）**：
用 `webView.getProgress() == 100` 替代 `everResponded` 作为「页面已加载完成」判据：

```java
// 超时回调内
if (webView.getProgress() == 100 && !responded[0] && !isFinishing() && !isDestroyed() && webView != null) {
    reloadWebView(webView);
}
```

- 首次加载中（无论 10s 内还是弱网 >10s）：progress < 100 → 不 reload ✅（保留弱网防护）；
- **已加载完成 → 后台冻结**：progress 保持 100（页面已提交）→ 探测超时 → reload ✅（首次后台冻结可恢复）；
- 无需替换 Capacitor 的 WebViewClient（规避了「替换会打断 bridge」的约束），非侵入。

### 【低】2. reload 后慢加载可能连环 reload（everResponded 不复位，仅靠 10s 防抖限频）

**位置**：`reloadWebView()`（L136-146）与超时回调

**问题**：
`everResponded` 在 reload 后**不会复位**。时序：首次 reload 后（弱网）页面重新加载需 >10s → 期间用户切后台再回 → 探测超时 → `everResponded` 仍为 true（此前置位）→ 再次 reload → 反复。虽然每次触发都要求一次前后台往返、且 10s 防抖限频，弱网下仍可能形成「每次回前台都重载一次」的体验劣化。

改用 `getProgress() == 100` 后此问题自动消除：reload 会重置 progress 为 0，重载期间 progress < 100 → 不触发二次 reload。✅
