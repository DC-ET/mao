## P2

### P2-1. 断线时等待中的确认卡片未收口、本地在途动作未中止 → 用户批准后本地仍执行，模型重试可能造成重复副作用

**位置**
- `sdk/embed/src/controller.ts:273-277`（`onDisconnected` 只清 LLM 重试与落库计时，不动页面引擎）
- `sdk/embed/src/page/authorization.ts:149-176`（`setLevel` 保留卡片；断线没有走任何 settle）
- `backend-ts/src/session/ws/streaming-ws-handler.ts:143-148`（断线即以 `embed_client_not_connected` 结束在途页面工具）
- `sdk/embed/src/ui/PageActionPanel.vue:51-53`（确认按钮不随连接态禁用）

**问题**

第 7 轮 P3-1 已记录，本轮未处理。断线时后端 `afterConnectionClosed` 立即对绑定会话 `failSession(..., 'embed_client_not_connected')`，把在途页面工具以「可重试」语义结束；但同一标签页内的 `PageEngine` 仍在 `await requestConfirmation`，且 `onDisconnected` 没有取消它。此时确认卡片仍在界面上且按钮可点。

复现：

1. `per_action` 下模型调用 `page_click`（例如「提交」）→ 弹出确认卡片，后端请求在途；
2. 恰好发生断线（网络抖动 / 空闲超时 / 服务重启）→ 后端已把该请求以 `embed_client_not_connected` 结束，模型侧收到「连接断开」；
3. 用户仍点「允许本次」→ `PageEngine` 本地照常执行点击 → 回包因后端 entry 已被 `failSession` 删除而被 `EmbedPageToolRegistry.complete()` 丢弃；
4. 模型大概率重试同一动作（新 `requestId`）→ 用户再确认一次 → **同一副作用执行两遍**（提交/删除类动作尤其危险），且第 3 步的这次执行在会话记录里没有成功结果，状态与页面实际不一致。

与本轮两处修复不同，这里的「卡片留存」没有任何授权层收口兜底（断线不触发 `emitState`/`onConfirmRequest(null)`），属于「结束/中断时未收口」。

**修复建议（二选一，建议 A）**
- A：`onDisconnected` 中以拒绝结束等待中的确认并让在途动作失败（例如调用页面引擎的取消确认入口，或 `authorization.destroy()` 后再按需复位），使 `authorizer` 返回 `authorization_denied`，本地不产生副作用；重连后由 `prepareNewTask()`/新一轮请求恢复，不影响后续任务；
- B：后端 `failSession` 的 payload 带 `retryable:false` + 文案「该操作可能已在页面执行，请先用 page_inspect 确认状态」，同时确认卡片在断线态禁用按钮，避免用户批准一个后端已放弃的动作。

## P3 / 备注（不阻塞）

### P3-1. `setLevel` 在 `sessionId` 校验之前放行等待中的确认（第 7 轮次要项遗留）

**位置**：`sdk/embed/src/page/authorization.ts:153-161`

`setLevel('task', null, true)` 会先 `approvePendingConfirmations()` 放行等待中的动作，再因 `sessionId == null` 退回 `per_action`。若用户点「本次任务授权」时 `store.sessionId()` 为 null（身份切换窗口/旧连接残留帧），会出现「动作被放行、级别却显示每次确认」。当前路径较难触达（确认存在期间会话通常非空，且身份切换会 `pageEngine.cancel()`），故仅备注。建议把 `approvePendingConfirmations()` 移到 `sessionId` 校验通过之后，或对 `full` 之外也先校验会话。

### P3-2. 页面工具可见性在任务开始时一次性快照（第 7 轮 P3-3 遗留）

**位置**：`backend-ts/src/harness/core/harness-service.ts:326`、`backend-ts/src/session/ws/streaming-ws-handler.ts:226-241`、`agent-loop.ts:568-571`（`isToolAllowed` 以 `context.tools` 为准）

`filterPageTools(..., isEmbedSession(sessionId))` 只在 `loadContext` 求值一次，而绑定发生在 `handleSubscribe`。若 `subscribe` 落后于 `send_message`（断线重连后立即发送），该轮任务不会暴露 `page_*`，`isToolAllowed` 会以「不在当前允许的工具集内」拒绝，Agent 只能纯文本作答（下一轮自愈）。概率低，列此备查。建议在 `handleSendMessage` 入口对 embed 连接补一次绑定，或每次 LLM 调用重新评估。

### P3-3. 宿主 `setPageAuthorization('task')` 保留确认卡片，与 task 级别语义略不一致（本轮 P3-2 修复的边界行为）

**位置**：`sdk/embed/src/page/engine.ts:129-134`、`sdk/embed/src/page/authorization.ts:149-176`

宿主设置 task 时不再放行等待中的确认（符合本轮修复目标），但 `level` 立即变为 `task`：`decide` 对后续动作不再要求确认，而这张 `per_action` 期间弹出的卡片仍停留等待用户点击；若用户点「拒绝」，动作会被拒（即使 task 级别本应允许），若点「允许本次」则正常执行。功能上不阻断，只是同一时刻「级别=task」与「仍在逐次确认」并存的展示/语义轻微不一致。建议卡片上标明「宿主已授权本次任务，是否执行该动作」或由宿主路径改为「保留卡片但标注级别已变更」。
