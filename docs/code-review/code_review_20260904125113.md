## 一、重大问题

### 1.1 「会话 ⇔ feishu_chat 指针行一一对应」的假设被多会话打破：非活跃会话的媒体发送 / 飞书工具 / 定时结果推送失败，且出站媒体映射丢失

`findConversationBySessionId`（`backend-ts/src/feishu/message.repository.ts:76-78`）的 SQL 是 `SELECT * FROM feishu_chat WHERE session_id = ? LIMIT 1`，而 `feishu_chat` 表唯一键为 `(app_id, chat_id)`（V084），`session_id` 是**可变的活跃指针**。多会话之后，同一私聊只有「当前活跃会话」能在该表查到行；旧会话（被 `---` 或引用切换切走的会话）**查不到任何行**。以下 4 条链路依赖该查询，在「旧会话执行中/排队中、指针已切走」的场景（即本需求明确允许的双会话并行场景）全部异常：

**（a）`feishu_send_image` / `feishu_send_file` 发送失败** —— 重大
- 位置：`backend-ts/src/create-app.ts:757-762`（`feishuMediaSendSupport.resolveSendTarget`）+ `backend-ts/src/harness/tool/impl/feishu-tools.ts:215-216、263-265`
- 描述：`resolveSendTarget(sessionId)` 对非指针会话返回 null，工具直接返回错误「当前会话不是飞书通道会话，无法发送飞书图片/文件」。旧会话 Agent 明明是飞书私聊会话，却在并行执行期间发不出媒体，且 Agent 只能把该错误转述给用户。
- 触发条件：旧会话执行期间用户 `---` 新建会话或引用切换，旧会话 Agent 随后调用发图/发文件工具。

**（b）定时任务结果卡片静默不推送** —— 重大
- 位置：`backend-ts/src/create-app.ts:1356-1358`（`setFeishuResultPusher`）
- 描述：`findConversationBySessionId(sessionId)` 返回 null 时直接 `return`——挂在旧会话上的定时任务触发后，**结果卡片一条都不发、无任何日志告警**，用户感知为「定时任务没跑」。本次提交特意为该链路新增了 OUT 映射记录（create-app.ts:1372-1374），说明意图是覆盖定时结果卡片，但前置的会话定位在旧会话场景就断了。
- 触发条件：定时任务绑定的会话不再是该私聊的活跃指针（用户用过 `---`/引用切换后）。

**（c）`feishu_read_doc` / `feishu_download_file` 工具失败** —— 一般
- 位置：`backend-ts/src/create-app.ts:727-732`（`feishuToolSupport.resolveBotAppId`）+ `backend-ts/src/harness/tool/impl/feishu-tools.ts:104-105、149-150`
- 描述：与（a）同根因，非指针会话无法解析 bot appId，工具返回「当前会话不是飞书通道会话」。

**（d）Agent 发送图片/文件的 OUT 映射记录依赖同一查询** —— 一般
- 位置：`backend-ts/src/create-app.ts:763-771、775-783`
- 描述：`sendImage`/`sendFile` 成功后为记录映射再次执行 `findConversationBySessionId(sessionId)` 以取 `conversation.appId`——但 `target.appId` 现成可用（上方两行刚用它取过 client）。该查询不仅多余，还带来 TOCTOU 窗口：发送成功与记录映射之间指针若被切走，映射被静默跳过，用户引用这条图片/文件消息无法切回原会话，违背「映射覆盖 Agent 发送的图片与文件」。
- 修复：直接 `recordP2pMessage(target.appId, messageId, sessionId, 'OUT')`，删除二次反查。

**统一修复方向**：会话到飞书通道的绑定不能依赖「活跃指针」这一可变状态。可选：
1. 新增/复用稳定的 session→chat 绑定（如在执行开始时把 `(appId, chatId)` 快照进执行上下文，媒体/工具按快照定位）；
2. 或利用 `feishu_p2p_message` 现有 `(app_id, session_id)` 索引反查 app_id、并补存 chat_id；
3. 或从 session 的 `projectKey`（`feishu-{accountId}-private-{uid}`）反推。

严重程度：重大（a、b）/ 一般（c、d）；建议合并前至少修复 (a)(b)。

## 二、一般问题

### 2.1 引用切换不校验目标会话的归属与存在性：换绑场景可切入他人会话（上下文越权），会话已删可切入无效会话

- 位置：`backend-ts/src/feishu/message.service.ts:55-62`（`switchP2pSession`）、`backend-ts/src/create-app.ts:1227-1234`（`switchSession` 装配）
- 问题描述：`findSessionByMessageId` 仅按 `(app_id, message_id)` 查映射，`switchP2pSession` 仅校验「指针行存在且目标 ≠ 当前」，**未校验目标 sessionId 对应会话的归属（owner）与存在性**：
  1. **换绑越权**：同一 union_id 从 mao 用户 A 换绑到 B 后，用户引用换绑前的历史消息（映射仍指向 A 名下的会话），指针会被切到 A 的会话，后续消息在 A 的会话上下文/历史中执行（仅执行账号是 B）。这与同文件「换绑不复用原会话」的既有隔离设计（`getOrCreateP2p`/`findActiveP2p` 均带 owner 过滤）直接矛盾，存在旧用户会话内容向换绑后账号泄漏的风险。
  2. **悬空映射**：会话被删除后映射行仍保留，引用其消息会把指针切到不存在的会话，后续执行报错且用户无法自行恢复（再发消息会因指针行 session 无效而失败，直到再次 `---`）。
- 触发条件：union_id 换绑后引用旧消息；或会话删除后引用其历史消息。
- 建议修复方向：`switchP2pSession` 内校验目标会话存在且 `session.userId === 当前 ownerUserId`（不匹配时静默保持现状并记日志，与「未命中静默」语义对齐）。
- 严重程度：一般

### 2.2 新会话命名状态存内存 + 默认标题魔法字符串三处硬编码：重启后命名失效、后续维护易踩坑

- 位置：`backend-ts/src/feishu/agent-inbound-handler.ts:88、249、273-289`（`pendingTitleSessionIds` / `renameNewP2pSessionIfNeeded`）、`backend-ts/src/create-app.ts:927、980、1241`
- 问题描述：
  1. `pendingTitleSessionIds` 是进程内 `Set`：`---` 新建会话后、首条消息到达前若发生重启（或多实例部署下单实例重启），该会话永远不会被命名为首条消息前 20 字，标题停留在「飞书Bot会话」。不影响路由正确性，但偏离「新会话以首条消息前 20 字命名」的需求点；另外用户连发多个 `---` 时，未收到消息的中间会话 id 会永久滞留集合（微量内存滞留）。
  2. 默认标题 `'飞书Bot会话'` 在 `create-app.ts:927`（建会话）、`:980`（`ensureFeishuSessionTitle` 守卫）、`:1241`（`renameSessionFromFirstMessage` 守卫）三处硬编码重复，任何一处文案改动都会让命名守卫失效或误覆盖。
- 触发条件：`---` 新建后重启才发首条消息；后续重构默认标题文案。
- 建议修复方向：将「待命名」状态持久化（如建会话时标题写 NULL/哨兵值，命名时按哨兵判断即可同时解决重启与魔法字符串问题）；至少把默认标题收敛为共享常量。
- 严重程度：一般

## 三、轻微问题

### 3.1 p2p 归属正确性依赖进程内锁，多实例部署下失效（存量架构约束，本次依赖被放大）

- 位置：`backend-ts/src/feishu/agent-inbound-handler.ts:578-591`（`withP2pChatLock`）、`backend-ts/src/feishu/message.service.ts:196-208`（`withChatLock`）
- 描述：两把互斥锁均为进程内 `Map<key, Promise>`。单实例无影响；多实例下同一用户并发消息可同时读到旧指针并各自切换/新建，产生归属错乱。存量 `withLock`（会话级）同样是进程内锁，属既有架构约束；本次的「指针切换 + 归属判定」正确性直接建立其上，影响面被放大。
- 建议：暂无需处理；在技术文档注明「p2p 多会话归属依赖单实例假设」，上多实例时改为 DB 事务（`SELECT ... FOR UPDATE`）。
- 严重程度：轻微

### 3.2 `recordInboundMapping` 死代码

- 位置：`backend-ts/src/feishu/agent-inbound-handler.ts:283-285`
- 描述：该 private 方法定义后无任何调用方（p2p 路径已内联调用 `control.recordMessageMapping`）。
- 建议：删除，或让 p2p 正常路径改用它以消除内联重复。
- 严重程度：轻微

### 3.3 两套几乎相同的进程内互斥实现并存，`previous` 链处理方式不一致

- 位置：`backend-ts/src/feishu/agent-inbound-handler.ts:556-570`（`withLock`）与 `:578-591`（`withP2pChatLock`）
- 描述：`withLock` 用 `this.mutex.set(sessionId, current)`，`withP2pChatLock` 用 `queued = previous.then(() => current)` 后 set——两种写法语义等价（release 均在 finally），但同一文件内两种风格并存，维护时容易只改一处引入 subtle bug（例如有人给 withLock 补 reject 传播时遗漏另一处）。
- 建议：提取通用 mutex 工具函数统一实现。
- 严重程度：轻微

### 3.4 V101 迁移注释滞后于实现；映射表无生命周期管理

- 位置：`backend-ts/db/migration/V101__feishu_p2p_multi_session.sql:3` 及建表语句
- 描述：注释写「出站消息（文本回复/进度卡片/排队卡片）归属记录」，实际还覆盖「定时任务结果卡片」「Agent 发送的图片/文件」，纯注释滞后（表结构无影响，无需新迁移）。另外 `feishu_p2p_message` 按 `(app_id, message_id)` 唯一键随消息数线性增长，无 TTL/清理机制，长期运行需要关注容量（引用切换通常只查近期消息）。
- 建议：顺带更新注释；可考虑按 created_at 定期归档清理（如保留 90 天）。
- 严重程度：轻微

### 3.5 spec 覆盖空隙：装配层（create-app）的负例未覆盖

- 位置：`backend-ts/src/feishu/agent-inbound-handler.spec.ts:479-719`
- 描述：handler 层单测断言与实现一致（指令变体、拦截不入会话、切换三态、群聊零改动、并行执行、命名一次性均已覆盖），无断言错误。但 `renameSessionFromFirstMessage` 的「标题已被用户/LLM 改过则跳过」守卫（create-app.ts:1241）只有正例、无负例用例；1.1 所述「非指针会话媒体发送」场景也无任何测试捕捉（这正是重大问题漏网的原因）。属测试覆盖建议，非错误。
- 严重程度：轻微
