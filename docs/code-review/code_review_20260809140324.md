## 高严重度

### H-1 treeUnread 聚合恒为 false（`Boolean.TRUE.equals(Integer)` 类型误用）

**位置**
- `SessionController.fillTreeSignals`：`backend/src/main/java/cn/etarch/mao/session/controller/SessionController.java` 第 699、705 行
- `SessionTreeSignalPublisher.publish`：`backend/src/main/java/cn/etarch/mao/harness/approval/SessionTreeSignalPublisher.java` 第 79、86 行

**问题**
`Session.unread` 字段类型是 `Integer`（0/1，见 `Session.java` 第 88 行），而两处聚合都写成：

```java
boolean unread = Boolean.TRUE.equals(main.getUnread());   // 恒 false
unread |= Boolean.TRUE.equals(st.getUnread());            // 恒 false
```

`Boolean.TRUE.equals(Integer)` 因类型不同恒返回 `false`，因此：

- 列表 VO 的 `treeUnread` 恒为 `false`；
- `session_tree_status` 事件的 `treeUnread` 恒为 `false`；
- 前端聚焦排序（`focusSort.ts` 的 `unread: !!s.unread || !!s.treeUnread`）中「边路任务未读 → 主任务提升到未读档（priority 3）」完全失效。

同文件其余位置（`toSessionVO` 第 629 行、`listSideTasks` 第 366 行）用的正确写法是 `Integer.valueOf(1).equals(session.getUnread())`，可对比确认。

**修复建议**
统一改为 `Integer.valueOf(1).equals(session.getUnread())`（两处聚合逻辑均改）。

## 中严重度

### M-1 用户回答 ask_user_questions 后未重发任务树信号，treePendingQuestionCount 残留

**位置**
- `StreamingWsHandler.handleAskUserQuestionsResult`：`backend/src/main/java/cn/etarch/mao/session/ws/StreamingWsHandler.java` 第 928~953 行（`askUserQuestionsRegistry.complete(...)` 成功后未发布）
- 对比：`ToolDispatcher` 第 228 行仅在 `register` 时调用 `treeSignalPublisher.publishIfSideTask(sessionId)`

**问题**
设计文档 5.7 明确「待回答新增 / 解除」都应触发 `session_tree_status`。当前只有新增（register）会发布，**解除（用户回答）不会**。对 SIDE_TASK：用户回答后父任务 `treePendingQuestionCount` 仍 ≥1，聚焦模式会一直把父任务顶在「待回答」（priority 0），直到列表刷新或该边路任务进入终态（TaskTerminalService 才补发）。

**修复建议**
在 `handleAskUserQuestionsResult` 中 `completed == true` 时调用 `treeSignalPublisher.publishIfSideTask(sessionId)`（可仿照 `handleToolResult` 的审批解除路径，见 M-2 关联的 `LocalToolExecutor` finally 中同样有发布）。

### M-2 服务重启后 WAITING_APPROVAL 会话永久卡死（无恢复/清扫路径）

**位置**
- `ApprovalRegistry`（内存态，注释自述「服务重启后内存清空，属可接受限制」）
- `CrashRecoveryRunner.run`：只查 `phase = 'RUNNING'`
- `SessionService.findStaleRunningSessions`：只查 `phase IN ('RUNNING','RESUMING')`

**问题**
本 PR 之前后端从不落库 `WAITING_APPROVAL`（HEAD 中无任何写路径），现在 `ApprovalRegistry.register` 会把该 phase 写入 DB。但：

- 审批 Registry 是内存态，重启后没有 `unregister` 会再触发；
- 崩溃恢复只处理 RUNNING；stale 清扫只处理 RUNNING/RESUMING。

结果：服务在「LOCAL 工具等待审批」时重启，该会话 phase 永久停在 `WAITING_APPROVAL`——聚焦模式永远显示「待审批」置顶、`session_status` 恢复快照（StreamingWsHandler 第 386 行对 WAITING_APPROVAL 重推）也会让前端一直认为有待审批，直到用户手动向该会话发新消息（`handleSendMessage` 会强制置 RUNNING）才解除。

**修复建议**
将 `WAITING_APPROVAL` 纳入重启恢复/清扫路径（如 `CrashRecoveryRunner` 把 stuck 的 WAITING_APPROVAL 一并恢复为 RESUMING/RUNNING，或 stale sweep 超时后置 FAILED），保证「内存注册表清空」后 DB 相位能自愈。

### M-3 register() 无条件覆盖终态，破坏「条件恢复不覆盖终态」的保证

**位置**
- `ApprovalRegistry.register`：`backend/src/main/java/cn/etarch/mao/harness/approval/ApprovalRegistry.java` 第 65 行 `sessionService.updatePhase(sessionId, "WAITING_APPROVAL")`

**问题**
`restoreRunningAfterApproval` 是条件更新（`eq(phase, WAITING_APPROVAL)`），但 **register 方向是无条件读改写**（`updatePhase` 先 `selectById` 再 `updateById`，无 phase 校验）。并发场景：AgentLoop 并行执行多个 LOCAL 工具，用户取消 → 取消线程写 `CANCELLED` 终态；若另一个工具恰好在其后执行 `register`，会把 `CANCELLED` 覆盖为 `WAITING_APPROVAL`；该工具随后因 `failAllForSession` 快速失败 → `finally` unregister → `restoreRunningAfterApproval`（此时 phase=WAITING_APPROVAL 满足条件）→ 置 `RUNNING`。**已取消的会话被「复活」为 RUNNING**，且取消线程的 `finishExecution(CANCELLED)` 可能已执行完毕（TaskTerminalService 读到非终态 RUNNING 不会再拦）。

**修复建议**
`register` 也改为条件更新：仅当 phase 属于活跃态（`RUNNING` / `RESUMING`，不含 CANCELLING/终态）时才置 `WAITING_APPROVAL`；或使用 `LambdaUpdateWrapper.eq(phase, active).set(phase, WAITING_APPROVAL)` 的原子 SQL，避免读改写竞态。

### M-4 主会话自身「待审批/待回答」无法实时达到聚焦优先级 0（事件契约缺口）

**位置**
- `ApprovalRegistry.publishPhase`（第 133~142 行）：`session_status` / `session_list_update` 只带 `phase`，不带 pending 计数
- `SessionTreeSignalPublisher.publishIfSideTask`：非 SIDE_TASK 直接 return，主会话自身审批变化不发布任何 tree 信号
- 前端 `focusSort.ts` `sessionToFocusCandidate`：priority 0 依赖 `treePendingApprovalCount ?? pendingApprovalCount`，且不并入 `sessionPendingApprovals` 实时计数（该计数只用于 TaskIndexPanel 徽标，未参与排序）

**问题**
聚焦模式排序对「待审批/待回答」的判定完全依赖 VO 中的 pending 计数，而该计数只在列表加载（`applySessionListSignals`）时填充。主会话在列表加载后进入 `WAITING_APPROVAL`（或发起 ask_user_questions）时：

- 前端只收到 phase=WAITING_APPROVAL 的 `session_status`，聚焦排序按 `RUNNING_PHASES` 只能得到 priority 2（运行中），而非设计的 priority 0（待审批/待回答）；
- 状态标签也显示「运行中」而非「待审批」。

边路任务场景因 `session_tree_status`（treePendingApprovalCount）已覆盖；主会话自身场景缺实时计数推送。

**修复建议（后端侧）**
在 `ApprovalRegistry.publishPhase`（以及 ask_user_questions 的 register 路径）的 `session_status` / `session_list_update` payload 中补充 `pendingApprovalCount` / `pendingQuestionCount`，并让前端在 `updateSessionPhase` 时同步写入 entity 的 pending 字段；或对主会话也发布 `session_tree_status`（把 publishIfSideTask 推广为「自身 + 父级」双发布）。

### L-2 LocalToolExecutor 中 approvalRegistered 标记顺序导致异常时注册表泄漏

**位置**
- `LocalToolExecutor.execute`：`backend/src/main/java/cn/etarch/mao/harness/local/LocalToolExecutor.java` 第 59~63 行

```java
if (needApproval && pending.requestId() != null) {
    approvalRegistry.register(sessionId, pending.requestId());  // 若此处抛异常
    approvalRegistered = true;                                   // 这行不会执行
    ...
}
```

**问题**
`register` 内部会调 `sessionService.updatePhase`（`getSession` 读库），若会话被并发删除（SESSION_NOT_FOUND）等抛异常，`approvalRegistered` 仍为 false，`finally` 不会 `unregister` → 该 requestId 永久留在注册表（计数 +1、phase 卡 WAITING_APPROVAL）。

**修复建议**
先置 `approvalRegistered = true` 再调用 `register`；或在 `register` 内部对异常做兜底移除。

### L-3 register/unregister 交错导致瞬态 phase 不一致（自愈，影响 UI 瞬时展示）

**位置**
- `ApprovalRegistry.register` / `unregister`（第 52~102 行）

**问题**
`unregister` 的计数归零判定在 `synchronized(ids)` 内，但 `restoreRunningAfterApproval` 与 `publishPhase` 在锁外执行。极端交错（最后一个请求 unregister 与并发新请求 register 同时发生）时，`restore` 可能把刚置 WAITING_APPROVAL 的会话改回 RUNNING，导致「仍有待审批但 phase=RUNNING」的瞬态；新审批结束时 `restore` 因 phase 已是 RUNNING 而 no-op，最终状态仍正确（自愈），但期间聚焦列表/状态标签显示「运行中」。

**修复建议**
把 restore 也纳入同步块（或 register 在置 WAITING_APPROVAL 后重查一次计数确认是否需要修正），保证「计数归零才恢复」与「计数非零必 WAITING_APPROVAL」两个不变量在同一临界区内成立。

### L-4 边路任务「进入运行」不发布 tree 信号，与设计文档 5.7 不符

**位置**
- `StreamingWsHandler.handleSendMessage`（第 539 行附近）、`edit_and_resend`（第 832 行附近）：对 SIDE_TASK 置 RUNNING 后只发 `session_status` / `session_list_update`，未调 `treeSignalPublisher.publishIfSideTask`

**问题**
设计文档 5.7 明确 Side Task「进入运行 / 等待审批 / 失败 / 完成」都应触发重聚合发布。当前实现只覆盖了审批、待回答新增、终态。实际影响有限（聚焦排序当前不使用 `treeRunning` / `treeFailed`），但存在两个可见偏差：① 边路任务失败（treeFailed=true 已推送）后用户重跑 → 无发布 → treeFailed 残留；② 若后续前端开始消费 `treeRunning`，运行态将长期失真。

**修复建议**
在 SIDE_TASK 置 RUNNING 的更新点（handleSendMessage / edit_and_resend / CrashRecoveryRunner 等）统一补 `treeSignalPublisher.publishIfSideTask(sessionId)`；或按设计文档建议在 `updatePhase` 侧做统一挂钩（注意与 `updateField` 的低级路径区分）。
