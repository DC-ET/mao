## BUG-1　embed-page 会话仍读盘并落一行永不使用的快照

- **文件:行号**：`backend-ts/src/harness/core/prompt-engine.ts:149-152`（`buildRequest` 无条件调用 `resolveWorkspaceRules`）；对照同文件 `:351-353`（`if (!embedPageAgent)` 才 push `workspace-rules` 节）与 `:439-441`（`isEmbedPageAgent` = 工具名带 `page_` 前缀）。
- **问题描述**：改造前 `workspaceRules()` 只在 `!embedPageAgent` 分支内调用，嵌入浮窗会话完全不读 `AGENTS.md`。改造后 `rulesText` 的计算上提到了 `buildRequest` 开头、早于 embed 判定，于是嵌入浮窗会话每轮仍会执行 `existsSync + statSync + readFileSync` 三次文件系统调用和一次 `session_workspace_rules` 主键点查，首轮还会 INSERT 一行快照——而这一行的文本**按设计永远不会被注入**（该节对 embed 会话不注入，`skills/mao-cli/reference/agent.md` 亦明确「不注入编程工作区 / AGENTS.md」）。
- **触发场景**：任何持有 `page_*` 工具的嵌入网页浮窗会话（`context.tools` 含 `page_screenshot` 等）的每一次 `buildRequest`。
- **影响**：无正确性影响（该节本来就不注入，不会注入错内容）；但属于本方案在该路径上新引入的开销——每轮 3 次 fs + 1 次 DB 点查，且每个 embed 会话泄漏一行永不使用的快照（只能等会话删除才回收）。嵌入浮窗是网页侧高频入口，累积量不可忽略。
- **建议修法**：把 embed 判定上提到 `buildRequest`，embed 会话跳过规则解析（读盘与快照都不做）：

  ```ts
  const embedPageAgent = this.isEmbedPageAgent(context);
  const rulesText = embedPageAgent ? '' : await this.resolveWorkspaceRules(context, effectiveWorkspace);
  ```
  （`buildSystemPromptSections` 已有 `embedPageAgent` 入参语义，可改为由调用方传入以避免重复判定。）
- **验证记录**：临时 spec `zz-temp-wrs-verify.spec.ts`（已删除）中对 `page_screenshot` 会话断言：`system` 不含 `## 工作区规则`（通过，符合设计）**且** `selectBySessionId(9102)` 返回非 null（通过 → 行确实被落库）。全量 `npm test` 对该路径无覆盖（现有新用例全部用 `read_file` 工具），说明这是测试盲区。

## BUG-2　`workspace` 不一致且空读：摘除该节 + 旧行残留

- **文件:行号**：`backend-ts/src/harness/core/workspace-rules-snapshot.service.ts:50-54`：

  ```ts
  if (existing != null && existing.workspace === workspace && hasText(existing.rulesText)) { … return existing.rulesText; }
  if (!hasText(rawText)) return '';   // ← workspace 不一致 + 空读走到这里
  ```

- **问题描述**：当快照行存在但 `workspace` 与当前 `effectiveWorkspace` 不一致（守卫列判定为无效快照）且本次读盘为空时，`resolve` 直接返回 `''`：该节被**摘除**——而「摘节」本身就是一次前缀塌陷，正是本方案要消除的那类事件；同时这条属于旧工作区的失效行既不被覆盖写回（因为 `rawText` 为空，不走 upsert）、也不被删除，一直残留到会话删除，或等到新工作区出现非空规则时才被顺带覆盖。
- **触发场景**：会话的 `effectiveWorkspace` 在生命周期内发生变化、且新工作区没有 `AGENTS.md`（或 LOCAL 桌面端该轮漏报）。需要说明：生产路径上 `session.workspace` 在 `createSession → initializeCloudWorkspace`（`session.service.ts:161`）里一次性落定、之后不再变更，因此**触发条件罕见**，TD §3.3 也把它定位为「测试/异常路径」的守卫；但守卫一旦触发，行为组合（塌陷 + 残留行）与方案目标相悖。
- **影响**：(1) 该节从系统提示中消失 → 一次完整前缀塌陷（该会话当轮起 system 后半段 + 工具 + 全部历史重算）；(2) 一条 workspace 不匹配的僵尸行长期驻留（不影响注入，因为不匹配就不会被取用，属数据卫生问题，下次读到非空规则时自愈）。
- **建议修法**：空读且存在**无效行**（workspace 不一致或 `rulesText` 异常空）时，把失效行删掉再返回 `''`，避免「摘节 + 僵尸行」并存：

  ```ts
  if (!hasText(rawText)) {
    if (existing != null) await this.repo.deleteBySessionId(sessionId); // 无效行不残留
    return '';
  }
  ```
  （若希望更保守，也可只在 `existing.workspace !== workspace` 时删；`rulesText` 为异常空值的行同理。）
- **验证记录**：临时集成 spec 对真实 MySQL：先 upsert `sessionId=9002, workspace='/ws/a'`，再 `service.resolve(9002, '/ws/b', '', …)` → 返回 `''`（通过）且 `selectBySessionId(9002)` 仍返回 `/ws/a` 行（通过 → 残留确认）。

## BUG-3　「磁盘已空但被冻结」日志无去重，LOCAL 会话每轮一条

- **文件:行号**：`backend-ts/src/harness/core/workspace-rules-snapshot.service.ts:89-95`（`logRetained` 的 empty 分支直接 `harnessLog('info', …)` 后 return，未过 `loggedDiskHashes` 去重表）；对照 `:96-105` 的「磁盘已变」分支有按会话去重。
- **问题描述**：TD §4.7 只对「磁盘已变但被冻结」约定了「同一 disk_hash 每会话只打一次」，对「磁盘已空/漏报但被冻结」没有约定去重，实现也就没有做。但后者的触发条件在 LOCAL 模式下是**持续性**的：`LocalAgentsMdRegistry`（`local-agents-md-registry.ts`）是进程内存，后端重启后登记表清空，桌面端只在发消息/编辑消息/建边路会话时上报（`streaming-ws-handler.ts:585/897/1087`）；于是重启后由**信号 / 定时任务**触发的轮次（没有桌面端上报）以及桌面端关闭期间的轮次，每一轮 `buildRequest` 都会打一条 `workspace rules empty on disk but snapshot retained session=…`。
- **触发场景**：LOCAL 会话已冻结过规则（桌面端至少成功上报过一次），其后端重启 + 自治轮次（信号/定时任务）连续触发；或桌面端异常不再上报。
- **影响**：日志噪声——每轮 LLM 请求一条 info，随会话生命周期无界增长（一个跨天、每几分钟触发一次的 LOCAL 会话可累积上千条），排障时反而淹没真正有用的 `pinned` / `invalidated` 行。与「磁盘已变」分支的去重口径也不一致。无正确性影响。
- **建议修法**：与「磁盘已变」共用去重表，用哨兵值标记「已打过空读日志」，状态变化（重新 pin / invalidate / 删除）时随 `loggedDiskHashes.delete(sessionId)` 一起清除：

  ```ts
  if (!hasText(rawText)) {
    if (this.loggedEmpty.get(sessionId) === true) return;   // 每会话只打一次
    this.loggedEmpty.set(sessionId, true);
    harnessLog('info', `workspace rules empty on disk but snapshot retained session=${sessionId} effective=on-next-snapshot`);
    return;
  }
  ```
  （`loggedEmpty` 同样需要 512 上限淘汰；或直接复用 `loggedDiskHashes` 以 `'<empty>'` 为哨兵值。）
- **验证记录**：临时集成 spec：LOCAL 会话先上报内容完成冻结，随后连续 5 轮 `agentsMdContent=null` → 捕获到 **5 条** `empty on disk but snapshot retained`（断言 `expect(n).toBe(5)` 通过 → 确认每轮一条、无去重）。
