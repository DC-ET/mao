## 中严重度

### 1. 飞书卡片工具区仍未使用已生成的业务摘要

**位置：**
- `backend-ts/src/harness/core/agent-loop.ts:495-515`
- `backend-ts/src/feishu/card-progress-listener.ts:25-30`

`AgentLoop.executeToolCalls` 已通过 `ToolResultSummarizer.summarize(...)` 计算并写入 `tc.summary`，例如 shell、read_file、grep_search 等工具会得到“执行命令”“读取文件”“匹配数量”等短摘要。但发送给事件监听器的参数仍是 `toolSave.content`：

```ts
listener.onToolCallResult(tc.id!, toolSave.content);
```

`FeishuCardProgressListener.onToolCallResult` 随后直接把该内容压缩并截断到 240 个字符，作为卡片中的工具说明。因此卡片展示的仍是工具结果正文/JSON，而不是已经计算好的 `tc.summary`。大段输出会被截断，且可能丢失成功、失败、行数或匹配数等关键信息；这与本轮要求的 round/tool 摘要展示不一致。

这不会改变 Agent 上下文：`context.addToolResult(tc.id!, toolSave.content)` 仍保存清洗后的工具结果，且工具消息随后继续用于下一轮请求；问题限定在飞书进度卡片的功能展示。

**修复建议：**

扩展工具结果事件，使其能传递 `tc.summary`（或传递包含 `summary` 与正文的结构），并让飞书卡片优先展示摘要；必要时再将清洗后的正文作为明确的兜底内容。建议补充 shell、read_file、grep_search 等工具的集成/监听器测试，断言卡片工具区展示摘要而非原始 JSON。

## 已核验未发现问题

- 最后一轮无工具的终止分支现在在 `break` 前调用 `listener.onRoundEnd?.(round)`，最后一轮内容能够进入 round 更新。
- 工具结果仍使用 `toolSave.content` 写入 `context.addToolResult`，没有因卡片监听改造而把摘要误写入 Agent 上下文；原始结果也继续用于持久化文件变更处理。
- `onRoundEnd` 在工具轮完成持久化后触发；空响应重试、后台子代理等待等继续循环路径不会误报 round 结束。
- `CompositeAgentEventListener` 对新增 round 事件采用可选调用，既有 WebSocket、定时任务等监听器不会因接口扩展而失效。
- 卡片更新通过 Promise 链串行排队，终态更新前等待已排队的处理中更新；卡片更新失败时仍回退到纯文本回复。
