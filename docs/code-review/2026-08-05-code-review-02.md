## 结论

上次报告中的 3 个问题主要路径均已修复。本次发现 1 个中等优先级问题和 1 个低优先级边界问题。

## 1. [中] 边路任务重命名响应可能写入切换后的主会话缓存

**位置**：`desktop/src/views/task/TaskView.vue:487-496`

`handleEditSideTaskTitle` 发出异步 PATCH 后，使用响应返回时的 `activeSessionIdRef.value` 更新边路任务缓存，并通过基于当前主会话状态的 `updateSideTaskTab` 更新标签。

触发过程：

1. 用户在主会话 A 中重命名某个边路任务；
2. PATCH 返回前切换到主会话 B；
3. 请求成功返回后，代码使用 B 的主会话 ID 更新缓存和标签状态。

服务端标题会正确修改，但 A 的前端缓存和标签可能仍保留旧标题；如果 B 的缓存中意外存在同 ID 条目，还可能错误更新 B。返回 A 后通常需要重新加载才能看到正确标题。

**建议**：请求发起前固定边路任务所属的父会话 ID，响应后用该 ID 更新缓存；标签更新也应按指定父会话处理，或仅在当前主会话仍是原父会话时更新当前标签状态。

## 2. [低] 补拉请求 pending 期间重新进入同一子会话，原请求随后失败时不会自动重试

**位置**：`desktop/src/views/task/TaskView.vue:295-337`

当前实现已允许请求失败后再次切入时重试，但存在以下低频时序：

1. 打开子会话 S，开始补拉 meta 或 todos；
2. 请求未完成时切走，又在请求仍 pending 时切回 S；
3. 第二次进入因 `pendingInspectorMeta/Todos.has(sid)` 被跳过；
4. 原请求随后失败并清除 pending。

普通 `Set` 的清除不会重新触发 `watch(inspectorSessionId)`，因此用户此时虽然停留在 S，也不会自动重试，仍需再切走、切回一次。该问题需要网络失败与快速切换同时发生，影响较低。

**建议**：再次进入同一子会话时复用并等待已有请求；请求失败后若该子会话仍是当前检查器对象，可执行一次受控重试或保留显式重试状态。
