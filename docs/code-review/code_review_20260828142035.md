## 一、高严重度（特定真实渠道下影响业务功能正确性，建议修复后联调）

### H1. usage 归一：Anthropic `input_tokens` 不含缓存部分，直接映射 `promptTokens` 会导致输入 token 少算

- **位置**：`backend-ts/src/harness/llm/anthropic-llm-adapter.ts:856-867`（`mapAnthropicUsage`），非流式路径 `parseAnthropicChatResponse` → `mapAnthropicChatUsage`（:876-887）同样受影响。
- **问题**：Anthropic 官方语义为 `总输入 = input_tokens + cache_creation_input_tokens + cache_read_input_tokens`，即 `input_tokens` 只统计最后一个缓存断点之后的部分；而统一类型的 OpenAI 语义中 `promptTokens`（`prompt_tokens`）是全量输入，`promptTokensDetails.cachedTokens` 只是其中的明细子集（对照 `openai-llm-adapter.ts` 经 `json.ts parseUsage` 的口径）。当前实现把 `input_tokens` 直接当 `promptTokens`：
  1. 渠道启用 prompt caching 时（Mao 请求体虽不带 `cache_control`，但部分网关类渠道会自动注入），`promptTokens` 严重少算（cache_read 可达几十万 token 级）；
  2. `cache_read_input_tokens` 被填进 `promptTokensDetails.cachedTokens`，但该值可能大于 `promptTokens` 本身，破坏「cachedTokens ⊆ promptTokens」的既有口径，用量展示与入库口径混乱；
  3. `cache_creation_input_tokens` 完全未读取，该部分 token 彻底丢失。
- **下游影响**：`AgentLoop` 用 `usage.promptTokens` 更新上下文锚点与 `lastPromptTokens`（`agent-loop.ts:243-254`），`CompactionService` 以真实 prompt usage 为下限判断压缩水位。少算会推迟/阻止上下文压缩触发，长会话最终溢出报 400。
- **修复建议**：`mapAnthropicUsage` 改为 `promptTokens = input + cacheRead + cacheCreation`（三者均 `?? 0`），`cachedTokens` 仍单列 `cache_read`；补读 `cache_creation_input_tokens`（如需区分可扩展 `PromptTokensDetails`，但至少并入总数）。

### H2. 流式 `message_delta` 的 usage 处理丢弃 `input_tokens`，兼容网关下 `promptTokens` 恒为 0

- **位置**：`backend-ts/src/harness/llm/anthropic-llm-adapter.ts:339-344`（`processStreamBody` 的 `message_delta` 分支）。
- **问题**：Anthropic 官方文档明确 message_delta 的 usage 是累计值，且当前官方响应中会重复携带 `input_tokens` 与 cache 字段（见官方 streaming 文档示例）；同时大量 Anthropic 兼容推理网关（sglang/vLLM 系）在 `message_start` 中 `input_tokens: 0`，真实值只在 `message_delta` 下发。当前实现只从 message_delta 取 `output_tokens`，`promptTokens` 永远停留在 message_start 的值（网关场景为 0）。
- **下游影响**：`usage.promptTokens === 0` 时 `AgentLoop.onComplete` 直接跳过锚点更新与 `lastPromptTokens` 更新（`agent-loop.ts:243` 的 `> 0` 守卫），上下文压缩水位链路对该渠道整体失效；入库 usage 也为 0。
- **修复建议**：`message_delta` 分支改为「有值即覆盖」：`if (u.inputTokens != null) usage.promptTokens = u.promptTokens`（cache 明细同理），与 completionTokens 的覆盖方式对称。

## 二、中严重度（条件触发或交互缺陷，建议修复）

### M1. 多条连续 tool 消息且带图片时，`tool_result` 不再位于 user 消息 block 序列最前 → Anthropic 400

- **位置**：`backend-ts/src/harness/llm/anthropic-llm-adapter.ts:748-758`（`convertMessages` 的 tool 分支）+ `pushBlocks` 相邻合并（:706-713）。
- **问题**：单条 tool 消息的转换是 `blocks = [image...]` 后 `unshift(tool_result)`，单条场景 tool_result 在最前、正确；但多条连续 `role:'tool'` 消息依次 `pushBlocks('user', ...)` 追加合并后，最终顺序为 `[tool_result_A, image_A, tool_result_B, image_B]`——`image_A` 出现在 `tool_result_B` 之前，违反 Anthropic「tool_result 必须位于 user 消息 block 序列最前」的硬约束，请求直接 400。这与技术方案 §4.2.2「tool_result 必须位于 user 消息 block 序列最前」的关键合并规则自相矛盾，且现有单测只覆盖了纯文本 tool 消息，未覆盖该组合。
- **现实触发面**：主链路中 `ToolMediaInjector`（`tool-media-injector.ts:33-38`）把工具图片注入为独立 user 消息、不塞进 tool 消息 content，因此当前 AgentLoop 链路不会命中；但 `convertMessages` 是通用纯函数，任何 tool 消息 content 数组携带 `image_url` 的输入（多工具并行返回图片等未来场景、外部直连调用）都会 400。
- **修复建议**：分两段收集——先把所有 tool_result 按序放入 user 消息头部，图片（及后续 user 文本）追加在全部 tool_result 之后；并补一条「多条 tool 消息 + 图片」的请求体级断言测试。

### M2. admin 表单 `clearable` 清空「供应商」后保存静默失效，provider 一旦设置便无法清回

- **位置**：`admin/src/views/model/ModelFormDialog.vue`（供应商 `el-select` 新增 `clearable`）；后端配合点 `backend-ts/src/model/model.service.ts` `updateModel` 的 `if (provider != null) model.provider = provider`。
- **问题**：项目 Element Plus 为 2.14（`admin/package.json`），`el-select` 清空后 `valueOnClear` 默认是 `undefined`（源码 `DEFAULT_VALUE_ON_CLEAR = void 0`，非空串）。`form.provider = undefined` 在提交 payload 序列化时整个字段被丢弃 → 后端 `body.provider === undefined` → 不更新。结果：用户在 UI 上点了清空、表单显示已清空，保存后 DB 仍是旧 provider，无任何提示；且由于后端 `updateModel` 对 `null/''` 一律不更新，「把 anthropic 误配改回 OpenAI 兼容」只能通过显式选择 `openai-compatible` 完成，直接清空这条路是坏的。
- **修复建议**（二选一，前端改更小）：给该 `el-select` 加 `:value-on-clear="''"`，使清空回落到「留空按 OpenAI 兼容处理」的既定语义；或提交时 `provider: form.provider ?? ''`。同时建议后端 `updateModel` 支持显式空串清空（`provider !== undefined && provider !== null` 时按 trim 后值写入），否则「下拉可清空」与「后端不可清空」的语义长期不一致。

## 三、低严重度（防御性 / 一致性问题，不阻塞本次上线）

### L1. `AnthropicChatClient` 透传 `stream` 参数但按非流式 JSON 解析响应

- **位置**：`backend-ts/src/model/anthropic-chat.client.ts:29`（`stream: request.stream ?? false`）与 `:47`（`JSON.parse(text)`）。
- **说明**：若调用方传 `stream: true`，上游返回 SSE 文本会被 `JSON.parse` 抛错。当前唯一调用方 `ModelService` 两处请求均未传 `stream: true`（probe 显式 `stream: false`），不构成现实 bug，但与 `OpenAiChatClient` 同属「接口允许、实现不支持」的隐患。建议要么忽略 `request.stream` 固定 false，要么不支持时显式抛错。

### L2. `AnthropicChatClient` 消息逐条转换、不合并相邻同 role

- **位置**：`backend-ts/src/model/anthropic-chat.client.ts:22-35`。
- **说明**：与 adapter 的 `convertMessages` 不同，该客户端未做相邻同 role 合并与首条 user 约束处理。当前唯一调用是单条 `user:'Hi'`，无实际触发路径；但作为「连通性测试客户端」被复用于其他探测场景时会产生难排查的 400。建议复用 `convertMessages`（或注明仅支持单轮 user 消息）。

### L3. `testAudioSynthesis` 固定使用默认 OpenAI 客户端，未走 `chatClientFor` 路由

- **位置**：`backend-ts/src/model/model.service.ts` `testAudioSynthesis` 内的 `this.llmClient.chat(...)`（对比 `testConnectivity` 与 `probeMidSystemMessage` 均已改为 `this.chatClientFor(config)`）。
- **说明**：语音模型按设计不会配 anthropic，行为无实际回归；但若误配，报错将来自 OpenAI 兼容客户端（URL/错误体都是 `/chat/completions` 风格），排障会有误导。顺手统一为 `chatClientFor(config)` 更一致（AnthropicChatClient 不支持 audio，报错文案至少语义正确）。

### L4. 转换后 `messages` 可能为空数组（纯 system 输入）

- **位置**：`backend-ts/src/harness/llm/anthropic-llm-adapter.ts` `buildRequestBody` / `convertMessages`。
- **说明**：消息序列全部为 system 时（`converted.length === 0` 且 systemParts 非空），请求体 `messages: []`，Anthropic 返回 400。正常业务（会话必有 user 消息、压缩请求会追加 user）不会出现，仅防御性提醒；可考虑空数组时兜底一条空 user 文本或直接抛出可读错误。

### L5. `processStreamBody` 中 `blockTypes` Map 只写不读（死代码）

- **位置**：`backend-ts/src/harness/llm/anthropic-llm-adapter.ts`（`content_block_start` 处 `blockTypes.set`、`content_block_stop` 处 `blockTypes.delete`，无任何读取）。
- **说明**：不影响功能，建议删除或补上实际用途（例如按 block 类型做分片校验）。

### L6. `llm-adapter-facade.spec.ts` 存在严格模式类型错误

- **位置**：`backend-ts/src/harness/llm/llm-adapter-facade.spec.ts:13`（`provider?: string | null` 赋给 `LlmModelConfig.provider?: string`，全量 `tsc --noEmit` 报 TS2322）。
- **说明**：仓库现状对 spec 本就不做全量严格 tsc（HEAD 存量约 188 个同类错误，CI 只跑 `tsconfig.build.json` 与 vitest），不阻塞；新文件建议顺手把测试辅助函数签名改为 `provider?: string | null` 对应的可选联合或直接传 `as LlmModelConfig`，避免新增存量。
