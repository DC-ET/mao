## P1：应优先修复

### R1. WS access 正常到期被误判为 SSO 失效，终止自动续期和重连

**位置**
- `sdk/embed/src/controller.ts:222-224`：SSO 模式下 onAuthFailed 无条件 rejectAuthentication。
- `sdk/embed/src/core/ws-client.ts:221-230`：所有 1003 关闭都调用 onAuthFailed。
- `sdk/embed/src/core/token-provider.ts:50-53,76-85`：login_required 停止后 get 不再换票，并清除定时器。
- `backend-ts/src/session/ws/streaming-ws-registry.ts:124-140`：SSO access 到期使用 close(1003, 'Authentication expired')。

**触发路径**
1. 用户已有正常 SSO WS 连接，宿主 SSO 仍有效。
2. 页面休眠错过续期，或临时 503/429 延续到旧 Mao access 到期。
3. 服务端按设计以 1003 关闭旧连接；浏览器处理该关闭事件。
4. SDK 把它当作 SSO 明确失效，调用 stop('login_required')，并通过 onStatus 调用 ws.disconnect()；后者还使 intentionalClose=true，阻止自动重连。
5. pageshow/online/visibilitychange 只自动 resume service_unavailable，不能解除 login_required。即使宿主能立即提供有效 SSO Token，也必须手工重试。

**影响**：正常 access TTL 变成一次需要人工介入的退出边界，违背“有效 SSO 下自动续期、休眠/过期后自动恢复”的主线。

**验证**：用真实 TokenProvider/WsClient 类、合成 fetch 和假 socket 做内存驱动：正常认证后模拟 server close(1003)，随后 get() 返回“登录凭据已失效”，换票调用数保持 1，没有尝试校验仍有效的 SSO。服务端到期使用 1003 也有现有 WS spec 明确断言。

**建议修复**：区分 Mao WS access 到期/认证拒绝与换票接口对 SSO 的明确拒绝。前者进入有界取新票和重连流程，只有换票返回明确终止状态才停止 SSO 生命周期；可用明确关闭码/协议原因分类，不依赖全部 1003 都代表宿主登录无效。不能延长旧 access 或放行过期连接。

**建议测试**：联动真实 controller + TokenProvider + WsClient，模拟休眠跨过 access.exp、旧连接到期但供应商凭证有效，断言自动换票、重连、恢复订阅与历史且不发送重复业务帧；另断言换票 401 确实停止。

### R2. SSO 失效后同账号重试会丢失会话订阅和历史对账

**位置**
- `sdk/embed/src/controller.ts:201-207,782-788`：非暂时认证错误 disconnect；重试成功后若 booted=true 只 connect。
- `sdk/embed/src/core/ws-client.ts:301-304`：disconnect 清除 authenticatedOnce、订阅意图。
- `sdk/embed/src/controller.ts:373-380`：isReconnect=false 时不重拉历史。

**触发路径**
1. 面板已完成 boot，当前会话 11 正在运行，booted=true。
2. 下一次换票返回明确失效或临期最终失败；SDK disconnect，但保留当前会话和 booted。
3. 宿主恢复为同一个用户，用户点击重试，换票成功。setIdentity 不认为身份发生变化，不重新 boot。
4. retry 只 ws.connect()；此前订阅集合已清空，connected 时没有 subscribe。authenticatedOnce 也被重置，所以 controller 不执行重连历史对账。

**影响**：面板显示在线但不再订阅当前会话，漏掉断线期间的历史和依赖订阅的后续流/状态恢复；已受理任务不会取消，但用户不能正确恢复查看。该问题独立于 R1：即便真正的 SSO 失效处理完全正确，恢复同账号仍会触发。

**验证**：真实 WsClient 内存驱动先订阅 11、完成鉴权、disconnect，再用同用户连接；第二连接只发送 auth，trackedSessionIds=[]。现有 controller.sso.spec 未覆盖“失败—同账号恢复”。

**建议修复**：区分“暂停认证连接”和“销毁身份会话”。同身份暂停保留订阅意图/重连对账信息，或重试成功后显式按当前 store 会话重新订阅、拉取历史、对账 pending saves；账号切换/destroy 仍必须清空旧身份状态。不应通过新建空会话规避恢复问题。

**建议测试**：会话运行中 SSO 401 → 同用户恢复 → retry，断言重新 subscribe 原 sessionId、补拉断线历史、恢复问题卡及 phase、对账未确认消息，且无新建会话/重复 send_message。

## P2：常规功能修复

### R3. 首次换票自动重试成功后不会继续 boot，面板停留在无会话/离线状态

**位置**
- `sdk/embed/src/controller.ts:552-559`：open 的 boot 只挂在当前 tokens.get() 的成功回调上。
- `sdk/embed/src/controller.ts:192-207,277-282`：后台换票成功只更新身份/WS 凭证/提示；首次身份赋值不安排 boot。
- `sdk/embed/src/core/token-provider.ts:88-94,147-150,159-165`：自动重试自行调用 get，成功没有恢复先前 open 的后续动作。

**触发路径**
1. 初次 open，换票返回 503 或 429，当前 get Promise 拒绝；open 的 catch 结束该链，尚未进入 boot。
2. TokenProvider 退避后自动重试成功。
3. onUpdate 首次设置 identity 后返回“未切换账号”；没有 socket，refreshAuth 直接完成。onStatus('authenticated') 清掉错误提示，但没有人再调用 boot。

**影响**：认证已恢复、错误横幅消失，但不加载 Agent、不恢复/创建会话、不建立 WS。用户必须再次关闭/打开面板等操作才能继续，自动重试没有恢复业务初始化。

**验证方式**：已核对上述完整调用链；此项为静态路径验证，未新增或修改测试文件。现有 TokenProvider 重试测试仅验证票据更新，不验证 controller 初始化。

**建议修复**：让成功认证状态驱动尚未完成的面板初始化：在面板打开、未 boot 且未销毁时，待 single-flight settle 后幂等启动 boot。避免 onUpdate 内等待当前换票自身，也避免普通在线续期重复 boot。

**建议测试**：真实 controller 初次 open → 503/429 → fake timers 驱动自动成功，用户不再操作，断言 Agent/会话请求和 WS 鉴权继续执行且只初始化一次；destroy/关闭面板时不得意外启动。

### R4. 手动重试会清除 Retry-After，限流等待可被连续点击绕过

**位置**
- `sdk/embed/src/core/token-provider.ts:68-73`：resume 无条件 retryAt=0。
- `sdk/embed/src/core/token-provider.ts:159-163`：最后一次失败进入 stopped 前没有记录该响应的新 Retry-After。
- `sdk/embed/src/controller.ts:782-788`：每次点击重试均 resume 后立即 get。

**触发路径**
1. 换票收到 HTTP 429 / Retry-After: 60，正常定时器已计划等待。
2. 用户马上点击重试，resume 清掉 retryAt，立即再次换票；重复点击会持续提前请求（仅重叠请求被 single-flight 合并）。
3. 五次耗尽后，网络/可见性恢复调用 resume 同样不会保留最后一次服务端冷却期限。

**影响**：SDK 未遵守服务端要求的 Retry-After，容易在限流故障时继续增加请求并反复收到 429。不是服务端限流绕过或无限后台重试漏洞，而是客户端重试策略错误。

**验证**：真实 TokenProvider + 合成 429 响应，第一次 get 失败后立即 resume/get，在 60 秒内观察到第二次 fetch。

**建议修复**：将服务端 not-before 冷却期限与自动重试次数分开管理。用户/网络事件可以开启新一轮重试，但不得清空尚未到期的 Retry-After；最终失败也应保存此次响应的期限。等待期间保持可读状态，过期 access 仍不可用。

**建议测试**：429 Retry-After:60 后反复点击 retry、触发 online/visibilitychange，60 秒前换票次数不增加；五次耗尽且最后一次有更长 Retry-After 也保持限制；期限届满后可正常恢复。
