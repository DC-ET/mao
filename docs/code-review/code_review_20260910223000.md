## 二、需要处理的问题

### R1【中】BUG-2 残留：`enqueueHead` 丢失 `scheduled_task_id`，内存映射可能被后续无关执行误回写

- 文件：
  - `backend-ts/src/session/message-queue.service.ts`（`enqueueHead`）
  - `backend-ts/src/session/ws/streaming-ws-handler.ts`（`autoConsumeQueue` / `requeueIfClaimed`）
- 现状：
  1. busy 入队时 `enqueue(..., task.id)` 已绑定 `scheduledTaskId`（正确）；
  2. `autoConsumeQueue` 出队后 `queueScheduledTaskIds.set(sessionId, head.scheduledTaskId)`（正确）；
  3. 但失败补偿统一走 `enqueueHead`，该方法**不接受、也不写入** `scheduledTaskId`：

```32:44:backend-ts/src/session/message-queue.service.ts
  async enqueueHead(sessionId: number, userId: number, content: string, images: string | null): Promise<void> {
    return this.repo.transaction(async (tx) => {
      const first = await tx.findFirstPendingForUpdate(sessionId);
      const minOrder = first?.sortOrder ?? 1;
      await tx.insert({
        sessionId,
        userId,
        content,
        images,
        sortOrder: minOrder - 1,
        status: 'PENDING',
      });
    });
  }
```

- 触发路径（任一即可）：
  - `autoConsumeQueue` 中 `saveMessage` 失败回补；
  - `handleSendMessage` 的 `requeueIfClaimed`（LOCAL 未连接、图片校验失败、submit 被拒等）。
- 影响：
  1. 回补行在 DB 中永久丢失来源任务 id，此后即使真正执行完成也不会按队列来源回写（依赖内存残留）；
  2. 更危险的是：首次出队时已 `queueScheduledTaskIds.set`，回补后**未删除**该映射。下一次同会话上任意无关消息执行到 `runExecution` finally 时，会用**陈旧 taskId** 调用 `onScheduledTaskQueueConsumed`，把定时任务的 `lastExecutionStatus` 写成与该定时消息无关的终态。
- 建议：
  - `enqueueHead` 增加可选 `scheduledTaskId` 并落库；
  - 所有 `enqueueHead` 补偿路径透传 `head.scheduledTaskId` / `item.scheduledTaskId`；
  - 回补失败路径同步 `queueScheduledTaskIds.delete(sessionId)`（或仅在真正进入执行时保留映射）。

### R2【中】BUG-2/BUG-3 残留：pendingCancel 提前落终态时，既不回写任务状态，也不清理 `queueScheduledTaskIds`

- 文件：`backend-ts/src/session/ws/streaming-ws-handler.ts`（`handleSendMessage` pendingCancel 分支 ~397–405 行）
- 现状：autoConsume 窗口内用户点「停止」时：

```397:405:backend-ts/src/session/ws/streaming-ws-handler.ts
    if (pendingCancelAt != null && pendingCancelAt >= sendStartedAt) {
      flag.set(true);
      this.executionClaims.delete(sessionId);
      this.autoConsumingSessionIds.delete(sessionId);
      this.runningExecutionIds.delete(sessionId);
      await this.finishCancelledSession(sessionId, userId, resolvedEventId ?? randomUUID());
      return;
    }
```

- 问题：
  1. 定时任务 busy 入队消息已出队并可能已 `saveMessage`，但此路径不调用 `onScheduledTaskQueueConsumed(taskId, 'CANCELLED')`，`lastExecutionStatus` 永久停在 `QUEUED`（本轮修复声称覆盖 CANCELLED，此窗口未覆盖）；
  2. 不清理 `queueScheduledTaskIds`，同 R1：下一次无关执行的 finally 可能误回写陈旧任务。
- 建议：该分支在 `autoSavedMessageId`/`queueScheduledTaskIds` 有绑定时，同步回写 `CANCELLED` 并删除映射；是否把已落库 USER 消息回补队首可按产品语义决定，但任务状态与映射必须收敛。

### R3【中低】BUG-2 残留：插队（`handleInsertMessage`）消费带 `scheduledTaskId` 的队列项时不绑定、不回写

- 文件：`backend-ts/src/session/ws/streaming-ws-handler.ts`（`handleInsertMessage` ~1037–1102 行）
- 现状：用户对定时任务排队消息点「立即执行」时，走 `handleInsertMessage`：删除队列项、落库、调用 `handleSendMessage`，但**从未**读取 `item.scheduledTaskId` 写入 `queueScheduledTaskIds`。
- 影响：busy 入队后改走插队执行的定时消息，完成后 `lastExecutionStatus` 仍永久 `QUEUED`。
- 建议：在 `item.scheduledTaskId != null` 时 `this.queueScheduledTaskIds.set(sessionId, item.scheduledTaskId)`，与 autoConsume 路径对齐。

### R4【中低】BUG-4 残留：用户行仍先于角色事务落库；禁用路径仍无锁

- 文件：`backend-ts/src/user/user.service.ts`、`backend-ts/src/permission/permission.service.ts`
- 已闭环部分：`changeRolesWithAdminGuard` 在同一事务内 `findByRoleIdForUpdate` 锁定 ADMIN 绑定并做最后管理员检查；`updateUser` 已接入；`assertCanChangeRoles` 前置快速失败。
- 残留：
  1. **顺序问题**：`updateUser` 仍是 `assertCanChangeRoles`（事务外）→ `userRepo.updateById(user)` → `changeRolesWithAdminGuard`。若事务内守卫因并发失败抛错，资料/状态已写入而角色未改（半截更新）。注释写「校验必须前置于用户行持久化」，但真正持锁的校验在用户行之后。
  2. **禁用路径 TOCTOU**：`assertCanDisableUser` 仍在事务外单独读库，无 `FOR UPDATE`。并发禁用仅剩两名管理员中的彼此时，仍可能双双放行，系统失去全部活跃管理员。`updateUserStatus` / `updateUser(status=0)` 均走此路径。
- 建议：
  - 角色变更：将用户行更新并入同一事务，或至少在 `changeRolesWithAdminGuard` 失败时回滚/补偿用户行；
  - 禁用：对 ADMIN 绑定行 `FOR UPDATE` 后再判断，或与 `changeRolesWithAdminGuard` 共用同一守卫事务。

## 三、确认已闭环的修复（摘要）

1. **P1 / BUG-9**：`handleChatSend` 在 `connect`/`upload*` 之前同步 `sending.value = true`；`releaseSendLock` 覆盖上传失败、无父会话、创建/发送失败、外层 catch；队列入队分支先 `releaseSendLock` 再 `enqueueMessage`，不长期占用互斥。双击/双 Enter 无法再创建两个边路会话。
2. **P2 / BUG-3 主路径**：`autoConsumeStartedAt = Date.now()` 在 `executionClaims.add` 与 `dequeue` 之前记录，并经 `data.autoConsumeStartedAt` 传入 `handleSendMessage` 作为 `sendStartedAt`；`pendingCancelAt >= sendStartedAt` 可识别 500ms 窗口及 saveMessage 窗口内的取消。残留见 R2。
3. **P4 / BUG-2 主路径**：V108 增加 `message_queue.scheduled_task_id`；busy 入队传 `task.id`；`runExecution` finally 按 `terminalPhase` 调用 `onScheduledTaskQueueConsumed`（create-app 已接线 `scheduledStore.updateById`）。残留见 R1–R3。
4. **P5 / BUG-8**：HTTP 先 `StreamableHTTPClientTransport` 的 `client.connect`，失败后再建新 Client 用 `SSEClientTransport` 重试；双失败时合并错误信息。回退发生在连接阶段而非构造器。
5. **P6 / BUG-13**：`sameMessageText` 的 endsWith 兜底左边界仅允许 `\n`（`0x0a`），空格边界已去掉。

## 四、修复优先级建议

1. **先修 R1**：内存映射误回写会把无关终态写到定时任务上，属于状态污染。
2. **再修 R2/R3**：补齐 CANCELLED/插队路径，使 BUG-2 声称的三种终态真正全覆盖。
3. **随后 R4**：角色半截更新与禁用 TOCTOU 为权限边界问题，优先级低于状态污染但建议同批处理。
