## 一、重大问题（本次修复引入的回归）

### R1 `awaiting_first_message_title` 永远置不上 1：`---` 新会话命名功能 100% 失效

- **位置**：`backend-ts/src/feishu/message.repository.ts:227-233`（`upsertSessionChannel`）、`backend-ts/src/feishu/message.repository.ts:101-108`（`saveConversation` 联动调用）、`backend-ts/src/feishu/message.service.ts:44-52`（`createP2pSession`）
- **问题描述**：`createP2pSession` 的执行顺序是：
  1. `saveConversation(...)` → 内部联动 `upsertSessionChannel(sessionId, appId, chatId, chatType)`（第 5 参默认 `false`）→ **INSERT 插入绑定行，`awaiting_first_message_title = 0`**；
  2. 紧接着 `await this.repository.upsertSessionChannel(session.sessionId, accountId, chatId, 'p2p', true)` 意图把标志置 1。

  但 `upsertSessionChannel` 的 SQL 为：
  ```sql
  INSERT INTO feishu_session_channel (session_id, app_id, chat_id, chat_type, awaiting_first_message_title)
  VALUES (?, ?, ?, ?, ?)
  ON DUPLICATE KEY UPDATE app_id = VALUES(app_id), chat_id = VALUES(chat_id), chat_type = VALUES(chat_type)
  ```
  `awaiting_first_message_title` **不在 ON DUPLICATE KEY UPDATE 子句中**。第 2 步因 `uk_feishu_session_channel(session_id)` 命中第 1 步刚插入的行，走 ON DUPLICATE 分支，**只更新 app_id/chat_id/chat_type，标志保持第 1 步写入的 0**——置 1 永远无效。

  下游后果：`finalizeNewSessionTitle`（create-app.ts:1246-1259）第一道检查 `if (channel?.awaitingFirstMessageTitle !== 1) return false;` 恒命中，命名永远 no-op。**需求点「新会话以首条消息前 20 字命名」全场景失效**——比修复前（仅重启场景失效，上轮 2.2 定级一般）更严重，且这是本次修复引入的回归。handler 侧为配合持久化标志已删除内存 `pendingTitleSessionIds`，两相叠加后命名链路完全断掉。
- **触发条件**：任何一次 `---` 新建会话后的首条消息（无需重启，100% 复现）。
- **为什么 1330 个测试没拦住**：`message.service.spec.ts` 对 repository 全量 mock（只断言了 `upsertSessionChannel` 的**调用参数**带 `true`，不执行真实 SQL），handler spec 对 `finalizeNewSessionTitle` 也是 mock（恒 true）——ON DUPLICATE 的列覆盖语义落在 SQL 字符串里，恰好处于两层 mock 之间的盲区。
- **建议修复方向**（任选其一）：
  1. `upsertSessionChannel` 的 ON DUPLICATE 增加 `awaiting_first_message_title = GREATEST(awaiting_first_message_title, VALUES(awaiting_first_message_title))`——「只进不清」语义与注释「标志只由命名动作清除」一致，saveConversation 的默认 0 也不会误清；
  2. 或把 awaiting 标志作为参数传入 `saveConversation`，一次 upsert 完成，消除两次写入；
  3. 补一个针对「先落行(0) 再置 1」真实 SQL 语义的集成测试（或至少在 spec 注释 mock 局限）。
- **严重程度**：重大

## 二、一般问题（修复不完整）

### Y1 owner 守卫对「目标会话不存在/已删除」失效：getSession 抛异常而非返回 null，引用已删会话的消息静默失败且无任何回复

- **位置**：`backend-ts/src/create-app.ts:1230-1237`（switchSession 守卫）、`backend-ts/src/session/session.service.ts:398-404`（`getSession` 抛 `SESSION_NOT_FOUND`）
- **问题描述**：上轮 2.1 指出两个问题：换绑越权（已修）与**悬空映射**（未修）。守卫代码：
  ```ts
  const targetSession = await sessionService.getSession(targetSessionId);
  if (targetSession?.userId != null && targetSession.userId !== triggerUserId) { ... return null; }
  ```
  开发者显然想用 `targetSession?.` 处理「目标不存在」的情况，但 `getSession` 对不存在/已软删会话**抛 `BusinessException(SESSION_NOT_FOUND)` 而不是返回 null**（`findById` 带 `notDeleted()` 过滤），可选链的空值分支是死代码。实际行为：
  1. 目标会话已被删除（`deleteSession` 为软删，session.routes.ts:237，且**不清理** `feishu_p2p_message` 映射、`feishu_session_channel` 绑定行、`feishu_chat` 指针行——悬空映射真实存在）→ 守卫处抛异常 → `switchSession` → `resolveP2pInbound`（引用切换分支无 catch）→ `onMessage` → `process()` finally 将该消息标记 FAILED → **用户引用旧消息后机器人毫无反应**（无确认、无报错文案），且重试（10 分钟后 claim 过期重放）仍失败。
  2. 所幸异常发生在指针切换之前（守卫先于 `switchP2pSession` 执行），会话状态未被破坏，用户仍可通过 `---` 或引用其他消息恢复，故不定为重大。
- **触发条件**：用户回复/引用一条属于**已删除会话**的历史消息（映射行残留）。
- **建议修复方向**：守卫改用 `sessionRepo.findById(targetSessionId)`（软删过滤、返回 null 不抛）或 try/catch `SESSION_NOT_FOUND`；目标为空时 `return null`（静默保持现状，与「未命中静默」语义对齐），即把守卫条件修正为「目标不存在或归属他人 → 拒绝」。`targetSession?.userId` 中的可选链相应删除或改为显式空值判断。
- **严重程度**：一般

- **建议**：绑定表写入失败降级为记日志（会话可正常工作，仅丢失反查/命名能力），或至少在 createP2pSession 中调整步骤顺序/容错使反馈一致。
