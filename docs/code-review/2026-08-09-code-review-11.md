## 中等严重程度

### 1. LOCAL 自动提交会同步读取整个未跟踪文件，大文件可阻塞或耗尽 Electron 主进程内存

**代码位置**

- `desktop/electron/gitOperations.cjs:146-152`
- `desktop/electron/gitOperations.cjs:166-192`
- `desktop/electron/main.cjs:1055-1057`

**问题说明**

LOCAL 构建提交信息时，`git-commit-input` IPC 直接在 Electron 主进程调用 `buildCommitInput()`。对于每个非敏感、未被状态逻辑识别为二进制的未跟踪文件，`buildFileDiff()` 使用：

```text
fs.readFileSync(absolute)
```

把整个文件一次性读入内存，之后才对所有 diff 做 200 KB 截断。也就是说，200 KB 限制只约束上传给后端的数据，不约束本地读取量。

当仓库中存在数百 MB/数 GB 的未跟踪文本文件或无 NUL 字节的生成文件时，点击提交会同步阻塞 Electron 主线程，并可能引发高内存、页面卡死甚至主进程崩溃。多个大文件会依次完整读取，风险进一步放大。CLOUD 实现虽然也使用 `readAllBytes`，但至少在单文件读取后裁剪到 2 MB；LOCAL 当前没有任何读取上限。

这属于正常业务边界：未跟踪日志、导出数据或生成产物可能很大，而需求要求提交全部变更、仅限制模型 diff，不应因生成提交信息导致桌面应用失去响应。

**建议修复**

对未跟踪文件采用有上限的异步/流式读取，只读取构建模型摘要所需的前缀（例如不超过 2 MB，并最终参与公平 200 KB 分配）；读取前可先检查文件大小，并使用小块前缀检测 NUL 字节。避免在 IPC handler 的 Electron 主线程执行无界 `readFileSync`。

补充一个大型未跟踪文本文件测试，验证：

1. 生成输入的读取量有明确上限；
2. 最终 `diffBytes <= 200 KB`；
3. 文件被标记为 `truncated=true`；
4. 不会同步分配与原文件大小等量的 Buffer。
