## 二、需要处理的问题

### N1【中低】R1 同类残留：两条异常路径设置 `queueScheduledTaskIds` 后未清理，陈旧映射仍可能误回写

- 文件：`backend-ts/src/session/ws/streaming-ws-handler.ts`
- 性质：与第 2 轮 R1 同一类问题（陈旧 taskId 被后续无关执行的 `finally` 误回写），但位于 R1 验收点未点名的两条异常路径上。验收点列出的三条路径（saveMessage 失败 / requeueIfClaimed / submit 拒绝）本身已正确闭环。

#### 路径 A：`autoConsumeQueue` 外层 catch

时序（1207–1210 行）：

```ts
if (head.scheduledTaskId != null) {
  this.queueScheduledTaskIds.set(sessionId, head.scheduledTaskId);  // 映射已设置
}
await this.sendQueueUpdated(sessionId, userId);                      // ← listPending DB 异常时抛出
```

外层 catch（1256–1260 行）只清理 claim 与 autoConsuming，**不清 `queueScheduledTaskIds`**：

```ts
} catch (e) {
  console.error(`Failed to auto-consume queue for session ${sessionId}`, e);
  this.executionClaims.delete(sessionId);
  this.autoConsumingSessionIds.delete(sessionId);
  // 缺少：this.queueScheduledTaskIds.delete(sessionId);
}
```

影响：队列行已出队（DB 已 DELETED）且未回补 → 消息丢失（此点为存量 M-3 类问题）；同时映射残留 → 同会话下一次**无关**消息执行到 `runExecution` finally（521–529 行）时，会用陈旧 taskId 调用 `onScheduledTaskQueueConsumed`，把定时任务 `lastExecutionStatus` 写成与该定时消息无关的终态。

#### 路径 B：`handleInsertMessage` 的 catch

时序：R3 修复在 1095–1097 行绑定映射后，才依次执行 `saveMessage`（1104）→ `delete(queueId)`（1105）→ `handleSendMessage`（1113）。以下任一失败都会落入 1120–1122 行的 catch：

```ts
} catch {
  this.autoConsumingSessionIds.delete(sessionId);
  this.executionClaims.delete(sessionId);
  // 缺少：this.queueScheduledTaskIds.delete(sessionId);
}
```

- `saveMessage` 抛出（DB 异常）：队列项尚在 PENDING，映射已设 → 后续无关执行先误回写一次；该项真正被消费时会重新绑定并最终收敛，但中间状态错误。
- `handleSendMessage` 内 `prepareMessage`（ws-handler 393 行）抛出：此时队列项已删、消息已落库，catch 又不回补 → 消息孤儿化且映射残留 → 误回写后不再自愈。

说明：`handleSendMessage` 内的受控失败出口（vision/LOCAL 校验 → `requeueIfClaimed`、pendingCancel → R2 回写、submit 拒绝 → `requeueIfClaimed`、正常执行 → finally）均能正确清理映射；缺口仅在「`handleSendMessage` 同步抛出、未走到上述出口」与 insert 自身的 saveMessage/delete 失败。

- 建议：
  1. `autoConsumeQueue` 外层 catch 与 `handleInsertMessage` catch 中补 `this.queueScheduledTaskIds.delete(sessionId)`；
  2. 顺带评估路径 A 是否应在 `sendQueueUpdated` 失败时回补队首（消息丢失为存量问题，可另立跟踪）；
  3. 路径 B 若希望语义与 `requeueIfClaimed` 对齐（失败回队而非孤儿化），可在 catch 中对 `autoSavedMessageId` 场景做回补，属产品决策可选。

### N2【低·备注】R4 禁用路径：检查已入锁事务，但状态写入仍在事务外，极端并发下理论残留

- 文件：`backend-ts/src/user/user.service.ts`、`backend-ts/src/permission/permission.service.ts`
- R4 声称的验收点（`assertNotLastAdmin` 事务内 `FOR UPDATE` 检查、`updateUser` 守卫先行）均已实现，角色变更路径（`changeRolesWithAdminGuard`）检查+写入同事务，完全闭环。
- 理论残留：禁用路径为「锁事务内检查 → 事务提交 → 事务外 `userRepo.updateById(status=0)`」。仅剩两名管理员 A、B 并发互禁时，若双方检查都在对方状态写入提交前完成（检查被锁串行化，但写入在锁释放后），仍可能双双放行。窗口较修复前已大幅缩小，触发需精确并发，按「不必过于苛刻」标准记为备注而非必改项。
- 若日后要彻底关闭：把 `status` 写入并入 `assertNotLastAdmin` 的锁事务（或对目标用户行一并 `FOR UPDATE` 后条件更新）。

## 三、确认已闭环的修复（摘要）

1. **R1 验收点**：`enqueueHead` 带 `scheduledTaskId` 落库；`saveMessage` 失败 / `requeueIfClaimed` / 两处 submit 拒绝均「透传 taskId + 清映射」；`runExecution` finally 按 `terminalPhase` 回写并清映射（521–529 行）。遗漏路径见 N1。
2. **R2**：pendingCancel 分支对绑定映射回写 `CANCELLED` 并删除映射；`onScheduledTaskQueueConsumed` 失败仅告警不阻塞取消收尾。已落库 USER 消息不回补队首，与第 2 轮报告约定的产品语义一致。
3. **R3**：`handleInsertMessage` 在 claim 占位后、saveMessage 前绑定 `queueScheduledTaskIds`，与 autoConsume 对齐；正常执行 / requeue / pendingCancel / submit 拒绝四类出口均能收敛映射。catch 清理缺口见 N1。
4. **R4**：`updateUser` 顺序改为「禁用断言 → 角色守卫事务 → 用户行落库」，守卫失败不再产生半截资料更新；`assertNotLastAdmin` 事务 + `FOR UPDATE` 串行化最后管理员检查。
5. **配套**：V108 迁移、`MessageQueue`/`MessageQueueItem` 类型、create-app `onScheduledTaskQueueConsumed` 增量 patch 接线均正确；`handleEnqueueMessage`（手动入队）不传 `scheduledTaskId`，语义正确。
