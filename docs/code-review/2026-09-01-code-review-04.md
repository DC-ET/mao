## 中

### M1. 停止 / 重试在 WS 重连挂起期间长时间无响应，与「失败会明确提示」的预期不符

- **位置**：`desktop/src/composables/useStreamWS.ts`（`sendReliable`、`connect`）；`desktop/src/composables/useChat.ts`（`stopExecution`、`retryExecution`）
- **背景**：本次将 stop/retry 由 fire-and-forget 的 `send()` 改为 `await sendReliable()`，发送失败时会提示「网络连接不可用，请重试」。
- **问题**：当 WS 处于 **CONNECTING**（断线重连中、TCP 未决）时，`sendReliable` 的 `trySend()` 失败后执行 `await connect()`，会复用 in-flight 的 `connectPromise`；该 promise 仅在 `onopen` / `onclose` 才 settle，而浏览器对 CONNECTING 状态的 WebSocket 没有内建超时（TCP 黑洞场景下可挂起 75 秒甚至更久）。期间：
  - `stopExecution` 卡在 `await wsCancel(sid)`，按钮无 loading、无任何提示；
  - `retryExecution` 已把 `sending.value = true`，输入框被锁住，同样无提示。
- **影响**：网络异常（如代理/LB 静默丢连接）时点「停止」/「重试」，界面像死机一样等 TCP 层超时，之后才弹出提示，用户体验与 CHANGELOG 承诺不符。
- **建议**：`sendReliable` 内 `await connect()` 加超时（10~15s，超时返回 false 走失败提示）；或为停止/重试按钮增加 pending 状态，至少给用户可感知的反馈。

## 低

### L1. 触屏长按的 `suppressNextClick` 可能残留，吞掉下一次点击

- **位置**：`desktop/src/components/task/SideTaskList.vue`（`onTouchStart` / `onTouchEnd` / `handleClick`，本次新增触屏长按功能）
- **问题**：长按 500ms 打开上下文菜单后，`suppressNextClick = true` 依赖「后续合成 click」来消费复位。但 Android Chrome 等浏览器在长按手势后通常**不派发 click**，标志会残留；用户随后点击**任意**任务项时，第一次点击在 `handleClick` 中被静默吞掉（仅复位标志），需要点第二次才能打开任务。
- **建议**：不要依赖 click 消费——在 `touchend` 里若菜单已打开则 `setTimeout(0)` 复位标志；或记录长按触发时间戳，touchend 后短时间窗内（如 300ms）到达的 click 才被抑制。

### L2. `useStreamWS` onopen 中 `ws!.send(auth)` 使用模块级可变引用，与 `disconnect()` 竞态时中断鉴权并挂起调用方

- **位置**：`desktop/src/composables/useStreamWS.ts` `connect()` 的 `ws!.onopen`
- **问题**：onopen 回调先执行 `connectPromise = null`，随后 `ws!.send(JSON.stringify({ type: 'auth', ... }))` 使用**模块级** `ws` 变量。若此刻用户登出/清理逻辑已执行 `disconnect()`（`ws = null`），`ws!.send` 抛 TypeError，onopen 中断，`resolve()` 不会执行——该次 `await connect()` 的调用方（sendReliable → sendMessage / stopExecution 等）**永久挂起**，`sending` 卡 true。后续新的 `connect()` 调用会新建连接（可恢复），但当前这一次操作已卡死。
- **说明**：agent-cli 的 `openOnce` 用局部变量与 `this.send()`（内部判空），无此问题；仅 desktop 端存在。
- **建议**：onopen/onmessage/onclose 回调统一捕获局部 socket 引用（闭包内的 `const socket = ws`），或在回调入口校验 `event.target === ws` 后再操作。

### L3. 微信绑定确认失败重试期间，错误 toast 可能每 3 秒刷屏

- **位置**：`desktop/src/views/settings/WeixinBotView.vue` `pollStatus`
- **问题**：`/weixin/binding/confirm` 失败后保持轮询并每 3s 重试（本次新增的容错，方向正确；后端 confirm 为覆盖式保存，重复调用幂等无副作用）。但每次失败都 `ElMessage.error('绑定确认失败，正在重试…')`，若后端持续不可用，会无限刷屏直到用户关闭弹窗。
- **建议**：连续失败 N 次（如 3 次）后再提示，或仅首次提示并更新状态文案。

### L4. 定时任务启停全局单飞：并发点击其他任务的开关被静默忽略

- **位置**：`desktop/src/composables/useScheduledTasks.ts`（`toggleStatus`、`togglingId`，本次新增防连点）
- **问题**：`togglingId` 为单值 ref，任务 A 的启停请求进行中时点击任务 B 的开关会直接 `return`；B 的开关既没有 disabled 也没有 loading/提示，用户会以为点击无效。
- **建议**：改为 `Set<number>` 按任务 id 记录 in-flight（面板里 `:loading="togglingId === task.id"` 相应改为集合判断），互不影响。

### L5. 窄面板「删除任务」弹窗路径：删除失败静默跳转

- **位置**：`desktop/src/components/task/TaskIndexPanel.vue`（`deleteSessionViaDialog`，本次新增）；`desktop/src/stores/session.ts` `deleteSession`
- **问题**：`sessionStore.deleteSession` 内部 `catch { // ignore }` 吞掉全部错误。弹窗确认后即使 DELETE 请求失败，也会照常切换到下一个会话或跳转首页，用户误以为删除成功。行内确认按钮路径（`confirmDelete`）是同样的既有模式，但弹窗是本次新加的正式入口，建议一并处理。
- **建议**：`deleteSession` 返回 boolean（或抛错），失败时 `ElMessage.error` 并留在原会话。

## 提示（不影响主流程）

### N1. 后端未认证连接发送「无法 JSON 解析」的帧不会立即关闭

- **位置**：`backend-ts/src/session/ws/streaming-ws-handler.ts` `handleTextMessage`
- 本次首帧鉴权后，非 auth 类型的业务帧会 fail-fast close（✔），但 `JSON.parse` 失败的垃圾帧走 `return` 不关闭连接，会一直留到 idle timeout（90s）。相比旧的握手期鉴权，多了一段未认证连接存活期；有 `maxPayload 1MB` 与 idle timeout 兜底，实际风险很低。可考虑 parse 失败时对未认证连接直接 close。
