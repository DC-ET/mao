## 一、低严重度

### L1. 会话停止/中止时的问题不再广播 `ask_user_questions_cancelled`，「等待取消确认」的语义发生回归

- **位置**：`backend-ts/src/harness/tool/tool-dispatcher.ts:157`、`backend-ts/src/harness/tool/ask-user-questions-registry.ts:93-99`
- **现象**：改造后 `waitForAnswer()` 的终态只有两类：
  - `answered=true`：正常应答，以及 `failAllForSession()` 在会话停止/中止/重试时以 `resolve('{"error":"Session cancelled"}')` 结束的路径（registry 第 97 行）；
  - `answered=false`：仅剩「无 pending 条目」和「应答超时」。
  
  改造前 `result.includes('"error"')` 会命中 Session cancelled 并广播 cancelled 事件；改造后该场景返回 `answered=true`，**不再广播**。
- **影响评估**：
  - 对 LLM 注入的结果内容正确（`{"error":"Session cancelled"}` 如实传递），核心修复目标（正常应答不再被误判为取消）达成；
  - 前端提问卡片在各终端场景由 phase 驱动的 `clearAskQuestions()` 兜底清理（useStreamWS.ts:342/585/740、useChat.ts:683 停止按钮），实测不会残留卡片，**不构成功能性 bug**；
  - 但 SideChatPanel.vue:653、SubagentChatPanel.vue:183 的注释明确写着「Keep the panel until the server confirms completion with ask_user_questions_cancelled」——即部分面板把该事件当作权威完成信号。停止/中止场景下这一信号消失后，只能依赖 phase 事件兜底，多端订阅同一会话时其余端的清理时序从「事件级」退化为「phase 级」。
- **建议**：在 registry 中将「取消/失败」与「应答」区分为不同终态（如 `AskUserAnswersResult` 增加 `cancelled` 标记，或 failAll 走 reject），让 dispatcher 能继续区分广播时机；若维持现状，建议更新上述两处前端注释并在 registry 补注释说明「failAll 走 answered=true 通道」是有意设计。

### L2. 后台任务结果双重截断标记与「整体限长后非法 JSON」

- **位置**：`backend-ts/src/harness/core/background-task-manager.ts:96-115`
- **现象**：`normalizeResult()` 先把 `output` 截到 10000 字符并追加 `... [truncated]`，重组 JSON 后又对全文按同样的 10000 截断。当 output 接近上限时，JSON 头部几十个字符的开销会把已经截断过的 output 再切一刀，尾部出现两个连续/嵌套的截断标记，且最终文本不是合法 JSON。单测注释已声明这是有意取舍（注入给模型阅读，不要求可解析），信息量足够，不算功能性错误，但输出观感较差且可能干扰模型对截断量的判断。
- **建议**（可选优化）：整体限长时为头部结构预留空间（如 `MAX_RESULT_LENGTH - 头部长度` 反推 output 截断点），保证最终文本要么是完整 JSON、要么只带一个截断标记。

### L3. EmptyResponseExhaustedException 穿透依赖 `instanceof`，对跨模块副本脆弱

- **位置**：`backend-ts/src/harness/llm/openai-llm-adapter.ts:189、347、586`
- **现象**：三处透传判断均为 `e instanceof EmptyResponseExhaustedException`。单包架构下没有问题；若未来出现双版本打包/模块多副本共存（Error 子类 instanceof 依赖具体构造函数引用），异常会回退为旧路径——因 message 不含现有关键词大概率仍走 `retryable=false`，实际退化后果有限，但属于隐式耦合。
- **建议**（防御性，可不做）：异常类增加判别标识字段（如 `readonly isEmptyResponseExhausted = true`），判断处兼容 `name === 'EmptyResponseExhaustedException'` 兜底。

## 二、提示级（健壮性 / 可维护性）

### P1. `handleAskUserQuestionsResult` 未校验 answers 类型，序列化结果类型不稳定

- **位置**：`backend-ts/src/session/ws/streaming-ws-handler.ts:548-549`
- **现象**：`data.answers == null` 时正确产出 `{"answers": []}`；但若客户端传非数组（对象/字符串），会产出 `{"answers": {}}`、`{"answers": "xx"}` 等，LLM 收到的 answers 字段类型不确定。当前桌面端 QuestionPanel 只发数组，不会触发。
- **建议**：序列化前校验 `Array.isArray(data.answers)`，非数组一律归一为 `[]` 或拒绝。

### P2. `normalizeResult` 以「含 string 类型 output 字段」识别 shell 结果，未来扩展易误伤

- **位置**：`backend-ts/src/harness/core/background-task-manager.ts:100`
- **现象**：判定条件是 `parsed.output` 为 string。已核实当前生产者只有两类（CLOUD `shell-session-tool.ts` 异步分支、桌面端 `localShell.cjs` await_async），均匹配该结构；错误负载 `{error}` 无 output 字段会原样透传，符合预期。但未来若有其它后台任务恰好返回含 `output` 字段的 JSON，会被强行重组为 `{exit_code, completed, output}` 三元组而丢失其余字段（exit_code 缺失还会默认成 -1）。
- **建议**：可在 TaskEntry 上携带任务类型标记做精确归一化；当前单一生产者场景可接受。

### P3. 回补队列时 images 经二次序列化，与出队时的原文非字节一致

- **位置**：`backend-ts/src/session/ws/streaming-ws-handler.ts:263-266`
- **现象**：`requeueIfClaimed` 用 `JSON.stringify(images)`（来自 WS 消息体解析后的数组）回补，而 autoConsumeQueue 出队时保存的是 `head.images` DB 原文。两者语义等价（imageList 即解析自 head.images），仅 JSON 格式化细节可能差异，DB 层无影响。另外 `enqueueHead` 以「队首最小 sortOrder − 1」实现插头，多次回补会使序号持续递减，理论上存在下界风险但实际不可触达。
- **建议**：无需修改；追求严谨可将 head.images 原文透传进闭包避免二次序列化。

## 三、已验证无问题的关键点（供复核参考）

以下高风险改动点经过调用链逐一核查，确认正确：

1. **空响应耗尽异常穿透**：修复的真实痛点是「带 thinking 输出的空响应轮」——旧代码在 `processStreamBody` 因 `emitted=true` 把 onComplete 抛出的普通 Error 包装成 `StreamInterruptedAfterOutputException`，被判定可重试后叠加整轮流重试（最多再 10 轮）。新代码三处拦截闭环：① `processStreamBody` catch（347 行）原样 rethrow 不包装；② `stream()` 主循环 catch（188-191 行）优先于 retryable 判定直接 `onError(e)` 终结，不触发 `onStreamReset`；③ `isRetryableNetworkFailure`（586 行）兜底防其它入口误判。AgentLoop 侧 onError 包装出的 `LLM call failed: ...` 由 runExecution 正常落 FAILED 并向用户展示原始 message，链路完整。
2. **自动消费回补**：autoConsumeQueue 占位→出队→落库→延迟提交（executionClaimHeld=true）之后，handleSendMessage 内所有校验失败早退出口均已接入 `requeueIfClaimed`（content 缺失/session 不存在/vision 两项/LOCAL 未连接/线程池拒绝）；`isAutoConsume` 分支跳过重复落库；submitExecution 拒绝路径同步清理 autoConsumingSessionIds；requeueIfClaimed 自身异常有内部捕获不影响主流程。手动「立即执行」路径（replaceExecution=true，820-857 行）的消息是从队列删除而非 dequeue，本就无需回补，未被波及。注：saveMessage/prepareMessage 若抛异常导致 claim 泄漏属改动前已存在的行为，不在本次范围。
3. **后台 shell 结果契约**：CLOUD 异步分支返回 `{exit_code, completed, output, truncated}` 与归一化期望完全匹配；LOCAL 路径桌面端 `formatExecResult`（localShell.cjs:360）含 string 类型 output，错误负载无 output 字段原样透传；output 单独限长 10000 与同步路径预览上限（shell-session-manager maxPreviewChars=10000）量级对齐。
4. **子代理计数跨轮保留**：`onLlmStreamReset` 仅在适配器整轮流重试（truncated/streamError）时触发，此时该轮 toolCalls 尚未真正执行，保留 `seenToolCallIds` 可对重试轮重放的相同 id 自然去重；正常轮间不触发 reset，跨轮累计语义成立；流结束用完整参数二次 `onToolCallStart` 刷新的路径也被既有去重覆盖。toolCallCount 的消费方（background-subagent-manager 快照/结果统计/subagent-execution-recovery）均为累计口径，无副作用。
5. **测试**：新增/调整的 4 个 spec 全部通过；全量 124 个测试文件、850 个用例通过；tsc 构建无错误。
