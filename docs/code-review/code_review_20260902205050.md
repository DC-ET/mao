## 3. UI 与交互体验（重点）

### P0-1 全屏重绘风暴：每次输出都清一次屏，连 scrollback 一起清

Ink 3 的核心渲染逻辑（`node_modules/ink/build/ink.js:72-76`）：

```js
if (outputHeight >= this.options.stdout.rows) {
  this.options.stdout.write(ansiEscapes.clearTerminal + this.fullStaticOutput + output);
  ...
}
```

`clearTerminal` = `\x1b[2J\x1b[3J\x1b[H`，其中 **`3J` 清除 scrollback（滚动历史）**。一旦整树输出高度超过终端行数（长会话必然超过），每一帧都走这条路径。

实测（`rows=30 cols=100`，喂 60 次 `content_delta`）：

| 指标 | 实测值 |
|---|---|
| 输出总字节 | 427,986 |
| `\x1b[2J`（清屏）出现次数 | **60** |
| `\x1b[3J`（清 scrollback）出现次数 | **60** |
| 平均每次 `content_delta` 输出字节 | **6,319**（min 1,033 / max 15,284） |
| 前 10 次均值 → 后 10 次均值 | **2,036 → 10,269**（随历史线性增长） |

后果三重：长会话越用越卡、屏幕持续闪烁、**终端原生滚动历史被反复清空**（而 `CHANGELOG.md:745` 恰恰把"不使用备用屏、scrollback 可回看"当作卖点写进了发版说明 —— 实际效果被 `3J` 抵消了）。在 SSH / 低带宽下，每次 token 增量都要重传整屏，体验直接崩坏。

叠加放大器：`tui/ink-renderer.ts:308-311` 的 spinner 定时器 **80ms** 一次 `flush()`，`liveRunning` 期间即整树 rerender —— 即使模型一个 token 都没吐，也在每秒 12.5 次全屏重绘。

> 修复方向见 §8 阶段一（推荐先止血：已完成回合不进 `<Static>`，直接 `writeToStdout` 落为普通滚动输出，把 live 区高度压到远小于 `rows`，彻底避开 `outputHeight >= rows` 分支）。

### P0-2 `/clear` 之后历史复活

`tui/ink-renderer.ts:160-174` 的 `clearAll()` 写了 `\x1b[2J\x1b[H` 并清空自己的 `staticRounds`，但 **Ink 内部的 `fullStaticOutput` 只累加、永不清空**。于是清屏后的每一次 `clearTerminal` 分支都会把已清历史重新打回屏幕。

实测：`[CLEARED]` 标记之后，`MARKER-ROUND1-ASSISTANT` 又出现 **26 次**、`WELCOME-BANNER` **26 次**、`2J`/`3J` 各 26 次。

即 `/clear` 这个命令目前是**语义错误**的：它清了一瞬间，随后历史全部复活。同一根因，与 P0-1 共享一套修复（不再依赖 Ink 的 `<Static>`），或退一步用 unmount + 重新 mount Ink 实例实现真清屏。

### P0-3 输入框没有光标，也没有行编辑

`tui/ink-input.tsx:71-172` 的 `useInput` 全部分支：

| 按键 | 行 | 行为 |
|---|---|---|
| `ctrl+c` | 75 | 中断 / 双击退出 |
| `ctrl+d` | 80 | **仅**草稿为空时退出 |
| `escape` | 88 | **仅**关闭补全面板 |
| `return` | 96 | 提交（含续行判定） |
| `upArrow` / `downArrow` | 120 / 130 | 历史或面板导航 |
| `tab` | 150 | **仅**面板内选中 |
| `backspace` \| `delete` | 159 | 恒为 `draft.slice(0, -1)` |
| 其他可见字符 | 166 | 追加到末尾 |

**没有光标概念**。左右方向键、Home/End、Ctrl-A/E/K/W/U、Alt-B/F、向后 Delete 全部不支持。

实测：喂入 `hello world` + `←←←` + `XYZ` + `Home` + `Ctrl-A` + `Ctrl-K` + `Ctrl-U` + `Enter`，提交结果是 `"hello worldXYZ"` —— 所有光标移动与行编辑键被静默丢弃，字符一律追加到末尾。

另外 `backspace` 按 UTF-16 code unit 切片，删 emoji 会切出半个代理对码点，产生乱码字符。

对一个以"和模型对话"为核心的 CLI 来说，输入框是**使用频率最高的 UI 元件**。当前状态下用户打错一个字就只能整行退掉重打，这是本次评审在体验维度上最值得投入的一项。

### P1-4 多行粘贴：内容进去了，但换行语义混乱

Ink 3 的 `use-input.js:56` 只把 `input === '\r'` 判为 return。因此：

- 单 chunk 粘贴 `line1\nline2\nline3`：全部进 draft，提交时 LF 保留 —— 行为可接受。
- 粘贴内容以 **CR** 分行（真实终端粘贴很常见）：实测喂 `AAA\rBBB\rCCC` 再输入 `ZZZ\r`，提交结果为 `"AAA\rBBB\rCCCZZZ"` —— **裸 CR 被当普通字符塞进消息体，并且第二次输入被拼接到同一条消息里**。用户以为发了两条，实际发了一条带控制字符的。

根因是完全没有 bracketed paste（`\x1b[?2004h` / `\x1b[?2004l`）支持，CLI 无法区分"用户敲的回车"与"粘贴内容里的换行"。

### P1-5 `--ascii` 不彻底

`--ascii` 只切换 `ui/symbols.ts`（`⏺→*`、`⎿→|`、`✔→+`、`❯→>`、Braille spinner→`|/-\`），而 Ink 的 `borderStyle="round"` 边框是硬编码 Unicode，共 5 处：`tui/ink-input.tsx:184,206`、`tui/app.tsx:80,91`、`tui/widgets.tsx:12`。

实测（`asciiOnly=true`）：`╭` 7 次、`╮` 7、`╰` 7、`╯` 7、`─` 1214、`│` 24；而 `⏺ ⎿ ✔ ❯ ⠋` 全部为 0。

即符号换了、圆角框还在。对不支持 Unicode 的终端 / 日志采集场景，这个 flag 的承诺没有兑现。

### P1-6 `announce` 截断按"调用次数"而非行数，且会污染对话记录

这一项与直觉相反，需要按实测更正常见判断：

- `tui/ink-renderer.ts:19` `ANNOUNCE_MAX = 8`，`:570-576 pushLiveAnnounce` 按**数组元素个数**（即 `announce()` 调用次数）裁剪，不看行数。
- 实测 A：单次 `announce()` 传入 20 行文本 → 20 行全部显示，不截断。因此 `/help`（`repl.ts:25-43 SLASH_HELP` 是单次多行 announce）**本身不被截断**。
- 实测 B：连续 12 次单行 `announce()` → 屏幕只剩 `SEQ-05..SEQ-12` 共 8 条，**前 4 条被静默丢弃**。被截断的是"连续多条提示"场景（如排队提示叠加、多条警告连发）。

更麻烦的是 `announceBuffer`（`:48`）在 `finish()`（`:463-466`）时会被回灌进 `<Static>` 成为 `kind:'sys'` 条目 —— 实测最后一屏可见 `HELPLINE-01..12` 与 `SEQ-01..12` 全部落进 static。**`/help` 全文会在下一轮对话结束后被永久写进对话记录**，一次查帮助污染整条会话历史。

正确做法：`ANNOUNCE_MAX` 按行数裁剪；一次性提示（help、补全说明）与需要留档的系统消息（警告、错误）分成两类，前者不进 static。

### P1-7 REPL 与 InkInput 的续行逻辑重复且互相打架

`repl.ts:44-47` 与 `ink-input.tsx:214-217` 各有一份同名 `fenceOpen()` 实现。InkInput 先消费一遍（`:96-115` 判行尾 `\` 与未闭合 ```` ``` ````），再交给 `repl.ts:125-137 handleSubmit` 又判一遍。

实测：连续 `onSubmit('foo\\')` 然后 `onSubmit('第二条正常消息')` → `SessionRunner` 只收到**一条** `"foo\n\n第二条正常消息"`，还多出一个空行。用户以为发了两条消息，实际被合并。

两层各自维护同一份状态机是典型的重复真相源。建议只保留 InkInput 一份（它离键盘最近），REPL 侧不再判定。

### P2-8 footer 与下一帧 static 卡片黏行

实测输出中出现 7 次 `A · m · CLOUD╭─────────╮\r\n│ WELCOME │` —— footer 行末缺换行，与下一帧 static 卡片首行黏连成一行，视觉上是明显的渲染错位。

### P2-9 颜色开关对 TUI 部分失效

`tui/ink-renderer.ts:101`：

```ts
const color = shouldUseColor({ colorFlag: undefined, printMode: false, stdoutIsTty: true });
```

`colorFlag` 被硬编码为 `undefined`，即 `--color` / `--no-color` 解析出来的 `cfg.colorFlag` **根本没传进渲染器**。目前只有 `NO_COLOR` 环境变量因为函数内部单独判断而生效。修复只需把 `cfg.colorFlag` 透传，但要注意 Ink 内部走 chalk@4，需一并处理其颜色级别。

### P1-10 模态单槽互踢，危险审批误按即生效

`tui/ink-renderer.ts:236-260`：`requestApproval` 若发现当前 modal 是 `ask` 类型，会先 `resolveAsk(requestId, [])` —— **以空答案替用户提交**，把提问框踢掉。审批走 FIFO `approvalQueue`，但 ask 没有队列。用户会看到自己正在填的答案被静默清空提交。

`tui/modals.tsx:158-180 ApprovalModal` 的 `y` / `n` / `a` / `Esc` 单键即生效，无二次确认 —— 对 `a`（always，等于本进程内该类工具全部免审，见 §6）这种不可逆授权，误触代价过高。

两个 modal 的 `useInput` 都没传 `isActive`，靠 `app.tsx:102 enabled={!modal}` 与 InkInput 做互斥 —— 能工作但很脆，属于隐式契约。

`AskModal` 的交互也绕：数字键直接选、但要"按 c 进自定义"（`modals.tsx:82-84, 105-118`），两种输入模式混在一个框里且没有可见提示。

### P2-11 其他交互细节

- `tui/ink-input.tsx:5` `HISTORY_MAX = 50`，历史仅存内存、不跨进程持久化 —— 关掉 CLI 再开，上一次的输入全丢。`historyDraft` 在补全面板打开时被吞掉。
- `repl.ts:220-227` 用 `setInterval(..., 200)` 轮询 `closing` 标志来保活 Promise —— 轮询反模式，应改为在关闭点 `resolve`。
- 斜杠命令**三处重复维护**：`repl.ts:25-43 SLASH_HELP` 文本、`ui/slash-complete.ts:7-22 SLASH_ITEMS`（13 条）、`repl.ts:239-322 handleSlash` switch。加一条命令要改三处，漏一处就是"补全里有但执行报未知命令"或"帮助里没写"。

## 4. 代码逻辑与正确性

### P1 参数解析：顺序敏感 + 缺值静默吞掉

`args.ts:96-136 parseRawArgs` 对 `--flag value` 采用"下一个 token 不以 `-` 开头就吃掉"策略。实测 `parseCliConfig` 结果：

| 输入 | 实际解析 | 期望 |
|---|---|---|
| `['-p','--local','写点东西']` | **`local=false`, `prompt=''`**, print=true | local=true, prompt='写点东西' |
| `['--local','-p','写点东西']` | 正常 | 正常 |
| `['--model','-foo']` | `model=undefined`，`-foo` 落进 prompt | 报错或接受 |
| `['--max-duration','-1']` | `maxDur=undefined` 静默丢弃 | 报错 |
| `['-p','hello','--agent']` | `agent=undefined`，无任何报错 | 报错"缺少值" |

三类缺陷叠加：**顺序敏感**（`-p` 把后面的 `--local` 当成自己的值吃了）、**负数与 `-` 开头的合法值无法传入**、**缺值静默忽略**。第一行那个例子尤其糟 —— 用户明明写了 `--local`，CLI 静默按 CLOUD 跑，且 prompt 也丢了。

修：为每个 flag 声明是否带值（布尔表 / 值表），缺值即报错，支持 `--flag=value` 与 `--` 终止符。

### P1 `session_already_running` 的提示与行为相反

`session-runner.ts:346-380` 的实现早已改为"等占用执行结束后以新 `executionId` 自动重发"，而 `tui/ink-renderer.ts:407-408` 仍打印：

### P1 waiter 泄漏风险

## 5. LOCAL 执行与安全边界

这一节是本次评审除 UI 外风险最集中的部分。所有条目都有 desktop（`desktop/electron/main.cjs`）或后端（`backend-ts/src/harness/`）的对照实现，可以直接对齐，不需要重新设计安全模型。

### 高危

**5.1 `local/tools/shell.ts:22-33` — 从 cwd 候选路径 `require()`，等于任意代码执行**

```ts
const candidates = [
  path.resolve(__dirname, '../../../vendor/localShell.cjs'),
  path.resolve(__dirname, '../../../../desktop/electron/localShell.cjs'),
  path.resolve(__dirname, '../../../../../desktop/electron/localShell.cjs'),
  path.resolve(process.cwd(), '../desktop/electron/localShell.cjs'),
  path.resolve(process.cwd(), 'desktop/electron/localShell.cjs'),
];
for (const c of candidates) if (fs.existsSync(c)) return c;
```

后两个候选依赖 `process.cwd()`。在任意目录（比如 clone 下来的第三方仓库）启动 CLI，只要该目录下存在 `desktop/electron/localShell.cjs`，就会被 `require` 进受信 CLI 进程执行。修：只保留 `__dirname` 相对的包内 `vendor/localShell.cjs`，解析失败直接报错，不做 cwd / 跨仓回退。

**5.2 `local/executor.ts:172-179` — shell 审批可被绕过**

```ts
return this.shell.handle(args, { conversationId: sessionId, workspace, needApproval: false });
```

硬编码 `needApproval: false` 且不传 `approve` 回调，导致 `vendor/localShell.cjs:354-358 ensureApproved` 恒为 true。后果：`action:'write_stdin'` 与**复用已存在 session 的后续命令全部免审**。desktop 侧 `main.cjs:1771-1778` 明确传了 `approve: ensureShellApproval(...)`，并在注释里把"首次批准不得解锁后续命令"写成不变量 —— CLI 违背了这条不变量。

**5.3 `local/deny-list.ts:33-41` — deny-list 不看 `input` 字段**

`describeToolForDeny` 采样的键是 `command` / `path` / `file` / `content` / `old_string` / `new_string`，**不含 `input`**。因此 `{action:'write_stdin', input:'rm -rf /'}` 完全不经过危险命令检测。与 5.2 组合成一条完整绕过链。

**5.4 `local/paths.ts:34-42` — 无路径沙箱**

```ts
if (path.isAbsolute(expanded)) { ... return expanded; }   // 绝对路径直接放行
if (!workspace) return expanded;
return path.join(workspace, expanded);                     // 相对路径不判越界
```

`../../etc/passwd`、`/etc/shadow` 均可达。后端有等价沙箱 `harness/safety/path-sandbox.ts:23-44`（`path.relative` 判越界并抛 SecurityException），CLI 无。

**5.5 `local/executor.ts:105-107` + `local/approval.ts:30-33` — 服务端可读本机任意文件**

`workspace = d.workspace || this.opts.workspace` 意味着服务端下发的 workspace 可以覆盖本地校验并信任过的目录。而 `MUTATING = ['shell','write_file','edit_file']` + `mcp__*`，**`read_file` / `glob` / `grep` 不受 trust 门禁**。两者相乘：服务端把 workspace 设为 `/`，即可读取本机任意文件而不触发任何审批。修：workspace 以本地启动参数为唯一权威（服务端值只做校验/告警），并把读类工具纳入信任边界。

**5.6 `local/executor.ts:199-215` — `skill_sync_done` 缺 `syncId`，带技能的 LOCAL 会话必失败**

CLI 回的是 `{type, sessionId, success[, error]}`，没有 `syncId`；而后端 `backend-ts/src/session/ws/streaming-ws-handler.ts:1076-1084` 自 commit `4162ff72`（2026-08-30「核心逻辑 BUG 全量扫描修复」L-8）起要求 `reportSyncId === pending.syncId`，为空时只 `console.warn` 并忽略 → `syncSkillsToClient`（`:1126-1157`）60s 超时 → `runExecution`（`:404-408`）走 `finishFailedSession` 回 `Skill sync failed or timed out`。

同文件 `:217-228` 的 `mcp_tools_report` **反而正确带了 syncId**，说明是漏改而非设计。

需要如实指出的是：**desktop 侧 `useStreamWS.ts:120-150 sendOrQueueSkillSyncDone` 同样不带 syncId**（全仓 grep 确认只有 MCP 那处传了），后端自身单测 `streaming-ws-handler.spec.ts:556` 也只发不带 syncId 的帧。所以这是"后端单方面加了校验、两个客户端都没跟上"的共性缺陷，不是 CLI 独有 —— 修的时候应该三处一起对齐。

**5.7 `local/skills.ts` — zip-slip + 隐藏运行时前提 + 凭据外泄**

- `:11-19 unzipTo` 用 `python3 -c "...zipfile...extractall(...)"`，`extractall` 不做 zip-slip 校验，服务端下发的恶意 zip 可通过 `../` 条目写出 skills 目录。
- **python3 是隐藏的运行时前提**：`scripts/install-mao-agent.sh:19-23` 只检查 node ≥ 20，未检查 python3。缺 python3 → 技能同步失败 → 后端把会话判 FAILED。desktop 侧用的是 `adm-zip`（`main.cjs:729`）。
- `:29-36 syncUrl` 若为绝对 URL 则直接请求并附 `Authorization: Bearer <token>` —— 服务端被篡改即可让 CLI 把 JWT POST 到任意主机（SSRF + 凭据外泄）。`tools/mcp.ts:122-156 connectHttp` 同理。

**5.8 `local/tools/mcp.ts:96-101` — MCP stdio 启动无约束**

用服务端下发的 `command` / `args` 直接 `spawn`（远端可指定任意可执行文件），且 `env: {...process.env, ...server.env}` 把含 token 的**全部环境变量**交给子进程。此路径无 deny-list、无路径校验、无审批。

### 中危（择要）

- `local/trust.ts:9-13` 信任判定是纯字符串前缀比较，无 `realpath` → 工作区内 symlink 指向外部目录不受限；大小写不敏感文件系统下语义不一致。

## 8. 重构路线图

分四期。每期都可独立发版，不需要一次性重写。

### 阶段一：渲染层止血 + 删死代码（收益/成本比最高）

**1.1 解 `clearTerminal` 风暴（P0-1 / P0-2）。** 三条路可选：

| 方案 | 做法 | 评价 |
|---|---|---|
| (a) 升级 Ink 4/5 + ESM | 改 `tsconfig module`、把 CJS `require` 改 import | 根治，并解掉 react-reconciler peer 冲突；但工作量大，需连带改构建与 `bin/` 入口 |
| **(b) 已完成回合不进 `<Static>`** | 完成的回合用 `writeToStdout` 直接落为普通滚动输出，live 区只渲染当前回合，把 live 高度压到远小于 `rows` | **推荐先做**：改动集中在 `ink-renderer.ts`，彻底避开 `outputHeight >= rows` 分支，同时顺带让 `/clear` 语义正确（不再依赖 `fullStaticOutput`） |
| (c) 弃 Ink 自接管重绘 | 回到自研 | 与 Ink 迁移的初衷相反，不推荐 |

建议 **(b) 立即止血，(a) 作为中期目标**。同期把 spinner 从 80ms 降频（或仅在 live 高度较小时刷新）。

**1.2 删死代码层。** 移除 `render/repl-renderer.ts`、`ui/composer.ts`、`ui/status-line.ts`、`ui/keys.ts`、`ui/box.ts` 未用导出、`util/ansi.ts` 的 markdown/行数计算、`session-runner.ts` 的 `resultToExitCode`/`summarizeMessages`、`InkTuiHandle`/`InkRendererLike` 空壳与 `TuiAppProps` 未消费 props、`tools/shell.ts:54 hostHome`、`args.ts PHASE3_FLAGS`、`local/paths.ts:36-38` 无意义分支。同步删掉对应测试，把测试预算移到 TUI 快照 / REPL 状态机 / 审批流 / 断线重连 / SIGINT。

**1.3 给 `SessionRunner` 加 `setRenderer()`**，删掉 `commands/chat.ts:209` 的私有字段穿透。

**1.4 修 P0-5 文案**：`ink-renderer.ts:407-408` 改为"会话忙，已排队，稍后自动重发"。顺手统一 `handleAlreadyRunningEvent` 两分支走 `resetRound()`，补上 REPL 分支漏掉的 waiter 归还。

### 阶段二：输入框重构（体验主战场）

- 引入真正的光标 state，支持 ←/→、Home/End、Ctrl-A/E/K/W/U、Alt-B/F、向后 Delete。
- 删除按 grapheme 而非 UTF-16 code unit（修 emoji 截断）。
- 开启 bracketed paste（`\x1b[?2004h`），把粘贴内容与键入区分开，正确处理多行与裸 CR。
- 历史持久化到 `~/.mao/agent-cli/history`（0600），修 palette 打开时吞 `historyDraft`。
- 续行 / `fenceOpen` **只保留 InkInput 一份**，REPL 侧不再判定（修 P1-7）。
- 补矮终端 / raw-mode 不可用时的 readline 降级（兑现 UX:468 的承诺）。

### 阶段三：LOCAL 安全边界对齐 desktop / 后端

按 §5「高危」五条优先：`shell.ts` 只从包内解析 → 传入 `approve` 回调让每次 exec/write_stdin 重新过策略 → deny-list 采样补 `input` → 引入与 `path-sandbox.ts` 同语义的沙箱 → workspace 以本地参数为唯一权威且把读类工具纳入信任门禁 → `skill_sync_done` 补 `syncId`（**同时修 desktop 与后端单测，三处一起对齐**）→ skills 解压换成带路径校验的 Node 实现（或至少校验每个条目）+ `install-mao-agent.sh` 声明 python3 前提。

中危项按 §5 清单逐条处理，重点是 `truncate.ts` 的无条件明文落盘、`always` 授权粒度、`globToRegExp` 的 shell 元字符跨越。

**同期把 CLI 与 desktop 的同源逻辑下沉共享**：纯 Node 部分（paths / files / search / mcp / skills / local-skills）抽到 `shared/`，两端 import；`vendor/localShell.cjs` 收敛到 `shared/` 或构建期生成，去掉手工 `cp`（CI 的 `cmp` 校验思路可保留作为兜底）。以 CLI 的 `rg --json` 实现为基准统一 search。

### 阶段四：功能与文档收口

- **`--thinking` 与 `ui.showTurnDividers` 二选一**：要么在 Ink 里实现，要么从 flag / help / config 中彻底删除。不做半吊子。
- **`--ascii` 补齐**：5 处 `borderStyle="round"` 按 `asciiOnly` 切 `classic` 或无边框。
- **参数解析重写**：声明式 flag 表（带值 / 布尔），缺值报错，支持 `--flag=value` 与 `--`，修顺序敏感与负数值。
- **`--help` 信息架构**：分组 + 默认精简 + `--help --all` 展开全量。
- **颜色贯通**：`cfg.colorFlag` 透传进 `InkTuiRenderer`，统一处理 Ink 内部 chalk@4 的颜色级别。
- **模态队列化**：ask 也进队列，去掉互踢；危险审批加显式二次确认；两个 modal 的 `useInput` 传 `isActive` 把互斥显式化。
- **announce 语义修正**：`ANNOUNCE_MAX` 按行数裁剪；一次性提示（help/补全）不回灌进 static 对话记录。
- **斜杠命令单一数据源**：收敛到 `ui/slash-complete.ts` 的清单，help 文本与 `handleSlash` 分发均由清单生成。
- **删 `&local=1`**（确认后端确无消费点后）。
- **`readStdin` 在 `end` 事件立即结算**，去掉固定 2s 等待。
- **测试补齐**：`ink-testing-library` 键序测试、`handleSlash` 纯函数单测、fake timers 驱动重连、`resolveConfig` 优先级、`auth/token.ts` 与 `config-store.ts` 安全行为；CI 加 node 22 matrix 与 mock 后端冒烟。
- **文档同步**（需用户授权才动文件）：两份设计文档加「状态：以 CHANGELOG 为准」或按 §6 表格逐条回写；补记 Ink/React 引入；0.1.x 版本在对应小节标注；手册补完整 flag 表、13 条斜杠命令、Ink 键位表、python3 前提、旧路径迁移说明；重写"备用屏"那一段。

### 风险与不做事项

- **不改后端核心逻辑**（本次约束）。§5.6 的 `syncId` 虽然涉及后端单测，但修 CLI/desktop 侧带上 `syncId` 即可，无需动后端校验逻辑。
- **Ink 4/5 升级是构建形态变更**（CommonJS → ESM），会影响 `bin/` 入口与 `npm pack` 产物。不建议与阶段一的止血捆绑，应单独一期并跑通 `agent-cli-e2e.sh`。
- **阶段一的 (b) 方案会改变输出形态**（完成回合变成普通滚动文本）。需要人工在真实终端确认视觉效果，`--ascii`、窄终端、`-p json` 三种模式都要过一遍。
- **删死代码会带走约 24 个测试用例**，测试总数会从 113 降下来 —— 这是正确的方向（去掉虚假信心），但需要在 CHANGELOG / PR 描述里说明，避免被误读为覆盖率退化。
- `tools/mcp.ts` 的帧格式问题**尚未实机联调确认**，动手前应先跑一次真实 MCP server 验证，再决定是改 NDJSON 还是直接换官方 SDK。
