## 一般问题

### 1. 聚焦模式主任务状态显示忽略服务端 treeRunning/treeFailed，边路任务未加载时会显示错误状态

- 位置：`desktop/src/components/task/TaskIndexPanel.vue:611-635`
- 位置：`desktop/src/components/task/TaskIndexPanel.vue:639-653`
- 位置：`desktop/src/components/task/TaskIndexPanel.vue:870-875`

**问题说明**：

聚焦模式排序仍通过 `sessionToFocusCandidate()` 使用服务端下发的 `treeRunning` / `treeFailed` 聚合字段：

- `desktop/src/components/task/TaskIndexPanel.vue:477-482`
- `desktop/src/utils/focusSort.ts:58-69`

后端 `/v1/sessions?status=ACTIVE` 也会通过 `enrichSessions()` / `applySessionListSignals()` 为主任务返回整棵任务树聚合状态：

- `backend-ts/src/session/session.routes.ts:112-126`
- `backend-ts/src/session/session.routes.ts:222-224`
- `backend-ts/src/session/session-vo.ts:404-452`

但本次改动后的 `focusStatusLabel()`、`focusStatusClass()`、`effectivePhaseClass()` 判断边路任务运行/失败时只读取 `sessionStore.getSideTasks(parentId)`。如果聚焦模式列表中某个父任务的边路任务列表尚未被展开或加载，`getSideTasks()` 会返回空数组，此时即使服务端 VO 已标记 `session.treeRunning === true` 或 `session.treeFailed === true`，主任务标签/样式仍可能显示为“空闲”或“已完成”。这会造成同一个任务在排序上被提升到“失败/运行中”优先级，但状态文案和状态类却按空闲/完成展示，影响聚焦模式对当前任务状态的判断。

**修复建议**：

在状态展示逻辑中继续将服务端聚合字段作为兜底或并集判断，例如：

- `failedSide` 判断改为 `session.treeFailed || sides.some(...)`；
- `runningSide` 判断改为 `session.treeRunning || sides.some(...)`；
- 当 `session.treeRunning === true` 但本地 `sideTaskCache` 未加载、无法拿到具体边路任务 `startedAt` 时，可回退显示 `运行中 ${formatDurationSince(session.updatedAt || session.createdAt)}`，或只显示“运行中”；
- `effectivePhaseClass()` 也应在本地 side task 列表为空时回退使用 `session.treeRunning` / `session.treeFailed`，保持与排序口径一致。

## 轻微问题

### 1. WebSocket 重连/订阅运行中会话时，运行时长会从客户端当前时间重新计算

- 位置：`desktop/src/composables/useStreamWS.ts:512`（`session_status` 中 RUNNING 使用 `new Date().toISOString()`）
- 位置：`desktop/src/composables/useStreamWS.ts:681`（`session_snapshot` 中 RUNNING 使用 `new Date().toISOString()`）
- 相关后端位置：`backend-ts/src/session/ws/streaming-ws-handler.ts:216-220`
- 相关后端位置：`backend-ts/src/session/ws/streaming-ws-handler.ts:337-339`

**问题说明**：

后端会在 `SessionVO` 和边路任务列表中返回真实 `startedAt`，但当前 WebSocket 的 `session_status` / `session_snapshot` 事件只携带 `phase` 和 `executionId`，没有携带服务端真实 `startedAt`。前端收到 RUNNING 状态后用客户端当前时间写入 `startedAt`。

这会导致用户刷新页面、WebSocket 重连或重新订阅一个已运行较久的任务时，聚焦模式/边路任务列表中的“运行中 X”从当前时刻重新开始计时，而不是显示真实运行时长。该问题不影响任务执行本身，但会影响运行状态信息的准确性。

**修复建议**：

优先让后端 `session_status` / `session_snapshot` 附带服务端 `startedAt`，前端使用事件中的真实时间。若短期不改协议，前端至少不要用当前时间覆盖已有的 `startedAt`；只有本地实体没有 `startedAt` 时才临时兜底。
