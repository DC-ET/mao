## 中等严重程度

### 1. CLOUD 自动提交对重命名文件只检查新路径，可能把敏感文件内容发送给模型

**代码位置**

- `backend/src/main/java/cn/etarch/mao/file/service/GitWriteOperationService.java:171-183`
- `backend/src/main/java/cn/etarch/mao/file/service/GitWriteOperationService.java:205-219`

**问题说明**

`buildCommitInput()` 只通过 `changed.getPath()` 判断敏感文件，没有同时检查重命名前的 `changed.getOldPath()`。当敏感文件被重命名为普通文件名时（例如 `.env` → `config.txt`），该文件会被当作非敏感文本，随后 `readDiff()` 会读取并把 diff 放入模型输入。

这会违反设计中“敏感文件 diff 内容不得发送给模型服务”的核心要求。LOCAL 实现已经同时检查 `file.path` 和 `file.oldPath`，CLOUD 与 LOCAL 行为因此也不一致。

**建议修复**

在 CLOUD 构建提交摘要时，只要新路径或旧路径任意一个命中敏感规则，就将文件标记为 `sensitive=true` 并完全跳过 diff 读取。补充“敏感文件重命名为非敏感名称”和“普通文件重命名为敏感名称”两个测试。

---

### 2. LOCAL 拉取在 pull 失败但未产生冲突时，会先恢复 stash 再返回失败，可能在远端改动已部分落盘时混入本地改动

**代码位置**

- `desktop/electron/gitOperations.cjs:315-342`

**问题说明**

当前流程只把“存在未合并文件”识别为 pull 冲突。对于其他失败场景，只要创建过 stash，就会无条件调用 `restoreStash()`，之后才检查 `pulled.exitCode`。

部分 Git 失败并不保证工作树仍是 pull 前状态。例如 `git pull --no-edit` 在合并成功、但因提交身份或签名配置失败而无法创建 merge commit 时，命令会返回非零，但合并后的远端内容可能已经写入 index/worktree，且未必存在 unmerged 文件。此时自动应用 stash 会把本地改动叠加到未完成的合并现场；随后接口仅返回普通“Git pull 失败”，用户难以判断仓库已经发生变化，也无法按“非冲突失败恢复原本地改动”的预期处理。

CLOUD 实现存在同类流程（`GitWriteOperationService.java:107-119`），同样仅以 unmerged 文件判断冲突并恢复 stash。

**建议修复**

在恢复 stash 前额外识别 Git 正在进行的 merge 状态（例如检查 `MERGE_HEAD`），并区分：

1. pull 未改变仓库的普通失败：恢复 stash；
2. 已进入冲突或未完成 merge 的失败：保留 stash 和现场，返回 `conflict=true` 或明确的未完成合并提示；
3. pull 成功：恢复 stash。

同时增加“分叉分支 + 脏工作区 + merge commit 因身份/签名失败”的 CLOUD/LOCAL 测试，确认 stash 不会错误应用到未完成的 merge 上。
