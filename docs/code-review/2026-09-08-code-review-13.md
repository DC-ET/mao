### P2-1. 确认卡片弹出时用户点「本次任务授权 / 完全授权」会把当前动作判为拒绝（第 5 轮 P3-2 未修）

**位置**
- `sdk/embed/src/page/authorization.ts:136-138`（`setLevel` 首行 `cancelPendingConfirmations()`）
- `sdk/embed/src/page/authorization.ts:75-90`（`cancelPendingConfirmations` 以 `resolve(false)` 结束）
- `sdk/embed/src/ui/PageActionPanel.vue:38-40`（授权级别按钮与确认卡片同屏，可同时点击）
- `sdk/embed/src/controller.ts:901-906`（`applyUserPageAuthorization`）

**问题**

`per_action` 下确认卡片弹出时，面板顶部仍显示「本次任务授权 / 完全授权」按钮（`level !== 'task' / 'full'` 即显示）。用户为了「以后别再问了」点击它，`setLevel()` 会先把**活动确认以 `false` 结束**：

```
setLevel(level, sessionId) {
  this.syncIdentity();
  this.cancelPendingConfirmations();   // ← 活动确认 resolve(false)
  ...
}
```

于是当前动作立即以 `authorization_denied` 失败（`engine.ts:352-355` 的 authorizer 拿到 `approved=false`），日志里出现「用户未批准该页面操作」。用户的实际意图是放行，结果却是拒绝，必须等模型重试一次才成功；卡片消失与动作失败同时发生，用户无从理解。

**修复建议**
- 按方向区分：升级（`→task` / `→full`）时以 `true` 结束或保留当前挂起确认（等待用户显式点「允许本次」）；仅降级（`→per_action`）、`revoke()`、`endTask()`、`syncIdentity()` 身份切换时以 `false` 结束。
- 同步调整 `authorization.spec.ts` 中依赖「`setLevel` 一律拒绝在途确认」的断言。
- 备选：确认卡片存在时隐藏授权级别按钮，避免同屏误触。

## P3 / 备注（不阻塞）

### P3-1. 断线/换绑/退订统一返回 `task_cancelled`，会误导模型认为「用户取消了任务」

**位置**
- `backend-ts/src/harness/embed-page-tool-registry.ts:107-109`（`failSession` 固定 payload `code: 'task_cancelled'`）
- 调用点：`streaming-ws-handler.ts:147`（连接断开）、`:238`（换绑）、`:272`（退订）

**问题**

一次瞬时断线重连（SDK `onclose` → 1s 后重建 → `restoreSubscriptions` 重订阅触发换绑）或用户新开标签页接管，都会让在途页面工具立刻返回 `{"success":false,"error":{"code":"task_cancelled","message":"页面连接已切换，页面操作已取消"}}`。模型收到 `task_cancelled` 常会判定「任务被用户取消」而收尾，而不是「连接抖动、重试该动作」；同时前端没有任何「已取消」提示，用户体验上表现为页面操作莫名失败。后端未对 `task_cancelled` 做特殊处理（全仓仅此一处产出），因此影响完全取决于模型解读。

**修复建议**
- 为「连接问题」使用独立错误码（如 `embed_client_not_connected` / `page_connection_lost`），或在 payload 中加 `retryable: true` 提示模型重试；
- `handleCancel` 保留 `task_cancelled`（那才是真正的取消）。

### P3-2. `ensureTask(sessionId<=0)` 早退且不复位 `cancelled`：身份切换后宿主 `executePageAction` 会被永久拒绝

**位置**
- `sdk/embed/src/page/engine.ts:208-214`（`ensureTask`）
- `sdk/embed/src/index.ts:67-69`（`executePageAction` 传 `store.sessionId() ?? 0`）
- `sdk/embed/src/controller.ts:365-395`（`setIdentity` → `store.reset()` + `pageEngine.cancel()`）

**问题**

P3-3 修复让 `ensureTask` 在 `sessionId<=0` 时直接返回，因此**不再复位 `cancelled`**。而 `setIdentity()`（身份就绪/切换）会 `pageEngine.cancel()`（`cancelled=true`）并 `store.reset()`（sessionId=null）。此时宿主按文档调用 `inspectPage()` 正常，但 `executePageAction(action, snapId)` 会走 `ensureTask(0)` 早退，随后 `executor.execute` 的 `shouldAbort` 与 authorizer 都命中 `cancelled=true`，返回 `task_cancelled`——直到 boot 重新绑定会话、或用户发送一条消息（`prepareNewTask`）才恢复。修复前 `ensureTask(0) → beginTask(0)` 会复位取消态，属本轮引入的行为回退（窄场景）。

**修复建议**
- 把「复位取消态」与「建立任务绑定」解耦：`ensureTask` 首行无条件 `if (this.cancelled) this.cancelled = false;`，再判断 `sessionId > 0` 才 `authorization.beginTask`；
- 或让 `setIdentity` 在 `cancel()` 后补一次 `prepareNewTask()`。

### P3-3. 页面工具可见性在任务开始时一次性快照，绑定缺失时整轮不可用

**位置**
- `backend-ts/src/harness/core/harness-service.ts:325-327`（`filterPageTools(..., isEmbedSession(sessionId))`）
- `backend-ts/src/session/ws/attach-websocket.ts:41`（`void handler.handleTextMessage(...)`，同连接消息未串行）
- `sdk/embed/src/core/ws-client.ts:337-345`（`subscribe` 帧在收到 `connected` 后才发出）

**问题**

`isEmbedSession` 依赖「会话已绑定且连接 OPEN 且已鉴权」。工具列表在 `loadContext`（任务开始）时一次性计算。若此刻绑定尚不存在——典型是断线重连后用户立即发送（`sendReliable` 在 socket OPEN 后即发 `send_message`，而 `subscribe` 帧要等 `connected` 才补发），或 `subscribe` 与 `send_message` 因未串行而乱序——该轮任务将完全没有页面工具，Agent 只能纯文本回答。实际链路中 subscribe 处理路径（单次 `requireOwnedSession`）远短于 send 路径（落库→占位→建上下文），多数情况下绑定先完成，故概率较低，但属真实脆弱点。

**修复建议**
- 在 `handleSendMessage` 入口也补一次 embed 绑定（需要把 `session` 传进去）；或
- 每轮/每次 LLM 调用重新评估 `filterPageTools`；或
- SDK 侧保证 `subscribe` 帧先于 `send_message` 落盘（`sendReliable` 在未鉴权时先等 `connected`）。

### P3-4. 宿主 `setPageAuthorization('full')` 会顺带清掉已持久化的 full 授权

**位置**
- `sdk/embed/src/page/engine.ts:120-125`（`setHostLevel('full') → authorization.setInitialLevel('per_action')`）
- `sdk/embed/src/page/authorization.ts:119-133`（`setInitialLevel('per_action')` 会 `level='per_action'`、`taskSessionId=null`）

**问题**

宿主 API 文档写明 `full` 会被降级，但 `setInitialLevel('per_action')` 同时把当前级别重置为 `per_action` 并清空 `taskSessionId`。若用户此前已在浮窗内授予并持久化「完全授权」，宿主一次 `setPageAuthorization('full')`（哪怕意图只是「请求」）就会把用户授权降级，且若 `initialLevel` 本身为 `'full'` 还会 `localStorage.removeItem` 删掉持久化值。行为可自洽，但「请求 full → 反而撤销用户已有的 full」容易让人意外。

**修复建议**
- `setHostLevel('full')` 只做「不升权」处理（保持当前级别不变或仅记录 initial 级别），不要重置当前 level/持久化；如需重置，明确用 `setPageAuthorization('per_action')`。
