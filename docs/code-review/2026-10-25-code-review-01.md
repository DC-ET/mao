## 一、问题清单

### 1. llm_call 大字段经 SELECT * 泄入列表接口与轨迹窗口查询（backend，中）

- **位置**：
  - 根因组合：`backend-ts/db/migration/V171__llm_call_request_capture.sql:7-11`（新增 `system_prompt` MEDIUMTEXT，应用层截断上限 262,144 字符）+ 既有全列查询未同步收窄；
  - 列表出站点：`backend-ts/src/usage/llm-call.repository.ts:240`（`list` 的 `SELECT * FROM llm_call ... LIMIT ? OFFSET ?`）→ `backend-ts/src/usage/llm-call.service.ts:399-421`（`enrichRecords` 以 `...row` 全字段展开为 `LlmCallListItem`）→ `backend-ts/src/usage/llm-call.routes.ts:44-79`（`/v1/admin/llm-calls`、`/v1/llm-calls/me` 把 records 整体 `sendOk` 序列化）；
  - 轨迹窗口消费点（DB→应用传输与 `toCamelList` 行复制背上部体积，不序列化出站）：`backend-ts/src/usage/llm-call.repository.ts:264`（`selectBySessionWindow` 的 `SELECT *`）被 `run-trace.service.ts:122,136,161`（轨迹主 VO 组装、每 run 窗口、未归属窗口）与 `run-trace-record.service.ts:72`（buildCallRecord 推 next）、`:113`（buildToolRecord.findCall 配对）复用。
- **问题描述**：技术方案 §5.7 明确契约「`toolsJson` / `systemPrompt` 只随记录详情按需返回，单次响应最坏 ~256K 字符……一次抽屉打开一条调用行，可控」；决策 9 再次强调「正文与提示词……进主 VO 违背 0.0.336 立下的防膨胀口径」。实现上两字段确实只进了 `toCallMeta`（详情 VO），但 `list` 与 `selectBySessionWindow` 都是 `SELECT *`：V171 之后每一行 llm_call 自动携带最多 262,144 字符的提示词原文与 tools_json，于是：
  1. **用户/管理端调用明细列表**（desktop「我的调用明细」`desktop/src/api/index.ts:943`、admin `LlmCallView.vue:403,456`）每行响应都带全文提示词。默认 size=20，按方案 §5.1 的典型体量（10–30KB/行）一页 ~200–600KB，MCP 工具目录较大时单行可达数百 KB、一页可到 MB 级——而这些字段对列表 UI 完全无用。对照先例：同表 `error_message` 被刻意设计为 `VARCHAR(512)` 并在写入侧 `truncateError` 截断（`llm-call.service.ts:279`），说明本表行宽原本是受控的，本次破坏了这一约束。
  2. **轨迹侧**每次打开轨迹面板 / 点一次工具或轮次抽屉，`selectBySessionWindow` 都把窗口内（buildCallRecord 甚至是全会话）所有调用的提示词全文从 MySQL 拉到 Node 并做一次 camelCase 复制，仅用于取 `id`/`createdAt`/`scene` 等小字段。
- **触发场景**：部署 0.0.346 并产生若干带采集的新调用后，① 打开 desktop 用量页「调用明细」或 admin 调用列表翻页；② 打开任一会话的运行轨迹面板（`/trace` 主接口内部逐 run 窗口查询）；③ 点任意工具行 / 轮次行打开抽屉。
- **影响**：列表接口响应体积与序列化耗时随采集行数线性膨胀（最坏每页数 MB）；轨迹视图内存峰值与 GC 压力上升（buildCallRecord 每次抽屉打开拉全会话调用行）。功能结果仍正确，属契约违背型性能回归，长会话 / 高频使用实例上会被感知。
- **建议修复方向**：`LlmCallRepository.list` 与 `selectBySessionWindow` 改显式列清单（枚举既有小字段，排除 `system_prompt` / `tools_json`），仅 `selectById`（详情端点专用）保留全列；补一条仓库层规格断言两条查询的 SQL 不含两列，防回归。
- **已用测试验证**（临时 spec `backend-ts/src/usage/tmp-review-verify-list-payload.spec.ts`，运行 2 passed 后删除）：
  ```ts

### 2. 编辑重发后旧轮「回复」空态文案误标为「未落库（崩溃恢复 / 中断）」（backend + desktop，低）

- **位置**：
  - `backend-ts/src/session/session.service.ts:1414-1418`（`editMessageAndTruncate`：更新锚点后 `logicalDeleteAfter` 软删其后全部消息，含旧轮助手回复）；
  - `backend-ts/src/session/session.repository.ts:792-796`（新增 `selectAssistantMessagesBetween` 按 `deleted = 0` 过滤）；
  - `backend-ts/src/session/run-trace-record.service.ts:159-178`（`findRoundMessages` 拿不到被软删的回复 → `messages: []`）；
  - `desktop/src/components/center/RunTraceRecordDrawer.vue:279-283`（`replyEmptyText`：`call.createdAt != null` 且 `messages` 空 → 固定文案「该轮回复未落库（崩溃恢复 / 中断）」）。
- **问题描述**：「回复」tab 的空态二分只有两种成因（时钟缺失 / 未落库）。但编辑重发会软删旧 run 的助手回复（数据层 `deleted = 1`），而旧轮次卡片的「编辑前」段仍展示这些轮次且可点进抽屉（llm_call 行未删、`toRoundVO` 照常产出）。此时窗口查询返回空数组、`call.createdAt` 正常，抽屉断言成「崩溃恢复 / 中断」——与真实原因（回复随编辑重发被清理）不符。数据本身不出错（回复确实不再存在），属空态文案归因错误；与本功能「空态区分成因、不误导」的设计初衷（方案 §5.3）相悖。
- **触发场景**：对最后一条用户消息执行「编辑重发」→ 展开该 run 卡片 → 点「编辑前」段的任一轮次 → 切到「回复」tab（默认 tab 即是）。
- **影响**：排障视图给出错误归因，用户可能误判会话发生过崩溃 / 中断。低危。
- **建议修复方向**：前端在 `messages` 为空且 `call.createdAt != null` 时的文案改为不归因的表述（如「该轮回复不存在（可能已随编辑重发清理或未落库）」）；或后端在 `TraceCallRecordVO.messages` 空时附带一个轻量成因标记（如查一次含软删行的 count 区分「被清理」与「从未落库」，代价是一次额外查询，可不做）。
- **已用测试验证**（临时 spec `backend-ts/src/session/tmp-review-verify-edit-reply-empty.spec.ts`，运行 2 passed 后删除；前端半环由本提交既有测试 `desktop/src/components/center/run-trace-record-drawer.test.ts:316`「回复 tab 两种空态分开」断言 `messages=[]` + `createdAt!=null` → 文案含「该轮回复未落库（崩溃恢复 / 中断）」，两半拼接即完整因果链）：

    const repo = new MessageRepository(db as never);

    expect(sqls[0]).toContain("role = 'ASSISTANT'");
  });

    const record = await service.buildCallRecord(1, 100);
    expect(record.call).not.toBeNull();
    expect(record.messages).toEqual([]); // → 抽屉显示「未落库（崩溃恢复 / 中断）」
  });
  ```

## 二、审查过并排除的点（供后续评审去重）

- **窗口归属语义未破坏**：`findRoundTools` 重构仅把 `next` 推导提升到 `buildCallRecord`，`(sessionId, upper=next?.createdAt ?? null, lower=call.createdAt ?? null)` 参数顺序与原实现逐字一致；两个 bugcheck 规格（round-window / call-window-direction）仅补 mock，基线全绿。`findRoundMessages` 与 `selectAssistantMessagesBetween` 的参数序（lower 在前）核对无误。
- **时钟缺失口径的刻意分叉**（工具退化为全会话清单、回复返回空数组）是方案 §5.3 明文设计并有测试锁定，非 bug。
- **采集口径**：`captureSystemPrompt` / `captureToolNames` 与 prompt-engine 实际构造一致（单条 `role:'system'` 消息、`ToolDefinition = {type:'function', function:{name}}`，见 `prompt-engine.ts:174,660-668`）；截断标记与前端 `TRUNCATION_SUFFIX` 正则逐字符匹配；截断上限内 MEDIUMTEXT 不会溢出。
- **落库链路**：`Db.insert` 的 camelToSnake 映射正确产出 `system_prompt` / `tools_json`；`jsonStrings: true` 使 JSON 列读回字符串，与 `TraceCallMetaVO.toolsJson: string | null` 口径一致；`record()` 失败有 try/catch 兜底。
- **selectMessageById 用 SELECT \***：Db 层 `toCamelList` 统一做 snake→camel，字段名（thinkingContent/tokenCount/createdAt/updatedAt）不会错位，与既有 `selectAssistantByToolCallId` 同款。
- **edited 判定**：USER 消息的 `updated_at` 唯一写入点是 `editMessageAndTruncate`（`markLastMessageFinished` 刻意跳过 USER，见其注释），`updatedAt !== createdAt` 判定自洽；毫秒精度（V142）下同刻碰撞可忽略。
- **越权与空态**：新端点复用 `requireSessionOwner`，`messageId` 非正整数钳制为 0 走空态 VO，与既有 tool/call 两端点口径一致；`selectMessageById` 带 `session_id` 过滤，跨会话查不到。
- **重试轮归属**：每个 agent 调用自成一轮（`run-trace.service.ts` buildRun），失败 attempt 轮的回复/工具窗口为空是准确表现；成功 attempt 轮窗口含其回复。
- **前端多模态口径**：`messageContentSummary` 的 `isMultimodalParts` 与后端 `isMultimodalContentParts`（`backend-ts/src/common/multimodal-content.ts`）逐条件一致，0.0.335 的「用户 JSON 数组文本被清空」陷阱未复发。
- **抽屉行为回归**：跨 kind 切换重置 tab、缓存 key 三前缀（tool:/call:/message:) 不冲突、过期响应丢弃、Esc 关闭均保持；`RunTraceCallMetaTable` 只渲染显式字段，不会重复输出大字段。
- **runId=锚点消息 id**（`run-trace.service.ts:345`）与 `openMessageRecord(run.runId)` 的主键直查语义一致；未归属组的预览不可点。
