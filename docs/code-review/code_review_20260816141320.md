## 高

### H1. `MessageBubble.vue` 的 `inject` 默认值类型错误，前端构建会失败

- 文件：`desktop/src/components/chat/MessageBubble.vue`
- 位置：第 254 行

```ts
const openSubagent = inject<(payload: { childSessionId: number; title?: string }) => void>('openSubagent', undefined)
```

`vue-tsc -b` 报错：

```
src/components/chat/MessageBubble.vue(254,108): error TS2345: Argument of type 'undefined' is not assignable to parameter of type '(payload: { childSessionId: number; title?: string | undefined; }) => void'.
```

由于项目 `desktop` 的构建脚本为 `vue-tsc -b && vite build`，该错误会直接中断前端打包。同仓库 `ToolCallCard.vue:71` 已给出正确写法：

```ts
const openSubagent = inject<(payload: { childSessionId: number; title?: string }) => void>('openSubagent', () => {})
```

修复建议：将默认值改为空函数（`() => {}`），或在泛型中显式包含 `undefined`（`inject<... | undefined>(... , undefined)`）。功能逻辑本身（点击卡片打开子代理 Tab）依赖 `TaskView.vue` 提供的 `openSubagent`，provider 存在，仅类型签名写法有问题。

## 中

### M1. `cancel_subagent` 存在取消竞态：后台子代理可能无法被取消

- 文件：`backend-ts/src/harness/delegate/background-subagent-manager.ts`
- 相关位置：`cancel()`（第 161-180 行）、`runBackground()`（第 242-249 行）
- 依赖：`backend-ts/src/harness/core/agent-loop.ts` 的 `registerCancelFlag`（第 68-72 行）会无条件覆盖已有 flag

问题链路：

1. `spawn()` 通过 `agentExecutor.submit(() => runBackground(...))` 异步启动后台执行；
2. `cancel()` 只调用 `agentLoop.requestCancel(childSessionId)`，该方法在 `AgentLoop.cancelFlags` 中找不到 child 的 flag 时是 no-op；
3. 若 `cancel_subagent` 在 `runBackground` 执行到 `registerCancelFlag(childSessionId)` 之前被调用，取消信号会丢失；
4. 更糟的是，即使 `cancel()` 先注册了 flag 并置 true，`runBackground` 随后仍会调用 `registerCancelFlag` 重新创建一个 `false` 的 flag 并覆盖，取消依然失效。

最终表现：`cancel_subagent` 返回 `success: false`，子代理继续运行到 `COMPLETED`，与「可取消」需求不符。

修复建议：取消状态应持久化或复用已注册 flag。例如：
- `cancel()` 直接对 child session 执行 `registerCancelFlag` 后 `set(true)`，并让 `runBackground` 复用已存在的 flag（`getCancelFlag` 存在则复用，不存在才注册）；或
- 在 `subagent_execution` 上增加/复用「取消请求」状态，`runBackground` 启动前先读取并据此跳过执行。

### M2. `resultsByParent` 未随执行结束清理，陈旧结果会泄漏到下一次执行

- 文件：`backend-ts/src/harness/delegate/background-subagent-manager.ts`
- 相关位置：`onCompleted()`（第 308-330 行，先 push 再判断父会话终态）、`failExecution()`（第 422-445 行）、`consumeResults()`（第 134-145 行）
- 触发点：`backend-ts/src/harness/core/agent-loop.ts` 第 286-298 行的主线收尾逻辑只检查 `hasRunning`，未检查是否还有未消费结果

问题链路：

1. `onCompleted` 在判断父会话是否为终态之前，已经把结果写入 `resultsByParent`；若父会话已 `CANCELLED/FAILED`，结果虽被 `SUPPRESSED`，但 map 中的条目不会清除。
2. 另一个竞态：子代理若恰好在「本轮循环顶部 `consumeResults` 之后、主线 `hasRunning` 检查之前」完成并完成 `untrackRunning`，主线会因为 `hasRunning === false` 直接 `break`，该结果未被消费，残留在 map 中。
3. 由于 map 以 `parentSessionId`（会话维度）为 key，跨执行不清理，下一次在同一会话发起新执行时，`AgentLoop.execute` 顶部会把上一次的陈旧 `<后台子代理结果>` 注入到新上下文，造成模型基于旧任务结果继续推理。

修复建议：
- 会话执行结束时（或 `AgentLoop.execute` 的 `finally` 中）清理该会话的后台结果 map；
- 主线收尾判断同时考虑「仍有 pending 结果」，若存在则 `consumeResults` 后 `continue`，而非直接 `break`；
- `onCompleted`/`failExecution` 在父会话终态时不应再向 `resultsByParent` 写入。

### M3. 父会话取消时，尚未启动的后台子代理可能仍继续完整执行

- 文件：`backend-ts/src/harness/delegate/background-subagent-manager.ts`
- 相关位置：`runBackground()` 第 242-249 行（仅依赖内存中的 `getCancelFlag(parentSessionId)`）

问题链路：

1. `spawn()` 提交 `runBackground` 到线程池后立即返回；若线程池繁忙，`runBackground` 可能延迟到父会话已被用户取消之后才真正执行。
2. 父会话取消后，`StreamingWsHandler`/`AgentLoop` 会移除父会话的 cancel flag；`abortSubagentChildren` 对尚未注册 child flag 的后台子代理调用 `requestCancel(child.id)` 也是 no-op。
3. `runBackground` 启动时 `getCancelFlag(parentSessionId)` 已返回 `undefined`，于是不会继承取消状态，子代理继续执行到完成，最终结果仅因父会话已终态而被 `SUPPRESSED`，造成资源浪费，且用户取消后子代理仍可能执行文件/shell 等实际副作用。

修复建议：`runBackground` 启动前从 DB 重新读取 execution 状态（若已 `CANCELLED/FAILED/COMPLETED` 则直接返回），并读取父会话 `phase`，若父会话已终态则不启动实际执行。也可与 M1 合并为统一的「持久化取消标记」方案。

### M4. `cancel_subagent` 的 `waitTerminal` 无超时，可能永久阻塞主循环

- 文件：`backend-ts/src/harness/delegate/background-subagent-manager.ts`
- 相关位置：`cancel()` 第 169 行、`waitTerminal()` 第 212-218 行

`cancel()` 在设置取消标志后进入 `waitTerminal` 无限轮询（300ms 一次），没有超时/宽限期。若子代理正阻塞在长任务（例如长时间 shell 调用，且该工具在结束前不检查取消标志），`cancel_subagent` 会一直阻塞主 agent 的工具执行，用户侧表现为卡死。

修复建议：为 `waitTerminal` 增加超时（如 N 秒），超时后返回 `success:false` 与明确错误信息；或结合「取消宽限期」机制，超时后标记执行失败/取消。

## 低

### L1. `check_subagent` 单任务查询未校验 `task_id` 归属

- 文件：`backend-ts/src/harness/delegate/background-subagent-manager.ts`
- 相关位置：`progress(parentSessionId, taskId)` 第 146-157 行，单任务路径直接 `snapshot(taskId)`

`snapshot` 仅按 `taskId` 查询 `subagent_execution`，没有校验 `execution.parentSessionId === parentSessionId`。与 `cancel()` 已做的归属校验不一致。虽然工具由会话内模型调用、通常只会拿到自己的 task_id，但若模型臆造/泄漏 task_id，可读取其他会话后台子代理的状态与最近输出，存在轻微跨会话信息泄露。

修复建议：单任务 `progress` 先 `findById(taskId)` 并校验 `parentSessionId`，不匹配返回「不存在或不属于当前会话」。

### L2. 后台子代理恢复在 LOCAL 模式下可能无限等待

- 文件：`backend-ts/src/harness/delegate/subagent-execution-recovery.service.ts`
- 相关位置：`waitForLocalNoDeadline()`（第 154-164 行）、`recover()` 中 BACKGROUND 分支（第 72-84 行）

BACKGROUND 恢复走 `waitForLocalNoDeadline` 且 `executeVisible(child, context, false)` 无超时。若父会话为 LOCAL 模式且桌面客户端未连接，恢复会永久阻塞在轮询等待上，占用 `SubagentRecoveryCoordinator` 的线程池线程，并阻塞同组其他 execution 的恢复/交付与父会话恢复。

修复建议：为 BACKGROUND 的 LOCAL 恢复设置合理超时（例如按任务类型或配置），超时后将 execution 置为 `FAILED`/`CANCELLED` 并继续后续流程。

### L3. 崩溃恢复路径不聚合后台子代理的文件变更

- 文件：`backend-ts/src/harness/delegate/subagent-result-delivery.service.ts`
- 相关位置：`deliverBackground()`（第 108-143 行）
- 对比：`background-subagent-manager.ts` 的 `persistCompletionNotice()`（第 349-370 行）在保存完成通知后会调用 `copyFileChanges()` 把子代理 fileChanges 聚合到父会话

正常完成路径（`onCompleted` → `persistCompletionNotice`）会复制 fileChanges，但崩溃恢复路径（`SubagentRecoveryCoordinator` → `SubagentResultDeliveryService.deliver` → `deliverBackground`）只插入完成通知消息，未复制 fileChanges。表现为：服务重启后恢复完成的后台子代理，其文件变更不会在父会话的文件变更面板中展示。

修复建议：`deliverBackground` 在插入通知消息后，同样读取子会话 fileChanges 并复制到父会话通知消息上（或抽公共函数供两处复用）。

### L4. 后台子代理「skip 取消」路径遗留 cancel flag

- 文件：`backend-ts/src/harness/delegate/background-subagent-manager.ts`
- 相关位置：`runBackground()` 第 259-264 行的 `finally`，以及第 250-257 行的 skip 分支

当 `childCancel` 在启动时已为 true（例如父会话已取消），`executeVisible(childSession, subContext, childCancel.get())` 直接返回（skip），不会进入 `AgentLoop.execute`，因此 `AgentLoop.execute` 的 `finally` 不会清理该 child 的 cancel flag；而 `runBackground` 的 `finally` 里 `if (!childCancel.get()) removeCancelFlag(...)` 又因 flag 为 true 而跳过清理，导致该 childSessionId 的 flag 残留在 `AgentLoop.cancelFlags` 中，属于小规模内存泄漏。

修复建议：`runBackground` 的 `finally` 无条件清理 child cancel flag（`removeCancelFlag(childSessionId)`），与注册逻辑对称。
