# 代码审查报告

- 审查范围：当前 Git 工作区未提交代码（第三轮；不含页面样式及文档内容）
- 审查重点：用户/群工作区隔离、绑定唯一授权来源、群成员自动维护、SDK `is_at_me` 精确@、执行串行锁、回复发送和长连接生命周期
- 结论：仍发现重大功能逻辑问题，建议修复后再验收。

## 严重问题

### [严重] 入站授权没有以 `feishu_binding` 作为唯一来源，且会话创建再次绕过该授权表

- 位置：`backend-ts/src/create-app.ts:668-676`、`backend-ts/src/feishu/binding.repository.ts:16-32`
- 问题：入站授权和会话创建都允许回退到 `user.feishu_user_id`：`findUserIdByUnionId` 在 `feishu_binding` 未命中时查询 `user.feishu_user_id`；创建会话时甚至直接调用 `userRepo.findByFeishuUserId`。因此已在新绑定表解绑/失效的身份，只要旧字段仍有值，就可能继续通过授权并执行 Agent；绑定表也不再是唯一授权来源。换绑时 `bind` 只清理当前用户的 binding，没有清理被 `ON DUPLICATE KEY UPDATE` 替换的旧用户 legacy 字段，旧用户的授权状态仍可能残留。
- 修复建议：入站身份解析和会话创建统一只调用 `feishu_binding` 的有效记录；移除 legacy 回退，或在一次迁移/事务中彻底清理并停止读 legacy 字段。换绑必须原子地清理旧用户字段、旧 binding 状态，并增加解绑/换绑后的入站拒绝测试。

### [严重] 长连接启动失败或断开后仍被监控视为 active，无法按配置恢复

- 位置：`backend-ts/src/feishu/monitor.service.ts:19-45, 91-114`
- 问题：`createFeishuBotHandle.start()` 将 `wsClient.start()` 的异常仅打印；monitor 在调用 `handle.start()` 前已把 handle 放进 `active`。Handle 没有把启动失败、close/error 或 SDK 重连耗尽状态反馈给 monitor，所以失败/断线的机器人不会从 active 移除，也不会重新创建。`reconnectDelayMs` 等配置没有参与该生命周期状态机。停用/删除时虽然调用 `close()`，但无法等待旧 SDK 连接真正停止，也没有防止旧连接回调继续处理事件。
- 修复建议：为 handle 增加 running/failed/closed 状态及状态回调；启动失败、异常关闭或重连耗尽时由 monitor 移除并重建，使用指数退避和连续失败阈值；停止时等待 close 完成，并使旧连接事件在 generation/token 校验失败后丢弃。

## 高严重问题

### [高] 精确@判断仍依赖不受校验的布尔字段，未保证“只@当前机器人”

- 位置：`backend-ts/src/feishu/event-normalizer.ts:22-27`、`backend-ts/src/feishu/inbound-processor.ts:55-61`
- 问题：标准化逻辑直接把 `message.is_at_me`/`event.is_at_me` 转成布尔值；当字段缺失时默认 false，当字段来源/事件形态不一致时没有依据 mentions 中的机器人身份进行校验。`mentions` 只提取 ID，但没有与当前 bot 的 open_id/app 身份比较。处理器默认也只返回这个布尔值。因此当前代码没有建立可证明的精确@语义，不能防止普通成员@、事件字段误读或多机器人路由下的误触发。
- 修复建议：以当前长连接机器人对应的 open_id（或 SDK 明确定义的 `is_at_me` 语义）作为唯一判定依据；保留并校验 mention ID，无法确认当前机器人身份时按未@处理。为 `is_at_me=true/false`、@普通成员、无字段、多机器人事件分别补测试。

### [高] 私聊/群聊会话映射使用 `feishu_chat` 的伪 chat key，数据语义和隔离边界容易被破坏

- 位置：`backend-ts/src/feishu/message.repository.ts:40-43`、`backend-ts/src/feishu/message.service.ts:20-29`、`backend-ts/src/create-app.ts:695-702`
- 问题：私聊通过 `chat_id = p2p:${unionId}` 存入原本定义为“机器人×群”的 `feishu_chat` 表；同时会话工厂按 `user.id` 拼接 project key。虽然当前可形成用户隔离，但该映射没有独立的 p2p 维度，也没有对 bot app_id/chat_id 的统一语义约束；一旦同一 union_id 的绑定发生变更或历史记录复用，旧用户会继续命中同一 p2p 映射并复用旧 session/workspace，造成换绑后的用户边界不清。
- 修复建议：为私聊使用明确的 `(bot, union_id/user_id)` 映射并在查询条件中绑定当前有效 Mao 用户，或新增独立私聊映射表；换绑/解绑时明确旧会话是否保留但不可被新身份复用。群聊仍保持 `(bot, chat_id)` 独立目录，并补充不同机器人、不同用户、换绑后的隔离测试。

## 中等问题

### [中] 群成员自动维护与需求表面一致，但当前写入缺少绑定快照一致性保障

- 位置：`backend-ts/src/create-app.ts:736-741`、`backend-ts/src/feishu/message.repository.ts:76-84`
- 问题：已绑定成员首次@时自动插入白名单符合“触发过且已绑定自动入表”的需求；但写入使用 `event.senderId`（open_id）和固定“未知用户”，没有校验/更新该 open_id 当前对应的 union_id 绑定关系。若同一群里 open_id 复用异常、身份换绑或绑定删除后再次触发，旧 `feishu_chat_member` 记录仍可按 `user_id` 放行。
- 修复建议：自动维护前后都以当前有效 `feishu_binding` 校验；成员表同时保存稳定身份锚（或每次按 open_id 与当前绑定核对），解绑/换绑时清理或使旧成员记录失效。未绑定成员只记录群日志并发送引导，不创建会话。

## 已复核项

- 用户私聊工作区 project key 已加入 `user.id`，相较上一轮已修复基本隔离问题；群目录使用 `feishu-chat/{accountId}/{chatId}`，不同机器人/群有独立路径。但旧 session 映射复用与 legacy 身份回退仍会削弱该隔离边界。
- Agent 执行阶段已存在按 `session.id` 的进程内串行锁，能避免同一进程内同一会话并发执行；该锁不覆盖跨进程场景，也未实现设计中提到的代际取消，但当前部署假设为单实例。
- 回复主路径已按私聊 `open_id`、群聊 `chat_id` 路由，并传入配置化截断长度；未发现上一轮 `receive_id_type` 遗漏问题。发送异常仍直接向入站处理链抛出，长连接事件回调缺少统一失败隔离/重试策略。
- 群消息会在@判断前持久化，未@不会执行 Agent；群上下文按数量和时间窗口查询。

本报告仅记录问题，未修改业务代码。
