## 中等严重程度

### 1. CLOUD 自动提交及 Git 状态仍会整文件读取大型未跟踪文件

**代码位置**

- `backend/src/main/java/cn/etarch/mao/file/service/WorkspaceGitService.java:491-508`
- `backend/src/main/java/cn/etarch/mao/file/service/WorkspaceGitService.java:575-583`
- `backend/src/main/java/cn/etarch/mao/file/service/GitWriteOperationService.java:197-204`

**问题说明**

LOCAL 的 `readTextLimited()` 已改为有界读取，但 CLOUD 对应路径仍使用 `Files.readAllBytes()`：

1. CLOUD commit 先调用 `workspaceGitService.changedFiles(repo)`；统计未跟踪文件时，`WorkspaceGitService.readTextLimited()` 会整文件读取，用于二进制检测和行数统计。
2. 随后 `GitWriteOperationService.readDiff()` 对未跟踪文件再次调用 `Files.readAllBytes(path)`，读取完成后才裁剪到 2 MB。

因此一个数百 MB/数 GB 的未跟踪文本文件会在一次 CLOUD 自动提交中至少被完整读入内存一次，通常是两次；普通 Git 状态刷新也会触发第一处读取。模型输入最终虽然限制为 200 KB，但限制发生在整文件读入之后。

这可能导致后端请求长时间阻塞、堆内存突增甚至 OOM，并影响同一服务上的其他用户。该场景与前两轮发现的 LOCAL 大文件问题相同，只是当前修复尚未同步到 Java 实现。

**建议修复**

将 Java 的 `WorkspaceGitService.readTextLimited()` 和 `GitWriteOperationService.readDiff()` 都改为有界流式/前缀读取：

- 状态与二进制检测只读取固定上限；
- commit diff 最多读取模型构建所需上限（例如 2 MB 或直接按 200 KB 预算）；
- 根据文件实际大小正确设置截断标记；
- 使用 try-with-resources 确保流关闭。

补充大型或稀疏未跟踪文件的 CLOUD 测试，验证状态读取和 `buildCommitInput()` 不会分配与文件总大小相等的字节数组，且最终 `diffBytes <= 200 KB`、文件 `truncated=true`。
