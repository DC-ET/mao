- 结论：发现 2 个中等严重度的功能问题。未修改源代码。

## 中严重度

### 1. 最后一轮无工具输出不会触发 `onRoundEnd`，导致最后一轮的处理中卡片更新被遗漏

**位置：**
- `backend-ts/src/harness/core/agent-loop.ts:347-365`（工作区当前行号附近，`pendingToolCalls` 为空时直接 `break`）
- `backend-ts/src/harness/core/agent-loop.ts:398-399`
- `backend-ts/src/feishu/card-progress-listener.ts:39-43`

`AgentLoop` 在每次循环开始都会调用 `onRoundStart(round)`，并且只在执行过工具调用、完成持久化后才调用 `onRoundEnd(round)`。当最后一轮 LLM 直接返回纯文本时，`pendingToolCalls` 为空，代码在 `if (!pendingCalls...)` 分支直接结束循环，跳过了后面的 `listener.onRoundEnd?.(round)`。

因此，多轮任务中最后一轮的内容不会生成对应的 `RUNNING` round 卡片更新；卡片会从上一轮的运行状态直接进入 `COMPLETED`。虽然终态卡片包含最终文本，但处理中阶段缺少最后一轮的进度/轮次更新，且其他依赖 round-end 作为每轮边界的 listener 也会漏收最后一轮事件。

**修复建议：**

在“无工具且将结束执行”的分支中，在 `break` 前触发当前轮的 `onRoundEnd(round)`；同时确保空响应重试、等待后台子代理等需要继续循环的分支不误触发 round-end。建议补充 AgentLoop 集成测试：第一轮返回工具调用、第二轮返回纯文本，断言依次收到 `onRoundStart(1)`、`onRoundEnd(1)`、`onRoundStart(2)`、`onRoundEnd(2)`，并验证终态只由 handler 发送一次。

### 2. 飞书卡片展示的是原始工具结果，不是已计算的工具摘要

**位置：**
- `backend-ts/src/harness/core/agent-loop.ts:335-338, 354-356`
- `backend-ts/src/feishu/card-progress-listener.ts:27-30`

`AgentLoop.executeToolCalls` 已使用 `ToolResultSummarizer.summarize(...)` 计算并写入 `tc.summary`，但随后向 listener 发送的仍是 `listener.onToolCallResult(tc.id!, rawResult)`。`FeishuCardProgressListener.onToolCallResult` 又直接对 `rawResult` 做空白压缩和截断，因此卡片显示的是工具原始输出（例如 shell/read/search 的完整 JSON 或输出片段），而不是 `ToolResultSummarizer` 生成的“执行命令/读取文件/匹配数量”等业务摘要。

这会使卡片工具区内容冗长且语义不稳定，尤其是工具返回大段 JSON 时只截取前 240 个字符，可能看不到成功/失败、文件数等关键信息，和“工具摘要正确”的需求不一致。

**修复建议：**

让 round 进度事件传递已经生成的摘要（或传递包含 `summary` 的工具结果事件），并在 Feishu listener 中优先展示该摘要；若确实需要保留原始结果作为兜底，应明确区分摘要与原始输出，不能把 raw result 直接当摘要。补充 shell、read_file、grep_search 等工具的 listener 断言，确认卡片展示摘要而非原始 JSON。

## 已核验未发现问题

- `onRoundStart/onRoundEnd` 已加入 `AgentEventListener` 可选接口，`CompositeAgentEventListener` 使用可选调用，既有未实现 round 事件的 listener 不会因新增事件崩溃。
- round 结束后的卡片更新通过 Promise 链串行排队；`createFeishuProgressCard` 的 patch 之间至少等待约 250ms，未发现并发 patch 或按每个文本 delta 更新导致的高频问题。
- 终态更新前会 `flush()` 已排队的 RUNNING 更新；成功、取消、失败状态均有独立终态更新，卡片 patch 失败时保留纯文本兜底。
- handler 传入的是 `CompositeAgentEventListener.of(listener, cardListener)`，不会替换既有 WebSocket listener，其他通道兼容性未见此次改动引入的明显问题。
