# 代码审查报告：客户端设置页新增个人信息页 + 支持上传头像

- 审查时间：2026-08-06 16:54
- 审查范围：`git status` 未提交改动（后端 auth/user 模块、桌面端 ProfileView/TopNav/router/authStore、UserServiceTest）
- 验证情况：`mvn compile` 通过；`vue-tsc --noEmit` 通过
- 审查原则：只关注功能逻辑正确性，不关注样式与文档

## 总体结论

**不存在必须修复的阻塞级（高优先级）bug。** 主流程功能正确：LOCAL 用户修改显示名/邮箱/头像、头像上传（local/OSS 双模式）、头像移除、LDAP/飞书用户仅允许改头像、顶栏展示真实头像、`authSource` 字段贯通登录/刷新/`GET /users/me` 各链路。

存在 **1 个需求范围内的功能缺陷（中优先级）**：飞书用户上传的自定义头像会被下次飞书登录覆盖；另有 2 个中优先级健壮性问题与若干低优先级问题，建议按优先级处理。

---

## 中优先级

### M1. 飞书用户上传的头像会被下次飞书登录覆盖（功能缺陷，直接违背本次需求）

- **涉及文件**：`backend/src/main/java/cn/etarch/mao/auth/service/FeishuAuthService.java` — `findOrCreateUser()` else 分支（约 281-288 行）
- **问题描述**：本次需求明确"头像所有登录方式均可更新"（`UserService.updateOwnProfile` 对非 LOCAL 用户也放行 `avatarUrl`），但飞书登录链路中，对已存在用户执行：
  ```java
  user.setAvatarUrl(avatarUrl);   // 飞书返回的头像，无条件覆盖
  userMapper.updateById(user);
  ```
  飞书用户上传自定义头像并保存成功后，下一次通过飞书登录时，`avatarUrl` 会被重置为飞书侧头像，自定义头像丢失，功能实质失效。LDAP 登录链路（`LdapAuthService`）不更新 `avatarUrl`，无此问题。
- **建议修复方向**：飞书登录时仅在用户尚未设置头像时填充（如 `if (!StringUtils.hasText(user.getAvatarUrl())) user.setAvatarUrl(avatarUrl)`），或引入"用户自定义头像优先"标记；若产品希望持续同步飞书头像，则需与本次"支持自助上传头像"的需求目标重新对齐。

### M2. `PUT /users/me/profile` 修改 email 无唯一性校验，存在账号混淆隐患

- **涉及文件**：`backend/src/main/java/cn/etarch/mao/user/service/UserService.java` — `updateOwnProfile()` email 分支；`backend/src/main/resources/db/migration/V001__init_schema.sql`（`email` 列无唯一约束）
- **问题描述**：LOCAL 用户可把 email 改为与其他用户相同（DB 无唯一索引，不会报错、无感知）。而飞书登录 `findUserByEmail`、LDAP 登录均依赖 email 关联/绑定账号，邮箱重复可能导致登录绑定错账号、资料串号。本接口为本轮新增的自助入口，建议在写入前做唯一性校验。
- **建议修复方向**：`updateOwnProfile` 中当 email 有值且变化时，`selectCount` 校验"email 相同且 id != userId"的记录数，>0 时返回业务错误（如"邮箱已被使用"）。

### M3. ProfileView `save()` 无异常捕获；上传成功但保存失败时重试会累积孤儿文件

- **涉及文件**：`desktop/src/views/settings/ProfileView.vue` — `save()`（约 150-172 行）
- **问题描述**：
  1. `api.put('/users/me/profile', ...)` 失败时（网络错误/5xx，拦截器不提示、直接 reject）异常冒泡为未处理的 Promise rejection，用户无任何反馈。
  2. 若新头像已上传成功（OSS/本地已落盘）但后续 PUT 失败，`previewUrl`/`selectedFile` 未清理，用户重试会再次上传一张新图，旧的成孤儿文件。
- **建议修复方向**：为 `save()` 增加 `catch`（拦截器已提示的请求错误可静默或补一条兜底提示）；保存失败时建议清理 `selectedFile`（预览可保留），避免重试重复上传。

## 低优先级

### L1. `resolveAuthSource` 判定顺序导致 LDAP 用户被飞书绑定后显示为"飞书"

- **涉及文件**：`backend/src/main/java/cn/etarch/mao/user/service/UserService.java` — `resolveAuthSource()`
- **问题描述**：判定顺序为 `passwordHash → feishuUserId → LDAP`。LDAP 用户（无 `passwordHash`）若邮箱与某飞书账号一致，通过飞书登录时 `FeishuAuthService.findOrCreateUser` 经 `findUserByEmail` 命中并写入 `feishuUserId`，此后该用户 `authSource` 返回 `FEISHU`，前端显示"飞书"且资料改由飞书维护。属跨源绑定的既有行为连带影响，建议确认该场景是否符合产品预期。

### L2. 相对路径头像 URL 在非后端 origin 下无法显示

- **涉及文件**：`backend/src/main/java/cn/etarch/mao/file/controller/FileController.java` — `toVO()`（baseUrl 为空时返回 `/uploads/xxx`）；`ProfileView.vue` / `TopNav.vue` 的 `el-avatar src`
- **问题描述**：local 上传模式在 `UPLOAD_BASE_URL` 未配置时返回相对路径 `/uploads/xxx`，前端 `el-avatar` 按当前页面 origin 解析；dev 环境（前端 localhost:5173、后端 9080）会 404，生产已配置 base-url 则无碍。与既有聊天图片同一模式，非本轮引入，但头像场景更容易被用户直接感知。
- **建议**：确认生产环境 `UPLOAD_BASE_URL` 已配置；可考虑头像展示时对相对路径拼后端 base。

### L3. `el-upload` 重复选择同一文件不触发 `on-change`

- **涉及文件**：`desktop/src/views/settings/ProfileView.vue` — `handleFileChange()`
- **问题描述**：用户移除头像后再次选择同一文件（input value 未变化）可能不触发 change，无法重新预览/上传。
- **建议**：选择文件后手动清空 input 值，或改用 `before-upload`/`on-change` 后重置。

### L4. 前端"显示名称"无必填校验

- **涉及文件**：`desktop/src/views/settings/ProfileView.vue`
- **问题描述**：仅 `maxlength=128`，用户可清空显示名称后保存，由后端抛"显示名称不能为空"错误（有 ElMessage 提示）。建议前端补必填校验，体验更佳。

### L5. 头像 URL 正则放行任意外链与协议相对 URL

- **涉及文件**：`backend/src/main/java/cn/etarch/mao/user/service/UserService.java` — `AVATAR_URL_PATTERN`
- **问题描述**：`https://任意域名/...`、`//cdn.xxx` 均可通过校验（后者以 `/` 开头匹配成功）。头像由用户本人设置，风险低；如需要可限制为本站/OSS 域名白名单。

### L6. 空请求体时 `updateById` 空转一次

- **涉及文件**：`backend/src/main/java/cn/etarch/mao/user/service/UserService.java` — `updateOwnProfile()`
- **问题描述**：`{}` 请求体（三个字段均 null）会执行一次无实际变更的 `updateById`。无副作用，可在开头加"三个字段均 null 直接返回"短路。

### L7. controller 更新后 `selectById` 未判空

- **涉及文件**：`backend/src/main/java/cn/etarch/mao/user/controller/UserController.java` — `updateOwnProfile()`
- **问题描述**：极端并发删除场景下 `userMapper.selectById(userId)` 返回 null，`buildUserInfoVO` 触发 NPE（500）。概率极低，可改用 `userService.getUser(userId)`（内部已判空抛业务异常）。
