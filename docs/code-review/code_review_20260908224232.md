## P1

### P1-1. 宿主公开 API `inspectPage()` → `executePageAction()` 首次调用必然 `snapshot_expired`

**位置**
- `sdk/embed/src/page/engine.ts:81-88`（`beginTask()` 里 `this.manager.invalidate()`）
- `sdk/embed/src/page/engine.ts:199-202`（`ensureTask()`）
- `sdk/embed/src/page/engine.ts:175-184`（`executeAction()`）
- `sdk/embed/src/index.ts:66-70`（`inspectPage` / `executePageAction` 实现）

**问题**

本轮为修 P3-1（host `executePageAction` 在 `cancel()/newSession()` 后被 `cancelled` 永久阻断）新增了 `ensureTask()`：

```
private ensureTask(sessionId: number): void {
  if (this.activeSessionId == null) this.beginTask(sessionId);   // → manager.invalidate()
}
```

但 `beginTask()` 会调用 `this.manager.invalidate()` 把当前快照置空。而宿主公开 API 的正常用法是「先 `inspectPage()` 拿 snapshotId，再 `executePageAction(action, snapshotId)`」——`PageEngine.inspect()` **不会**调用 `beginTask()`，所以 `activeSessionId` 仍为 `null`；紧接着的 `executeAction()` 会走 `ensureTask()` → `beginTask()` → `invalidate()`，把刚 inspect 出来的快照清掉，随后 `executor.execute()` 的 `manager.resolve()` 返回 `snapshot_expired`。

实测（一次性临时用例，已删除）：

```
const snapshot = engine.inspect({ sessionId: 1 });            // 成功
await engine.executeAction({ type:'click', elementId:'e1' }, snapshot.snapshotId, 1);
// → { success:false, error:{ code:'snapshot_expired', message:'快照已失效…', elementId:'e1' } }
```

影响：`skills/mao-cli/reference/embed-sdk.md:25` 明确把 `inspectPage()` / `executePageAction(action, snapshotId?)` 列为公开实例方法。只要当前没有进行中的 Agent 页面任务（即宿主独立驱动页面操作的场景），首次动作就必失败；带 `elementId` 的动作全部不可用（`wait`/无 `elementId` 的 `scroll` 不受影响）。Agent 驱动的链路不受影响（`handleRequest` 先 `beginTask` 再 inspect，快照是在 invalidate 之后生成的）。

**修复建议（任选其一）**
1. 让 `PageEngine.inspect()` 也先 `ensureTask(sessionId)`，这样宿主 inspect 时就建立活动任务，后续 `executeAction()` 的 `ensureTask()` 变成 no-op，不再 invalidate（最小改动；注意会顺带把 `pageTaskActive` 置 true）。
2. 拆出「轻量复位」：`ensureTask()` 只复位 `cancelled` 并设置 `activeSessionId`，不调用 `manager.invalidate()`；`beginTask()` 保留 invalidate 语义供 Agent 首次请求使用。
3. `executeAction()` 先解析/保留快照引用再 `beginTask()`。
- 补回归用例：`engine.inspect()` → `engine.executeAction(action, snapId)` 断言不返回 `snapshot_expired`。

## P2

### P2-1. 单动作 `page_actions` 在 per_action 下被误报为「中断」

**位置**
- `sdk/embed/src/page/executor.ts:177-180`

**问题**

`executeBatch` 的暂停判定没有排除「已经是最后一步」的情况：

```
if (options.stopOnConfirmation && lastNeededConfirmation) {
  stoppedAt = index;
  reason = '已执行经用户确认的动作；per_action 下批量动作暂停，请逐个确认后继续';
  break;
}
```

当批量里只有一个写动作时（模型把「填一个字段」也包成 `page_actions` 很常见），执行完后 `stoppedAt=0`、`reason` 却说「暂停，请逐个确认后继续」，而 `handleBatch` 返回的 `success` 仍为 `true`。实测结果：

```
{ steps: 1, stoppedAt: 0, reason: '已执行经用户确认的动作；per_action 下批量动作暂停，请逐个确认后继续', success: true }
```

`tool-result-summarizer.ts` 会把它渲染成「执行批量页面操作 (1 步，中断于第 1 步)」。模型可能据此认为该动作未完成而重发同一批（对 `click` 类动作就是重复点击/重复提交）。

**修复建议**
- 仅在 `index < actions.length - 1` 时才设置 `stoppedAt/reason`（单动作批量视为正常完成）；或
- 用独立字段（如 `paused: true`）表达「因逐次确认而暂停」，并同步 `page-tools.ts` 的工具描述与 `tool-result-summarizer.ts` 的文案。
- 补用例：单动作批量断言 `stoppedAt === undefined`。

### P2-2. 并发页面工具调用的确认排队可能超过后端 180s 超时：动作仍执行，但结果被丢弃

**位置**
- `backend-ts/src/harness/core/agent-loop.ts:516`（同轮多个 tool call 用 `Promise.all` 并发派发）
- `sdk/embed/src/page/authorization.ts:228-257`（队列 + 单张 120s 超时）
- `backend-ts/src/harness/embed-page-tool-registry.ts:23-24`（`DEFAULT_PAGE_TOOL_TIMEOUT_SECONDS = 180`）
- `backend-ts/src/config/app-config.ts:169`（注释明确「需覆盖 SDK 确认超时 120s」）

**问题**

`stopOnConfirmation` 只约束**单个 `page_actions` 批量**内的确认次数，无法约束**同一轮并发的多个独立页面工具调用**（例如模型一轮里同时输出 `page_fill` + `page_click`）。这类调用经 `Promise.all` 并发发出，后端每个 future 各自从 t≈0 起算 180s；SDK 侧确认队列一次只展示一张卡片，第二张要等第一张处理完（或被 120s 定时器拒绝）才展示。

最坏情况：用户对第一张不响应 → 120s 时以拒绝结束 → 第二张 120s 才出现、240s 才超时。若用户在 180s~240s 之间点「允许本次」，动作会真实执行，但后端 future 已在 180s 以 `page_tool_timeout` 结束，`EmbedPageToolRegistry.complete()` 因 pending 已被删除而丢弃回包（`embed-page-tool-registry.ts:117-128`）。这正是第 3 轮 P2-3 想消除的「Agent 以为超时、页面却已执行」的副作用，只是从「批量内」转移到了「并发调用之间」。

**修复建议（任选其一）**
- 后端按会话串行化页面工具请求（同一 session 同时只允许一个 in-flight），让每个请求都拥有完整的 180s 确认窗口；
- 或 SDK 侧按剩余后端预算限制排队确认的等待时间（例如首张确认超时从 120s 降到 ~60s，使 2~3 张也能落在 180s 内），超预算直接以拒绝结束并让模型重试；
- 至少在文档/工具描述中说明「同一轮不要并发下发多个需要确认的页面写动作」。

## P3 / 备注（不阻塞）

1. **升级授权会拒绝正在等待的确认**：`setLevel()` 第一行 `cancelPendingConfirmations()`（`authorization.ts:136-138`）会把活动确认以 `false` 结束。用户在确认卡片弹出时点「完全授权 / 本次任务授权」，本意是放行，结果当前动作反而被 `authorization_denied` 拒绝（模型需重试才能成功）。建议按方向区分：升级（→task/full）时以 `true` 结束或保留挂起，仅降级/revoke/endTask 时拒绝。注意 `authorization.spec.ts` 现有用例断言了当前行为，需一并调整。
2. **构建产物与源码不同步**：`desktop/public/embed/mao-chat.js`、`mao-chat.v0.1.1.js`、`sdk/embed/dist/mao-chat.js` 的 `defaultRenderer` 内层 div 仍是 `width:${u}px">`，缺少 `screenshot.ts:129/137` 新增的 `${bodyMargin}`（产物 mtime 22:35:16 / 22:34:43，早于 `screenshot.ts` 22:35:44 的编辑）。提交/部署前需 `cd sdk/embed && npm run build` 并重新同步两份 `desktop/public/embed` 产物（P2-1~P2-4 的主体修复已在产物中，仅缺 body margin 补偿）。
3. **元素级遮罩受 `MAX_INLINE_ELEMENTS` 限制**：`defaultRenderer` 按索引对 `sourceNodes` 涂黑，而 `sourceNodes` 被 `slice(0, 2500)` 截断（`screenshot.ts:107,121`）。DOM 顺序在 2500 之后的敏感字段不会被元素级涂黑，只能靠 `maskRects` 兜底；在「滚动容器内 + 敏感字段位于截断之后」时 rect 兜底会错位，存在漏遮窗口。建议遮罩遍历用完整的 source↔clone 映射（或对遮罩单独放开该上限）。
4. **phase `IDLE` 未触发 `endTask()`**：`controller.ts:329` 只对 `COMPLETED/FAILED/CANCELLED` 调 `endTask()`，而 `WsTaskPhase` 含 `IDLE` 且 `store.ts:5` 的 `TERMINAL_PHASES` 也把 `IDLE` 视为终态。embed 会话的终态由 `task-terminal.service.ts` 产出（COMPLETED/FAILED/CANCELLED），实际风险低，但建议把 `IDLE` 一并纳入以防御。
5. **`desktop/package.json` 版本手改**：0.0.109 → 0.0.112 直接改文件，仓库约定用 `./scripts/changelog-extract.sh sync-desktop`。
