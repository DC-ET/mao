## 中等问题

### M1. 飞书用户「移除头像」后，下次飞书登录头像被回填，移除操作无法持久

- **位置**：`backend/src/main/java/cn/etarch/mao/auth/service/FeishuAuthService.java`，`findOrCreateUser()` 已存在用户分支（约 286-290 行）：

  ```java
  // 不覆盖用户已设置的（含手动上传的）头像，仅首次无头像时回填飞书头像
  if (!StringUtils.hasText(user.getAvatarUrl())) {
      user.setAvatarUrl(avatarUrl);
  }
  ```

- **问题**：本次需求新增了"移除头像"能力（`PUT /v1/users/me/profile` 将 `avatar_url` 置 NULL）。但 NULL 无法区分「从未设置过头像」与「用户主动移除」。飞书用户执行移除后，只要再次通过飞书登录（重新授权/扫码），`hasText(avatarUrl)` 为 false，飞书头像会被重新回填，用户刚移除的头像又回来了——移除操作对飞书用户实际上不可持久。
- **建议**：增加显式状态区分两种 NULL（如 `avatar_removed_at` 时间戳或标志位），回填前检查；或在本需求层面与产品确认该行为可接受（若接受则无需改动）。

## 低级别问题

### L1. email 缺少长度校验，超长邮箱导致 DB 异常（500）而非友好 400

- **位置**：`backend/src/main/java/cn/etarch/mao/user/service/UserService.java`，`updateOwnProfile()` 中 `EMAIL_PATTERN`：

  ```java
  private static final Pattern EMAIL_PATTERN =
          Pattern.compile("^[\\w.+-]+@[\\w-]+(\\.[\\w-]+)+$");
  ```

- **问题**：正则未限制长度，而 DB 列 `email VARCHAR(128)`（V001 迁移）。攻击或误输入一个数百字符的"邮箱"可通过后端校验，随后 MySQL 抛 `Data too long for column 'email'`，经全局异常处理大概率返回 500；同类字段 `displayName`（128）与 `avatarUrl`（512）均已有长度校验，唯独 email 缺失。前端邮箱输入框也无 `maxlength`。
- **建议**：`EMAIL_PATTERN` 前置 `(?=.{1,128}$)` 断言，或单独校验 `mail.length() <= 128`。

### L2. LDAP 用户被飞书登录绑定 `feishu_user_id` 后，authSource 误判为 FEISHU

- **位置**：`FeishuAuthService.findOrCreateUser()`（`findUserByEmail` 匹配分支）+ `UserService.resolveAuthSource()` 判定顺序。
- **问题**：LDAP 用户（`password_hash` 为空）邮箱若与飞书账号邮箱一致，飞书登录时 `findUserByEmail(email)` 会命中该 LDAP 用户并写入 `feishu_user_id`；之后 `resolveAuthSource` 按 `passwordHash → feishuUserId → LDAP` 的顺序判定，返回 FEISHU。该用户实际是 LDAP 目录账号，个人页登录方式标签与管理后台用户列表的 authSource 显示均错误（本次改动前该场景显示 LDAP，属行为变化）。同企业邮箱相同的情况在实际部署中并不罕见。
- **影响**：仅为展示/标签错误；前端对 FEISHU 与 LDAP 均禁用资料编辑，功能无差异。
- **建议**：飞书绑定前判断命中用户是否已有登录来源（如 `password_hash` 或历史 auth_type），或在 `resolveAuthSource` 中补充区分；低优先级。

### L3. ProfileView 表单快照在多标签页 / 外部变更场景下会回写旧值

- **位置**：`desktop/src/views/settings/ProfileView.vue`（`form` 与 `avatarUrl` 均取自已进入页面时的 `authStore.user` 快照）+ `UserService.updateOwnProfile()` 的"请求值 vs DB 值"比较策略。
- **问题**：若另一标签页（或管理后台、飞书登录）在用户进入本页后修改了 displayName/email/avatar，本页保存头像时会连同表单中的**旧值**一起提交；后端发现与 DB 当前值不同 → 判定"实际变更" → 覆盖回旧值。需求强调的"仅实际变更才写入"在此场景反而导致回写。单标签页常规操作不会触发。
- **建议**：保存前先 `GET /users/me` 拉取最新值做差异合并，仅提交真正被用户编辑过的字段（或后端改为增量语义）。

### L4. 保存成功后 `fetchUserInfo` 失败会误报"失败"，且重试会重复上传头像文件

- **位置**：`desktop/src/views/settings/ProfileView.vue` `save()`：

  ```js
  await api.put('/users/me/profile', { ... })
  await authStore.fetchUserInfo()   // 若此处抛错，进入 catch，误报保存失败
  ```

- **问题**：PUT 已成功、仅刷新用户信息失败时，前端落入 catch（拦截器提示失败），预览与 `selectedFile` 保留；用户重试会再次调用 `uploadImages` 上传同一文件（OSS/本地产生孤儿文件）并重复 PUT。
- **建议**：将 `fetchUserInfo` 移出 try 块单独 catch 静默处理（保存已成功，仅本地展示未刷新），或置为 finally 前的最佳尝试。

### L5.（提示）`UpdateWrapper.set(null)` 的运行时落库未被测试覆盖

- **位置**：`UserService.updateOwnProfile()` 置空分支 + `UserServiceTest.captureSqlSet()`。
- **说明**：单测仅断言 `getSqlSet()` 字符串包含列名，未断言参数值为 null 的真实 MyBatis 执行（Mockito 不落库）。经核对 MP 3.5.6 源码，`set(column, null)` 生成 `column = #{...}` 占位符，null 参数以 `setNull` 绑定，MySQL 下可正常置空，为官方推荐写法，风险极低。若希望 100% 稳妥可改用 `setSql("avatar_url = NULL")`。此条仅为提示，无需强改。
