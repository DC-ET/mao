# 代码审查报告：集成配置（LDAP/飞书/上传/Tavily/OSS）迁移至 system_setting

- 审查时间：2026-08-30 08:34
- 审查基线：工作区未提交改动（基于 origin/main @ 806aafc）
- 需求：将 LDAP、飞书 OAuth 登录、上传配置、Tavily API Key、OSS/STS 配置从 yml+环境变量迁移到 `system_setting` 表，管理后台可视化编辑、保存即生效。
- 审查范围：`backend-ts/src/settings/*`、`backend-ts/src/auth/*`、`backend-ts/src/oss/*`、`backend-ts/src/file/*`、`backend-ts/src/harness/tool/*`、`backend-ts/src/config/*`、`backend-ts/src/create-app.ts`、`backend-ts/db/migration/V093__settings_integration_config.sql`、`admin/src/views/settings/*`
- 验证手段：`tsc` 构建通过；`vitest` 148 个文件 / 1146 个用例全部通过。以下问题均为测试未覆盖的逻辑缺陷。

## 高严重度

### H-1 迁移迁移失败：`auth.ldap.enabled` / `auth.feishu.enabled` / `file.maxSizeMb` 的环境变量永远不会被导入，升级后 LDAP/飞书登录会静默关闭

- 位置：`backend-ts/db/migration/V093__settings_integration_config.sql`（第 9-11 行 UPDATE）+ `backend-ts/src/settings/settings-bootstrap.ts`（`row.value != null` 即跳过）
- 问题：
  - V048 早已插入 `('auth.feishu.enabled', 'false', ...)`, `('auth.ldap.enabled', 'false', ...)`, `('file.maxSizeMb', '50', ...)`，这三行 `value` 为**非 NULL**。
  - V093 对前两行只 UPDATE 了 `category/editable/description`，**没有清空 value**。
  - SettingsBootstrap 的导入条件是「仅当 DB 行 value 为 NULL」——因此 `LDAP_ENABLED=true`、`FEISHU_ENABLED=true`、`FILE_MAX_SIZE_MB` 这三个环境变量在升级后**永远不会导入**，DB 中保持 `'false'`。
  - 后果：生产环境原本通过 `FEISHU_ENABLED=true` + `FEISHU_APP_ID=xxx` 启用飞书扫码登录、通过 `LDAP_ENABLED=true` 启用 LDAP 登录的部署，升级后这两种登录方式**静默关闭**（`/v1/auth/features` 返回 `feishuEnabled:false`，LDAP `isConfigured()` 为 false），且无任何报错。与 CHANGELOG「升级首次启动自动将仍在的环境变量值导入数据库」的承诺直接矛盾。
- 修复建议：V093 中对这三行 UPDATE 时将 `value` 置为 NULL（例如 `UPDATE system_setting SET category='集成配置', editable=1, value=NULL WHERE setting_key IN ('auth.ldap.enabled','auth.feishu.enabled')`），让 Bootstrap 接管导入；或 Bootstrap 对 `editable=1` 且值为 V048 默认占位（'false'/'50'）的行做一次性覆盖。

### H-2 `GET /v1/files` 返回 Promise 数组，响应体退化为 `[{}, ...]`

- 位置：`backend-ts/src/file/file.routes.ts:52`（`toVO` 本次改为 `async function`）与 `:256`（`return sendOk(reply, files.map(toVO));`）
- 问题：本次改动将 `toVO` 从同步改为 async（内部需要 `await deps.getUploadBaseUrl()`），`POST /v1/files/upload` 与 `/upload-incoming` 两处调用均已补 `await`，但列表接口 `GET /v1/files` 漏改：`files.map(toVO)` 得到的是 `Promise[]`，`JSON.stringify(Promise)` 序列化为 `{}`，接口返回 `data: [{}, {}, ...]`。同时 N 个未 await 的 Promise 还会各自触发一次 `getUploadBaseUrl()` DB 查询，存在未处理 rejection 风险。
- 现状影响：目前 desktop/admin/agent-cli 均未消费 `GET /v1/files`（只用了 `workspace-list`/`project-list` 等子端点），故尚未暴露；但接口契约已破坏，一旦前端接入即出错。
- 为什么测试没抓到：`file.routes.spec.ts:80` 仅断言 `(await get('/v1/files')).code === 0`，未断言 `data` 内容。
- 修复建议：改为 `sendOk(reply, await Promise.all(files.map(toVO)))`，并在 spec 中补充对返回字段（如 `data[0].originalName`）的断言。

## 中严重度

### M-1 multipart 50MB 硬编码未与新的 `file.maxSizeMb` 配置联动，后台把上限调到 >50MB 实际无效

- 位置：`backend-ts/src/create-app.ts:310`（`app.register(multipart, { limits: { fileSize: 50 * 1024 * 1024, ... } })`）与 `:299`（`bodyLimit: 52MB`）
- 问题：本次将上传上限改为后台可配（`FileService.getMaxSizeMb` 动态读库，`validateValue` 允许任意正整数），但 `@fastify/multipart` 的单文件截断阈值仍是硬编码 50MB。管理员配置 `file.maxSizeMb=100` 后：50–100MB 的文件会在 multipart 层被截断抛 413 类错误，`FileService` 里友好的「文件大小超过限制: 100MB」提示永远不会出现；配置项名存实亡。
- 修复建议：注册 multipart 时按当前配置值取 max（如 `Math.max(50, 配置值)`）动态注册，或后台校验 `file.maxSizeMb` 上限 ≤ 50 并在描述中说明；同时让 `bodyLimit` 与之联动。

### M-2 「保存即生效」对已运行的桌面端不成立：desktop 侧上传配置为进程级缓存

- 位置：`desktop/src/utils/storageMode.ts:15-18`（`cachedConfig` 终身缓存，失效逻辑为空）
- 问题：本次后端 `/v1/upload/config` 改为实时读库，管理员把存储模式 local↔oss 切换或修改 baseUrl 后「保存即生效」；但桌面端 `getUploadConfig()` 首次请求后永久缓存，已打开的客户端必须重启才能拿到新配置，会出现「后台已切 OSS、客户端仍走本地上传（或反之）」的割裂状态。desktop 虽不在本次改动文件内，但该行为直接削弱本次需求的核心承诺，建议一并处理（如附时间窗 TTL 缓存，或保存配置时通知客户端失效）。

### M-3 前端无法清空 secret 类配置（后端支持、UI 无入口）

- 位置：`admin/src/views/settings/components/IntegrationConfigPanel.vue`（`saveGroup`：secret 留空一律提交 `null`=不修改）；`SystemSettingsView.vue` 的 `saveSetting` 同样把空串转 `null`
- 问题：后端语义链完整（`value=''` 表示清空，`null` 表示不变），但前端把「留空」固定映射为「不修改」，管理员没有任何途径清除已泄露/作废的 Tavily Key、OSS Secret 等（只能覆盖新值）。需求是「可视化编辑」，清空是编辑的基本能力之一。
- 修复建议：在 secret 输入框旁提供「清空」按钮（提交 `''`），或约定特定输入（如输入 `CLEAR`）为清空语义。

### M-4 V093 权限初始化硬编码自增 id + INSERT IGNORE，id 被占用时权限会静默缺失

- 位置：`backend-ts/db/migration/V093__settings_integration_config.sql:42-44`
- 问题：`INSERT IGNORE INTO permission (id,name,code,...) VALUES (8,...),(9,...)`。当前 V001 只用到 id 1-7，正常环境没问题；但若运维在迁移前手工插入过 id=8/9 的其他权限码，INSERT IGNORE 会**静默跳过**，`settings:read`/`settings:write` 不存在 → 所有系统设置接口（含只读 list）一律 403，且无任何日志可查。
- 修复建议：迁移中改用「按 code 先查后插」或直接不指定自增 id（`INSERT IGNORE ... (name,code,description) SELECT ... WHERE NOT EXISTS`），并给 role 1 授权部分同理。

## 低严重度

### L-1 `updateBatch` 逐条落库、无事务

- 位置：`backend-ts/src/settings/settings.service.ts`（`updateBatch` 第二个 for 循环）
- 说明：已做「先全量校验再写入」缓解，但极端情况（DB 中途故障、单条 `updateById` 失败）会留下部分写入。前端按卡片分组提交、组内字段无强一致依赖，风险低。建议后续用 `db.transaction` 包裹。

### L-2 前端菜单权限与后端接口权限粒度不一致

- 位置：`admin/src/router/index.ts:105`（settings 路由 `meta.permission: 'user:write'`）vs 后端 `settings:read`/`settings:write`
- 说明：拥有 `user:write` 但无 `settings:read` 的非 ADMIN 角色会看到「系统设置」菜单，进入后接口 403。本次 V093 只给 role 1 授权，日常仅 ADMIN 使用、影响有限；建议路由 meta 与权限码对齐。

### L-3 `oss.sts.maxSizeMb` 配置项迁移后依然没有消费方

- 位置：`V093` 插入该行（默认 50）+ `settings.service.ts` 返回 `sts.maxSizeMb`，但 `OssStsService`、`OssStsConfig` 及 desktop 的 `ossUpload.ts` 均未使用（迁移前 yml 版本同样无消费方）。
- 说明：属于「可编辑但不生效」的配置展示项，容易误导管理员以为改了就有直传大小限制。建议在描述中标注「暂未生效」或补齐 desktop 直传前的大小校验。

### L-4 LDAP 登录热路径的设置查询翻倍

- 位置：`backend-ts/src/auth/auth.service.ts:23-24`（`login` 中先 `await isConfigured()`（内部 `getLdapConfig()` 6 次查询），命中后 `authenticate()` 又 `getConfig()` 再查 6 次）；`web_search` 工具每次执行也查 2 次。
- 说明：功能正确，仅性能优化空间；可在 `AuthService.login` 中取一次配置传给 LDAP 认证，或给 `getLdapConfig` 加短 TTL 缓存（保存配置时本就无需重启，TTL 5-10s 即可）。

### L-5 测试连接接口间行为不一致：OSS 组不感知表单未保存的修改

- 位置：`settings.routes.ts`（`test/oss` 仅用已存配置 merge）vs `test/ldap`、`test/feishu`（merge 表单 overrides）；前端 `IntegrationConfigPanel.vue` 中 oss 组没有 `testPayload`
- 说明：用户在 OSS 表单填了新 AccessKey 未保存点「测试连接」，测的是旧凭证，成功/失败都可能误导。建议 oss 组也支持表单 overrides（secret 留空回落已存值）。

### L-6 `GET /v1/files` 的 spec 断言过弱

- 位置：`backend-ts/src/file/file.routes.spec.ts:80`
- 说明：只断言 `code===0`，导致 H-2 逃逸。建议对列表接口断言返回元素的具体字段。

## 已核实无问题的关键点（抽样）

- `FeishuAuthService.isEnabled` 改 async 后，所有调用方（`auth.routes.ts:20`、`create-app.ts:1399`、内部 `ensureEnabled`）均已 `await`，无遗漏的同步调用。
- secret 掩码链路闭环：`list` 掩码回显、前端留空提交 `null`、后端拒绝提交 `******` 掩码、`SETTINGS_SECRET` 缺失时保存报错/解密失败按未设置处理，均符合设计。
- Bootstrap 幂等性正确：后台保存过（含显式清空 `''`）的行不会被环境变量覆盖；secret 导入在主密钥缺失时跳过并 WARN，不落明文。
- Flyway（V093）在 `runSettingsBootstrap` 之前执行（`create-app.ts:296-298`），新行对 Bootstrap 可见。
- `SystemSetting.isSecret` 由 `is_secret` 列经 `toCamelList` 正确映射；`updateById` 不写 `is_secret` 亦无碍（该列仅由迁移维护）。
- OSS 未配置时 `getOssConfig()` 返回 null，`generateStsToken` 与 `test/oss` 均给出明确业务错误；`OssStsService` 客户端按配置指纹缓存，配置热更后自动重建。
- `web_search`/`generate_image` 的 `getConfig` 均在工具 try 块内，DB 异常会走 `errorJson` 兜底而非 500。
- `INTEGRATION_KEYS`（前端 26 个）与 V093 插入/更新的 26 个 setting_key 完全对齐；集成行已从普通分类 tabs 中排除，无重复展示。
- 权限码 8/9 与 V001 的 1-7 当前无冲突；role_permission 去重子查询写法正确。

## 结论

本次迁移整体结构清晰、测试覆盖较全，但存在 2 个高优先级缺陷必须在发版前处理：**H-1（升级后 LDAP/飞书登录静默关闭的迁移遗漏）** 直接违背需求目标与 CHANGELOG 承诺；**H-2（列表接口返回 Promise 序列化）** 是本次 diff 明确引入的接口行为破坏。建议修复 H-1/H-2 并评估 M-1/M-2 后再发布 0.0.75。
