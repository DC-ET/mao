# 代码审查报告：会话消息搜索功能

- 审查时间：2026-08-07
- 审查范围：本次「桌面端顶部操作栏会话消息搜索」需求涉及的未提交改动（后端 3 个 Java 文件 + 2 个测试文件，前端 6 个文件 + 1 个 E2E 测试）
- 结论：整体实现思路清晰（SQL 粗筛 + Java 纯文本二次校验 + 前端竞态控制），新增单测全部通过（16 + 2）。发现 1 个中等、3 个低严重度问题，均不影响主流程，但存在「真实命中会话被静默剔除（假阴性）」的边界缺陷，建议修复。

## 【中】二次查询全局 `LIMIT 200` 会静默丢弃部分真实命中的会话

**位置**：
- `backend/src/main/java/cn/etarch/mao/session/mapper/MessageMapper.java` 第 66-77 行（`selectMessagesForSearch`，`ORDER BY m.id ASC LIMIT 200`）
- 配合 `backend/src/main/java/cn/etarch/mao/session/service/SessionService.java` 第 453-469 行的二次校验循环

**问题描述**：
第一层候选最多 20 个会话；第二层 `selectMessagesForSearch` 在**全部候选会话上**只取 200 条命中消息（`ORDER BY m.id ASC`，即优先取 id 较小的旧消息）。若 20 个候选会话的命中 user 消息总数超过 200 条，则排在后面的会话（或消息 id 较新的会话）一条消息都取不到：
- `messagesBySession.getOrDefault(s.getId(), List.of())` 返回空列表 → `snippet` 为 null → 第 469 行 `continue` 把该会话整体剔除。

**影响**：
真实包含关键词的会话会从搜索结果中消失（假阴性），搜索结果不完整。该场景并不罕见：长会话中用户高频词（如「帮我」「请」「修复」）极易命中 200+ 条 user 消息，一旦某几个会话占满 200 条配额，其余会话全部漏检，与「检索主会话与边路会话」的功能预期不符。

**建议修复方向**：
Service 层每条会话只需要「第一条命中消息」即可生成 snippet，无需取回全部命中消息。建议：
- 方案 A（推荐）：将二次查询改为每会话只取 1 条最早命中消息，例如用窗口函数 `ROW_NUMBER() OVER (PARTITION BY m.session_id ORDER BY m.id) = 1`，去掉全局 `LIMIT 200`（候选最多 20 个会话，取 20 条消息即可）；
- 方案 B：保留全局 LIMIT，但改为按会话分组限制（`LIMIT` 无法直接 per-group，需子查询/union）；
- 方案 C（最小改动）：若坚持全局 LIMIT，需在 Service 侧对「候选存在但无消息返回」的会话发起补偿查询（不推荐，增加复杂度）。

## 【低】搜索请求在途时按 Enter 会跳转到上一次的旧结果

**位置**：
- `desktop/src/components/search/SessionSearchPopover.vue` 第 134-150 行（`runSearch`：请求开始时只置 `status='loading'`，**未清空** `results`/`activeIndex`）
- 第 153-168 行（`onPanelKeydown`：`Enter` 分支无状态校验，直接读 `results.value[activeIndex.value]`）

**问题描述**：
输入新关键词触发请求后（含 300ms 防抖窗口与请求在途期间），`status='loading'` 时结果列表已被隐藏（模板 `v-else-if` 链），但 `results.value` 与 `activeIndex` 仍保留**上一次关键词**的旧数据。此时用户按 Enter，会基于旧数据执行 `handleJump`，跳到与当前输入无关的旧会话。

**影响**：
「输入新词后立即回车」这一常见操作会跳转到错误的会话，属功能正确性问题（虽然窗口期较短）。

**建议修复方向**：
- `runSearch` 开始时清空 `results.value` 并将 `activeIndex` 置 0（或加 `status` 判定）；
- 或在 `onPanelKeydown` 的 Enter 分支增加守卫：`if (status.value !== 'results' || !item) return;`，并在 loading 时回车直接触发立即搜索（跳过防抖）。

## 【低】`extractVisibleText` 对「恰好是合法 JSON 数组」的普通文本消息产生假阴性

**位置**：
- `backend/src/main/java/cn/etarch/mao/session/service/SessionService.java` 第 517-541 行（`extractVisibleText`）

**问题描述**：
纯文本 user 消息若**恰好以 `[` 开头且是合法 JSON 数组**（例如用户输入 `[1,2,3]`、`["登录","500"]`、`[{"a":1}]`），会进入 JSON 解析分支；解析成功后循环只收集 `type=="text"` 的 Map 元素，上述内容一个都不匹配 → 返回空字符串 → 第 462-469 行将其跳过（`text.isEmpty() → continue`），该消息即使真实包含关键词也会导致整个会话被剔除。

**影响**：
此类消息无法被搜到（假阴性），且用户无感知。注意反向场景（解析失败回退原文）是正确的；此处仅「合法 JSON 但非多模态结构」的文本消息受影响。

**建议修复方向**：
解析成功后若未提取到任何 `type=="text"` 部分，且该 JSON 结构不是预期的 content-part 数组（例如没有任何元素含 `type` 键），则回退返回原文，交由第二层 `buildSnippet` 判断是否真实命中；或至少当提取结果为空时，用原文再做一次 `buildSnippet` 校验。

## 【低】SQL LIKE 与 Java 二次校验的匹配语义不完全一致（重音/特殊字母）

**位置**：
- `backend/src/main/java/cn/etarch/mao/session/service/SessionService.java` 第 509-511 行（`indexOfIgnoreCase`）及其注释「与数据库 utf8mb4 默认 collation 的匹配行为一致」

**问题描述**：
MySQL 8 默认 collation（`utf8mb4_0900_ai_ci`）对 ASCII 大小写**和重音**均不敏感（如 `café` ≡ `cafe`，德语 `ß` 可匹配 `ss`），而 Java 侧 `toLowerCase(Locale.ROOT)` 只做 ASCII 大小写折叠，不处理重音/扩展字符。因此含重音字母的关键词会「SQL 第一层命中、Java 第二层未命中」→ 会话被剔除（假阴性）。注释对「匹配行为一致」的表述仅对纯 ASCII 成立。

**影响**：
仅影响含重音/特殊拉丁字母的搜索词（如搜索 `cafe` 找不到含 `café` 的会话）。对中文内容无影响，属边缘场景。

**建议修复方向**：
- 若接受该边界，建议修正注释，明确只保证 ASCII 大小写不敏感；
- 若需严格一致，可在 Java 侧用 `java.text.Normalizer`（NFD 去重音）做规范化匹配，或接受该差异（推荐前者）。
