## 一、轻微问题

### 1. 新建任务首发失败回填：旧 blob 预览 URL 在新 URL 创建之前即被 revoke，存在中间态失效窗口；且回填未校验当前 draftKey 是否仍为 'new'

- **严重程度**：轻微（低频复合场景；最坏后果为图片缩略图短暂裂图或预览失效，文本与文件本体不受影响，可正常重发）
- **位置**：
  - `desktop/src/components/chat/ChatPanel.vue:635-643`（首发失败回填分支）
  - `desktop/src/components/chat/ChatInput.vue:1170-1188`（restoreContent：先 clearInput 再重建预览）
- **描述**：回填分支的处理顺序是：① 对草稿条目中的旧预览 URL 执行 `URL.revokeObjectURL`；② `clearDraft('new')`；③ `restoreContent(entry.text, entry.files)`——其内部先 `clearInput()`（此时组件 `props.draftKey` 已因路由跳转变为 `'s:{newId}'`，清除的是新会话键，对 'new' 无操作），再按文件类型重新 `createObjectURL` 生成新预览。整体自洽，但有两处瑕疵：
  1. **revoke 先于重建**：旧 URL 被显式 revoke 后，新 URL 要等到 `restoreContent` 内部 `addPendingImage` 才创建。虽然当前代码同步执行、中间不会渲染，但若 `entry` 中存在**非图片文件**（`filePreviewUrls` 对应位为空串，revoke 循环已用 `if (url)` 防护，此路径安全），或未来 `restoreContent` 改为异步/分帧执行，就会出现"草稿已回填但预览指向已释放 URL"的中间态。更重要的是，该分支绕过了 ChatInput 统一的 URL 所有权规则（卸载/清除时才 revoke），属于对同一 blob URL 的第二处释放点，后续维护容易顾此失彼。
  2. **未校验当前键**：回填条件只校验了 `generation === sendGeneration && draftKeyAtSend === 'new'`，未校验 `currentDraftKey.value === 'new'`。若保存确认失败前用户已手动点回"新建任务"模式并输入了新内容，`restoreContent` 会先 `clearInput()` 把用户新输入的内容连同其草稿键（'new'）一起清掉，再覆盖为失败草稿——用户的新输入丢失。此窗口内 `generation` 仍相等（切模式不递增 sendGeneration），故保护未生效。
- **建议修复方向**：① 将旧 URL 的释放延后到 `restoreContent` 成功重建预览之后，或干脆不在此处 revoke（交给 `clearInput`/卸载逻辑统一管理，'new' 条目已被 clearDraft 删除，卸载时无条目自然 revoke）；② 回填前增加"输入框当前为空或用户确认覆盖"的校验（如 `chatInputRef.value?.hasDraft()` 为 true 时先提示，与队列撤回编辑 `handleQueueEdit` 的交互保持一致）。

### 2. 主会话队列发送路径：`clearInput()` 依赖"当前" draftKey 联动清草稿，await 期间用户切走会话时可能清错槽位（误清新会话草稿 / 漏清目标槽位由显式 clearDraft 兜住）

- **严重程度**：轻微（触发需同时满足：会话 RUNNING/WAITING_APPROVAL 走队列 + 队列路径内图片/文件上传或 WS 建连耗时 + 用户恰在 await 完成前后切换会话；毫秒级窗口，后果为新会话正在编辑的草稿被误清）
- **位置**：
  - `desktop/src/components/chat/ChatPanel.vue:613-620`（队列分支：`await sendMessageWithQueue(...)` 之后才执行 `clearDraft(draftKeyAtSend)` 与 `chatInputRef.value?.clearInput()`）
  - `desktop/src/composables/useChat.ts:870-887`（`sendMessageWithQueue` → `enqueueMessage` 内含 `uploadChatImages` / `uploadPendingFiles` / `connect` 多个 await，中途 `requireCurrentSession` 失败会提前返回 false）
  - `desktop/src/components/chat/ChatInput.vue:1146-1157`（`clearInput` 内部按 `props.draftKey`（当前键）联动 `clearDraft`）
- **描述**：队列分支在 `await` 之前捕获了 `draftKeyAtSend`，显式清除目标槽位这半边是对的。但 `chatInputRef.value?.clearInput()` 内部会执行 `draftStore.clearDraft(props.draftKey)`——用的是**执行时刻**的当前键。时序推演：
  1. 用户在会话 A（RUNNING）发送队列消息，`draftKeyAtSend = 's:A'`；
  2. `enqueueMessage` 内部 await 上传/建连期间，用户切到会话 B：draftKey watcher 先 `saveDraft('s:A')` 把未发送内容存入 A 槽位（此时消息尚未入队，保留草稿合理），再恢复 B 的草稿到编辑器；
  3. `enqueueMessage` 恢复执行：若此时才走到第二步 `requireCurrentSession(sid)`，返回 false → `sent === false` → 不清任何草稿，行为正确；若校验已在切换前全部通过、仅剩同步收尾，`sent === true`；
  4. `sent === true` 时：`clearDraft('s:A')` 清目标槽位（正确）；随后 `clearInput()` 按当前键 `'s:B'` 联动清除——**把用户在 B 会话正在编辑的草稿清掉了**（包括编辑器内容、待发文件及其 blob URL，并标记 `clearedKeys`）。用户在 B 的未发送内容无端丢失。
  首发路径（`sendMessageAndWaitForSave`）不存在此问题，因其用 `generation === sendGeneration` 拦截了跨会话的 `clearInput`；队列路径缺少同等的 UI 保护。等待保存路径（ChatPanel.vue:627-632）同样有 generation 校验，仅队列分支遗漏。
- **建议修复方向**：与首发/等待保存路径对齐——队列分支在 `sent === true` 时也校验 `generation === sendGeneration`（发送前 `++sendGeneration`，或复用现有代次变量）后再调用 `chatInputRef.clearInput()`；或将 `clearInput` 的草稿联动改为可选参数（如 `clearInput({ keepDraft: true })`），队列路径只清 `draftKeyAtSend` 槽位，编辑器 UI 的清空交给键切换 watcher 的恢复逻辑处理。

## 二、已核查无问题的关键点（供回归参考）

1. **clearedKeys 语义闭环**：`clearDraft` 标记 → 兜底 `saveDraft` 跳过（ChatInput.vue:733）→ `setDraft` 写入解除标记（draft.ts:39）→ `reset` 全清（draft.ts:62）；`isCleared` 仅在 ChatInput 内部使用，未泄漏到业务层。
2. **SideChatPanel 双路径清草稿**：队列路径显式 `clearDraft(props.tabId)`（SideChatPanel.vue:530）+ 等待保存路径捕获 `draftKeyAtSend` 后清除（617），二者幂等；tab 关闭/晋升后晚到的保存确认只清一个不存在的键，无副作用。边路 `tabId` 在占位→正式 ID 演变中恒定（useCenterTabs.ts:227 注释"不改变 tab.id"），草稿键稳定。
3. **删除会话**：`deleteSession` 的 `clearDraft('s:'+sid)` 收口于 API 删除成功之后（session.ts:1022），API 抛错则不清，语义正确；配合 clearedKeys，KeepAlive 淘汰卸载的晚到兜底保存不会复活条目。
4. **删除边路任务 / 晋升**：TaskView.vue:588-590、604-606 在 `closeTab` 后立即 `clearDraft(tab.id)`；晋升后路由跳转新主会话，旧 tab 草稿已清。
5. **登出**：`logout()` finally 块中 `useDraftStore().reset()`（auth.ts:89），与 session reset 同步；TopNav 登出后整页 reload 双保险。
6. **blob URL 所有权主链路**：卸载时仍有草稿条目则不 revoke（ChatInput.vue:1196-1200）；`removePendingFileAt` 因浅拷贝隔离不再影响 store 快照。
7. **restoreContent 非图片文件支持**：按 `file.type` 分流 `addPendingImage` / `addPendingFile`，与 `handleDropFiles` 一致；`addPendingFile` 的 LOCAL 模式拦截在边路/主会话 CLOUD 模式下不触发（撤回回填仅发生在已有会话中，其执行模式与发送时一致）。
8. **uploadingFiles 恢复语义**：`restoreDraft` 统一置 false，与"恢复的都是本地已选定文件"前提一致；`handleSend` 的"文件上传中"拦截不受影响。
9. **GIT_SUGGEST_TEXT 自动填充**：仅在 `editor.isEmpty` 时填充，与草稿恢复无冲突。
10. **类型与测试**：`vue-tsc -b` 通过；draft store 单测 9/9 通过。
