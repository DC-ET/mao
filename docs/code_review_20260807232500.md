## 一、本轮新发现问题

### 【一般】1. 原子抢占 `.ne(phase, 'RUNNING')` 对 `phase IS NULL` 的行无效 → 崩溃窗口下子会话永久无法追问

- **位置**：`DelegateFollowupTool.java`（原子抢占条件）
- **问题**：SQL 三值逻辑下 `phase <> 'RUNNING'` 对 NULL 不匹配，`claimedRows=0` 返回误导性「正在执行中」。触发场景：子代理创建后、`executeVisible` 置 RUNNING 前进程崩溃 → 子会话有执行记录但 `phase=NULL`，`CrashRecoveryRunner` 只恢复 RUNNING 的会话 → 永久无法追问。
- **修复**：抢占条件改为 `.and(w -> w.ne(phase, "RUNNING").or().isNull(phase))`。`originalPhase=null` 时 skip 恢复分支 `isTerminalPhase(null)=false` 不误恢复，安全。

### 【一般】2. 取消/skip 路径下追问 USER 消息滞留子会话历史

- **位置**：`DelegateFollowupTool.java`（cancelled 分支）
- **问题**：skip 或执行中取消后，刚落库的追问 USER 消息永久留在历史中 → 「无应答用户消息」+ 连续 USER 消息（部分 LLM 端点 400）+ 子代理误判「连续追问两次」。
- **修复**：`saveMessage` 返回 Message 记录 id；cancelled 分支删除 `session_id=? AND id >= 追问USER消息id` 的全部消息（完整回滚本次追问产生的消息）。

### 【轻微】3. skip 恢复终态使用陈旧 `originalPhase`，极端并发下可能覆盖新终态

- **修复**：写回前重读当前 phase，仅当仍为本追问抢占的 RUNNING 时才恢复 originalPhase。

### 【轻微】4. 追问执行期间前端无法定位子会话

- **处理决定**：**不做**。属已确认「前端零改动」决策下的已知限制；结果返回后由 `child_session_id` 兜底。

### 【轻微】5. 失败结果摘要丢失 child_session_id

- **处理决定**：**不做**。错误响应多为校验失败（追问未开始），原始 delegate 结果仍在更早历史中。

### 【轻微】6. 测试覆盖缺口

- **修复**：新增用例——`claimSucceedsForNullPhase`（问题 1 回归）、`cancelDuringExecutionRollsBackMessages`（执行中取消回滚）；skip 测试同步验证消息回滚与恢复前重读。
