## 问题清单

### P1（中等）：`useForegroundRecovery` 在 `ws === null`（登录页 / 已登出）时也会整页刷新，与注释意图相反

- **位置**：
  - `desktop/src/composables/useForegroundRecovery.ts:33-36`
  - `desktop/src/composables/useStreamWS.ts:845-847`（`getReadyState`）
- **现象**：`maybeReload` 中注释明确写着「WS 未建立（从未连接 / 已登出 disconnect 置 null）：交给 useChat 建连或保持登出状态，不刷新」，但实现只有 `if (getReadyState() === WebSocket.OPEN) return`，其余一律 `window.location.reload()`。而 `getReadyState()` 为 `ws?.readyState ?? WebSocket.CLOSED`，**把 null 与 CLOSED 混为一谈**，ws 为 null 时返回 CLOSED(3) ≠ OPEN，照样刷新。
- **影响**：安卓登录页 / 登出状态下（此时 `disconnect()` 已把 `ws` 置 null），用户每次切后台再回前台都会触发整页 reload（10s 防抖内最多一次）。表现为登录输入丢失、白屏闪烁、重复拉取远程 SPA 浪费流量；且与代码注释（以及「保持登出状态，不刷新」的意图）直接矛盾。
- **修复建议**：让 `getReadyState()` 区分「未建立」与「已断开」，例如 ws 为 null 时返回哨兵值 `-1`；`maybeReload` 改为仅当 **ws 存在且非 OPEN** 时才刷新，即：
  ```ts
  const st = useStreamWS().getReadyState()
  if (st === WebSocket.OPEN || st < 0) return
  ```
  或明确按设计文档「非 OPEN 一律刷新」执行，同时修正注释，二选一保持一致。

### P2（低）：`connect()` 在旧 ws 处于 CLOSING/CONNECTING 且 `connectPromise` 为 null 的窗口内会重复建连，可能产生双连接

- **位置**：`desktop/src/composables/useStreamWS.ts:159-176`（`connect()`）
- **现象**：心跳超时 `ws.close()`（readyState=CLOSING）之后、onclose 派发之前（onclose 会把 `connectPromise` 置 null 并 `scheduleReconnect()`），若期间有代码调用 `connect()`（`sendReliable` 重连 / `useChat` 发消息），会直接 `new WebSocket` 覆盖旧 ws；随后旧 ws 的 onclose 触发 → `connectPromise = null` + `scheduleReconnect()` → 1s 后 `connect()` 发现新 ws 仍 CONNECTING 且 `connectPromise` 为 null → **再次新建 socket**，将前一个 CONNECTING 的 socket「孤儿化」。被孤儿的 socket 的 onopen/onmessage 仍会执行（闭包持有），造成双连接、双心跳、双订阅，流式事件可能重复叠加（如 content_delta 重复追加）。
- **背景说明**：该竞态是纯 JS 路径的**既有逻辑**（旧代码非桥分支同样存在），本次改动把安卓从「原生桥路径」切到「纯 JS 路径」，安卓首次暴露于该窗口。触发条件苛刻（close 与 onclose 之间微秒级窗口 + 期间必须有主动 connect 调用），实际概率极低。
- **修复建议（可选）**：`connect()` 开头对 `ws` 处于 `CONNECTING` / `CLOSING` 且 `connectPromise` 为 null 的情况做兜底（如 CONNECTING 时等待其终态、CLOSING 时直接复用并等 onclose），或在 `connectPromise` 置 null 前不新建 socket。属防御性加固，非本次需求阻塞项。

### P3（低 / 设计内提示）：冷启动防护 3s 对弱网初始建连不足，CONNECTING 态回前台会刷新

- **位置**：`desktop/src/composables/useForegroundRecovery.ts:24-25`（`COLD_START_GUARD_MS = 3_000`）
- **现象**：若初始建连超过 3s（弱网），用户在 3s 后切后台再回前台，此时 ws 处于 CONNECTING → 非 OPEN → 触发整页 reload，中断进行中的建连。
- **说明**：设计文档明确「回前台时 WS 非 OPEN（CLOSED / CLOSING / CONNECTING）直接整页 reload」，故属设计内行为，不算缺陷；但可将 CONNECTING 排除在刷新条件之外（重连/建连中本就无需刷新），进一步减少无谓刷新。仅作提示。

## 已核查且无问题的项

1. **残留引用**：`wsBridge` / `useAppResumeSync` / `trackSessions` / `untrackSessions` / `syncSubscriptions` / `stopKeepAlive` / `sendAsync` / `isNativeBridgeActive` / `createWsBridge` / `beginRecovery` / `pendingNavigate` / `getActiveBridge` 等关键词在 `desktop/src` 中均无残留（含 .ts / .vue）。
2. **类型检查**：`vue-tsc -b` 通过，无编译错误。
3. **`client` 取值**：`isAndroidCapacitor() ? 'android' : ...` 保留，符合设计。
4. **`disconnect()`**：删除原生桥提前 return 分支后，登出走纯 JS 路径（`ws.close()` + 置 null + 清订阅 + mcpClose），与原非桥分支一致。
5. **`sendReliable`**：`trySend` 由 async 改为同步，await 语义保持正确（首次失败 → `connect()` → 重试）。
6. **`subscribe` / `unsubscribe` / onopen 重订阅 / `flushPendingSkillSyncDones` / 心跳（5s ping / 15s pong 超时）** 逻辑与旧非桥分支完全一致。
7. **`useVersionCheck.ts`**：本地 `isAndroidCapacitor` 抽取至共享 `utils/capacitor.ts` 后行为一致（函数体相同），其余逻辑未变。
8. **`useForegroundRecovery` 触发时机**：仅 `visibilitychange` → visible 时检测；冷启动初始 visible 不触发；`initialized` 模块级防重入；仅安卓注册监听；reload 后 `bootAt`/`lastReloadAt` 重置由 3s 冷启动防护接管，无刷新循环。
9. **删除通知点击跳转（pendingNavigate）**：与原生保活/通知一并删除，属设计内（`AppNotification.java` 已删，不再有通知来源）。
