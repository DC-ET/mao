## 总体结论

**存在 1 个必须修复的高优先级问题（H1）**：邮箱唯一性校验未区分「邮箱是否实际变更」，在存在历史邮箱重复数据的场景下，会导致用户连头像都无法保存。其余为 2 个中优先级与若干低优先级问题，建议一并修复。

---

## 高优先级

### H1. 邮箱唯一性校验误伤「邮箱未变更」的保存，历史重复邮箱用户无法保存头像

- **位置**：`backend/src/main/java/cn/etarch/mao/user/service/UserService.java` `updateOwnProfile()` 第 167-179 行
- **问题描述**：
  1. 前端 `ProfileView.vue` 的 `save()` 无论邮箱是否修改，都会携带 `email` 当前值（`email: isLocalUser.value ? form.email : undefined`）；
  2. 后端只要 `email != null` 就执行 `selectCount(email = mail AND id != userId)` 查重，命中即抛「该邮箱已被其他用户使用」并**终止整个请求**；
  3. 而系统中邮箱重复是现实存在的：管理员 `createUser()`、LDAP 登录（`LdapAuthService` 无条件 `setEmail`）、飞书登录（`FeishuAuthService` 无条件 `setEmail`）均不校验邮箱唯一性，且 `V001__init_schema.sql` 中 `email` 列**无唯一索引**；
  4. 结果：若某 LOCAL 用户当前邮箱与任一 LDAP/飞书用户重复（历史遗留数据），该用户进入个人信息页后**上传头像也会被同一请求中的邮箱查重拒绝**，新功能完全不可用，且报错信息与头像无关，用户无从排查。
- **建议修复方向**：仅当邮箱实际发生变化时才查重，即先与 `user.getEmail()`（当前库内值）比较，`!mail.equalsIgnoreCase(user.getEmail())` 时才执行 `selectCount`；邮箱未变则直接放行。这同时能消除「每次保存都多做一次无意义查询」的冗余。

## 中优先级

### M1. LOCAL 用户被飞书按邮箱绑定后（authSource 仍显示 LOCAL），编辑的资料会被每次飞书登录覆盖

- **位置**：`backend/src/main/java/cn/etarch/mao/auth/service/FeishuAuthService.java` `findOrCreateUser()`（update 分支，约 307-320 行）；`UserService.resolveAuthSource()`（约 188-195 行）
- **问题描述**：
  - `findUserByEmail()` 会按邮箱匹配到已有 LOCAL 用户并写入 `feishuUserId`；此后该用户 `passwordHash` 与 `feishuUserId` 并存；
  - `resolveAuthSource()` 因 `passwordHash` 优先返回 `LOCAL`，前端据此**放开 displayName/email 编辑**；
  - 但飞书登录时 `user.setDisplayName(...)`、`user.setEmail(...)` **无条件覆盖**（本次只修复了头像不再覆盖）→ 用户在设置页改的显示名称/邮箱，下次飞书登录即被还原。用户感知为「改了又变回去」。
- **建议修复方向**：与头像处理保持一致——对已有 `passwordHash`（LOCAL）的用户，飞书登录不覆盖 displayName/email；或在 `resolveAuthSource` 中对「LOCAL+FEISHU 双绑定」用户返回 `FEISHU`，前端据此禁用资料编辑。

### M2. 邮箱唯一性校验存在并发竞态（TOCTOU），且 DB 无唯一索引兜底

- **位置**：`UserService.updateOwnProfile()`（selectCount 查重 + update 两步非原子）；`V001__init_schema.sql`（`email VARCHAR(128)` 无 UNIQUE）
- **问题描述**：两个用户并发提交同一新邮箱时，可能都通过查重并写入成功，产生重复邮箱。当前校验完全依赖应用层。
- **建议修复方向**：在 DB 层为 `email` 加唯一索引（需先清理既有重复数据），并在 `updateOwnProfile` 捕获 `DuplicateKeyException` 转为业务错误兜底。

### M3. 前端 `save()` 缺少 catch，保存失败产生未处理 Promise rejection 且预览状态残留

- **位置**：`desktop/src/views/settings/ProfileView.vue` `save()`（约 156-178 行）
- **问题描述**：`try { ... } finally { saving.value = false }` 无 `catch`。`api.put` 失败（业务错误或网络错误）时异常冒泡为 unhandled rejection；虽然 api 全局拦截器已 toast 错误，但若用户刚选了新头像，`previewUrl` / `selectedFile` 不会被清理（需求声明要「保存失败提示」，此处实际依赖拦截器而非页面自身处理）。
- **建议修复方向**：补 `catch` 分支——提示保存失败，并决定保留或清理预览态（保留可让用户直接重试，属合理交互，但需显式处理避免控制台报错）。

## 低优先级

### L1. 头像相对路径在 Electron（file://）环境不可用

- **位置**：`ProfileView.vue` / `TopNav.vue` 头像 `src`；`FileController.toVO()`（baseUrl 未配置时返回 `/uploads/xxx`）
- **问题描述**：若 `upload.base-url` 未配置，上传返回相对路径；Web 远程加载（https）下可用，但 Electron 打包（file:// + hash 路由）下 `el-avatar :src` 解析为 `file:///uploads/...` 无法显示。与既有聊天图片链路行为一致，但头像展示更前置，建议确认生产 `base-url` 已配置，或头像保存时统一转为绝对 URL。

### L2. 飞书用户移除头像后，下次飞书登录会回填头像

- **位置**：`FeishuAuthService.findOrCreateUser()`（`!StringUtils.hasText(user.getAvatarUrl())` 判断）
- **问题描述**：「仅首次无头像时回填」实际判断的是「当前无头像」，因此用户手动移除头像后，再次飞书登录头像会重新出现。符合当前设计注释，但可能让用户困惑，建议产品侧确认是否为预期行为（如需「永久移除」可考虑增加标记）。

### L3. 有头像的用户每次保存都会重写 `avatar_url` 列

- **位置**：`UserService.updateOwnProfile()`；前端 `save()` 中 `avatarUrl` 默认取当前值
- **问题描述**：未改动头像时前端仍传当前 URL，后端重新 `set` 一次，产生无意义的 UPDATE。与 H1 修复可一并解决（仅在字段变化时 set）。
