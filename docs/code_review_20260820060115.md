## 问题列表

### [中] 1. `deleteSession` 用 try/catch 包住全部数据库删除，任何失败都会被吞掉并返回成功

- 位置：`backend-ts/src/session/session.service.ts`（`deleteSession`，约 394-412 行）
- 问题：原实现中 `sessionRepo.lockActiveSessionById` / `compaction` / `messageRepo.logicalDeleteBySession` / `sessionRepo.logicalDelete` 任一抛出都会向上传播（路由返回 500）。改动后整个方法被 `try { ... } catch (e) { console.error(...) }` 包裹，**数据库删除失败、行锁失败等都会被吞掉**，`DELETE /v1/sessions/:id` 永远返回成功，而会话实际未被删除/半删除（DB 状态不一致：compaction 删了、message 没删等）。吞异常的本意是「文件清理失败不能影响会话删除」，但作用域过大，把数据库失败也吞了。另外 catch 后 `console.error` 的文案是 `Failed to delete runtime dir for session`，与实际吞掉的「会话删除失败」语义不符。
- 修复建议：将 try/catch 缩小到文件清理调用（`cleanupRuntimeDir` / `deleteRuntimeWorkspaceFiles`）上；数据库删除应先于文件清理，且数据库异常应继续抛出。

### [中] 2. `runtimeSessionCleanup` 收敛后，`runtime/{userId}/{sessionId}/skills` 与 `shellOutput` 目录残留且无其他清理路径

- 位置：`backend-ts/src/create-app.ts`（`runtimeSessionCleanup`，约 788-798 行）
- 问题：上一轮 `rmSync(sessionDir)` 会连带删除 `skills`（SkillSyncService 的运行时同步副本）、`shellOutput`（ShellSessionManager 写入的 stdout/stderr 文件）、`git-askpass.sh`。收敛为只删 `incoming` 后：
  - `skills` 目录由 `SkillSyncService.syncToSession` 在每次执行时创建（`mkdirSync(skillsDir, { recursive: true })`），会话删除后**不会**被任何路径清理（`localSkillRegistry.clear`/`closeByConversation` 只清内存/进程，不删目录）；
  - `shellOutput` 由 `ShellSessionManager.create` 创建并写 `<shellId>.out`，会话删除若未先 close 也会残留；
  - `git-askpass.sh` 由 git 工具写入 runtime 会话目录，同样残留。
  - 本地模拟验证：删除会话后 `runtime/7/11/` 下 `incoming` 被删，`skills/`、`shellOutput/` 保留。
  - 由于 `create-app.ts` 中对 PathSandbox **全局放行整个 runtime 根**，Agent 工具可以读取这些残留目录/文件（已删除会话的 shell 输出、技能副本），泄漏面扩大。
- 修复建议：`runtimeSessionCleanup` 改为删除整个 `runtime/{userId}/{sessionId}/` 目录（`rmSync(resolve(sessionDir), {recursive, force})`），或至少显式再删 `skills`、`shellOutput`、`git-askpass.sh`。若担心 shell 进程仍存活导致输出丢失，先按上一轮建议调用 `releaseSessionExecutionResources`（`closeByConversation`）。

### [中] 3. `upload-incoming` 上传的文件落在 runtime，但 `toVO().url` 仍指向 `/uploads/{storedName}` 静态目录，该 URL 不可用

- 位置：`backend-ts/src/file/file.routes.ts`（`upload-incoming` 分支，约 67-87 行）
- 问题：`uploadIncomingFile` 落盘在 `runtime/{userId}/{sessionId}/incoming/`，而 `toVO()` 的 `url` 无条件拼 `uploadBaseUrl + '/uploads/' + storedName`，指向静态 uploadDir，`GET /uploads/<uuid>.txt` 会 404（文件不在 uploadDir）。当前前端只消费 `absolutePath`，主链路不受影响；但 `GET /v1/files` 列表会把这些 incoming 文件也列出来（有 sessionId 过滤），返回的 `url` 全部不可用；`/v1/files/:id/download` / `preview` 走 `file.filePath`（能读对文件，行为正常）。属于数据一致性问题。
- 修复建议：给 `toVO` 增加区分：incoming 文件不返回 `url`，或将其 `url` 指向 `/v1/files/:id/download` 形式的合法下载地址。

### [低] 4. `safeExtension` 仅白名单校验扩展名，未处理 URL 编码形式的路径穿越文件名（`%2e%2e%2f`）

- 位置：`backend-ts/src/file/file.service.ts`（`buildFileEntity` / `safeExtension`，约 139-164、255-264 行）
- 问题：`basename` 能剥掉 `/`（POSIX），但路径穿越可以 URL 编码形式出现：`..%2F..%2Fevil.txt`、`%2e%2e%2f%2e%2e%2fevil.txt` 等。这类文件名经 `basename` 后**仍含 `%2e%2e%2f` 字面量**，`safeExtension` 因扩展名 `.txt` 合法而放行，storedName 为 `uuid.txt`（不会真的造成路径逃逸，因为只有扩展名部分被拼入），但 `originalName`（展示名/下载名）会保留编码字符串 `..%2F..%2Fevil.txt`，未来若其他链路按 originalName 反向拼路径存在潜在风险。另外 `C:\evil\a.txt` 在 Linux 下 `basename` 不剥 `\`，原始名含 `\` 字符（safeExtension 拒掉扩展名后 storedName 无扩展名，不逃逸，但展示/下载名含 `\`）。
- 修复建议：`basename` 后对 `%` 编码字符做解码剥离，或直接按安全字符集过滤整个文件名（如 `/^[^\\/:\\u0000-\\u001F]+$/` 再取），对含 `%`/`\` 的名字统一替换为 `_`。

### [低] 5. 前端并发上传的索引错位：`idx = pendingFiles.length` 配合 `splice` 会导致失败/删除后错删元素、引用插错位置

- 位置：`desktop/src/components/chat/ChatInput.vue`（`uploadFileToRuntime` 约 904-932 行、`removePendingFileAt` 约 935-942 行）
- 问题：`uploadFileToRuntime` 用 `idx = pendingFiles.length` 记位，`await` 完成后若此前有其他文件失败触发 `removePendingFileAt`（splice 改变数组索引），或用户手动把某个条目移出（`removeFile` → splice），再执行 `removePendingFileAt(idx)` / `uploadingFiles.value[idx] = false` 会错位：可能把**别的**待发条目移除、把上传中的标记清掉，或引用节点插入到错误位置。典型场景：用户同时选中多个文件（`for` 循环全部 `void uploadFileToRuntime`），第一个先失败、第二个后完成，第一个的 `removePendingFileAt(0)` 会把第二个条目删掉，而第二个完成时 `uploadingFiles.value[1] = false` 设置到已移位位置——UI 状态混乱。`removeFile`（用户点 ×）也会在等待期间发生：上传完成后仍会 `insertFileReferenceAt`，即使该条已被移除。
- 修复建议：为每个任务维护稳定标识（如自增 id 或直接按 File 对象引用定位），`removePendingFileAt` 改用 findIndex；上传完成/失败时用「文件对象匹配」而非保存的索引；删除中条目时同步标记任务已取消，完成后不再插入引用节点。

### [低] 6. `handleSend` 的 `uploadingFiles` 检查与「引用插入」存在 gap：上传成功但编辑器不可用时节点丢失

- 位置：`desktop/src/components/chat/ChatInput.vue`（`handleSend` 约 958-980 行、`insertFileReferenceAt` 约 944-955 行）
- 问题：`handleSend` 检查 `uploadingFiles.value.some(Boolean)` 后即发送。但 `uploadFileToRuntime` 在 `await` 完成后才 `insertFileReferenceAt`（该函数在 `editor.value` 为空时直接 return，不插入节点）。若用户在上传期间切换会话/组件卸载（`onBeforeUnmount` 未取消在途请求），文件已上传到 runtime 但引用节点从未插入，消息发送时 `text` 不含 `@{…}@`，上传的文件成为孤儿（文件仍占 runtime 磁盘，直到会话删除）。现有 `clearInput` 只清列表不清在途请求。
- 修复建议：在卸载/切换时 abort 在途上传（或完成后若组件已卸载则调用删除文件接口清掉）；或把「引用插入」与「发送」绑定为原子流程。

### [低] 7. `requireOwnedSession` 未用于 `upload-incoming`，且未校验 LOCAL/CLOUD 执行模式

- 位置：`backend-ts/src/file/file.routes.ts`（`upload-incoming` 分支，约 70-76 行）
- 问题：`upload-incoming` 手工 `getSession` + `userId` 比对，与 `requireOwnedSession` 重复；未校验 `executionMode` 为 CLOUD——LOCAL 会话也可通过该接口上传，落盘后服务器端 Agent 工具可读，但 LOCAL 模式语义上应由桌面端处理。攻击面较小（需已知 sessionId + 用户权限），但语义不严谨。
- 修复建议：复用 `requireOwnedSession`；如 LOCAL 会话不应支持服务端上传，增加 executionMode 校验。

### [低] 8. 代码风格残留：`deleteRuntimeWorkspaceFiles` 与 `promoteSideTaskToMainSession` 缩进错位

- 位置：`backend-ts/src/session/session.service.ts`（418-437 行）
- 问题：`deleteRuntimeWorkspaceFiles` 方法体缩进缺失（`try {` 顶格），`promoteSideTaskToMainSession` 的 `async` 关键字顶格（方法签名失去缩进）。上轮已指出缩进问题，但本次仅修正了死代码，这两个函数仍未对齐。非功能性，但影响可读性、易在后续 diff 中误判。
- 修复建议：对齐为标准缩进。

### [低] 9. incoming 文件经 `GET /v1/files` 暴露且 `url` 不可用，`DELETE /v1/files/:id` 仅逻辑删除、磁盘文件保留到会话删除

- 位置：`backend-ts/src/file/file.routes.ts`（`GET /v1/files`、`DELETE /v1/files/:id`）
- 问题：incoming 文件写入 `file` 表（sessionId 关联），`GET /v1/files?sessionId=..` 会返回它们（且 `url` 不可用，见 [中]3）；`/v1/files/:id` DELETE 为逻辑删除，磁盘文件在会话删除前不回收。设计上可接受，但无独立清理机制，若用户上传了大量文件并手动删除会话前逐个删除记录，磁盘占用不可回收。
- 修复建议：如不需要在列表中暴露 incoming 文件，可在 `list` 时过滤；或补充「删除 file 记录即删除磁盘文件」的策略。
