# 未提交代码审查报告

审查范围：当前 Git 工作区未提交的代码变更；忽略页面样式和文档变更。

## 结论

发现 5 个会影响业务正确性的问题。

## 1. [高] 无 MCP 管理权限的用户可关联服务器并取得明文凭据

**位置：**
- `backend/src/main/java/cn/etarch/mao/agent/controller/AgentController.java:45-72`
- `backend/src/main/java/cn/etarch/mao/agent/service/AgentService.java:67-73`
- `backend/src/main/java/cn/etarch/mao/agent/service/AgentService.java:121-127`
- `backend/src/main/java/cn/etarch/mao/harness/mcp/local/McpSyncService.java:108-128`

Agent 创建、更新接口可直接接收任意 `mcpServerIds`，但没有校验调用者是否具备 `mcp:read`/MCP 使用权限，也没有验证这些服务器 ID。迁移脚本却只把 MCP 权限授予管理员。

普通用户可绕过管理后台，直接在 Agent 请求中提交已知或猜测的服务器 ID。LOCAL 会话启动后，`buildSyncPayload()` 会读取这些全局配置、解密 `env_json`，并将明文环境变量发送到该用户的 Electron 客户端。这会让未授权用户调用管理员配置的 MCP 服务，并可能获得 API Token 等敏感凭据。

建议在 Agent 关联 MCP 服务器时校验资源和使用权限，并重新确认 LOCAL 模式下长期凭据的下发边界。

## 2. [中] LOCAL Side Task 首轮不会加载 Agent 关联的 MCP 工具

**位置：**
- `backend/src/main/java/cn/etarch/mao/session/ws/StreamingWsHandler.java:1048-1060`
- 对照正常消息路径：`backend/src/main/java/cn/etarch/mao/session/ws/StreamingWsHandler.java:518-531`

普通 LOCAL 消息在执行前调用 `syncMcpServersToClient()`，但 Side Task 创建后直接执行 `executeSideFirstMessage()`，没有进行 MCP 同步。MCP 工具缓存又按独立的 `sideSessionId` 隔离，因此父会话已同步的工具也无法复用。

结果是 Side Task 的首条消息中，关联的 MCP 工具不会进入模型工具清单，Agent 无法发现或调用这些工具。

## 3. [中] 合法的服务器名包含连续下划线时，LOCAL 工具无法调用

**位置：**
- `backend/src/main/java/cn/etarch/mao/harness/mcp/service/McpServerService.java:29,236-244`
- `backend/src/main/java/cn/etarch/mao/harness/mcp/model/McpToolRef.java:35-37`
- `desktop/electron/main.cjs:1332-1341`

服务端名称校验允许下划线，因此 `foo__bar` 是合法 MCP 服务器名。生成的工具名为 `mcp__foo__bar__toolName`，但 Electron 使用第一个 `__` 拆分服务器名和工具名，最终解析为服务器 `foo`、工具 `bar__toolName`。

实际连接缓存的 key 是 `foo__bar`，调用时会报服务器未连接。所有名称包含 `__` 的合法配置在 LOCAL 模式下均不可用。

## 4. [中] LOCAL 模式丢弃 MCP 工具的顶层结构化结果

**位置：** `desktop/electron/main.cjs:1435-1443`

`callMcpTool()` 只把 `result.content` 传给 `formatMcpContent()`。MCP 的 `CallToolResult` 可以将结构化输出放在顶层 `result.structuredContent`；尤其声明 `outputSchema` 的工具可能主要或仅返回该字段。

此类合法响应会被格式化为空字符串并发送给模型，导致模型误判工具没有输出、重复调用或基于缺失数据作答。当前 `formatMcpContent()` 对 `structuredContent` 的分支无法处理该情况，因为调用方已经丢弃了完整的 `result`。

## 5. [中] MCP 同步缺少轮次标识，迟到报告可能完成错误的一轮同步

**位置：**
- `backend/src/main/java/cn/etarch/mao/session/ws/StreamingWsHandler.java:90-91`
- `backend/src/main/java/cn/etarch/mao/session/ws/StreamingWsHandler.java:1445-1460`
- `backend/src/main/java/cn/etarch/mao/session/ws/StreamingWsHandler.java:1512-1517`

`pendingMcpSyncs` 只以 `sessionId` 为 key，下发的 `mcp_sync_required` 和回传的 `mcp_tools_report` 没有 `syncId` 或 generation。

如果一轮同步超时后桌面端报告迟到，而同一会话已经开始下一轮同步，旧报告会覆盖当前工具缓存并完成新一轮的 Future。Agent 随后可能使用旧配置或旧 schema 开始执行；与此同时桌面端正在重建连接，工具调用还可能因连接与 schema 不一致而失败。

建议为每次同步生成唯一标识，只接受与当前等待轮次匹配的报告。

审查过程中后端完整测试、Admin 构建、Desktop 构建及 Electron 语法检查均通过；现有测试未覆盖上述场景。
