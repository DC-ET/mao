## 高严重度

### H1. 登录 / 刷新 / LDAP / 飞书登录响应中的 UserInfoVO 均未填充 `authSource`

- **涉及文件与位置**
  - `backend/src/main/java/cn/etarch/mao/auth/service/AuthService.java`：`buildLoginResult()`（约 L61-70）、`refreshToken()`（约 L93-101）
  - `backend/src/main/java/cn/etarch/mao/auth/service/LdapAuthService.java`：`authenticate()` 构建 `UserInfoVO` 处（约 L114-121）
  - `backend/src/main/java/cn/etarch/mao/auth/service/FeishuAuthService.java`：`buildLoginVO()`（约 L369-376）
  - 前端依赖方：`desktop/src/stores/auth.ts`（`applyLogin` 直接使用登录响应作为 `user`）、`desktop/src/views/settings/ProfileView.vue`（`isLocalUser = authStore.user?.authSource === 'LOCAL'`）、`desktop/src/components/common/TopNav.vue`
- **问题描述**
  - 本次改动仅在 `AuthController.UserInfoVO` 声明了 `authSource` 字段，且只在 `UserController.buildUserInfoVO()`（即 `GET /users/me`）中填充。登录、刷新 token、LDAP 认证、飞书登录四个入口构造的 `UserInfoVO` **都没有 `setAuthSource(...)`**。
  - 前端 `applyLogin()` 直接把登录响应赋给 `authStore.user`，而路由守卫 `beforeEach` 只在 `!authStore.user` 时才调用 `fetchUserInfo()`（`desktop/src/router/index.ts` L100-110）。因此**用户登录成功后（未刷新页面）直接进入设置页时，`authStore.user.authSource` 为 `undefined`**。
  - 后果：
    1. 本地（LOCAL）用户此时 `isLocalUser === false` → 显示名称/邮箱输入框被禁用、错误提示"LDAP / 飞书账号的资料由系统维护，仅可修改头像"；
    2. `save()` 因 `isLocalUser` 为 false 而不发送 `displayName/email`（传 `undefined`）→ 后端不更新 → **本地用户无法编辑资料**；
    3. "登录方式"标签显示"—"而非"本地账号/飞书/LDAP"。
  - 该问题仅在刷新页面（触发守卫 `fetchUserInfo`）或保存过一次头像后（`save()` 内调用 `fetchUserInfo`）自愈，但"登录 → 设置 → 个人信息 → 编辑资料"是本次需求的核心路径，属必现缺陷。
- **建议修复方向**
  - 方案 A（推荐）：在 `AuthService.buildLoginResult`、`AuthService.refreshToken`、`LdapAuthService.authenticate`、`FeishuAuthService.buildLoginVO` 四处构建 `UserInfoVO` 时统一注入并调用 `userService.resolveAuthSource(user)` 填充 `authSource`（注意这几个类与 `UserService` 的依赖注入关系）。
  - 方案 B（兜底）：前端 `applyLogin()` 后统一追加一次 `fetchUserInfo()`，用 `/users/me` 的结果覆盖 `user`；但需处理飞书轮询 `pollFeishuLogin` 路径与失败降级。

## 中严重度

### M1. 后端对 `avatarUrl` 无任何校验（长度 / 协议）

- **涉及文件与位置**
  - `backend/src/main/java/cn/etarch/mao/user/service/UserService.java`：`updateOwnProfile()`（约 L139-144）
  - `backend/src/main/java/cn/etarch/mao/user/controller/UserController.java`：`UpdateOwnProfileRequest`
- **问题描述**
  - `avatar_url` 列为 `VARCHAR(512)`（`V001__init_schema.sql` L8），但 `updateOwnProfile` 直接接受任意字符串，无长度校验：恶意/异常客户端提交超长串会触发 MySQL Data truncation 导致 500。
  - 无协议/格式校验：可存入 `javascript:` 等非 http(s) URL，虽经 `<img>` 渲染脚本不会执行（XSS 风险低），但可被用来存放任意第三方/内网地址，作为头像展示。
- **建议修复方向**
  - 在 `updateOwnProfile` 中对 `avatarUrl` 增加校验：非空时长度 ≤ 512，且协议须为 `http://` 或 `https://`（本地模式上传返回的相对路径 `/uploads/...` 需一并兼容，可做"相对路径或 http(s) 绝对路径"白名单）；非法时抛 `PARAM_INVALID`。

### M2. 非 LOCAL 用户提交"资料 + 头像"混合请求时校验时机靠事务回滚兜底

- **涉及文件与位置**
  - `backend/src/main/java/cn/etarch/mao/user/service/UserService.java`：`updateOwnProfile()`（L131-147）
- **问题描述**
  - 逻辑本身正确（`@Transactional` 下先改头像再抛异常会回滚），但可读性/健壮性略弱：LDAP/飞书用户在同一个请求中同时提交 `avatarUrl` 和 `displayName` 时，`avatarUrl` 的修改发生在权限校验之前，依赖回滚才能保持数据一致。
- **建议修复方向**
  - 将"非 LOCAL 用户不可改资料"的校验提前到 `avatarUrl` 处理之前，先校验再赋值，避免依赖事务回滚，逻辑更清晰。

## 低严重度

### L1. 头像上传失败时预览残留、无失败提示

- **涉及文件与位置**：`desktop/src/views/settings/ProfileView.vue`：`save()`（约 L147-160）
- **问题描述**：`uploadImages()` 返回空数组时直接 `return`，此时 `previewUrl`/`selectedFile` 未清理，用户看到"已预览但未保存"的状态，且无"保存失败"提示（仅上传环节内部提示过）。
- **建议修复方向**：失败分支清理预览态并 `ElMessage.error('头像上传失败，请重试')`；或保留预览允许重试（二选一，保持状态一致即可）。

### L2. 邮箱唯一性未校验

- **涉及文件与位置**：`UserService.updateOwnProfile()`（email 分支）
- **问题描述**：LOCAL 用户可把邮箱改成与其他用户重复；系统既有 `createUser`/`updateUser` 也均未校验邮箱唯一性，属既有设计延续，非本次引入，但既然新增自助改邮箱入口，建议评估是否补充唯一性约束（表层面或应用层面）。
- **建议修复方向**：如产品要求邮箱唯一，可在 `updateOwnProfile` 增加 `selectCount(email)` 校验并排除自身；否则记录为已知行为即可。

### L3. 顶栏下拉"设置"入口跳转变更

- **涉及文件与位置**：`desktop/src/components/common/TopNav.vue`：`handleCommand()`（L306-313）
- **问题描述**：下拉"设置"由原 `/settings/git-credentials` 改为 `/settings`（重定向到 `/settings/profile`），属需求有意调整；仅提醒确认其他依赖"设置下拉直达 Git 凭证"的习惯路径是否可接受，无功能错误。
