# 子代理崩溃恢复功能第三次增量复审报告

- 复审时间：2026-08-15 14:27:33
- 历史报告：`docs/code_review_20260815140829.md`、`docs/code_review_20260815141539.md`
- 审查范围：当前工作区中与子代理重启恢复、原 execution 续跑和父结果幂等交付相关的 Java/TypeScript 功能代码
- 结论：**仍存在重大功能 Bug。构建问题已修复，但“终稿已落库、execution 尚未终态化”的关键崩溃窗口仍未被关闭；TypeScript 首次 delegate 路径甚至仍未写 `final_message_id`。**

## 高（核心恢复语义仍可能重复运行子代理）

### 1. `final_message_id` 仍在终稿落库之后才更新，无法覆盖它本应解决的崩溃窗口

**代码位置**

- Java 终稿由 AgentLoop/Harness 持久化，工具返回后才查询并更新 execution：
  - `backend/src/main/java/cn/etarch/mao/harness/core/HarnessService.java:100-160`
  - `backend/src/main/java/cn/etarch/mao/harness/tool/impl/DelegateTool.java:313-328,448-473`
  - `backend/src/main/java/cn/etarch/mao/harness/tool/impl/DelegateFollowupTool.java:385-414,529-554`
- TypeScript follow-up 同样在执行返回后才查询并更新：
  - `backend-ts/src/harness/core/agent-loop.ts:224-235`
  - `backend-ts/src/harness/tool/impl/delegate-tool.ts:406-416,486-507`
- 两套恢复逻辑只有在 `final_message_id` 已写入时才无条件复用终稿；字段为空时要求子会话已经处于终态才会推断终稿：
  - `backend/src/main/java/cn/etarch/mao/harness/delegate/SubagentExecutionRecoveryService.java:143-147`
  - `backend-ts/src/harness/delegate/subagent-execution-recovery.service.ts:109-120`

**问题说明**

本轮确实增加了在 `markExecutionTerminal` 中查询最终 ASSISTANT 并写入 `final_message_id`，但该更新仍发生在 AgentLoop 已单独提交最终 ASSISTANT 消息之后。以下窗口依然存在：

1. AgentLoop/Harness 将最终 ASSISTANT 消息提交到数据库；
2. `executeVisible` 返回前后，后端立即重启；
3. `markExecutionTerminal` 尚未执行，因此 execution 仍为 `RUNNING`、`final_message_id` 仍为空；
4. `finishSubagent` 也尚未执行，子会话 phase 仍是 `RUNNING`；
5. 启动恢复既不能通过 `final_message_id` 识别终稿，也不会走“子会话已终态”的兜底，于是再次调用 LLM/工具。

所以新增查询只记录了正常完成后的关联关系，没有建立可跨崩溃恢复的提交协议，上一轮指出的核心窗口并未真正关闭。

**影响**

恰好在子代理已生成终稿但终态更新前重启时，原 execution 会被再次运行，可能重复执行工具副作用并生成第二份结果。父会话最终交付的也可能是重跑结果，而非已经完成的原结果。这属于单实例重启恢复的核心需求，不涉及明确排除的多实例恢复能力。

**修复建议**

在“最终无 tool-calls 的 ASSISTANT 消息落库”这一持久化点同步绑定当前 execution，而不是等 DelegateTool 返回后再反查：

- 将 execution ID/执行范围传入子代理消息持久化回调；
- 在同一数据库事务中插入最终 ASSISTANT，并更新该 execution 的 `final_message_id`（可同时终态化 execution）；
- 或引入明确的 round/terminal marker，使恢复服务在 `final_message_id` 为空时也能无歧义识别该消息已是本 execution 的完整终稿；
- 增加故障注入测试：最终 ASSISTANT 事务提交后、DelegateTool 获得返回值前模拟进程退出，重启后断言不调用 LLM/工具，只复用终稿并交付父结果。

### 2. TypeScript 首次 `delegate` 正常路径仍完全没有写入 `final_message_id`

**代码位置**

- `backend-ts/src/harness/tool/impl/delegate-tool.ts:132-162`
- 对照仅 follow-up 使用的 `markExecutionTerminal`：`backend-ts/src/harness/tool/impl/delegate-tool.ts:405-425,486-507`

**问题说明**

`DelegateTool.execute()`（首次委派）结束时仍直接调用：

```ts
subagentExecutionMapper.updateById(execution.id, {
  status, result, totalRounds, ...
})
```

该更新没有 `finalMessageId`，也没有调用文件后半部分属于 `DelegateFollowupTool` 的 `markExecutionTerminal()`。因此即使首次委派完全正常完成，execution 的 `final_message_id` 仍长期为空。只要后端在父 AgentLoop 将该 delegate 的 TOOL 结果持久化前重启，启动扫描会看到 terminal execution + `delivery_status=PENDING`，父结果仍可交付；但如果重启发生在 execution 终态更新前，则恢复完全没有可用的终稿指针并会重跑。

**影响**

TypeScript 首次委派是本需求最主要的入口，该路径没有实现设计中的终稿锚点，恢复行为与 follow-up/Java 不一致，关键重启窗口仍会重复执行子代理。

**修复建议**

为首次 `DelegateTool` 接入与 follow-up 一致的 execution 终态持久化服务，并按上一问题的建议把终稿消息与 `final_message_id` 绑定放到同一持久化事务中；不要只在工具返回后追加一次普通 `updateById`。
