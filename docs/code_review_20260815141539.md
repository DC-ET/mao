# 子代理崩溃恢复功能增量复审报告

- 复审时间：2026-08-15 14:15:39
- 历史报告：`docs/code_review_20260815140829.md`
- 范围：当前工作区内与子代理重启恢复、原 execution 续跑、父结果幂等交付相关的 `backend/` 与 `backend-ts/` 功能代码
- 结论：**仍存在重大功能 Bug，Java 实现当前无法构建。**

## 严重（阻断发布）

### 1. Java 恢复实现仍引用已删除的配置类，并保留不匹配的方法调用

**代码位置**

- `backend/src/main/java/cn/etarch/mao/config/DelegateConfig.java:1`：文件仍为空，`DelegateConfig` 类已不存在。
- `backend/src/main/java/cn/etarch/mao/harness/delegate/SubagentExecutionRecoveryService.java:3,42`：仍导入并注入 `DelegateConfig`。
- `backend/src/main/java/cn/etarch/mao/harness/delegate/SubagentExecutionRecoveryService.java:83,116`：调用 `waitForLocal(child.getId(), cancelFlag)`，实际方法仍要求 `(Long childId, long deadline, AtomicBoolean cancelFlag)` 三个参数。

**复审验证**

执行 `cd backend && mvn -q -DskipTests compile`，编译器仍明确报告：

- `DelegateConfig.java` 不包含 `cn.etarch.mao.config.DelegateConfig`；
- `SubagentExecutionRecoveryService` 无法解析 `DelegateConfig`。

由于前一错误会阻断后续类型分析，参数数量错误未出现在本次输出首批诊断中，但源码调用与签名仍客观不匹配。

**影响**

Java 后端无法编译，本需求 Java 版本无法部署和执行；因此本需求整体仍存在阻断发布的重大功能问题。

**修复建议**

完成超时策略的范围收口，而不是同时保留两套残片：

- 若恢复功能继续采用原执行 deadline，应恢复 `DelegateConfig` 类，并通过 `startedDeadline(execution.getStartedAt(), delegateConfig.getTimeoutSeconds())` 计算 deadline 后传给 `waitForLocal`，同时将剩余时间传入有超时的可见执行路径；
- 若已明确移除 Java 委派超时，则删除 `DelegateConfig` 依赖、`startedDeadline` 和 deadline 形参，统一使用无超时、仅可取消的等待和执行 API。

修复后必须重新执行 Java 编译，并增加 CLOUD/LOCAL 恢复路径的编译与单测覆盖。

## 高（恢复结果可能重复生成）

### 2. 正常完成 execution 时没有持久化 `final_message_id`，重启窗口内会重新调用子代理

**代码位置**

- Java 正常委派终态：`backend/src/main/java/cn/etarch/mao/harness/tool/impl/DelegateTool.java:310-348,448-468`
- Java 正常追问终态：`backend/src/main/java/cn/etarch/mao/harness/tool/impl/DelegateFollowupTool.java:380-414,526-545`
- Java 具备但未被调用的终态逻辑：`backend/src/main/java/cn/etarch/mao/harness/delegate/SubagentExecutionLifecycleService.java:66-87`
- TypeScript 正常委派终态：`backend-ts/src/harness/tool/impl/delegate-tool.ts:140-160`
- TypeScript 正常追问终态：`backend-ts/src/harness/tool/impl/delegate-tool.ts:406-425,486-500`
- TypeScript 全局搜索仅在恢复服务中写入 `finalMessageId`：`backend-ts/src/harness/delegate/subagent-execution-recovery.service.ts:54,91`

**问题说明**

迁移新增了 `final_message_id`，两套恢复服务都依赖它识别“子代理终稿已经落库，但 execution 终态或父 TOOL 结果尚未来得及落库”的崩溃窗口。然而正常 `delegate` / `delegate_followup` 完成时，现有终态更新只写 status、result、usage 等字段，没有把刚落库的最终 ASSISTANT 消息 ID 写入 execution。

Java 的 `SubagentExecutionLifecycleService.markTerminal()` 虽然实现了查询并写入 `finalMessageId`，但当前正常委派/追问路径没有调用该方法；TypeScript 正常路径也没有等价写入。

典型窗口如下：

1. AgentLoop 已把子代理最终 ASSISTANT 消息持久化；
2. 后端在 execution 更新为 `COMPLETED` 前重启；
3. 数据库里的 execution 仍是 `RUNNING` 且 `final_message_id IS NULL`，子会话 phase 也可能仍为 `RUNNING`；
4. 启动恢复无法把已有终稿识别为完成结果，清理后再次调用 LLM，生成第二份子代理结果并重复可能的后续行为。

这正是本需求需要覆盖的“子代理运行期间重启后恢复原 execution”关键崩溃边界，不属于多实例恢复扩展。

**影响**

在终稿已生成但 execution 尚未终态化的重启窗口中，子代理会被重复运行，可能产生重复工具副作用或不同结果；父任务最终收到的是第二次运行结果，而不是已完成的原 execution 结果。

**修复建议**

使“最终 ASSISTANT 落库”和“execution 记录 final_message_id/终态”形成可恢复的持久化协议：

- 正常委派和追问完成/失败路径均应记录本 execution 对应的 final message ID；
- 最好在同一事务中写最终消息与 execution 终态；若架构上不能同事务，至少在最终消息落库时立即绑定 execution，并让恢复逻辑可依据 execution 起始消息范围及明确的完成标记安全识别；
- Java 应实际接入 `SubagentExecutionLifecycleService.markTerminal()` 或等价事务逻辑；TypeScript 增加对应实现；
- 增加故障注入测试：在“终稿消息已提交、execution 仍 RUNNING”时模拟重启，断言不再次调用 LLM/工具，只交付已有结果并恢复父会话。
