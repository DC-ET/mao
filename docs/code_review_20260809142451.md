## 二、新发现问题 / 遗留提示

### P3-1【低】focusStatusLabel / focusStatusClass 未并入实时计数，主会话自身待回答时「标签」与「排序」不一致

**位置**
- `desktop/src/components/task/TaskIndexPanel.vue` `focusStatusLabel`（L496-511）/ `focusStatusClass`（L513-521）
- 对比：`desktop/src/stores/session.ts` `focusedSessions`（已并入 `sessionPendingApprovals` / `sessionPendingQuestions` 取 max）

**问题**
第三轮只给**排序**（`focusedSessions`）做了实时并集，但状态**标签/样式**仍只看服务端字段：

```js
const approval = (session.treePendingApprovalCount ?? session.pendingApprovalCount ?? 0)
const question  = (session.treePendingQuestionCount ?? session.pendingQuestionCount ?? 0)
```

场景：**主会话自身发起 ask_user_questions**（phase 保持 RUNNING，服务端不发 tree 事件——`publishIfSideTask` 对主会话直接 return）：
- 排序：`realtimeQuestions.length=1` → max(tree*=0, 1)=1 → 升到 priority 0（待回答）✅
- 标签：`treePendingQuestionCount=0` → 显示「运行中」（fallthrough 到 RUNNING 分支）❌

不一致持续存在（主会话自身待回答没有后续 tree 事件修正，直到列表刷新）。主会话自身**审批**场景不受影响（phase 会变 WAITING_APPROVAL，标签 switch 分支正确显示「待审批」）。

**修复建议**
将 `focusStatusLabel` / `focusStatusClass` 的 approval/question 判定改为与 `focusedSessions` 相同的并集口径（提取共用计算：`Math.max(tree*/pending 服务端值, sessionPendingApprovals/sessionPendingQuestions 实时值)`），或把并集结果回写到实体字段，保证标签与排序同一数据源。

### P4-1【提示】CrashRecoveryRunner 恢复 SIDE_TASK 时不发布 tree 信号（N-2 未覆盖的恢复路径）

**位置**
- `CrashRecoveryRunner.recoverSession`（`updatePhase(sessionId, "RUNNING")` 后仅 notifyClient，无 `publishIfSideTask`）

**影响评估**
服务重启时若 SIDE_TASK 卡在 RUNNING 会被恢复，其父任务 `treeRunning` 不实时发布。但重启场景 WebSocket 断开、事件无人接收，前端重连后会主动拉取列表（`applySessionListSignals` 填充 tree*）自愈，实际影响≈0。可顺手补上，或维持现状。

### P4-2【提示】markAsRead 中重复查询 session（微优化）

**位置**
- `SessionController.markAsRead`：`requireSessionOwner` 已返回 Session，随后 `sessionService.getSession(id)` 又查一次

**影响**
单次冗余 SELECT，无功能影响。可改为复用 `requireSessionOwner` 返回值（`Session s = requireSessionOwner(userId, id)`）。

### P4-3【提示】前端无实时并集单测

**位置**
- `desktop/src/stores/session.test.ts` / `focusSort.test.ts`

**说明**
现有测试覆盖 tree* 事件重排，但未覆盖「`sessionPendingApprovals`/`sessionPendingQuestions` 与 tree* 取 max」的实时升档逻辑。建议补一条：模拟实时待回答计数 → 断言 focusedSessions 排序升到 priority 0。
