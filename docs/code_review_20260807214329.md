## 问题清单

### 【中】边路/子代理会话的 LLM 重试提示仍然不显示（漏显未修复，显示条件作用域不一致）

- 位置：
  - `desktop/src/components/chat/MessageBubble.vue:229-234`（`isAssistantRunning` 用主会话 `sessionStore.activeStreaming` / `activeThinking`）
  - `desktop/src/components/chat/MessageBubble.vue:103`（`v-if="isAssistantRunning && llmRetry"`）
  - `desktop/src/components/chat/SideChatPanel.vue:38-43` 与 `SubagentChatPanel.vue:31-36`（打字区仅三点动画，无重试条兜底）
- 根因：本轮把 `llmRetry` 改为按消息所属会话读取（`getLlmRetry(props.sessionId)`），**但 `isAssistantRunning` 仍基于主会话的 `activeStreaming`/`activeThinking`**。重试发生在 LLM 流开始前，此时该会话自身 `streaming=false`、`thinking=false`（`thinking_start`/`content_delta` 前的 HTTP 阶段）。于是：
  - 边路/子代理会话自身重试，且主会话空闲（子代理委派期间主会话通常无流式输出）→ `isAssistantRunning=false` → 重试条不渲染；边路/子代理打字区又没有重试兜底条（只有 ChatPanel 加了 `typing-retry`）→ 用户只能看到三点动画，**完全看不到「模型服务繁忙，正在重试 n/max」**。
  - 若主会话恰好正在流式输出，边路最后一条 assistant 消息又满足 `isLast`，则 `isAssistantRunning=true`，此时会"碰巧"显示——**显示与否取决于主会话是否在流式，行为不确定**。
- 说明：本轮修复了第 1 轮【中】问题的串扰（误显）部分，但漏显缺口依旧；且修复后 `llmRetry` 与 `isAssistantRunning` 的会话作用域错配，使漏显从"稳定不显示"变成"随机显示"，更难以排查。
- 建议：
  1. `isAssistantRunning` 改为按消息所属会话读取：`props.sessionId ? sessionStore.isSessionStreaming(props.sessionId) || sessionStore.isSessionThinking(props.sessionId) : (sessionStore.activeStreaming || sessionStore.activeThinking)`（`isSessionStreaming`/`isSessionThinking` 已存在于 store）；或
  2. 至少为 SideChatPanel / SubagentChatPanel 的打字区补充与 ChatPanel 相同的重试条兜底（读取 `getLlmRetry(该会话ID)`）。

### 【低】`thinking_start` 分支未调用 `clearLlmRetry`，重试成功后可能短暂残留并重复显示

- 位置：`desktop/src/composables/useStreamWS.ts:744-748`（`case 'thinking_start'` 只做 `setStreaming(false)` / `setThinking(true)`，未清理 retry）
- 问题：重试成功后 LLM 流式输出的首个事件若是 `thinking_start`（而非 `content_delta`），retry 状态会一直保留到首个 `thinking_delta`/`thinking_end` 到达。期间：
  - ChatPanel 打字区 `showTypingIndicator` 仍为 true（`activeStreaming=false`、无 running tool）→ `typing-retry` 继续显示「正在重试」；
  - 同时 MessageBubble 的 `activeThinking=true` → `isAssistantRunning=true`，且 `llmRetry` 未清 → `llm-retry-bar` 也显示；
  - 两处同时展示过期重试条，直到 `thinking_delta` 清理（通常数百毫秒的闪烁窗口）。
- 建议：`thinking_start` 分支补充 `sessionStore.clearLlmRetry(sessionId)`（与 `thinking_end`/`thinking_delta`/`content_delta` 保持一致）。

### 【低】WS 断线场景下 retry 状态残留（第 1 轮遗留，本轮未覆盖）

- 位置：`desktop/src/composables/useStreamWS.ts` `ws.onclose`（约 260 行起）与重连恢复逻辑
- 问题：本轮已补 `error` 事件路径（`resetSessionStreamState` 增加 `clearLlmRetry`），但断线（`onclose` → 重连）路径未清理 `sessionLlmRetry`。若 LLM 重试期间 WS 断线、终态事件（`session_status` COMPLETED/FAILED 或 `error`）丢失，retry 条目会跨会话留存；重连恢复会话后，若该会话最后一条消息满足显示条件，可能短暂展示上一次的过期重试信息（影响极小，与第 1 轮报告一致）。
- 建议：可选优化——重连成功后对已订阅会话或当前激活会话调用 `clearLlmRetry`，或对 retry 条目附加时间戳做过期丢弃。

### 【低】SideChatPanel 占位会话期间 `session-id` 传空串，回退主会话 retry 状态

- 位置：`desktop/src/components/chat/SideChatPanel.vue:21`（`:session-id="hasRealSession ? String(realSessionId) : ''"`）
- 问题：首次发送边路消息、后端尚未返回 `side_session_created`（`realSessionId` 未就绪）的占位窗口内，`session-id=''` 使 MessageBubble 回退 `activeLlmRetry`（主会话状态）。由于主会话 retry 与 `activeStreaming`/`activeThinking` 基本互斥（重试时主会话无流式），误显概率极低；但占位会话自身若此刻收到 `llm_retry`（带新会话 ID，已写入 map），同样因 `session-id=''` 而不可见。窗口极短（`side_session_created` 与 `llm_retry` 竞态），影响可忽略。
- 建议：占位期间可传占位缓存 key 或维持现状；如要彻底解决，可在 `realSessionId` 更新后再订阅/展示（属可选优化）。

## 已核查通过项（无问题）

1. **事件字段与后端 payload 一致**：`llm_retry` 事件与 `statusCode/attempt/maxRetries/delaySeconds` 四字段名与 `WsStreamingEventListener.onLlmRetry` 完全一致；`attempt` 语义（1 起、含首次失败）与 `OpenAiLlmAdapter.stream()` 一致。
2. **事件路由正确**：后端 `send()` 统一经 `WsEvent.of(type, sessionId, payload)` 注入会话 ID 与 `executionId`（WsStreamingEventListener.java:302-303），前端 `routeEvent` 按 sessionId 写入 `setLlmRetry(sessionId, ...)`，边路/子代理会话的 retry 各存各的 map 条目；`llm_retry` 已在 `STREAM_EVENT_TYPES` 白名单，受 `isStaleExecution` 过滤（取消/过期执行的重试被丢弃）。
3. **清除时机（正常路径）完整**：`content_delta`/`thinking_delta`/`tool_call_start`/`thinking_end`/`message_end`/终态 `session_status`/`error`（经 `resetSessionStreamState`）均已清理；`resetState`（登出）清空整个 map。重试只发生在 HTTP 响应阶段（流开始前），一旦流开始即重试结束，清理时机正确。
4. **主会话显示条件正确且不重复**：首轮/工具完成后重试 → `showTypingIndicator=true` → ChatPanel 打字区 `typing-retry` 显示；此时 `isAssistantRunning=false`（主会话 streaming/thinking 均 false）→ MessageBubble 不显示，两处互补不重复；`sending` 全程持有至终态。
5. **串扰（误显）已修复**：边路/子代理面板的 MessageBubble 通过 `getLlmRetry(边路子代理会话ID)` 读取，不再显示主会话的 retry 状态；主会话 ChatPanel 传入 `sessionId ?? ''`，`sessionId` 为 null（无活动会话）时回退 `activeLlmRetry`（此时 activeSessionId 亦为 null，返回 null，一致）。
6. **Vue 响应性**：`sessionLlmRetry` 为 `ref<Map>`，Vue 3 响应式代理覆盖 Map 的 set/delete（与既有 `sessionStreaming` 等模式一致）；`llmRetry` computed 依赖 `sessionLlmRetry.value` 与 `props.sessionId`，set/delete 会触发重算；空值守卫（`sessionId && data`、`?? null`、`sessionId: ''` 默认值）完备。
7. **类型检查**：`vue-tsc -b --force` 通过，无类型错误。
8. **子代理面板 `session-id` 正确**：`SubagentChatPanel.vue:18` 传 `sid`（真实子代理会话 ID），只要 `isAssistantRunning` 条件成立即可正确显示自身重试条（受问题 1 制约）。
