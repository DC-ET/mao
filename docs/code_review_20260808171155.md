## 一、上一轮问题修复核查结果

### 修复 1：冷启动探测误判 —— ⚠️ 基本有效，但存在残余场景

**已生效部分** ✅
- `firstStartAt` 在 `onCreate` 记录，`scheduleWebViewRecoveryProbe` 中 10s 内直接 return；
- 冷启动（onCreate→onStart）被正确拦截；10s 后首次回前台才探测；Activity 重建时 `onCreate` 重跑、防护窗口重置，行为合理。

**残余问题（新发现，低严重度）** ⚠️
- 防护基于**时间窗**而非**页面加载完成状态**：弱网下远程 SPA（Vue+Monaco）首次加载可能 >10s。若用户在加载完成前经历一次 onStop/onStart（如按电源键熄屏点亮），此时防护已过期 → 触发探测 → 页面仍在加载、`evaluateJavascript` 回调延迟 >3s → 误判无响应 → reload 取消首次加载。
- 对比：JS 侧 `useForegroundRecovery` 的 3s 防护无此问题——`visibilitychange` 只在 JS 存活（页面已加载完成）时触发，而原生探测不受此限制。
- **建议**：改为监听首次 `onPageFinished`（或 `onPageCommitVisible`）置 `pageLoaded` 标志，页面加载完成前一律不探测；比时间窗更可靠，且天然覆盖弱网场景。

### 修复 2：销毁边界 —— ✅ 有效

- `probeWebViewAlive` 入口、超时回调、`reloadWebView` 三处均校验 `isFinishing()/isDestroyed()/webView==null`；`onDestroy` 中 `handler.removeCallbacksAndMessages(null)` 清理延迟任务。✅
- 小瑕疵（不构成 bug）：`onDestroy` 先 `super.onDestroy()` 再清理，建议先清理再 super（顺序无实质影响）；
- 小遗漏（低）：`onDestroy` 只清理 `handler` 上的任务，`reloadWebView` 里 3 次 `webView.postDelayed(inject,…)` 走的是 WebView 关联的 UI 线程队列，清理不到；Activity 销毁后这些 Runnable 仍会执行 `evaluateJavascript`（对已销毁 WebView 调用可能抛 IllegalStateException）。与 `configureWebView` 存量注入模式相同，风险低（窗口短），可考虑注入统一走 `handler` 或加判空 try-catch。

## 二、发现的新问题（重点）

### 【中】1. 修复 3 无效：onStop 只清标志、未取消已排定任务，后台 reload 场景依然存在

**位置**：`onStop()`（L93-96）+ `probeWebViewAlive()` 超时回调（L124-131）

**问题**：
`onStop` 仅 `probing = false`，但**延迟探测任务（2s）与超时回调（3s）都是 `handler.postDelayed` 排定的，标志位不会取消队列中的任务**。超时回调执行时：

```java
probing = false;
if (!responded[0] && !isFinishing() && !isDestroyed() && webView != null) {
    reloadWebView(webView);
}
```

后台时 `isFinishing()/isDestroyed()` 均为 false、webView 非空 → **若 WebView 无响应（responded=false），超时回调依然会在后台执行 `reloadWebView`**。回调内并没有任何"是否在前台"的校验。

**触发场景**：回前台后 2s~5s 探测窗口内用户切后台（如回前台瞄一眼又切走 / 看通知栏），且 WebView 确实无响应 → 后台 reload。后台 reload 会被系统节流/延迟，产生无谓唤醒；回前台时页面可能正处于重载中，叠加 JS 侧刷新，体验抖动。

**注释误导**（L126）：
> `// 超时判定前再次校验销毁状态与前台状态（onStop 已清 probing，此处不会在后台执行）`

该注释**与实际行为不符**：onStop 清 probing 并不会阻止已排定的超时回调执行，且回调内也**不存在前台状态校验**（只校验了销毁状态）。误导后续维护者以为已防护。

**正确修复方案**（任一）：
- `onStop` 中真正取消任务：保存延迟/超时 Runnable 引用，`handler.removeCallbacks(delayedProbe)` / `handler.removeCallbacks(timeoutRunnable)`（或直接 `handler.removeCallbacksAndMessages(null)`——注意该 handler 仅用于探测，无其他用途）；或
- 超时回调内校验前台状态：记录最近一次 `onStop` 时间戳（或 `onStart` 计数），回调内若"探测期间发生过 onStop"则跳过 reload。

### 【中低】2. 双重探测竞态：onStop 清标志 + 重新 onStart 导致两个延迟任务同时排队

**位置**：`scheduleWebViewRecoveryProbe()`（L105 `if (probing) return`）与 `probeWebViewAlive()` 入口（L113，**无 probing 检查**）

**问题**：
`probing` 防重复只挡在**调度处**，但 `probeWebViewAlive` 入口不检查 `probing`。快速前后台切换时序：

1. onStart(t=0) → 排定延迟任务 A（t+2s）
2. t+1s 切后台 → onStop → `probing=false`（任务 A 仍在队列！）
3. t+1.5s 回前台 → onStart → `probing=false` → **又排定延迟任务 B（t+3.5s）**
4. t+2s 任务 A 执行 → `probing=true` → evaluateJavascript → 排定超时 A
5. t+3.5s 任务 B 执行 → **入口无 `if (probing) return`** → 又 evaluateJavascript → 排定超时 B

结果：双重探测、两个超时回调并存（均置 `probing=false`、均可能触发 reload，靠 10s 防抖兜底最多一次）。属浪费 + 轻微竞态，不致命但违背"同一次前台停留只探测一次"的设计意图。

**建议**：
- 最简：`probeWebViewAlive` 入口加 `if (probing) return;`（探测已在进行则静默丢弃本次延迟任务）；且
- 更干净：`onStop` 时 `handler.removeCallbacksAndMessages(null)` 彻底取消队列中的探测任务（与修复 1 的 onStop 方案统一），回前台重新排定，杜绝双任务。

### 【低】3. 冷启动防护的残余误判场景（见"修复 1"节）：弱网首屏加载 >10s 时防护过期

同上，建议改为监听首次 `onPageFinished` 置标志。
