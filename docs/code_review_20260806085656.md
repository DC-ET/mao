# 未提交代码审查报告

审查范围：当前 Git 工作区未提交的功能代码（忽略页面样式和文档变更）。

## 结论

发现 8 个会影响业务正确性或安卓后台保活可靠性的潜在 bug，其中 4 个为高优先级。

## 高优先级

### 1. Service 首次启动后没有绑定插件监听器，原生事件无法回传前端

- 位置：`android/android/app/src/main/java/cn/etarch/mao/app/WsBridgePlugin.java:36-42`、`android/android/app/src/main/java/cn/etarch/mao/app/WsBridgePlugin.java:55-69`
- 触发场景：应用进程首次启动时，插件 `load()` 先执行，`WsKeepAliveService` 尚不存在；随后前端调用 `ensureKeepAlive()` 启动 Service。
- 问题：插件只在 `load()` 时尝试 `registerEventListener(this)`。`ensureKeepAlive()` 启动 Service 后没有补注册，Service 的 `onCreate()` 也没有反向绑定插件。
- 影响：首次启动的常规路径下，`wsStatus`、`wsEvent`、`replayDone`、`keepAliveStopped`、`pendingNavigate` 均无法送达 JS。前端连接会等待至超时，聊天流式事件也无法显示。

### 2. 磁盘追加会覆盖原事件文件，冷启动恢复只能拿到最后一条事件

- 位置：`android/android/app/src/main/java/cn/etarch/mao/app/PendingQueue.java:227-243`
- 触发场景：进入持久化模式后连续收到两条及以上 tracked 会话事件。
- 问题：`appendToDisk()` 打开的是新的 `events.jsonl.append.tmp`；append 参数却依据正式文件 `events.jsonl` 是否存在。即使以 append 模式打开临时文件，也不会把正式文件的旧内容复制进临时文件，随后 rename 会用仅含当前记录的临时文件替换正式文件。
- 影响：进程被系统回收或崩溃后，之前尚未 ACK 的事件永久丢失，可靠重放失效。

### 3. tracked 会话的终态事件在入队前被移出 activeTracked，后台时会丢失

- 位置：`android/android/app/src/main/java/cn/etarch/mao/app/WsKeepAliveService.java:534-558`、`android/android/app/src/main/java/cn/etarch/mao/app/TrackedManager.java:174-201`
- 触发场景：tracked 会话收到 `COMPLETED`、`FAILED` 或 `CANCELLED`，尤其是 App 在后台时。
- 问题：代码先调用 `tracked.onSessionStatus()`，终态会将会话从 `activeTracked` 移除；随后路由阶段重新计算 `trackedSid` 得到 false，因此终态事件不进入可靠队列。后台又不会走 subscribed 实时转发。
- 影响：前端恢复后可能仍显示运行中，且缺失最终状态事件。

### 4. 原生重连期间桥仍显示 OPEN，发送失败被吞掉

- 位置：`desktop/src/capacitor/wsBridge.ts:151-162`、`desktop/src/capacitor/wsBridge.ts:227-243`、`desktop/src/composables/useStreamWS.ts:356-376`
- 触发场景：网络切换或短时断网使原生层进入 `reconnecting`，用户此时发送消息、取消任务或执行其他 WS 操作。
- 问题：收到 `reconnecting` 时没有把 `readyState` 改为 CONNECTING/CLOSED；`send()` 又忽略 Capacitor Promise 的 reject 并同步返回 true。上层据此认定发送成功。
- 影响：业务消息会被静默丢弃，服务端未收到请求，但 UI 可能进入等待执行结果的状态。

## 中优先级

### 5. ACK 或丢弃记录时未扣减 `pendingBytes`，累计流量超过 10 MB 后持续误判溢出

- 位置：`android/android/app/src/main/java/cn/etarch/mao/app/PendingQueue.java:114-170`
- 触发场景：同一会话长期运行，累计接收事件超过约 10 MB，即使前端一直及时 ACK。
- 问题：`pendingBytes` 只增加；`ackUpTo()`、`dropOldest()` 和 `markSkipped()` 删除 pending 记录时均未减少字节计数。
- 影响：达到阈值后每条新事件都会触发伪溢出，持续丢弃记录并要求 REST 校准，正常 ACK 无法恢复。

### 6. 编辑重发和首次创建 Side Task 没有纳入 tracked，切后台后无法保活

- 位置：`desktop/src/composables/useStreamWS.ts:426-455`、`desktop/src/composables/useStreamWS.ts:484-505`
- 触发场景：安卓端执行“编辑并重新发送”或首次创建 Side Task 后立即切到后台。
- 问题：普通 `sendMessage()` 会调用 `trackSessions()`，但 `sendEditMessage()` 与 `createSideSession()` 没有。Side Task 的原生自动 track 又要求父会话已经 tracked。
- 影响：这些入口启动的任务可能没有前台服务、可靠缓冲和完成通知；进入后台后流式事件可能丢失。

### 7. 冷启动页面已可见时不会主动执行 recovery

- 位置：`desktop/src/composables/useAppResumeSync.ts:87-116`、`desktop/src/main.ts:49-54`
- 触发场景：WebView 进程被回收后重新打开 App，或点击通知冷启动，此时页面初始化时已经是 `visible`。
- 问题：`init()` 只监听后续 `visibilitychange`，没有在当前页面可见且原生桥连接成功后主动调用一次 `runRecovery()`。
- 影响：磁盘缓冲重放和 REST 校准不会立即执行，用户可能看到缺失或过时状态，必须再切一次前后台才会恢复。

### 8. STARTING 超时的 REST 查询失败被当作 IDLE，可能错误停止后台保活

- 位置：`android/android/app/src/main/java/cn/etarch/mao/app/WsKeepAliveService.java:657-703`
- 触发场景：任务已在服务端运行，但 20 秒超时检查时网络断开、REST 超时、接口非 200 或响应解析失败。
- 问题：`querySessionPhase()` 的所有失败都返回 null，而 `checkStartingTimeout()` 将 null 与明确的 `IDLE` 一并执行 `rollbackStarting()`。
- 影响：实际仍运行的任务会被移出 tracked；若这是最后一个 tracked 会话，后台 Service 可能停止，后续事件及终态通知无法接收。
