## 中等严重程度

### 1. CLOUD 仓库锁存在移除竞态，同一仓库可能同时执行两个写操作

**代码位置**

- `backend/src/main/java/cn/etarch/mao/file/service/GitWriteOperationService.java:219-220`
- `backend/src/main/java/cn/etarch/mao/file/service/GitWriteOperationService.java:236-238`

**问题说明**

当前锁生命周期为：

1. 通过 `locks.computeIfAbsent(repo, ...)` 获取锁对象；
2. `tryLock()` 失败时立即返回；
3. 操作完成后先 `unlock()`，再执行 `locks.remove(repo, lock)`。

`unlock()` 与从 Map 移除不是原子操作，因此存在以下竞态：

1. 请求 A 持有锁 L；
2. A 执行 `unlock()`；
3. 请求 B 在 A 尚未 `remove` 前，从 Map 取得同一个 L，并成功 `tryLock()`；
4. A 执行 `remove(repo, L)`，将 B 正在持有的锁从 Map 删除；
5. 请求 C 调用 `computeIfAbsent` 创建新锁 L2，并成功进入；
6. B 与 C 同时对同一仓库执行 commit/pull/push。

这会破坏设计要求的“同一仓库写操作互斥”，可能造成 index lock、stash/commit 状态互相干扰。该问题仅需三个请求在极短窗口内交错，虽然概率不高，但一旦发生会直接影响 Git 操作正确性。

Electron 使用单一 `Set` 且 JavaScript 主线程同步完成删除，不存在相同的线程竞态。

**建议修复**

不要在简单 `unlock()` 后直接删除锁对象。可采用带引用计数/使用者计数的锁条目，并在 Map 的原子 `compute` 中确认无持有者、无等待/已取得该锁的调用后再移除；或者保留按仓库路径缓存的锁，不在每次操作后删除，并通过其他可控清理策略避免 Map 无限增长。

补充三线程并发测试：A 释放时让 B 已取得旧锁、C 随后尝试进入，断言任意时刻同一仓库最多只有一个写操作处于临界区。
