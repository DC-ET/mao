## 问题清单

### 【中】多会话场景：边路/子代理会话的重试提示不显示，且存在串扰风险

- 位置：`desktop/src/components/chat/MessageBubble.vue:103`（`v-if="isAssistantRunning && sessionStore.activeLlmRetry"`）
- 根因：`activeLlmRetry` 是 store 中基于**主会话** `activeSessionId` 的 computed（`session.ts:203`）。而 `MessageBubble` 被 `ChatRoundList` 复用，`ChatRoundList` 除主 `ChatPanel.vue` 外还被 `SideChatPanel.vue:17` 与 `SubagentChatPanel.vue:14` 使用。当边路/子代理会话自身 LLM 重试时，`setLlmRetry(sideSessionId, ...)` 写入的是边路会话的 map 条目，边路面板读取 `activeLlmRetry`（主会话条目）取不到 → **边路/子代理会话的重试提示不显示**（功能缺口）；反向，若主会话恰好在重试而用户正查看边路面板，且边路面板最后一条 assistant 消息满足 `isAssistantRunning`，则可能**误显主会话的重试提示**（串扰，概率较低）。
- 说明：`isAssistantRunning`/`showStreamIndicator` 本就用主会话的 `activeStreaming`/`activeThinking`（既有模式），本次新增的重试条沿用了同样的会话作用域缺陷，但属于本需求引入的新展示功能，建议一并修正。
- 建议：在 `MessageBubble` 中按消息所属会话读取重试状态（如新增 prop 传入真实 sessionId，改用 `getLlmRetry(realSessionId)`），或要求边路/子代理面板传入自身会话 id；至少保证边路会话自身的重试可见。

### 【低】`error` 事件路径未清理 retry 状态，可能残留

- 位置：`desktop/src/composables/useStreamWS.ts` `case 'error'`（约 815 行）→ `resetSessionStreamState()`（405 行）
- 问题：`resetSessionStreamState` 只清理 streaming/thinking/askQuestions/activeExecution，**未调用 `clearLlmRetry`**。当 LLM 重试耗尽触发 `onError` → `error` 事件时，若后续 `session_status FAILED` 未到达（如紧随其后的断线、或服务端未补发终态），`sessionLlmRetry` 中该会话的条目会残留。虽然残留时 UI 通常不可见（`isAssistantRunning` 与 `sending` 均已为 false），但属于状态残留，且与其余所有「收尾路径都清 retry」的约定不一致。
- 建议：在 `resetSessionStreamState` 中补充 `sessionStore.clearLlmRetry(sessionId)`。

### 【低】异常中断（WS 断线）下 retry 状态残留，重新打开会话时可能短暂显示过期信息

- 位置：`desktop/src/stores/session.ts` `clearLlmRetry` / `resetState`
- 问题：正常终态（`session_status` COMPLETED/FAILED/CANCELLED/IDLE）会清 retry；但若重试期间 WS 断线、终态事件丢失，`sessionLlmRetry` 条目会跨会话切换留存。下次用户打开该会话并发送新消息时，在首个 `content_delta`/`thinking_delta`（或新的 `llm_retry`）到达前，提示条可能短暂展示上一次的过期重试信息（影响极小）。
- 建议：可选优化——在会话激活/重连成功时清理当前会话的 retry 状态，或对 `sessionLlmRetry` 条目附加时间戳做过期丢弃。

### 【低】`getLlmRetry` 为死代码

- 位置：`desktop/src/stores/session.ts:1040`（`getLlmRetry` 定义并导出，但全仓库无调用方）
- 问题：无功能影响，仅为冗余导出（可能与上述多会话修复配合使用，可保留）。
- 建议：若后续不用可移除；若要修多会话问题，正好可用它按真实 sessionId 读取。

## 已核查通过项（无问题）

1. **事件字段与后端 payload 一致**：`llm_retry` 事件、`statusCode/attempt/maxRetries/delaySeconds` 四个字段名与 `WsStreamingEventListener.onLlmRetry` 完全一致；`attempt` 语义（1 起、含首次失败）与后端 `OpenAiLlmAdapter.stream()` 的 `attempt` 一致。
2. **白名单与 stale 过滤**：`llm_retry` 已加入 `STREAM_EVENT_TYPES`（useStreamWS.ts:89），后端 `send()` 统一注入 `executionId`（WsStreamingEventListener.java:302），`isStaleExecution` 可正确丢弃取消/过期执行的重试事件；服务端 `session_status RUNNING` 先于 LLM 调用发送，FIFO 保证新执行的重试不会被 suppressed 状态误杀。
3. **清除时机完整（正常路径）**：`content_delta`/`thinking_delta`/`tool_call_start`/`thinking_end`/`message_end`/终态 `session_status` 均已补 `clearLlmRetry`；重试只发生在 HTTP 响应阶段（流开始前），一旦流开始即重试结束，清理时机正确；`resetState`（登出）也清空整个 map。
4. **显示条件正确（主会话）**：
   - 首轮 LLM 重试（无内容/思考/工具）：`activeStreaming=false`（流未开始）→ MessageBubble 不显示，ChatPanel `showTypingIndicator=true`（sending=true、无 running tool）→ 打字区显示重试条；
   - 工具执行后 LLM 重试：toolCalls 已全部完成 → `showTypingIndicator=true` → 打字区显示；
   - 两处显示互补、不会重复出现；`sending` 由 useChat 全程持有至终态，重试期间为 true。
5. **Vue 响应性**：`sessionLlmRetry` 为 `ref<Map>`，Vue3 响应式代理覆盖 Map 的 set/delete（与既有 `sessionStreaming` 等模式一致），`activeLlmRetry` computed 会正确重算；空值守卫（`sessionId && data`、`?? null`）完备。
6. **类型检查**：`vue-tsc -b --force` 通过，无类型错误。
