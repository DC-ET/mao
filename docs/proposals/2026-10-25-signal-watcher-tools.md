# 提案：信号哨兵对话内配置 —— 补上「变化驱动自动化」的 Agent 工具组

> 用户在对话里说「盯住这个接口，发布状态一变就告诉我」，Agent 今天只能回答：请打开设置 → 信号哨兵，自己填表。定时任务早就能在对话里一句话建好，哨兵不行——同一个「自动化」页面下的两件事，能力不对称。

- 状态：已否决（2026-10-25），存档勿再评审
- 日期：2026-10-25
- 提案总览：见 [docs/proposals/README.md](README.md)
- 规模：小~中（一个工具组 + 展示规范三处同改 + 回执入口；零新表零迁移）
- 关联：`signal` 域（哨兵服务 / 私网禁令）、`harness/tool/impl/scheduled-task-tools.ts`（同模式先例）、`session/util/tool-result-summarizer.ts`、`desktop/src/utils/toolDisplay.ts`

## 1. 背景与现状

### 1.1 定时任务的另一半早就通了，哨兵还堵着

代码现状：Agent 工具箱里定时任务工具组**已齐全**——`create_scheduled_task` / `list_scheduled_tasks` / `update_scheduled_task` / `delete_scheduled_task`（`tool-registry.ts:166-169`），用户说「每天早上九点帮我查一次」就能当场建好、当场回执。

信号哨兵（2026-10-11 实施）是同一页面下的另一半自动化：按间隔探测外部 HTTP 接口，**判定值变化时**才触发 Agent 会话。但它只有设置页的手工表单，**没有任何 Agent 工具**。结果是一个割裂的体验：

- 「每天 9 点跑一次」→ 一句话，Agent 建好。
- 「这个接口变了就跑」→ Agent 解释半天哨兵怎么配，用户切到设置页，把 URL、间隔、判定字段、提示词一个一个抄过去。

后者恰恰是更常见、更该自动化的诉求（盯发布状态、盯库存、盯汇率），也是最容易被抄错参数的一类配置（判定值选「内容哈希」还是「JSON 字段」、字段路径怎么写，用户经常配错）。

### 1.2 一个真实场景

用户：「帮我盯着 https://build.internal/api/jobs/88 的 state 字段，从 RUNNING 变成别的就跑一次构建总结，把日志里的失败原因找出来。」

今天的对话：Agent（没有工具）只能回复一段「配置教程」；用户手动建哨兵时还要把「构建总结 + 找失败原因」这段提示词复制进表单，下次需求变化再改一遍。

提案后：Agent 直接调 `create_signal_watcher`，URL、间隔 60s、判定 JSON 字段 `state`、触发提示词原样带入，回执卡片展示全部参数，「已创建，触发时会在本会话累积历史」——与定时任务体验完全对齐。用户看得懂参数就能当场纠错（「间隔改 5 分钟」→ `update_signal_watcher`）。

### 1.3 为什么现在做

- 哨兵的全部服务端能力已就位（探测 / 判定 / 触发 / 自动停用 / 私网禁令），缺的只是工具封装——工程上是「把既有 service 挂进工具注册表」。
- 定时任务工具组提供了逐条可抄的实现先例：命名、参数描述、防滥用提示词约束（「仅响应用户直接表达的定时处理需求」）、回执格式。
- 哨兵的失败自动停用 + 通知已实施，Agent 建的哨兵与手工建的进同一条治理链路，无新增运维面。

## 2. 目标 / 非目标

**目标**

1. 新增工具组 `create_signal_watcher` / `list_signal_watchers` / `update_signal_watcher` / `delete_signal_watcher`，与定时任务工具组对称。
2. 参数与服务端既有校验完全一致：探测 URL（复用私网禁令判定，违禁直接报错给模型）、间隔、判定模式（内容哈希 / JSON 字段 / 状态码）、字段路径、触发提示词。
3. 触发的会话在**创建哨兵的会话**中累积历史（与定时任务同语义），用户在原会话里能看到每次触发与结果。
4. 回执展示：创建 / 修改后回显全部关键参数，用户可当场口头纠错。
5. 防滥用约束与定时任务同款：工具描述明确「仅响应用户直接表达的盯守需求，禁止在自身任务执行中擅自创建」。

**非目标**

- 不改哨兵服务端任何行为（探测频率上限、失败停用阈值、私网禁令均不动）。
- 不做哨兵的批量导入 / 导出。
- 不做「Agent 自己消费哨兵结果」的新触发语义（触发仍走既有开新会话 / 绑定会话逻辑）。
- 不引入哨兵写操作的强制审批（与定时任务工具对齐：靠提示词约束 + 用户可见回执；若评审认为哨兵带 URL 出网更敏感，可加审批，见开放问题）。

## 3. 与已否决 / 已排除方向的边界

| 方向 | 本提案为何不是它 |
|---|---|
| 任务模板 / Runbook（2026-10-19 否决） | 不产出任何模板资产；是配置动作的工具化，产物落在既有 `signal` 表，与「参数化提示词一键跑」无关 |
| 低代码工作流画布（README 排除） | 无编排、无画布；单工具单配置动作 |
| 执行中引导 / 批量任务（2026-10-24 否决） | 不改执行形态；哨兵触发后的执行就是一次普通会话 |
| 出网边界 / 防泄漏（2026-10-09 否决） | 不放宽任何出网面：探测地址沿用哨兵既有私网禁令与放行机制，Agent 传私网地址会被服务端拒绝并把原因回给模型 |
| 多 Agent 协作 DAG（2026-10-05 否决） | 单 Agent 单工具，无编排 |

## 4. 技术方案

### 4.1 工具组（挂 `harness/tool/impl/signal-watcher-tools.ts`，注册进 tool-registry）

| 工具 | 参数（对齐服务端校验） | 说明 |
|---|---|---|
| `create_signal_watcher` | name / url / interval_seconds / compare_mode（HASH/JSON_FIELD/STATUS）/ field_path / trigger_prompt / enabled | 创建后绑定当前 Agent 与当前会话；url 过私网禁令，违禁返回结构化错误 |
| `list_signal_watchers` | 无必填 | 列本人哨兵（id、名称、地址、判定、状态、最近触发时间） |
| `update_signal_watcher` | id + 可变字段 | 改间隔 / 判定 / 提示词 / 启停 |
| `delete_signal_watcher` | id | 删除（与设置页删除同语义） |

- 参数描述逐条参照 `scheduled-task-tools.ts` 的写法：trigger_prompt 里写清「只描述变化发生后要做什么，不要包含探测与频率措辞」。
- 权限：工具执行以会话用户身份调用 signal 域服务，沿用其所有权校验（只能管自己的哨兵）。

### 4.2 展示与治理的规范同改（AGENTS.md 硬性要求）

- `session/util/tool-result-summarizer.ts`：四个工具的成功 / 失败 / 缺参数摘要。
- `desktop/src/utils/toolDisplay.ts`：中文名称（如「创建信号哨兵」）与参数预览（URL + 判定模式 + 间隔）。
- `harness/core/no-progress-notice.ts`：结果含探测地址、随机 id 时的归一化与 `VOLATILE_RESULT_KEYS` 补充。
- 回归测试：成功 / 失败 / 缺参数三态，与既有定时任务工具测试同款。

### 4.3 前端

- 桌面端零新页面：工具回执经既有工具卡片渲染；「设置 → 信号哨兵」列表无需区分创建来源（Agent 建的与手工建的完全同构）。
- 可选小增强（P2）：哨兵列表行加「来源会话」跳转，便于从列表回到当初对话。

### 4.4 数据模型

零迁移、零新表：哨兵已有 `signal_watcher` 表；会话绑定复用哨兵既有的 session 绑定字段（与定时任务同模式）。

## 6. 风险与开放问题

| 问题 | 风险 | 推荐默认 |
|---|---|---|
| Agent 擅自创建哨兵（未获用户明确要求） | 中 | 与定时任务同款提示词硬约束 + 回执卡片即时可见；列表可当场删 |
| Agent 配错参数（判定模式 / 字段路径） | 低 | 服务端校验原样返回错误；回执展示全部参数供口头纠错；首探（立即测试探针）在创建回执中带一次实测结果 |
| 用户借哨兵探测内网（绕私网禁令） | 中 | 禁令在 service 层强制，工具层无豁免；管理员网段放行机制照旧 |
| 触发提示词注入（哨兵页面的既有风险，非本提案新增） | 低 | 与手工创建同一校验链路，无新增面 |

**待确认决策**

1. `create_signal_watcher` 是否走工具审批（哨兵带出网 URL，比定时任务敏感一档）？建议 P1 不加审批（与定时任务对称），靠回执 + 列表治理；若评审倾向从严，可只对 `create` 加审批。
2. 创建回执是否自动附带「立即测试探针」结果？建议附带（既有能力，配置错误当场暴露）。
3. 删除是否需要确认？建议与设置页同语义（直接删），回执告知。

## 7. 测试要点

- 工具三态：成功（回执含全部参数）、服务端拒绝（私网 URL、字段路径非法、间隔越界——错误信息模型可读）、缺参数。
- 所有权：只能 list / update / delete 本人哨兵；跨用户 id 被拒。
- 防滥用：提示词约束文案存在性断言（对齐定时任务工具测试）。
- 展示链路：summarizer 摘要、toolDisplay 中文名与预览、no-progress 归一化各有用例；结果中探测地址不进 no-progress 误杀名单的语义字段。
- 回归：设置页哨兵 CRUD 行为零变化；哨兵触发链路（探测 → 判定 → 开会话）零变化。

## 8. 验收标准与观察指标

**验收**

1. 对话中说「盯住 X 接口的 Y 字段，变了就做 Z」，Agent 创建哨兵成功，回执展示全部参数且首探结果正常；后续真实变化在原会话触发执行。
2. 「把间隔改成 5 分钟」「暂停这个哨兵」「删掉」分别经 update / delete 工具完成，设置页列表同步。
3. 私网地址创建被拒，模型收到可读错误并向用户解释。
4. 定时任务工具与设置页行为无任何回归。

**指标（上线后 8 周）**

- 经 Agent 创建的哨兵占比（对比手工创建）；
- Agent 创建后 24h 内被修改 / 删除的比例（配置质量）；
- 哨兵总体创建量是否上升（验证「对话即配置」降低门槛假设）。
