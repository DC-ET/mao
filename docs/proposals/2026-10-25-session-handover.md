# 提案：会话移交 —— 人会休假、会离职，会话和挂在它身上的自动化不该跟着断

> 团队里 Agent 的使用以「人」为锚：会话归人、定时任务绑在人的会话上、工作区是人的目录。人一休假或离职，这条链就悬空——今天没有任何机制把「进行中的工作」从一个人交给另一个人。

- 状态：已否决（2026-10-25），存档勿再评审
- 日期：2026-10-25
- 提案总览：见 [docs/proposals/README.md](README.md)
- 规模：小~中（ownership 变更 + 权限 + 审计 + 双端入口；一张关联表或一列）
- 关联：`session`（user_id / 分享 / 导出）、`schedule` / `signal`（会话绑定的自动化）、`file`（工作区归属）、`audit`、`shared-directory`

## 1. 背景与现状

### 1.2 会话以人为锚，人走链断

现状事实：

- 会话 `session.user_id` 归属创建人，全链路（消息、收件箱、定时任务历史、边路任务）跟着这个人。
- 会话分享（已实施）是**只读快照**：水位冻结、看不了后续、接手人不能继续对话。
- 定时任务 / 哨兵绑定在「创建时的会话」上（工具描述与设置页语义均如此），触发历史也在该会话累积。
- 账号停用是唯一与「人离开」相关的机制——停用后一切冻结，没有「交给谁」的出口。

于是真实发生的事：同事休产假 / 离职 / 换组，他名下那个跑了两个月的「每周竞品简报」定时任务、那个上下文已经磨合得很好的巡检会话，要么跟着账号一起冻结，要么接手人在自己的会话里从零重建——把提示词、经验、口径从旧会话里一点点抄出来。**团队两年攒下的最值钱的资产（磨合好的会话上下文），恰恰是最不可交接的。**

### 1.2 现有机制为什么不够

| 现有机制 | 缺口 |
|---|---|
| 会话分享（只读链接） | 冻结快照，不能续聊、不能接管定时任务 |
| JSONL / Markdown 导出 | 内容能带走，工作区、自动化绑定、后续执行带不走 |
| 团队经验库 / 经验 | 沉淀的是结论不是「进行中的工作」 |
| 管理员会话可见 | admin 看得到，但无法变更归属，更不该替用户长期背账号 |

### 1.3 一个真实场景

运营 A 配了一个哨兵盯库存接口，触发时在专属会话里做补货建议，跑了三个月，提示词和经验都磨顺了。A 下月离职。今天 B 接手的方式是：A 临走前把哨兵配置截图、提示词复制、工作区文件打包发给 B，B 逐项重建——参数抄错一点，三个月的磨合就打折。

有移交后：A（或管理员）在该会话「移交」给 B——消息历史、哨兵与定时任务绑定、边路任务记录一并过去，B 第二天照常收到触发通知，在同一个会话里继续；A 的账号随后停用，无任何影响。全程有审计记录。

## 2. 目标 / 非目标

**目标**

1. 桌面端会话提供「移交给…」：把会话（含消息历史、边路任务 / 子代理会话记录、其上绑定的定时任务与哨兵）移交给同实例另一用户。
2. 前置校验：仅终态会话可移交（执行中 / 排队中先等或取消）；接收人须具备会话创建权限与对应 Agent 使用权；渠道会话（飞书 / 钉钉 / 微信绑定）P1 不支持。
3. 工作区分级处理：共享目录工作区无碍直接跟；个人工作区默认**不随会话移交**（留在原主名下），移交互动里明示，可选由管理员另行转共享。
4. 移交后：接收人成为会话 owner（可继续对话、收到其定时任务 / 哨兵的触发与完成通知），原主失去访问；定时任务 / 哨兵的触发与历史在新 owner 账下继续。
5. 双向确认：移交需接收人**接受**（收件箱新事件，可拒绝），避免垃圾会话硬塞。
6. 全程审计：谁在何时把什么移交给谁，可追溯。

**非目标**

- 不做运行中会话的热移交（不新增相位、不碰 `task-terminal.service.ts`）。
- 不做部分移交（只交定时任务不交会话等拆分动作；P1 整体移交）。
- 不做跨实例移交（bundle / 导出已覆盖跨实例搬运）。
- 不做渠道会话移交（渠道绑定与实例账号强耦合，P1 明确排除）。
- 不做工作区文件所有权的自动变更（个人工作区文件含隐私边界，交由管理员按共享目录机制处理）。

## 3. 与已否决 / 已排除方向的边界

| 方向 | 本提案为何不是它 |
|---|---|
| 渠道人工接管 Human Handoff（2026-10-11 否决） | 那是渠道会话**运行中**切真人回答（新增 `WAITING_HUMAN` 相位 + 渠道回发）；本提案是桌面 / Web 会话的**静态归属变更**，要求终态、零新相位、零执行链路改动 |
| 团队知识层（2026-10-19 否决） | 不新增共享 scope、不做内容投稿审核；被移交的会话始终只有一个 owner |
| 数据保留与可携带（2026-10-09 否决） | 不删数据、不做导出增强；是权限层面的归属变更 |
| 多 Agent 协作（2026-10-05 否决） | 无编排无协作语义，单会话单 owner |

## 4. 技术方案

### 4.1 数据模型（迁移按实施顺序顺延，当前最新 V170）

```sql
ALTER TABLE `session` ADD COLUMN `handover_from_user_id` BIGINT NULL COMMENT '最近一次移交的原 owner，展示溯源用', KEY `idx_session_handover` (`handover_from_user_id`);
```

- 不引入移交单表：移交是一次性动作，用收件箱事件承载「待接受」状态（`pending_handover` 记在 session 扩展字段或收件箱 payload），接受 / 拒绝即终态；审计记录走既有 audit。
- 备选：若评审希望移交历史可查，再加 append-only 的 `session_handover_log`（from / to / at / result），P1 先不加。

### 4.2 后端（`session` 域内新增 handover 服务与路由）

1. `POST /v1/sessions/:id/handover { toUserId }`：校验（owner 本人或 `session:write` 管理员发起；终态；接收人活跃且有权用该 Agent；非渠道会话）→ 置待接受 + 收件箱通知接收人（新 kind `SESSION_HANDOVER`，按规范三处同改）。
2. 接受：事务内 `session.user_id = to`，同步更新其绑定的 `scheduled_task` / `signal_watcher` 的归属与通知投递目标；边路任务 / 子代理会话若挂在该会话下则一并改归属（复用其既有归属字段）；写审计。
3. 拒绝 / 7 天超时：回退待接受标记，通知发起人。
4. 移交后原主对该会话所有接口返回 404 / 无权限（与从未拥有过一致）；会话分享链接若存在则失效（快照含原主隐私语境，一并作废重建）。

### 4.3 前端

- 桌面端会话右键 / 详情菜单「移交」：选人（搜索同实例用户）→ 确认页明示将移交的内容清单（消息历史、N 个定时任务、M 个哨兵、边路记录）与**不移交**的内容（个人工作区文件）→ 发起。
- 收件箱 `SESSION_HANDOVER` 事件：接受 / 拒绝按钮 + 会话摘要预览（标题、最近活动、绑定自动化数量）。
- admin：会话详情显示移交记录（来自审计）；支持管理员代发起（人员已离职场景）。

### 4.4 权限与隐私

- 发起权：owner 本人，或持 `session:write` 的管理员（离职场景）；审计区分两类发起。
- 隐私强提示：确认页明示「接收人将看到完整消息历史」；移交互斥于「仅移交流水」之类的折中（P1 不做脱敏移交）。
- 接收人侧的 Agent 权限：若接收人无权使用该 Agent，移交前置校验直接拒绝并提示管理员先授权。

## 6. 风险与开放问题

| 问题 | 风险 | 推荐默认 |
|---|---|---|
| 消息历史含原主隐私内容（与模型的私人对话、误发的敏感信息） | 高 | 确认页强提示 + 只能整体移交；建议同时提供「导出后删除」的替代出口（既有导出） |
| 定时任务 / 哨兵归属联动漏改（通知仍发旧主） | 高 | 归属变更收口在一个事务服务方法；「触发通知只达新主」专项测试 |
| 接收人被塞垃圾会话 | 中 | 双向确认 + 7 天超时自动拒绝 |
| 离职账号的大量会话逐个移交太烦 | 中 | P2 给 admin 批量移交（按用户全量），P1 单会话 |
| 边路任务 / 子代理会话归属模型不一致 | 中 | P1 先随主会话整体变更，回归既有边路 Tab / 轨迹视图 |
| 移交中的会话被并发唤醒（定时任务到点） | 低 | 移交窗口内置为终态 + 队列暂停，接受后恢复 |

**待确认决策**

1. 个人工作区是否允许「随会话移交」？建议 P1 不允许（隐私边界清晰），需要文件协作走共享目录。
2. 移交后原主是否保留只读访问期（如 7 天）？建议不保留（干净切割），有需要先导出。
3. 接收人是否必须与原主同 Agent 权限组？建议是（前置校验拒绝），避免移交完不能用。
4. 定时任务历史（过往执行记录）是否随会话可见？建议随会话整体可见（它们本来就在会话消息流里）。

## 7. 测试要点

- 状态机：终态才可移交；待接受 / 接受 / 拒绝 / 超时各路径；并发移交（第二人发起时第一单在途）被拒。
- 归属联动：接受后定时任务到点触发，会话消息与通知只达新主；哨兵触发同；原主 API 全部 404。
- 权限：非 owner 且非管理员发起被拒；接收人无该 Agent 权限被拒；渠道会话被拒。
- 分享链接：移交后旧链接失效。
- 审计：发起 / 接受 / 拒绝均有记录，管理员代发起可区分。
- 回归：分享、导出、收件箱、定时任务可靠性 E2E 无变化。

## 8. 验收标准与观察指标

**验收**

1. 用户 A 将带 1 个定时任务、1 个哨兵的终态会话移交 B；B 接受后，下一次定时触发在 B 的通知与会话内出现，A 无任何访问。
2. B 拒绝后回退，A 收到通知，会话原样。
3. 管理员对离职用户名下会话代发起移交并成功。
4. 移交全程在审计中可查。

**指标（上线后 8 周）**

- 移交发生次数与场景分布（休假 / 离职 / 换组）；
- 被移交会话在移交后 30 天内的继续使用率（验证「接得住」）；
- 被移交自动化的存活率（移交后 30 天仍在跑的比例）——本提案核心假设「资产不断链」的直接验证。
