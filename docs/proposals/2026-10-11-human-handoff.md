# 提案：渠道会话人工接管（Human Handoff）—— 飞书群里 Agent 答不动时，@ 一下真人

- 状态：**已否决**（2026-10-11 评审：不做。本文仅存档，勿再评审）
- 日期：2026-10-11
- 提案总览：见 `docs/proposals/README.md`

## 1. 背景与现状

Mao 的三个 IM 通道（飞书 / 钉钉 / 微信 Bot）今天都是**纯 Agent 应答**：用户说一句话，Agent 跑一轮，把最终回复发回群里。链路已经相当完整——飞书有进度卡、排队卡、点踩、合并转发展开、卡片回调（`card-action.service.ts` 分派「立即发送」与「取消本次任务」）；微信有 24 小时窗口预检与 Webhook 降级；钉钉有排队卡片。

但**没有一条"人进来"的路**：

1. **Agent 解决不了时没有出口**。用户问了一个超出知识范围或需要内部决策的问题，Agent 只能猜或说不知道。群里对话就此卡死——用户得不到答案，也没有"转人工"的概念。
2. **真人想答也插不进**。Agent 会话是服务端自动执行的，人类成员在群里说话不会影响会话；除非管理员去后台改配置，没有任何办法让"这一轮由人来回答"。
3. **问对人的机制缺失**。即使想转人工，转给谁？按什么规则转（关键字？值班表？提问者是谁？）？转过去之后上下文怎么带（总不能让人去后台翻会话）？
4. **渠道端 ≠ 桌面端**。桌面端 / Web 端用户可以直接在会话里打字接管，但 IM 渠道的使用者（飞书群成员）**根本不在 Mao 里**——他们唯一的入口就是群消息本身。对"把 Agent 接进飞书群"的团队，人工接管是客服 / 运维场景的刚需。

相邻方向的边界：

- **不是多 Agent 协作 / 队友信箱**（已否决）：不引入持久队友、DAG 调度，只是"本轮会话由 Agent 切给人"，执行模型不变。
- **不是审批**：工具审批（`approval-rule` 域）是"这一步能不能做"的动作门；本提案是"这一轮谁来答"的执行者切换，发生在 Agent 回合边界，不在工具边界。
- **不是 ask_user_questions**：那是 Agent 向**发起者**提问（本会话的 Mao 用户）；本提案是把会话**移交给另一个真人**（可能是完全不同的 Mao 用户，甚至群里的非 Mao 用户经由管理员代答）。
- **不改渠道会话的自动执行主链路**：无接管请求时行为与今天完全一致。

## 2. 目标 / 非目标

**目标**

1. **接管请求**：Agent 可以主动发起接管（工具 `handoff_to_human`：带原因与建议转交对象），用户也可以触发（飞书卡片按钮「转人工」、桌面端会话操作、API）。任一入口都在当前回合边界把会话切到 `WAITING_HUMAN` 相位。
2. **通知到人**：接管请求按配置路由到目标 Mao 用户（飞书 / 钉钉 / 站内信 + 收件箱新 kind `HANDOFF_PENDING`），通知里带**脱敏上下文摘要**（用户原话 + Agent 已尝试的思路 + 建议），人点链接直达桌面端该会话。
3. **人在环里回答**：被指派的用户在桌面端（或飞书卡片上，P2）直接输入回复，该回复作为本轮最终答复发回渠道会话，消息标记 `handledBy=用户ID`；接管人可查看该会话的完整历史（含 Agent 跑过的轮次，对齐现有只读分享的视野）。
4. **路由策略**：按 Agent 配置默认接管人（`agent.configJson.handoff.userId`）；Agent 发起时可建议对象（按值班关键词匹配，P2）；无人可转时明确报错回渠道，不静默失败。
5. **审计与状态**：接管 / 回答 / 放弃全程写审计与 `activity`；会话相位 `WAITING_HUMAN` 在桌面端任务列表可见（与 `WAITING_APPROVAL` 同级的橙点语义），崩溃恢复可还原该相位。

**非目标**

- 不做群内非 Mao 用户的直接接管（P1 被指派人必须是 Mao 用户，从桌面端作答；群成员代答是 P3 评估项，涉及渠道侧身份映射）。
- 不做值班表 / 排班系统（P1 静态默认接管人 + Agent 建议；值班轮换是后续可评估方向）。
- 不做接管人的工作负载均衡（同时多个接管请求时的分配策略）。
- 不做"转给外部工单系统"（Zammad / 客服系统对接）——那是出站 Webhook 的延伸场景，另立议题。
- 不改飞书 / 钉钉 / 微信的入站解析与消息落库链路。

## 3. 技术方案

### 3.1 相位与状态机

- `session.phase` 新增取值 `WAITING_HUMAN`（复用既有相位字段，`isActivePhase` 语义需评审：等待人工**不算**可继续自动执行，但任务列表要显示为"等待中"——建议单列状态而非并入 RUNNING）。
- 进入条件：Agent 调 `handoff_to_human` 且被接受 / 用户触发接管；离开条件：接管人提交回复（→ COMPLETED）、接管人放弃（→ FAILED 并附原因，或回到 RUNNING 由 Agent 重试，按操作选择）、超时未接（配置默认 30 分钟，→ 回渠道提示"暂时无人处理"并保留会话可人工回看）。
- 崩溃恢复：`WAITING_HUMAN` 相位落库，重启后恢复为等待态（不自动续跑，等的是人不是机器）。

### 3.2 工具与入口

- **内置工具 `handoff_to_human(reason, suggestUserId?)`**：注册进 `createDefaultToolRegistry`（`harness/tool/impl/`）。按 AGENTS.md 规范同步：`session/util/tool-result-summarizer.ts` 补结果摘要、`desktop/src/utils/toolDisplay.ts` 补中文名称与参数预览、补成功 / 失败 / 缺参回归测试。
  - 该工具**不产生工具结果文本给模型**——调用即终结本轮 Agent 执行（与 `ask_user_questions` 的"本轮挂起"语义同源，但去向不同：一个是问发起者，一个是移交给别人）。
  - 被指派人不存在 / 已停用 → 工具报可读错误，Agent 可继续自行处理或再次发起。
- **桌面端入口**：会话操作栏「转人工」（仅渠道会话显示；本地 / 桌面发起的主会话不需要——用户自己就在）→ 弹指派对象选择 → WS 帧 `handoff_request`。
- **飞书卡片入口（P2）**：进度卡 / 排队卡增加「转人工」按钮，走既有 `card.action.trigger` 回调链路（复用 `FeishuCardActionService` 的分派模式，按钮仅原发送者可操作）。

### 3.3 通知与路由

- 通知内容：标题「有人请求人工接管」+ 会话名 + 渠道来源徽标（飞书群 / 钉钉 / 微信）+ 脱敏摘要（用户原话 ≤200 字、Agent 已尝试的工具概要、handoff reason）。
- 投递通道：站内信 + 收件箱（新 kind `HANDOFF_PENDING`，偏好默认开）+ 若接管人绑定了钉钉 / 飞书个人通知（复用现有通知配置，`notification` 偏好体系）。
- 指派解析顺序：工具参数 `suggestUserId`（校验存在且启用）→ Agent 配置默认接管人 → 报错无可转对象。
- 摘要脱敏：复用 feedback 草稿同源的敏感规则（工具目标中的敏感文件名摘要化），用户原话按现有 inbox 脱敏口径。

### 3.4 接管人回答

- 桌面端该会话顶部显示「人工接管中 · 指派给 X」横幅 + 输入框（替代普通发送入口，发送的是**接管回复**而非新任务）。
- 回复提交：`POST /v1/sessions/:id/handoff-reply`（登录态，仅被指派人本人）→ 回复作为 ASSISTANT 消息落库（`metadata.actor=human`、`handledBy=userId`）→ 经渠道既有回复通道发回群里（飞书 `message.reply`、钉钉 / 微信同源）→ 相位转 COMPLETED。
- 接管人可见完整历史：会话详情本就是属主可见；被指派人若非会话属主，需新增「接管人可读」授权（`handoff.assignee_id` 落库，读校验放行 assignee 与属主）。这是本提案唯一的权限模型扩展点。
- 放弃接管：`POST /v1/sessions/:id/handoff-release`（附原因）→ 相位回退（FAILED 或 RUNNING 重试，按原因选择）→ 通知原请求方（Agent 发起时无"原请求方"可通知，仅记录审计；用户触发时通知该用户）。

### 3.5 数据模型（迁移号顺延，当前已到 V147）

`session` 表加一列（不加新表，接管是一次性事件、无历史查询需求）：

```sql
ALTER TABLE `session`
    ADD COLUMN `handoff_assignee_id` BIGINT NULL COMMENT '人工接管被指派人（user_id），非空即 WAITING_HUMAN' AFTER `memory_injection_disabled`;
```

- 指派人 ID 落库即授权；回答 / 放弃后置 NULL（保留审计在 `activity` 与消息 metadata）。
- 不做 `handoff_request` 历史表：P1 单会话同时只有一个在途接管请求（重复请求直接覆盖并重新通知，语义简单）；历史追溯靠 activity 记录。

## 4. 分阶段实施

| 阶段 | 内容 | 规模 |
|---|---|---|
| P1 | `WAITING_HUMAN` 相位 + 工具 `handoff_to_human` + 桌面端入口与接管横幅 + 站内信 / 收件箱通知 + 接管人回答通道（REST + 渠道回发）+ assignee 读授权 | 中 |
| P2 | 飞书卡片「转人工」按钮（回调链路复用）+ Agent 建议对象（值班关键词）+ 超时未接策略 | 小~中 |
| P3 | 群成员代答评估（渠道身份 → Mao 用户映射）、接管统计（管理后台：接管率 / 平均响应 / 未接率） | 小~中 |

## 5. 风险与开放问题

- **相位语义扩散**：`WAITING_HUMAN` 加入后，所有消费 `isActivePhase` 的地方（任务列表徽标、边路任务聚合、崩溃恢复巡检、预算准入）都要重新审视。缓解： Phase 作为新枚举值单列，不改动 RUNNING 等既有取值的判定；`isActivePhase` **不**纳入 `WAITING_HUMAN`（等待人不该阻塞"自动执行中"的统计），任务列表用独立文案与橙色徽标。实施时逐处回归（本提案测试要点列出）。
- **Agent 滥用 handoff**：模型可能过早转人工把活推给人。缓解：工具描述里明确"仅在确实无法解决时使用"；管理后台可看每个 Agent 的接管发起次数；P3 再评估阈值熔断。
- **接管人越权读会话**：assignee 授权是持久能力（直到回答 / 放弃）。缓解：授权仅限该会话只读 + 一次回复，回答后即收回；assignee 读不包含 `export` 等破坏性操作（读校验只放行 GET 消息与上下文）。
- **通知骚扰**：接管请求默认进收件箱 + 个人通知。缓解：偏好可关（收件箱偏好新增 `handoffPendingEnabled`）；同会话重复接管 5 分钟内只通知一次（dedup）。
- **超时策略误伤**：30 分钟无人接就 FAILED 可能太短（夜间 / 周末）。缓解：超时可配（按 Agent），默认行为改为「不失败、保留等待」仅通知原触发方"仍无人处理"，只有显式配置超时的 Agent 才自动收尾。
- **开放问题**：渠道群里"转人工"后，用户继续在群里说话怎么办（期间的新消息应入队，等人工回复后由 Agent 或人工继续处理，不丢失）——建议复用现有渠道入站队列（`inbound-queue`），P1 实现时确认排队消息在 WAITING_HUMAN 期间的行为口径。
- **开放问题**：一个会话被接管后，原 Agent 的定时任务 / Webhook 触发打到这个会话怎么办——建议触发照常入队但暂不执行，人工回复后按队列消费，评审确认。

## 6. 测试要点

- 工具：`handoff_to_human` 正常发起（相位切 `WAITING_HUMAN`、通知落库、`handoff_assignee_id` 落库）；缺 reason 报错；建议对象不存在 / 停用报可读错误且 Agent 可继续。
- 通知：站内信 + 收件箱 kind `HANDOFF_PENDING` 写入；摘要脱敏（敏感文件名为 `[sensitive]`、用户原话按既有口径）；偏好关闭时不写库不广播；5 分钟重复接管 dedup。
- 回答：非被指派人调 `handoff-reply` 返回 403；被指派人回复后消息落库带 `actor=human` + `handledBy`、渠道回发（飞书 reply / 钉钉 / 微信同源）、相位 COMPLETED、`handoff_assignee_id` 置 NULL。
- 放弃：release 后相位按原因回退；assignee 读授权收回（再调 handoff-reply 返回 403）；审计记录完整。
- 相位回归：`isActivePhase('WAITING_HUMAN')` 为 false；任务列表显示"等待人工接管"橙点；边路 / 子代理聚合不把 WAITING_HUMAN 计入 RUNNING；崩溃恢复把该相位还原为等待态且不自动续跑。
- 排队：WAITING_HUMAN 期间渠道新消息入队不执行；人工回复后队列正常消费。
- 渠道入口（P2）：飞书卡片按钮仅原发送者可操作；回调后卡片刷新为新状态（对齐既有排队卡终态模式，不能停在 loading）。
- 预算与准入：接管回复不计入 Agent 任务预算（不是模型调用），但会话既有预算状态不变；Agent 发起 handoff 前的调用照常计费。
