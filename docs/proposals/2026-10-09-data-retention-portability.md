# 提案：数据保留策略与个人数据可携带 —— 让数据"有寿、可拿、可注销"

- 状态：**已否决**（2026-10-09 评审：不做。本文仅存档，勿再评审）
- 日期：2026-10-09
- 提案总览：见 `docs/proposals/README.md`

## 1. 背景与现状

平台的数据增长今天只有一处有寿可期：`inbox/inbox.cleanup.ts` 对收件箱历史做 90 天硬编码清理（代码常量、调度器模式成熟）。其余全部无限增长：

- **会话/消息**：`session` + 消息表随使用单调增长，归档的 compaction 文件也堆在数据目录；
- **`llm_call`**：管理后台调用流水，逐次调用一行，是最快的增长源；
- **审计日志**（`audit` 域）：管理 API 调用全量落库；
- **`message_file_change` / `session_activity`**：逐工具、逐文件变更的记录。

后果有三个，都指向团队采用：

1. **运维成本**：DB 体积与备份时长线性恶化（备份提案的保留策略正好需要一个"删"的对偶）。
2. **合规问询无解**：成员离职"他的数据怎么处理"、审计"调用记录保留多久"——今天只能手工写 SQL。
3. **数据可携带缺失**：用户问"我的数据能不能导出带走"，唯一的现成能力是单会话只读分享快照与会话 JSONL 导出（2026-10-06 session-share-export 已实施）——那是**单会话**粒度，没有账号级全量导出，更没有注销。

与已实施提案的边界：session-share-export 是"把一次任务结果分享给别人看"；本提案是"把一个人的全部数据交给本人"与"让旧数据按期退场"，粒度（账号 vs 会话）与目的（可携带/保留 vs 分享）都不同。

## 2. 目标 / 非目标

**目标**

1. **保留策略**：按数据类型（会话消息 / 调用流水 / 审计日志 / 收件箱 / 会话活动）分别配置 TTL，默认全关；执行器每日一次，删除走"软删标记 → N 天后硬删"两段（对齐既有 `deleted` 列惯例），删除前对目标数据打包归档（压缩进数据目录 `archives/`），可找回。
2. **执行可见**：每次执行产出报告（类型、命中行数、删除行数、归档包路径），管理后台「数据治理」页可见；支持 dry-run（只报告不动手）。
3. **账号级导出**：用户自助"导出我的数据"→ ZIP：全部会话 JSONL（复用既有导出格式）+ 记忆条目 + 上传文件清单（含文件本体）+ 用量汇总 + 个人设置；异步生成 + 收件箱通知下载（对齐大文件异步生成模式）。
4. **停用与注销**：账号停用（拒绝登录、会话保留可恢复）与注销（会话匿名化保留统计 or 级联删除，二选一配置）——管理员执行 + 审计留痕。

**非目标**

- 不做法律合规咨询/认证材料（提供机制，不提供意见）。
- 不做跨实例迁移（那是备份提案的职责，见 `2026-10-09-backup-restore.md`）。
- 不做冷存储/对象库归档（归档 = 压缩包落数据目录，运维自行 rsync）。
- 不做实时匿名化流（批量作业满足诉求）。

## 3. 技术方案

### 3.1 保留策略（P1）

- `retention` 域：`retention_policy` 表（data_type、ttl_days、enabled、soft_delete_grace_days）+ `retention_run` 表（执行批次：起止、命中/删除数、归档路径、dry_run 标记）。
- `RetentionScheduler` 完全对齐 `InboxCleanupScheduler` 结构（start/stop + 每小时 tick、每日执行一次）；删除分批 + 限流（每批 N 行、批间 sleep），避开大事务。
- 归档：删除批次对应数据打包（JSONL + manifest）进 `{dataDir}/archives/retention-{type}-{date}.tar.zst`，manifest 记 WHERE 条件与行数，供人工找回。
- 级联顺序：消息 → 会话 → 活动/文件变更 → 调用流水 → 审计（按外键依赖排序，每类独立策略独立执行，一类失败不影响其余）。

### 3.2 账号导出（P2）

- 复用 session-share-export 的 JSONL 序列化（首行元信息 + 逐行原始消息）+ memory 域读取 + file 域遍历上传目录；ZIP 流式生成到 `{dataDir}/exports/`，完成进收件箱通知（notification 域已有任务事件类型，新增导出事件）。
- 导出包可选加密口令（与备份提案的加密方案二选一实现后共享，避免双份代码）。

### 3.3 停用与注销（P3）

- `user` 域增加 `status`（ACTIVE/DISABLED）+ `anonymized_at`；停用：JWT 失效 + 登录拒绝；注销：级联删除 or 匿名化（user 行保留 id、清 PII、会话 title 匿名、消息保留 or 删除按配置），全程审计。
- 注销是毁灭性操作：管理员二次确认 + 执行前自动导出该账号数据包（默认开，可关）。

## 4. 分阶段实施

| 阶段 | 内容 | 规模 |
|---|---|---|
| P1 | 策略表 + RetentionScheduler + dry-run + 报告 + 审计日志/调用流水 TTL | 中 |
| P2 | 会话消息/活动 TTL + 账号级导出（ZIP + 收件箱通知） | 中 |
| P3 | 停用/注销 + 导出包加密 + admin 数据治理页完善 | 小~中 |

## 5. 风险与开放问题

- **误删**：默认全关 + dry-run 先行 + 每类策略单独开关 + 执行报告先行审阅；软删两段给后悔期。
- **与用量历史冲突**：删了 `llm_call` 后历史报表出现断层。缓解：报表明示"统计范围受保留策略影响"，策略变更在管理后台留痕。
- **外键深度**：会话删除涉及消息/todo/activity/file_change/subagent 多层。缓解：按依赖序分批删 + 每类限流；先仅在测试库全链路验证。
- **导出含敏感数据**：导出的可能是别人共享的会话。缓解：导出范围仅"本人创建的会话 + 本人参与可写的"，共享快照不含他人私有会话；包体大时异步 + 通知。
- **开放问题**：保留策略是否需要团队共享池口径（与预算提案同款问题）——P1 按数据类型全局策略，用户级差异不做。

## 6. 测试要点

- TTL 到期只删目标类型，关联类型不受影响；dry-run 零删除。
- 软删 → 宽限期 → 硬删两段行为正确；归档包可解包且 manifest 行数与删除数一致。
- 分批删除不产生长事务（批量与限流参数生效）；一类策略执行失败不影响其余。
- 账号导出 ZIP：会话 JSONL 与单会话导出口径一致、记忆/上传清单完整、用量汇总数值对得上。
- 停用后登录拒绝且数据保留；注销后 PII 清除、统计保留、审计留痕、执行前自动导出默认开启。
