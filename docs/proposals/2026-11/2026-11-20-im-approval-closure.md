# 提案：IM 渠道审批闭环 —— 审批卡直达飞书 / 钉钉

> 多端审批（2026-11-06）落地后，桌面 / 浏览器 / CLI 已能在任何 WS 端裁决审批，但**IM 通道仍是断头路**：飞书 / 钉钉用户收到的唯一审批相关推送是 3 分钟无人处理后的升级提醒 webhook——一张**没有按钮**的卡片，文案是「有一条本地操作待你审批，请回到桌面端处理」；微信会话则连提醒都被整体跳过。而 IM 恰恰是「人不在电脑前」的主场景：任务发到飞书后出门， LOCAL 高危操作挂起 30 分钟无人裁决，任务就死等。与此同时，飞书 / 钉钉的交互卡片基建已经完全成熟——进度卡的取消 / 重试 / 点踩 / 深链按钮、「仅原发送者可点」的 open_id 鉴权先例、排队插队，全都现成。本提案把审批请求作为第 4 张卡（排队 / 进度 / 完成 / **审批**）接进同一套卡片动作体系，裁决走 approval-registry 同源先到先得，**不新增任何审批语义**。

- 状态：已否决（2026-11-20 评审：云端模式目前无需审批）
- 日期：2026-11-20
- 提案总览见 [docs/proposals/README.md](../README.md)
- 规模：中（约 3 人日；0-1 迁移（审批卡消息映射，视复用 `feishu_p2p_message` 模式而定）；后端 feishu / dingtalk / weixin + notification + approval 投递）
- 关联：`backend-ts/src/harness/approval/approval-registry.ts`（广播 `tool_approval_request`/`tool_approval_resolved` :264/:273）、`backend-ts/src/feishu/card-action.service.ts`（open_id 鉴权先例 :74/:168）、`backend-ts/src/feishu/progress-card.ts`、`backend-ts/src/dingtalk/card-action.service.ts`、`backend-ts/src/notification/task/delivery.service.ts`（微信跳过 :104-116）、`backend-ts/src/notification/task/feishu-notification-card.ts`（升级提醒无按钮 :36/:75/:156）、`docs/plan/2026-11/2026-11-06-multi-end-approval-technical-design.md`

## 1. 背景与现状

| 场景 | 现状 | 代码证据 |
|---|---|---|
| 审批投递面 | approval-registry 仅向 WS 在线端广播 `tool_approval_request`；先到先得裁决 | `approval-registry.ts:264/:273`、`streaming-ws-handler.ts:759/:1374` |
| IM 收到的审批信息 | 仅升级提醒 webhook：无按钮文本卡「请回到桌面端处理」 | `feishu-notification-card.ts:36/:75/:156` |
| 微信渠道 | 审批 / 任务通知整体跳过 | `notification/task/delivery.service.ts:104-116` |
| 飞书卡片基建 | 进度卡含取消 / 重试 / 点踩 / 详情深链；动作鉴权「仅原发送者可点」（open_id 比对） | `progress-card.ts:112-170`、`card-action.service.ts:74/:168` |
| 钉钉卡片基建 | 一卡到底模板（run/cancel/retry/dislike actionId），需管理员配模板 ID，无模板降级 markdown | `dingtalk/card-action.service.ts:42-108` |

## 2. 目标 / 非目标

**目标**

1. **P1 飞书审批卡**：审批挂起时向会话绑定的飞书会话推送「审批卡」（工具名、参数摘要、会话标题、审批级别、来源任务深链），按钮「允许 / 拒绝」——点击经既有 card-action 通道鉴权（**operator open_id 必须匹配会话归属用户的绑定身份**，他人点击返回「仅任务归属人可裁决」），走 approval-registry 同源摘除（先到先得：已被桌面 / CLI 裁决则回「该审批已处理」并刷新卡片终态）；裁决后卡片就地变终态（结果 + 裁决端 + 时间）。拒绝按钮带 confirm 二次确认（防误触）。
2. **P1 钉钉审批卡**：同构——推荐新增独立「审批卡」模板配置项（复用互动卡片基建）；未配置模板时降级为带深链的 markdown 文本提醒（不闭环，与现状等价但不再等 3 分钟）。
3. **P2 微信审批提醒**：取消微信渠道对审批通知的整体跳过——推送**文本提醒**（含会话标题与工具摘要 + 「请在桌面端处理」）。个人微信无回调按钮能力，只提醒不闭环。
4. **P2 升级链路收敛**：审批已成功推送 IM 卡后，3 分钟升级提醒不再发「回桌面处理」文案（改为在已推送的卡上追加超时备注或跳过，评审定），避免双份打扰。
5. **P2 用户级开关与范围**：通知偏好面板（既有）新增「审批推送到 IM」开关（默认开）与「IM 可裁决的审批级别」约束项（默认全部级别可裁决；是否限制最高危级别为评审决策点）。IM 裁决全部进审计（带 channel 来源标记）。

**非目标**

- 不做微信审批闭环（个人微信 bot 无卡片回调能力）。
- 不做群聊成员审批（鉴权锁定会话归属用户一人；群内他人不可裁决）。
- 不做 ask_user_questions 的 IM 化（该工具在渠道会话本就被屏蔽，`harness-service filterToolsForSession :737-751`，属另一个议题）。
- 不改审批规则引擎、权限分级、超时语义（批次 3 / 2026-11-06 方案已定稿，全部沿用）。
- 不做跨任务审批收件箱（批次 21 已否决——桌面不新增收拢面板，IM 卡是「推到人所在的地方」，不是新抽屉）。

## 3. 与已落地 / 已否决方向的边界

| 方向 | 本提案为何不是它 |
|---|---|
| 多端审批（2026-11-06 已落地） | 那是 WS 端广播与裁决；本提案把**投递面**延伸到 IM，裁决语义（先到先得、摘除 CAS、超时）零变化 |
| 升级通知（批次 18 已落地） | 那是「人不在场」的兜底提醒；本提案让在场的人就地裁决，兜底链路保留并收敛 |
| 渠道人工接管（批次 6 否决） | 那是切给真人处理；本提案裁决者仍是任务归属用户本人 |
| 跨任务审批收件箱（批次 21 否决） | 不收拢、不建桌面抽屉；每条审批随其会话推送 |

## 4. 方案设计

- **投递钩子**：approval-registry 广播 `tool_approval_request` 处追加渠道投递——会话为渠道会话（source 线路已可判别，批次 19）且归属用户已绑定时，组装审批卡并推送；记录 (渠道, 卡片消息 ID, 审批 ID) 映射（飞书可复用 `feishu_p2p_message` 的 messageId→sessionId 映射模式，或独立小表，技术方案定）。
- **裁决入口**：飞书 / 钉钉 card-action service 新增 allow / deny actionId 分支——鉴权（绑定身份比对）→ 调 approval-registry 既有摘除接口（与桌面 WS 裁决完全同源，天然先到先得）→ 摘除成功即广播 `tool_approval_resolved`（桌面端卡片自动收口，链路现成）→ 回调响应带新卡（终态）。摘除失败（已处理 / 已超时）返回状态刷新卡。
- **终态回流**：审批被任何一端裁决后，钩子更新 IM 卡终态（谁 / 何端 / 何时）；会话为渠道会话时工具执行结果照常回流聊天。
- **微信提醒**：`delivery.service.ts` 移除对审批事件的微信跳过，改走文本模板；沿用 24 小时窗口与 webhook fallback 既有口径。
- **安全口径**：IM 裁决 = 与桌面点击「允许」完全同权（同一 registry、同一审计）；新增来源标记 `channel:feishu|dingtalk` 进审计明细；开关默认开（关掉即回到现状「只提醒不闭环」）。

## 6. 风险与对策

| 风险 | 对策 |
|---|---|
| IM 误触「允许」放行高危操作 | 拒绝 / 允许均带 confirm 弹窗（飞书卡片 confirm、钉钉模板按钮确认）；用户级开关可整体关闭 IM 裁决；高危级别约束项为评审决策点 |
| 双端竞态（IM 与桌面同时点） | approval-registry 摘除已是 CAS 先到先得（多端审批方案既定语义）；失败方收到「已处理」并刷新卡 |
| 卡片过期 / 机器人重启后按钮失效 | 沿用进度卡「重启恢复续更」同思路：回调时审批不存在即回「该审批已处理或已超时」终态卡，不静默 |
| 钉钉模板缺失导致功能不可用 | 显式降级为文本提醒 + 深链（不闭环但即时可达），管理后台配置处给明确引导 |
| 微信 24h 窗口限制 | 沿用定时任务结果推送的既有兜底（webhook fallback）；窗口失效文案明确 |
| 升级提醒与审批卡重复打扰 | 已成功推卡则会话升级提醒收敛（目标 4） |
| 审计归属 | IM 裁决写入审计时带 channel 来源与操作者绑定身份，与桌面裁决可区分 |

## 7. 测试要点

1. CLOUD 会话（飞书绑定）触发需审批工具：审批卡秒级送达；归属用户点「允许」→ 工具放行、卡变终态、桌面 WS 端同步收到 resolved。
2. 先到先得：桌面先裁决后 IM 点击 → 回「该审批已处理」，卡刷新为桌面裁决终态；反向同验。
3. 非归属人（群聊其他成员）点击 → 返回「仅任务归属人可裁决」，审批状态不变。
4. 拒绝流：confirm 后工具收到拒绝原因，会话继续；升级提醒不再发「回桌面处理」文案（已推卡场景）。
5. 钉钉无模板：降级文本提醒即时送达 + 深链可跳；配置模板后卡片闭环可用。
6. 微信：审批文本提醒送达；24h 窗口失效走 fallback 文案。
7. 开关关闭：审批卡不推送，升级提醒行为与现状逐字节一致（回归口径）。
8. 审计：IM 裁决记录含 channel 来源；与桌面裁决可区分；失败 / 超时审批的 IM 点击不产生裁决记录。
