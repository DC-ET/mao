# 提案：用户自建 Agent —— 把「造 Agent」的权力下放给普通用户，用治理边界兜住

> README 说「Agent 是一等公民」，但今天只有管理员能造 Agent。团队里每个人心里那个「专门帮我干某件事的 Agent」，都要排队等管理员配置。

- 状态：已否决（2026-10-25），存档勿再评审
- 日期：2026-10-25
- 提案总览：见 [docs/proposals/README.md](README.md)
- 规模：中（agent 域归属/可见性 + 桌面端 Agent 编辑器 + 权限边界；复用提示词版本 / 经验 / bundle 全部既有设施）
- 关联：`agent`（agent.routes / agent.service / bundle）、`permission`（RBAC）、`budget`（用户预算）、`model`（模型可见性）、desktop `views/settings`

## 1. 背景与现状

### 1.1 创建权是管理员垄断的

代码事实：Agent 的创建 / 编辑要求 `agent:write` 权限（`agent.routes.ts`），该权限默认在管理员角色手里。README 描述的日常路径也是「管理员：配模型 → 建 Agent → 开账号 / 配权限；用户：选 Agent → …」。

这在「平台早期、Agent 数量少、管理员就是最懂提示词的人」阶段是合理的。但两个场景正在把瓶颈暴露出来：

- **团队规模化**：20 人的团队，每个人对「自己的助手」的想象都不一样——有人要「周报整理 Agent」、有人要「代码评审 Agent」、有人要「专查出货额口径的 Agent」。全走管理员，管理员成为全团队 Agent 迭代的单点；用户的个性化需求被排队劝退。
- **个人自部署**：一个人自托管 Mao，明明 admin 就是自己，调教 Agent 却要切到管理后台操作，心智上「我的助手」和「平台管理」搅在一起。

同时，Mao 已经把 Agent 做成了完整资产（提示词版本化回滚、经验、推荐问题、bundle 导入导出、团队经验库）——**唯独「谁能创造」没动过**。

### 1.2 治理不是下放的反义词，是下放的前提

直接把 admin 的 Agent 编辑器开放给所有用户是不行的：用户自建 Agent 若能任意配模型（烧别人的预算池）、任意加 MCP server（连任意外部系统）、任意拼工具，治理面立刻失控。本提案的核心是**能力引用制**：用户能创造的是「用平台已开放素材组装的私有 Agent」，素材的口子仍在管理员手里。

### 1.3 一个真实场景

运营同学想要一个「日报 Agent」：每天把自己维护的三个数据口径核对一遍，异常时按固定格式提醒。他心里已经有完整的提示词（哪个表、什么口径、什么算异常），但今天他只能把这个提示词发给管理员，等管理员有空配进某个 Agent——而他所在团队的 Agent 是全组共用的，提示词一改影响所有人，管理员也不敢随便加。

如果有私有 Agent：他自己建、自己调、自己用；用顺了之后点「提交为团队 Agent」，管理员在 bundle 导入页一键采纳，全组受益。**个性化不阻塞公共化，公共化从验证过的个性化里长出来。**

## 2. 目标 / 非目标

**目标**

1. 普通用户在桌面端「我的 Agent」页创建 / 编辑 / 停用**私有 Agent**（仅本人可见、可用、可分享给自己的会话）。
2. 能力边界（引用制）：
   - 模型：只能选管理员标记为「用户可选」的模型；
   - Skill：从技能目录只读引用；
   - MCP / 自定义 HTTP 工具：只能**引用**管理员已配置且标记可引用的 server / 工具，不能新建连接；
   - 提示词、经验、推荐问题：与团队 Agent 同设施同体验（含版本化）。
3. 可从任一可见团队 Agent「克隆为我的起点」（fork 提示词 / 技能 / 经验快照）。
4. 「提交为团队 Agent」：一键导出 bundle 申请给管理员，管理员走既有 bundle 导入发布（不新建审核工作流）。
5. 治理：用户 Agent 的用量计入**本人**预算与用量报表；admin 可见用户 Agent 清单（只读 + 停用）；用户 Agent 的会话受全部既有 RBAC / 审计 / 审批约束。
6. 单用户私有 Agent 数量上限（默认 10，可配），防失控。

**非目标**

- 不做用户级 MCP server 创建、用户级自定义 HTTP 工具定义（引用制，连接权仍在管理员）。
- 不做团队共享 / 组织可见 Agent 的新可见级别（P1 只有「团队（现状）」和「私有」两级，不做「小组可见」）。
- 不新建发布审核工作流（bundle 申请 + 管理员导入即全流程）。
- 不做用户间 Agent 转让 / 协作编辑。
- 不改 admin 既有 Agent 管理的行为与界面结构。

## 3. 与已否决 / 已排除方向的边界

| 方向 | 本提案为何不是它 |
|---|---|
| 任务模板 / Runbook（2026-10-19 否决） | 模板是「一次配置、参数化重复执行」的任务资产；本提案是持久的 Agent 配置（角色 / 技能 / 工具集），不涉及调度与参数化 |
| 团队知识层（2026-10-19 否决） | 不新增 TEAM 记忆 scope、不做用户经验提案通道；「提交为团队 Agent」复用 bundle + 管理员显式导入，不是内容级投稿审核 |
| 技能蒸馏（2026-10-11 否决） | 不自动生成任何资产；用户手写自己的提示词，系统不代笔 |
| 低代码画布（README 排除） | 无编排界面；就是表单化的提示词 + 素材引用 |
| 资产分发（已实施，非否决） | 分发解决「搬运」，本提案解决「创造权」；bundle 恰好被复用为发布通道，两者互补 |

## 4. 技术方案

### 4.1 数据模型（迁移按实施顺序顺延，当前最新 V170）

```sql
ALTER TABLE `agent`
  ADD COLUMN `owner_user_id` BIGINT NULL COMMENT 'NULL=团队 Agent（现状）；非空=该用户私有',
  ADD COLUMN `visibility` VARCHAR(16) NOT NULL DEFAULT 'TEAM' COMMENT 'TEAM/PRIVATE',
  ADD COLUMN `origin_agent_id` BIGINT NULL COMMENT '克隆来源 Agent，溯源用',
  ADD KEY `idx_agent_owner` (`owner_user_id`);

ALTER TABLE `llm_model` ADD COLUMN `user_selectable` TINYINT NOT NULL DEFAULT 0 COMMENT '1=用户私有 Agent 可选';
```

- 存量 Agent 全部 `visibility='TEAM' / owner NULL`，行为零变化。
- `mcp_server` / `user_tool` 若需要「可引用」标记，P1 先用「管理员配置的即全部可引用 + 已有的用户可见性规则」收口，不加列；评审时再定是否加 `user_referenceable`。

### 4.2 后端

- 新路由（挂在 `agent` 域，`/v1/agents/my` 前缀）：CRUD + 克隆 + 提交申请；鉴权用**新权限码 `agent:self:write`**（默认授予普通用户角色），与 `agent:write`（管理员）彻底分离。
- 可见性过滤：`agentService` 的列表 / 选用查询统一加 `visibility='TEAM' OR owner=me` 条件——会话创建、推荐问题、经验库、MCP 暴露等所有读 Agent 的路径收口到同一 repository 方法，防止漏过滤。
- 能力边界校验（service 层强制，不信任前端）：提交的 `defaultModelId ∈ user_selectable`、`mcpServerIds / httpToolIds ∈ 已配置集合`、Skill 名 ∈ 目录；越界请求整单拒绝。
- 提交申请：生成 bundle（复用 `agent-bundle.service` 导出，密钥脱敏已有）落到管理员导入入口 + 收件箱通知管理员（新 kind `AGENT_PUBLISH_REQUEST`，按规范三处同改：`@mao/contracts` InboxKind、`backend-ts/src/inbox/types.ts`、桌面图标与偏好）。
- 用量 / 预算：私有 Agent 会话的 `agent_id` 归属即 owner，用户预算、用量报表、LlmCallScene 统计天然生效，零额外开发。

### 4.3 桌面端

- 「设置 → 我的 Agent」：列表（名称 / 模型 / 最近使用 / 状态）+ 新建 / 克隆 / 编辑 / 停用。
- 编辑器为 admin Agent 编辑的**简化子集**（同一份表单组件抽出共享，或独立轻量实现，评审时定）：系统提示词（含版本历史只读）、模型下拉（仅可选池）、技能多选、MCP / HTTP 工具引用多选、经验与推荐问题维护入口。
- Agent 选择器：团队 Agent 与「我的 Agent」分组展示，私有组仅本人有内容时不出现在他人界面。
- 新会话默认无感：私有 Agent 的使用流程与团队 Agent 完全一致（含边路任务、定时任务可选）。

### 4.4 admin

- Agent 列表加「归属」筛选（团队 / 按用户）；用户 Agent 行只读 + 停用（停用即本人不可用，提示原因走收件箱）。
- 模型管理加「用户可选」开关列。
- bundle 导入页对「提交申请」来源打标展示（谁提交的、原 Agent 链接）。

## 6. 风险与开放问题

| 问题 | 风险 | 推荐默认 |
|---|---|---|
| 可见性过滤漏网（某条读 Agent 的路径没加过滤） | 高 | 过滤收口到 repository 单一方法 + 专项测试枚举所有读路径；E2E 用例「用户 A 绝不出现 B 的私有 Agent」 |
| 用户私有 Agent 挤占模型预算 | 中 | 计入本人用户预算（既有硬拦截）；上限默认 10 个 |
| 提示词质量参差拖累体验观感 | 中 | 不做审核（私有即自负责）；克隆入口让好起点可复制；「提交为团队」把质量闸门留在 bundle 导入 |
| 编辑器组件 admin/desktop 双端重复实现 | 中 | P1 允许轻量独立实现快速验证，P3 收敛共享（避免一开始就做跨端抽象） |
| 权限码扩散 | 低 | 只加一个 `agent:self:write`，默认全角色持有，可按角色关闭（整体关停开关） |
| 私有 Agent 的会话分享 / 导出语义 | 低 | 复用既有会话分享（分享的是会话快照，不暴露 Agent 配置）；提示词版本历史对本人全可见 |

**待确认决策**

1. 用户停用账号时其私有 Agent 如何处置？建议随账号停用一并冻结，数据保留。
2. MCP / HTTP 工具是否需要更细的「可引用」标记（区别于「用户可见」）？建议 P1 不加列，观察误配案例。
3. 管理员能否编辑用户私有 Agent？建议只读 + 停用，不代改（责任边界清晰）。
4. 私有 Agent 能否配定时任务 / 哨兵触发？建议可以（用户自己的自动化）。

## 7. 测试要点

- 可见性：用户 A 的私有 Agent 在 B 的选择器 / 推荐 / 搜索 / MCP tools / 定时任务选择中一律不可见；repository 过滤的路径穷举测试。
- 边界校验：提交不可选模型 / 未配置的 MCP id / 目录外技能名均整单拒绝；前端绕过直发 API 同样被拒。
- 克隆：fork 后与原 Agent 完全解耦（原 Agent 改提示词不影响克隆体）；快照包含技能 / 经验。
- 提交申请：bundle 生成 + 管理员收件箱通知 + 导入后成为团队 Agent 且与原私有 Agent 解耦。
- 治理：本人预算超额时私有 Agent 会话被拦截；admin 停用后本人会话创建被拒且收到通知。
- 回归：团队 Agent 全链路（创建 / 编辑 / 使用 / bundle）行为不变；权限目录页新码展示正确。

## 8. 验收标准与观察指标

**验收**

1. 普通用户在桌面端创建私有 Agent（选可选池模型、引用既有 MCP），用它开会话执行任务，用量落在本人报表与预算内。
2. 用户 B 在任何界面与 API 下都拿不到用户 A 私有 Agent 的存在痕迹。
3. 克隆团队 Agent 后修改私有副本，原 Agent 不受影响；提交申请后管理员导入，团队里出现新 Agent。
4. admin 停用某私有 Agent，该用户下次使用时被明确提示。

**指标（上线后 8 周）**

- 创建过私有 Agent 的用户占比、人均私有 Agent 数；
- 私有 Agent 的周活跃会话数 vs 团队 Agent；
- 「提交为团队」的申请量与采纳率（个性化 → 公共化的转化率，本提案的核心假设验证点）。
