# 提案：定时任务可靠性（重试 / 错过补偿 / 运行历史）—— 自动化骨干不能"设了忘"

- 状态：待评审
- 日期：2026-10-09
- 提案总览：见 `docs/proposals/README.md`

## 1. 背景与现状

定时任务（`schedule/scheduled-task.service.ts`）当前的语义是"到点提交一次，成败听天由命"：

1. **无重试**：提交执行后若本轮运行失败（模型故障、会话创建失败、执行异常），没有任何重试机制，只能等下一个触发周期——按天的任务失败一次就空一天，按周的任务空一周。注意这不是 LLM 调用层的事：适配器内部重试只覆盖当次 API 调用，任务级"整轮跑挂"无人兜底。
2. **无错过补偿**：`nextFireTime` 在提交被拒时会回滚（service 内有专门处理），但服务停机、重启期间的触发点直接蒸发，没有"启动后补跑错过的周期"的逻辑。对比会话执行有 `harness/core/crash-recovery-runner.ts` 做崩溃恢复，调度器自己是裸奔的。
3. **无运行历史**：用户看不到一个定时任务"历史上跑过几次、成败如何、上次是什么时候、跑了多久、花了多少钱"。失败是否发生过只能翻会话列表猜。
4. **失败无升级**：`scheduled-task.service.ts` 与通知域无任何集成——任务挂了只有会话自己变成失败态，收件箱不响、管理员不知情。对比入站 Webhook 触发器已有"连续失败自动停用并通知"的成熟先例（`webhook-trigger.service.ts`），定时任务反而没有。

已上线的任务收件箱解决的是**交互类事件**（完成/提问/审批）的汇聚，定时任务这种"无人值守自动化"的可靠性是其自然延伸，但不重叠：收件箱是通道，本提案补的是**重试、补偿、历史、熔断**这套可靠性语义。

对产品定位的影响很直接：定时任务是"重复劳动交给 Agent"的支柱功能（日报、巡检、同步），而无人值守场景对可靠性的要求远高于交互场景——用户不在电脑前，失败了都不知道。

## 2. 目标 / 非目标

**目标**

1. **失败重试**：按任务可配的重试策略（次数 + 间隔，如 3 次 / 隔 5 分钟）对"提交后整轮失败"自动重提；可转移类故障（模型侧）与任务配置错误（已删 Agent）区分，后者重试无意义直接标记。
2. **错过补偿**：服务重启后检测停机期间错过的触发点（`nextFireTime` 在过去且未执行过），按策略补跑（立即补一次 / 跳过 / 仅补最近 N 次），并与崩溃恢复 runner 的执行中语义错开，避免双跑。
3. **运行历史**：新增按任务的运行记录（触发时间、实际执行时间、状态、耗时、成本、跳转会话），桌面端定时任务面板可展开"最近运行"，失败一眼可见。
4. **失败升级**：连续失败达阈值自动暂停任务并通知（复用 Webhook 触发器的停用+通知模式）；单次失败也按用户通知偏好进收件箱。
5. **不双跑保证**：重试、补跑与正常触发共享同一执行占位机制（现有 liveExecution/runExecution 的相位收敛点），任何路径下同一触发点只跑一次。

**非目标**

- 不做 DAG / 任务依赖编排（多 Agent 协作方向已否决，不重启）。
- 不做"错过周期批量补跑全部历史"（只补最近一次或按次数上限，防止复工当天被作业淹没）。
- 不改 cron 表达式解析语义与触发精度（秒级触发、错过窗口判定沿用现有口径）。
- 不做跨实例的调度器选主（当前单后端部署，调度在进程内；多实例部署列入开放问题）。

## 3. 技术方案

### 3.1 运行记录表（V142）

新增 `scheduled_task_run`：`id / task_id / fire_time（计划触发点）/ started_at / finished_at / status（success|failed|skipped|missed_compensated）/ attempt / error_summary / session_id / duration_ms / cost`。与 `scheduled_task` 一对多；触发点 `fire_time` 唯一索引（task_id + fire_time）作为幂等底座——重试是同一 fire_time 的新 attempt，补跑是新的 fire_time 行，天然区分。

### 3.2 重试与占位

- 重试判定放在执行终态收敛处：终态为 failed 且错误属"可重试"（模型类、临时性；不含配置类如 Agent 已删、会话创建失败）时，按策略写入下一次重试计划（间隔退避），到点由调度器以同一 `fire_time`、`attempt+1` 重新提交。
- 复用现有 `liveExecution` 收敛点做占位：同一 `fire_time` 只允许一个 attempt 处于"运行中/待重试"，重启后恢复的 attempt 若超过最大次数直接标记 failed，不无限重试。

### 3.3 错过补偿

- 启动时（或定时巡检）扫描 `next_fire_time < now` 且任务启用、无对应 `scheduled_task_run` 成功记录的任务，按任务策略处理：`skip`（只记一行 missed）｜`run_once`（立即补跑一次）｜`run_recent`（补最近 N 次，默认 1）。
- 停机超过一个完整周期的循环任务，补跑策略默认退化为 `run_once`——补昨天的日报没有意义，记 missed 供历史查看即可。
- 与 `crash-recovery-runner.ts` 的分工：崩溃恢复管"已提交但执行中断的会话"，本提案管"压根没提交的触发点"，两者经 `fire_time` 唯一索引天然不重叠。

### 3.4 前端与通知

- 桌面 `ScheduledTaskPanel.vue`：每个任务展开"最近运行"列表（时间、状态徽标、耗时、跳转会话）；任务编辑弹窗加重试策略（次数/间隔）与错过补偿（跳过/补一次）两个配置项。
- 通知：单次失败按用户通知偏好进收件箱（类型 `SCHEDULED_TASK_FAILED`）；连续失败达阈值（默认 3）自动暂停任务 + 通知，恢复需用户手动启用（对齐 Webhook 触发器"连续失败自动停用并通知"的既有交互，不造新范式）。

## 4. 分阶段实施

| 阶段 | 内容 | 规模 |
|---|---|---|
| P1 | `scheduled_task_run` 表 + 触发点唯一索引 + 运行历史落库与 API + 面板"最近运行" | 小~中 |
| P2 | 失败重试策略（配置 + 调度器重提 + 可重试判定） | 中 |
| P3 | 错过补偿（启动扫描 + 策略）+ 连续失败自动暂停 + 收件箱通知 | 中 |

## 5. 风险与开放问题

- **排期注意**：P2/P3 动 `scheduled-task.service.ts` 的相位收敛点（`finishExecution` 附近），与历史上记忆/收件箱/预算动过的 `task-terminal.service.ts` 收敛点相邻——实施时与在途同类改动错开，重试判定只读终态、不重写收敛逻辑。
- **补偿与重试叠加**：停机期间失败的触发点，复工后先补跑还是先重试易纠缠。缓解：`fire_time` 唯一索引下，补跑是"欠账"的新执行，重试是"已开跑但挂了"的续跑，两条路径经 attempt 与状态机分离，测试用矩阵覆盖（停机×失败×超周期组合）。
- **通知风暴**：多个任务同时失败可能刷屏。缓解：连续失败才自动暂停，单次失败按类型开关走偏好，默认聚合进收件箱不弹系统通知。
- **开放问题**：运行记录的保留期（与已否决的数据保留策略提案的边界——本表只存摘要不存内容，保留期可独立设短，如 90 天）。
- **开放问题**：多实例部署时调度器选主与补偿的竞态（当前架构单实例，列为后续观察项）。

## 6. 测试要点

- 失败重试：可重试失败按策略重提且 attempt 递增；达上限标记 failed 不再重试；配置类错误不重试。
- 幂等：同一 `fire_time` 并发/重启场景下只产生一个运行中 attempt；重启后恢复的 attempt 正确续跑或终结。
- 错过补偿：停机跨越触发点，复工后按策略 skip/run_once 执行且不产生重复执行；错过周期记 missed 行。
- 历史：面板"最近运行"状态、耗时、成本与 `scheduled_task_run` 及会话实际一致；跳转落到对应会话。
- 通知：单次失败进收件箱；连续失败自动暂停并通知；手动恢复后可正常触发。
