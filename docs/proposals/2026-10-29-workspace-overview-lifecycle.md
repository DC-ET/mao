# 提案：工作区看得见也退得掉 —— 工作区总览与生命周期管理

> 文件直管（0.0.281）解决的是「**一个工作区里面**」的操作，Git 管理器（0.0.375）解决的是「一个工作区里面的版本」，但「**我的所有工作区**」至今没有一块面板：新建任务时那个「复用已有工作区」下拉（`/v1/sessions/cloud-projects`）只是一次同步 `readdir` 的目录名平铺——多大、被哪些会话用着、多久没动过、能不能删，一概不知。自托管跑上几个月，git clone 的仓库、试验性目录、机器人通道的工作区越积越多，磁盘只进不出，唯一的清理方式是管理员 ssh 上去 `du` + `rm`。

- 状态：**已细化，技术方案待评审**（[../plan/2026-10-29-workspace-overview-lifecycle-technical-design.md](../plan/2026-10-29-workspace-overview-lifecycle-technical-design.md)，11 项决策已定案；方案对提案有一处关键收窄：通道工作区（feishu-chat / dingtalk-chat，位于全局根、按机器人聚合）明确不做总览与清理）
- 日期：2026-10-29
- 提案总览见 [docs/proposals/README.md](README.md)
- 规模：中（P1 约 2~3 人日、P2 约 1~2 人日；零迁移）
- 关联：`backend-ts/src/session/session.routes.ts`（cloud-projects 端点）、`backend-ts/src/file/workspace-browse.service.ts`、`backend-ts/src/file/workspace-write.service.ts`、`backend-ts/src/session/session.repository.ts`、`desktop/src/components/center/CenterTabBar.vue`、`desktop/src/views/task/TaskView.vue`

## 1. 背景与现状

### 1.1 工作区只有「用的时候的一面」，没有「资产的一面」（代码可查）

| 能力 | 现状 | 证据 |
|---|---|---|
| 列出我的工作区 | `GET /v1/sessions/cloud-projects`：同步 `readdirSync` 平铺 `{userRoot}/projects/*`，只返回 `name / path / isGit` | `session.routes.ts:166-188` |
| 占用大小 | 无任何端点 | — |
| 会话关联 | 无（`session.workspace` 存了路径，但没有反向聚合查询） | `session.repository.ts` |
| 删除 / 清理 | 无端点；文件直管的删除仅限工作区**内部**条目 | `file.routes.ts:411`（workspace-delete 需先有会话上下文） |
| 桌面入口 | 新建任务时「复用已有」下拉 + 会话内工作区 chip（`WorkspaceChip.vue`）→ 都是会话视角 | `TaskView.vue:1066` |

### 1.2 后果

- **磁盘只增不减**：每个 CLOUD 任务的工作区、每次 Git clone、飞书 / 钉钉通道自动生成的会话工作区（`{workspaceRoot}/feishu-chat|dingtalk-chat/…`，`session.routes.ts:642` 注释）都常驻服务器；用户侧零感知、零手段。
- **复用下拉越来越难用**：目录名按字典序排列，几十个 `project-*` 之后用户靠记忆挑；哪个是活跃项目、哪个是半年前的一次性实验无从判断。
- **删不敢删**：用户甚至不知道某个目录被多少会话（尤其归档会话）引用，手动让服务器清理后归档会话的文件浏览 / Git 面板会静默变空。

## 2. 目标 / 非目标

**目标**

1. **P1 工作区总览**：新端点返回用户根目录下全部工作区目录的资产视图——大小、是否 Git 仓库、关联会话数（区分进行中 / 归档）、最近使用时间；桌面端新增「工作区」总览页签（CenterTabs，与 Git 管理器同层），表格呈现、按大小 / 时间排序、点关联会话数跳会话列表。
2. **P2 清理动作**：总览页对「无进行中会话引用」的工作区提供删除（强确认 + 输入目录名确认），复用文件直管「物理删除 + 强确认、不做回收站」的既有先例；有进行中会话引用时拒绝并给出引用清单。
3. 通道工作区一并纳入：总览覆盖用户根目录下全部一级目录（`projects/`、`feishu-chat/`、`dingtalk-chat/` 等），标注来源类别。

**非目标**

- 不做工作区环境模板 / 快照（2026-10-11 已否决）。
- 不做自动清理策略 / 保留期（数据保留提案 2026-10-09 已否决）——本提案只做**用户手动**的查看与删除。
- 不做重命名 / 移动工作区（`session.workspace` 存绝对路径，改名会断全部历史会话引用，收益配不上风险）。
- 不做存储配额与限额（治理向，超出「完整度」范围，若将来做另立提案）。
- LOCAL 不涉及：本机目录用户在文件系统里自理，桌面端 LOCAL 会话不显示该页签。

## 3. 与已否决 / 已排除方向的边界

| 方向 | 本提案为何不是它 |
|---|---|
| 工作区环境模板与快照（2026-10-11 否决） | 不解决「重复装环境」，不新增任何模板资产与共享面；只读现状 + 删除。 |
| 数据保留策略与可携带（2026-10-09 否决） | 无自动策略、无后台任务、无过期时间；删除永远由用户显式触发并双重确认。 |
| 实例备份与一键恢复（2026-10-09 否决） | 不动实例级数据，不做备份。 |
| 工作区文件直管（已实施，0.0.281） | 是它的外延：从「工作区内部」扩到「工作区之间」，同一套沙箱与确认范式。 |

## 4. 方案

### 4.1 后端（P1）

- 新端点 `GET /v1/sessions/workspace-overview`（不动既有 `cloud-projects`，新建任务下拉零回归）：
  - 目录枚举：`{userRoot}` 一级目录（经 `pathSandbox.getWorkspaceRoot()` 口径），逐目录判定 `isGit`；枚举全程走 `workspace-browse.service` 既有符号链接防御（不跟随出根）。
  - 大小统计：**异步按需计算 + 进程内缓存**（TTL + 手动刷新按钮），单目录并发限制与总耗时上限（如 5s 超时则返回部分结果并标注「统计未完成」），避免深目录阻塞请求——参照 `run-trace` 导出的超时降级范式。
  - 会话关联：`session.workspace LIKE '{dir}%'` 聚合出 `activeCount / archivedCount` 与 `lastUsedAt`（max `updated_at`），一次 SQL 分组完成，无 N+1。
- P2 删除端点 `DELETE /v1/sessions/workspace`（body 传目录相对路径）：
  - 前置校验：路径必须位于本人根目录一级、非当前任何 ACTIVE / 运行中会话的 `workspace`、非该用户正在使用的交互终端 cwd；命中则 409 并返回引用会话清单。
  - 删除动作复用 `workspace-write.service` 的沙箱解析与写锁协同（`withFiles` 同款），物理删除 + 审计留痕（复用 audit 拦截器既有面）。

### 4.2 desktop（P1 + P2）

- 「工作区」中央页签（`CenterTabBar` 新成员，Git 管理器同范式）：表格列 = 名称 / 类别（项目、Git 仓库、飞书 / 钉钉通道）/ 大小 / 关联会话（进行中 · 归档）/ 最近使用；行操作 = 打开（跳转新建任务并预填复用该目录）、刷新大小、删除（P2）。
- 新建任务的「复用已有工作区」下拉顺带升级为带大小与会话数的富条目（同一数据源，纯展示增量）。
- 删除交互：二次确认弹层列出引用的归档会话（提示「这些会话的文件浏览 / Git 面板将不再可用」）+ 输入目录名确认。

## 6. 风险与对策

| 风险 | 对策 |
|---|---|
| 大小统计拖慢接口 / 打爆磁盘 IO | 异步 + TTL 缓存 + 并发限制 + 超时降级；首屏允许「大小统计中」占位 |
| 删错目录（路径逃逸、误删他人 / 平台目录） | 一级目录白名单口径 + `pathSandbox` 复用 + 符号链接不跟随 + 输入名称确认；删除动作进审计 |
| 删除后归档会话「变空」引发困惑 | 确认弹层强制展示受影响会话清单；会话文件树对不存在的工作区给出「工作区已删除」空态（补一处兜底文案） |
| 通道工作区（feishu-chat 等）被误删导致机器人会话异常 | 类别标注 + 默认排序把「活跃会话 > 0」的目录置顶；删除校验同样覆盖通道目录的进行中会话 |
| 与新建任务下拉的既有体验回归 | 既有 `cloud-projects` 端点原样保留；新数据源只做展示增量，接口失败时回落纯目录名列表 |

## 7. 测试要点

1. overview：混合 projects / 通道目录 / 深目录 / 符号链接指向根外的目录，枚举不逃逸、大小不跟随链接出根。
2. 大小统计超时：构造超限目录，接口在上限内返回部分结果并标注未完成；二次请求命中缓存。
3. 会话关联聚合：同目录多会话（进行中 / 归档混合）计数正确；无会话目录计数为 0。
4. 删除校验：进行中会话引用 → 409 + 清单；仅归档引用 → 允许；路径越界 / 二级目录 → 拒绝。
5. 删除后：归档会话文件树空态文案；新建任务下拉不再出现该目录。
6. 回归：`cloud-projects` 响应结构与现状逐字段一致（新建任务下拉零变化）。

3. 删除是否需要管理员级开关（如实例设置「允许用户删除工作区」默认开）？还是与文件直管同权限口径不设开关？
