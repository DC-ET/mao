# 提案：待审批散在会话里 —— 全局审批收件箱与一次性审计

> 本地（LOCAL）模式下需要人工审批的工具调用，审批卡只出现在发起它的那个会话的中央页签里。用户开着好几个 LOCAL 任务时，系统托盘和会话树虽然能显示「有待审批」的红点（`treePendingApprovalCount`），但桌面端却没有一处「把我所有待审批都列出来一下点就批」的地方——人得逐个会话点进去找。收件箱里虽然写了 `APPROVAL_PENDING`，但点击跳转跳的仍是单个会话，没有也不可能跨会话批量决策；审批做完后，更没有一本「谁在什么时候批了哪条命令」的账本可查。

- 状态：**已否决，存档勿再评审**（2026-11-04 评审驳回）
- 日期：2026-11-04
- 提案总览见 [docs/proposals/README.md](README.md)
- 规模：小~中（桌面审批抽屉约 1.5 人日；后端只读接口 + 审计视图约 1.5 人日；零迁移）
- 关联：`desktop/src/composables/useChat.ts`（审批挂点）、`backend-ts/src/harness/local/local-tool-executor.ts`、`backend-ts/src/harness/approval/session-tree-signal-publisher.ts`、`backend-ts/src/inbox/inbox.service.ts`、`shared/contracts/src/inbox.ts`

### 1.2 真实痛点

1. **多任务并行时审批成为隐形瓶颈**：一个用户开了 5 个 LOCAL 任务，其中 3 个卡在等批。托盘红点告诉你「有待审批」，但点过去要一个个会话找——会话被中央页签折叠、被归档、或根本切到了安卓/浏览器端，审批卡就一直躺在那里。那个子代理在执行上下文里等 15 分钟（`localToolTimeoutSeconds = 900`）超时后带着失败回执回来，用户回来看到的是「任务失败了」——而真正的卡面其实已经超时自动处理过了，只是没人告诉用户。
2. **批了账目没有**：审批卡上只显示命令，不显示决策人和决策时间。出了「某用户在生产数据库上跑了 DROP」这类问题，管理后台的审计日志里找不到「谁点了批准」。这和「谁创建了这个工作区文件」「谁改了这个定时任务」这类场景是一致的证据要求——本地工具审批是唯一没有账目的高危动作。
3. **收件箱审批行的价值打了半折**：邮箱通知都会跳到会话，但用户想要的是「列出我所有待审批，一条条批掉」。当前只能跳单个会话，看不到队列。

## 2. 目标 / 非目标

**目标**

1. **桌面端全局审批收件箱（审批抽屉）**：新增一个只读审批列表视图（中央页签旁或右侧抽屉，与用法抽屉同层），聚合当前用户名下所有未决策的 `APPROVAL_PENDING`（会话标题 / 命令 / 工具名 / 等待时长 / 风险说明），点击单条跳回对应会话并聚焦到审批卡；支持逐条批/拒（复用既有 `confirmApproval` 语义，跳回原会话执行，**不在抽屉里二次执行命令**）。状态来源直接复用已推送的 `treePendingApprovalCount` 与收件箱未读数，不新起轮询。
2. **审批审计落账**：`tool_approval` 帧的决策人（userId）与决策（approve/reject）写入审计日志（复用既有 audit 基础设施，审计一条消息，不新增管理后台页面），管理后台现有审计日志可按会话/用户过滤即可查。
3. 超时自动拒绝的审批在收件箱或审批抽屉里显示为「已超时（自动拒绝）」，让用户能区分「没人理」和「系统替我拒了」——直接复用 `localToolTimeoutSeconds` 现有超时终态。

**非目标**

- **不在抽屉里执行审批动作**：点击跳转回原会话，走原来的审批卡路径。理由是审批卡的决策逻辑（审批规则、`needApproval`、工具结果回传）只在会话 WS 上下文里完整——抽屉里重做一遍就是给安全边界新开一扇门。
- 不做审批策略升级（不加「按命令类型自动批准」的新规则、不加审批分级）。
- 不做远程审批（飞书/钉钉卡片上直接点批准已定案为不做，见 2026-10-27 方案 D5）。
- 不改变审批超时时长、审批触发点和执行路径。

## 3. 与已否决 / 已排除方向的边界

| 方向 | 本提案为何不是它 |
|---|---|
| 审批规则 / 工作流引擎 | 不新增规则类型、不加策略决策点；只把既有规则执行结果的待审批项聚合展示。 |
| 远程审批（卡片上点批） | 点击跳转回原会话，没有新渠道的远程执行。 |
| 人工接管（Human Handoff） | 说的是「会话交接给另一个人」，本提案说的是「同一个人把手头所有待审批收口到一处」。 |

## 4. 方案设计

### 4.1 桌面审批抽屉

- **位置**：与任务抽屉/用量抽屉同层的右侧抽屉（`desktop/src/components/` 新建 `ApprovalInboxDrawer.vue`），入口放在顶栏通知铃铛旁，带未读角标（复用既有未读信号，不新起计数）。
- **数据**：新增只读端点 `GET /v1/approvals/pending`（复用收件箱 `APPROVAL_PENDING` 未读且未 resolve 的查询，不新起表），返回会话标题、命令预览、工具名、等待时长。**零迁移**。
- **交互**：每条一行，「去处理」跳回原会话并聚焦审批卡（`locateMessageId` 同口径）；已超时的标记「已超时」灰态，不可再处理。
- **零回归关键**：抽屉只读 + 跳转，审批的决策、执行、超时、树信号全部走既有通道。抽屉关掉后，原会话的审批卡行为与以前完全一致。

### 4.2 审批审计

- `tool_approval` 帧到达时补写审计日志：`userId`、`sessionId`、`requestId`、`decision`（approve/reject）、时间。写日志在既有 audit 服务的调用链上做，不新起表/新起端点。
- 超时自动拒绝同样写一条审计（decision = `TIMEOUT`），与用户决策区分开。

## 6. 风险与对策

| 风险 | 对策 |
|---|---|
| 审批列表与原会话状态的竞态（跳转后会话已自动超时） | 跳转后审批卡已是超时终态，显示「已超时」灰态即可；不单独处理 |
| 审计日志写入失败拖慢审批 | 审计写入 fire-and-forget（失败只记日志），不得阻塞 `handleToolApproval` 主链 |
| 抽屉入口与收件箱的功能重叠造成两个真相 | 抽屉与收件箱共用同一只读端点与 `APPROVAL_PENDING` 事实，跳转目标也一致；收件箱原有行行为不变 |

## 7. 测试要点

1. `GET /v1/approvals/pending`：只返回当前用户未 resolve 的审批、已 resolve 的不返回、多用户隔离。
2. 审计：批准/拒绝/超时各写一条；审计失败不阻塞审批主链。
3. 桌面：抽屉打开能聚合多会话待审批、点击跳转并聚焦审批卡；跳转后会话审批卡行为与无抽屉时逐项一致；已超时条目灰态且不可处理。
4. 回归：原会话的审批卡（已审批、超时、树信号、收件箱写入）行为与本次改动前一致。
