# 提案：模型容灾与故障转移（Model Fallback）—— 供应商挂了，任务不能死

- 状态：**已否决**（2026-10-09 评审：不做。本文仅存档，勿再评审）
- 日期：2026-10-09
- 提案总览：见 `docs/proposals/README.md`

## 1. 背景与现状

今天每一次 LLM 调用的容错只有一层：**单模型内重试**。`harness/llm/anthropic-llm-adapter.ts` 与 `openai-llm-adapter.ts` 对限流（429）、5xx、网络类错误按 `rateLimitMaxRetries` 指数退避重试，参数/鉴权/余额类错误直接判终态。重试耗尽即抛错，**整轮执行失败**，任务以失败态收尾。

`llm-adapter-facade.ts` 里虽有一个 `fallback` 字段，但那是**协议适配器的兜底选择**（按 protocol code 找不到 delegate 时返回默认适配器），与"模型挂了换一个模型"完全无关。

这意味着自托管实例的可用性被单一供应商绑定：

1. **供应商区域性故障**（502/503 持续数分钟）→ 期间所有新任务必败，重试只是把失败推迟几分钟。
2. **额度耗尽 / 账号被限** → 余额类错误判终态不重试，任务当场死亡；月底撞额度时尤其致命。
3. **模型下线或改名** → 该模型上所有 Agent 集体失能，只能管理员手工改配置。
4. **次级调用无人兜底**：标题生成（`session-title.service.ts`）、压缩摘要（`compaction-config` 指定的压缩模型）、飞书溢出摘要同样只有单模型，主模型活着也可能因为这些小调用失败而丢功能。

已上线的预算管控（`2026-10-06-usage-cost-budget.md`）管的是**钱**（超额提醒/拦截），不管**可用性**；已否决的出网边界（`2026-10-09-egress-data-boundary.md`）管的是**网络策略**。三者互不重叠，本提案补的是第三维：**故障时任务继续跑完的能力**。

对"把 Agent 放进自己环境干活"的产品定位，这是从"演示可用"到"生产敢用"的关键一环：用户可以接受慢，不能接受供应商打喷嚏自己任务就死。

## 2. 目标 / 非目标

**目标**

1. **故障转移链**：模型可配置备用链（全局默认 + 按 Agent 覆盖），主模型出现可转移故障（重试耗尽、超时、余额/额度类终态、5xx 持续）时自动切到下一个可用模型，本轮任务继续跑完。
2. **健康感知**：按"供应商+模型"维度记录近期失败率，连续失败进入冷却（熔断），冷却期内直接跳过，避免每次调用都去撞一遍已知故障的端点。
3. **次级调用同链路**：标题生成、压缩摘要、溢出摘要等非主对话调用纳入同一容灾逻辑（可配更省的备用，如主模型是旗舰、备用给轻量模型仅用于标题）。
4. **可观测**：每次转移在 `llm_call` 留痕（`fallback_from` / `fallback_reason`），运行轨迹与调用流水可见；发生转移时按需通知（收件箱），不让用户事后才发现"刚才其实是另一个模型答的"。
5. **成本护栏**：转移不绕过预算闸门（预算检查在转移后的模型上继续生效）；可配置"仅当备用模型价格不高于主模型时才允许自动转移"的保守档，防止容灾变成烧钱。

**非目标**

- 不做多模型并行竞速（race）取最快返回——那更像 Evals/评测基础设施，且成本翻倍，已否决方向不重启。
- 不做语义路由（按 prompt 内容智能选模型）——P1 只做故障驱动，不做负载/成本驱动的主动选路（列入开放问题）。
- 不改各供应商适配器内部重试策略；不做跨实例（多台服务器）的供应商健康共享。
- 不做"模型质量降级检测"（切到弱模型后答坏了怎么办）——只保证"跑完"，不保证"答好"，质量评估属已否决的 Evals 范畴。

## 3. 技术方案

### 3.1 故障分类与转移判定

- 在 `harness/llm/` 定义统一的 `TransferableFailure` 判定：可重试错误耗尽（已有 `retryable` 口径）、`http_status` 502/503/504 持续、超时（`httpCallTimeoutSeconds`）、以及明确的额度类终态（insufficient_quota / 403 rate-limit-exceeded 等供应商错误码白名单）。
- 参数错误、上下文超长、内容审核拒绝**不转移**——换模型同样会失败，转移只会掩盖真实问题（上下文超长应走压缩，见 `compaction-service`）。

### 3.2 模型解析与健康状态

- 模型解析当前在 `agent-executor.ts` / `model.service.ts` 一线完成。新增 `model-health` 模块（挂 `model` 域或 `harness/llm/`）：内存态健康表（`provider+model` → 连续失败数、冷却截止时间、最近转移时间），启动时为空、运行期累积；进程内生效即可，不落库（重启即重置是可接受的简化，列入开放问题）。
- 熔断策略：连续 N 次可转移失败（默认 3）→ 冷却 M 分钟（默认 5）；冷却内该模型对**新调用**直接跳过，已在进行的流不打断。
- 备用链解析顺序：Agent 级覆盖（`agent.fallback_model_ids`，新列或 JSON 配置）→ 全局默认链（settings）→ 无则失败（保持现状，不偷偷换模型）。

### 3.3 执行链路接入

- 接入点选在 agent-loop 单轮 LLM 调用外层（`agent-loop.ts` 取模型之后、调用之前包一层 `executeWithFallback`）：主模型失败且判定可转移 → 按链取下一个健康模型 → 以相同 messages 重放请求（流式已产出的部分输出作废，向用户发一次"模型切换"事件，桌面端在轨迹/消息区可见）。
- 次级调用（标题/压缩/溢出）复用同一 `executeWithFallback`，但链可配为独立的一条（如压缩模型故障时回退到主模型，而不是旗舰互备）。
- 转移后的调用正常记 `llm_call`（`model_id` 为实际模型），新增 `fallback_from_model_id` 与 `fallback_reason` 两列（V142），管理后台调用流水可筛选"发生过转移的调用"。

### 3.4 前端与管理后台

- 桌面端：发生转移时当前轮内插一条系统提示样式的事件条（"主模型 X 不可用，已切换至 Y"），轨迹面板对应轮次打"转移"徽标（与既有压缩/预算/审批徽标并列）。
- 管理后台：模型管理页每个模型显示健康状态徽标（正常/冷却中）与"今日转移次数"；设置页配全局默认备用链。

## 4. 分阶段实施

| 阶段 | 内容 | 规模 |
|---|---|---|
| P1 | 故障分类 + 进程内健康表与熔断 + 主对话调用链接入 + `llm_call` 转移字段 | 中 |
| P2 | Agent 级/全局备用链配置（后台 UI + settings）+ 桌面端转移事件条与轨迹徽标 | 小~中 |
| P3 | 次级调用纳入 + 转移通知（收件箱）+ 健康状态落库与重启恢复（按需） | 小 |

## 5. 风险与开放问题

- **静默降质**：用户不知道回答已换模型。缓解：转移必留痕（调用流水 + 轨迹 + 事件条），并在 P2 提供"转移时通知我"开关，不默认全局静默。
- **备用模型上下文窗口更小**：切过去后同一 prompt 可能超窗。缓解：链配置时展示各模型窗口，转移前做一次窗口预检，不满足则跳过该备用继续找下一个；仍无可用才失败。
- **连锁故障**：主用同一供应商的多个模型（如 OpenAI 全线故障）时整条链同死。缓解：文档建议链跨供应商；工具层面在配置 UI 对"同供应商占多数"的链给警告，不强制。
- **开放问题**：健康状态是否落库（重启后冷却丢失 vs 多实例部署时各进程状态不一致——当前单后端部署下进程内态够用，多实例需 Redis 类共享，P1 不做）。
- **开放问题**：是否允许"成本驱动的主动降级"（闲时用便宜模型）——与预算提案的关系需评审界定，P1 严格限定为故障驱动。

## 6. 测试要点

- 可转移故障（429 耗尽、502 持续、超时、insufficient_quota）触发切换，下一模型以相同 messages 续跑，任务终态为成功。
- 不可转移故障（参数错误、上下文超长）不切换，错误原样上报。
- 熔断：连续失败进入冷却后，冷却内新调用不再触达故障模型；冷却结束恢复尝试。
- 窗口预检：备用模型窗口小于当前 prompt 时被跳过；全链不可用时任务失败且原因可读。
- 转移记录：`llm_call.fallback_from_model_id` / `fallback_reason` 正确；调用流水筛选"发生转移"可命中；轨迹轮次有徽标。
- 预算仍生效：转移后调用计入对应模型成本并受预算闸门约束；配置"备用不高于主模型价格"时贵备用被跳过。
