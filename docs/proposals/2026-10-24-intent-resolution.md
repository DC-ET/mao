# 提案：模糊指令解析（Intent Resolution）—— 先对齐业务语义，再决定查什么、问什么

> 模糊指令不该靠猜：先解析出业务语义，再决定是执行、按默认执行，还是只问一个关键问题。
>
> 「团队」仍然指同一个 Agent 的所有使用者：解析规则与默认值一次校准，所有人下次都受益。

- 状态：已否决（2026-10-24），存档勿再评审
- 日期：2026-10-24
- 提案总览：见 [docs/proposals/README.md](README.md)
- 规模：中（运行时解析层 + 澄清策略 + 解析日志；不改执行引擎）
- 关联：[业务词典](2026-10-24-business-glossary.md)、`HarnessService.buildContext`、`ask_user_questions`、`term_resolution_log`

## 1. 背景与现状

### 1.1 同一个词，在这句话里到底指什么

有了[业务词典](2026-10-24-business-glossary.md)还不够。词典告诉 Agent「推单可能有两种含义」，但用户说的是：

- 「这批 W 单**推单**了吗」——这是**查推单状态**，不是执行写操作；
- 「**推单**一下这几个 W 单」——这是**执行提前推单**，是写操作，必须先预检、确认；
- 「**佣金**多少」——可能是经销商佣金计算、推广佣金流水、代理服务费、虚拟币收益，缺用户/订单/SPU，必须先问；
- 「看下这个月**出货额**」——这是 `pmt_gmv` 还是 `act_pmt_gmv`？含税还是不含税？按渠道还是按客户？

今天 Agent 要么直接猜一个含义去调命令，要么问一串问题让用户烦。两种都不可接受：猜错会查错表/触发写操作，问太多会让用户回到「自己写 SQL/自己点页面」。

### 1.2 现有链路的缺口

- `PromptEngine` 只负责把系统提示、经验、技能文档拼起来；没有「这句话里的业务词指什么」这一步。
- `ask_user_questions` 工具很强（1-4 个问题、2-4 个选项、支持多选/自定义），但**什么时候该问、问哪个槽位**全靠模型临场判断。
- 技能文档里有大量「需要 X 用命令 A，需要 Y 用命令 B」的说明，但模型要读完才可能选对；文档本身也承认「同义问题落到不同表」的坑。
- 没有任何地方记录「这次把‘出货额’理解成了什么、用户后来纠正了没有」，所以无法越用越准。

### 1.3 为什么现在做

- 业务技能已经齐全，瓶颈在「选对技能里的哪条命令、哪个口径」；解析层是投入产出比最高的一层。
- 团队输入高度口语化、黑话化，靠模型通用常识无法稳定对齐；必须把「解析」从模型自由发挥变成可配置、可观测的步骤。
- 解析日志是[术语学习](2026-10-24-term-learning.md)的原料；没有解析，就没有「越用越懂」的数据。

## 2. 目标 / 非目标

**目标**

1. 在每次执行前，对最新用户消息做一次**业务语义解析**：命中哪些术语、每个术语采用哪种含义、哪些槽位已有/缺失/可默认。
2. 输出一张紧凑的 `<business-resolution>` 卡，明确告诉模型：采用什么口径、数据源是什么、读还是写、缺什么、下一步该执行还是该问。
3. **最小澄清**：只在「歧义会改变结果」时提问，最多 1 个问题；能默认的就默认，并在回答首行写明假设。
4. **写操作前置确认**：`mode=WRITE` 的术语（如提前推单）必须先确认订单范围与执行意图，不能因为用户说了「推单」就直接执行。
5. 全通道生效：桌面 / Web / 飞书 / 钉钉 / 微信 / 定时任务 / 开放接口都在服务端装配上下文，解析一致。
6. 解析结果落 `term_resolution_log`，供学习与复盘；不存用户原文。

**非目标**

- 不做执行前计划门 / 审批门（计划模式 2026-10-09 已否决）：解析层只补充语义，不拦截执行；写操作仍走既有工具审批与权限。
- 不做结构化回复卡片：假设说明就是普通文本首行，不新增消息块协议。
- 不做人工接管 / 转人工（2026-10-11 已否决）。
- P1 不额外调用 LLM：用词典 + 规则 + 上下文打分；P2 只对规则无法判定的少数消息做 LLM 兜底。
- 不做完整 NLU / 意图分类体系：只解析「词典里有的业务术语」；通用意图仍交给模型。
- 不改工具执行、权限、沙箱、审批语义。

## 3. 与已否决方向的边界

| 方向 | 本提案为何不是它 |
|---|---|
| 计划模式 / 执行前计划门（2026-10-09 否决） | 不生成计划、不要求用户批准计划；只解析「这句话里的业务词指什么」，执行仍由模型继续 |
| 渠道人工接管（2026-10-11 否决） | 不换人、不引入 `WAITING_HUMAN`；澄清仍由原 Agent 在原会话完成 |
| 结构化回复卡片（2026-10-19 否决） | 不新增消息块、不改渲染器；「按…口径理解」是普通文本 |
| 模型对照 / Evals（已否决） | 不做多模型并排、不做离线评分；只记录生产解析与澄清结果 |
| 团队知识层（2026-10-19 否决） | 不共享自由文本记忆；解析只读结构化词典，日志只存术语/槽位/决策 |
| 业务词典（本批提案一） | 词典负责「词可能是什么意思」；本提案负责「这句话里选哪个、缺什么、问不问」 |

## 4. 技术方案

### 4.1 解析流程

`BusinessIntentResolver.resolve(context, latestUserMessage)` 在 `HarnessService.buildContext` 装载完历史后运行：

```
最新用户消息
  → 术语检测（词典别名索引）
  → 含义打分（意图动词 + 实体 + 会话/角色上下文 + 优先级）
  → 槽位抽取（时间 / 实体 / 维度 / 税基 / 读写）
  → 决策（RESOLVED / AMBIGUOUS / MISSING_SLOT / WRITE_CONFIRM / NO_MATCH）
  → 注入 <business-resolution> 卡（ephemeral，不落库）
  → 写 term_resolution_log
```

若业务词典 P1 的消息侧注入已上线，本解析器**接管注入**：只保留 `<business-resolution>`，不再重复注入 `<business-terms>`；两者不要同时出现。

**旁路调用跳过**：压缩、标题生成、记忆抽取、经验起草等非用户执行的 `buildContext`（如 `forCompaction=true`）不解析、不注入、不写日志；只处理真实用户消息触发的主执行与边路任务。

**含义打分（P1，可解释规则）**

| 信号 | 例子 | 作用 |
|---|---|---|
| 意图动词 | 查/看/统计/多少/明细 → READ；推/执行/提交/帮我推 → WRITE | 强信号 |
| 实体 | `W` 单号、`spuId`/`skuId`、`idCode`、品牌名、订单号 | 决定槽位与含义 |
| 时间表达 | 本月/上月/本周/近 7 天/2026-09/Q3 | 填 `timeRange` |
| 维度表达 | 按渠道/按客户/按品牌/按天 | 填 `dimension` |
| 税基 | 含税/不含税/未税 | 填 `tax` |
| 上下文 | Agent 绑定、渠道、用户角色、当前 `projectKey`、本会话已解析过的术语 | 打破平局 |
| 词典优先级 | `business_term_meaning.priority` | 最后兜底 |

**裸术语规则**：用户只说了术语、没有动词时（「推单」「佣金」「出货额」），默认选 `READ` 含义；只有明确出现「执行 / 帮我推 / 提交 / 跑一下」这类写意图，才允许选 `WRITE`。如果该术语只有 `WRITE` 含义，走 `WRITE_CONFIRM` 并先问，不能默认执行。

打分结果与依据写进解析日志；UI/日志能回答「为什么选了这条含义」。

**槽位抽取（P1）**

- 时间：正则覆盖本月/上月/本周/上周/今天/昨天/近 N 天/`YYYY-MM`/`YYYY-MM-DD`/Q1-Q4；解析成 `{kind, start, end}`。
- 实体：`W\d+` 订单号、`spuId/skuId` 键值、纯数字 idCode（需结合术语配置）、品牌名（词典别名）。
- 维度/税基：关键词表，可由术语的 `clarify_options` 扩展。
- 缺失判断：`required_slots` 逐项检查；有 `defaults` 的槽位算「可默认」，不算缺失。

### 4.2 决策与卡片

| 决策 | 条件 | 卡片要求 | 模型行为 |
|---|---|---|---|
| `RESOLVED` | 单一含义得分显著领先，且必填槽位齐全/可默认 | 采用含义 + 口径 + 默认值 + 数据源 | 直接执行；回答首行写明假设 |
| `AMBIGUOUS` | 前两名分差小于阈值，或同一消息命中多个术语且互相冲突 | 候选含义 + 各自差异 + 建议选项 | 最多问 1 个问题（用 `ask_user_questions`） |
| `MISSING_SLOT` | 单一含义，但关键槽位无值且无默认（如佣金缺用户/订单） | 缺失槽位 + 候选选项 | 最多问 1 个问题 |
| `WRITE_CONFIRM` | 含义 `mode=WRITE` | 写操作警告 + 必填订单范围 + 预检建议 | 先预检/确认，未确认不得执行 |
| `NO_MATCH` | 未命中任何术语 | 零注入 | 按现有行为 |

卡片示例（`RESOLVED`）：

```
<business-resolution>
业务语义解析：
- 术语：出货额
- 采用含义：支付金额口径（pmt_gmv）
- 口径：含税、本月、按渠道（默认，用户未指定维度）
- 数据源：bigdata-cli，表 access_cdm.dmd_index_managerial_report_goods_dd_f
- 缺失槽位：无
回答要求：首行写明「按出货额（pmt_gmv）· 本月 · 按渠道理解」；若用户随后纠正口径，按新口径重查。
</business-resolution>
```

卡片示例（`WRITE_CONFIRM`）：

```
<business-resolution>
业务语义解析：
- 术语：推单
- 采用含义：执行提前推单（WRITE，ascm-cli push early-push）
- 必填：orderNos（W 单号列表）+ 明确执行确认
- 当前缺失：orderNos
- 风险：写操作，涉及货权转移；拦截/风控/冻结订单不可推
回答要求：先向用户确认订单范围与「先预检 / 确认执行」；未得到明确确认前，不得调用执行命令。
</business-resolution>
```

卡片上限 1.5KB；多条术语按「写操作 > 缺失槽位 > 只读」排序，超出截断并提示用 `business_term_lookup`。

### 4.3 澄清策略

- **最多 1 个问题**（P1）；P2 允许在「多术语互相冲突」时最多 2 个，但需要配置开关。
- 只问「会改变结果」的槽位：例如「出货额」缺维度可以先按渠道默认；「佣金」缺用户/订单必须问。
- 问法使用 `ask_user_questions` 的结构化选项（2-4 个，推荐项放首位），并带 `metadata.termResolutionId`，便于[术语学习](2026-10-24-term-learning.md)把答案配对回解析记录。
- 回答首行必须写假设；如果用户没纠正，视为弱接受；如果用户纠正，进入学习候选。
- 写操作：即使槽位齐全，也要一次显式确认；确认文案要包含「写操作 / 影响范围 / 是否先预检」。

### 4.4 解析日志

```sql
CREATE TABLE `term_resolution_log` (
  `id`            BIGINT PRIMARY KEY AUTO_INCREMENT,
  `session_id`    BIGINT NOT NULL,
  `message_id`    BIGINT NULL COMMENT '最新用户消息 id',
  `user_id`       BIGINT NULL,
  `agent_id`      BIGINT NULL,
  `detected_json` JSON NOT NULL COMMENT '命中的术语/别名/候选含义与得分',
  `chosen_json`   JSON NULL COMMENT '采用的含义、槽位、默认值',
  `missing_json`  JSON NULL,
  `decision`      VARCHAR(16) NOT NULL COMMENT 'RESOLVED/AMBIGUOUS/MISSING_SLOT/WRITE_CONFIRM/NO_MATCH',
  `card_bytes`    INT NULL,
  `created_at`    DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  KEY `idx_resolution_session` (`session_id`, `created_at`),
  KEY `idx_resolution_agent` (`agent_id`, `created_at`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='业务语义解析日志';
```

只存术语 id、槽位、决策、得分与卡片大小；不存用户原文、不存工具结果。`NO_MATCH` 也记一行（用于发现「团队说了但词典没收的词」），但不带原文。

`message_id` 取 `HistorySnapshot` 里最后一条真实 USER 消息的 id；取不到时置 NULL，不影响解析，只是后续学习少一个配对锚点。

### 4.5 前端与用户感知

- **回答首行假设**：例如「按出货额（pmt_gmv）· 本月 · 按渠道理解」，用户一眼能看出 Agent 的理解，纠正成本最低。
- **澄清卡**：复用 `ask_user_questions` 的既有 UI（桌面 / 飞书卡片 / 微信文本），不新增组件。
- **管理后台（P2）**：业务词典页增加「解析日志」Tab，看最近命中、决策分布、高频缺失槽位；可按 Agent/术语筛选。
- **不新增消息块**：假设说明、澄清问题都是普通文本/既有工具卡。

### 4.6 通道与执行模式

- 解析在服务端 `buildContext`，对桌面、Web、飞书、钉钉、微信、定时任务、开放接口一致生效。
- LOCAL 会话也先解析；`ask_user_questions` 走桌面端既有能力；工具执行仍在本地，解析不触碰本地文件。
- 子代理：P1 跳过（父会话已解析并会把任务描述传给子代理）；P2 评估子代理任务描述里的术语。

## 6. 风险与开放问题

| 问题 | 风险 | 推荐默认 |
|---|---|---|
| 误命中（别名太宽） | 中 | 低置信度直接 `NO_MATCH`，不注入；保留「命中但不确定」日志供调参 |
| 过度澄清 | 中 | 最多 1 问；只问影响结果的槽位；能默认就默认并写明假设 |
| 默认值错 | 中 | 首行明示假设；用户纠正进入学习候选；默认值有版本 |
| 写操作误执行 | 高 | `WRITE_CONFIRM` + 必填订单范围 + 既有审批/权限；未确认不得执行 |
| 模型忽略卡片 | 中 | 卡片带硬性「回答要求」；P2 对高风险写操作做服务端强制门 |
| 卡片膨胀 | 中 | 1.5KB / 5 术语上限；超出只给摘要 + lookup |
| 规则覆盖不足 | 中 | P1 先覆盖高频词；P2 LLM 兜底只对低置信度消息，限制频率与成本 |
| 角色/渠道差异 | 中 | P1 不按角色区分；P3 再做角色/渠道默认值，避免早期误判 |
| 解析日志隐私 | 低 | 只存术语/槽位/决策，不存原文与结果 |

**待确认决策**

1. 默认值缺失时，是「按默认执行并写明」还是「先问」？建议按术语配置：`ALWAYS / IF_MISSING / NEVER`，默认 `IF_MISSING`。
2. 写操作确认门放 P1 还是 P2？建议 P1 先靠卡片 + 提示词，P2 再做服务端强制门（避免 P1 改动执行链路）。
3. 是否允许一条消息解析出多个术语？建议允许，但最多 3 个；互相冲突时只问 1 个。
4. LLM 兜底用哪个模型？建议复用默认模型、低采样、只对 `AMBIGUOUS` 且规则分差极小的消息；单独用量场景。
5. 首行假设是否所有回答都强制？建议只在「使用了默认值」时强制；明确指定口径的回答不重复。

## 7. 测试要点

- 检测/打分：`推单` + 「查/看/了吗」→ READ；`推单` + 「帮我/执行/提交」→ WRITE；`佣金` + 「流水/明细」→ revenue money；`佣金` + 「算/多少」→ finance calculate。
- 槽位：本月/上周/近 7 天/`2026-09`/Q3；`W` 单、`spuId`、`idCode`；按渠道/客户/品牌；含税/不含税。
- 决策：RESOLVED / AMBIGUOUS / MISSING_SLOT / WRITE_CONFIRM / NO_MATCH 五类各一组；阈值边界；多术语排序与截断。
- 注入：卡片字节上限；无命中零注入；不落库；不改写历史消息；模态消息只取可见文本。
- 澄清：`ask_user_questions` 的 metadata 带 resolutionId；答案配对正确；最多 1 问；选项 2-4 个。
- 写操作：未确认不执行；确认文案包含写操作与范围；既有工具审批仍然生效。
- 日志：五类决策各落一行；不存原文；重复执行幂等；按 Agent/术语查询正确。
- 回归：无术语消息的上下文与改动前一致；系统提示词字节不变；不同通道解析行为一致。

## 8. 验收标准与观察指标

**验收**

1. 「这批 W 单推单了吗」→ 解析为「查推单状态」，不触发写操作；回答先给状态，不出现执行命令。
2. 「推单一下这几个 W 单」→ `WRITE_CONFIRM`，先要求确认订单范围与「先预检/确认执行」；未确认前没有执行调用。
3. 「佣金多少」→ `MISSING_SLOT`，只问 1 个问题（用户/订单/SPU），选项来自词典；用户回答后继续。
4. 「看下这个月出货额」→ `RESOLVED`，采用 `pmt_gmv` + 本月；回答首行写明口径；若用户说「要实际成交额」，下一次切到 `act_pmt_gmv` 并记录纠正。
5. 无业务术语的消息，注入字节为 0，行为与改动前一致。

**指标（上线后 8 周）**

- 含业务术语消息的澄清次数 / 首次回答接受率 / 用户纠正率；
- 写操作误触发次数（应为 0）与确认后取消率；
- 从用户发消息到第一条工具调用的平均步数（对照 `bigdata-cli` 记录的探索步数）；
- 解析日志中 `AMBIGUOUS` / `MISSING_SLOT` 的占比与高频槽位（用于补词典/默认值）。
