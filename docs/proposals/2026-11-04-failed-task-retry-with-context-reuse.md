# 提案：失败任务重跑 —— 带上下文的重试与失败归因

> 任务跑失败之后，用户最常见的三个诉求依次是：① 「别重跑全文，能不能接着失败的那一轮往下走」；② 「到底错在哪，帮我指出来」；③ 「用别的方式（换个模型、换个 Agent）再跑一遍」。现状是模型/工具的瞬时错误早就自己重试了，但整轮失败后，用户只能从头复述一遍目标让 Agent 重新规划——算好上下文、记好文件变更、把子代理做了一半的工作再捡回来。今天我们既有任务、轮次、工具调用的完整运行轨迹（Run Trace），又有 `dump_user_messages`（按轮次导出用户消息）的现成能力可以给上下文锚点——独缺的是「失败后一步重试的入口」。

## 1. 背景与现状

### 1.1 已有积木全在，唯独缺「失败后一步」的操作入口（代码可查）

| 能力 | 现状 | 代码证据 |
|---|---|---|
| 轮次内工具重试 | ✅ 模型/工具的瞬时错误已有重试，但「整轮失败」的入口只有 `ExecutionErrorBanner` 里的重试按钮——那是轮内重试的续跑，不是用户主动发起的整任务重跑 | `ExecutionErrorBanner.vue`（`retry` 事件） |
| 运行轨迹 | ✅ 按轮次有模型耗时、首字延迟、成本、工具调用的完整轨迹（Run Trace），可定位失败发生的 tool_call | `run-trace-record.service.ts`、`run-trace.service.ts` |
| 上下文锚点 | ✅ `dump_user_messages` 可按轮次取用户消息——适合作为「从失败轮重跑」的上下文种子 | `dump-user-messages-tool.ts` + 导出服务 |
| 文件变更记录 | ✅ 每轮写入 `file_change`，子代理交付时还有按次复制去重的 `fileChangeCopyKey` 机制 | `file-change-copy.ts`、`V037__add_message_file_change.sql` |
| 失败通知 | ✅ `TASK_FAILED` 收件箱 + 任务完成/失败的外推都在，失败后用户会收到提醒，但点进去之后长什么样、错在哪、怎么处理——UI 不给结论 | `inbox.service.ts:95-100`、`digest/repository.ts:127` |
| 失败重试 | ❌ 轮次级工具重试只有瞬时错误在跑；整轮/整任务失败后，用户要从头复述 | — |

### 1.2 真实痛点

1. **失败后用户面对的是一句「执行错误」和一个「重试」按钮**：用户不知道是模型连接超时、工具被审批超时、还是 Agent 逻辑自己决定了「做不了」。Run Trace 有全量信息，但用户得钻进去一个个轮次看。
2. **用户复述的目标和失败轮次的上下文脱钩**：模型已经从头开始又成了一次「全新对话」——之前读的文件、做过的子代理任务、搭了一半的环境，全部丢了。用户复述的时候只能复述目标文字，不能把上轮的上下文带过去。
3. **换了模型/换了 Agent 之后能不能接着跑**：用户已经能通过「会话内切换 Agent / 模型」把配置改了，但改完之后要重新触发一轮才有上下文，失败轮次的锚点不带过去。

## 2. 目标 / 非目标

**目标**

1. **失败归因卡（失败摘要视图）**：任务失败后，在错误横幅上给出一行式归因摘要——「失败于第 N 轮 · 工具 `shell` 超时（900s）」/「模型连接失败」/「审批超时被拒」/「Agent 判定无法执行」，由 Run Trace 的最后失败 tool_call 派生。点击展开看最后 3 条工具调用与那一轮的模型回复。
2. **「从失败轮重跑」**：在归因卡上给「从失败轮重跑」按钮。实现方式是：以失败轮次的最后一条用户消息为锚点，本会话新建一条消息「基于上一轮上下文继续」，仅把失败轮次之后的执行原样再跑一轮（不重述目标、不重起会话）。

**非目标**

- 不做任务循环的全局重试引擎（瞬时错误的整轮重试已经在跑，本提案只加用户主动的一步）。
- 不做任务自动归因的 LLm 推理层（如分析「Agent 为什么逻辑失败」）——只从既有事实字段派生。
- 不碰任务终端相位收敛逻辑（`task-terminal.service.ts` 的 `COMPLETED/FAILED` 写入逐字节不变）。

## 4. 方案设计

### 4.1 失败归因卡

- **位置**：任务列表失败任务的右侧标记 / 桌面任务收件箱里的失败行，点开后在现有 Run Trace 面板里按轮次展示失败工具调用摘要。
- **判定规则**（只读派生，不调 LLM）：
  - 最后失败 tool_call 工具名 + 失败原因（超时/拒绝/异常）→ 「第 N 轮 · `{tool}` {reason}」。
  - 模型调用失败（连接错误、限流）→ 「第 N 轮 · 模型调用失败」。
  - 审批超时 → 「第 N 轮 · 本地工具审批超时被拒」。
- **渲染**：归因卡上只放一句摘要 + 「展开」；展开内容（失败 tool_call 的参数、那一轮的模型回复、耗时）直接透出 Run Trace 既有面板，不新起布局。

### 4.2 从失败轮重跑

- **入口**：归因卡上的「从失败轮重跑」按钮，二次确认「将基于上一轮上下文继续执行（不重述目标）」。
- **上下文锚点**：以失败轮次的最后一条用户消息为种子（复用 `dump_user_messages` 的按轮次导出能力取锚点），本会话追加一条新消息作为续跑的起点，从该轮的下一轮开始执行。
- **叠加在现有会话上**：不新建会话、不重置 `AgentLoop` 状态；上下文压缩、记忆注入、子代理挂载全部走既有通道。
- **共用前置守卫**：重跑前复用 `messageQueueService` 忙检测与 `withSessionLock` 会话串行锁（同定时任务 `runNow` 手法），会话正忙时给明确提示，**不自动排队**。

## 6. 风险与对策

| 风险 | 对策 |
|---|---|
| 重跑与刚好到点的新任务撞车（`messageQueueService` 已有忙检测但非强一致） | 复用 `withSessionLock` + 忙检测；撞车时返回明确错误「会话正在忙」，不排队不叠加 |
| 用户要点「从失败轮重跑」但那一轮的上下文已被压缩/归档 | 归因卡上标注「上下文已被压缩（重跑将基于压缩后的上下文）」；有压缩记录时退化到仅带锚点重跑，不静默丢弃上下文 |
| 子代理已产出的文件变更在重跑时重复写入 | 重跑不回放子代理交付内容；`fileChangeCopyKey` 去重逻辑不依赖本提案，仍按既有子代理交付通道去重 |

## 7. 测试要点

1. 失败归因：超时/拒绝/模型失败/审批超时各派生一句正确的摘要；Run Trace 展开内容与归因卡一致。
2. 从失败轮重跑：续跑只记失败轮之后的新轮次；锚点是失败轮最后一条用户消息；会话正忙时返回明确错误。
3. 压缩后回退：失败轮上下文已压缩时归因卡提示并带锚点续跑。
4. 回归：瞬时错误轮内重试、失败收敛写入 `TASK_FAILED` 收件箱、原「重试」按钮——行为与本次改动前一致。

## 8. 待确认决策

1. 归因卡要不要在任务列表直接露一句摘要，还是只在点开失败任务后展示（上下文密度取舍）——建议点开后展示，列表只保留失败标记。
2. 「从失败轮重跑」的锚点范围：默认是失败轮最后一条用户消息；是否允许用户在确认弹窗里改种子消息文本（给「换个说法再试」的机会）——建议允许。
