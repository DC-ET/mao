# 提案：跨会话全文检索（Global Search）—— 那个答案 Agent 上周明明说过

- 状态：待评审
- 日期：2026-10-09
- 提案总览：见 `docs/proposals/README.md`

## 1. 背景与现状

今天唯一的会话搜索在 `session/session.repository.ts:609`（`selectMessagesForSearch`），三个硬限制：

1. **只搜用户消息**：SQL 里 `m.role = 'USER'` 写死——Agent 的回答、工具执行结果、文件内容一概搜不到。而"上周那个报错 Agent 给过修复方案"恰恰是最常见的检索需求，答案全在 ASSISTANT 消息里。
2. **LIKE 全表扫**：`content LIKE CONCAT('%', ?, '%')`，每会话最多取 5 条命中，长会话/大库下延迟随数据量线性恶化；中文无分词，多词命中靠连续子串，搜"部署 脚本"这种自然语言基本失灵。
3. **无筛选无跳转**：结果只有会话标题 + 片段，不能按 Agent / 时间 / 会话类型过滤，点了只能落到会话开头，无法定位到命中消息所在位置。

与此同时数据量在稳定累积：长期记忆沉淀的是偏好与事实，中间过程、命令输出、报错栈、代码片段全在会话里；会话分享/导出解决的是"把结果带出去"，检索解决的是"把过去找回来"，互补但今天后者缺失。

与已否决的知识库/RAG（`2026-10-05-knowledge-rag.md`）边界必须划清：那是把外部文档灌进来做语义问答，本提案是**搜用户自己会话里的原文**，不引入 embedding 设施、不做语义相似、不建新知识库——就是 MySQL 全文索引 + 现有数据的快速定位。

## 2. 目标 / 非目标

**目标**

1. **全文覆盖**：可检索 USER + ASSISTANT 消息正文（工具结果摘要与 thinking 内容按隐私/噪声评估后决定是否纳入，默认不纳入 tool result 原文，P1 先覆盖两类对话消息）。
2. **中文可用**：MySQL 8 原生 `FULLTEXT ... WITH PARSER ngram`（中文分词）替代 LIKE 全表扫；短词（≥2 字符）走全文，单字符/符号回退 LIKE 兜底。
3. **结果可定位**：命中消息片段 + 高亮关键词，点击**跳转到会话中该消息位置**并短暂高亮（复用现有消息定位/滚动机制），而不是落到会话顶部。
4. **可筛选**：按 Agent、时间范围、会话类型（主会话/边路/子代理）过滤；结果按相关度 + 时间排序，分页。
5. **隐私边界**：严格限定"自己的会话"（现有搜索即按 userId 过滤），管理员的消息 compact（`admin-message-compact.ts`）脱敏后的内容同样只对归属用户可见；分享出去的只读快照不纳入搜索池。

**非目标**

- 不做语义/向量检索（RAG 方向已否决，不重启；如需语义搜索是另一个量级的工程）。
- 不搜工作区文件内容（那是 IDE/grep 的领域；工作区内搜索已有 `workspace-search`，本提案只管会话消息）。
- 不做跨用户搜索（团队知识检索涉及权限模型扩展，超出本提案）。
- 不改造消息表存储结构（不加 ES，不进消息队列表外存）。

## 3. 技术方案

### 3.1 索引与查询（V142/V143）

- 迁移：`message` 表建 `FULLTEXT INDEX ft_message_content (content) WITH PARSER ngram`（MySQL 8.0+；ngram_token_size 默认 2，覆盖中文常用词；英文与数字天然支持）。历史行由建索引时一次构建，新写入行 InnoDB 自动维护。
- 兼容评估点：若运行环境 MySQL 版本/配置不支持 ngram（如 MariaDB），降级路径为维持 LIKE + 候选会话预筛（现状），功能开关 `search.fulltext.enabled` 控制，不阻断发版。
- 查询改写：`session.service.ts` 的 `searchSessionsByUserMessage` 扩展为 `searchMessages(userId, {keyword, agentId, dateFrom, dateTo, sessionType, page})`：
  - 关键词过短或含全文保留字时自动回退 LIKE 路径；
  - `MATCH(content) AGAINST(? IN BOOLEAN MODE)` 按 user_id 过滤（JOIN session），相关度（`MATCH ... AGAINST` 分值）+ `message.id DESC` 排序；
  - 返回结构从"会话摘要"改为"命中消息"：`{messageId, sessionId, sessionTitle, agentId, role, snippet（前后各截断约 80 字，关键词两侧优先）, createdAt}`。

### 3.2 后端改造

- `session.repository.ts` 新增 `selectMessagesFulltext`，保留现有 LIKE 实现作为回退；`session.service.ts` 编排两种路径 + 分页 + 过滤条件拼接；`/v1/sessions/search` 响应结构升级（旧字段保留一版过渡，桌面端同版切换）。
- 命中消息定位：消息 id 已知，桌面端跳转后走现有"定位到消息"滚动能力（消息渲染层已有 id 锚点，需补短暂高亮样式）。

### 3.3 前端

- `SessionSearchPopover.vue` 升级：搜索框支持 `agent:`、`before:`/`after:` 等轻量过滤语法（或直接给筛选行，优先筛选行更直观）；结果列表按会话分组展示命中消息（一条会话多命中折叠为"N 条命中"）；点击跳转定位 + 高亮 2 秒。
- 全局快捷键（如 Ctrl/Cmd+K 直达搜索）与顶栏搜索入口统一；最近搜索词本地记忆。

## 4. 分阶段实施

| 阶段 | 内容 | 规模 |
|---|---|---|
| P1 | ngram FULLTEXT 迁移 + fulltext 查询实现 + LIKE 回退 + 响应结构升级 + 跳转定位 | 中 |
| P2 | 筛选（Agent/时间/类型）+ 分页 + 桌面搜索面板改版（按会话分组、高亮、快捷键） | 小~中 |
| P3 | 结果片段相关度调优、搜索范围扩展（工具结果摘要）评估 | 小 |

## 5. 风险与开放问题

- **ngram 索引体积**：中文全文索引可能显著增大（经验值为原文的 30%~100%）。缓解：迁移前用生产规模数据实测；如体积不可接受，退化为"仅对近 N 个月消息建索引"或布尔回退方案。发版前必须给出体积数据。
- **短词与停用词**：ngram 对 2 字词友好，单字查询仍弱；全文模式对常见词可能命中过万。缓解：最小查询长度限制（默认 2 字符）+ 结果分页 + 相关度排序；单字符走 LIKE。
- **多词语义**：布尔模式下多词是 AND 语义，"部署 OR 脚本"需用户显式写操作符。缓解：P2 在 UI 上把多词默认按 OR 处理更符合直觉（`AGAINST (+kw1 +kw2 ...)` 或自然语言模式评测后定）。
- **消息内容含敏感信息**：用户只搜自己的会话无越权；但需确认分享快照（只读页）数据不落入索引池，以及 compact 脱敏消息的搜索行为（脱敏后文本即存储文本，搜不到原文符合预期）。
- **开放问题**：工具结果（命令输出、报错栈）是否纳入索引——价值高但噪声与体积双高，建议 P3 用开关灰度评估。

## 6. 测试要点

- 中文查询：双字及以上关键词命中 ASSISTANT 消息（现状盲区）；多词组合查询符合预期布尔语义。
- 回退：单字符、特殊符号、全文保留字场景自动走 LIKE 且结果正确；`search.fulltext.enabled=false` 时功能降级可用。
- 权限：用户 A 搜不到用户 B 的会话内容；分享快照来源会话的搜索行为符合定义。
- 跳转：点击结果落到会话内正确消息并高亮；长消息定位后滚动位置可见该消息。
- 筛选：Agent/时间/会话类型过滤生效且可分页；结果计数与翻页一致性。
- 性能：万级消息会话的关键词搜索 P95 延迟可接受（给出基准数字）；索引迁移在大库上可在线执行（评估 `ALGORITHM=INPLACE` 或 pt-osc 类方案）。
