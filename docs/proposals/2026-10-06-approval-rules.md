# 提案：工具审批规则 —— "本会话总是允许"与持久 allowlist

- 状态：已转入实施（2026-10-06；技术方案见 [docs/plan/2026-10-06-approval-rules-technical-design.md](../plan/2026-10-06-approval-rules-technical-design.md)）
- 日期：2026-10-06
- 提案总览：见 `docs/proposals/README.md`

## 1. 背景与现状

LOCAL 边界的审批现状：

1. **逐次审批、无记忆**：五档权限（READ_ONLY / READ_WRITE / SMART / PROXY / FULL，`permission-level.ts`）判定是否需要审批，`ApprovalStack.vue` 只有"执行 / 拒绝"两个按钮，每次调用独立弹窗。全库无 always_allow / remember / whitelist 逻辑。
2. **审批疲劳的出口只有降级**：频繁弹窗把用户逼向唯一出口——把权限档直接调到 FULL，安全性整体倒退。"逐次确认太烦"与"FULL 太危险"之间没有中间态。
3. **SMART 档已有短路先例**：DangerAssessor（LLM 评险）与 ProxyApprover（代批）都在审批链路上，规则化放行可以在评险**之前**短路，反而省一次 LLM 调用。

## 2. 目标 / 非目标

**目标**

1. 审批弹窗增加第三个选项"本会话总是允许（限定匹配模式）"：模式由当次请求的参数自动归一化生成（如 shell 取 `命令 + 子命令` 前缀、文件操作取目录级前缀、MCP 取工具级）。
2. 用户级持久规则：设置页可增删启停，命中即静默放行，只对创建者生效。
3. 审批透明：规则放行记入审批流水（命中哪条规则），admin 可只读查看全量规则。

**非目标**

- 不做 admin 集中下发 / 组织级策略（先用户自助，后续再说）。
- 不做自由正则规则（安全面失控；只提供受控模板：前缀 / 精确 / 工具级）。
- 不改五档语义：规则是档位之上的放行加速器，READ_ONLY 档的写操作不可被任何规则放行。

## 3. 技术方案

### 3.1 会话级"总是允许"（P1）

- 表 `approval_rule`（id, user_id, scope: SESSION | USER, session_id nullable, tool_name, pattern_type: PREFIX | EXACT | TOOL, pattern, enabled, created_at）。
- 判门顺序调整（`tool-dispatcher.ts` `shouldRequireApproval`）：五档判定 → **规则匹配（会话级优先）** → SMART 评险兜底 → 弹窗。规则命中直接放行并记 `approval_decision = RULE`。
- ApprovalStack 第三按钮：点选时把当次参数归一化为 PREFIX 模板展示给用户确认（"以后本会话允许 `npm run *`"），用户看到的是将要记住的模式而不是盲选。

### 3.2 用户级规则管理（P2）

- 设置页规则 CRUD，按命中次数排序、展示最近命中时间，辅助清理长期未命中的规则。
- 审批流水中规则放行可视化（哪条规则、什么参数）；admin 增只读规则清单页。

### 3.3 危险兜底（P3）

- 高危模式黑名单：模板生成阶段显式拒绝为高危动词生成"总是允许"（rm -rf、`git push --force`、drop table 等，黑名单内置 + admin 可补充）；黑名单内的请求即使命中规则仍走弹窗。
- 兜底顺序固定为：规则匹配 → 评险红线 → 弹窗，规则永不越过评险红线。

## 4. 分阶段实施

| 阶段 | 内容 | 规模 |
|---|---|---|
| P1 | 规则表 + 会话级总是允许 + 判门短路 + 审批弹窗三选项 | 小~中 |
| P2 | 用户级规则管理页 + 流水可视化 + admin 只读清单 | 中 |
| P3 | 高危黑名单兜底 + 规则清理辅助 | 小 |

## 5. 风险与开放问题

- **模板过宽**：`git push*` 会放行所有 push。缓解：模板归一化粒度固定（命令 + 子命令，不带通配到任意位置）+ P3 黑名单；生成时 UI 展示模式全文由用户确认。
- **规则膨胀**：设置页按命中排序 + 未命中提示；会话级规则随会话删除一并清理。
- **MCP 参数差异大**：P1 只支持 MCP 工具级（TOOL）放行，参数模板等工具元数据成熟后再做（开放问题）。
- **开放问题**：PROXY 档（LLM 代批）与规则的关系——建议规则优先于代批（规则是用户明示意图，代批是模型推测），实施时验证两者叠加的审计语义。

## 6. 测试要点

- 规则命中短路不触发评险 LLM 调用（scene 计数验证）。
- 会话级规则不跨会话泄漏；用户级规则只对创建者生效。
- READ_ONLY 档写操作即使命中规则仍被拒。
- 高危黑名单内命令生成模板被拒、命中规则仍弹窗。
- 审批流水记录规则 id 与放行动作；规则禁用后立即生效。
