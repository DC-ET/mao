# 提案：计划模式（Plan Mode）—— 执行之前，先让人看一眼方案

- 状态：**已否决**（2026-10-09 评审：不做。本文仅存档，勿再评审）
- 日期：2026-10-09
- 提案总览：见 `docs/proposals/README.md`

## 1. 背景与现状

今天的交互是「描述目标 → Agent 直接开跑」。人的介入点只有两个，且都在执行**之后**或执行**之中**：

1. **工具审批**（approval-rule 域）：单个高风险工具执行前弹窗，是**工具级**闸门——一次任务要改 8 个文件，就是 8 次弹窗，人看到的是"这一步"，看不到"全貌"。
2. **执行中提问**（ask-user-questions，`harness/tool/ask-user-questions-registry.ts`）：Agent 中途发问，人回答问题——是**点状**交互，不是方案评审。

`session_todo`（`harness/todo/session-todo.mapper.ts`）+ task_create / task_update 工具 + 桌面 `TodoChecklist.vue` 提供了一份执行中的清单，但它是 **Agent 自管、用户只读**的进度展示，用户不能改、不能在跑之前签字。

结果：LOCAL 场景（改的是用户本机目录）尤其别扭——用户把"帮我重构这个模块"交给 Agent，第一次看到具体要动哪些文件，是文件已经被改之后。这与产品"执行边界可切换、治理才是平台"的定位不匹配：边界管的是"能在哪执行"，缺的是"执行前人对计划的确认"。

与相邻方向的边界：

- **不是低代码画布**：计划单任务生效、执行后即弃，不可复用、不可编排，没有 DAG/触发器语义（README 明确"不是 Dify / n8n"）。
- **不是多 Agent 协作**：不引入依赖调度、队友信箱、持久化计划状态机（该方向已否决），计划只是本会话内的一份结构化意图声明。
- **不是工具审批的替代**：计划门通过后，工具级审批照常生效，两者叠加。

## 2. 目标 / 非目标

**目标**

1. 任务进入执行前可进入**计划态**：Agent 先产出结构化计划（步骤列表 + 每步涉及的文件/工具预估 + 预期产出），此态下只允许只读工具（读文件、搜索、列出目录），任何写操作被拒绝并提示"计划未批准"。
2. 人对计划的处置：**批准**（进入执行，todo 与计划步骤关联，执行中步骤状态可见）、**编辑后批准**（增删步骤、改文件清单）、**驳回并附意见**（意见回注给 Agent 重新出计划）。
3. 计划可见性：桌面端计划卡片（步骤清单 + 文件清单 + 批准/驳回按钮），执行中计划步骤与 `session_todo` 并排展示完成度。
4. 触发方式：用户主动开启（新任务 composer 的开关，按会话记忆）+ Agent 对复杂任务主动建议进入计划态（经 ask-user-questions 同款确认卡片）。

**非目标**

- 不做可复用计划模板 / 计划市场（P1 单任务生效；模板是后续可评估的衍生，不在本提案）。
- 不做计划与执行的强契约（Agent 必须严格按计划执行）——计划是**意图声明与人的确认记录**，执行允许偏离，UI 明示"执行可能与计划有出入"。
- 不改 FULL 权限档语义；计划门与权限档、审批规则三者独立叠加。
- 不做计划的多端编辑冲突处理（P1 单人单会话编辑；渠道端（飞书等）只读展示）。

## 3. 技术方案

### 3.1 会话状态机（P1）

- 会话新增执行相位：`normal → planning → approved → (执行)`，驳回则 `planning` 重入（带意见）。相位落 `session` 表（或 execution 记录），崩溃恢复时能还原"计划待批"态（对齐现有 crash-recovery 的相位恢复模式）。
- 计划数据结构：`session_plan`（id、session_id、steps JSON、status: DRAFT/APPROVED/REJECTED、feedback、created_at）。steps JSON 内含步骤标题、描述、涉及文件 glob、预估工具。

### 3.2 引擎侧（P1）

- prompt-engine 在计划态注入计划模板与约束：只读工具白名单（复用现有 permission-level 的只读判定），写工具返回明确错误码 `PLAN_NOT_APPROVED`。
- agent-loop 在轮首检查相位：计划态遇到写工具调用，走 tool-dispatcher 判门链新增的 plan 判定项（与权限档、审批规则并列），返回可读错误而非异常。
- 批准后：计划 steps 写入 `session_todo`（带 plan_step 来源标记，排序在前），Agent 执行中正常更新 todo 状态——计划即初始 todo，不引入第二套清单存储。

### 3.3 交互（P1）

- 计划卡片复用 ask-user-questions 的卡片交互与 center-panel-approval 的确认 UI 模式：步骤列表（可编辑态）、涉及文件、批准/驳回按钮；驳回弹意见输入。
- WS 事件新增 `plan_created` / `plan_updated` / `plan_approved` / `plan_rejected`，桌面 `useStreamWS` 消费；执行中计划步骤与 todo 合并渲染。
- 渠道端（飞书/钉钉/微信）：计划以卡片消息展示，批准/驳回走既有卡片回调链路。

### 3.4 触发策略（P2）

- composer 计划开关（默认关，按用户偏好记忆）；Agent 主动建议：提示词中给出"多文件修改/不可逆操作前建议先出计划"的判据，经确认卡片由人决定。

## 4. 分阶段实施

| 阶段 | 内容 | 规模 |
|---|---|---|
| P1 | 计划态状态机 + session_plan + 只读约束 + 桌面计划卡片（批准/驳回） | 中 |
| P2 | 计划编辑（增删步骤）+ composer 开关 + Agent 主动建议 | 小~中 |
| P3 | 渠道端计划卡片 + 执行完成度报告（计划 vs 实际） | 小 |

## 5. 风险与开放问题

- **误伤简单任务**：计划门增加一次往返。缓解：默认关、按会话/用户记忆；简单问答（无写工具意图）不触发。
- **模型不遵守结构化计划**：计划输出用 JSON schema 约束；解析失败时降级为普通执行并在 UI 明示"计划生成失败，已直接执行"，不阻塞任务。
- **计划与执行漂移**：不追求强契约，UI 常驻"执行可能与计划有出入"提示；P3 的完成度报告只做展示不做考核。
- **渠道端交互深度**：飞书卡片按钮承载"编辑计划"过重，P3 渠道端只做批准/驳回，编辑仅桌面端。
- **开放问题**：计划是否随会话分享快照一起导出（分享提案已实施，计划作为消息元数据自然带入，需验证序列化）。

## 6. 测试要点

- 计划态下写工具被拒且错误码为 `PLAN_NOT_APPROVED`；只读工具正常。
- 批准后 `session_todo` 含计划步骤且排序在前；执行中 todo 状态流转正常。
- 驳回带意见：意见进入重新计划的提示上下文；相位回到 planning。
- 崩溃恢复：执行中崩溃后重启，"计划待批"态可还原、已批准计划不重复要求批准。
- 计划生成失败（模型输出非法 JSON）降级普通执行，不抛错、不卡会话。
