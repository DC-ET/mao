# 提案：技能蒸馏（Skill Distillation）—— 把一次成功的会话，变成下次能直接用的技能

- 状态：**已否决**（2026-10-11 评审：不做。本文仅存档，勿再评审）
- 日期：2026-10-11
- 提案总览：见 `docs/proposals/README.md`

## 1. 背景与现状

Mao 的技能体系（`skill` 域 + `harness/skill/`）今天是这样运转的：

- **系统技能**：`SKILL.md`（frontmatter name/description + 正文）放在服务端技能目录，管理后台可增删改。
- **用户技能**：每用户一个目录（`/opt/mao/data/skills/{userId}/`），`SKILL.md` 同构，桌面设置页可上传 / 查看 / 删除，同名多目录可按 `folder` 精确寻址（0.0.237 起）。
- **分发**：Agent Bundle 可内联用户技能跨实例搬运；技能独立 bundle（`mao-skill-bundle` v1）可单独导出导入。
- **注入**：按 Agent 绑定的技能清单进 system prompt 的「可用技能」节。

**问题在于技能的来源只有一条：手写。** 用户想让 Agent"下次会做某件事"，必须自己把做法提炼成 `SKILL.md`——而提炼所需的信息（那次到底怎么跑通的、用了哪些工具、踩了什么坑）明明都在会话里：

1. **成功的路径不可复用**。上周让 Agent 做了一次"拉取竞品数据 → 清洗 → 生成周报"，跑通了，很满意。下周再来一次，要么把整段历史翻出来当上下文（贵且慢），要么凭记忆重新描述一遍（丢细节）。
2. **轨迹数据已经齐了但没人用**。0.0.251 上线的运行轨迹（`run-trace.service.ts`）已经能把一个会话按 run 聚合成"轮次 / 工具 / 耗时 / 成败"，导出 JSON / CSV——这是蒸馏的现成原料，但今天它只服务于"复盘"，不服务于"沉淀"。
3. **与相邻资产的断层**。长期记忆（0.0.234）沉淀的是"事实与偏好"，Agent 经验（0.0.209 起）沉淀的是"通用行为准则"，**两者都不承载"做某类事的具体操作步骤"**。技能正是这个载体，但从会话到技能之间没有桥。
4. **技能冷启动成本高**。写 `SKILL.md` 有格式门槛（frontmatter、描述要写得让模型知道何时用），劝退了大量"我其实有个好流程但懒得写"的用户。

相邻方向的边界：

- **不是记忆**：记忆是"记住关于用户与世界的事实"，注入后不改 Agent 的能力边界；技能是"教 Agent 一套做法"，注入后改变可复用的行为模式。
- **不是 Agent 经验**：经验是 ≤300 字的单条行为准则（"X 场景优先 Y"），技能是带步骤的操作手册（"做 X 类事分 5 步，第 3 步注意 Z"）。粒度与用途不同。
- **不是 Evals**（已否决）：不做数据集与回归评分；蒸馏的产物验证靠"人预览 + 试跑一次"，不是量化评测。
- **不是低代码画布**（README 明确排除）：蒸馏产物是自然语言指令（`SKILL.md`），不是流程图或编排 DSL。

## 2. 目标 / 非目标

**目标**

1. **从轨迹到草稿**：在任意会话（主会话 / 边路任务 / 子代理）的操作菜单里选「蒸馏为技能」→ 后端取该会话的轨迹（复用 `RunTraceService`）+ 最终结论 + 文件变更摘要，LLM 起草一份 `SKILL.md`（frontmatter name/description + 分步正文），**人预览编辑确认**后才落盘。
2. **落到用户技能目录**：确认后写入属主用户技能目录（复用 `staged-skill-writer.ts` 的校验链：name 合法性、frontmatter 解析、总量上限 10MB、同名不覆盖），桌面设置页技能列表立即可见。
3. **描述质量把关**：`description` 是模型选择技能的依据，草稿必须包含"何时用这个技能"的触发条件；预览界面把 frontmatter 单独高亮编辑，并给出"描述是否含触发条件"的轻校验提示。
4. **可试用再定稿**：预览阶段提供「试跑」——用草稿技能在当前会话（或新会话）跑一次原始任务，把结果与首次对照（成功 / 失败、耗时、token），人据此决定是否保存。**人始终在环里。**
5. **多会话蒸馏**：支持选中多个会话（如同一类任务做过三次）一起蒸馏，产出更通用的技能草稿；轨迹按会话分组呈现，模型归纳共性步骤。

**非目标**

- 不做全自动"每次任务完成就自动蒸馏"（自动写入技能 = 无声的能力漂移，人必须确认）。
- 不做技能的版本管理（一次蒸馏 = 一次写入，覆盖走"另存为新技能"）。
- 不做蒸馏产物的效果量化（"装了该技能后同类任务成功率提升 X%"）——Evals 范畴。
- 不改系统技能的写入路径（蒸馏只产用户级技能；系统技能仍由管理员手工维护）。
- 不做从轨迹到**代码型**技能的蒸馏（产出可执行脚本而非指令）——那是另一个量级的工程（沙箱、依赖、安全审查）。

## 3. 技术方案

### 3.1 数据流

```
会话（主/边路/子代理）
  → RunTraceService.buildTrace(sessionId)      # 既有，只读
  + 最终结论（最后一条 ASSISTANT 消息摘要）
  + 文件变更摘要（message.metadata.fileChanges 既有字段）
  → DistillationService.draft({ sessionIds })  # 新：LLM 调用，scene=skill_distill
  → 草稿 SKILL.md（name/description/body）
  → 人预览 / 编辑 / 试跑（可选）
  → staged-skill-writer 校验链落盘            # 既有
  → 用户技能目录 → 设置页可见 / 可绑 Agent
```

草稿阶段**不落库、不落盘**：草稿是瞬时的，只在桌面端内存 + 后端一次性返回；只有确认保存才走写入。这与「负反馈闭环」的草稿哲学一致（生成即评审，不建中间态表）。

### 3.2 蒸馏服务

新增 `src/skill/distillation.service.ts`：

- 输入：`sessionIds: number[]`（校验均属当前用户）+ `agentId?`（限定技能服务的目标 Agent 范围，用于 description 措辞）。
- 原料装配（对齐 feedback 草稿的脱敏口径）：
  - 轨迹：run → rounds → tools（**只取工具名 / 目标 / 成败 / 耗时**，不取工具结果全文）；
  - 最终结论：最后一条 ASSISTANT 消息，截断到 4000 字；
  - 文件变更：路径 + 增删行数（不含内容）；
  - 用户原始诉求：第一条 USER 消息（这是"何时用"的关键信号）。
- prompt 约束：输出严格 frontmatter（`name` 合法、`description` 必须含触发条件与适用场景）+ 分步正文（ numbered steps，含注意事项与失败处理）；禁止臆测轨迹中未出现的步骤；单次输出 ≤ 8KB。解析失败一次纠错重试，仍失败返回可读错误。
- 用量：`scene=skill_distill` 进 `llm_call` 体系（对齐 `git_commit_message` / `feedback_experience_draft`）。

### 3.3 桌面端交互

- 入口：会话右键菜单 / 会话操作栏「蒸馏为技能」（主会话、边路任务、子代理视图均有；只对本人会话显示）。
- 蒸馏向导（三态）：
  1. **选料**：多选会话（默认当前会话）+ 显示各会话的轨迹摘要预览（run 数 / 工具链 / 是否成功）；
  2. **草稿**：frontmatter 编辑区（name / description，带触发条件轻校验）+ 正文编辑区 + 「试跑一次」按钮；
  3. **定稿**：保存到我的技能（写入后弹「去设置页查看 / 去绑定 Agent」）。
- 试跑：以草稿技能 + 原始诉求建一次性会话执行（技能以临时用户技能形式注入，不落盘），结果与首次执行对照展示（终态、耗时、token、成本）。试跑消耗正常计入用量。

### 3.4 写入与校验

- 落盘完全复用 `staged-skill-writer.ts`（bundle 导入同款）：暂存交换、原子 rename、name 合法性、frontmatter 解析、总量上限。
- 同名冲突：不覆盖，提示改名或「另存为新名称」（自动加后缀）。
- 保存后：用户技能列表（`listUserSkills`）天然可见；Agent 绑定走既有技能选择器。

## 4. 分阶段实施

| 阶段 | 内容 | 规模 |
|---|---|---|
| P1 | DistillationService（单会话草稿）+ 桌面向导（选料 / 草稿 / 定稿）+ staged 落盘 +  summarizer / toolDisplay 同步（若引入工具，见下） | 中 |
| P2 | 多会话蒸馏 + 试跑对照 + description 触发条件校验 | 小~中 |
| P3 | 蒸馏历史（最近 N 次草稿，避免重复蒸馏同一会话）+ 边路 / 子代理会话的产物归属策略 | 小 |

**关于是否引入内置工具**：本提案默认**不做** `distill_skill` 工具（Agent 自己蒸馏自己=失控面：模型可以借蒸馏无限改写自己的能力边界）。蒸馏是**人的操作**，入口只在桌面端菜单。若评审认为 Agent 主动建议蒸馏有价值，应走"Agent 通过 ask-user-questions 建议 → 人确认打开向导"的路径，仍不开放直接写入。

## 5. 风险与开放问题

- **草稿质量**：轨迹只有工具名与目标，模型可能写出流水账而非可复用流程。缓解：prompt 强调"面向下次执行，不是复盘本次"；人可编辑；试跑提供验证手段；不满意可弃用重蒸。
- **轨迹信息不足**：会话若被压缩过（compaction），早期轮次细节在轨迹里可能已丢。缓解：蒸馏入口对"压缩次数 ≥ N"的会话给出提示"早期上下文已压缩，草稿可能不完整"；原料以压缩后的轨迹为准（所见即所得）。
- **技能投毒**：用户自己蒸馏的技能自己用，无跨用户传播，投毒面限于本人；但若技能经 bundle 分享给他人，劣质技能会传播。缓解：分享仍是既有 bundle 链路（导出时人能看到内容），不因蒸馏改变分享的安全模型。
- **总量与体积**：单次草稿 ≤ 8KB，用户技能总量上限 10MB 已有；无明显新增风险。
- **敏感内容**：轨迹目标可能含敏感文件名 / 内部域名 / 数据样本。缓解：复用敏感文件规则（命中摘要为 `[sensitive]`）；蒸馏产物是用户自己的，落盘前人有预览环节。
- **开放问题**：子代理会话的蒸馏产物归属——子代理会话的 `user_id` 即发起者，归属无歧义；但"子代理跑通的流程"是否应提示用户"这是子代理的能力边界（无 ask_user_questions 等工具），蒸馏成主技能时注意步骤假设"——建议在草稿里加来源标注（`source: subagent`），P3 实现。
- **开放问题**：多会话蒸馏的选料上限（10 个？）与轨迹裁剪策略（每个会话取最近 N 个 run）——P2 实现时定，倾向 10 会话 × 每会话最近 5 run。

## 6. 测试要点

- 草稿服务：单会话产出合法 frontmatter + 分步正文；description 含触发条件（prompt 契约校验）；输出非法时纠错一次、二次失败可读报错；LLM 失败不写任何东西。
- 脱敏：轨迹目标含敏感文件时为 `[sensitive]`；不含工具结果全文（断言 prompt 输入中无 `tool_result` 正文）。
- 落盘：暂存交换原子性（中断不留半文件）；name 非法被拒；同名不覆盖（提示改名）；总量超限拒绝；落盘后 `listUserSkills` 可见。
- 向导：多会话选择与轨迹预览；草稿编辑后保存的是编辑版而非原始生成版；试跑产生一次性会话且技能不落盘；试跑结果对照展示。
- 权限：只能蒸馏本人会话（越权 sessionId 返回 404 / 403）；保存路径限定本人用户技能目录。
- 用量：`scene=skill_distill` 的 `llm_call` 正确记录且计入成本与预算口径。
- 回归：`staged-skill-writer` / bundle 导入路径零改动（只复用）；系统技能写入路径不受影响；`tool-result-summarizer` 与 `toolDisplay` 若未新增工具则无改动（本提案不引入工具）。
