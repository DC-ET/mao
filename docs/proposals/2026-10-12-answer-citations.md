# 提案：回复引用溯源（Answer Citations）—— 让 Agent 的每句话可验证

- 状态：**已确认**（2026-10-12 评审通过，技术方案见 [../plan/2026-10-12-answer-citations-technical-design.md](../plan/2026-10-12-answer-citations-technical-design.md)，决策记录 9 条于 2026-10-12 逐条确认）
- 日期：2026-10-12
- 提案总览：见 `docs/proposals/README.md`

## 1. 背景与现状

今天 Agent 说"根据最新公告，X 政策的截止时间是 11 月 30 日"，用户没有任何办法验证这句话是哪来的——是 `web_search` 搜到的第 3 条结果，是 `open_web_page` 抓的页面原文，还是模型自己编的。

现状盘点：

1. **工具结果里明明有 URL，但出口就丢了**。`web_search` 返回 `{title, url, content}` 三元组、`open_web_page` 抓回整页正文，这些 URL 进了模型上下文、也进了运行轨迹，但最终回复是纯 markdown 文本，来源信息在消息渲染时被完全丢弃。用户看到结论，看不到依据。
2. **幻觉 URL 是真实风险**。让模型"给出处"，它可能一本正经地编造 `https://example.gov.cn/notice/2025/xxxx.html`——域名对、路径不存在。不做校验的引用标注比不标注更危险：它给幻觉盖了个"可验证"的章。
3. **企业场景的信任门槛**。私有化部署的用户把 Agent 的回答转给领导 / 客户前，需要自己能核验。今天的做法是复制一句话去手动搜索，比对成本极高。

相邻方向的边界：

- **不是 RAG / 知识库**（已否决）：不做语料检索与 embedding，只把本轮工具已经拿到的 URL 结构化地呈现出来。
- **不是 Evals / 提示词回归**（已否决）：不评估"引用准确率"这类指标，引用是给最终用户看的功能，不是给评测集用的。
- **不是运行轨迹**（已实施）：轨迹记录工具调用了什么，是"向过去看"的排障视图；引用是嵌在回复里的、面向读者的信任构件。

## 2. 目标 / 非目标

**目标**

1. **引用标记**：系统提示词增加引用契约——模型在引用外部信息时用 `[^1^]` 行内标记（不用标准 markdown 脚注语法，避免与模型自造的脚注区冲突），消息尾部由系统生成「来源」列表（序号 + 标题 + 域名）。
2. **白名单校验（核心）**：后端在每轮结束时扫描本轮全部工具结果，提取出现过的 URL 集合（registry）。消息里的每个 `[^n^]` 必须能对上 registry 里的一个 URL——**对不上的一律剥掉标记按纯文本展示**。模型编造的 URL 到不了用户眼前。
3. **来源列表渲染**：桌面 / Web / 安卓三端在助手消息末尾渲染「来源」折叠区：序号、标题（取自 registry 中该 URL 的标题，没有则显示域名 + 路径）、可点击外跳（复用 `externalLink.ts` 的 http/https 安全校验）。
4. **零迁移的 P1**：registry 与引用映射存进助手消息行（`message` 表新增一列 `citations_json`，仅一个迁移），不动消息内容本身，历史消息无引用即无渲染。

**非目标**

- 不做引用内容的语义核对（"这句话是否真的支持该结论"）——那是 NLP 判重，P1 只保证 URL 真实出现在本轮工具结果中。
- 不做链接健康巡检（定期 HEAD 探测源站是否还活着）——哨兵已是通用探针设施，但给引用做巡检是过度设计；源失效用户点过去自然知道。
- 不做非 HTTP 来源（文件路径、记忆条目、经验）的引用标记——P1 只覆盖 web_search / open_web_page 两个联网工具；本地文件引用今天已有 FileReference 机制。
- 不改渠道消息（飞书 / 钉钉 / 微信卡片）的引用渲染——卡片里放折叠来源区交互蹩脚，P1 只做桌面 / Web / 安卓的消息流。

## 3. 技术方案

### 3.1 数据模型（V150，当前最新 V149）

```sql
ALTER TABLE `message`
    ADD COLUMN `citations_json` TEXT NULL
    COMMENT '引用注册表：[{index, url, title}]，本轮工具结果中出现过的 URL；无则 NULL';
```

- 只写助手最终回复所在的消息行；用户消息、工具消息、边路 / 子代理消息不写。
- 存量消息为 NULL，前端读到 NULL 即不渲染来源区，无兼容分支。

### 3.2 引用提取与校验（后端，`session` 域）

新增 `session/message-citations.ts`：

- **URL registry 构建**：每轮 `TASK_COMPLETED`（对齐 `task-terminal.service.ts` 的相位收敛点）时，从本轮消息序列里收集 `web_search` / `open_web_page` 工具结果中的 URL（去重、保序，上限 20 条，防爆）。
- **标记解析**：对助手最终回复文本扫描 `[^n^]` 模式，n 与 registry 位置对齐（模型输出 `[^1^]` 即 registry[0]，不是"模型自己编号"——编号权在系统，模型只负责插标记）。
- **校验与清洗**：剥掉所有对不上 registry 的标记（含伪造 URL 场景——伪造的 URL 根本进不了 registry，标记自然被剥）；未被任何标记引用的 registry 条目不进 `citations_json`。
- **落库**：`{index, url, title}` 数组写入助手消息行；内容文本不动（标记保留原文，渲染层决定怎么显示——这样 JSONL 导出 / 会话分享快照里引用结构不丢失）。

### 3.3 提示词契约（`harness/prompt`）

- 系统提示词「工具使用规范」增加一段：引用 web_search / open_web_page 得到的信息时，在句末插入 `[^n^]`，n 为本轮中该来源第一次被引用时的顺序编号（从 1 开始）；没有来源支撑的说法不得添加标记；标记必须紧贴被支撑的句子。
- 契约放进提示词版本管理（既有 `agent_prompt_version` 机制），老 Agent 升级时可见 diff。

### 3.4 前端渲染（desktop，三端共用）

- `useMarkdown.ts` 的 renderer 扩展：`[^n^]` 渲染为上标 `<sup class="cite-ref">[n]</sup>`（DOMPurify 白名单加 `sup` 及其 class），点击平滑滚动到本条消息的来源区并高亮对应条目。
- `MessageBubble.vue`（或 ChatRoundList 的消息尾部）：`citations_json` 非空时渲染折叠「来源 N」区，条目 = 序号 + 标题（超长截断）+ 域名徽标；点击经 `openExternal` 外跳。
- 消息导出（JSONL / Markdown 导出，既有 `session-export`）在文末追加来源列表，保持离线可读。

### 3.5 权限与开关

- 用户级开关：「设置 → 通用」新增「回复引用溯源」总开关（默认开）；单会话级不需要——引用是渲染层行为，不注入上下文，无上下文透视的联动成本。
- 无新权限码：纯渲染 + 提示词契约，不动任何数据边界。

## 4. 分阶段实施

| 阶段 | 内容 | 规模 |
|---|---|---|
| P1 | V150 迁移 + registry 构建与标记校验（后端）+ 提示词契约 + 桌面端上标与来源区渲染 | 中 |
| P2 | 导出（JSONL / Markdown）带来源 + 分享快照保留引用结构 + 渠道会话不渲染的降级确认 | 小 |
| P3 | 管理后台引用覆盖率统计（有引用消息 / 联网工具轮次占比，按 Agent）+ 「仅联网工具强制引用」的 Agent 级开关 | 小 |

## 5. 风险与开放问题

- **模型不听话**：小模型可能完全不插标记，或乱插。缓解：P1 验收以"白名单校验不漏放"为硬指标（伪造 URL 必须被剥掉），"引用覆盖率"只作统计不作硬性 KPI；提示词契约随版本发布后可迭代文案。
- **标记语法冲突**：`[^n^]` 与标准 markdown 脚注 `[^1]` 不同，但模型可能混用两种。缓解：解析器只认 `[^n^]`；清洗阶段把标准脚注语法当普通文本（现状行为），不引入歧义。
- **registry 上限截断**：一轮搜索超过 20 个 URL 时尾部被截，对应标记会被剥。缓解：上限 20 已覆盖单轮正常引用量；超限场景在服务端记日志（不打扰用户）。
- **XSS 与外跳安全**：标题 / URL 全部转义；外跳复用 `isSafeHref`（仅 http/https）；`citations_json` 是后端写入的结构化数据，不经模型原文直出。
- **开放问题**：子代理 / 边路任务会话里的引用要不要渲染——建议渲染（同一个消息组件），registry 只收集本会话工具结果，天然隔离。
- **开放问题**：记忆沉淀时是否把引用带入——建议不带（记忆是结论性事实，引用是轮次性证据，混入会让记忆条目体积膨胀且快速过期）。

## 6. 测试要点

- 解析：`[^1^][^2^]` 混排、编号乱序（`[^2^]` 先于 `[^1^]`）、无标记、标记超出 registry 范围等输入的清洗结果符合预期。
- 白名单：模型输出含伪造 URL 的句子时，该 URL 不进 registry、对应标记被剥、纯文本保留。
- registry：web_search 多结果去重保序；超过 20 条截断；非联网工具的文件路径不进 registry。
- 落库与兼容：`citations_json` 仅在最终回复行写入；NULL 行前端无来源区；JSONL 导出 / 分享快照往返后引用不丢。
- 前端：上标点击滚动高亮；来源区折叠展开；外跳链接 `javascript:` 被拦截（回归 `externalLink` 既有用例）；深色模式下的可读性。
- 回归：现有 markdown 渲染（代码块 / 表格 / 标准脚注）零变化；渠道消息不出现来源区。
