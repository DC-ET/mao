# 提案：开放接口调用中心（Open API Call Center）—— 外部系统驱动 Agent，不能是个黑盒

- 状态：待评审
- 日期：2026-10-09
- 提案总览：见 `docs/proposals/README.md`

## 1. 背景与现状

开放接口（`2026-10-05-open-api-webhook.md`，已实施）让外部系统能驱动 Agent：入站有 API Token 远程触发（`POST /v1/open/agents/:id/run`，异步 202）与 Webhook 触发器（HMAC 验签、连续失败自动停用并通知），出站有事件订阅推送到自建端点（失败退避重试）。

但**入站调用的可观测性几乎为零**：

1. **无调用流水**：`openapi/` 域里出站有 `GET /v1/open/subscriptions/:id/deliveries` 看投递历史，入站侧只有 Token 的 `lastUsedAt` 一个时间戳（`openapi/types.ts`）。外部系统什么时候调的、带了什么参数、成功了还是失败了、失败原因是什么，一概查不到。
2. **失败不可感知**：入站调用若因为"会话忙排队中""Agent 已停用""参数不合法"被拒，外部系统拿到的是当时的 HTTP 响应，之后没有任何地方回看——Token 被盗刷、对接方联调报错，都只能去翻服务端日志。
3. **无用量视角**：哪个 Token 调用最频繁、哪个 Agent 被外部驱动最多、延迟分布如何，与现有用量分析（`scene=agent` 口径）不通，管理后台答不上来。
4. **不可重放**：联调时想"再发一次刚才那个请求"验证修复，只能回外部系统重新触发，没有服务端侧重放。

对比之下出站订阅有投递历史、入站 Webhook 有失败计数与自动停用通知，唯独最常用的 API Token 触发是黑盒——这是开放接口三件套里明显的短板。当产品主张"让外部系统驱动 Agent"时，运维侧至少要能回答：**它被谁、在什么时候、以什么姿势、调用得怎么样**。

## 2. 目标 / 非目标

**目标**

1. **入站调用流水**：记录每次 Token 调用与 Webhook 触发（Token/触发器、来源 IP、Agent、请求体摘要、HTTP 状态、排队/执行结果、耗时、错误摘要、关联会话），后台可分页查询、筛选、导出 CSV（口径对齐现有调用流水导出）。
2. **调用统计**：按 Token / Agent / 天的调用量、成功率、P95 延迟、排队时长，管理后台一屏总览；异常（成功率骤降、单 Token 突发流量）在面板高亮。
3. **失败告警**：入站失败按用户/管理员通知偏好进收件箱（复用收件箱现有类型体系）；连续失败达到阈值的 Token 可配置自动停用（与 Webhook 触发器"连续失败自动停用并通知"对齐，从"仅 Webhook 有"扩展到"Token 也可选开"）。
4. **请求重放**：流水详情提供"复制为 cURL"与"原样重发"（重发走正常入口、正常计用量与审计），联调排障闭环。
5. **安全基线**：请求体摘要默认脱敏（只记结构与关键字段，不记全量内容，防密钥/隐私数据进流水）；来源 IP 落库支持异常排查。

**非目标**

- 不做开放 API 的能力扩展（更多端点/参数）——本提案只补可观测，不动接口表面。
- 不做外部系统侧的 SDK/代码生成（mao-cli 已够用，SDK 是另一议题）。
- 不改出站订阅的投递历史（已有实现，只做与入站流水的入口统一）。
- 不做跨实例的调用日志聚合（单后端部署，落库即可）。

## 3. 技术方案

### 3.1 调用流水表（V142）

新增 `open_api_call_log`：`id / token_id（nullable）/ trigger_id（nullable）/ agent_id / user_id / source_ip / request_summary_json（脱敏摘要）/ http_status / outcome（accepted|queued|rejected|failed）/ error_code / session_id / latency_ms / created_at`。写入点在 `open/open.routes.ts` 两个入站端点（Token run、Webhook 触发）的响应前：无论 202 排队、400 参数拒、409 会话忙、429 限流（`rate-limiter.ts` 已有），都落一行——**被拒的调用恰恰是最需要被看见的**。

- 脱敏摘要：请求体按字段名白名单/黑名单生成摘要（如 `{messageChars: 120, hasFile: true}`），全量内容不落库；具体字段清单随实现评审定。
- 异步结果关联：202 接受的调用只记"已受理 + 排队位"，任务终态后回写 `outcome` 与 `session_id`（与 `open-run.service.ts` 的执行收敛点衔接，只读不重写）。

### 3.2 查询与统计

- 新增 `GET /v1/open/calls`（用户看自己的 Token 调用）与 `GET /v1/admin/openapi/calls`（管理视角），支持按 Token/Agent/状态/时间筛选与分页；`GET /v1/admin/openapi/call-stats` 出聚合（调用量/成功率/P95/排队时长，按天或按 Token）。
- 统计优先读聚合表或定时物化（数据量大后），P1 可直接 GROUP BY 加时间范围限制（默认近 30 天）。

### 3.3 前端与管理后台

- 设置页「开放接口」（`OpenApiView.vue`）每个 Token/触发器下增加"调用记录"折叠区（时间、结果徽标、耗时、跳转会话）；管理后台「开放接口」视图（或并入现有 llm-call 风格的独立页）提供全量流水 + 统计面板 + CSV 导出。
- 重放：详情弹窗展示脱敏请求摘要 + "复制为 cURL"；"重发"按钮对 Token 调用开放（Webhook 重发等价于外部重新推送，不提供服务端伪造签名重发，避免绕过验签语义）。

### 3.4 告警与自动停用

- 入站失败（rejected/failed）按 Token 归属用户发收件箱通知（类型 `OPEN_API_CALL_FAILED`，可关）；连续失败阈值（默认 10 次/小时，可配）+ 开关控制的 Token 自动停用，停用后该 Token 调用直接 403 并通知，恢复需用户手动启用——完整复用 Webhook 触发器的既有交互。

## 4. 分阶段实施

| 阶段 | 内容 | 规模 |
|---|---|---|
| P1 | `open_api_call_log` 表 + 两个入站端点埋点（含拒绝路径）+ 用户侧调用记录查询与 UI | 小~中 |
| P2 | 管理后台流水 + 统计面板 + CSV 导出 + 请求重放（复制 cURL / 重发） | 中 |
| P3 | 失败收件箱通知 + Token 连续失败自动停用（可配开关） | 小 |

## 5. 风险与开放问题

- **写入放大**：每次入站调用多一行日志，Token 调用频率通常远低于对话轮次，量级可控；仍需给 `created_at` + `token_id` 建索引，并评估保留期（与已否决的数据保留提案边界：本表建议默认 90 天滚动清理，复用 inbox 域已有的 cleanup 模式）。
- **脱敏与排障的矛盾**：摘要太简则排障不够用。缓解：摘要结构可配置（管理员可临时对指定 Token 开启"记录完整请求体"，带审计与显眼警示），默认关。
- **异步回写一致性**：202 受理的调用回写终态依赖执行收敛点，崩溃时可能停在 accepted。缓解：崩溃恢复 runner 已有会话恢复，回写失败的行在统计中单列"结果未知"，不猜。
- **开放问题**：调用流水是否计入 Token 级用量配额（与用量预算的关系——建议只观测不限额，限额继续走全局/用户/Agent 预算，避免双闸门混淆）。
- **开放问题**：重放是否需要对"原样重发"做幂等键支持（防联调时重复触发副作用）——P2 只做手动重发，幂等键列为后续。

## 6. 测试要点

- 埋点完整性：202 排队、400/403/409/429 各类拒绝均落流水且字段正确；请求体摘要不含敏感字段全量。
- 查询筛选：按 Token/Agent/状态/时间过滤与分页正确；用户只能看自己的 Token 流水，管理员看全量。
- 统计：调用量/成功率/P95 与流水明细口径一致；CSV 导出行数与筛选结果一致。
- 重放：复制 cURL 可直接执行；服务端"重发"产生新流水行且正常排队执行。
- 告警：失败通知进收件箱且可关；连续失败达阈值自动停用并通知；停用后调用 403；手动恢复后可用。
- 回写：异步任务终态后 outcome/session_id 正确回写；崩溃场景留 "accepted" 不误报。
