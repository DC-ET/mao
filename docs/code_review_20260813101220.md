## 中等严重程度

### 1. CAS 冲突重载并发摘要后没有重置上下文 token 锚点

**代码位置**

- `backend/src/main/java/cn/etarch/mao/harness/core/SessionCompactionOrchestrator.java:57-72`
- `backend/src/main/java/cn/etarch/mao/harness/core/HarnessService.java:409-413`
- `backend/src/main/java/cn/etarch/mao/harness/core/AgentLoop.java:416-420`

**问题说明**

历史报告中的“CAS 冲突后继续使用旧请求快照”已经通过调用方无条件重建请求修复。但是 CAS 冲突路径在 `applyHistory` 将 `context.messages` 替换为并发压缩后的“最新摘要 + 边界后消息”后，直接返回 `false`，没有像本次 CAS 成功路径一样清空以下旧锚点：

- `lastPromptTokens`
- `contextAnchorMsgId`
- `messagesCoveredByAnchor`
- 数据库中的 context anchor

这些锚点描述的是重载前的旧消息列表。随后首轮请求虽然已正确重建，但 `AgentLoop.computeActiveTokens()` 仍会把旧 `lastPromptTokens` 当作基数，再基于新消息列表计算后缀，得到不可信的上下文 token 数。业务影响包括：

- 上下文窗口展示可能明显偏大或偏小；
- mid-loop 压缩阈值判断可能错误，导致刚接收并发摘要后又重复触发压缩，或实际接近窗口上限时未及时压缩；
- 错误锚点继续持久化并影响后续请求。

**修复建议**

只要 orchestrator 执行了 `applyHistory` 且重载出的边界/摘要与调用前不同，就应使旧锚点失效，而不应只在本次 CAS 成功时重置。CAS 冲突路径至少应：

1. 清空数据库和 `context` 中的 token anchor；
2. 将 `messagesCoveredByAnchor` 恢复为 `-1`；
3. 使用重建后的最新请求重新计算并保存基线 token；
4. 必要时发送对应的 `context_window` 更新。

也可以让 orchestrator 返回结构化结果，明确告知调用方“上下文已被并发结果重载，需要重建请求并重置锚点”。
