## 中等严重程度

### 1. CLOUD pull 恢复 stash 时未使用 `--index`，会丢失用户原有的暂存状态

**代码位置**

- `backend/src/main/java/cn/etarch/mao/file/service/GitWriteOperationService.java:242-250`

**问题说明**

CLOUD 的 `restoreStash()` 使用：

```text
git stash apply <oid>
```

该命令会恢复文件内容，但不会恢复 stash 中记录的 index 状态。若用户在 pull 前已有已暂存变更，自动 stash 后再成功 pull，恢复出的改动会变成未暂存变更，原本的 staged/unstaged 边界被破坏。

例如：文件 `f` 已执行 `git add f`，随后触发 CLOUD pull。当前实现完成 stash 与恢复后，`git diff --cached` 为空，而 `f` 出现在普通 `git diff` 中。LOCAL 实现使用了 `git stash apply --index <oid>`，因此 CLOUD 与 LOCAL 行为不一致。

这会影响用户后续在终端中继续处理暂存区，也不符合“恢复本次 stash”通常应恢复原工作区状态的业务预期。

**建议修复**

将 CLOUD 恢复命令改为等价的：

```text
git stash apply --index <oid>
```

继续保留现有的冲突检测和“成功应用后按对象 ID 精确删除 stash”逻辑。补充 CLOUD 回归测试，覆盖 pull 前同时存在：

1. 已暂存 tracked 变更；
2. 未暂存 tracked 变更；
3. untracked 文件；

并验证 pull 后三者均恢复，且已暂存文件仍位于 index 中。
