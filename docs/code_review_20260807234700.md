## 一、问题清单

### 【一般】1. 追问「上一轮被取消且从未完成过」的子会话产生连续 USER 消息，触发 LLM 400 风险

- **场景**：delegate 首轮被用户取消 → 子会话历史以孤立 USER 结尾（无任何回复）→ 主代理对同一子会话追问 → 落库追问 USER2 → 历史出现 `[USER1, USER2]` 连续 USER。既有回滚逻辑只覆盖「本次追问产生的消息」，无法清理 delegate 取消遗留的孤立 USER。
- **修复**：落库追问 USER 前，循环删除子会话尾部所有孤立 USER（`messageMapper.selectOne` 取最后一条，`role=USER` 则 `deleteById`），杜绝连续 USER；新增单测 `orphanTrailingUserRemovedBeforeFollowupMessage` 覆盖。

### 【一般偏轻】2. 返回的 `round` 计数包含 CANCELLED/FAILED 记录，追问轮次跳号

- **修复**：响应新增 `completed_rounds` 字段（仅统计 status=COMPLETED），`round` 保持累计执行次数；主代理可区分「有效完成轮次」与「累计尝试次数」。

### 【轻微】1. 管理后台工具名映射未收录 `delegate_followup`

- **处理决定**：**不做**。管理后台零改动是已确认的用户决策（方案文档 7.2），admin 端显示原始英文名可接受。

### 【轻微】2. `getInputSchema` 中 `child_session_id` 来源说明不完整

- **修复**：描述补充「delegate 或上一次 delegate_followup 返回结果的 child_session_id，支持连续多轮追问」。

### 【轻微】3. 执行中取消（非 skip）观感：子代理 Tab 显示 CANCELLED 但消息列表仍是上一轮内容

- **处理决定**：**不做**。前端零改动是已确认决策；取消时审计单独标记 CANCELLED，DB 与前端语义一致。
